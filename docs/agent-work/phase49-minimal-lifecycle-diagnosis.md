## Windows Job Object capability check (synthetic processes only)

Root next asked whether a Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` can bound **owned descendants** in this sandbox. I searched the scoped repo paths for an existing `CreateJobObject`/`AssignProcessToJobObject` helper and found none. This check used inline PowerShell `Add-Type` P/Invoke only; it did not start Convex, push functions, touch temp roots, create files, use network, edit source, or target any preexisting process. All synthetic PowerShell processes were started with `UseShellExecute=false`, `CreateNoWindow=true`, and hidden window style.

The first native setup set extended-limit information but its readback lacked the flag because PowerShell's nested value-type assignment did not marshal as intended; **no child was spawned** in that attempt. The corrected setup wrote `0x2000` at the native extended-limit `LimitFlags` offset and `QueryInformationJobObject` class 9 read it back. `IsProcessInJob(GetCurrentProcess(), NULL)` reported **true** (the shell itself is in a job), yet `AssignProcessToJobObject` accepted the synthetic child in the new job. The child was gated on redirected stdin so it could not spawn a descendant before assignment.

An intermediate attempt assigned synthetic child PID **20676**, released the gate, and observed independently spawned grandchild PID **4392**. A nonessential `QueryInformationJobObject` accounting call (class 8) failed with Win32 error **24** and aborted before the close test; fallback `TerminateJobObject` on the **owned job** was used, and exact-PID readback found both absent. This is a query-marshalling/size limitation of the inline probe, not evidence that job assignment failed.

The final close test gave this closed result:

```json
{"Stage":"complete","CurrentProcessInJob":true,"KillOnCloseReadback":true,"Assigned":true,"AccountingQuery":false,"ActiveProcesses":null,"ChildPid":12552,"GrandchildPid":22440,"CloseHandle":true,"ChildStopped":true,"GrandchildStopped":true,"ErrorCode":null,"FallbackUsed":false,"AccountingError":24}
```

After the gated child spawned grandchild PID **22440**, closing the only owned job handle returned success. Child PID **12552** exited within 5 seconds; the grandchild was absent on immediate follow-up, and a second read-only exact-PID check confirmed both absent. No fallback direct kill or `TerminateJobObject` was used in this successful close test. The accounting query still returned Win32 error 24, so **membership count is not claimed**; the flag readback, successful assignment, and both process exits on close are the supported observations. The intermediate fallback PIDs were also confirmed absent. Every created job handle and unmanaged buffer was closed/freed by the inline probe.

Minimal supported design implication: a bounded, owned job with `KILL_ON_JOB_CLOSE` is available **for this synthetic child/grandchild route even inside the current parent job**. Any future runner integration would have to create and verify the job first, start a gated/suspended owned launcher, assign it before it can spawn descendants, retain the job handle during work, then close it and independently verify exit/listeners/root cleanup. Merely assigning an already-running backend after `spawn` would leave a race for descendants created before assignment. This capability result does **not** prove that Convex creates the historical holder, that its launch pattern will behave identically, or that a job change fixes the 14 empty-root sharing violations. No runner change or backend/push repetition was made here.
