# Phase 50 merchant decision packet — pending

**Reviewed:** 2026-09-27. **Status:** pending remaining provider, legal and operating evidence; this is not ADR-049, adapter authority, merchant approval, or release evidence. Public storefront and live commerce remain closed.

## Locked scope and decision boundary

- Both **Stripe and PayPal** must be available in the first **test-mode** commerce release. Each merchant owns its direct receiving account; Pikar-AI does not pool seller proceeds or reuse its subscription-billing account. A merchant may select one eligible provider; the release itself must qualify both.
- Both **physical and digital goods** are in first-release scope. Physical shipping/returns and digital access, delivery failure, revocation and refunds need separately named authority and test paths; neither path is implicitly supported merely because checkout succeeds.
- Each **merchant sets its own tax, shipping, refund and buyer-retention policies**. Pikar-AI must validate required entries, enforce the recorded version for an order and refuse absent/unsupported configurations; it must not invent platform-wide fallback terms. This does not waive applicable law, provider rules, privacy rights or platform duties, which still need separate review.
- Seller-country reach is targeted at **all countries**, with **USD, EUR and GBP settlement** targeted. Neither statement means every provider/account/country/currency combination is available. Quote/presentment currency and actual receiving/settlement currency are separate facts. Unsupported or unverified combinations must visibly refuse; never silently substitute a provider or currency.
- For the first test-mode release, **all countries remains a long-term target**: enable only provider-verified eligible seller/account/currency combinations and visibly refuse the rest. This is a scope decision, not proof that any particular combination is eligible.
- Each merchant sets a **whole-minute finite-stock checkout hold from 1–60 minutes**; the system rejects longer/partial-minute policies and releases an expired hold. This is the owner's first-test-mode range, not a provider capability statement.
- If payment succeeds after a stock hold has expired and the item is no longer available, **stop the order for merchant review**. No automatic fulfilment or refund occurs. A merchant admin chooses a refund or documented fulfilment alternative and the buyer receives a status notice. The actual review workflow, provider refund permissions, fulfilment constraints and notification delivery still need implementation and verification before activation.
- The current official matrices already disprove universal seller availability: Stripe does not list Tanzania among its supported payment-account countries, while PayPal marks Tanzania **send only** for its partner seller-onboarding flows. Keep the all-country target visible as an unmet target, not a launch claim; no alternative account location or payout product is presumed equivalent to a Tanzania merchant-owned direct receiving account.
- `pikar-ai` is a provisional name. Registered legal-entity details are pending. No provider application, credentials, live charge, or public opening follows from this packet.

### 2026-09-25 flow review

For PayPal, [its current onboarding comparison](https://developer.paypal.com/platforms/seller-onboarding) recommends **before-payment** onboarding, supports PayPal Checkout for eligible personal or business accounts, and requires onboarding and email confirmation before processing. The **after-payment** flow instead requires a business account and excludes authorization payments; [PayPal's partner Checkout guide](https://developer.paypal.com/platforms/checkout/standard/integrate) requires approved-partner status and seller onboarding. Before-payment onboarding plus PayPal Checkout is therefore the candidate for the first test-mode shop. This is a technical inference from the documented options, not evidence of Pikar-AI partner approval or a final account/country/currency matrix. Keep after-payment and Expanded Checkout out of the first adapter unless a separately reviewed decision and capability evidence add them. The adapter entry gate must prove the actual seller's completed onboarding, confirmed email, granted `PAYMENT`/`REFUND` features as applicable, and server-side seller identity before checkout; a browser return alone cannot do that.

For Stripe, [the current Standard-account page](https://docs.stripe.com/connect/standard-accounts) labels its account-type instructions as legacy and directs new platforms to Accounts v2; OAuth remains documented for an extension accessing an existing account. [Direct charges](https://docs.stripe.com/connect/direct-charges?platform=web&ui=stripe-hosted) place PaymentIntents and Charges on the connected account, requiring account-scoped retrieval. The candidate is Accounts v2 connected-account onboarding with hosted Checkout direct charges, subject to confirming that the chosen account configuration permits the merchant-owned receiving account and required operations. Do not substitute legacy Standard creation or OAuth merely because the merchant owns the account. Stripe's onboarding return indicates exit from the flow, not charge readiness; the chosen configuration needs a server-side status and capability readback.

### 2026-09-26 PayPal browser-SDK generation check

The [current PayPal partner Standard Checkout guide](https://developer.paypal.com/platforms/checkout/standard/integrate) was updated 2026-09-11. Its merchant-ID/partner-attribution browser sample uses JavaScript SDK **v5**, which remains supported, but the page directs **new integrations to v6**. The [v6 setup guide](https://developer.paypal.com/sdk/js/set-up/) documents a different script, initialization and `createOrder` return shape. The partner v5 example therefore cannot silently define a new Pikar-AI browser implementation. Before Plan 50-08, record `providers.paypal.buyerSdkGeneration` as `javascript-sdk-v6` or an explicitly justified `javascript-sdk-v5` exception, and separately evidence `buyerSdkMerchantBinding` for the selected SDK, platform REST app and exact seller ID. A v6 preference is an inference from PayPal's new-integration guidance, **not** proof that Pikar-AI's partner account or chosen seller flow supports it. If v6 merchant binding is unavailable and a v5 exception is not evidenced, the PayPal adapter remains blocked. The server-side merchant assertion, grant, Orders API and exact-account read/refund remain separate gates.

Recheck provider documentation and actual account/partner capability immediately before either adapter. Public docs are not account approval. Do not copy the app OpenRouter key or merchant secrets into this packet.
