<interfaces>
Use `callbacks.createOrUpdateUser`, not `afterUserCreatedOrUpdated`. The pinned
`@convex-dev/auth@0.0.94` invokes it before account/session creation inside one `auth:store`
mutation. Throwing rolls the transaction back.

Convex Auth strips the provider profile's `id` before the callback. Both OAuth provider profile
mappers must therefore return `id: p.sub` and a second non-id field such as `oauthSubject: p.sub`;
the callback strips that helper before writing the `users` row.

Email is the first-redemption matching key only. Normalize with trim + lowercase. For Microsoft,
use `email ?? preferred_username` and reject `INVITE_NO_EMAIL` if neither exists. The persisted
authorization root is `${provider.id}|${oauthSubject}`. Do not use Entra `oid` and do not assert an
exact Entra subject length.

OAuth cannot carry the typed invite code through Convex Auth; a matching provider-verified email is
the gate. Password email is self-asserted, so credentials admission requires both matching email and
the exact code carried by the existing Password profile mapper.
</interfaces>

  <name>Task 1: Define the admission rows and owner-gated issuance</name>
  <files>packages/backend/convex/schema.ts, packages/backend/convex/invites.ts, packages/backend/convex/invites.test.ts</files>
  <behavior>
    - A public waitlist request stores normalized email, optional bounded name/referral text, status `pending`, and timestamps without creating a user or tenant.
    - Repeating the same normalized email is idempotent and does not mint codes.
    - Only `ownerMutation` can approve a pending row; approval mints one cryptographically random, high-entropy code and one invite, then marks the waitlist row approved.
    - Approval replay returns the existing invite rather than minting another live code.
    - Public preflight accepts a code and returns only `{valid, invitedEmailMasked}`; it never returns another invite, redemption subject, user id, or raw waitlist data.
    - A non-owner approval rejects with `OWNER_REQUIRED` and leaves row counts and statuses byte-unchanged.
  </behavior>
  <action>

    that can contain tenant-owned data must lead with `tenantId`; admission rows that deliberately
    precede a tenant must be classified and justified as auth-plane exceptions in Plan 03. Keep the
    schema minimal: normalized email, status, code digest or code as required by the existing link
    UX, redemption subject/user/timestamp fields, created/approved timestamps, and refs/counts-safe
    provenance only. Never put a raw invite code in audit payloads.

    Implement the public waitlist/preflight functions using the project's explicit public-function
    allowlist pattern and the approval/list functions with `ownerMutation`/`ownerQuery`. Reuse Web
    Crypto already available in the runtime; add no package. Keep issuance idempotent under retries.
    Write the tests first and use one convex-test harness where possible to avoid the known shared
