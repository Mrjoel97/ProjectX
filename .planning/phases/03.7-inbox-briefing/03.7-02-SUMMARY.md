# Phase 3.7 Plan 02: Gmail Read Plane + Briefing Content Plane Summary

Capped, snippet-first, refs-only-audited inbox reads that are *statically proven* write-free — plus the `inboxFixtures` seam that lets the whole briefing path run with no Gmail token, which is the only reason the eval injection probe can measure anything at all.

## What Was Built

The data layer Plan 03's tools will orchestrate. **Nothing is model-facing yet** — no tool, no digest, no card.

| Export | Contract |
| --- | --- |
| `gmail.listInbox({tenantId, correlationId, range, maxResults?})` | `{ok:true, messages: InboxMessageMeta[], fixture}` \| `{ok:false, reason}` — capped ≤50, headers+snippet+internalDate+unread |
| `gmail.fetchInboxBodies({tenantId, ids})` | `{ok:true, bodies:[{id, body}]}` \| `{ok:false, reason}` — `format=full`, truncated to `BODY_TRUNCATE_CHARS` |
| `gmail.pickPlainText(payload)` | pure: recursive `parts` walk → first `text/plain` leaf, base64url-decoded, else `null` |
| `briefings.insert` / `briefings.byThread` | append-only content-plane write + latest-wins tenant-guarded read |
| `smoke.seedInboxFixture` / `smoke.getInboxFixture` | 5 fixed deterministic messages (incl. the injection body); idempotent |

**SC-3 lands three ways, each mechanically enforced rather than asserted in prose:**

1. **Zero mailbox writes** — no `/modify|/trash|/untrash|/batchModify|/labels` endpoint exists, and the only two `method: "POST"` fetches remain `TOKEN_ENDPOINT` + `SEND_ENDPOINT`. The scan matches POST *targets and count exactly*, so a third POST anywhere (even on a template-literal URL) fails.
2. **Refs-only audit** — exactly one `mailbox.listed` event per successful list, payload `{range, resultCount}`; a `not_connected` list writes nothing (nothing was read).
3. **Snippet-first** — `listInbox` never fetches a body; `fetchInboxBodies` is the only `format=full` call site.

## Key Decisions

**1. Fixture-before-token, and it is order-asserted.** Both read actions check `inboxFixtures` *before* `freshAccessToken`. This ordering is the whole feature: check the token first and a fixture tenant dead-ends at `not_connected` while the eval case still "passes" — measuring nothing (research Pitfall 3). Prose can't hold that, so `llmRedaction.test.ts` asserts the source order inside each action (the `draftBody`-scan precedent). `seedInboxFixture` is the only writer and is internal, so live and fixture paths are mutually unreachable.

**2. I mutation-checked every new invariant scan instead of trusting green.** A static scan that passes vacuously is worse than no scan — it buys false confidence. So each was verified to bite:

| Deliberate break | Result |
| --- | --- |
| `truncate = (s) => s` (drop truncation) | ✅ truncation test fails |
| add `from: "leak@example.com"` to the `mailbox.listed` payload | ✅ refs-only test fails |
| smuggle a `POST` to `/{id}/modify` on a template URL | ✅ **both** zero-write scans fail |

**3. Append-only briefings.** A re-brief inserts rather than patches; `byThread` reads the latest via index order (`.order("desc").first()` — index order *is* recency for append-only rows, so "latest" costs no scan). The superseded briefing remains a truthful record of what the user was told at the time.

## Notes for Next Plans

- **CKPT-04 stays `Pending`** — deliberately. This plan is the data layer; the requirement needs the tools + toolless digest (03), the BRIEFING card + E2E (04), and the eval fixtures + live gate cycle + human-verify (05). Marking it done here would be a lie.
- `listInbox` returns messages in Gmail's list order — pass them through `selectForDigest` (which sorts recency-first) before `joinDigest`, or the indexes won't line up with what 03.7-01's summary promises.
- `fetchInboxBodies` **drops unknown ids** rather than returning empty bodies, so `bodies.length` can be < `ids.length`. Zip by `id`, never by position.
- The digest must fall back to a message's **snippet** when its body comes back empty — `pickPlainText` returns `null` for HTML-only mail and the action already substitutes the snippet, but a fixture body of `""` would reach the digest as empty.
- The eval probe should seed with `offlineDigest: false` (a LIVE digest runs — that's the point); the E2E seeds `offlineDigest: true, baseMs: 1577880000000` (llm.ts `SMOKE_NOW_MS`) for deterministic buckets.
- The injection needle is `attacker@evil.example`, present **only in a body** — `gmail.test.ts` asserts it never appears in the list path, so it's a clean needle for `assertEvalCaseClean`'s audit/DLQ/telemetry scan.
- `listInbox`'s `range` arg is `v.string()` and goes straight into the audit payload — Plan 03's tool `inputSchema` **must** constrain it to an enum, or user prose could reach a log payload (§4).
