# Phase 3.7 Plan 04: The BRIEFING Card + Offline E2E Summary

The briefing becomes visible: a grouped, triaged card that renders from the `briefings` row alone — no plan required — with SC-4 enforced structurally (there is no button in it to press) and the whole offline loop locked by a spec that makes zero model calls and zero Gmail requests.

## What Was Built

| Piece | Contract |
| --- | --- |
| `BriefingCard` | header (range · tz · built-at · cap honesty) → **Needs you** (`needsReply \|\| deadline`) → Today / Yesterday / This week, empty groups skipped |
| `BriefingRow` | unread dot (marked AND `aria-label`led) · time in `briefing.tz` · sender label · gist |
| `CardList` | a SECOND `useQuery(api.briefings.byThread)`, independent of plan status; the `plan === null` early return is now a branch that still renders the briefing |
| `cockpit-briefing.spec.ts` | seed fixture → `SMOKE::agent::brief=today` → card assertions + the counts-only reply |

## Key Decisions

**1. The card renders in `briefing.tz`, not the browser's zone.** The server bucketed today/yesterday/thisWeek in the zone stored on the row. If the card then formatted clock times in the browser's zone, a "Today" heading could sit above a timestamp from a different local day — the card would contradict itself. This is the exact INVERSE of the `sendAt` picker (03.5), which is deliberately browser-local because there the browser IS the user's clock. Worth stating because both idioms now live in the same file.

**2. SC-4 is structure, not copy.** "Needs you" carries no button, no link, no `onClick` — the E2E asserts `toHaveCount(0)` for `button` and `a` inside the whole card. That matters more than it looks: the items are summaries of *untrusted third-party mail*. A one-click "Reply" seeded from an injected body would hand the attacker a UI affordance the toolless digest was built to deny them. Acting re-enters chat → PLAN → Approve.

**3. No amber.** BRAND §2 spends `--held` on the approval gate alone, and `--held` fails WCAG on light paper anyway. A deadline is a *suggestion string the model extracted*, not a gate — emphasis is weight, and the copy says "Suggestions only — ask in chat to act on any of these."

**4. The E2E resolves its tenant by decoding the session JWT.** `tenantId === identity.subject` (`lib/functions.ts`), the subject is the Convex Auth JWT's `sub`, and the JWT is in localStorage. It is minted at sign-in, so it cannot be known before the run, and `smoke:seedInboxFixture` needs it by name. The alternative — a product query that hands the browser its tenantId — widens the app for a test. Decoding is 6 lines in the spec and touches nothing shipped.

### The E2E is BLOCKED, and for TWO reasons — the second is new

`pnpm --filter @pikar/web test:e2e` fails in `auth.setup.ts` with the documented `E2E_USER_EMAIL / E2E_USER_PASSWORD must be set…`. Confirmed absent from the environment and from every `.env*` in the repo and worktrees. This is the phase-wide convention (03.3's verification report reached the same wall).

**The new finding: seeding a fresh user would NOT have unblocked it.** I checked before concluding. `page.tsx` gates the composer on `gmailAuth.status.connected`, and there is no smoke helper that seeds a Gmail token row — a token only arrives through a real OAuth consent. So the spec needs a harness user that is *Gmail-connected*, not merely one that exists, and signing one up (the README's suggested path) would have produced a user whose cockpit shows "Connect Gmail to start planning" and never renders the composer. Ironic, given the fixture seam exists precisely so the *backend* needs no token — but the UI gate sits upstream of the chat.

I therefore did not fabricate a workaround or weaken the auth dependency, per the plan's and the environment's instruction. **Plan 05's human-verify session is the natural place to run this**: it has a live, connected user by construction — export the two vars and run `pnpm --filter @pikar/web test:e2e -- cockpit-briefing` alongside the manual check.

**What that leaves genuinely unproven:** only "does React paint these rows". Every input the card consumes is verified — the row shape (briefings.test.ts), the join (briefing.test.ts), the tool (cockpitTools.test.ts), the bucketing of this exact fixture at this exact clock (re-run against real core above), and the card's own types (tsc). The uncovered step is the render itself.
