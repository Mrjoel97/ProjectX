# Phase 3.7 Plan 01: Pure Briefing Module Summary

Timezone-correct day bucketing, recency-first digest selection under the body cap, and the index-join that makes it structurally impossible for the model to own a timestamp, sender, or bucket — pure, dependency-free, and TDD'd against fixed clocks east and west of UTC.

## What Was Built

`packages/core/src/briefing.ts` — the Phase 3.7 foundation. Nothing consumes it yet; the tools, digest action, table, and card land in later plans.

| Export | Contract |
| --- | --- |
| `dayKey(ms, tz)` | `"YYYY-MM-DD"` in an IANA zone via `Intl.DateTimeFormat("en-CA")` |
| `bucket(msgTsMs, nowMs, tz)` | `"today" \| "yesterday" \| "thisWeek" \| null` (null = outside the 7-day window) |
| `selectForDigest(messages, cap = 25)` | recency-first, capped, non-mutating |
| `joinDigest(selected, items, nowMs, tz)` | welds model gists onto code-owned sender/ts/bucket by index |
| `BRIEFING_BODY_CAP` / `BODY_TRUNCATE_CHARS` | `25` / `2000` |

This lands SC-1's locked decision (ADR-004): **time grouping is pure code, never LLM output.** The digest schema is index-keyed and carries no `sender`/`ts`/`bucket` field at all, and `joinDigest` reads those exclusively from the fetched message — so a model that emits `sender: "attacker@evil.example"` is ignored, and a model that invents index `99` produces nothing. That is asserted directly by two tests.

## Key Decisions

**1. The DST-proof yesterday derivation (the one real design choice).** The research left this open (Open Question 4: "two pure implementations noted — pick one"). I picked the UTC-math derivation over the naive `dayKey(now - 86400000)` and proved the difference rather than asserting it:

```
LA, now = 2026-03-09T07:30Z (00:30 local, the day after spring-forward)
  naive dayKey(now - 86_400_000) → "2026-03-07"   ← skips a whole calendar day
  previousDayKey(dayKey(now))    → "2026-03-08"   ← correct
```

The day after a spring-forward is only 23 local hours long, so "24h ago" from just after local midnight lands two calendar days back — a message from yesterday afternoon would silently show up under "this week". The regression test pins the naive value explicitly (`expect(dayKey(now - 86_400_000, LA)).toBe("2026-03-07")`), so the test fails loudly if anyone ever "simplifies" the derivation back. The research called this an "acceptable ceiling"; it costs 3 lines to close, so I closed it.

**2. Future-dated messages bucket as `today`** (per plan). Marked `ponytail:` — a skewed sender clock makes it the newest thing in the mailbox, so burying it is the surprising outcome. The test uses `now + 30h` (a later *local* day) so it genuinely exercises the clamp rather than passing incidentally.

**3. Duplicate-index drop** — beyond the plan's letter (which named only out-of-range). Two digest items claiming index 0 would otherwise produce two briefing rows for one email. Same invariant, same one-line `Set` guard.

## Notes for Next Plans

- `joinDigest` expects the digest items' `index` to address `selectForDigest`'s output **in its returned order** — pass the model the selected array in that exact order and it lines up for free.
- The digest schema in `llm.ts` must be `{ index, gist, category, needsReply, deadline? }` with **no** `sender`/`ts`/`bucket` — adding them back would reopen ADR-004 (and `joinDigest` would ignore them anyway).
- `bucket()` returning `null` is a real case the caller must handle: `joinDigest` already drops those rows, so `items.length` and the briefing row count legitimately differ. The card's "summarized N of M" cap-honesty line should read `listedCount`, not the digest length.
- Missing `clientContext` → pass `"UTC"` (the documented `buildAgentContext` default); briefing is read-only, so a zone miss is cosmetic.
