# Phase 3.5: Deferred Send - Context

**Gathered:** 2026-07-14
**Status:** Ready for planning

<domain>
## Phase Boundary

A cockpit plan can carry an OPTIONAL future send time (Tier 1 / SCHD-01). The guided
conversation accepts a natural-language time; the PLAN card shows the resolved absolute time
(user's timezone) before the single Approve; Approve **schedules** (never immediately starts)
the existing `deliverApprovedPlan` fan-out via Convex's built-in scheduler (`runAt`); the plan
is cancellable any time before it fires. No time given → immediate send on Approve (today's
behavior, the unchanged default). This composes onto the plan/approve/execute spine — it does
NOT change the send mechanics.

Out of scope: recurring / standing-instruction sends (Tier 2 — deferred to post-Phase-9, see
`.planning/design/scheduled-send.md`).
</domain>

<decisions>
## Implementation Decisions

### Time intake (natural-language + picker)
- BOTH paths, one source of truth (the plan row's single nullable absolute-time field):
  1. **Natural-language is the fast path** — the agent parses the time from chat ("send at 4pm
     tomorrow", "Monday 9am") through the existing governed tool-loop and sets the time.
  2. **A date/time picker on the PLAN card is the precise correction** — the card renders the
     resolved absolute time as an editable picker the user can nudge and **confirm** before
     Approve. The picker ADJUSTS/CONFIRMS the parsed time; it is not an independent input path
     the agent is unaware of.
- Locked (design doc): timezone captured client-side; the stored value is an absolute epoch ms.

### Scheduled-state UI (distinct card)
- After Approve, a **distinct SCHEDULED card state** replaces the PLAN card: "Scheduled for
  <absolute time, user timezone> · Cancel". Mirrors the existing status-driven card dispatch
  (PLAN / DRAFT / REPORT / RESOLUTION). When it fires, the card transitions to REPORT (the
  existing live per-recipient projection).
- The Cancel control lives on this SCHEDULED card.

### Ambiguity & bounds
- A resolved time in the **past or effectively now → re-ask** ("that time has passed — when did
  you mean?"), never silently sent. Same rule as recipient ambiguity: re-ask, never guess.
- Ambiguous natural-language ("4 AM" with no day / no timezone) → re-ask, never guess (design doc).
- **No far-future cap** for slice 1 (a cap is a Tier-2 concern where token-expiry matters).

### Cancel semantics
- Cancel moves the plan to a **terminal `canceled` state** (audited — the halt-control promise).
  The card shows "Canceled." To send again, the user starts a new request (no re-schedule /
  re-approve of a canceled plan in slice 1).

### Failure at fire time (locked, design doc)
- Identical to immediate sends: an expired token lands `awaiting_reauth` + notification; never a
  silent loss, never an unaudited retry. Audit/telemetry/DLQ/reauth reused verbatim.

### Claude's Discretion
- Exact picker widget (native `<input type="datetime-local">` vs a small custom control) and its
  styling — reuse existing tokens; no new component library.
- Whether Cancel needs a confirm click vs a single click (lean single-click; it is reversible-by-
  re-sending, not destructive of sent mail).
- The exact scheduling primitive (`ctx.scheduler.runAt` on an internal mutation that starts the
  workflow, vs the workflow component's own delay) — planner/researcher choose, preserving the
  single `workflow.start(deliverApprovedPlan)` call-site invariant.
- Natural-language time parsing approach (agent tool + a pure parser vs a library) — keep it
  deterministic/testable per the ponytail rung; no heavy new dependency if avoidable.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `plans` table + PINNED status enum (`collecting → proposed → approved → delivering → done`,
  schema.ts): add ONE nullable absolute-time field (append-only optional field, same discipline
  as `recipientBodies`/`attachments`) + the new terminal `canceled` state (and a `scheduled`
  state for the post-Approve-pre-fire window). No migration.
- `executePlan` (cockpit.ts) — the human approve gate + the SOLE `workflow.start(deliverApprovedPlan)`
  call site: this is where "schedule instead of start" branches on the presence of a send time.
- `buildCockpitTools` / `runCockpitAgent` (llm.ts) — the governed agent tool-loop: a `setSendTime`
  tool (parse NL → absolute epoch ms, re-ask on ambiguity/past) mirrors `setSubject`;
  `buildAgentContext` surfaces the scheduled time so the agent reasons about it.
- `cards.tsx` — status-driven card dispatch (`CardList` switch): add a `ScheduledCard` (Scheduled-
  for + editable picker + Cancel), reusing the PlanCard chip/label/dim tokens.
- Audit spine: `audit.log` refs-only (§4) — a `plan.scheduled` and `plan.canceled` audit event
  (ids/counts/hashes only, never raw content).
- `deliverApprovedPlan` fan-out + `reportForPlan` live projection — reused verbatim once the
  scheduled workflow fires.

### Established Patterns
- Append-only optional field on `plans` (no migration) — the Tier-1-compatibility rule (one
  nullable absolute-time field) fits this exactly.
- Single `workflow.start` call site is a grep-verified invariant — scheduling must WRAP it (a
  scheduled internal function starts the workflow at fire time), not add a second call site.
- Content-plane vs log-plane separation (§4) — the send time is content-plane; audit carries
  refs/counts only.

### Integration Points
- `executePlan`: branch on send-time presence → `ctx.scheduler.runAt(fireTime, internal.…startFanout)`
  vs the immediate `workflow.start`; capture the scheduled function id on the plan row for Cancel.
- New `cancelScheduledPlan` tenantMutation: `ctx.scheduler.cancel(id)` + status → `canceled` +
  audit; guarded on tenant + only-if-not-yet-fired.
- Picker → a tenantAction/mutation patching the absolute-time field (client passes the resolved
  epoch ms + timezone).

</code_context>

<specifics>
## Specific Ideas

- "Scheduled for …" + Cancel is the PROJECT.md halt-control promise applied to *time* — the
  cancel path is a hard requirement, not a nice-to-have.
- The picker is the precise correction on top of the conversational parse — NL gets you 90% there
  fast, the picker confirms the exact minute before you approve.

</specifics>

<deferred>
## Deferred Ideas

- Recurring / standing-instruction sends ("every day at 8 AM") — Tier 2, explicitly out of v1
  (Gmail Testing-mode 7-day token expiry + the unmade approve-template-vs-re-draft governance
  decision). Design constraints recorded in `.planning/design/scheduled-send.md`.
- Far-future scheduling cap / token-expiry mitigation — noted, not built in slice 1.
- Re-scheduling a canceled plan (edit + re-approve) — slice 1 is terminal-canceled; revisit if
  beta users ask.

</deferred>
