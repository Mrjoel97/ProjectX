# Phase 03.5 Plan 06: Far-Future Scheduling Cap Summary

A send can no longer be scheduled so far out the Gmail OAuth token is dead by fire time. The authoritative guard is a refusal in `executePlan` — the one schedule-vs-immediate chokepoint — so it covers every write path (NL tool, picker, Plan 05 reschedule) at once; a pure-parser `tooFar` variant + a `setSendTime` re-ask + native picker `max` caps are the soft, fail-fast complements. The horizon is one exported constant (`SEND_TIME_HORIZON_MS`, default 7d = Gmail Testing-mode refresh-token life) shared by all four seams.

## What was built

**Task 1 — `SEND_TIME_HORIZON_MS` + `tooFar` in the pure parser (emailIntent.ts, `59de0a5`)**
Added the exported `SEND_TIME_HORIZON_MS = 7*24*60*60*1000` next to `SEND_TIME_EPSILON_MS` with a ponytail comment naming the ceiling (Gmail Testing-mode 7-day refresh-token expiry, `design/scheduled-send.md`) and upgrade path (raise/remove post verified-OAuth). Added `| { kind: "tooFar" }` to `SendTimeParse`, and factored `classify(epochMs, nowMs)` → past (≤ now+epsilon) | tooFar (> now+horizon) | resolved, replacing the three duplicated `epochMs <= now+EPSILON ? past : resolved` returns (relative / day-anchor / no-day PM) so all three share the same two bounds. Pure — no `Date.now`. Five new colocated tests (169h → tooFar; 167h → resolved; 168h boundary → resolved inclusive; the horizon-value assertion; a within-horizon no-regression). `pnpm --filter @pikar/core test emailIntent` 39/39 green (RED confirmed first — the constant was `undefined` → `NaN`).

**Task 2 — `executePlan` far-future refusal (cockpit.ts, `bf97a61`)**
Imported `SEND_TIME_HORIZON_MS`, extended the return union's reason to `"gmail_not_connected" | "send_time_too_far"`, and added an early guard right after the token check and before the CAS flip: `if (plan.sendAt !== undefined && plan.sendAt > Date.now() + SEND_TIME_HORIZON_MS) return { ok: false, reason: "send_time_too_far" };`. Fail-before-mutate — no seed, no status flip, no arm — mirroring the `gmail_not_connected` guard. The existing `> Date.now()` schedule/immediate branch is untouched (it only ever sees an in-window `sendAt` now). One new `cockpit.test.ts` case (fake timers + `seedSchedulable`): a `now + horizon + 1hr` plan → `{ok:false, reason:"send_time_too_far"}` + status still `proposed` + zero requests rows + zero scheduled rows, plus a within-horizon control (`now + 1hr` → scheduled). Full cockpit suite 72/72 green (including the sometimes-flaky `runCockpitAgent.test.ts`, which passed here under lighter load).

**Task 3 — `setSendTime` re-ask + picker caps + playbook (llm.ts / cards.tsx / cockpitTools.test.ts / cockpit.md, `b163dfc`)**
`setSendTime` gained `case "tooFar"` (re-ask: "further out than I can reliably schedule — the connection may expire before then; ask the user for a sooner time. Nothing was scheduled.", no `patchPlan`), and the catch-all `default: // "none"` became an explicit `case "none":` — the switch is now exhaustive over `SendTimeParse`, so a future variant is a TS error rather than a silent fall-through to immediate send. `cards.tsx` imported `SEND_TIME_HORIZON_MS` and added `max={toLocalInputValue(Date.now() + SEND_TIME_HORIZON_MS)}` to BOTH the PLAN-card picker and the CanceledCard picker (added by Plan 05) — one shared constant, both seams. New `cockpitTools.test.ts` case drives "in 169 hours" through the pinned-clock shim → asserts the re-ask string + `sendAt` still undefined (no write). `cockpit.md` gained the far-future-refusal invariant and a new `Last verified: 03.5-06` block. Verify: cockpitTools 38/38, `pnpm --filter web typecheck` exit 0, `check-playbooks` exit 0.
