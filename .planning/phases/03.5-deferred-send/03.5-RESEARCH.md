## Summary

Deferred send is a **thin time-branch over an already-complete spine**. The cockpit already: fills a `plans` row through a governed agent tool-loop, proposes it (`proposed`), gates approval at `executePlan` (the SOLE `workflow.start(deliverApprovedPlan)` call site — `cockpit.ts:268`), seeds one `requests` row per recipient with a server-minted `correlationId`, and fans out a governed per-recipient send whose `awaiting_reauth`/DLQ/telemetry paths already exist (`deliverApprovedPlan.ts`, `gmail.ts:150-157`). Phase 3.5 adds exactly: **one nullable epoch-ms field, two PINNED status states, one scheduled-fn-id field, one `executePlan` branch, one scheduled internal mutation, one cancel mutation, one agent tool, one pure parser, one picker, and one card.**

The Convex scheduler is the whole engine and it is **already used in this repo** — `review.ts:63` calls `ctx.scheduler.runAfter(...)` and `review.ts:116` calls `ctx.scheduler.cancel(row.scheduledId as Id<"_scheduled_functions">)`. `runAt(timestampMs, internal.fn, args)` returns an `Id<"_scheduled_functions">`; `cancel(id)` un-schedules it. No version bump, no new dependency (CLAUDE.md §6/§8). The pinned `convex@1.42.1` ships this API.

**Primary recommendation:** Freeze content at Approve (seed `requests` rows exactly as today), then branch `executePlan`: if `plan.sendAt` is a valid future time → `ctx.scheduler.runAt(sendAt, internal.cockpit.startScheduledDelivery, {...})`, set status `scheduled`, store the returned id; else → today's immediate path. Extract the one `workflow.start` into a shared plain helper `startFanout(ctx, ...)` that BOTH the immediate path and the scheduled internal mutation call — the grep-able single-call-site invariant is preserved. Cancel is a CAS-guarded `tenantMutation` that calls `ctx.scheduler.cancel` + flips to `canceled` + writes a refs-only `plan.canceled` audit. Parse time with a pure, deterministic `@pikar/core` function `(text, nowMs, ianaTz) → resolved | ambiguous | past | none`; the picker is the confirm-source-of-truth writing the same `plan.sendAt`.

### Pattern 1: Schema — one nullable epoch field + scheduled-fn id + two PINNED status states (append-only)
**What:** Follow the exact append-only optional-field discipline used for `recipientBodies`/`attachments`/`greetingName` (no migration).
**Where:** `schema.ts` `plans` table (`schema.ts:133-194`) and mirror the status union in `plans.ts:17-23`.
```typescript
// schema.ts plans.status — APPEND the two states (never reorder existing literals — shared singleton, PARALLELIZATION.md):
status: v.union(
  v.literal("collecting"),
  v.literal("proposed"),
  v.literal("approved"),
  v.literal("scheduled"),   // NEW: approved + a future sendAt; scheduler armed, nothing sent
  v.literal("delivering"),
  v.literal("done"),
  v.literal("canceled"),    // NEW: terminal — scheduled send halted before fire (audited)
),
// ...and, alongside the existing optional slot fields:
sendAt: v.optional(v.number()),                               // absolute epoch ms — the ONE source of truth (nullable = immediate)
scheduledFunctionId: v.optional(v.id("_scheduled_functions")),// the scheduler handle to cancel (mirrors pendingTimeouts.scheduledId)
```
**Lifecycle:** `collecting → proposed → approved → (scheduled | delivering) → done`, plus `scheduled → delivering` (at fire) and `scheduled → canceled` (halt).
**Note:** `plans.ts:17-23`'s `PLAN_STATUS` union is a hand-maintained mirror — it MUST gain the same two literals or `setPlanStatus`/`patchPlan` reject them.

### Pattern 2: `executePlan` branch + the single-call-site helper (preserve the grep invariant)
**What:** A mutation cannot lexically share a `workflow.start` call across two entry points, but it CAN call a plain async helper. Extract the sole `workflow.start` into `startFanout(ctx, ...)`; both the immediate branch and the scheduled internal mutation call it → `git grep 'workflow.start('` still returns exactly one hit.
```typescript
// cockpit.ts — the SOLE workflow.start call site (plain helper, not a Convex fn).
// ctx is a mutation ctx (GenericMutationCtx) — workflow.start works here exactly as today (cockpit.ts:268).
async function startFanout(ctx, { planId, tenantId, requestIds, correlationIds, planCid }) {
  const workflowId = await workflow.start(
    ctx, internal.deliverApprovedPlan.deliverApprovedPlan,
    { planId, tenantId, requestIds, correlationIds },
    { onComplete: internal.deadLetter.onPipelineComplete,
      context: { tenantId, correlationId: planCid, payload: { planId } } }, // refs only (§4)
  );
  await ctx.db.patch(planId, { status: "delivering", correlationId: planCid, workflowId });
}

// executePlan, AFTER the CAS + token check + the UNCHANGED seed loop (attachments + requests rows,
// each with its own server-minted correlationId — content frozen at approval, key question #3):
const planCid = crypto.randomUUID();
const args = { planId, tenantId: ctx.tenantId, requestIds, correlationIds, planCid };
if (plan.sendAt !== undefined && plan.sendAt > Date.now()) {
  const scheduledFunctionId = await ctx.scheduler.runAt(
    plan.sendAt, internal.cockpit.startScheduledDelivery, args,
  );
  await ctx.db.patch(planId, { status: "scheduled", scheduledFunctionId });
  return { ok: true, scheduled: true };
}
await startFanout(ctx, args);            // immediate — synchronous, behavior-identical to today
return { ok: true };

// The scheduled callback — an internalMutation that only STARTS the frozen fan-out (single call site holds).
export const startScheduledDelivery = internalMutation({
  args: { planId: v.id("plans"), tenantId: v.string(), requestIds: v.array(v.id("requests")),
          correlationIds: v.array(v.string()), planCid: v.string() },
  handler: async (ctx, a) => { await startFanout(ctx, a); },
});
```
**When to use:** always — this is the phase's structural core.
**Why seed at Approve (key question #3):** the design's "approve once" = freeze content at approval. Seeding `requests` rows + materializing attachments at Approve (today's `executePlan:229-265`, unchanged) means the scheduled fn only starts the fan-out — per-recipient `correlationId`, the shared subject/body/attachment fan-out, and the redaction spine are all minted/frozen at the moment the user approved, and the fire is a pure trigger. This keeps the single `workflow.start` call site and the per-recipient-cid isolation intact.

### Pattern 3: SC4 is free — the scheduled fn starts the SAME workflow
**What:** Because `startScheduledDelivery` → `startFanout` → the SAME `internal.deliverApprovedPlan.deliverApprovedPlan`, a dead token at fire time flows through the identical `gmail.send` branch: `freshAccessToken` fails → `pipeline.setStatus{awaiting_reauth}` + `return {delivered:false}` (`gmail.ts:150-157`); the fan-out `continue`s (`deliverApprovedPlan.ts:38`); DLQ/telemetry/onComplete are byte-identical. **No new failure code.** SC4's "+ notification exactly like an immediate send" means: whatever the immediate cockpit send produces on a dead token, the deferred send produces identically — verify the immediate behavior once and the deferred path inherits it.

### Pattern 4: Cancel — CAS-guarded, `scheduler.cancel`, refs-only audit
**What:** A `tenantMutation` that is idempotent (cancel-once) and never sends.
```typescript
export const cancelScheduledPlan = tenantMutation({
  args: { planId: v.id("plans") },
  handler: async (ctx, { planId }) => {
    const plan = await ctx.db.get(planId);
    if (!plan || plan.tenantId !== ctx.tenantId) throw new Error("plan not found"); // no cross-tenant
    if (plan.status !== "scheduled") return { ok: true, alreadyResolved: true };   // CAS: cancel-once; already fired → no-op
    // Convex mutations are serializable; status==="scheduled" ⇒ startScheduledDelivery has NOT committed
    // (it flips status→delivering as its first act), so cancel targets a still-pending fn and cannot throw.
    if (plan.scheduledFunctionId) await ctx.scheduler.cancel(plan.scheduledFunctionId);
    await ctx.db.patch(planId, { status: "canceled" });
    await ctx.runMutation(internal.audit.log, {                 // mutation→runMutation is valid (deadLetter.ts:43)
      tenantId: ctx.tenantId, correlationId: plan.correlationId ?? String(planId),
      eventType: "plan.canceled", actor: ctx.tenantId,
      payload: { planId },                                       // refs only — never subject/body/recipients (§4)
    });
    return { ok: true, canceled: true };
  },
});
```
**Critical (verified against docs):** `ctx.scheduler.cancel` **throws** if the target has already committed/completed. The CAS on `status === "scheduled"` is the guard that guarantees we never call `cancel` on an already-run fn (serializability + startScheduledDelivery flipping status first). Ponytail ceiling: a defensive `try/catch` around `cancel` is optional belt-and-suspenders; the CAS is the real invariant.

### Pattern 5: `setSendTime` tool + the pure parser (mirror `setSubject`/`draftBody`)
**What:** A governed tool in `buildCockpitTools` (`llm.ts:509+`) that calls the pure parser and writes `plan.sendAt` (or re-asks). The parser is pure and lives in `@pikar/core`.
```typescript
// packages/core/src/emailIntent.ts (append; already watch-registered — watch.json line 14)
export type SendTimeParse =
  | { kind: "resolved"; epochMs: number }
  | { kind: "ambiguous" }   // e.g. "4am" with no am/pm-vs-day anchor → RE-ASK (locked bound 3)
  | { kind: "past" }        // resolves to <= now (+small epsilon) → RE-ASK, never silently send
  | { kind: "none" };       // no time expressed → immediate send (today's default, SC1)
export function parseSendTime(text: string, nowMs: number, ianaTz: string): SendTimeParse { /* pure, no Date.now */ }
```
**Tool:** on `resolved` → `patchPlan{ sendAt }` + return the ABSOLUTE time string for the model to confirm; on `ambiguous`/`past` → return a re-ask message, write NOTHING (SC2). The tool receives `nowMs`+`ianaTz` from a trusted CLIENT source (never the model — the model must not invent "now"; see Open Question 1 for threading).
**SMOKE:** extend the `SMOKE::agent::` grammar (`llm.ts:1011-1075`) with `sendTime=<expr>` → `invokeTool(tools,"setSendTime",{...})`, using a pinned `nowMs`/`ianaTz` offline (mirror the attachment date-pinning `1970-01-01` trick at `llm.ts:560`).

### Pattern 6: The picker + `ScheduledCard` (native, one-source-of-truth)
**What:** On the PLAN card (`cards.tsx` `PlanCard`, ~line 191), render `<input type="datetime-local">` bound to `plan.sendAt` (converted to the user's local wall-clock via `Intl`), plus a "send immediately" clear. On change the CLIENT computes epoch ms natively (the browser IS in the user's tz) and writes it through a new `setPlanSendTime(planId, sendAt|null)` `tenantMutation`. Both the NL tool and the picker write the SAME `plan.sendAt` — one source of truth. Show the resolved absolute time + tz label above Approve (SC2). After Approve, `CardList` (`cards.tsx:419-440`) dispatches: `status === "scheduled"` → `ScheduledCard` ("Scheduled for <abs, tz> · Cancel" → `cancelScheduledPlan`); `status === "canceled"` → a "Canceled" note. Reuse the existing `box`/`label`/`chip`/`btn` tokens — no new component (ponytail).

### Anti-Patterns to Avoid
- **Two `workflow.start` call sites.** Do not inline `workflow.start` in both `executePlan` and the scheduled fn — extract `startFanout` (Pattern 2). The invariant is grep-enforced in the playbook.
- **Letting the model supply "now" or the timezone.** The tool must take `nowMs`/`ianaTz` from the client (§2-D trust boundary) — a hallucinated clock schedules the wrong instant.
- **`Date.now()` inside the pure parser.** Breaks determinism + offline SMOKE (core is pure by discipline — `emailIntent.ts:7`). Inject `nowMs`.
- **Storing wall-clock strings or a tz-plus-local pair.** Store ONE absolute epoch ms (Tier-1-compatibility rule; the design forbids speculative schema).
- **Cancelling without the status CAS.** `scheduler.cancel` throws on an already-fired fn; the `status === "scheduled"` gate is mandatory.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Delayed execution | A cron that polls `plans` for due `sendAt` rows | `ctx.scheduler.runAt(sendAt, fn, args)` | Native, durable, per-plan, cancellable; already the repo idiom (`review.ts:63`). A poller adds a table scan + latency + its own failure modes. |
| Cancel-before-fire | A "canceled" flag the fire-fn checks | `ctx.scheduler.cancel(id)` + status CAS | The scheduler physically un-schedules; the flag would still wake the fn and risk a race. |
| Retry/DLQ/reauth at fire | New failure handling for scheduled sends | Reuse `deliverApprovedPlan` verbatim | SC4 is satisfied by construction; new code would drift from the immediate path. |
| local wall-clock ↔ epoch in the user's tz | Manual UTC offset math in the browser | Native `datetime-local` + `Intl.DateTimeFormat` | The browser already knows its tz; the picker gives/takes local wall-clock natively. |
| NL date parsing | A large dep | ~60-line pure `@pikar/core` reducer over a small grammar | Deterministic, testable, offline-SMOKE-able; no bundle cost (no dep installed). |

**Key insight:** every hard part of "deferred + governed + cancellable + fault-tolerant" already exists in this codebase. The phase is a *composition*, not new machinery — exactly what `scheduled-send.md` promised ("it composes onto the plan/approve/execute spine, it does not change it").

## Common Pitfalls

### Pitfall 1: Cancelling an already-fired scheduled function throws
**What goes wrong:** `ctx.scheduler.cancel(id)` on a scheduled mutation that has already committed **throws** ("fail to cancel if it has committed" — Convex docs).
**Why:** the fire and the cancel race; without a guard the Cancel button 500s after fire.
**How to avoid:** gate on `status === "scheduled"` (Pattern 4). `startScheduledDelivery` flips status→delivering as its first act, and Convex mutations are serializable, so reaching `cancel` implies the fn has not run.
**Warning signs:** a Cancel that intermittently errors under load or right at fire time.

### Pitfall 2: The single-`workflow.start` invariant silently breaks
**What goes wrong:** copy-pasting `workflow.start` into the scheduled fn creates a second call site; the playbook's grep-verified "zero sends before Approve" invariant is now unenforceable.
**How to avoid:** the extracted `startFanout` helper (Pattern 2); add a test/grep assertion that `workflow.start(` appears exactly once.
**Warning signs:** `git grep 'workflow.start('` returns >1 hit.

### Pitfall 3: Timezone drift between parse and picker
**What goes wrong:** the NL parse uses server time or a default tz while the picker uses the browser tz → the confirmed absolute time differs from what the user sees.
**How to avoid:** thread the SAME client `ianaTz`+`nowMs` to the parser; make the picker the confirm-source-of-truth writing the same `plan.sendAt`. Show the resolved absolute time (with tz label) before Approve (SC2).
**Warning signs:** "it said 4pm but sent at 4pm UTC."

### Pitfall 4: A past `sendAt` at Approve time
**What goes wrong:** the user sets 4pm, then approves at 4:05pm; `runAt` in the past fires immediately (Convex runs past-due schedules ASAP), which may be fine — or the user expected a re-ask.
**How to avoid:** `executePlan` re-validates `sendAt > Date.now()` at the trust boundary (Pattern 2). Recommend: `sendAt <= now` at Approve → treat as an immediate send (the user clicked Approve intending to send; sending now is not "silent"). The locked "re-ask on past" bound governs the INTAKE/parse stage, not the moment of Approve. **Flag for the planner** (Open Question 2).
**Warning signs:** a plan that "sends late" or an approve that silently no-ops.

### Pitfall 5: `plans.ts` PLAN_STATUS mirror not updated
**What goes wrong:** `schema.ts` gains `scheduled`/`canceled` but the hand-maintained `PLAN_STATUS` union in `plans.ts:17-23` doesn't → `setPlanStatus`/`patchPlan` validators reject the new states at runtime.
**How to avoid:** update BOTH unions in the same change.

### Pitfall 6: Scheduled args must be serializable + parallel arrays must stay aligned
**What goes wrong:** `runAt` args are persisted; passing anything non-serializable (a Blob, a Model) fails. And `deliverApprovedPlan` relies on `requestIds`/`correlationIds` being parallel (`deliverApprovedPlan.ts:31-34`).
**How to avoid:** pass only ids/strings (as `startFanout` does); mint both arrays together at Approve.

## Open Questions

1. **How is the client `ianaTz` + `nowMs` threaded to the server-side `setSendTime` tool?**
   - What we know: the model must NOT supply these (trust boundary §2-D); the picker natively has the browser tz; the SMOKE path can pin them.
   - What's unclear: the exact carrier. Options — (a) add an optional `clientContext:{tz,nowMs}` arg to `sendCockpitMessage`/`runCockpitAgent`, threaded into `buildCockpitTools`; (b) capture the tz once onto the plan row (a `clientTz` optional field) + use `Date.now()` server-side as "now" (server clock ≈ client clock within seconds — acceptable for minute-granularity NL like "tomorrow 9am"); (c) rely on the picker as the authoritative writer and let the NL tool only produce a coarse guess.
   - Recommendation: **(a) is cleanest for correctness** (deterministic, testable, no server-clock assumption). Minimal additive change: one optional arg down the existing driver. Since the picker is the confirm-source-of-truth, (b) is an acceptable ponytail fallback if (a) balloons the driver. Planner decides; this is the single biggest design choice.

2. **Past `sendAt` at Approve time → immediate send or refuse?** (Pitfall 4.) Recommend: treat `sendAt <= now` at Approve as an immediate send (Approve = explicit consent to send). The "re-ask on past" bound is an intake-stage rule. Confirm with the planner.

3. **Does `canceled` suppress the `DraftCard`?** `CardList` renders `DraftCard` whenever `body`/`subject` exist (`cards.tsx:426,436`). Under `scheduled`/`canceled` you likely want the `ScheduledCard`/"Canceled" note to dominate. Recommend gating `hasDraft` rendering off when `status` is `scheduled`/`canceled` (a one-line dispatch tweak).

4. **Skill change?** If the agent needs new instructions to *ask* for a send time / confirm the absolute time / re-ask on ambiguity, that flows through the `cockpit-agent` 5-file skill mirror (§5), NOT hardcoded (`skills.ts:101`, `packages/contracts/skills/cockpit-agent.md`). If `setSendTime` is purely reactive (user volunteers a time), the skill may need only a light "## Scheduling" section. Planner scopes.

4. Cancel-before-fire: `cancelScheduledPlan` → assert `status === "canceled"`, the scheduled system row is gone, a refs-only `plan.canceled` audit row exists; then `vi.advanceTimersByTime(...)` + `finishInProgressScheduledFunctions()` and assert **nothing sent** (no `requests` row moved to `delivering`/`sent`).
