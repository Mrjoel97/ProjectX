## 1. The one-paragraph answer

The cockpit is **overwhelmingly a reuse+wiring phase, not a build phase**. The governed
backend spine already exists and is reused verbatim: `gmail.send` (per-request-row),
`audit.log` (insert-only), `telemetry.writeTerminal` (idempotent by correlationId),
`deadLetters`/`onPipelineComplete`, the `WorkflowManager`, the `email-drafter` skill (already
seeded), the `SMOKE::` offline path, and the tenant wrappers. The Connect-Gmail infinite-loading
bug is **already root-fixed** (`18c8442`). Genuinely new code is small and well-bounded: a pure
`emailIntent` module (clone of `validateSubmit.ts`), a two-pane cockpit page (native CSS grid, no
new dep), a `plans`/`artifacts` content table, `proposeEmailPlan`/`executePlan`, a lean
`deliverApprovedPlan` fan-out loop (~1 workflow + 1 dead-letter helper), a `tenantAction` wrapper,
and the test/smoke/E2E scaffolding.

## 4. ⚠ CROSS-LANE DECISION #1 — the PLAN/REPORT data model (planner MUST resolve)

The agent-lane and delivery-lane proposed **two different data models**. They must be unified
into ONE before task-writing, or the card-wiring and fan-out tasks will not compose.

| | Agent-lane proposal | Delivery-lane proposal |
|---|---|---|
| PLAN | `artifacts` row, `kind:"plan"`, holds recipients/mode/subject/body + `status` | a `plans` row with a `status` for the CAS |
| Fan-out unit | workflow patches a `report[]` array on the artifact | **one `requests` row per recipient** (reuses `gmail.send` verbatim) |
| REPORT | `report[]` field patched by `patchReportRow` | **reactive projection** over the per-recipient `requests` rows + `gmail.sent` audits (no report writer) |

**Recommended reconciliation (ponytail — take the reuse that deletes the most new code):**
1. **Adopt the delivery-lane fan-out: one `requests` row per recipient, grouped by `planId`.**
   Decisive because `gmail.send({requestId})` reads recipient/subject/body off the row — reusing
   it verbatim means **zero new send/audit/telemetry/status code**. A bespoke `report[]` patched
   by the workflow would re-implement what request-row status transitions already give for free.
2. **Keep ONE `plans` (or `artifacts` kind=`plan`) content row** as the approve-gate object —
   it holds recipients/mode/subject/body (draft) **and the `status` field the idempotency CAS
   needs** (`draft → approved → delivering → done`). This is the agent-lane's contribution.
3. **REPORT = live `tenantQuery` projection** over `requests` where `planId` matches (status +
   `gmail.sent` audit messageId + correlationId audit-link). No `report[]`, no report writer.
4. Net: `plans` table = plan+draft content plane; `requests` gains an optional `planId` column;
   REPORT is a query. This honors CLAUDE.md §4 (raw content stays in content-plane `requests`/
   `plans`, never in audit/DLQ) and §1 (thin adapters).

**Consequence for the schema:** add a `plans` table (tenantId, threadId, recipients, mode,
subject, body, status, correlationId?, workflowId?, createdAt) + `planId` (optional) on
`requests`. Do **not** add a `report` array. (If a later slice needs denormalized report
snapshots, add then — YAGNI now.)

## 5. ⚠ CROSS-LANE DECISION #2 — conversation control (planner MUST resolve)

- **(A) LLM-driven agent loop** — `agent.generateText({ tools:{ proposeEmailPlan } })`; the model
  decides when slots are full. Native to the component, but non-deterministic + hard to test.
- **(B) Deterministic `emailIntent`** — the pure module computes the next question; the thread is
  just message store; the LLM is called **only** for the body draft; `proposeEmailPlan` is invoked
  when `emailIntent` reports `ready`.

**Both backend researchers independently recommend (B).** It makes "nothing sends on assumption"
structural, keeps the pure-assert testability the design mandates, needs **no new conversation
skill/seed**, and is the ponytail choice (no LLM where a checklist works). **Adopt (B)** unless the
planner has a reason otherwise.

## 6. Other confirmed constraints (do not violate)

- **Single `"use node"` module.** `llm.ts` is the ONLY `"use node"` file; a second one re-triggers
  a TS circular-inference cliff (`llm.ts:10-12,63-66`). The cockpit draft step MUST live inside
  `llm.ts` — do not create a new node action module.
- **`tenantAction` does not exist.** `lib/functions.ts` has only `tenantQuery`/`tenantMutation`.
  Add `tenantAction` via `customAction` (convex-helpers, already installed) reusing `requireTenant`
  — keeps the raw-`action` import ban (§2) intact. The agent runs in an action.
- **`executePlan` is a human gate, not an LLM tool.** Approval idempotency = a compare-and-set on
  plan `status` inside the mutation (Convex tx is serializable). Second approve reads
  `status !== "draft"` → no-op → **double-approve sends once**.
- **Per-row `correlationId`.** Each recipient row needs its own correlationId (audit/telemetry/DLQ
  all key by it; a shared cid collapses per-recipient isolation). Server-minted, never client-supplied.
- **Zero-sends-before-Approve** is enforced structurally: `gmail.send` is only called from inside a
  delivery workflow, `deliverApprovedPlan` is only started by `executePlan`, and the CAS gates it.
- **Redaction (§4):** recipient email / subject / body are content-plane (`requests`/`plans`) —
  never in `audit.payload` or `deadLetters.payload` (refs/ids/counts only). Verify `error:String(e)`
  from a Gmail non-2xx carries no echoed content (smoke `assertNoRawPii`).
- **Pinned pre-1.0 versions** (`@convex-dev/agent@0.6.4`, workflow, retrier) — do not bump (§6).
  `apps/web` must pin the SAME `@convex-dev/agent@0.6.4`.
- **Prereq order:** run `npx convex run skills:seedSkills` on a fresh deployment (drafter row).
- **Group mode:** verify `buildMime`'s single `To:` line accepts a comma-joined address list
  (`gmail.ts:21`); individual mode is unaffected.
