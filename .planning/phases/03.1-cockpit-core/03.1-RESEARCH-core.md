# Phase 3.1: Cockpit Core — Research (Pure `emailIntent` Module)

**Researched:** 2026-07-12
**Domain:** Pure-TS slot-filling state module in `packages/core` + email validation reuse + test approach
**Confidence:** HIGH (all findings from the repo itself, not training data)
**Lane:** ONLY the pure `emailIntent` module, its validator, and its test. NOT UI, NOT the delivery workflow, NOT the Convex agent-tool wiring (siblings own those).

## Summary

`packages/core` already has an established, boringly consistent pattern for exactly this kind of
module: a single-file pure function that takes plain inputs and returns a discriminated union,
with a side-by-side `*.test.ts` vitest file. `validateSubmit.ts` is a near-perfect template — it
already validates a recipient email with a structural regex and returns `{ ok } | { ok:false, reason }`.
The `emailIntent` module should follow that file's shape exactly: no class, no state-machine
framework, no zod, no Convex imports.

The whole module reduces to two pure functions over an immutable `EmailIntentState`:
`nextQuestion(state)` (what to ask next, or "ready") and `applyAnswer(state, answer)` (fold an
answer into new state). Ordering, the invalid-email re-ask, the mode question, and the
"never send on assumption" guarantee are all just the order and content of the branches in those
two functions — which is precisely what a single assert/vitest file pins down.

**Primary recommendation:** Add `packages/core/src/emailIntent.ts` + `emailIntent.test.ts`,
modeled 1:1 on `validateSubmit.ts`. Export the existing `EMAIL_RE` (currently a private const in
`validateSubmit.ts`) as `isValidEmail()` and reuse it — do NOT add a new validator or a zod dep.

## 1. Existing `packages/core` conventions (the template)

**Package facts** (`packages/core/package.json`):
- `"@pikar/core"`, `"type": "module"`, ESM.
- Exports: `"." -> ./src/index.ts` and `"./*" -> ./src/*.ts`. So both `import { x } from "@pikar/core"`
  and subpath `import { x } from "@pikar/core/emailIntent"` work with **no build step** (source is the entrypoint).
- Deps: only `ai@7.0.20`. Dev: `vitest@3.2.7`. **No zod** (deliberate — see `contracts/drafting.ts`:
  zod lives in `@pikar/contracts`; core stays zod-free). Do not pull zod into core.
- Scripts: `typecheck` = `tsc --noEmit` (extends `../../tsconfig.base.json`), `test` = `vitest run`.

**Module conventions** (observed across `validateSubmit.ts`, `tokenExpiry.ts`, `result.ts`):
- One concern per file, `camelCase.ts`. **Named exports only** (no default). Re-export the whole file
  from `src/index.ts` via `export * from "./emailIntent";`.
- Pure functions, no classes, no `this`. Caller passes everything in (e.g. `tokenExpiry` takes `now`
  as an arg — no wall-clock reads). `emailIntent` must do the same: no I/O, no Date.now, no randomness.
- **Return discriminated unions, don't throw.** Two idioms coexist:
  - Generic `Result<T,E>` from `result.ts` (`ok(v)` / `err(e)`, `isOk`, `unwrap`).
  - A local inline union like `validateSubmit`'s `{ ok:true } | { ok:false; reason: RejectionReason }`.
  For `emailIntent`, a **local union is the better fit** (the "answers" are richer than a single error
  reason) — matches the `validateSubmit` precedent.
- Heavy top-of-file doc comment stating the invariant the module protects and the CLAUDE.md rule it
  satisfies (`§1: no Convex imports`). Continue that style — it is the house voice.

**Concrete template snippet** (this is the exact skeleton to clone — `validateSubmit.ts`):


## 2. Email validation to reuse (do NOT rebuild)

**The validator already exists** — `packages/core/src/validateSubmit.ts:37`:

```typescript
const EMAIL_RE = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;   // structural shape only, NOT deliverability
```

It is currently **private** (module-scoped const) and its test (`validateSubmit.test.ts:41-45`)
already pins its behavior: rejects `"" , "nope", "a@b", "a b@c.com", "@b.com", "a@.com"`.

**Recommended move (smallest diff):** in `validateSubmit.ts`, promote it to a named export helper and
reuse it from both places:

```typescript
/** Structural email check — shape only, NOT deliverability. Anchored, single address. */
export const isValidEmail = (s: string): boolean => /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(s);
```

Then `validateSubmit` calls `isValidEmail(recipient)` and `emailIntent` imports `isValidEmail`.
One regex, one test, two callers — the ponytail root-cause shape (fix/own it once where all callers route).

**Do NOT reuse the PII email regex** (`packages/pii/src/scan.ts:49`,
`/[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}/g`). It is **unanchored + global-flag** — built to
*find* emails inside prose, not to *validate* a single address (it would accept `"junk a@b.com junk"`).
Wrong tool for this boundary.

**Do NOT add zod / a new email lib.** Core is deliberately zod-free; a stricter RFC validator is
YAGNI here — the guarantee that matters is "the user typed a real-looking address and confirmed it",
not RFC-5322 completeness. `ponytail: structural regex; upgrade to a real validator only if bounce
rates demand it.` (Matches the existing `// shape only, NOT deliverability` comment intent.)

## 3. Recommended `emailIntent` API shape

Pure state + two pure functions. Sketch (planner refines names/exact reasons):

```typescript
// --- Slots (all optional until filled; presence = "known") ---
export type RecipientMode = "individual" | "group";

export interface EmailIntentState {
  readonly recipients: readonly string[];     // validated, deduped; [] = none yet
  readonly subject?: string;
  readonly bodyIntent?: string;               // the goal → drafter turns it into wording
  readonly mode?: RecipientMode;              // only meaningful when recipients.length > 1
  readonly attachmentIntent?: boolean;        // optional slot; upload-only in slice 1
}

export const emptyIntent: EmailIntentState = { recipients: [] };

// --- What to ask next (ordered, one topic at a time) ---
export type NextQuestion =
  | { kind: "ask_recipients" }
  | { kind: "reask_recipient"; invalid: string }   // invalid email → re-ask ONLY this one
  | { kind: "ask_subject" }
  | { kind: "ask_body_intent" }
  | { kind: "ask_mode" }                            // only when recipients.length > 1 && mode undefined
  | { kind: "ready" };                              // all required slots filled → assemble PLAN

/** Pure: given current slot state, the single next thing to ask, or "ready".
 *  Never returns "ready" while any required slot is missing or a recipient is invalid. */
export function nextQuestion(state: EmailIntentState): NextQuestion;

// --- Fold a user answer into new state (immutable; returns a fresh state) ---
export type Answer =
  | { slot: "recipients"; value: string[] }   // may contain invalids → validated inside
  | { slot: "subject"; value: string }
  | { slot: "bodyIntent"; value: string }
  | { slot: "mode"; value: RecipientMode }
  | { slot: "attachment"; value: boolean };

export type ApplyResult =
  | { ok: true; state: EmailIntentState }
  | { ok: false; state: EmailIntentState; rejected: { slot: "recipients"; invalid: string[] } };

/** Pure: validate + merge one answer. Invalid recipients are NOT stored — they come back
 *  in `rejected` so the caller re-asks; valid ones are added. Never mutates `state`. */
export function applyAnswer(state: EmailIntentState, answer: Answer): ApplyResult;
```

Design notes for the planner:
- **`nextQuestion` ordering is the spec** (design doc §Guided conversation): recipients → (reask if any
  invalid) → subject → body intent → mode (only if >1) → ready. Encode the order as the order of the
  `if` branches — this is the whole module.
- **`applyAnswer` is the trust boundary.** Invalid recipients never enter `state.recipients`; they bounce
  back in `rejected`. That is what makes "an invalid email re-asks only that one and nothing is sent on an
  assumption" *structurally* true, not merely convention (mirrors `validateSubmit`'s stated purpose).
- **Immutability**: return fresh objects (`{ ...state, recipients: [...] }`). No in-place mutation — keeps
  it trivially testable and matches the pure-function house style.
- **"Ready" ≠ "send".** `nextQuestion` returning `ready` only signals "enough to assemble the PLAN card".
  The actual send is gated by Approve in the sibling workflow. This module never sends and has no concept
  of sending — keep it that way (it can't violate "no send before approve" because it has no send path).
- Dedupe recipients in `applyAnswer` (case-insensitive) — cheap, avoids double-emailing the same person.

## 4. How the mode (individual/group) slot fits

- `mode` is a **conditional required slot**: required iff `recipients.length > 1`, otherwise irrelevant
  (a single recipient has no individual-vs-group distinction — don't ask).
- `nextQuestion` emits `ask_mode` only when `recipients.length > 1 && mode === undefined`, AFTER subject +
  body intent are filled (or wherever the planner slots it — but only for >1). For a single recipient,
  `nextQuestion` skips straight from body-intent to `ready`.
- **Default is `individual`** (design doc §Multiple recipients: "safe default — each person gets their own
  private email"). Model the default carefully: the design says the agent *asks the one question that
  matters*, so do NOT silently default — `nextQuestion` should surface `ask_mode` so the user chooses, and
  the PLAN card shows the chosen mode explicitly before approval. (If the planner wants a fallback, default
  to `individual` only if the user declines to choose — flag as open question below.)
- Same content to all recipients in slice 1 (personalization is a later slice) — so `mode` is the *only*
  multi-recipient slot this module tracks. No per-recipient fields.

## 5. Test approach (the ONE runnable check)

One file, `emailIntent.test.ts`, vitest, side-by-side (per §1). It must cover — these map directly to
SC2/SC3 and the design doc's error table (§Error & edge handling):

| # | What it pins | Assertion sketch |
|---|---|---|
| 1 | **Missing-slot ordering** | from `emptyIntent`, `nextQuestion` → `ask_recipients`; after valid recipient → `ask_subject`; then `ask_body_intent`; single recipient → `ready` (no mode) |
| 2 | **Invalid-email re-ask (only that one)** | `applyAnswer(state, {slot:"recipients", value:["ok@x.com","nope"]})` → `ok:false`, `rejected.invalid:["nope"]`, state keeps `ok@x.com`; `nextQuestion` → `reask_recipient` |
| 3 | **Mode question trigger** | with 2 valid recipients + subject + body filled, `nextQuestion` → `ask_mode`; with 1 recipient it never emits `ask_mode` |
| 4 | **Never-send-on-assumption / never ready early** | while any required slot missing OR any recipient rejected, `nextQuestion` **never** returns `ready`; all-filled → exactly `ready` once |
| 5 | **Immutability / dedupe** | `applyAnswer` returns a new object; `state` unchanged; duplicate recipient not added twice |
| 6 | **Validator reuse** | reuse `validateSubmit`'s existing bad-email table (`"a@b"`, `"@b.com"`, `"a@.com"`, …) against `isValidEmail` — one shared truth |

Style: table-driven `for` loops + `.toEqual({...})` full-shape asserts, exactly like
`validateSubmit.test.ts`. No fixtures, no mocks (nothing to mock — it's pure). This single file IS the
"ONE runnable check" the ponytail rule mandates; it runs in `pnpm test` with the rest of core.

## 6. Open questions / risks

1. **Mode default vs. always-ask.** Design says `individual` is the "safe default" AND that the agent
   "asks the one question that matters". Resolve: does `nextQuestion` always emit `ask_mode` for >1
   (user must pick), or only if the user hasn't already implied a mode? *Recommendation: always ask for
   >1 (explicit choice shown on PLAN card); treat `individual` as the value pre-selected in the UI, not a
   silent skip.* — planner/UI sibling decision.
2. **Where does `ask_mode` sit in the order?** Before or after subject/body? Design doesn't fix this.
   *Recommendation: after body intent, just before `ready`* — but low stakes; pick one and test it.
3. **Attachment slot in the state machine.** Slice 1 is upload-only and attachment is optional, so it
   likely never blocks `ready`. *Recommendation: track `attachmentIntent?` for the PLAN card but never let
   its absence gate `ready`.* Confirm the module doesn't need to *ask* about attachments at all in slice 1
   (probably a UI affordance, not a conversation slot) — the UI sibling owns that seam.
4. **Test-framework wording mismatch (low risk):** design doc says "assert-based"; repo convention is
   vitest. Recommendation in §1 = follow vitest (already wired). Planner to confirm so the phase gate's
   test command (`pnpm --filter @pikar/core test`) stays green.
5. **`isValidEmail` export placement.** Promote from `validateSubmit.ts` (my recommendation, keeps one
   regex) vs. new `email.ts`. Either is fine; the risk is two divergent regexes — avoid that. LOW risk.

None of these block planning; all are small, local decisions.
