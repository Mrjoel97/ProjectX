# 03.1-07: Cockpit orchestration seam (SC2/SC3/SC4)

Wired the guided conversation to the plan. `sendCockpitMessage` (tenantAction) runs a
deterministic turn: saves the user message to the agent thread, projects the `plans` row into
an `EmailIntentState`, maps the free-text reply to an `Answer` for the slot the PRIOR
`nextQuestion` was asking, folds it in with `applyAnswer`, and then either asks the next
question (deterministic assistant copy — no LLM) or, when every required slot is filled,
redacts the body-intent, calls the SOLE LLM step (`draftCockpit`), and code-invokes
`proposeEmailPlan` to write the PLAN (status → `proposed`).

`executePlan` (tenantMutation) is the human approve gate: a serializable-mutation CAS on
`plan.status` means only the first `proposed→approved` transition seeds one `requests` row per
recipient (each with its own server-minted `correlationId`) and starts `deliverApprovedPlan` —
a double-approve re-reads a non-proposed status and no-ops. It is the only
`workflow.start(deliverApprovedPlan)` call site, making "zero sends before Approve" a grep-able
invariant. A Gmail-connected pre-check stops before any delivery when no mailbox is linked.

DECISION #2 holds structurally: the Agent is the codebase's first `new Agent(...)` but is used
as a message store only — it never runs `generateText`/`streamText`, so question selection is
100% the pure `emailIntent` module and nothing is ever proposed on an assumption.
