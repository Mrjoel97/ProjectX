## Locked design decisions (from `.planning/design/email-chat-cockpit.md`)

- Approve at the **PLAN**, not mid-run. Execution is a straight, hands-off governed fan-out.
- **Reuse** delivery/audit/telemetry/DLQ/tenant-scoping/skills primitives unchanged. **Do NOT reuse** the review-gate pause.
- Same content to all recipients in slice 1 (personalization is a later slice). Two modes: individual copies (default) or one group email.
- `SMOKE::` sentinel path must work offline.

## Summary

The existing `pipelineWorkflow` (`packages/backend/convex/pipeline.ts`) already contains the exact governed per-send step we need: `step.runAction(internal.gmail.send, { requestId })` → its discriminated result drives `sent` vs `awaiting_reauth`, with the `gmail.sent` audit (messageId ref) and terminal telemetry written around it. The cockpit drops steps 0–3 (guard/route/draft/**review-gate pause**) for the delivery workflow and keeps only step 4 (deliver) — looped once per recipient.

The single most important structural fact: **`gmail.send` is inherently per-request-row.** It takes only `{ requestId }` and reads recipient/subject/body from that row via `gmailAuth.getForDelivery` (`subject = goal`, `body = editedBody ?? draft ?? ""`). Therefore the leanest fan-out that reuses the governed step *verbatim* is: **create one `requests` row per recipient at approve time** (same body, distinct `recipient` + distinct `correlationId`, grouped by a shared plan id), then loop `step.runAction(internal.gmail.send, { requestId })` over those rows inside one durable `deliverApprovedPlan` workflow. Each row gets its own status transitions, its own `gmail.sent` audit, and its own terminal telemetry — all reused unchanged.

Per-recipient isolation ("one fails, the rest still send") is a `try/catch` around each send step inside the handler. **Confirmed HIGH** against the `@convex-dev/workflow` README: *"If a step fails, it will either retry based on the configured policy, or throw a catch-able exception in the workflow handler, allowing graceful recovery."* On catch, dead-letter just that recipient row (reusing the existing deadLetters/audit/telemetry shapes) and continue the loop; the whole workflow still completes `success`.

**Primary recommendation:** One `requests` row per recipient (grouped by `planId`), one `deliverApprovedPlan` workflow that loops `gmail.send` per row inside `try/catch`, idempotency enforced by a compare-and-set on plan status in `executePlan`. Zero new delivery/audit/telemetry/DLQ code — only the fan-out loop, a per-row dead-letter helper, and a `planId` grouping key are new.

## 1. Existing `pipelineWorkflow` anatomy

**File:** `packages/backend/convex/pipeline.ts` — `pipelineWorkflow = workflow.define({ args: { correlationId, requestId, tenantId }, handler: async (step, ...) })`.

The handler is a linear spine of steps, each transitioning `requests.status`:

| Step | What it does | Cockpit delivery workflow |
|------|--------------|---------------------------|
| 0. GUARD | `setStatus("scanning")` → `guardrails.prepare` → `request.redacted` audit | **DROP** (guarding happens pre-plan/at draft, sibling's lane) |
| 1. ROUTE | `setStatus("routing")` → `llm.route` (`retry:false`) | **DROP** |
| 2. DRAFT | `setStatus("drafting")` → `llm.draft` / verbatim | **DROP** (draft assembled during guided conversation) |
| 3. REVIEW GATE | `setStatus("awaiting_review")` → `armTimeout` + `awaitEvent` loop (regenerate/reject/approve/timeout) | **DROP THE PAUSE** — this is the mid-run gate the cockpit replaces with plan-time Approve |
| **4. DELIVER** | `setStatus("delivering")` → `step.runAction(internal.gmail.send, { requestId })` → branch on `result.delivered` → `setStatus("sent")` + `writeTelemetry("sent")`, else hold at `awaiting_reauth` | **KEEP — this is the reusable governed per-send step. Loop it per recipient.** |

**The reusable governed per-send step (pipeline.ts lines ~284–290):**
```typescript
await setStatusStep("delivering");
const result = await step.runAction(internal.gmail.send, { requestId });
if (!result.delivered) return null;      // hold at awaiting_reauth (set inside gmail.send)
await setStatusStep("sent");
await writeTelemetry("sent");
```

**Key reuse note (from STATE.md / 02-06-SUMMARY):** delivery uses `step.runAction(internal.gmail.send, …)` with the **workpool default retries**, NOT `retrier.run`. A `workflow.define` handler is `(step, args)` — it has **no scheduler/mutation `ctx`**, so it cannot `await retrier.run(ctx, …)` (that returns a runId, fire-and-onComplete, not a synchronous result). The fan-out loop must use the same `step.runAction` pattern. The `retrier` export in `index.ts` is for non-workflow call sites only.

**Retry budget (index.ts `WorkflowManager`):** `defaultRetryBehavior: { maxAttempts: 3, initialBackoffMs: 100, base: 2 }`, `retryActionsByDefault: true`. So each `gmail.send` step auto-retries transient 5xx up to 3 attempts before throwing into the handler.

## 2. Reused primitives — exact signatures

All in `packages/backend/convex/`. Every one is reused **unchanged**.

### `gmail.send` — `gmail.ts` (`"use node"`, actions only)
```typescript
export const send = internalAction({
  args: { requestId: v.id("requests") },
  handler: async (ctx, { requestId }): Promise<SendResult> => { ... }
});
type SendResult =
  | { delivered: false; reason: "not_connected" | "refresh_failed" }
  | { delivered: true; messageId: string };
```
- Reads recipient/subject/body via `ctx.runQuery(internal.gmailAuth.getForDelivery, { requestId })`.
- **Token dead → returns `{ delivered:false }` and sets `status:"awaiting_reauth"` (NO throw)** — the draft is preserved, delivery resumes on reconnect. Do not burn retries on token death.
- **5xx / non-ok → THROWS** → workpool retries → (exhausted) throws into handler.
- On success writes the audit ref itself: `audit.log({ eventType: "gmail.sent", payload: { requestId, messageId: sent.id } })`. **Does NOT set `status:"sent"`** — the caller owns that transition after the step returns.

### `gmailAuth.getForDelivery` — `gmailAuth.ts`

```typescript
export const getForDelivery = internalQuery({

});
```

## 3. Proposed `deliverApprovedPlan` shape

**Fan-out unit = one `requests` row per recipient.** Reuses `gmail.send`, per-row audit/telemetry/status verbatim; nothing about the send action changes.

### Row seeding (in `executePlan`, before `workflow.start`)
For each recipient (individual mode) OR one row (group mode, all addresses joined in the `To:`):
```
requests row: { tenantId, correlationId: <fresh per row>, goal: subject, draft/editedBody: body,
                recipient, status: "approved", planId: <shared>, attachmentRefs:[], createdAt }
```
- **`planId`** (new): the grouping key so the REPORT reads all rows for one plan. Add `planId: v.optional(v.id("plans"))` (or `v.optional(v.string())`) to `requests`. Optional → no backfill. **Coordinate the concrete type with the UI/artifacts sibling** (they own the plan/report artifact table).
- Each row keeps its **own `correlationId`** — mandatory, because audit/telemetry/deadLetters all key by correlationId; a shared cid would collapse per-recipient isolation (telemetry write-once would drop all but the first).

### The workflow
```typescript
export const deliverApprovedPlan = workflow.define({
  args: { planId: v.string(), tenantId: v.string(), requestIds: v.array(v.id("requests")) },
  handler: async (step, { planId, tenantId, requestIds }): Promise<null> => {
    for (const requestId of requestIds) {
      await step.runMutation(internal.pipeline.setStatus, { requestId, status: "delivering" });
      try {
        const result = await step.runAction(internal.gmail.send, { requestId }); // workpool retries
        if (!result.delivered) continue;                       // held at awaiting_reauth — not a failure
        await step.runMutation(internal.pipeline.setStatus, { requestId, status: "sent" });
        await step.runMutation(internal.telemetry.writeTerminal, {
          requestId, correlationId: <row cid>,
          outcome: { reviewOutcome: "sent", durationMs: 0, decisionCounts: {}, regenerateCount: 0, usages: [] },
        });
      } catch (e) {
        // per-recipient isolation: dead-letter THIS row, keep the loop going
        await step.runMutation(internal.deadLetter.deadLetterRecipient, {
          tenantId, requestId, correlationId: <row cid>, error: String(e),
        });
      }
    }
    return null;
  },
});
```
- **Per-recipient isolation is the `try/catch`.** README-confirmed: an exhausted-retry step throws a *catchable* exception in the handler. One recipient's terminal failure is caught, dead-lettered, and the loop proceeds — the other rows still send. The whole workflow returns `success`.
- Correlation-id per row: either pass a parallel `correlationIds` array or read it back inside a tiny mutation from the requestId (the row already stores it). Passing the array is the lazy, deterministic choice (no extra read inside the workflow).

### New per-row dead-letter helper (only genuinely new backend code, ~15 lines)
`deadLetter.onPipelineComplete` has the wrong signature to call inline (it's an onComplete handler expecting `{ workflowId, result, context }`). Add a sibling internal mutation reusing the **same three writes**:
```typescript
export const deadLetterRecipient = internalMutation({
  args: { tenantId: v.string(), requestId: v.id("requests"), correlationId: v.string(), error: v.string() },
  handler: async (ctx, { tenantId, requestId, correlationId, error }) => {
    await ctx.db.insert("deadLetters", { tenantId, correlationId, workflowId: "", payload: { requestId }, error, status: "new", createdAt: Date.now() });
    await ctx.runMutation(internal.audit.log, { tenantId, correlationId, eventType: "deadletter.written", actor: "system", payload: { requestId, status: "new" } });
    await ctx.db.patch(requestId, { status: "failed" });
    // one "failed" telemetry row (idempotent by correlationId) — same buildTelemetry shape as onPipelineComplete
  },
});
```
`// ponytail: mirrors onPipelineComplete's per-request terminal writes; the two converge if the workflow component ever exposes per-step onComplete.` → skipped: unifying with onPipelineComplete; add when the component gives a per-step completion hook.

### Live REPORT (SC5) — a projection, not a write path
The REPORT card is a reactive `tenantQuery` over the request rows for a `planId`:
- **status** = `requests.status` per row (`delivering` → `sent` | `awaiting_reauth` | `failed`).
- **message id** = the `gmail.sent` audit row for that row's correlationId (`payload.messageId`).
- **audit link** = the row's `correlationId` (drives an audit-trail view via the existing `by_correlation` index).

Because each `setStatus` / `gmail.sent` audit lands mid-loop, a reactive query updates the card **live, per recipient**, with zero extra "report writer" code. `// ponytail: REPORT = projection over request rows + audits; a dedicated report artifact table only if the UI sibling needs denormalized snapshots.`

**Rejected alternative:** teach `gmail.send` a `recipient` override and loop inside one request row. More code (new arg, new audit shape, a bespoke report table) and it breaks per-recipient telemetry/status reuse. Ponytail rung 2 (reuse what's here) wins with the one-row-per-recipient approach.

## 4. Idempotency — double-approve sends once

**Where double-send can occur:** starting the fan-out twice (two Approve clicks → two `workflow.start`). Within a single workflow, durable journaling already guarantees each `gmail.send` step runs exactly once even across replays — the risk is *two workflows*.

**Dedupe key + enforcement:** a **compare-and-set on plan status inside `executePlan`**. Convex mutations are serializable transactions, so a status CAS is the natural, race-free dedupe primitive (same shape `submit`/`markResolved` already rely on):
```typescript
// executePlan (tenantMutation)
const plan = await ctx.db.get(planId);
if (!plan || plan.tenantId !== ctx.tenantId) throw new Error("plan not found");
if (plan.status !== "draft") return { ok: true, alreadyStarted: true }; // idempotent no-op
await ctx.db.patch(planId, { status: "approved" });   // flip BEFORE start; 2nd concurrent tx sees "approved"
// seed per-recipient request rows...
await workflow.start(ctx, internal.<...>.deliverApprovedPlan, { planId, tenantId, requestIds }, { onComplete, context });
await ctx.db.patch(planId, { status: "delivering", workflowId });
```
The second approve — concurrent or later — reads `status !== "draft"` and no-ops. This mirrors the existing `deadLetters.markResolved` guard (`if (row.status !== "new") return`). No new dedup table.

**Note:** `submit` (the old intake) mints a fresh `correlationId` and does NOT dedupe — every call starts a workflow. The cockpit differs precisely because Approve must be idempotent, so the plan-status CAS is the added guard. This also depends on there being a plan/artifact row with a `status` field — **owned by the UI/artifacts sibling**; this lane needs `executePlan` to read+CAS it. Coordinate the field name/enum.

**Secondary idempotency already free:** `telemetry.writeTerminal` and the failed-terminal path are idempotent by correlationId, so even a step replay never doubles a telemetry/DLQ row.

## 5. Zero-sends-before-Approve enforcement point

Three structural facts, all already true in the codebase, make a pre-approve send impossible:
1. **`gmail.send` is only ever invoked from inside a delivery workflow.** grep confirms the only caller is `pipeline.ts` step 4; the new one is `deliverApprovedPlan`. The guided-conversation / draft phase never references `gmail.send`.
2. **`deliverApprovedPlan` is only started by `executePlan`** — make `executePlan` the sole `workflow.start(deliverApprovedPlan)` call site (a grep-able invariant, same as `submit` being the sole starter of `pipelineWorkflow`).
3. **The plan-status CAS (§4)** gates `executePlan`: the fan-out starts only when the plan transitions `draft → approved`. No Approve → status stays `draft` → no `workflow.start` → no send.

So "zero sends before Approve" is enforced at `executePlan`'s CAS + the single-caller invariant, not by a runtime check inside the send.

## 6. Redaction — what goes in audit/DLQ payloads (CLAUDE §4)

**Rule:** `audit.payload` and `deadLetters.payload` carry **refs / hashes / ids / counts ONLY** — never subject, body, or the recipient email address. Redact-then-write.

| Plane | ALLOWED (refs/ids) | FORBIDDEN (raw content) |
|-------|--------------------|-------------------------|
| `gmail.sent` audit | `{ requestId, messageId }` (existing shape — keep verbatim) | subject, body, recipient email |
| `deadletter.written` audit | `{ requestId, status:"new" }` (+ optional `workflowId`) | error strings with content, recipient, body |
| `deadLetters` row | `payload: { requestId }`, `error: String(e)` (a Gmail HTTP status/message — verify it carries no body) | recipient email, subject, body |
| `telemetry` row | counts/durations/outcome only (buildTelemetry) | any content |

**Recipient email is content-plane data:** it lives on `requests.recipient` (allowed there, shown in the REPORT), but must **never** appear in an audit or deadLetters payload. The existing `gmail.sent` audit already excludes it — keep it that way, and reference recipients by `requestId` in the per-row dead-letter. One live risk: `error: String(e)` from a Gmail non-2xx includes `await sendRes.text()` (gmail.ts line 101) — the Gmail API error body. That is Google's error JSON, not the user's email content, but the smoke's `assertNoRawPii`-style scan should confirm no subject/body/recipient needle leaks into `deadLetters.error`.

## 7. Smoke-test plan (matches the existing harness)

**Harness pattern** (`packages/backend/scripts/smokeRun.mjs`): Windows-safe `must(fn, args)` / `pollPass(fn, args)` invoke `npx convex run` via `spawnSync` (JSON args as one argv element; success/failure judged by CLI OUTPUT banner, not exit code — Node 24 teardown crash workaround). Each `smoke:*` script (`package.json`): seed via an `internalMutation`, then `pollPass` an `smokeAssert:*` `internalQuery` that throws on failure. Add `"smoke:fanout": "node ./scripts/run-smoke-fanout.mjs"`.

**New smoke: `run-smoke-fanout.mjs`** — mirror `run-smoke-pipeline.mjs`/`run-smoke-dlq.mjs`:
1. **Seeder** `smoke:seedFanout({ correlationId, planId, recipients })` (new `internalMutation` in `smoke.ts`): insert one `requests` row per recipient (tenant `"smoke"`, `SMOKE::` body so no LLM key needed, status `approved`), then `workflow.start(internal.<...>.deliverApprovedPlan, …)` with the onComplete-DLQ context (`payload: { planId }`).
   - Tenant `"smoke"` has no Gmail token → each `gmail.send` returns `{ delivered:false, reason:"not_connected" }` → row holds at `awaiting_reauth` (the automatable half — a real send needs human OAuth, manual per VALIDATION). This proves the loop reaches every recipient.
2. **Forced-failure recipient → DLQ:** include one recipient whose send is forced to throw terminally. Reuse the `smoke.boom`/`SMOKE_FAILURE` convention: a `SMOKE::fail` sentinel recipient/body that makes `gmail.send` throw (or a seeded row the assertion targets), so `pollPass("smokeAssert:assertRecipientDeadLettered", { correlationId })` confirms exactly that row got a `deadLetters` row + `deadletter.written` audit + `status:"failed"` + one `failed` telemetry row — **while the sibling rows still reached `awaiting_reauth`/`sent`** (the isolation assertion).
3. **Idempotency:** call `executePlan`/seed twice for one `planId`; assert exactly one workflow ran and (with a token) one `gmail.sent` audit per recipient — double-approve sends once.
4. **No-raw-PII invariant:** reuse the `assertNoRawPii` pattern (`smokeAssert.ts`) — scan every audit row (by cid), the deadLetters row, and telemetry for subject/body/recipient needles; assert none appear.

New assertions go in `smokeAssert.ts` as `internalQuery`s that throw on failure (same style as `assertDeadLetter`, `assertPipelineDelivered`). This is the phase's runnable check (ponytail: one check behind the loop) — `convex-test` cannot emulate component-backed workflows, so the dev-deployment smoke is the test, consistent with every existing durable-flow check.

## 8. Open questions / risks

1. **`planId` type + plan-status enum (cross-sibling).** The dedupe CAS (§4) and the REPORT grouping (§3) both need a plan artifact row with a `status` field and an id this lane can reference. The UI/artifacts sibling owns that table. **Action:** agree on `planId` type (`v.id("plans")` vs `v.string()`) and the status enum (`draft → approved → delivering`) before planning. LOW risk, pure coordination.
2. **Per-row correlationId plumbing.** Passing a `correlationIds` array into the workflow args (parallel to `requestIds`) is the deterministic, no-extra-read choice; the alternative (read cid from the row inside a step) adds a mutation round-trip. Recommend the array. HIGH confidence.
3. **`deadLetters.workflowId` is `v.string()` (required).** The inline `deadLetterRecipient` has no per-row workflowId at hand (it's the fan-out's, not a per-recipient one). Passing `""` or the fan-out's `step.workflowId` both satisfy the schema; prefer `step.workflowId` for traceability. Trivial.
4. **Group-email mode.** One row with all addresses in `recipient` (Gmail `To:` accepts a comma-joined list — verify `buildMime`'s single `To:` line handles it, gmail.ts line 21). If not, group mode may need a joined-address builder. Verify during planning; individual mode is unaffected.
5. **`error: String(e)` content check (§6).** Confirm the Gmail non-2xx `await sendRes.text()` body carries no echoed recipient/subject; the no-raw-PII smoke covers it, but flag for the redaction review.
6. **onComplete DLQ vs per-row DLQ overlap.** With per-row `try/catch`, the workflow completes `success`, so `onPipelineComplete` archives nothing (correct). Keep onComplete wired anyway as the catch-all for a catastrophic whole-workflow failure (e.g. a throw outside the try). No conflict — onComplete only archives non-success.
