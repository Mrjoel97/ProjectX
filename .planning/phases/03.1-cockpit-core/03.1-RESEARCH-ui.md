## Summary

The frontend is **Next 16 App Router + React 19**, no Tailwind, no component library, no
resizable-pane dep. Styling is **inline `style={}` objects + CSS variables in
`apps/web/app/globals.css`**. All authed pages live under the `(app)` route group and inherit
one shell: `apps/web/app/(app)/layout.tsx`. Live data is plain `useQuery(api.*)` from
`convex/react` — Convex reactivity is already the "live update" mechanism used by
`DeadLetterBadge` and `ReconnectBanner`, and it is exactly what the live REPORT card needs.

**The Connect-Gmail infinite-loading bug is already fixed at its root cause** by commit
`18c8442`, which gated the entire `(app)` shell behind `<Authenticated>` so no tenant-scoped
query mounts before the client auth token is attached, plus a 6-second stall fallback. The new
`/dashboard/workspace` cockpit page lives under the same shell and inherits the fix for free.

The cockpit is greenfield in three spots: (1) a two-pane resizable layout, (2) teal design
tokens (current tokens are an amber "custody & clearance" theme), (3) `@convex-dev/agent` React
hooks — installed in the backend (0.6.4) and exposing `useThreadMessages`/`useUIMessages` but
**not yet a dependency of `apps/web`**.

**Primary recommendation:** Build `/dashboard/workspace` as one new client page under `(app)`,
reuse the shell + inline-style conventions, do the resizable divider with **native CSS grid +
a pointer-drag `role="separator"` handle persisted to `localStorage`** (no new dep), render
PLAN/DRAFT/REPORT as a `switch`-on-`artifact.type` card dispatcher fed by a live
`useQuery(api.artifacts.*)`, add teal CSS variables to `globals.css`, and add
`@convex-dev/agent@0.6.4` to `apps/web` for the chat hooks.

## 2. Connect-Gmail bug — current state after `18c8442`

**Status: root-caused and fixed. Groundwork is essentially "verify," not "build."**

`git show 18c8442` touched exactly one file — `apps/web/app/(app)/layout.tsx` (+69/-3). The
fix (read in full at that path):

- **Root cause identified:** authed pages issue tenant-scoped queries that *fail closed*
  without an identity. The old shell rendered them without checking the Convex **client's**
  auth state, so when a session's client token wasn't attached, `gmailStatus` hung `undefined`
  forever → eternal "Loading…" on `/connect-gmail`.
- **Fix (correct, at the shared shell all authed pages route through):** `AppShell` renders
  `children` **only inside `<Authenticated>`** (guarantees a token before any query mounts);
  `<AuthLoading>`/`<Unauthenticated>` render an `AuthGate` with a real "Sign in again" path
  (teal `#009689`), and a **6s stall timeout** flips loading → sign-in so a never-resolving
  token can't strand a spinner.

**Why this covers the cockpit:** `/dashboard/workspace` sits under the same `(app)` group, so
it inherits the `<Authenticated>` gate automatically — no per-page auth handling needed.

**What remains (small, verify-level):**
1. The `connect-gmail/page.tsx` still shows `status === undefined ? "Loading…"` and a
   `"Preparing consent link…"` fallback while `gmailConnectUrl` resolves. These are now
   *bounded* (a token is guaranteed before mount), but there is **no per-query timeout** — if
   `gmailConnectUrl` itself hangs/throws, "Preparing consent link…" shows indefinitely. LOW
   likelihood; flag as a verification step (E2E), not a rebuild. Optional lazy hardening: an
   error boundary or a local timeout on that one message.
2. **Verify** the fix end-to-end on a real Google-authed session (the original repro) as part
   of the phase gate — the fix landed but the phase treats it as groundwork to confirm.

**Do NOT** re-touch `layout.tsx`'s auth gate; the fix is correct and shared.

## 3. Resizable two-pane — recommendation

**Recommendation: native CSS grid + a pointer-drag `role="separator"` handle, state persisted
to `localStorage`. No new dependency.** (Ponytail: rung 4 native beats rung 5 adding
`react-resizable-panels` for ~40 lines; a11y is handled explicitly, see below.)

- **Layout:** a client component with `display: grid; grid-template-columns: <chatPct>% 6px 1fr`.
  Chat left (~30% default), 6px handle, workspace right (~70%). Matches design §Layout.
- **Drag:** on the handle, `onPointerDown` → capture pointer, `onPointerMove` computes
  `pct = clamp(20, (clientX - containerLeft)/containerWidth*100, 80)` (enforces the min ~20%
  each pane), `onPointerUp` releases + writes to storage. ~40 lines, one `useState`.
- **Accessibility (NOT optional — CLAUDE.md/ponytail "never lazy about accessibility"):**
  `role="separator"`, `aria-orientation="vertical"`, `aria-valuenow={pct}`, `tabIndex={0}`,
  and `onKeyDown` arrow-left/right to nudge ±2% (keyboard resize). `cursor: col-resize`.
- **Per-user persistence:** `localStorage` keyed by user id, e.g.
  `cockpit.split.<userId>` (get the id from an existing identity query / the auth context).
  Read on mount (lazy `useState` initializer), write on `pointerUp`/key change. This is
  per-user *within a browser*. **See Open Question §6** — the design says "persisted per user";
  if cross-device persistence is required, that needs a Convex `userPrefs` row instead.
- **`ponytail:` comment to leave:** `// ponytail: localStorage split, per-user-per-browser.
  Upgrade to a convex userPrefs row if cross-device sync is required.`

**Alternative considered:** `react-resizable-panels` (latest, popular, gives keyboard a11y +
`autoSaveId` localStorage persistence + min sizes out of the box). **Tradeoff:** it's a new
dep for a problem ~40 native lines solve; adopt only if the native handle's touch/keyboard
behaviour proves fiddly in E2E. Do not add it up front.

## 4. Artifact-card rendering (PLAN / DRAFT / REPORT) + live REPORT

**Rendering:** a single **card dispatcher** — `switch (artifact.type)` → `<PlanCard>` /
`<DraftCard>` / `<ReportCard>` — mapped over the artifact list for the active thread. Cards are
plain inline-styled `<div>`s (reuse the `box` const style from `review/[id]`). Card contents
per design §Layout:
- **PLAN:** recipient chips, mode (individual/group), subject, body preview, steps, one
  **Approve** button (reuse the `review/[id]` approve pattern; onClick → `executePlan` seam §7,
  guarded by `busy`, idempotent per design "double-approve → sends once").
- **DRAFT (`EMAIL`):** full email body; "editable via chat" means edits arrive as new
  artifact versions from the agent — the card just re-renders the latest, no inline editor
  required in slice 1.
- **REPORT:** one row per recipient — status + Gmail message id + audit link.

**How live REPORT updates arrive (the key mechanism):** **Convex query reactivity — no polling,
no socket code.** The card list comes from a live `useQuery(api.artifacts.listForThread, {
threadId })` (seam §7). When the `deliverApprovedPlan` workflow patches a per-recipient row in
the artifacts/report table, every subscribed `useQuery` re-runs and the REPORT card re-renders
automatically. This is the identical pattern already proven by `DeadLetterBadge`
(`api.deadLetters.newCount`) and `ReconnectBanner` (`api.requests.list`). Handle `undefined`
(loading) → skeleton/nothing; empty array → "no artifacts yet."

**Chat pane (left):** rendered from `@convex-dev/agent` React hooks. The package exposes
(verified in `node_modules/.pnpm/@convex-dev+agent@0.6.4.../dist/react/`):
`useThreadMessages`, `useUIMessages`, `useStreamingThreadMessages`, `useStreamingUIMessages`,
`useSmoothText`, `useStreamingText`, `optimisticallySendMessage`. Import from
`@convex-dev/agent/react`.
- **Blocker to note:** `@convex-dev/agent` is a dependency of `packages/backend` only
  (`packages/backend/convex/convex.config.ts`), **not `apps/web`**. Add
  `"@convex-dev/agent": "0.6.4"` to `apps/web/package.json` (exact pin — CLAUDE.md rule 6, and
  it must match the backend 0.6.4).
- **Lazy default:** start with non-streaming `useThreadMessages` (list) + a send-message
  mutation seam; the live activity chips ("Drafting…", "Sending to 5", "Sent ✓") can be driven
  by artifact/thread status queries. Upgrade to `useUIMessages`/`useSmoothText` streaming only
  if token-by-token rendering is wanted. (`ponytail:` note the ceiling.)

## 5. Teal token wiring

Current `globals.css` `:root` is an **amber "custody & clearance" theme** (`--paper #f2f3f5`,
`--ink`, `--held #f0a22e`, `--released #3e9e75`) built for the marketing/landing + auth surfaces
— **no teal tokens exist**. Add the design's teal palette as CSS variables (exact hex from
design doc §Layout):

```css
:root {
  --teal-900: #0B4F4A; /* left rail / dark frame */
  --teal-600: #009689; /* primary action: send, active tab, Approve, CTAs */
  --teal-400: #40CAD0; /* highlight / logo / glow */
  --canvas:   #F8FAFC; /* slate-50 app canvas / panels */
  --card:     #FFFFFF; /* cards & bubbles */
}
```

Notes:
- `#009689` is **already hardcoded** in `layout.tsx` `AuthGate` ("Sign in again" button) and a
  blue `#2563eb` sits in `connect-gmail`/`review` buttons — the cockpit standardizes on
  `--teal-600` for primary actions. Optional cheap cleanup: swap those literals to the var.
- Keep the inline-style convention: reference via `var(--teal-600)` in `style={}` objects, or
  add a few cockpit-scoped classes to `globals.css`. Don't introduce Tailwind.
- **Contrast check (accessibility, verify):** teal-600 `#009689` as *text on white* is ~2.9:1
  — fails WCAG AA for normal text. It's fine as a **button background with white text** (large
  / bold) and for large headings. Use it for fills/CTAs, not small body text; darken for any
  small teal text. (Same discipline `globals.css` L14–16 already applies to amber.)

## 6. Open questions / risks

1. **Divider persistence scope.** Design says "persisted per user." `localStorage` gives
   per-user *per-browser* (lazy default). Cross-device sync needs a Convex `userPrefs` mutation
   + row. **Recommendation:** localStorage now, flag as the ceiling. Confirm with planner which
   is intended. No sibling owns `userPrefs` — if cross-device is required it's new backend work
   for this phase.
2. **`@convex-dev/agent` must be added to `apps/web` deps** (currently backend-only), pinned
   `0.6.4` to match. Small but a prerequisite for the chat pane.
3. **Streaming vs static chat.** `useUIMessages`+`useSmoothText` (streaming) vs
   `useThreadMessages` (static list). Recommend static first; streaming is an upgrade.
4. **Teal-600 contrast** on small text fails AA — restrict to fills/CTAs (see §5).
5. **`gmailConnectUrl` residual** — no per-query timeout on the "Preparing consent link…"
   fallback (§2). LOW risk; cover with an E2E assertion rather than code.
6. **Thread lifecycle seam.** Where a thread is created (on first message? on page load?) and
   how its `threadId` reaches the page is a sibling/backend decision the UI depends on — the
   cockpit needs a `threadId` to call both the chat hooks and the artifact query (§7).
7. **Old pages stay.** Design scope: retiring `/submit` + `/review` is OUT (later slice). Add
   `/dashboard/workspace` alongside; keep existing NAV entries.
