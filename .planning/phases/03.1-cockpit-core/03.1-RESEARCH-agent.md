## Summary

The `@convex-dev/agent@0.6.4` component is **installed and registered** (`convex.config.ts` line 3, `app.use(agent)`) but **never instantiated** — the cockpit is the codebase's FIRST `new Agent(...)`/`createTool`/`createThread` use. The component owns its own thread/message tables (registered via `app.use`), so **no `threads`/`messages` table goes in `schema.ts`** — only the new `artifacts` table.

The governed drafting engine already exists and must be reused verbatim: `convex/llm.ts` loads `EMAIL_DRAFTER_SKILL` from the registry at runtime (`internal.skills.getActiveSkill`), runs `generateObject(draftSchema)` through the Vercel AI Gateway with a CHEAP_MODEL fallback, and honors a per-request `SMOKE::` sentinel for offline determinism. The drafter skill row is **already seeded** (`skills.seedSkills`). The critical constraint: `llm.ts` is the **ONLY `"use node"` module** and must stay that way (adding a second node module re-triggers a TS circular-inference cliff — comments at `llm.ts:10-12,63-66`), so any cockpit draft action MUST live inside `llm.ts`.

**Primary recommendation:** Drive question selection with the pure `emailIntent` module (deterministic, testable — sibling owns it); use the agent thread purely for message persistence + streaming; call the LLM only for the body draft by adding a thin `draftCockpit` internalAction **inside `llm.ts`** that reuses `parseSmoke` + the drafter skill. Model `proposeEmailPlan` as an agent `createTool` (or code-invoked write) that inserts a PLAN artifact; model `executePlan` as a **human-gated `tenantMutation`** (NOT an LLM tool — approval is a human gate) that idempotently starts `deliverApprovedPlan`, mirroring the existing `requests.submit` → `workflow.start` pattern.

## 2. Tool-definition pattern for proposeEmailPlan / executePlan

**`createTool` (v0.6.0+ shape, from `dist/client/createTool.d.ts`):** uses `inputSchema` + `execute` (NOT `args`/`handler` — those throw a compile error now). `ctx` inside a tool is a full `ActionCtx` plus `{ agent, userId, threadId, messageId }`, so tools reach the DB via `ctx.runMutation`/`ctx.runQuery` to **internal** functions.

```ts
// convex/cockpit.ts  (or convex/artifacts.ts)
import { createTool } from "@convex-dev/agent";
import { z } from "zod";
import { internal } from "./_generated/api";

// proposeEmailPlan — the LLM (or code, see §7) calls this when emailIntent reports slots complete.
// It WRITES a PLAN artifact; it does NOT send. Recipient is structural, never model-invented (mirrors validateSubmit).
export const proposeEmailPlan = createTool({
  description: "Assemble the approved-pending email PLAN once all slots are filled.",
  inputSchema: z.object({
    recipients: z.array(z.string()),           // validated emails, collected by emailIntent
    mode: z.enum(["individual", "group"]),
    subject: z.string(),
    body: z.string(),
  }),
  execute: async (ctx, input) => {
    // ctx has threadId + userId (tenant). Write through an INTERNAL mutation (tenant scoping).
    const planId = await ctx.runMutation(internal.artifacts.insertPlan, {
      tenantId: ctx.userId!,          // pass userId=tenantId when creating the thread
      threadId: ctx.threadId!,
      recipients: input.recipients,
      mode: input.mode,
      subject: input.subject,
      body: input.body,
    });
    return { planId };                // returned to the model / rendered as the PLAN card
  },
});
```

**`executePlan` is NOT a `createTool`** — approval is a **human gate** ("zero sends before Approve", "double-approve → idempotent"). Model it as a `tenantMutation` invoked by the Approve button, exactly like the existing `requests.submitDecision`/`submit` pattern (`requests.ts:40,174`):

```ts
// convex/cockpit.ts
import { tenantMutation } from "./lib/functions";
import { v } from "convex/values";
import { internal } from "./_generated/api";
import { workflow } from "./index";

export const executePlan = tenantMutation({
  args: { planId: v.id("artifacts") },
  handler: async (ctx, { planId }) => {
    const plan = await ctx.db.get(planId);
    if (!plan || plan.tenantId !== ctx.tenantId) throw new Error("plan not found");
    // Idempotency: only the first approve transitions proposed→executing (§5).
    if (plan.status !== "proposed") return { ok: true, workflowId: plan.workflowId };

    const correlationId = crypto.randomUUID(); // server-minted, names the delivery + report
    const workflowId = await workflow.start(
      ctx,
      internal.deliverApprovedPlan.run,        // SIBLING owns the workflow body
      { tenantId: ctx.tenantId, correlationId, planId },
      { onComplete: internal.deadLetter.onPipelineComplete,
        context: { tenantId: ctx.tenantId, correlationId, payload: { planId, correlationId } } }, // refs only, §4
    );
    await ctx.db.patch(planId, { status: "executing", correlationId, workflowId });
    return { ok: true, workflowId };
  },
});
```

Reuse notes: `workflow` is `convex/index.ts` `WorkflowManager`. `onPipelineComplete` DLQ wiring already exists (`deadLetter.ts`). Payload carries `planId` + `correlationId` **refs only** (CLAUDE.md §4).

## 4. Proposed `artifacts` table schema (redaction-safe)

**Redaction-safety note:** `artifacts` is a **content-plane** table like `requests` (CLAUDE.md §4 — raw content lives in content tables, NEVER in `audit`/`deadLetters` payloads). So subject/body/recipients CAN live here. Audit events referencing an artifact carry only `artifactId` + counts. Mirror the `requests` table conventions (tenantId + correlationId + the index its reactive query needs).

Ponytail: ONE table discriminated by `kind`; explicit named fields (not a `v.any()` blob) for the content plane since it's read+validated, matching how `requests` names its content fields.

```ts
// schema.ts — add alongside requests/telemetry
artifacts: defineTable({
  tenantId: v.string(),
  threadId: v.string(),                 // agent thread → renders cards in the workspace pane
  correlationId: v.optional(v.string()), // set on executePlan; links plan → delivery → report (idempotency key)
  kind: v.union(v.literal("plan"), v.literal("draft"), v.literal("report")),
  // Lifecycle (plan): proposed → executing → done. draft/report use created/done.
  status: v.union(
    v.literal("proposed"),
    v.literal("executing"),
    v.literal("done"),
  ),
  // Plan/draft content plane (raw — allowed here, NEVER in audit/DLQ):
  recipients: v.optional(v.array(v.string())),
  mode: v.optional(v.union(v.literal("individual"), v.literal("group"))),
  subject: v.optional(v.string()),
  body: v.optional(v.string()),
  // Report: per-recipient live status, patched by the fan-out workflow (sibling).
  report: v.optional(v.array(v.object({
    recipient: v.string(),
    status: v.union(v.literal("pending"), v.literal("sent"), v.literal("failed"), v.literal("awaiting_reauth")),
    messageId: v.optional(v.string()),
    // error NAME only if failed — no raw content:
    error: v.optional(v.string()),
  }))),
  workflowId: v.optional(v.string()),   // set on executePlan
  createdAt: v.number(),
})
  .index("by_thread", ["tenantId", "threadId"])       // render all cards for a thread
  .index("by_correlation", ["correlationId"]),        // fan-out patches the report row live
```

Adapter mutations live in a thin `convex/artifacts.ts` (internal writers + `tenantQuery` readers): `insertPlan`, `insertDraft`, `insertReport`, `patchReportRow` (internal, called by the workflow). Client reads via a `tenantQuery listByThread` (reactive → cards update live). Skipped a separate `data: v.any()` blob → named fields cost nothing extra and stay validated; add a blob only if a later slice needs freeform artifact kinds.

## 5. executePlan → deliverApprovedPlan handoff seam + idempotency

**Seam (name it, sibling owns the body):** `internal.deliverApprovedPlan.run` — a `workflow.define` that fans out per recipient over the existing `internal.gmail.send` + retrier + `audit`/`telemetry`/`deadLetters` primitives (design doc "Backend flow" step 5).

**What `executePlan` passes:** `{ tenantId, correlationId, planId }` only — the workflow reads the PLAN artifact (`ctx.runQuery` on `planId`) for recipients/mode/subject/body. Keeps the workflow args tiny and content out of the workflow context/DLQ payload (payload = `{ planId, correlationId }` refs only, §4).

**Idempotency key = the plan's status transition, guarded in a single mutation:**
- `executePlan` reads the plan; if `status !== "proposed"` it returns the existing `workflowId` (no second workflow) — **double-approve sends once** (design "Double-approve → idempotent").
- The `proposed → executing` patch + `workflow.start` happen in the same `tenantMutation` (atomic — Convex mutations are transactional), so two concurrent approves cannot both pass the guard.
- `correlationId` is server-minted here (never client-supplied — mirrors `requests.submit:47` "must never be client-supplied") and is the durable idempotency/name key threaded into delivery, audit, telemetry, and the report artifact.

**Gmail-not-connected pre-check:** design says "No Gmail connected → stop before planning." The `executePlan`/propose path should check `internal.gmailAuth.getTokens` (already exists, used by `gmail.send`) and refuse — reuse, don't rebuild.

Report artifact: created at execute time (rows = recipients, all `pending`), then `patchReportRow` (internal, by_correlation) flips each to sent/failed/awaiting_reauth live — the sibling workflow calls it; the table + patch mutation are this lane's deliverable.

## 6. SMOKE:: offline draft path

**Existing seam (`llm.ts:36-57`):** a per-request `SMOKE::route=<r>::[cache=1::][fail=primary::]` sentinel embedded in the (redacted) goal text short-circuits the real LLM so smokes run offline (no `AI_GATEWAY_API_KEY` on the local backend). `parseSmoke(text)` detects it; `draftUncached`/`draft` return a fixed `{ subject: "Smoke Subject", body: "Smoke draft for <hash>" }` and honor `fail=primary` to exercise the fallback path. It degrades ONLY the caller's own request (content sentinel, not an env flag).

**Reuse for the cockpit draft — CRITICAL constraint:** the draft step must NOT be a new `"use node"` module. `llm.ts` is the ONLY node module and a second one re-triggers the TS circular-inference cliff (`llm.ts:10-12,63-66`). Therefore add a thin `draftCockpit` **inside `llm.ts`** (or generalize the existing `draftUncached`) that:
1. loads `EMAIL_DRAFTER_SKILL` via `internal.skills.getActiveSkill`,
2. runs `parseSmoke(bodyIntentText)` → if sentinel, return the deterministic smoke draft (no model call),
3. else `generateObject({ model, schema: draftSchema, system: skill.body, prompt })` with the same CHEAP_MODEL `isFallbackEligible` fallback + `AbortSignal.timeout(45s)`.

Input to this action is the body-intent text. Two open items: (a) whether the cockpit draft routes through `guardrails.prepare` redaction (the pipeline does before drafting — §7 open question), (b) the existing `draftUncached` is keyed to `safeTextHash`/`requests` rows; the cockpit conversation is not a `requests` row, so either seed a lightweight request-equivalent or add a hash-keyed variant that takes the redacted text directly. Laziest: a sibling internalAction in `llm.ts` taking `{ tenantId, safeText, safeTextHash }` that shares `parseSmoke` + the drafter skill + `generateObject` + fallback. For the E2E Playwright smoke, the user types a body intent containing `SMOKE::route=direct_llm::` and the draft returns deterministically offline (design "Testing" bullet 3).

## 7. Open questions / risks

1. **Conversation control: LLM-driven agent loop vs. deterministic `emailIntent` (CENTRAL DECISION).**
   - (A) LLM-driven: `agent.generateText` with `tools: { proposeEmailPlan }`; the model decides when slots are full and calls the tool. Native to the agent component, but non-deterministic and harder to test.
   - (B) Deterministic: pure `emailIntent` (sibling's core module) computes the next question; the agent thread is just message store; the LLM is used ONLY for the body draft (§6); `proposeEmailPlan` is code-invoked when `emailIntent.complete`.
   - **Recommendation: (B).** Matches "nothing sends on assumption", the pure-assert testability of `emailIntent` (design "Testing" bullet 1), and ponytail (no LLM where a deterministic checklist works). It also needs no new conversation skill/seed. Flag for the planner to confirm.

2. **`tenantAction` wrapper.** No tenant-scoped action wrapper exists (`functions.ts` has only query/mutation). The cockpit's public agent action needs one. Recommend adding `tenantAction` via `customAction` (convex-helpers, already installed) reusing `requireTenant`. Small, consistent, keeps the raw-`action` ban intact.

3. **Guardrails on the conversation/draft input.** The pipeline redacts via `guardrails.prepare` before the LLM sees text. The cockpit sends user messages to the LLM too (at least the body intent → drafter). Does the draft step reuse `guardrails.prepare`/PII scan? Likely yes for the draft input; the free-form chat is broader. **In-lane recommendation:** route the draft body-intent through the existing scan (reuse `scanText`/`guardrails.prepare`), and flag the broader "raw chat → LLM" surface to the guardrails owner. Governance invariant to verify: no raw email content in any audit/DLQ payload (design "Testing" bullet 4).

4. **`draftUncached` is `requests`/`safeTextHash`-coupled.** Reusing it for the cockpit either forces a `requests` row or a new redacted-text-in variant. Recommend the variant inside `llm.ts` (§6) — avoids fabricating a `requests` row per chat.

5. **Thread ↔ tenant binding.** Pass `userId = tenantId` when calling `createThread`, so `ctx.userId` inside tools equals the tenant. Verify the component's `userId` cross-thread search doesn't leak across tenants (single-owner beta makes this low-risk now, but note for multi-tenant).

6. **Streaming vs. generate.** For the chat pane, `streamText` + `@convex-dev/agent/react` gives live "Drafting…" UX (design left pane). Sibling UI lane owns rendering; this lane just needs to expose a streaming-capable action. Non-blocking.
