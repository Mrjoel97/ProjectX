<objective>
The second budget rail, and the transactional JOB reservation that is this phase's real money guard.

Purpose: a per-request cap bounds NOTHING when a reel is N clips PLUS N voice takes PLUS an STT pass
PLUS a render — six 480p×10 s clips are six passing $0.50 requests and one $3.00 job. And the shipped
LLM rail's shape (check in `prepare`, consume in `recordSpend` afterwards) **cannot be copied**: the
line items are in flight concurrently for minutes, so post-hoc recordings all pass against a window
nothing has consumed — a TOCTOU on money. D10 states it plainly: the job *"now has strictly more line
items, so the TOCTOU argument that killed the check-then-record-later shape is stronger, not weaker."*
The fix is one mutation that estimates the whole job, refuses over the cap, checks the per-tenant
window and consumes it with `reserve: true`, all in the same serializable transaction.

Output: `mediaSpendCents` + `deploymentMediaSpendCents` at the D10 numbers, the media kill switch,
and `media.reserveJob`.
</objective>

Implement the reservation as a **plain exported async function plus a thin `internalMutation`
wrapper**:

```ts
export async function reserveJobInner(
  ctx: MutationCtx,
  a: { tenantId: string; planId: Id<"plans">; blocks: readonly Block[]; clipSeconds: number;
       withCaptions: boolean },
): Promise<{ ok: true; batchId: string; estUsd: number; estCents: number; lineCount: number }
         | { ok: false; reason: "kill_switch" | "unknown_model" | "over_job_cap" | "illegal_duration"
                              | "narration_too_long"
                              | "media_daily_exhausted" | "deployment_media_exhausted" }>;

export const reserveJob = internalMutation({ /* args validators; body = reserveJobInner */ });
```

**Why a plain function and not only a mutation:** plan 20-07's approve arm runs INSIDE `executePlan`,
which is itself a `tenantMutation` — and a Convex mutation cannot `runMutation`. Calling
`reserveJobInner` directly keeps the reservation in the SAME transaction as the plan's
`proposed → approved` CAS, which is exactly the property that makes "approve once, reserve once"
true. The `internalMutation` wrapper exists for the canvas path (plan 20-09) and for tests.

The algorithm, in order, and **the order is load-bearing**:
1. `const cfg = await getGuardrailConfig(ctx)` → `if (cfg.killSwitch || cfg.mediaKillSwitch) return { ok:false, reason:"kill_switch" }`.
2. **The free pre-flight guard, BEFORE anything else costs a thought (delta pitfall 13).** For every
   block, `block.narration.length <= MAX_CHARS_PER_BLOCK`; otherwise return
   `{ ok:false, reason:"narration_too_long" }`. **This check MUST live upstream of the reserve, not
   downstream** — the whole point is that an overrun is caught before payment rather than by `ffprobe`
   after $3.00 of clips have landed. Comment it with that sentence. A narration-length validation
   that lives downstream of the reservation is the warning sign the delta names.
3. **Build the WHOLE job's spec list — this is what D10 changed.** One array, in this order:
   - one `{ kind:"video", model, resolution, seconds: clipSeconds }` per PAID block (`isPaidBlock`),
     with model and resolution pinned from `MEDIA_DEFAULT_VIDEO` — never left for fal to default;
   - one `{ kind:"tts", model, characters }` per block, where **`characters = block.narration.length * 2`**;
   - if `withCaptions`, one `{ kind:"stt", model, audioMinutes: blocks.length * clipSeconds / 60 }`;
   - exactly one `{ kind:"render" }` — the flat `MEDIA_SANDBOX_USD_PER_RENDER` constant.
   **The 2× on the voice line is deliberate and needs its comment:** *"reserved at twice the character
   estimate so ONE rewrite round is already paid for. The provider returns no duration, so an
   overrunning line is only provable in the sandbox; when it happens the cure is a rewrite and a
   re-voice, and a job that cannot afford its own cure would strand a paid deck. At $0.012 the
   doubling is free, and the fail-closed direction is over-reserving."*
4. `chooseMediaBatch(specs, MEDIA_JOB_CAP_USD)` → on Err, return its `code` as the reason. FAIL
   CLOSED — never guess a price. **`chooseMediaBatch` floors the cents ONCE**, so `est.value.estCents`
   is the ONE number that moves both windows; the per-line `estUsd` values go onto the rows unfloored.
5. `rateLimiter.check(ctx, "mediaSpendCents", { key: tenantId, count: estCents })` → refuse
   `media_daily_exhausted`. **Tenant checked FIRST**, so a tenant that is personally out is told so
   rather than blamed for a global pause (the `prepare` ordering, verbatim).
6. `rateLimiter.check(ctx, "deploymentMediaSpendCents", { count: estCents })` → refuse `deployment_media_exhausted`.
7. `rateLimiter.limit(ctx, "mediaSpendCents", { key: tenantId, count: estCents, reserve: true })` **and**
   the same for `deploymentMediaSpendCents`. **CONSUME NOW, before any POST exists.**
8. `batchId = crypto.randomUUID()` (server-minted; the shipped `cockpit.ts` correlationId idiom).
   Insert one `mediaJobs` row per spec **except the `render` line** (the render is a plan-row concern,
   not a provider job — it has no `falRequestId` and no webhook), each carrying its own `estUsd`,
   `spec`, `kind`, `model`, `promptHash = await contentHash(prompt-or-narration)` (`lib/hash.ts`),
   `blockIndex` (`-1` for the deck-wide `stt` row), `createdAt`/`updatedAt`.
9. Return `{ ok: true, batchId, estUsd, estCents, lineCount }`.

**Steps 5-7 MUST be in the same mutation.** Convex mutations are serializable, so check-then-limit is
atomic and two concurrent jobs cannot both pass a check against a window neither has consumed.
Splitting them across an action boundary is the defect this whole task exists to prevent — leave a
comment saying so.

**Reserve BEFORE the POST, not after — this is the one place media DIVERGES from the LLM rail.**
`prepare`/`recordSpend` can safely check-then-record-later because LLM calls inside a turn are serial
and an overshoot is cents. Here 13+ jobs are submitted back-to-back and land minutes apart, so
post-hoc recording would let all of them fire against a window that had room for one. Comment it with
`20-PROVIDER-EVAL.md` §4's line: *an LLM overshoot is cents, a media overshoot is dollars.*

**The sandbox render is reserved as a flat cost line, and D10 requires that be stated rather than
implied.** Comment at the `{ kind: "render" }` spec: *"D10 — sandbox compute is a cost line too.
Estimated at a flat constant because Vercel exposes no per-sandbox billing at request time; the
ceiling and its upgrade path are named on `MEDIA_SANDBOX_USD_PER_RENDER` in the price table. It is
reserved here so that a job that cannot afford its own render is refused before its clips are bought."*

`ponytail:` comment on the no-refund rule: *"if 3 of 6 blocks come back provider_blocked, the reserved
cents stay consumed. Over-reservation is the fail-closed bias, same as `Math.max(1, Math.ceil(...))`.
Refunding turns a rate-limiter window into a ledger; if drift ever proves material the upgrade path is
a real spend table, not a credit call."*

Regenerate-one-block is a **job of one block** through this identical path (one video line, one tts
line, one render line — because regenerating a block invalidates the reel and forces a re-render).
No second rail, no second cap, no bypass. Say so in the doc comment.
