<objective>
The assemble stage as an orchestration: the moment every clip and every voice take of a reel has
landed, render them into one mp4, publish it only if its governance record validates, and delete the
intermediates that are now 55 MB of dead weight.

Purpose: three separate things that all live at this seam and nowhere else.
1. **The trigger.** N clips and N voice takes land minutes apart through a webhook. Something must
   notice when the last one arrives. The lazy correct answer is not a chain, a workflow or a poller —
   it is one check inside the landing mutation that already runs on every arrival.
2. **The publish gate.** D8: *"a final video without an `assembly.json` was hand-assembled."* Presence
   of a VALID sidecar is the proof-of-governed-render, so publishing must be conditional on it.
3. **Retention (D12b).** A job produces ~55 MB — 6 clips (~30 MB) + 6 voice takes (~5 MB) +
   `final.mp4` (~10 MB) + the captioned cut (~10 MB). At D10's 2 jobs/day that is **3.3 GB/month**
   against a Convex Free/Starter allowance of **1 GB total**. Without a rule the rail fills the
   deployment. With one it is a single `ctx.storage.delete()` loop.

Output: the trigger, the terminal, the retention rule and the dead-letter path.
</objective>

```ts
// The batch-complete check. No workflow, no poller, no chain entry action: landResult already runs
// on every arrival and a Convex mutation is serializable, so the pending -> rendering transition IS
// the once-only guard. Two concurrent landings cannot both observe "pending".
const siblings = await ctx.db.query("mediaJobs")
  .withIndex("by_batch", q => q.eq("tenantId", tenantId).eq("batchId", batchId)).collect();
const renderable = siblings.filter(s => s.kind === "video" || s.kind === "image" || s.kind === "tts");
if (renderable.every(s => s.status === "succeeded") && plan.renderStatus === "pending") {
  await ctx.db.patch(planId, { renderStatus: "rendering" });
  await ctx.scheduler.runAfter(0, internal.render.renderReel, { tenantId, planId, batchId });
}
```
If any renderable sibling is `failed`/`blocked` and none is still in flight, patch
`renderStatus: "failed"`, `renderReason: "incomplete_batch"` instead. **Do not start a render that
will produce a reel with a missing block** — D8's fixed-window contract makes a missing clip a hard

// ponytail: delete-on-success is the WHOLE retention policy. No TTL, no cron, no sweep job.

readable), then delete. A crash between the two leaves orphaned blobs, which is 35 MB of waste; a
crash in the other order leaves a published reel whose tiles point at deleted blobs, which is a broken
canvas. Fail toward waste, not toward a lie.
