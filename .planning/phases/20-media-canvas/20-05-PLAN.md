<objective>
The fal submit adapter: build a request body that is a pure function of the priced spec, POST it to
fal's queue with a per-job authenticated webhook URL, and return immediately.

Purpose: pitfall 1, the money bug. `fal-ai/wan-25-preview` defaults to **1080p**. An estimate at
480p against a submit that omits `resolution` under-reports by 3× and the daily window drains at
triple the rate **with no test going red**. The containment is structural: the submit body is
assembled FROM the same `spec` object `chooseMediaBatch` consumed, and a test asserts the submitted
JSON field-for-field against it.

Output: `submitBatch` + the offline seam, all provable at $0.
</objective>

<task type="auto" tdd="true">
  <name>Task 2: `submitBatch` — idempotent per shot, and it never waits</name>
  <files>packages/backend/convex/media.ts, packages/backend/convex/media.test.ts</files>
  <behavior>
    - `submitBatch({ tenantId, batchId })` POSTs once per `queued` row and returns without awaiting completion.
    - A row already at `submitted`/`succeeded`/`failed`/`blocked` is **SKIPPED** — re-running the whole
      action re-POSTs nothing. (Assert the fetch spy's call count across two consecutive runs.)
    - Each shot's row moves `queued → submitted` in a MUTATION **before** its POST.
    - A 422 sets that one row `blocked` with `verdict: "provider_blocked"` and leaves siblings alone.
    - `falRequestId` is recorded on success.
    - No code path in `media.ts` polls fal or awaits a terminal status.
  </behavior>
  <action>
`submitBatch` is an `internalAction` (default runtime). For each row in the batch:

1. **Claim first.** `ctx.runMutation(internal.media.claimShot, { jobId })` flips `queued → submitted`
   and returns `false` if the row is already past `queued`; skip on `false`.
   **This is pitfall 5's whole fix.** The action-retrier re-runs a failed action, so a `submitBatch`
   that dies on shot 7 of 10 would re-POST shots 1–6 on retry — a real double spend against a window
   already consumed. A claim in a serializable mutation before the POST makes the retry free.
2. Mint the webhook URL:
   `${process.env.CONVEX_SITE_URL}/fal/callback/${jobId}.${await hmacHex(jobId, requireEnvMedia("FAL_WEBHOOK_SECRET"))}`
   — the `gmailAuth.buildAuthorizeUrl:59` construction verbatim, per JOB rather than per tenant.
   The segment binds to ONE `mediaJobs` row; a leaked URL buys an attacker one already-finished job.
   **No `callbackHash` is stored** (plan 20-02's recorded deviation) — plan 20-06 re-derives it.
3. `submitShot(spec, prompt, webhookUrl)`; on ok patch `falRequestId`; on a 422 patch
   `status: "blocked"`, `verdict: "provider_blocked"`, `failureReason: <code>`; on a transport/5xx
   failure patch `status: "failed"`, `failureReason: <code>` and let the retrier's own policy apply.
4. **Return immediately.** SC2: a 5–10 s Wan clip takes 1–3 minutes of wall clock; nothing here
   awaits it. Add a static assertion in the test that `media.ts`'s source contains no
   `status_url`/`response_url` poll and no wait loop (comment-stripped source scan — `llmRedaction`'s
   idiom).

The prompt text is read from `plans.shots[shotIndex].prompt` at submit time (content plane). It is
passed to fal and to nothing else — never to an audit row, never to a log, never onto the job row
(only its `promptHash` lives there).
  </action>
