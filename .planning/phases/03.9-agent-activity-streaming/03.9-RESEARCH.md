# Phase 03.9: Agent Activity Streaming — Research

**Researched:** 2026-07-17
**Domain:** Agent-loop observability (AI SDK lifecycle callbacks) + Convex reactive UI state
**Confidence:** HIGH (the two decisive facts — `@convex-dev/agent` is version-blocked, and `ai@7.0.20` ships native tool-execution callbacks — were both verified against the installed `node_modules` source, not docs)

---

## Summary

The cockpit looks frozen for 10–30s because **the only mid-turn writes are the `plans`-row patches a tool happens to make**, and most tools patch nothing visible (`resolveContacts` parks candidates; `briefInbox` writes only at the very end; a turn where the agent just asks a question writes *nothing at all*). The workspace has no progress surface (confirmed: `page.tsx:219` is a `gmailStatus === undefined` branch, not a progress branch). The only progress-ish thing that exists today is `ChatPane`'s `.trace-line` chip derived from `plan.status` — which only lights *after* the plan reaches a milestone, i.e. after the wait is over.

The two candidate "reuse it" paths resolve cleanly, and in opposite directions:

1. **`@convex-dev/agent@0.6.4` streaming is NOT available to us — this is a hard version block, not a preference.** 0.6.4 is the *latest* published version and it peer-requires `ai@^6.0.35`; this repo pins `ai@7.0.20`. The `Agent` object in `cockpit.ts` only survives today because of a documented cast *whose stated precondition is that the model is never called*. Agent's streaming surface (`streamText` → `syncStreams`/`vStreamArgs` → `useUIMessages`) requires the agent to *make* the model call, which would break that precondition. Bumping is forbidden (§6) and there is nothing to bump to. **Secondary point:** even if it worked, agent streaming is *assistant-token* streaming — it would deliver the "bubbles" half and none of the "steps in the workspace" half, which is the primary ask.
2. **`ai@7.0.20`'s `generateText` already emits exactly the events this phase needs** — `onToolExecutionStart` / `onToolExecutionEnd`, awaited, with `toolCall.toolName`, `toolExecutionMs`, and a `toolOutput.type: "tool-result" | "tool-error"` discriminator. This is ponytail rung 4 (a native framework feature covers it). It requires **zero edits to any of the 14 tool wrappers** — it is options on the one `generateText({...})` call in `runAgentLoop`.

**Primary recommendation:** Add one append-only `agentSteps` table (the `briefings.ts` adapter pattern, verbatim), emit rows from `ai@7`'s `onToolExecutionStart`/`onToolExecutionEnd` inside `runAgentLoop` plus one driver-owned `thinking` row per turn, and render it in two places off one reactive `tenantQuery` (a plan-independent card in `CardList`, and an in-progress bubble in `ChatPane`). **Give the step row no free-text field at all** — a closed tool-name union + a phase enum + numbers. Then §4 is enforced by the schema itself rather than by vigilance. **No skill edit is needed → no eval gate cycle** (see §"Skill gate").

## Architecture Patterns

### Recommended shape

```
packages/backend/convex/
├── schema.ts             # + agentSteps table (new table, no migration needed — see Pitfall 8)
├── agentSteps.ts         # NEW thin adapter: record/finish (internalMutation) + byThread (tenantQuery)
│                         #   ← mirrors briefings.ts VERBATIM (writes no log-plane row)
├── llm.ts                # runAgentLoop: + onToolExecutionStart/onToolExecutionEnd → agentSteps
│                         # runCockpitAgent: + the SMOKE-path step emission (one site)
└── cockpit.ts            # sendCockpitMessage / resolveRecipients: mint turnId, write the
                          #   `thinking` row, terminalize in a finally
apps/web/app/(app)/dashboard/workspace/
├── cards.tsx             # + ActivityCard, dispatched from CardList's THIRD independent useQuery
└── ChatPane.tsx          # + in-progress agent bubble off the same query (replaces the `busy` gap)
```

### Pattern 1: emit from the SDK's callbacks, not from the tools (the whole backend, ~20 lines)

```ts
// packages/backend/convex/llm.ts — inside runAgentLoop's `run()`
// Source: ai@7.0.20 dist/index.d.ts:3255-3337 (event shapes), dist/index.js:2895-2995 (dispatch)
const res = await generateText({
  model: m.model,
  system,
  prompt,
  tools,
  stopWhen: stepCountIs(8),
  abortSignal: AbortSignal.timeout(CALL_TIMEOUT_MS),
  maxRetries,
  // Activity trace (CKPT-05). NAME + phase only — never `event.messages`, never toolOutput.output.
  onToolExecutionStart: async ({ toolCall }) => {
    await ctx.runMutation(internal.agentSteps.record, {
      tenantId, threadId, turnId, stepKey: toolCall.toolCallId, tool: toolCall.toolName,
    });
  },
  onToolExecutionEnd: async ({ toolCall, toolOutput, toolExecutionMs }) => {
    await ctx.runMutation(internal.agentSteps.finish, {
      tenantId, turnId, stepKey: toolCall.toolCallId,
      phase: toolOutput.type === "tool-error" ? "error" : "done",
      durationMs: toolExecutionMs,
    });
  },
});
```

**Verified properties (read from the installed implementation, not the docs):**

| Property | Evidence | Why it matters |
|----------|----------|----------------|
| The callbacks are **awaited** — `onToolExecutionStart` completes *before* `tool.execute` runs; `onToolExecutionEnd` *after* | `dist/index.js:2633-2642` (`notify` = `await Promise.all(...)`), called at `:2902` (start) and `:2960`/`:2983` (end) | The `running` row is committed and on-screen before the slow tool begins. No ordering hazard, no dangling promise. |
| **Callback throws are swallowed** (`try { await callback(event) } catch (e) {}`) | `dist/index.js:2636-2639` | **Fail-open by construction** — a broken step writer can never break an agent turn. Also means it fails *silently* → see Pitfall 6. |
| `onToolExecutionEnd` fires on **both** success and error, discriminated by `toolOutput.type` | `dist/index.d.ts:3308-3315`, `.js:2955-2983` | The per-tool terminal state is free. A throwing tool cannot leave a spinner running. |
| The event carries `toolCall.toolCallId` (stable per call) and `toolExecutionMs` | `dist/index.d.ts:3229-3240`, `:3262-3266` | `toolCallId` is the start↔end join key (better than a name, which repeats within a turn). |
| The event ALSO carries `messages: ModelMessage[]` and `toolOutput.output` | `dist/index.d.ts:3218-3221`, `:3284` | **§4 hazard.** These carry model context and the tool's full return string (`listInbox`'s return contains SUBJECTS). Destructure `toolCall`/`toolOutput.type` ONLY — never spread the event. |

### Pattern 2: the `briefings.ts` adapter, verbatim

`briefings.ts` is the exact precedent and should be copied down to its comments: a thin content-plane adapter that **writes no log-plane row** (the acting module owns the refs-only audit), an `internalMutation` writer, and a `tenantQuery` reader that the browser subscribes to.

```ts
// schema.ts — the §4 enforcement IS the schema. There is no free-text field to leak into.
agentSteps: defineTable({
  tenantId: v.string(),
  threadId: v.string(),          // renders the activity card for this thread, like plans/briefings
  turnId: v.string(),            // server-minted per turn (crypto.randomUUID) — groups the trace
  stepKey: v.string(),           // toolCall.toolCallId (SDK-owned) | "thinking" — the start↔end join
  tool: v.union(                 // CLOSED union of OUR tool names — a model cannot widen it
    v.literal("thinking"),
    v.literal("resolveContacts"), v.literal("addRecipients"), v.literal("setRecipients"),
    v.literal("removeRecipient"), v.literal("setSubject"), v.literal("setMode"),
    v.literal("setSendTime"), v.literal("draftBody"), v.literal("proposePlan"),
    v.literal("generateAttachment"), v.literal("regenerateAttachment"),
    v.literal("removeAttachment"), v.literal("personalizeRecipient"),
    v.literal("listInbox"), v.literal("briefInbox"),
  ),
  phase: v.union(v.literal("running"), v.literal("done"), v.literal("error")),
  startedAt: v.number(),
  endedAt: v.optional(v.number()),
  durationMs: v.optional(v.number()),
  // NOTE: there is deliberately NO label/text/detail/result field. The human-readable verb is a
  // code-owned map in the UI keyed off `tool`. §4 is enforced by the ABSENCE of a place to put text.
}).index("by_turn", ["tenantId", "turnId"])
  .index("by_thread", ["tenantId", "threadId"]),
```

Why the closed union rather than `v.string()`: the model *chooses* which tool to call, but the name in the event is a key of **our** `tools` record (`ai` throws `NoSuchToolError` before `execute` on a hallucinated name), so the union can never legitimately fail — and it turns "the model can't inject a label" from an argument into a schema constraint. Precedent: the "PINNED status enum" on `plans` (03.1-01).

### Pattern 3: the driver owns turn lifecycle; the SDK owns step lifecycle

`sendCockpitMessage` and `resolveRecipients` (both in `cockpit.ts`, both `tenantAction`s that already wrap `runCockpitAgent` in try/catch) mint `turnId = crypto.randomUUID()`, write the `thinking` row **before** calling the loop, pass `turnId` into `runCockpitAgent`, and terminalize in a `finally`. This is load-bearing for two reasons:

1. **Many turns call zero tools.** The agent asking "who should I send this to?" emits no tool events at all — a tool-only surface would show *nothing* for exactly the turns where the model call itself is the whole 10–30s wait. The `thinking` row is the floor.
2. `preCall` + the skill-registry load + the first model round-trip all happen before any tool event could fire. The `thinking` row lands within ~ms of the send.

`turnId` reaches `runAgentLoop` as an **append-only optional arg** — the codebase's established signature-evolution convention (`buildCockpitTools`'s 4th `clientContext` and 5th `skillVersions` args both say "append-only Nth arg — every existing caller keeps working"). It threads `sendCockpitMessage → runCockpitAgent → runAgentLoop`; it does **not** need to reach `buildCockpitTools`, because the tools don't emit — the SDK does. Keep it that way.

### Pattern 4: a THIRD independent `useQuery` in `CardList` (the trap 03.7-04 already sprang)

`CardList` already runs two independent reactive queries (`api.plans.byThread`, `api.briefings.byThread`) precisely because 03.7's RESEARCH Pitfall 6 caught a plan-status-gated dispatch rendering literally nothing. The activity card is the third, on the same footing: **never nested under a plan-status branch.** STATE.md's 03.7-04 entry records the exact lesson — *"a status-'collecting' row made the OLD dispatch render literally nothing"* — and this phase's card must render during `collecting`, which is when *most* of the waiting happens.

### Pattern 5: derive the chat bubble from the same query — but keep `busy` for the first turn

`ChatPane` already holds a `busy` boolean around the `send()` await, and already renders a `.trace-line` chip. The in-progress bubble should render from the **same** `agentSteps` query so the bubble and the workspace can never disagree.

**But see Pitfall 1** — on the *first* message there is no `threadId` until `send()` resolves (i.e. until the wait is over), so a `byThread` query is `"skip"` for the entire first turn. Recommended resolution: the reader is a **tenant-scoped latest-turn query taking no threadId**:

```ts
// agentSteps.ts — `tenantQuery({ args: {} })` with no args is an established shape (cockpit.listThreads).
export const latestTurn = tenantQuery({
  args: {},
  handler: async (ctx): Promise<{ threadId: string; steps: StepView[] } | null> => {
    const newest = await ctx.db.query("agentSteps")
      .withIndex("by_thread", (q) => q.eq("tenantId", ctx.tenantId))
      .order("desc").first();                         // index order === recency (briefings precedent)
    if (!newest) return null;
    const steps = await ctx.db.query("agentSteps")
      .withIndex("by_turn", (q) => q.eq("tenantId", ctx.tenantId).eq("turnId", newest.turnId))
      .take(12);                                      // BOUNDED — never .collect() (see Pitfall 7)
    return { threadId: newest.threadId, steps: steps.map(toView) };
  },
});
```

The client renders it when `threadId === undefined || row.threadId === threadId`. This is tenant-scoped by the wrapper (the multi-tenant linchpin, §2), covers the first turn for free, and needs **no change to `sendCockpitMessage`'s contract** (which would otherwise cascade into every cockpit test + 5 E2E specs). `stepCountIs(8)` caps a turn at 8 steps, so `take(12)` is a real ceiling, not a truncation.

### Anti-patterns to avoid

- **Deriving the label from the tool's return string.** `listInbox` returns *subjects*; `resolveContacts` returns *display-name labels*. Parsing `toolOutput.output` into a label pipes third-party content into a new persisted surface for zero benefit. Use the code-owned `tool → verb` map.
- **Logging step events to `audit`/`telemetry`.** This is UI state, not an audit trail. The agent's audit trail already exists (`mailbox.searched`, `mailbox.listed`, `briefing.created`) and is refs-only. A second, less-governed shadow log is a §4 regression with no requirement behind it. `agentSteps.ts` must write **no log-plane row** — the `briefings.ts` property, stated in its header comment.
- **A per-tool `emitStep()` call inside each `execute`.** 14 edit sites, 14 chances to drift, and the fail-open property is lost (a throwing emitter would now break a real tool). The SDK callback is one site.
- **Making the agent aware of steps** (e.g. a `reportProgress` tool). Violates ADR-004's "agents act on state, never surfaces" spirit, burns model steps against `stepCountIs(8)`, spends tokens, and makes progress *model-nondeterministic*. The trace must be code-owned like `briefings`' `sender`/`ts`/`bucket`.

## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---------|-------------|-------------|-----|
| Knowing when a tool starts/ends | A wrapper that maps over `buildCockpitTools`' returned record and re-wraps each `execute` | `generateText`'s `onToolExecutionStart` / `onToolExecutionEnd` | Native, awaited, fires on error too, gives `toolCallId` + `toolExecutionMs` free, and is swallow-on-throw (fail-open). A hand-rolled wrapper gets none of that and must be kept in sync with `invokeTool`/`runAgentSmokeOp`/the two test shims that also reach into the tools record. |
| Pushing state to the browser mid-action | Polling, SSE, an `EventSource` route | `ctx.runMutation` from the running action + `useQuery` | Actions aren't transactional — each `runMutation` commits and pushes to subscribers *while the action is still running*. This is the mechanism the whole app already relies on. |
| A "latest per thread" read | A `latest: true` flag patched across rows | `.withIndex(...).order("desc").first()` | Append-only ⇒ index order IS recency. `briefings.byThread` states it: *"index order (`_creationTime`) IS recency — `.order('desc').first()` is the whole 'latest' story, no scan."* |
| Keeping the step row's text §4-safe | A redaction pass / a scan over a `label` field | **Don't have a text field** | The cheapest invariant is a missing field. A `count: v.number()` literally cannot hold a subject line. |
| Relative time on the card ("3s ago") | A `setInterval` ticker | `durationMs` from the SDK + `Intl` | `toolExecutionMs` is measured server-side and is already in the event. |

**Key insight:** every part of this phase already exists in the codebase or the SDK — the honest scope is *wiring*, not building. The single largest risk is the opposite of under-building: inventing a progress *protocol* (labels, payloads, a shadow log) when the requirement is a list of verbs and a spinner.

## Common Pitfalls

### Pitfall 1 — The first turn has no `threadId` until the wait is over (**the worst one**)
**What goes wrong:** `ChatPane` gets `threadId` from `send()`'s *resolved value*; `sendCockpitMessage` returns only after the entire loop finishes. So `useQuery(..., threadId ? {threadId} : "skip")` is skipped for the whole first turn — the surface is blank at exactly the moment a first-time user decides the product is broken. A plan that ships `byThread`-only will pass its E2E (which sends a second message) and fail the human-verify.
**Why it happens:** the thread id is minted *inside* the action, and Convex actions return once.
**How to avoid:** the tenant-scoped `latestTurn` query (Pattern 5) — no threadId needed. Keep `ChatPane`'s existing `busy` as the sub-second bridge before the first row commits.
**Warning sign:** any plan task whose acceptance is "steps render" but whose test only exercises turn 2+.

### Pitfall 2 — Terminal state on a hard action kill
**What goes wrong:** a `running` row spins forever.
**The four death modes, and where each is covered:**
| Mode | Covered by | Status |
|------|-----------|--------|
| Tool throws | `onToolExecutionEnd` fires with `toolOutput.type === "tool-error"` (`.js:2955-2983`) | **Free** |
| Model call times out (`AbortSignal.timeout(45_000)`) or throws un-eligibly | `runAgentLoop` throws → `cockpit.ts`'s existing `try/catch` → add a `finally` that terminalizes the turn | **Cheap** |
| Governed stop (`preCall` → kill switch / budget) | `runCockpitAgent` returns the PAUSED_REPLY *early*, before any loop — the `thinking` row must be terminalized on this path too. **This is the easy one to miss:** it is a `return`, not a throw, so a `catch`-only fix leaves it running. | **Must be explicit** |
| Convex action hard-killed (deploy, OOM, platform) | Nothing server-side runs | **Not coverable server-side** |
**How to avoid the last one:** client-side staleness, not a watchdog. The turn is bounded at 45s per model call; render a `running` row older than ~90s as "this step may have stalled — send again". Zero backend, no scheduler, no new failure mode. A `ctx.scheduler` watchdog is the over-build here (a scheduled mutation to clean up UI state that a page refresh already fixes).

### Pitfall 3 — The fallback retry re-runs the tools → duplicate rows
**What goes wrong:** `runAgentLoop`'s `catch (e) { if (isFallbackEligible(e)) return await run(fallback, 0) }` re-enters `generateText` with the **same** `tools` object (built once, above `run`). Every tool the primary attempt already executed can execute again, emitting a second set of rows with new `toolCallId`s. The trace shows "Drafting the email…" twice.
**How to avoid:** append honestly — this is a *correct* rendering of what happened (the agent did draft twice). Recommended: pass an `attempt` number into the two callbacks and let the UI render a `Retrying on the backup model…` divider between attempts. Do NOT delete or supersede the primary's rows — the trace is the one place a user can see that a retry occurred, and silently hiding it is the same "computed and discarded" failure the 03.7 UAT called out on `category`.
**Warning sign:** a plan task that "de-duplicates steps by tool name".

### Pitfall 4 — The SMOKE path emits nothing (your offline E2E can't see the feature)
**What goes wrong:** `runCockpitAgent` step 4 short-circuits `SMOKE::agent::*` sentinels straight into `runAgentSmokeOp(tools, op)` → `invokeTool` → `tool.execute(...)` directly. `generateText` is never called, so **no callback ever fires**. Every offline E2E in the repo (`cockpit-briefing.spec.ts`, `cockpit-attachment.spec.ts`, …) drives that path — so the activity surface would be invisible to all of them and the phase would ship with zero automated UI coverage.
**How to avoid:** emit around the *one* smoke call site in `runCockpitAgent` (step 4), through the same `agentSteps.record`/`finish` helper. One extra site, both feeding one mutation pair. Do **not** put emission inside `invokeTool` — it is also the seam for `__invokeCockpitTool`/`__runCockpitAgentWithScript` (the unit-test shims), and firing there would make `cockpitTools.test.ts` write step rows as a side effect.
**Bonus:** `__runCockpitAgentWithScript` (the mock-model shim) **does** go through `runAgentLoop` → `generateText` with `mockModel`, so the SDK callbacks *do* fire there. That gives a real offline integration test of the emission path (see Validation Architecture).

### Pitfall 5 — Widening the §4 surface through the event object
**What goes wrong:** `ToolExecutionEndEvent` carries `messages: ModelMessage[]` (the full model context) and `toolOutput.output` (e.g. `listInbox`'s subjects, `resolveContacts`' display-name labels). A `...event` spread or a "just log the result for debugging" line pipes third-party mail content into a persisted row — and invariant 10's static scans in `llmRedaction.test.ts` **do not currently cover a new table**, so nothing would catch it.
**How to avoid:** (a) the schema has no field to hold it (Pattern 2); (b) destructure `{ toolCall, toolOutput, toolExecutionMs }` and use only `toolCall.toolName` / `toolCall.toolCallId` / `toolOutput.type`; (c) add a **mutation-checked static scan** to `llmRedaction.test.ts` in the established style: assert the `agentSteps` block in `schema.ts` declares no field outside the allow-list, and that neither `messages` nor `.output` is referenced inside the `onToolExecution*` blocks. STATE.md shows every prior §4 scan in this repo was mutation-checked (deliberately broken, confirmed red, restored) — hold that bar.

### Pitfall 6 — The emitter fails silently
**What goes wrong:** `notify` swallows callback exceptions (`.js:2636-2639`). A step write that throws (bad validator, wrong arg name, missing index) produces **no error, no log, no red test** — the feature just quietly renders nothing in production while every unit test passes.
**How to avoid:** the offline `__runCockpitAgentWithScript` integration test must **assert the rows exist** (not just that the loop returns). This is the one test that can catch a swallowed emitter. Treat it as required, not optional.

### Pitfall 7 — An unbounded `byThread` read eventually hard-fails
**What goes wrong:** `agentSteps` grows monotonically per thread. A `.collect()`-based read is the exact failure Phase 2 documented for the `audit` table: *"any `.collect()`-based count will eventually exceed Convex read limits and hard-fail rather than degrade."*
**How to avoid:** always `.withIndex(...).order("desc").first()` + `.withIndex("by_turn").take(12)`. Never `.collect()`, never `.filter()` without an index. `stepCountIs(8)` bounds a turn at ≤9 rows, so the ceiling is real.
**Retention:** none in v1 (YAGNI; rows are tiny and non-audit). Note it as a `ponytail:` ceiling with the upgrade path (a cron sweeping `agentSteps` older than N days) rather than building it.

### Pitfall 8 — Migrations, watch.json, and the Stop hook
- **Migration:** none needed. `@convex-dev/migrations` guards *changes to existing rows*; a brand-new empty table with all-required fields needs no migration (precedent: `briefings` + `inboxFixtures` landed in 03.7-02 with none).
- **`watch.json` (§9, Stop-hook-enforced):** `packages/backend/convex/agentSteps.ts` (+ `.test.ts`) is a **new code file under `packages/` that no playbook covers** — the hook will *block the turn* until it is registered. Register under `cockpit.md` (which already owns `cockpit.ts`, `plans.ts`, `briefings.ts`, `llm.ts`, and `apps/web/app/(app)/dashboard/workspace/`). `schema.ts` is watched by no playbook and `apps/web/e2e/` is already a `cockpit.md` prefix — so the only new entries are the two `agentSteps` paths.
- **Playbooks to update in-phase:** `cockpit.md` (Data flow steps 2/3/5 + Key files + a new invariant + `Last verified`) **and** `agent-runtime.md` — its Data-flow line 4 currently claims *"the UI re-renders reactively — the human watches the agent work live"*, which is precisely the overclaim this phase is fixing. Both are touched because `llm.ts` and `cockpit.ts` are `cockpit.md`-watched while the *loop invariants* live in `agent-runtime.md`.

### Pitfall 9 — Stale `ponytail:` comments that name a blocked upgrade path
`ChatPane.tsx:35-37` and `cockpit.ts:168-169` both say token streaming is *"a later upgrade via `useUIMessages`/`vStreamArgs` (research §4)"*. That path is **version-blocked** (see Standard Stack). ## Open Questions

1. **Do step labels carry counts in v1 ("Read 12 messages") or only verbs ("Reading your inbox…")?**
   - *Known:* the ROADMAP's key-constraint line uses counts as the example. The user's verbatim ask names **verbs** ("reading the inbox, summarizing, drafting"). Counts are not in any tool event — they exist only inside the tool's return string, which is §4-hazardous to parse (Pitfall 5).
   - *Unclear:* whether the count materially reduces the "is it stuck?" feeling versus the verb alone.
   - *Recommendation:* **verbs in v1.** Ship `count: v.optional(v.number())` in the schema but leave it unwritten, with a `ponytail:` comment naming the ceiling and the upgrade path: an append-only per-turn count recorder threaded into `buildCockpitTools`, written explicitly by the ≤3 tools that know a count (`briefInbox`, `listInbox`, `resolveContacts`) — never parsed out of a return string. Amend the ROADMAP line in the same phase rather than contradicting it silently.

2. **Does the activity card persist after the turn, or vanish?**
   - *Known:* the rows are append-only and cheap to keep; the canvas copy already promises "Plans, drafts, and delivery reports render here live as the agent works."
   - *Recommendation:* keep the last turn's trace visible in a **collapsed/settled** state (it becomes the BRAND-§5 "Thought Process" affordance and answers "what did it just do?"), and expand it while running. Confirm with the user at the human-verify — this is a taste call, not a governance one.

3. **Does `resolveRecipients` (the contact-pick re-entry turn) get a trace too?**
   - *Known:* it is a second `tenantAction` that re-enters `runCockpitAgent` with a synthetic prompt, and it is a real 10–30s wait the user currently watches in silence after clicking a chip.
   - *Recommendation:* **yes** — it is the same lifecycle, ~6 lines, and omitting it leaves one of the two agent entry points frozen. This is what "cross-cutting" means in the phase goal.
