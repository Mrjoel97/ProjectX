## Decisions & findings

**A real bug in the research's own recommendation, caught by the tests.** RESEARCH.md proposed
reading the newest turn from a `by_thread` index (`["tenantId", "threadId"]`) equalling `tenantId`
ALONE. That leaves `threadId` as the dominant sort key, so `.order("desc").first()` returns the
**alphabetically-largest thread's** row — not the newest. The `briefings.byThread` precedent it was
copied from only holds because it equals BOTH prefix fields: **"index order IS recency" does not
generalize to a partial prefix.** The index shipped is therefore `by_tenant` (`["tenantId"]` alone),
and there is deliberately no `by_thread` index because nothing reads by thread.

**§4 is enforced structurally, not by vigilance.** The row has no field that can hold text — a closed
`tool` union + a `phase` enum + numbers. The display verb is a code-owned map in the UI keyed off
`tool`. This matters because the SDK's tool events carry `messages[]` and `toolOutput.output`, and
`listInbox`'s return contains SUBJECTS — a `label` field would have been one careless spread from a
leak.

**`count` is declared but UNWRITTEN** (`ponytail:`) — verbs are the ask. Upgrade path: an explicit
per-turn recorder written by the ≤3 tools that actually know a count, never parsed out of a return
string.

**CKPT-04 deliberately not reshaped** — it is a distinct capability, is itself Pending, and is
blocked on its own Gap-1 rework sequenced after this phase. Coupling them would contradict the
user's sequencing decision (2026-07-17).
