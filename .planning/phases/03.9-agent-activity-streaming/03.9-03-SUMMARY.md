## Decisions & findings

**The brain button was wired, not retitled** (the plan's preferred, laziest honest option; ~10 min).
It toggles the bubble's collapsible trace — BRAND §5's "optional collapsible 'Thought Process'
trace", verbatim — and is `disabled` only when there is genuinely no trace to show, with a title
that says why. The old `disabled title="Thought process — coming soon"` was a lie the moment this
phase shipped.

**Trace open-state is `boolean | null`, where null = follow the turn.** Expanded while a step runs,
collapsed once it settles, and the brain button overrides either way. A plain `boolean` would have
forced a choice between auto-expand and user control; this gets both in one line. The persistence
recommendation (research Open Question 2) is implemented as recommended — **it is a taste call and
03.9-04's human-verify rules on it.**

**The bubble deliberately has NO second `aria-live` region — a deviation from the plan's letter,
serving its intent.** The plan mandates `aria-live="polite"` on the trace region (BRAND §6); the
`ActivityCard` has it. But the cockpit is two-pane and the card is ALWAYS on screen, so giving the
bubble one too would make a screen reader announce every step **twice** — worse than the silence §6
exists to prevent. One live region, on the canvas card. Honest limitation: an `aria-live` region
must exist before its content changes to announce reliably, so the very first step of a session may
not be spoken; every row after it lands in an already-mounted region and does announce (the card
mounts within ms of the `thinking` row and stays mounted, since the trace persists).

**An `error` step shows the ATTEMPT verb, not the done verb.** The plan's shorthand was
`VERB[tool]?.[phase === "running" ? 0 : 1]`, which renders "Drafted the email" on a step that
FAILED — a lie (BRAND §5). `stepText` instead strips the running verb's ellipsis and appends
"— couldn't complete this step". No amber (`--held` is the approval gate's alone), no colour at
all: the meaning is entirely in the text, so §6's no-colour-only rule is satisfied structurally and
there is no status dot to trip Biome's `useAriaPropsSupportedByRole` (the 03.7-04 precedent).

**Staleness is the whole hard-kill mitigation, and it is 3 lines.** A `running` row older than
`STALE_MS` (90s — comfortably past `CALL_TIMEOUT_MS`'s 45s/model-call bound) reads as "this step
may have stalled; try sending again". Computed from `Date.now()` at render: no ticker, no
scheduler, no watchdog. Wave 2 deliberately left this mode uncovered server-side because nothing
server-side runs after a hard action kill — and a scheduled mutation to clean up UI state a refresh
already fixes would be a new failure mode, not a fix.

**`stepText` is exported, not `VERB`.** The plan asked for one map in one module; exporting the
*function* rather than the map means both surfaces also share the error wording, the ellipsis
strip, and the staleness threshold — not just the verbs. `VERB` stays private to `cards.tsx`.

**No animation, and that is the point.** The rows arriving one by one IS the motion the phase
exists to deliver, so nothing needed registering in the existing
`@media (prefers-reduced-motion: reduce)` blocks and `globals.css` went untouched.

**Overflow discipline applied up front** (bitten twice before — vault cards `3bdea02`, briefing card
`44e95c0`): `traceText` is `{ minWidth: 0, overflowWrap: "anywhere" }` on every step's text span.
`minWidth:0` sizes the BOX, not the TEXT — the verbs are short and code-owned so an unbroken token
is unlikely, but the workspace divider is user-resizable and the cost is one shared constant.

## Deviations from plan

1. **`PlanCards` was extracted from `CardList`** (Rule 3 — required to satisfy the plan's own
   structural criterion). The trace must render above both early returns; the existing dispatch was
   moved verbatim into a sibling component so `CardList` could return a wrapper. The plan-status
   logic is byte-identical — only its enclosing function name changed.
2. **No `aria-live` on the chat bubble** — reasoned above. The plan's requirement is met on the
   card; duplicating it would harm the users §6 protects.
3. **`error` steps use the running verb + a suffix**, not the plan's literal `[phase === "running" ? 0 : 1]`
   index expression — reasoned above (that expression renders a false claim).
4. **The `activity` chip in `ChatPane` was renamed `milestone`.** `activity` now names the trace
   query (matching `cards.tsx`); the chip is about milestones and the old name actively misled about
   which of the two is the live one. Behavior unchanged — it is kept, as the plan requires.
5. **`"coming soon"` is not spelled out in the replacement comment.** The plan's verify greps for a
   literal `grep -c "coming soon" → 0`; a comment quoting the old string would have tripped that
   guard forever. The comment says so.
