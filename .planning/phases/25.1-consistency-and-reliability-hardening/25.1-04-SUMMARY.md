# Phase 25.1 Plan 04: Approvals Feedback Summary

**Every click on the approvals gate now ends in something the user can actually read: the success message survives the row it dismisses, the refusal sits at the top of the card instead of off its bottom, the stale-card copy stops asserting a start it cannot know happened, and the one button on this page that could never succeed is gone.**

## Performance

- **Duration:** ~25 min (11:41 → 12:00 UTC+3)
- **Tasks:** 2 (both TDD, one shared RED commit — see Deviations)
- **Files modified:** 3 · created: 0
- **Cost:** $0 (no model calls, no live deployment)

## Accomplishments

- **D9a closed — the success message was unreadable BY CONSTRUCTION.** A successful approve *is* the `proposed → approved` transition, and `approvals.listAwaiting` paginates `proposed` only, so the card that called `setResult` was unmounted by the very mutation that produced the message. The user saw a row vanish with no outcome — indistinguishable from a broken button. `dashboard-pages.md`'s 19-12 entry **named this exact rule** ("any state produced BY a status transition must not live in a component gated ON that status") and then left the transient copy in place; this plan obeys it. The outcome map moved to `AwaitingSection` as `Record<planId, string | null>`, and `persistentOutcomes(outcomes, liveIds)` returns the entries whose row has left the list, each rendered as a `ResolvedOutcomeCard`. Discard and schedule route through the same channel — they drop the row for the same reason and were equally mute.
- **D9b closed — the notice is now the FIRST child of the card.** It rendered below the discard fieldset: the last element of a card, under a collapsed confirm box, at the bottom of a scrolling list.
- **D9c closed — the stale copy stops lying.** `executePlan` returns `{ok: true, alreadyStarted: true}` for ANY status that is not `proposed`, `discarded` and `canceled` included, because its CAS only knows it did not win. "This plan already started" asserted a start that may never have happened. `STALE_PLAN_MESSAGE` says only what that return can promise: the card was out of date, and this click created nothing.
- **D10 closed — an image plan renders no Approve button.** `executePlan`'s media arm reserves against a SHOT DECK (`sceneDeckOf` / `deckOf`); a standalone image plan has neither, so that button has returned `no_deck` on every click it has ever received. `IMAGE_CANVAS_NOTE` replaces it and points at the workspace canvas, where `api.media.generateImage` already works. `approvals.ts` is untouched — the card still lists, only the mute button goes. The reel path keys off the same `mediaMode` discriminator `planKind` uses, so it is unaffected by construction (and asserted).
- **8 new tests, 6 of them rendering REAL markup.** The card was split into a connected shell over an exported `AwaitingCardBody` precisely so DOM order and the absent button could be asserted against a DOM instead of a regex.

## Deviations from Plan

### 1. [Rule 1 — smaller honest fix] `cockpit.ts`, `cockpit.test.ts` and `cockpit.md` were NOT touched

- **Found during:** Task 1 (the plan's `files_modified` lists all three)
- **Issue:** The plan offered a choice: return a distinct code separating a recycled row from a genuinely-started plan, "if cheap", otherwise copy-only.
- **Decision:** Copy-only. `STALE_PLAN_MESSAGE` is true in every case `alreadyStarted` covers, including the genuinely-started one ("already handled"), so the extra return field would buy nothing the copy does not already say — while widening the return contract of the mutation that sits on the money path. It also kept the commit clear of `cockpit.md`, which carries a foreign uncommitted hunk in this shared tree.
- **Consequence:** three fewer files changed than the plan's frontmatter predicts.

### 2. [Rule 3 — blocking the plan's own test requirement] `AwaitingCard` split into a shell + `AwaitingCardBody`

- **Found during:** Task 1
- **Issue:** The plan requires "DOM ORDER for the notice (notice node precedes the actions node), not mere presence". `AwaitingCard` is not exported and calls `useQuery`, so it cannot be rendered; `apps/web`'s vitest config has **no jsdom and no testing-library** by deliberate decision, and the existing file's own comment concedes its pins are source scans for that reason.
- **Fix:** the presentational half is exported as `AwaitingCardBody` and the hooks stay in the shell. `renderToStaticMarkup` needs no DOM — the blocker was the hooks, not the environment — so no dependency was added. `PlanMeta`'s prop type was widened to a structural `PlanMetaFields` so a test fixture needs no Convex ids.
- **Cost:** 14 explicit props, no behaviour change. **Payoff:** 6 of the 8 new assertions became real render tests, including the two the plan cared most about.

### 3. [Rule 2 — same defect, sibling callers] discard and schedule joined the outcome channel

- **Found during:** Task 1
- **Issue:** `doDiscard` and `schedule` set the same doomed local `result`. A successful discard moves the plan to `discarded` and a successful schedule to `scheduled`; both drop the row out of `listAwaiting` exactly as approve does, so both messages were equally unreadable.
- **Fix:** all three call `onOutcome`. Fixing the shared channel is a smaller diff than fixing approve alone would have been in three places later.

### 4. Tasks 1 and 2 share one RED and one GREEN commit

Both tasks change the same extracted component in the same region. Splitting them would have produced either a commit that leaves half the already-committed RED tests failing, or a contrived add-then-re-add. The RED commit names both defects; the GREEN commit names both fixes.
