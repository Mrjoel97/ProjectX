# Phase 25.1: Consistency and Reliability Hardening - Context

**Gathered:** 2026-08-21
**Status:** Ready for planning
**Source:** Owner-directed, from the Pikar Consistency Audit rev 2 (published artifact, session 2026-08-21). The audit's findings were produced by six parallel code investigations and verified against source with file:line evidence; the owner reviewed the audit and directed "start the reliability phase". The audit findings are restated with evidence in 25.1-RESEARCH.md — treat that file as the ground truth for every claim below.

<domain>
## Phase Boundary

Harden already-shipped subsystems so that **every governed background job reaches an honest terminal state the user can see** — no silent stalls, no vanishing media, no mute Approve button. This phase adds NO new capabilities: no batch content creation, no document canvas, no research-depth upgrade (beyond card rendering + sources), no durable-agent refactor, no production deploy. Those are separate later phases (audit gaps G10, G5, G4, G6) or separate owner decisions.

Subsystems touched: media pipeline (media.ts, mediaComplete.ts, render/), dispatch landing (dispatch.ts, plans.ts), approvals surface (approvals.ts, ApprovalsView.tsx), workspace cards (cards.tsx), vault persistence (renderReel.ts save path, vault.ts), crons, env manifest, one ADR.

</domain>

<decisions>
## Implementation Decisions

### Honest terminal states (audit G1, findings F1–F3)
- Every `batchToRender` refusal MUST write a terminal: `renderStatus: "failed"` + `renderReason` (and a dead-letter row where the sibling paths write one). The early-return before `markRendering` at `renderReel.ts:759-761` is the primary defect; no code path may leave `renderStatus` at `pending`/`rendering` without a scheduled reconciler that will terminalize it.
- `renderReel` runs under the ActionRetrier with an `onComplete`, exactly like its sibling `submitBatch` (pattern at `cockpit.ts:657-697` `EXTERNAL_TARGETS`). A throw after `markRendering` must produce a terminal, not a stuck row.
- One watchdog cron (pattern precedent: `vault-pending-extraction-sweep`, `crons.ts:43-50`) sweeps stuck non-terminal states to failure terminals + a user-visible notification: `mediaJobs` stuck at `submitted` (severed poll chain), plans stuck at `renderStatus: "rendering"`/`"pending"` past a threshold, `captionStatus: "transcribing"` stuck, and plans stuck at `status: "collecting"` (specialist action died before landing — today the card is invisible forever).

### Media vault persistence (audit G11, findings V1–V3, B1)
- Generated images are saved to the vault at generation success. Today NO image vault path exists — bytes live only on `mediaJobs.assetStorageId` and become unreachable from the UI when the thread's plan row is recycled. Mirror the reel pattern (`saveReelToVault`, `renderReel.ts:606`): a `vaultDocuments` row with the prompt as text + stored image bytes. Widening the `vaultDocuments.kind` union is expected and acceptable.
- Reels are saved at the RENDER terminal and re-pointed after caption burn — not gated solely on the caption terminal. Today captions are pinned on for every reel, so the caption-burn terminal is in practice the only save; a stranded transcription publishes a reel that never reaches the vault.
- `resetPlan` (plans.ts:864-945) MUST clear `reelVaultDocId`. Today a second reel in the same thread upserts over the first reel's vault doc and the orphan cleanup deletes the old mp4 — silent destruction of the user's prior deliverable.
- Fix the permanent second-image refusal: `generateImage` refuses `already_started` when ANY `mediaJobs` row is `queued|submitted|succeeded`, and nothing ever deletes `mediaJobs` rows — so one successful image forever blocks another. Scope the guard to genuinely in-flight rows.

### Approvals feedback (audit G12, findings A1–A3)
- Approve MUST produce a persistent, visible outcome. Success currently unmounts the card before its message renders (acknowledged in a comment at `cockpit.ts:992-996`) — indistinguishable from a broken button. Add a toast or a "started" card state that survives the unmount.
- Refusal notices move to a prominent position (top of card), not appended below the discard controls.
- Image plans: the Approve button on /dashboard/approvals is structurally incapable of succeeding (`executePlan`'s media arm has no image branch → always `no_deck`). Either implement an image arm or stop rendering Approve for image plans with honest copy pointing at the workspace canvas. **Owner preference: honesty over silence — which of the two is Claude's discretion during planning, but shipping the always-failing button is not acceptable.**
- The false "already started" message when the plan row was recycled (stale-list trap) should tell the truth or the stale card should not render an Approve button.

### Research presentation (audit G3, findings R2–R3 — presentation only, NOT depth)
- The memo plan card renders `plan.body` through `MarkdownDocument` (renderer already used by chat bubbles at `ChatPane.tsx:279`) instead of the raw pre-wrap paragraph at `cards.tsx:560-573`. The approvals body preview gets the same treatment where practical.
- Research `sources` (already captured structurally at `llm.ts:4541-4548` and deliberately not threaded at `dispatch.ts:1096-1098`) are threaded through `landSpecialistResult` onto the card as a references block: title, URL, retrieval date. Redaction rule stands: audit/log payloads still carry counts only, never URLs — the URLs go to the plan card and vault doc, not to audit rows.
- Research DEPTH (page fetching, model pins) is explicitly OUT of this phase — audit G4, a later phase.

### Hygiene (audit G9)
- Env manifest completeness: `MEDIA_RENDER_URL`, `MEDIA_SANDBOX_SNAPSHOT_ID` (and the web-side `NEXT_PUBLIC_CONVEX_URL` where the readiness pattern can reach it) become visible to the readiness/drift checks (`lib/env.ts:122-132`; drift test only sees literal `process.env.X`).
- Dead fal webhook code removed: the `/fal/callback/` route (`http.ts:354`), its HMAC handling, and the `FAL_WEBHOOK_SECRET` manifest entry — nothing passes a webhook URL since the Sora cutover.
- A superseding ADR records the media provider cutover (Sora `sora-2` / `gpt-image-2` via OpenAI, legacy Wan poller retained for pre-cutover tasks) — ADR-011's fal.ai/Wan decision is superseded in code but not in docs/decisions/.
- DLQ visibility: dead letters are written with `status: "new"` and nothing ever lists or re-drives them. Minimal ops-surface listing (owner-facing) is in scope; a re-drive worker is NOT (defer).

### Claude's Discretion
- Watchdog thresholds (minutes per state), sweep cadence, and notification wording/shape.
- Toast vs "started" card-state for approve success (either satisfies the decision).
- Image-arm-vs-honest-button choice for image plans on approvals.
- Exact shape of the DLQ listing surface (smallest honest thing; /ops precedent exists).
- Whether the sources references block folds/collapses on the card.

</decisions>

<specifics>
## Specific Ideas

- The audit's one-line thesis, owner-endorsed: "inconsistency is one defect class — work that fails silently, with no terminal state, no watchdog, and no surface the user can see." Every task in this phase should be justifiable as removing a silent state or making an outcome visible.
- The vault extraction sweep exists because this exact failure mode was observed there; the fix pattern is proven in-repo. Reuse it, don't invent.
- `submitBatch` already shows the correct retrier + onComplete shape; `renderReel` should look like its sibling.
- CLAUDE.md governance applies in full: playbooks updated in the same commit (cockpit.md and the media playbook both watch these files), audit rows stay redaction-safe (ids/counts, never URLs or content), wrapper imports only, no new dependencies, ponytail discipline.

</specifics>
