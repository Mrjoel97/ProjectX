# Phase 25.1 Plan 03: Media Vault Persistence Summary

**Both media kinds now reach the vault at their own success terminals, and nothing a user generated can be silently destroyed or stranded by generating again — the image gets a vault doc it never had, the reel stops waiting on a caption pass that may never come, a reset frees the vault pointer so reel #2 cannot eat reel #1, and a finished image stops locking the button that made it.**

- **Files modified:** 12 · created: 1 (deferred-items.md)

## Accomplishments

- **D5 closed.** `mediaComplete.saveImageToVault`, called from `landResult`'s success arm, files a generated still image as a `vaultDocuments` row: the reviewed PROMPT as `text` (searchable, on the ordinary embed rail via `startIngest`), the image bytes in `storageId` with `storedMimeType` naming them, `category: "images"`, `sourcePlanId` for provenance, and one refs-only `media.image_saved` audit line. Before this the bytes existed ONLY on `mediaJobs.assetStorageId`, read through the plan row — so recycling the thread's plan made a paid-for, finished image unreachable from every surface at once.
- **D6 closed.** The `!captionsComing` gate on the render terminal's `saveReelToVault` is gone. Captions are pinned on for every reel, so that gate was true at **every render terminal that has ever run** — the caption burn was the only save site in practice, and a caption pass that stalls, loses its transcript or is swept by 25.1-02's watchdog never reaches it. The burn's own save still runs; the upsert converges onto the same doc.
- **D7 closed.** `plans.resetPlan` clears `reelVaultDocId`. `saveReelToVault` upserts on that pointer, so a surviving one made the next reel in the thread PATCH the previous reel's doc — and `deleteOrphanedFinals` then deleted the previous mp4, because nothing referenced it any more. `deleteOrphanedFinals` itself needed no change: it reads the live set fresh, so once reel #2 has its own doc, reel #1's blob is never a candidate (asserted, not assumed).
- **D8 closed.** `generateImage` refuses `already_started` only on `queued|submitted`. `succeeded` was in that set and nothing ever deletes a `mediaJobs` row, so the first image a plan produced locked the button **for ever**, explaining itself as "already started" about work that had finished.
- 8 new tests + 3 rewritten ones; every new guard mutation-checked.
