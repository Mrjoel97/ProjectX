## User Constraints (from CONTEXT.md)

### Locked Decisions

**Format and scale**
- **CSV only.** No vCard, no XLSX. Building them now is speculative.
- **Hard cap 1,000 rows.** Larger files are refused outright with a message naming the limit,
  and the cap carries a `ponytail:` comment naming the ceiling and the job-based upgrade path.
- **No job queue, no reservation table, no resumable cursor, no cleanup job.** Justified by the
  convergence property below — this absence is a deliberate decision, not an omission.

**Where parsing happens**
- **In the browser. The raw file is NEVER uploaded and NEVER stored.** No PII at rest, no
  retention policy, no cleanup path. This was chosen over the server-side parse specifically to
  avoid recreating the PII honeypot Phase 19 worked to keep out of `audit.payload`.
- **`parseCsv` is hand-rolled RFC-4180 in `packages/core/src/contactImport.ts`** — pure TS, no
  Convex, testable in the core suite. NOT a new dependency. It must handle: quoted fields,
  commas inside quotes, newlines inside quotes, doubled quotes as an escaped quote, a leading
  BOM, and CRLF or LF.
- Header auto-mapping covers common aliases (`email`/`e-mail`/`email address`;
  `name`/`full name`/`first`+`last`; `company`/`organization`; `phone`; `title`/`job title`).
  Every column is overridable in the preview. Unmapped columns are dropped.

**Two reuses that are load-bearing**
- Identity comes from `normalizeAddress` (`@pikar/core`).
- Validity comes from `isValidEmail` (`packages/core/src/validateSubmit.ts`) — the repo's
  designated single email regex, already the send path's rule and already wired into
  `parseCrmOperations` by 19-13.
- **Rationale (do not deviate):** using both means import cannot disagree with the send path
  about who a row is or whether an address is real. An import-local rule would produce contacts
  that exist but can never be emailed.

**Merge semantics**
- **Fill empty fields only. NEVER overwrite a non-empty field.** A CRM export is usually staler
  than what the user has since typed; nothing typed by hand may be destroyed.
- **Within-file duplicates collapse client-side** under the same rule, before anything is sent.
  Two rows sharing a normalized address in one batch would otherwise race on a single contact.
- **The convergence property:** because the write is upsert-by-address and fill-empty-only,
  re-running the same file is safe and converges. Retry-the-whole-thing IS the recovery
  strategy. This is what buys the right to skip all job machinery.

**Consent**
- **One attestation at import, recorded PER CONTACT** (not once per batch) as
  `consentSource: "imported-attested"`.
- `"imported-attested"` is deliberately DISTINCT from `"asserted-by-user"`. One attestation over
  500 rows is weaker evidence than consent recorded for one person; the schema must not flatten
  that difference.
- **The attestation sentence is part of the spec**, versioned in `@pikar/core` beside the parser:
  > I have a lawful basis to contact these people — they are business contacts of mine, and I am
  > not importing a purchased or scraped list.
- `consentWording` stores that sentence **byte-for-byte**, never a paraphrase or a key into a
  message table. It is the evidence. Changing the wording later applies only to future imports.
- The free-text "where did these come from?" is stored as `consentContext`.
- **The checkbox starts unticked and Confirm is DISABLED until ticked.** A pre-ticked box would
  make the stored wording a false statement about what the user did. This keeps the schema's
  "NOTHING is defaulted to consented" honest.
- `consentWording` and `consentContext` are content plane — **neither may reach `audit.payload`**
  (CLAUDE.md §4). Import audit rows carry counts and contact ids only.

**Data model**
- Three new optional fields on `contacts`: `company`, `phone`, `title`. **Three, and no more.**
  No custom fields, no tags, no arbitrary key-value.
- Two union extensions: `origin` gains `"imported"`; `consentSource` gains `"imported-attested"`.

**Backend surface**
- Two new public functions, both in `packages/backend/convex/contacts.ts`. **No second store** —
  PIPE-01 forbids it and 19-02's structural scan enforces it.
- `matchExisting({ emails })` — `tenantQuery`, bounded by input, chunked client-side at 500
  addresses per call. Returns per address: exists?, and which of `name`/`company`/`phone`/`title`
  are empty.
- `importContacts({ rows, attestation })` — `tenantMutation`, batched at **100 rows per call**
  (starting value, tunable against Convex transaction limits; the correctness argument does not
  depend on the number). Returns `{ created, enriched, unchanged, rejected }`.
- The mutation **re-validates rather than trusting** client-normalized input — same write-boundary
  discipline `parseCrmOperations` follows.
- Both functions join the `COVERED` pin in `contacts.test.ts` **with real asA/asB isolation
  tests**. 19-13 established that bumping the pin without adding the test defeats its purpose.

**Interface**
- Lives on `/dashboard/pipeline` beside the existing "Add your first contact". **No new route.**
- File picker follows the vault's `Dropzone.tsx` pattern rather than introducing a second one.
- Three steps in one panel: choose file → preview (mapping + counts + rejected rows by line
  number and reason) → attest and confirm.
- Tokens from `globals.css`, **no component library**, refusals inline in grey `--ink-soft` —
  Phase 19's rule that a refusal is information, not failure. Never amber.

**Who can import**
- **Human only.** The agent cannot initiate an import: the attestation is a legal statement a
  person makes, the agent cannot see the file, and keeping it out avoids a new registration
  surface on the 14-site checklist.

**Testing**
- `packages/core`: the CSV cases that break naive parsers, header alias mapping, within-file dedup.
- `contacts.test.ts`: asA/asB isolation on both new functions; fill-empty-only asserted **on
  stored state, not on the reply**; consent wording stored byte-for-byte; the §4 scan extended to
  prove no wording reaches `audit.payload`.
- `pipeline-uat.spec.ts`: **a real browser** uploading a real fixture CSV, seeing the preview
  counts, confirming, and finding the rows in the table. **This row is a REQUIREMENT, not a
  nicety.**
- Every new guard mutation-proven: broken, observed red, reverted, failing text recorded.

## Summary

The plan's risk is concentrated in three places, and the parser is not one of them.

**First, the two union widenings.** `origin` and `consentSource` have **19 consuming sites**
between them. I walked every one. The good news is better than the spec feared: widening either
union produces a compile error at the type mirrors, because `listContacts` assigns
`doc.origin`/`doc.consentSource` straight into hand-typed literal unions on `PipelineContactRow`
and `ConsentRecord`. The bad news is that there are **three genuinely silent sites**, and one of
them is exactly the 19-06 `PlanRow`/`media` shape, live: **`PipelineView.tsx` renders the consent
chip as "Consented \<date\>" and never reads `row.consent.source` at all.** The whole stated reason
`"imported-attested"` exists — "the schema must not flatten that difference" — is flattened at the
only surface a user or a regulator-facing screen ever sees, and `tsc` will never say a word. The
plan must decide this explicitly rather than discover it.

**Second, the interaction between a 1,000-row import and `SCAN_LIMIT = 1_000`.** Every Pipeline
read model caps its scan at 1,000 rows. `listContacts` and `listUnassignedFollowUps` take
`SCAN_LIMIT + 1` and honestly report `partial: "row-cap"`. **`pipelineTiles` does not** — it takes
exactly 1,000, returns no bound, and silently under-counts past that. A single max-size import into
a tenant that already has one contact crosses the line, so this phase can make the four
"ALWAYS-KNOWN counts" (playbook invariant 3) quietly wrong on its first real use.

**Third, the merge rule is not what `upsertContactRow` already does.** Its current name handling is
"a blank name must not *erase* a name on record" — a non-blank name **does** overwrite. Import needs
"never overwrite a non-empty field," which is a different rule. The laziest correct shape is one
flag on the existing shared helper (invariant 13: ONE implementation of the write rule), not a
second upsert. And the same fill-empty-only logic must cover **consent**: an import must not
replace a per-person `asserted-by-user` record with the weaker batch attestation.

Everything else is comfortable. All four batch/chunk numbers in the spec sit at roughly 1% of every
hard Convex limit. No migration is needed (widening a union and adding optional fields are both
backward-compatible at rest). `resolveMimeType` already maps `.csv` → `text/csv` for the Windows
empty-`File.type` case. `useConvex()` already has two precedents for the one-shot query the preview
needs.

**Primary recommendation:** structure the plan around three explicit decisions — (1) render or
knowingly suppress `consent.source` on the Pipeline; (2) fix or knowingly accept `pipelineTiles`'
silent cap; (3) add a `fillEmptyOnly` flag to `upsertContactRow` rather than a second writer — then
build the parser, which is the easy part.

**Indexes:** `by_tenant_email` (`["tenantId","email"]`) and `by_tenant_createdAt`
(`["tenantId","createdAt"]`). **No new index is needed.** `matchExisting` and the upsert both
key on `by_tenant_email`; the Pipeline pages on `by_tenant_createdAt`.

**New fields go here:** `company`, `phone`, `title`, all `v.optional(v.string())`, all content
plane. Add the CLAUDE.md §4 comment beside them the way `consentWording` carries one.

### `upsertContactRow` (`contacts.ts:90-116`) — exactly how create-vs-update works today

```
const address = normalizeAddress(email);
if (address === "") throw new Error("CONTACT_EMAIL_REQUIRED");   // the trust boundary
const existing = await contactByEmail(ctx, tenantId, address);    // by_tenant_email, .unique()
if (existing) {
  const trimmed = name?.trim();
  await ctx.db.patch(existing._id, { ...(trimmed ? { name: trimmed } : {}), updatedAt: now });
  return existing._id;
}
return await ctx.db.insert("contacts", { tenantId, email: address,
  ...(name?.trim() ? { name: name.trim() } : {}), origin, createdAt: now, updatedAt: now });
```

Four facts the plan must build on, precisely:

1. **The current rule is "don't erase", NOT "fill empty only".** A non-blank `name` on an update
   **overwrites** whatever was there. Pinned by `contacts.test.ts:320`
   (`"a nameless re-save must not erase a name on record"`) — that test asserts the blank case only,
   so changing the non-blank case unconditionally would silently change hand-add behaviour that
   nothing tests. **Import needs a different rule and must not change the hand-add one.**
2. **`origin` is written on INSERT only and never patched.** Pinned by `contacts.test.ts:321`:
   `"provenance is set once, on creation"`. An import touching a pre-existing `user-entered`
   contact correctly leaves it `user-entered`. Assert this for the import path too.
3. **`updatedAt` is bumped on every patch**, including a no-op one. If the import patches
   unconditionally, `unchanged` rows still move `updatedAt`. Skip the patch entirely when nothing
   changes, or `unchanged` is a lie in the DB even if the count is right.
4. **It is a plain async helper over an explicit `tenantId`, not a Convex function** — shared
   deliberately between the public mutations and `cockpit.ts`'s `crm_write` applier
   (playbook invariant 13, "ONE implementation of the write rule, shared by both actors").
   **Recommended shape:** `upsertContactRow(ctx, tenantId, { email, name, company, phone, title,
   origin, fillEmptyOnly?: boolean })`. Default `false` ⇒ hand-add and the agent path are
   byte-identical to today. This is CLAUDE.md §8 rung 2, and it keeps invariant 13 true.

### `assertConsent` and `consentRecord` — exact signatures and cost

```ts
// contacts.ts:256 — tenantMutation
assertConsent({ contactId: v.id("contacts"), wording: v.string(), context: v.optional(v.string()) })
  -> Promise<null>
// contacts.ts:314 — tenantQuery
consentRecord({ contactId: v.id("contacts") }) -> Promise<ConsentRecord | null>
type ConsentRecord = { at: number; source: "asserted-by-user" | "inbound-form";
                       wording: string | null; context: string | null }
```

**There is no consent table.** Consent is four optional columns on the contact row. `assertConsent`
costs **1 `db.get` + 1 `db.patch`** and hardcodes `consentSource: "asserted-by-user"`. It refuses
blank-after-trim wording (`CONSENT_WORDING_REQUIRED`) and trims both fields before writing. It
writes **no audit row at all**.

**Cost of "one consent per contact" in the import: ZERO extra writes** — fold `consentAt`,
`consentSource`, `consentWording`, `consentContext` into the SAME `db.insert`/`db.patch` the
contact upsert already performs. Do **not** call `assertConsent` per row: it re-reads the row you
just wrote, and it hardcodes the wrong `consentSource`. So a 100-row batch is 100 indexed reads +
100 writes, not 200 + 200.

**⚠ Consent must be fill-empty-only too, and the spec does not say so.** A contact carrying a real
per-person `asserted-by-user` record with its own wording, re-touched by an import, would have that
stronger evidence overwritten by the weaker batch attestation — precisely the destruction
fill-empty-only exists to prevent, applied to the field where it matters most. **Write consent only
when `existing.consentAt === undefined`.** Name this in the plan; it is a decision, not a detail.

**Do not copy the `?? "asserted-by-user"` fallback** at `contacts.ts:322` and `:837` into any new
code. It exists because `consentAt` and `consentSource` are independently optional; the import
always writes both, so a defaulted source in the import path would be an invented fact.

### ⚠ Site 16 in full — this is the phase's `media`-in-`llm.ts` moment

```tsx
// PipelineView.tsx:278-284 — the entire Consent column
{row.consent === null
  ? <span style={quietChip}>none on record</span>
  : <span style={chip}>Consented {formatDay(row.consent.at)}</span>}
```

`row.consent.source` crosses the network on every row and is discarded. An
`"imported-attested"` contact and a per-person `"asserted-by-user"` contact render **byte-identical
chips**. The design spec's justification for the distinct literal is:

> "A single attestation covering 500 rows is weaker evidence than consent recorded for one person…
> The schema should not flatten that difference; a regulator asking 'how do you know?' gets a
> different, honest answer for each."

The schema will not flatten it. **The product already does**, and no compiler will report it. The
per-contact `consentRecord` query does return `source`, but it has **no UI surface at all**
(deliberately, per 19-13) — so after this phase the distinction is reachable only by calling a
Convex query by hand.

**The plan must take one of two positions, in writing:**
- **(a) Render it.** Cheapest honest fix: `Consented {formatDay(at)}{source === "imported-attested" ? " · imported" : ""}`, one expression, plus a `pipelineView.test.ts` case. Recommended.
- **(b) Accept it,** and record in `contacts-crm.md` that the Pipeline deliberately does not
  distinguish consent strength, with the upgrade path named.

Discovering this at verification time is how a phase ships a capability that every test certifies
and no user can see — the exact failure `pipeline-uat.spec.ts` exists to prevent.

### ⚠ The other silent hazard: `SCAN_LIMIT` vs a 1,000-row import

`contacts.ts:621` sets `SCAN_LIMIT = 1_000` for every Pipeline read model.

| Reader | Take | Reports being capped? |
|--------|------|----------------------|
| `listContacts` (`:791`) | `SCAN_LIMIT + 1` | ✅ yes — `bound.partial` + `partialReason: "row-cap"` |
| `listUnassignedFollowUps` (`:866`) | `SCAN_LIMIT + 1` | ✅ yes |
| `newestSendByAddress` (`:691`) | `SCAN_LIMIT + 1` | ✅ internally |
| **`pipelineTiles` (`:726, :732, :736`)** | **`SCAN_LIMIT` exactly, no `+1`** | ❌ **NO. Returns four bare numbers with no bound.** |
| `savedForName` (`:922`) | `SCAN_LIMIT` | ❌ no — documented `ponytail:` ceiling |

The hard cap is 1,000 rows *per import*, not per tenant, and imports converge/repeat. A tenant that
imports 1,000 contacts into a book that already holds any at all lands past 1,000, at which point
**"Contacts needing attention" and "Consent on record" silently under-count** — directly against
playbook invariant 3 ("The four tiles are ALWAYS-KNOWN counts… a real zero is `0`, never `Unknown`")
and the `pipeline-uat.spec.ts` step 1 assertion that a tile always parses as an integer (which will
keep passing, because a wrong integer is still an integer).

**Options for the plan, in ascending cost:** raise `SCAN_LIMIT` to e.g. 5,000 with a note (one-line,
still bounded, still far under the 32,000-doc read limit — see below); or give `pipelineTiles` the
`+1` and a `partial` flag plus a rendered caveat; or accept and document. **Do not leave it
undecided.** Note the existing `ponytail:` comment at `:633` already names the upgrade path
(index-range-driven cursors) for the paging half.

## Convex Limits — the batch-size evidence

Convex `1.42.1` (`packages/backend/package.json:53`). All figures from
[docs.convex.dev/production/state/limits](https://docs.convex.dev/production/state/limits),
cross-checked against `packages/backend/convex/_generated/ai/guidelines.md` (lines 75-77, 159, 248).

| Limit | Documented value | What 100 rows/batch uses | Headroom |
|-------|------------------|--------------------------|----------|
| Function **argument** size | **16 MiB** | ~20 KB (100 rows × 5 short strings) | ~800× |
| Function **return** value size | 16 MiB | 4 integers | — |
| **Array** element count | **8,192** | 100 (and 1,000 at the file cap) | 8× even unbatched |
| Documents **scanned** per transaction | **32,000** | 100 indexed `.unique()` reads | 320× |
| Documents **written** per transaction | **16,000** | ≤100 inserts/patches | 160× |
| Bytes read / written per transaction | 16 MiB each | ~50 KB | ~300× |
| Query/mutation **execution time** | **1 second of USER code** (excludes DB ops) | 100 × (normalize + regex) ≈ sub-millisecond | vast |
| Document size | 1 MiB | one contact row ≈ 400 bytes | — |
| Scheduled functions per mutation | 1,000 | 0 (no job queue — locked) | — |

**Verdict: the spec's numbers are correct and need no revision.** Both `100` and `500` sit at
roughly 1% of the tightest applicable limit. Every hard Convex limit would in fact permit the whole
1,000-row file in a single call. **The plan should therefore justify 100 on the real reasons, not
on a limit it does not approach:**

1. **Retry blast radius.** A failed batch replays 100 rows, and convergence makes the replay free.
2. **Progress granularity.** Ten batches at the cap give the UI ten honest progress steps; one call
   gives a spinner and nothing else.
3. **OCC conflict window.** Every row in a batch writes the same tenant's `contacts` rows; a
   shorter transaction is a smaller window against the user's own concurrent Pipeline writes.
   *(Convex's docs do not publish OCC retry semantics — MEDIUM confidence on the magnitude of this
   effect, HIGH on the direction.)*

**`matchExisting` at 500 addresses/call** is likewise unremarkable: 500 sequential indexed
`.unique()` reads, vs 32,000 scanned. Precedent already exists in this exact file —
`suppressedAmong` (`contacts.ts:560`) loops an **unbounded** `v.array(v.string())` doing one indexed
read each. **`matchExisting` should be stricter than its precedent** and refuse an array longer than
its documented chunk (write-boundary discipline, the `parseCrmOperations` idiom): a named
`IMPORT_MATCH_TOO_MANY` refusal, not an implicit slice.

### No migration is required

Per `packages/backend/.claude/skills/convex-migration-helper/SKILL.md` — "Safe Changes (No Migration
Needed): Adding Optional Field". Both changes here are widening: three `v.optional` columns, and two
unions gaining a member. Every row at rest still validates. `@convex-dev/migrations` is not needed
and should not be introduced. Narrowing later *would* need one — worth a one-line note in
`schema.ts` beside the new members.

Also inherited from Phase 19 (19-01 summary): **schema-only changes need no `npx convex codegen`** —
`_generated/dataModel.d.ts` derives table types generically from `schema.ts`. Codegen is only needed
for a new *module*, and this phase adds no Convex module (both functions land in the existing
`contacts.ts`).

## The Browser File-Read Precedent

Four candidates, and **none of them is a local-only read** — all four upload. The right answer is a
*narrowing* of `Dropzone.tsx`, keeping its picker shape and dropping its upload half.

| Precedent | What it does | Relevance |
|-----------|-------------|-----------|
| `vault/Dropzone.tsx` | Hidden `<input type="file">` + `useRef` click-through + drag-and-drop, size guard **before** reading, `await file.arrayBuffer()`, `new TextDecoder().decode(buf)` for text types, **then** `generateUploadUrl` → `POST` → `vaultUpload` | **THE ONE TO FOLLOW** (locked decision), and CONTEXT is right. Take: the hidden-input + ref idiom, `resolveMimeType`, the pre-read size guard, the `FileOutcome[]` per-item result list (`:53`, added because "the old code wrote every failure into `error`, so nine failures out of ten left only the last message"), and the exported `pillPrimary` / `pillSecondary` style helpers (`:58-79`). **Drop: everything from `generateUploadUrl` onward.** |
| `_components/AttachmentPicker.tsx` | "Upload-first (CONTEXT): the file goes to Convex storage as it is picked" | Upload-first by design — the opposite of this phase's core decision. Reference only for its `MAX_*` client-mirror pattern. |
| `workspace/IntakeControls.tsx` | Hosts `AttachmentPicker`; no file read of its own | Not relevant. |
| `dashboard/onboarding/page.tsx:369` | `blob.arrayBuffer()` on a **recorded audio Blob**, not a picked File | Not relevant. |

**What they all share:** a hidden `<input type="file">` driven by a ref (never a visible input),
size/type validation client-side stated as "UX only; the server is the boundary", a `busy` flag, and
the input's `value` reset to `""` in a `finally` so re-picking the same file re-fires `change`
(`Dropzone.tsx:174`, `AttachmentPicker.tsx:38`). **All three matter for a CSV import** — especially
the reset, since "fix my file and try the same name again" is the expected retry loop here.

**For reading text, prefer `await file.text()` over `arrayBuffer()` + `TextDecoder`.** `Dropzone`
uses the two-step form only because it needs the same `ArrayBuffer` for SHA-256 hashing; this phase
hashes nothing. `File.text()` is a one-liner and handles the UTF-8 decode. **The BOM must still be
stripped in `parseCsv`** — `TextDecoder("utf-8")` does not strip it by default and `File.text()`
follows the same rule, which is exactly why the spec lists "a leading BOM" as a parser requirement.

**Playwright drives it identically:** `page.locator('input[type="file"]').setInputFiles({ name, mimeType, buffer })` — `vault.spec.ts:139` and `intake.spec.ts:48` both use the in-memory buffer form, so the fixture CSV needs no file on disk.

## Common Pitfalls

### P1 — `upsertContact`'s arg validator is a hand-maintained union with nothing binding it
**What goes wrong:** the schema widens, `upsertContact`'s `v.union` at `contacts.ts:240` does not,
and every typecheck in the repo still passes (`Doc<"contacts">` derives from the schema, not from
the arg validator). Exactly `patchPlan`'s Pitfall 1 (`cockpit.md:507`).
**How to avoid:** decide *deliberately* — recommendation is **do not widen it**, and pin the
decision with a test that the runtime validator rejects `origin: "imported"`.
**Warning sign:** any test that calls `upsertContact` with the new origin and passes.

### P2 — `ORIGINS` in `core/src/contacts.ts:126` is typed `readonly string[]`
**What goes wrong:** it is structurally decoupled from `CrmContactOrigin`, so nothing forces the
two to agree in either direction. A careless "widen every origin list" edit silently grants the
**agent** the ability to stage `origin: "imported"` — contradicting the human-only decision.
**How to avoid:** leave it alone; add a `parseCrmOperations` test asserting
`CRM_CONTACT_ORIGIN_INVALID` for `"imported"`.

### P3 — the Pipeline consent chip drops `source` entirely
See §"Union Blast Radius", site 16. **The single most likely way this phase ships a
schema distinction with no product meaning.** Decide (a) render or (b) accept-and-document.

### P4 — `pipelineTiles` caps at 1,000 with no `partial` signal
See §"SCAN_LIMIT". A 1,000-row import can silently make the four "ALWAYS-KNOWN counts" wrong, and
step 1's integer-parse assertion will keep passing on a wrong integer.

### P5 — "fill empty only" is not what `upsertContactRow` does today
Its rule is "a blank name must not *erase*". A non-blank name **overwrites**. Only the blank case is
tested (`contacts.test.ts:320`), so changing the wrong one is silent for hand-add.
**How to avoid:** a `fillEmptyOnly` flag defaulting to today's behaviour, plus a test that hand-add
STILL overwrites (non-vacuity on the other side of the flag).

### P6 — consent overwrite destroys stronger evidence
An import re-touching a contact with a real per-person `asserted-by-user` record would replace it
with the batch attestation. **Write consent only when `consentAt === undefined`.**

### P7 — the §4 audit scan and the PIPE-01 structural scan both read the new code
`contacts.test.ts:1057` scans `convex/contacts.ts` **and** `core/src/contacts.ts` for
`/amountCents|opportunit|\bstage\b/i` with comments stripped. **The word "stage" is forbidden** —
a three-**stage** import panel described in a `contacts.ts` comment is fine (comments are stripped),
but an identifier like `importStage` or `type Stage` in either scanned file fails the suite. Name
the UI states `step` / `phase`, and note the scan does **not** currently cover a new
`core/src/contactImport.ts` — extending it there is optional but cheap.
The §4 scan (`:533`) `JSON.stringify`s the whole `audit` table and asserts it contains neither the
address nor the wording. **Extend it to cover an import run** — that is a locked testing decision.

### P8 — the playbook Stop hook will block the commit
`docs/playbooks/watch.json:233-239` maps `contacts-crm.md` to `packages/core/src/contacts.ts`,
`packages/core/src/contacts.test.ts`, `packages/backend/convex/contacts.ts`,
`packages/backend/convex/contacts.test.ts`, `apps/web/app/(app)/dashboard/pipeline/`.
Two consequences:
- **`packages/core/src/contactImport.ts` is covered by NO playbook.** The hook blocks a turn that
  adds a new code file under `packages/` that no playbook covers. **Add `contactImport.ts` and
  `contactImport.test.ts` to `contacts-crm.md`'s `watch.json` array in the same commit.**
- **`cockpit.md` watches `apps/web/e2e/` (line 109).** Touching `pipeline-uat.spec.ts` therefore
  requires a `cockpit.md` `Last verified` bump too — exactly the "WATCH-GATE BUMP ONLY" note 19-07
  left. Expect **two** playbook edits, not one.

### P9 — CRLF anchors silently no-op on `.planning/*.md` and `docs/playbooks/*.md`
`core.autocrlf=true` + `* text=auto`. Multi-line `\n` Edit anchors fail silently. **Use SINGLE-LINE
anchors** and assert uniqueness first. (From CONTEXT `<specifics>`, and independently recorded in
memory.)

### P10 — the shared working tree
Parallel lanes commit into this same tree. **Pathspec commits only** (`git commit -m "…" -- <paths>`),
never `git add -A`, and check `.git/MERGE_HEAD` before committing. 19-01 lost a foreign lane's
staged files into `38ac3d2` by not doing this.

### P11 — the backend vitest fork crashes under component registration pressure
`contacts.test.ts`'s `harness({ audit: true })` registers the aggregate component and is used by
exactly 4 of ~40 tests, deliberately: registering it 40× "pushed the shared vitest fork over its
memory budget" and killed `vaultDigest.test.ts` mid-file. **New import tests must use the default
`harness()`** unless they assert on audit rows.

### P12 — the typecheck baseline may not be zero
CONTEXT records `packages/backend/convex/cash.ts` possibly carrying 2 `TS2739` from the finance
lane (⇒ `pnpm typecheck` 8/10). `convex dev` typechecks before pushing, so a stale build can be
served silently; `:3210` was last running with `--typecheck=disable`. **Measure the baseline before
starting** and again after, and compare deltas rather than absolutes.

### P13 — `createdAt` ties on a bulk import
1,000 rows inserted in one transaction share a `Date.now()` per batch. `pageBounded`
(`contacts.ts:640`) sorts with `compareDashboardOrder`, which the file comment says handles the
"createdAt TIE handling (id-descending)" exactly rather than approximately. So paging stays correct —
**but the plan should assert it** with a >25-row import followed by a full page-through, because
this phase is the first thing in the repo that can produce a thousand-way tie.

## Open Questions

1. **Does writing consent count as "enriched"?**
   - Known: the four counts are `{ created, enriched, unchanged, rejected }`, and `matchExisting`
     reports emptiness for exactly `name`/`company`/`phone`/`title`.
   - Unclear: if consent is written to every previously-unconsented existing row, then *every*
     existing row is modified and `unchanged` is structurally always 0 — a preview that promises
     "K unchanged" and then changes them.
   - **Recommendation:** define the counts over the **four mappable fields only**, matching what
     `matchExisting` reports, and state that in the returned type's doc comment plus the preview
     copy. Test it: a row whose four fields are all full but which gains consent must count as
     `unchanged`.

2. **Which line number does a rejected row report?**
   - Known: locked decision says "rejected rows listed by line number and reason".
   - Unclear: an embedded newline inside a quoted field makes the physical file line diverge from
     the record index, and a user matching the message against their spreadsheet cares about the
     spreadsheet's row.
   - **Recommendation:** report the **1-based record index excluding the header** (what a
     spreadsheet shows), and say so in the preview copy. Track it in `parseCsv`'s output so
     `mapRows` does not have to re-derive it.

3. **Does `SCAN_LIMIT` get raised in this phase or in a follow-up?**
   - Known: `pipelineTiles` silently under-counts past 1,000 (§SCAN_LIMIT).
   - Unclear: raising it is a one-line change to a shared constant that affects five readers,
     including `savedForName`, which the cockpit calls on every resolution.
   - **Recommendation:** raise `SCAN_LIMIT` to 5,000 (still ~6× under the 32,000-doc read limit)
     **and** give `pipelineTiles` the `+1`/partial treatment, both in this phase. The alternative —
     shipping an import that can make the headline tiles wrong — contradicts playbook invariant 3.

4. **Does the Pipeline chip render `consent.source`?**
   - See §"Union Blast Radius" site 16 and Pitfall P3. **Must be decided in the plan, not deferred.**

5. **Is there a 1,000-row *tenant* cap anywhere, or only a per-import one?**
   - Known: the file cap is 1,000 rows per import; imports converge, so re-running is expected.
   - Unclear: nothing stops ten sequential 1,000-row imports.
   - **Recommendation:** none needed for correctness (`by_tenant_email` scales; the cap is on the
     *read models*, addressed by Q3). Worth one sentence in the playbook's ceilings section.
