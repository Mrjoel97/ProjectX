**The picker idiom (from `Dropzone.tsx`, upload half DROPPED):** a hidden `<input type="file">`
driven by a `useRef`, `resolveMimeType(file.name, file.type)` (Chrome on Windows reports `""` for
`.csv`), a size/row guard BEFORE reading, a `busy` flag, a per-item outcome list rather than one
overwritten `error` string, and **`input.value = ""` in a `finally`** so re-picking the same
filename re-fires `change` — "fix my file and try again" is the expected retry loop here.

  <action>
Create `ImportPanel.tsx` (`"use client"`). ONE file, three screens, driven by a `step` union:
`"choose" | "preview" | "done"`.

**Step 1 — choose.** Hidden `<input type="file" accept=".csv,text/csv" data-testid="import-file-input">` + ref, a visible button, the Dropzone drag handlers if they are
cheap to lift. On pick: `resolveMimeType` sanity check, `await file.text()`, `parseCsv`, then
`detectMapping(records[0].fields)` and `mapRows`. Catch the two named refusals and render them
through `PipelineStateNotice`:
- `IMPORT_TOO_MANY_ROWS` → "This file has more than 1,000 rows. Split it and import the parts —
  re-running an import is safe." (name the limit, per the locked decision)
- `IMPORT_NO_EMAIL_COLUMN` → "No email column detected. Pick which column holds the address."
Reset `input.value = ""` in a `finally`.

**Step 2 — preview.** Four parts, in this order:
1. The detected mapping, each field a `<select>` over the header cells with a "— not imported —"
   option, so every column is overridable. Changing one re-runs `mapRows` locally (no re-read of
   the file needed — hold the parsed records in state).
2. The counts `N new · M enriched · K unchanged · R rejected`, from `matchExisting` chunked at
   `IMPORT_MATCH_CHUNK` via `useConvex().query`. `enriched` = exists AND at least one of the row's
   non-blank values lands on a field the match reports as empty; `unchanged` = exists and none do.
   Copy under the counts stating that the counts are about the four importable fields.
3. The rejected rows, each `line` + `reason`, inside a `scroller`.
4. A back-out that returns to step 1.
3 and 4 use `--ink-soft`, never amber.

**Step 3 — attest (same screen, below the preview).** The `IMPORT_ATTESTATION` sentence rendered
verbatim beside a checkbox that **starts unticked**, a free-text "Where did these come from?"
(`consentContext`), and a Confirm button **disabled until the box is ticked** (`data-testid="import-confirm"`). A pre-ticked box would make the stored wording a false
statement about what the user did.

**Confirm.** Loop the deduped rows in `IMPORT_BATCH_ROWS` slices through
`useMutation(api.contacts.importContacts)`, passing `{ wording: IMPORT_ATTESTATION, context }`,
summing the four counts as they land. Show honest progress ("batch 3 of 7"). On a batch failure,
stop and report what landed plus: re-running the same file is safe — it fills blanks and overwrites
nothing. Then `step = "done"` with the totals and a note that the table below is now current.

Export, for the DOM-free test runner: `ImportPreview` (props: mapping, header, counts, rejected,
handlers) and `ImportAttest` (props: wording, ticked, busy, handlers) as PURE prop-driven
components; keep the hook-bearing `ImportPanel` the only stateful export. `pipelineView.test.ts`
renders to a string with `renderToStaticMarkup`, so anything holding a hook is untestable there.

Testids: `import-panel`, `import-file-input`, `import-preview`, `import-counts`, `import-rejected`,
`import-mapping`, `import-attest`, `import-confirm`, `import-refusal`, `import-done`.

**Never** a `window.alert` / `window.confirm` / `<dialog>` — every refusal is inline (proven in plan
07 by counting dialogs). **Never** a new dependency, and **no component library** (CLAUDE.md §10).
Wrap the preview table in `scroller`: the e2e phone-width step asserts
`document.documentElement.scrollWidth <= 391` at 390px.
