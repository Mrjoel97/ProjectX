## Test Infrastructure

| Property | Value |
|----------|-------|
| **Framework** | vitest (core, backend, web) + Playwright (browser) |
| **Config file** | per-package `vitest.config.ts`; `apps/web/playwright.config.ts` |
| **Quick run command** | `pnpm --filter @pikar/core test` (~15s — the parser lives here) |
| **Full suite command** | `pnpm test` (turbo, 9 tasks) then `pnpm typecheck` |
| **Browser command** | `npx playwright test e2e/pipeline-uat.spec.ts --no-deps --workers=1` (~4 min) |
| **Estimated runtime** | quick ~15s · full ~6 min · browser ~4 min |

**Two harness facts that invalidate naive commands:**
- `pnpm --filter <pkg> test -- <name>` **does NOT filter** anywhere in this repo — it runs the
  whole package suite. Do not write a per-task command that relies on it. The working forms are
  `pnpm --filter @pikar/core test contactImport` (no `--`) and, for the backend,
  `cd packages/backend && npx vitest run convex/contacts.test.ts`.
- The backend vitest fork crashes (`vaultDigest.test.ts` failures + `Cannot set properties of
  undefined (setting 'exit')`) when aggregate/retrier components are registered for tests that
  write no audit row. Use `harness({ audit: true })` / `withFanoutOnly()` / per-test
  `convexTest`. A red backend suite after adding tests is yours, not pre-existing — re-run once
  before believing it (the suite also flakes under memory pressure).

**A THIRD, found at 19.1-07 and worth as much as both: the browser and the harness CLI can address
different deployments.** `pipeline-uat.spec.ts` seeds its throwaway tenant through `convex run`
(which resolves `packages/backend/.env.local` / `CONVEX_DEPLOYMENT`) while the browser talks to
`NEXT_PUBLIC_CONVEX_URL` from `apps/web/.env.local`. During this plan a concurrent lane repointed
the backend file at the **cloud** dev deployment while the local backend on `:3210` kept serving the
browser, so every seed landed where the browser could not see it and the **entire spec, including
the 15 pre-existing steps, failed at the onboarding gate** with no message naming the cause. The
symptom to recognise: `onboarding.status` returns `needsOnboarding: true` for a tenant
`__seedOnboardedTenant` has just reported writing. The fix used here was to name the local
deployment for the run rather than to edit a file a foreign lane owns:
`CONVEX_DEPLOYMENT="local:local-<...>" npx playwright test …`.

## Wave 0 Requirements

Existing infrastructure covers the unit and integration layers — `packages/core` and
`contacts.test.ts` both exist and are green, and `pipeline-uat.spec.ts` already provisions its
own throwaway tenant via `/signup`. Two setup items were genuinely new:

- [x] A fixture CSV exercising the five parser hazards (quoted comma, embedded newline, doubled
      quote, BOM, CRLF) **plus** a duplicate-of-an-existing contact, so the browser step observes
      `enriched` and not only `created`.
      **DONE at 19.1-07 task 1 as `FIXTURE_CSV`, an INLINE TS constant in `pipeline-uat.spec.ts` —
      NOT a committed `.csv` under `e2e/fixtures/`.** The reason is the repo's own git config:
      `core.autocrlf=true` + `* text=auto` would normalize a committed file's CRLF on checkout and
      can strip its BOM, and those are two of the five hazards the fixture exists to prove — a
      checked-in file would have quietly stopped testing them. Built with explicit `\uFEFF` and
      `\r\n` escapes it is byte-identical in every checkout, and Playwright's
      `setInputFiles({ name, mimeType, buffer })` needs no file on disk (`vault.spec.ts:139`,
      `intake.spec.ts:48`). All six required rows are present, and the embedded newline is
      load-bearing: it is what makes the malformed row's PHYSICAL file line (7) differ from its
      record index (6), which is the assertion the step actually makes.
- [x] `packages/core/src/contactImport.ts` registered in `docs/playbooks/watch.json` under the
      `contacts-crm.md` entry — **the Stop hook blocks the commit without this**, because it is a
      new code file under `packages/` covered by no playbook. **DONE at 19.1-01 task 3**;
      `node scripts/check-playbooks.mjs` has exited 0 at every wave since.
- [x] No framework install needed — Vitest and Playwright are both present and configured.
- [x] No new test *file* is needed on the backend or e2e side: `contacts.test.ts` and
      `pipeline-uat.spec.ts` both exist and are extended in place. `ImportPanel.tsx`'s tests go in
      the existing `pipelineView.test.ts` (a new `.test.tsx` would be SILENTLY SKIPPED —
      `apps/web/vitest.config.mts` includes `app/**/*.test.ts` only).

The second Stop-hook gate is not a Wave 0 item but blocked the LAST wave: `cockpit.md` watches

## Anti-Vacuity Requirements

This phase inherits five findings of green-but-meaningless tests from Phase 19. Each rule below
exists because a specific test passed while the thing it named was broken.

1. **Assert on stored state, not on the reply.** Fill-empty-only, consent non-downgrade and the
   counts must be asserted by reading the contact rows back — a mutation's return value can agree
   with itself while the write is wrong. *(19.1-03 T2, 19.1-04 T2, 19.1-07 T1 step 9.)*
   **HELD.** 19.1-07's browser step reads back through `listContacts`, `matchExisting` and
   `consentRecord`, and the "Jane D." mutation proved the oracle sees the stored value.
2. **Every new guard is mutation-proven:** break it, observe red, record the exact failing text,
   revert. A guard never observed failing is not proven. *(19.1-02 T3, 19.1-03 T3, 19.1-04 T3,
   19.1-05 T2, 19.1-06 T3 — 13 proofs in total.)* **HELD**, and 19.1-07 added two more against its
   own new assertions (15 in the phase).
3. **The browser step is a REQUIREMENT, not a nicety.** Phase 19 shipped a capability that unit
   tests, SMOKE tests and a paid eval gate all certified while it was unreachable from the
   product, because each supplied context the browser never provides. An import feature has the
   identical shape: a `tenantMutation` passing every backend test can still be unreachable
   because the button is not wired. *(19.1-07 T1 — a whole plan, not a bullet.)* **HELD** — a real
   Chromium picked a real CSV, and the four counts, the file-line rejection, the disabled Confirm
   and the written rows were all observed there.
4. **The union walk is evidence, not faith in `tsc`.** Research found 19 sites, of which **3 are
   silent**: `upsertContact`'s hand-maintained arg validator (`contacts.ts:240`), `ORIGINS` in
   `core/src/contacts.ts:126` (structurally decoupled from `CrmContactOrigin`), and
   `PipelineView.tsx:279-283`. Each silent site needs a test that goes red when its case is
   missing. *(19.1-02 T2 — one test each; 19.1-02 T3 mutation-proves all three.)* **HELD**, and the
   third site is now also browser-observed: the imported contact's chip reads
   `Consented <day> · imported` in a real page.
5. **`pipelineTiles`' bound must be proven by a test that fails on the old behaviour** — an
   assertion that merely reads a number would pass on the confidently-wrong integer that
   motivated the fix. *(19.1-05 T1 — seeds `SCAN_LIMIT + 1` rows and asserts `partial === "row-cap"`, a field the old code does not return.)* **HELD** — RED-first observed as
   `expected undefined to be 'row-cap'`.
