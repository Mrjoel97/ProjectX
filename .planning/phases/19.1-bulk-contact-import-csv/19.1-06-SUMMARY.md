# Phase 19.1 Plan 06: The CSV Import Panel Summary

`matchExisting` and `importContacts` had **zero callers** until this commit. A user on
`/dashboard/pipeline` can now pick a CSV, see the mapping and the four counts with every rejected
row named by its file line, override any column, tick the attestation, confirm, and watch the
contacts appear in the table below — with the file never leaving the browser.

## Why This Plan Existed

Phase 19 shipped a capability that unit tests, SMOKE tests and a paid eval gate all certified while
no user could reach it (the clock plane: `runAgentLoop` and the web caller both needed the
parameter, only one got it). 19.1-01 through 19.1-05 rebuilt that exact situation on purpose — a
pure parser, a widened schema, a shared writer flag, two tenant-scoped functions, an honest tile
bound, and **not one line of it reachable from the product**. This plan is the wiring; 19.1-07 is
the browser that proves it.

So the wiring is *asserted*, not assumed. The source scan pins that `ImportPanel.tsx` imports the
parser by SUBPATH and names both `api.contacts.matchExisting` and `api.contacts.importContacts` —
because a tested function with no caller is invisible to every green suite in this repo.

## What Was Built

**`ImportPanel.tsx` (new, 599 lines)** — one file, one `step` union (`"choose" | "preview" | "done"`;
never `stage`, which the PIPE-01 structural scan bans and now scans this file for too).

| Step | What it does |
| --- | --- |
| choose | Hidden `<input type="file" accept=".csv,text/csv">` + ref + a visible button that also accepts a drop. `resolveMimeType` sanity check → `await file.text()` → `parseCsv`. `input.value = ""` in a `finally`, so re-picking the same filename re-fires `change` |
| preview | The mapping (a `<select>` per field over the header cells, every column overridable, `— not imported —` always available), the four counts from `matchExisting`, the rejected rows by PHYSICAL FILE LINE inside a `scroller`, and a back-out |
| done | The four totals and a line saying the table below is now current |

**The file never leaves the browser.** `file.text()`, not `arrayBuffer()` + `TextDecoder` —
`Dropzone` only uses the two-step form because it hashes bytes and nothing here is hashed. Only
mapped rows cross the wire. `generateUploadUrl` and `vaultUpload` appear nowhere, and a test scans
for both: if either ever appears, the "no PII at rest, so no retention rule" claim in the playbook
is false and the retention question re-opens.

**The counts are a projection, not a guess.** `matchExisting` is a **one-shot**
`useConvex().query` chunked at `IMPORT_MATCH_CHUNK` (the boundary *refuses* a longer array rather
than slicing it, so the chunking is not optional), and a row counts as `enriched` only when it
carries a value for a field the match reports **empty** — the same four-field definition the write
uses, so the preview and the result cannot disagree.

**Confirm** loops `IMPORT_BATCH_ROWS` slices through `useMutation(api.contacts.importContacts)`,
passing `{ wording: IMPORT_ATTESTATION, context }`, showing `Importing batch 3 of 7…` and summing
the four counts as they land. A failed batch stops and reports what landed plus *re-running the same
file is safe — it fills blanks and overwrites nothing*, which is true by construction
(upsert-by-address + fill-empty-only) and is the whole reason this feature has no job queue.

**Refusals are inline, grey, and each names the way out.** Every one goes through
`PipelineStateNotice` (`role="status"`, `aria-live="polite"`, `--ink-soft`, dashed rule). Never
amber — that is the approval gate's alone (BRAND §2). No `window.alert`, no `window.confirm`, no
`<dialog>`: a browser modal blocks the page and cannot be driven by plan 07's Playwright spec, which
counts dialogs.

**`PipelineView.tsx`** gains `ConnectedImport` — the fourth connected section, mounted **between
`ConnectedTiles` and `ConnectedContacts`** (not between contacts and unassigned: the e2e
document-order assertion pins that `pipeline-unassigned` FOLLOWS `pipeline-contacts`). It is the
only section that reads nothing on mount, so it costs nothing until a file is picked. Ten style
objects are now `export`ed for the panel rather than re-declared there.

## The Attestation Is the Contract

The checkbox **starts unticked** and Confirm carries `disabled` until it is ticked. The sentence is
rendered from `IMPORT_ATTESTATION`, never re-typed — what appears on screen and what is stored
byte-for-byte on every contact are the same string. A pre-ticked box would make the stored wording a
false statement about what the user did, and the stored wording is the evidence.

## Tests (+5, and one rewritten)

`pipelineView.test.ts` **27/27** (was 22). `@pikar/web` **176/176** across 10 files (was 171).

| Test | The trap it closes |
| --- | --- |
| Confirm carries `disabled` at `ticked: false` and **the attribute is absent entirely** at `ticked: true`; the box renders without `checked` | the gate itself, with its own non-vacuity floor — asserting only the disabled case would pass on a permanently-disabled button |

actually requires — it forbids a row appearing because software went looking. The banned *third*
button (seeded suggestions from recent mail, the contacts-CACHE seed) is still asserted absent.

## Deviations from Plan

### 1. [Rule 1 — the plan falsified an existing test it did not mention]

- **Found during:** Task 2
- **Issue:** The plan says to update `ContactsEmptyState`'s "EXACTLY ONE action" **doc comment**. It
  does not mention that the same claim is an assertion — `expect(html.split("<button").length - 1).toBe(1)` — which the second button turns red. Leaving it would have blocked the plan; weakening
  it to "at least one" would have deleted the guard against the mailbox-suggestions seed.
- **Fix:** the test now pins **two** buttons, names the second by testid, keeps every
  no-mailbox-suggestion assertion, and records in the test itself why two deliberate human acts do
  not contradict invariant 1.
- **Files modified:** `apps/web/app/(app)/dashboard/pipeline/pipelineView.test.ts`
- **Commit:** `4b78f5f`

### 2. [Rule 1 — a strict MIME equality would have refused valid CSVs]

- **Found during:** Task 1
- **Issue:** The plan says "`resolveMimeType(file.name, file.type)` (Chrome on Windows reports `""`
  for `.csv`)". `resolveMimeType` returns the browser type whenever it is non-empty, and Chrome on
  Windows reports `application/vnd.ms-excel` for `.csv` when Excel owns the extension — so a strict
  `!== "text/csv"` refusal would bounce exactly the files this feature exists for, on the platform
  this repo is developed on.
- **Fix:** accept when the filename ends `.csv` **or** the resolved type is `text/csv`. The comment
  records both failure modes so the next reader does not "tighten" it back.
- **Files modified:** `apps/web/app/(app)/dashboard/pipeline/ImportPanel.tsx`
- **Commit:** `4b78f5f`

### 3. [Rule 3 — the row cap had to be checked before `mapRows`]

- **Found during:** Task 1
- **Issue:** `mapRows` checks the email column FIRST and the row count second, so a 5,000-row file
  with an unrecognised header throws `IMPORT_NO_EMAIL_COLUMN` — and the plan routes that refusal
  into the preview, where the user would fix the column only to be refused again for size. Worse,
  the size refusal must be reachable from the picker: with no importable rows there is nothing to
  preview.
- **Fix:** the panel checks `parsed.length - 1 > IMPORT_ROW_MAX` at the picker using the shared
  constant (no second rule, no drift), and `mapSafely` still maps both codes to copy for the preview.
- **Files modified:** `apps/web/app/(app)/dashboard/pipeline/ImportPanel.tsx`
- **Commit:** `4b78f5f`

### 4. [Plan-internal] One commit, not per-task commits

Task 3 of the plan specifies the single pathspec commit and gives its message. Same call as
19.1-02/03/04/05, for the same reason: the panel and the page that mounts it are one change, and
task 3's mutation-proofs revert code that would otherwise have been committed broken-then-fixed.

### 5. [Noted] The local `confirm()` was renamed to `runImport()`

Task 3's behaviour list bans `window.confirm`. A helper literally named `confirm` would have made
the strongest form of that scan (`confirm(`, which the phase-19 test already uses on
`PipelineView.tsx`) impossible to apply to this file. Renaming cost one line and let the scan cover
both files identically.

## What This Does NOT Do

No e2e, no fixture CSV, no owner judgement. No agent path — an import stays human-only, because the
attestation is a legal statement a person makes and the agent cannot see the file. Nothing in this
plan has been exercised by a browser against a real deployment; until 19.1-07 runs, "a user can
import contacts" is a claim supported by a compiled bundle and a DOM-free renderer, which is
precisely the evidence phase 19 had when it was wrong.
