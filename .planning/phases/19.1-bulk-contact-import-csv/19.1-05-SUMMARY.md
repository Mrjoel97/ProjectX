# Phase 19.1 Plan 05: pipelineTiles Reports Its Scan Bound Summary

The four headline Pipeline tiles can no longer be confidently wrong. `pipelineTiles` scans
`SCAN_LIMIT + 1`, counts over the first `SCAN_LIMIT`, and returns `partial: "row-cap" | null`; the
page renders `1000+`. `SCAN_LIMIT` itself is untouched.

## The Bug, Precisely

`pipelineTiles` took exactly `SCAN_LIMIT` (1 000) on all three of its scans, with no probe row and
no bound on its return — while its two siblings, `listContacts` and `listUnassignedFollowUps`, had
taken `SCAN_LIMIT + 1` and reported their bound since 19-07. Nothing caps a tenant's contact count
(the 1 000-row ceiling is PER IMPORT), so **one max-size CSV import into a book that already held a
single contact** put the tenant past the cap and made all four ALWAYS-KNOWN tiles under-count
silently.

The reason it survived phase 19's verification is the interesting part: the e2e assertion is
`Number.parseInt(text, 10)` + `Number.isInteger` (`pipeline-uat.spec.ts:130`), and **a wrong integer
is still an integer**. Playbook invariant 3 was being broken by a page that looked perfectly fine.

## What Changed

**Backend (`convex/contacts.ts`)** — three `.take(SCAN_LIMIT)` became `.take(SCAN_LIMIT + 1)`; the
extra row is a BOUND PROBE and never a counted row, because every count is computed over
`slice(0, SCAN_LIMIT)`. `capped` is the OR of the three probes, and the return gains:

```ts
partial: "row-cap" | null;
```

One nullable literal rather than three per-scan flags: the tiles are read as a set, and any capped
scan makes every one of the four a floor rather than a total.

**`SCAN_LIMIT` was deliberately NOT raised** (owner decision 2026-08-10, restated in the source and
the playbook). Five readers share the constant — `savedForName` among them, which the cockpit calls
on *every* contact resolution — so raising it charges four other read models for one reader's
symptom, and the first book past the new number is wrong in exactly the same way. The upgrade path
recorded in the playbook's ceilings section is a counter or an aggregate component, never a bigger
cap.

**Frontend (`PipelineView.tsx`)** — the value cell is

```tsx
{`${tiles[tile.key]}${tiles.partial === "row-cap" ? "+" : ""}`}
```

`1000+` is a **floor stated honestly**, which is not the hedge invariant 3 bans: the page still
knows a number, it just knows there are at least that many. A real zero is still `0`.
`Number.parseInt("1000+", 10)` is still `1000`, so the e2e integer-parse assertion keeps working
untouched.

## Two Small Design Calls Worth Keeping

**1. `partial` must never become a fifth tile.** `TILES` was `satisfies ReadonlyArray<{ key: keyof
Tiles }>`, and `keyof Tiles` now admits `partial` — adding it would render the string `row-cap` in a
stat cell with nothing for `tsc` to say. `TILES` is now keyed on a **derived** type:

```ts
type TileCountKey = { [K in keyof Tiles]: Tiles[K] extends number ? K : never }[keyof Tiles];
```

A new *count* on the backend stays usable here; a new *non-count* is a compile error. This is the
same class as 19.1-02's `ORIGIN_LABELS` `satisfies` bind — the site that `tsc` would otherwise let
through silently.

**2. One template literal, not two JSX children.** The plan's form was `{tiles[tile.key]}{... ? "+"
: ""}`. That renders two text children, and `pipelineView.test.ts`'s zero test counts occurrences of
the literal substring `">0<"` — a form that split the value into separate nodes would have quietly
changed what that assertion measures. The template literal keeps the value ONE text node, so the
existing invariant-3 assertion still means what it meant. (Deviation 1 below.)

## Deviations from Plan

### 1. [Rule 1 — the plan's render form would have weakened an existing assertion]

- **Found during:** Task 2
- **Issue:** The plan specifies `{tiles[tile.key]}{tiles.partial === "row-cap" ? "+" : ""}`. Two JSX
  children is a different DOM shape from one, and invariant 3's enforcement test counts occurrences
  of the literal `">0<"` in the markup — a substring assertion that depends on the value being a
  single text node. Shipping the two-child form would have made the phase-19 invariant-3 test's
  meaning depend on a `renderToStaticMarkup` implementation detail.
- **Fix:** One template literal, identical output, comment records why. Verified: the existing
  `">0<"`-appears-four-times test is green unchanged.
- **Files modified:** `apps/web/app/(app)/dashboard/pipeline/PipelineView.tsx`
- **Commit:** `e860094`

### 2. [Rule 2 — missing type safety the plan asked for in prose only]

- **Found during:** Task 2
- **Issue:** The plan says "Keep `TILES` a list of exactly the four count keys (`partial` is not a
  tile)" — but `satisfies ReadonlyArray<{ key: keyof Tiles }>` now *accepts* `partial`, so that
  instruction was enforced by discipline alone. This is the exact defect class 19.1-02 hit with
  `ORIGIN_LABELS` (a widened union, a loosely typed consumer, a blank cell, and nothing for `tsc` to
  say).
- **Fix:** the derived `TileCountKey` above. Adding `partial` to `TILES` is now a compile error.
- **Files modified:** `apps/web/app/(app)/dashboard/pipeline/PipelineView.tsx`
- **Commit:** `e860094`

### 3. [Plan-internal] One commit, not per-task commits

Task 2 of the plan specifies the single pathspec commit and gives its exact message; the backend
change and the render that consumes it are one change, and the mutation-proofs revert code that
would otherwise have been committed broken-then-fixed. Same call as 19.1-02/03/04.

### 4. [Noted] Two existing assertions had to be updated, which the plan did not mention

`toEqual` on the tiles object is exact, so the empty-tenant test and the `pipelineTiles` isolation
test both had to gain `partial: null`, and the `Object.values(tiles)` typeof-number loop had to
narrow to the four count keys. Not a deviation in behaviour — worth recording because "the new field
is additive" is not true of a `toEqual`.

## Deferred / Out of Scope

- **`apps/web/e2e/pipeline-uat.spec.ts` was NOT touched.** `Number.parseInt("1000+", 10)` is `1000`
  and `Number.isInteger` holds, so `tileValue` needs no change, and a UAT tenant never reaches
  1 000 rows anyway. Touching `apps/web/e2e/` would also have required a second playbook bump
  (`cockpit.md` watches it) for no behavioural gain.
- **No aggregate/counter.** A tenant that genuinely outgrows a 1 000-row tile needs a counter, not a
  bigger scan; the playbook's ceilings section names that upgrade path and this plan does not take it.
- **`.planning/REQUIREMENTS.md` was NOT modified.** ACTN-05 and PIPE-01 were ticked at phase-19
  closure and the phase-25 lane owns that file.
- **Foreign lanes are live in this shared working tree.** `.planning/ROADMAP.md` was dirty at start
  with phase-20/20.1/21 edits and `docs/README.md` + `docs/governance/iso-9001-conformance-map.md`
  were already STAGED by another lane; the ROADMAP was therefore staged hunk-only (a
  `git hash-object -w` blob built from `HEAD` + this plan's three edits) and the doc commit was built
  through a TEMPORARY index so the other lane's staged files were neither committed nor unstaged.
