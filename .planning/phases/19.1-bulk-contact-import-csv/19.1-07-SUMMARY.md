# Phase 19.1 Plan 07: The Browser Proof Summary

A real Chromium picked a real CSV off a file input, read `2 new · 1 enriched · 1 unchanged ·
1 rejected`, was refused a Confirm until the attestation was ticked, wrote four contacts, and left a
hand-typed name byte-for-byte intact — and that last fact was read back out of stored state, not off
the screen that was under test.

## Owner Verdict

The blocking checkpoint (task 3) was presented with the two frames, the 16/16 run and three findings.
The owner's response, **verbatim and complete**, was one word:

> approved

Nothing else was said. **The three findings below were presented at the gate and were NOT
individually adjudicated.** They are open, carried-forward observations — not owner-accepted, not
owner-waived, not owner-approved-as-is.

## Why This Plan Existed

Phase 19 shipped a capability that unit tests, SMOKE tests and a paid 35/35 eval gate all certified
while no user could reach it: `runAgentLoop` dropped the trusted clock on the way to
`buildCockpitTools`, and separately the browser never sent `clientContext` at all. Each of those
harnesses supplied context a browser never provides.

19.1-01 through 19.1-06 rebuilt that exact situation deliberately — a pure parser, two widened
schema unions, a `fillEmptyOnly` flag on the one contact writer, two tenant-scoped functions, an
honest tile bound, a three-step panel — every one green, and none of them evidence that a user can
import a file. This plan is the evidence.

## What Was Built

**`step 3b`, placed immediately after step 3** (serial mode makes ordering the contract). Step 3 has
already created `JANE` ("Jane Doe", no company) and a NAMELESS contact, so one file produces all
four counts at once.

**`FIXTURE_CSV` — six rows, one per outcome, every parser hazard:**

| file line | row | outcome | what it proves |
| --- | --- | --- | --- |
| 1 | header | — | alias auto-mapping over `email,name,company,phone,title` |
| 2 | a new address | created | a comma inside a quoted field (`"Acme, Inc."`) |
| 3 | JANE, respelled `Jane D.`, with a company | enriched | fill-empty-only: the company lands, the name does not move |
| 4 + 5 | a new address | created | a NEWLINE inside a quoted field **and** a doubled quote (`"O""Neil, Ann"`) |
| 6 | NAMELESS, all mappable fields blank | unchanged | a matched contact the file adds nothing to |
| 7 | `not-an-address` | rejected | reported at **physical line 7**, not record index 6 |

Plus a BOM and CRLF throughout. It is an **inline TS constant with explicit `\uFEFF` / `\r\n`
escapes, not a committed `e2e/fixtures/*.csv`** — this repo runs `core.autocrlf=true` with
`* text=auto`, which normalizes a committed file's CRLF on checkout and can strip its BOM. A
checked-in fixture would have quietly stopped testing two of the five hazards it exists for.
`setInputFiles({ name, mimeType, buffer })` needs no file on disk.

**The ten assertions, in the plan's order:** dialogs counted from the top and asserted `0` at the
end; the panel's own control used as the entry point; the four counts asserted as an exact string;
the rejected row asserted as `Line 7: not a usable email address` with `toHaveCount(1)`; Confirm
`toBeDisabled()` with the box unchecked and `toBeEnabled()` after; the screenshot; tick, context,
confirm; the rows in the table with `Imported from a file` and `· imported` on the imported one and
`You added them` on Jane; **the read-back**; and an over-`IMPORT_ROW_MAX` file refused inline.

**The oracle is stored state.** `listContacts` gives Jane's `name` (`"Jane Doe"`) and `origin`
(`"user-entered"`); `matchExisting` gives her post-write emptiness (`["phone","title"]` exactly — so
`company` was filled and the two blank columns were not invented); `consentRecord` gives
`source: "imported-attested"`, `wording` compared against the **imported** `IMPORT_ATTESTATION`
constant, and the `context` string the browser typed. A re-typed copy of the sentence would keep
passing after the constant drifted, and the sentence is the evidence.

**Step 14 extended.** The 390px step now opens the import preview — its widest state, the mapping
table — and re-asserts that `document.documentElement.scrollWidth <= 391`, that the four tiles are
still >80px, and that Confirm's right edge stays inside the viewport. Nothing is confirmed there:
reaching the preview writes nothing.

**Both playbook gates.** `cockpit.md` carries a `Last verified` block marked **WATCH-GATE BUMP
ONLY** (it watches `apps/web/e2e/`; no cockpit behaviour moved and the agent still cannot initiate
an import). `contacts-crm.md` carries the phase's three closing invariants, every ceiling in one
place, the run instructions with both environment traps, and the two open defects.

## Three OPEN Items

Presented at the gate. The gate was approved. **These were not individually adjudicated and remain
open.**

### 1. The closed consent gate does not look closed (BRAND / accessibility)

`import-confirm` genuinely carries `disabled` before the tick — asserted, mutation-proven at
19.1-06, browser-observed here. But it is styled from the inline `primary` object, which has no
disabled variant, so in `step-03b-import-preview.png` the unarmed Confirm is full-teal and reads
exactly as pressable as the armed one. The gate is real; its affordance is not. Code left unchanged
(CLAUDE.md §10 makes visual direction the owner's).

### 2. The preview says `1 rejected`, the result screen says `0 rejected` — USER-VISIBLE

Both numbers are individually true: the client drops the unusable row before batching, so
`importContacts` rejected none. But the user is told one row cannot be imported and is then shown
`2 added · 1 filled in · 1 already up to date · 0 rejected` for the same file, which reads as "it got
in after all". Visible in `step-03b-import-chips.png`.

**The fix, written down so it is not lost:** in `ImportPanel.tsx`'s `done` branch, report
`result.rejected.length + mapped.rejected.length`. `mapped` is still in scope at `done` (`reset()`
only runs on "Import another file"), so it is one expression.

**Deliberately not applied here.** `ImportPanel.tsx` belongs to 19.1-06 and is outside this plan's
`files_modified`; an out-of-scope product edit made while closing a checkpoint is how a gate stops
meaning anything. This is a KNOWN GAP in a phase whose whole thesis is that the counts do not lie,
and it is recorded as such in `contacts-crm.md` and `19.1-VALIDATION.md`.

### 3. The consent-chip comparison could not be performed

The checkpoint asks for a hand-added contact's Consent chip beside an imported one. On the UAT
tenant **all four rows read `Consented Aug 10, 2026 · imported`**, because none carried consent
before the import and one attestation covered the whole file — correct behaviour, not a bug. The
column that actually distinguishes them is **Origin** (`You added them` vs `Imported from a file`),
and that is what the frame shows. A true chip-vs-chip comparison would need a seeded per-person
`asserted-by-user` record; **nothing was seeded**. The judgement stands unmade.

- **Found during:** Task 1, first run
- **Issue:** `pipeline-uat.spec.ts` seeds its throwaway tenant through `convex run` (which resolves
  `packages/backend/.env.local` / `CONVEX_DEPLOYMENT`) while the browser talks to
  `NEXT_PUBLIC_CONVEX_URL`. A concurrent lane had rewritten `packages/backend/.env.local` at 21:04 to
  point at the **cloud** `dev:woozy-wren-368`, while the local backend on `:3210` kept serving the

  15 pre-existing steps — failed at the onboarding gate**, with `pipeline-tiles` "element(s) not
  found" and nothing naming the cause. Confirmed by probing `onboarding.status` with the tenant's own
  JWT: `needsOnboarding: true` for a tenant `__seedOnboardedTenant` had just reported writing.
- **Fix:** named the local deployment per run rather than editing a file a foreign lane owns —
  `CONVEX_DEPLOYMENT="local:local-joel_feruzi-pikar_ai_50c69-1" npx playwright test …`. Recorded in
  both `contacts-crm.md` and the validation map.
- **Collateral, recorded not hidden:** before the cause was found, two probe seeds

## Environment Note Added After the Gate

The owner hit a dead sign-in redirect at `http://localhost:3000/dashboard?code=…`. The cause was the
local deployment's `SITE_URL` naming `:3000` with nothing listening there — **auth was succeeding and
only the final hop was dead**. It was corrected to `http://localhost:3111` on
`local:local-joel_feruzi-pikar_ai_50c69-1`, restoring the value this project's setup notes specify
and matching `convex/http.ts`'s own fallback. `packages/backend/.env.local` was **not** edited and
still names the cloud deployment, so the per-run `CONVEX_DEPLOYMENT` override remains necessary.
**These are two separate faults with two separate symptoms; fixing either does not fix the other.**
Both are now written into `contacts-crm.md`'s run instructions and the validation map.
