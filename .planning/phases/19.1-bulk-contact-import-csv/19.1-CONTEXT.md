# Phase 19.1: Bulk Contact Import (CSV) - Context

**Gathered:** 2026-08-10
**Status:** Ready for planning
**Source:** PRD Express Path (`docs/superpowers/specs/2026-08-10-contact-import-design.md`, committed 71c512a)

<domain>
## Phase Boundary

A user with an existing business migrates their contacts into Pikar from a CSV export in one
pass: parsed in the browser so the file is never stored, previewed as
`N new · M enriched · K unchanged · R rejected` before any write, and committed under a single
consent attestation recorded verbatim on every contact.

**This is 1 of 4 contact-acquisition subsystems.** The other three are OUT OF SCOPE and specced
separately: extract contacts from documents, search-then-import from the vault, and third-party
CRM migration. Do not build toward them; do not add seams for them.

Builds directly on the Phase 19 contacts substrate: `normalizeAddress`, `upsertContact`,
`assertConsent`, the `COVERED` isolation pin in `contacts.test.ts`, and the
`pipeline-uat.spec.ts` browser harness.

</domain>

<decisions>
## Implementation Decisions

Every item below is LOCKED by the approved design spec. The spec is the authority; read it.

### Format and scale
- **CSV only.** No vCard, no XLSX. Building them now is speculative.
- **Hard cap 1,000 rows.** Larger files are refused outright with a message naming the limit,
  and the cap carries a `ponytail:` comment naming the ceiling and the job-based upgrade path.
- **No job queue, no reservation table, no resumable cursor, no cleanup job.** Justified by the
  convergence property below — this absence is a deliberate decision, not an omission.

### Where parsing happens
- **In the browser. The raw file is NEVER uploaded and NEVER stored.** No PII at rest, no
  retention policy, no cleanup path. This was chosen over the server-side parse specifically to
  avoid recreating the PII honeypot Phase 19 worked to keep out of `audit.payload`.
- **`parseCsv` is hand-rolled RFC-4180 in `packages/core/src/contactImport.ts`** — pure TS, no
  Convex, testable in the core suite. NOT a new dependency. It must handle: quoted fields,
  commas inside quotes, newlines inside quotes, doubled quotes as an escaped quote, a leading
  BOM, and CRLF or LF.
- Header auto-mapping covers common aliases (`email`/`e-mail`/`email address`;
  `name`/`full name`/`first`+`last`; `company`/`organization`; `phone`; `title`/`job title`).
  Every column is overridable in the preview. Unmapped columns are dropped.

### Two reuses that are load-bearing
- Identity comes from `normalizeAddress` (`@pikar/core`).
- Validity comes from `isValidEmail` (`packages/core/src/validateSubmit.ts`) — the repo's
  designated single email regex, already the send path's rule and already wired into
  `parseCrmOperations` by 19-13.
- **Rationale (do not deviate):** using both means import cannot disagree with the send path
  about who a row is or whether an address is real. An import-local rule would produce contacts
  that exist but can never be emailed.

### Merge semantics
- **Fill empty fields only. NEVER overwrite a non-empty field.** A CRM export is usually staler
  than what the user has since typed; nothing typed by hand may be destroyed.
- **Within-file duplicates collapse client-side** under the same rule, before anything is sent.
  Two rows sharing a normalized address in one batch would otherwise race on a single contact.
- **The convergence property:** because the write is upsert-by-address and fill-empty-only,
  re-running the same file is safe and converges. Retry-the-whole-thing IS the recovery
  strategy. This is what buys the right to skip all job machinery.

### Consent
- **One attestation at import, recorded PER CONTACT** (not once per batch) as
  `consentSource: "imported-attested"`.
- `"imported-attested"` is deliberately DISTINCT from `"asserted-by-user"`. One attestation over
  500 rows is weaker evidence than consent recorded for one person; the schema must not flatten
  that difference.
- **The attestation sentence is part of the spec**, versioned in `@pikar/core` beside the parser:
  > I have a lawful basis to contact these people — they are business contacts of mine, and I am
  > not importing a purchased or scraped list.
- `consentWording` stores that sentence **byte-for-byte**, never a paraphrase or a key into a
  message table. It is the evidence. Changing the wording later applies only to future imports.
- The free-text "where did these come from?" is stored as `consentContext`.
- **The checkbox starts unticked and Confirm is DISABLED until ticked.** A pre-ticked box would
  make the stored wording a false statement about what the user did. This keeps the schema's
  "NOTHING is defaulted to consented" honest.
- `consentWording` and `consentContext` are content plane — **neither may reach `audit.payload`**
  (CLAUDE.md §4). Import audit rows carry counts and contact ids only.

### Data model
- Three new optional fields on `contacts`: `company`, `phone`, `title`. **Three, and no more.**
  No custom fields, no tags, no arbitrary key-value.
- Two union extensions: `origin` gains `"imported"`; `consentSource` gains `"imported-attested"`.

### Decisions added 2026-08-10 AFTER research (19.1-RESEARCH.md), all LOCKED

These close gaps the original spec missed. The research file cites the lines.

- **An import must NEVER downgrade consent.** If a contact already carries
  `consentSource: "asserted-by-user"` — consent recorded for one person the user spoke to — the
  batch attestation must NOT replace it. Same principle as fill-empty-only: bulk data may never
  destroy stronger hand-recorded data. *(Gap in the original spec; caught by research.)*
- **`upsertContactRow`'s current rule is "don't erase", NOT "fill empty only"** — today a
  non-blank name DOES overwrite, and only the blank case is tested. Fill-empty-only is therefore
  a real behaviour change and must arrive as a flag (e.g. `fillEmptyOnly`) on the shared helper
  so hand-add behaviour and playbook invariant 13 are preserved unchanged.
- **The preview counts are defined over the four mappable fields ONLY** (`name`, `company`,
  `phone`, `title`). Writing a consent row must NOT make a contact count as `enriched` — if it
  did, `unchanged` would be structurally always 0 and the preview would lie.
- **A rejected row reports its PHYSICAL FILE LINE**, not the record index. The two diverge when a
  quoted field contains a newline, and the file line is what the user sees opening the CSV.
- **Batch sizes stay 100 rows / 500 addresses, but the JUSTIFICATION CHANGES.** They sit at ~1% of
  every hard Convex limit (arg 16 MiB, array 8192, docs scanned 32,000, docs written 16,000, 1s
  user code) — every limit would permit the whole file in one call. Do NOT justify them by citing
  a limit they never approach. The real reasons are **retry blast radius, progress granularity,
  and the OCC window**. (Convex publishes no OCC retry semantics; research flagged this as its one
  LOW-confidence area — do not assert what cannot be measured.)
- **The Pipeline consent chip MUST render the source.** `PipelineView.tsx:279-283` currently shows
  `Consented {date}` and never reads `row.consent.source`, so the imported-vs-asserted distinction
  the schema preserves is invisible at the only surface anyone looks at — and `tsc` will never
  flag it. This is the 19-06 `media`/`llm.ts` failure recurring. Owner decision 2026-08-10: render
  it.
- **`pipelineTiles` MUST report its bound.** It currently takes exactly `SCAN_LIMIT` (1,000) and
  returns no bound, so a max-size import into a non-empty book silently under-counts all four
  ALWAYS-KNOWN tiles — breaking playbook invariant 3 while the e2e integer assertion keeps passing
  on a wrong integer. Follow the pattern its siblings already use: scan `SCAN_LIMIT + 1` and
  surface `partial: "row-cap"` so the tile can read `1000+` rather than a confidently wrong
  number. Owner decision 2026-08-10: fix the honesty bug at its root; do NOT merely raise the cap.

### Two Stop-hook gates that WILL block the commit if missed
- `packages/core/src/contactImport.ts` is a new code file under `packages/` covered by no
  playbook. It must be added to `contacts-crm.md`'s entry in `docs/playbooks/watch.json`.
- `cockpit.md` watches `apps/web/e2e/`, so touching `pipeline-uat.spec.ts` needs a **second**
  playbook bump.

### Backend surface
- Two new public functions, both in `packages/backend/convex/contacts.ts`. **No second store** —
  PIPE-01 forbids it and 19-02's structural scan enforces it.
- `matchExisting({ emails })` — `tenantQuery`, bounded by input, chunked client-side at 500
  addresses per call. Returns per address: exists?, and which of `name`/`company`/`phone`/`title`
  are empty.
- `importContacts({ rows, attestation })` — `tenantMutation`, batched at **100 rows per call**
  (starting value, tunable against Convex transaction limits; the correctness argument does not
  depend on the number). Returns `{ created, enriched, unchanged, rejected }`.
- The mutation **re-validates rather than trusting** client-normalized input — same write-boundary
  discipline `parseCrmOperations` follows.
- Both functions join the `COVERED` pin in `contacts.test.ts` **with real asA/asB isolation
  tests**. 19-13 established that bumping the pin without adding the test defeats its purpose.

### Interface
- Lives on `/dashboard/pipeline` beside the existing "Add your first contact". **No new route.**
- File picker follows the vault's `Dropzone.tsx` pattern rather than introducing a second one.
- Three steps in one panel: choose file → preview (mapping + counts + rejected rows by line
  number and reason) → attest and confirm.
- Tokens from `globals.css`, **no component library**, refusals inline in grey `--ink-soft` —
  Phase 19's rule that a refusal is information, not failure. Never amber.

### Who can import
- **Human only.** The agent cannot initiate an import: the attestation is a legal statement a
  person makes, the agent cannot see the file, and keeping it out avoids a new registration
  surface on the 14-site checklist.

### Testing
- `packages/core`: the CSV cases that break naive parsers, header alias mapping, within-file dedup.
- `contacts.test.ts`: asA/asB isolation on both new functions; fill-empty-only asserted **on
  stored state, not on the reply**; consent wording stored byte-for-byte; the §4 scan extended to
  prove no wording reaches `audit.payload`.
- `pipeline-uat.spec.ts`: **a real browser** uploading a real fixture CSV, seeing the preview
  counts, confirming, and finding the rows in the table. **This row is a REQUIREMENT, not a
  nicety** — Phase 19 shipped a capability that unit tests, SMOKE tests and a paid eval gate all
  certified while it was completely unreachable from the product.
- Every new guard mutation-proven: broken, observed red, reverted, failing text recorded.

</decisions>

<specifics>
## Specific Ideas

**The riskiest part of the build is NOT the parser — it is the two schema union extensions.**
`origin` and `consentSource` are discriminated unions consumed at multiple sites. 19-06
established that widening such a union produces a compile error at MOST call sites but falls
through silently where a consumer is typed loosely (`PlanRow` never declares `kind`, so `media`
shipped a whole phase without reaching its branch in `llm.ts`). Both extensions need a deliberate
site walk against the registration checklist in `docs/playbooks/cockpit.md`, not faith in `tsc`.

**Environmental facts the planner should know:**
- `packages/backend/convex/cash.ts` may still carry 2 `TS2739` errors from the finance lane,
  making `pnpm typecheck` 8/10. `convex dev` typechecks before pushing, so a stale build can be
  served silently; `:3210` was last running with `--typecheck=disable`. Verify before believing
  a deploy took effect.
- The backend vitest fork crashes (`vaultDigest.test.ts` failures + `Cannot set properties of
  undefined (setting 'exit')`) when aggregate/retrier components are registered for tests that
  do not write audit rows. Use `harness({ audit: true })` / `withFanoutOnly()` / per-test
  `convexTest` registration.
- `pnpm --filter <pkg> test -- <name>` does NOT filter anywhere in this repo.
- Line endings are not stable (`core.autocrlf=true` + `* text=auto`): use SINGLE-LINE Edit anchors.
- Parallel lanes share this working tree. Pathspec commits only; never `git add -A`; check
  `.git/MERGE_HEAD` before committing.

</specifics>

<deferred>
## Deferred Ideas

Explicitly OUT OF SCOPE for this phase (from the spec's "Out of scope" section):

- vCard, XLSX, or any format other than CSV
- Custom fields, tags, or arbitrary key-value on a contact
- Agent-initiated import
- Imports above 1,000 rows
- Any change to whether consent gates sending — it currently does NOT, and changing that affects
  hand-added contacts too, so it is a separate decision
- Undo / rollback of an import
- The other three contact-acquisition subsystems (document extraction, search-then-import,
  third-party CRM migration). Subsystem 4 will use REST, not MCP — ADR-011 records the Pikar-Ai
  MCP as structurally unreachable from a Convex action.

</deferred>
