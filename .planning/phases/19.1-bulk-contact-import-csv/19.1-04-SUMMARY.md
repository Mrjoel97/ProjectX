# Phase 19.1 Plan 04: matchExisting and importContacts Summary

The two functions the import panel talks to — the read that lets the preview state
`N new · M enriched · K unchanged` **before** anything is written, and the write that keeps that
promise — both landed in the existing `convex/contacts.ts`, tenant-scoped, isolation-tested, pinned,
and proven to leave the audit log untouched.

## What Was Built

**`matchExisting` (tenantQuery)** — one entry per REQUESTED address, in request order, each
`{ email, exists, empty }` where `empty` names which of `name`/`company`/`phone`/`title` are unset.
One `contactByEmail` indexed read each (the `suppressedAmong` shape, no new index). An unknown
address answers `exists: false` with all four fields listed, so a new row has something to count.
Addresses are normalized **here** — `"  Known@X.com  "` finds the stored `known@x.com` — rather than
trusted from the client, or the preview and the write could disagree about who a row is. An array
longer than `IMPORT_MATCH_CHUNK` is refused with `IMPORT_MATCH_TOO_MANY` **before any read**: an
implicit slice would silently under-report and the preview would promise a write it never makes.

**`importContacts` (tenantMutation)** — the write boundary, in the plan's order:

| Step | Rule |
| --- | --- |
| 1 | `rows.length > IMPORT_BATCH_ROWS` → `IMPORT_BATCH_TOO_LARGE`. The client batches; the boundary enforces |
| 2 | `attestation.wording.trim() === ""` → `CONSENT_WORDING_REQUIRED`, before the loop |
| 3 | per row: `normalizeAddress` then `isValidEmail`, **re-run, not trusted** — a failure is a `rejected` entry, never a throw |
| 4 | `upsertContactRow(..., origin: "imported", fillEmptyOnly: true, consent: { source: "imported-attested", wording, context })` |
| 5 | classify from the reply: `created` → created, `filled > 0` → enriched, else unchanged |
| 6 | **no audit row at all** |

**The batch numbers are documented by their REAL reason.** The comment on the `IMPORT_BATCH_ROWS`
guard says explicitly that 100 rows is ~1% of every hard Convex limit and that every one of them
would permit the whole 1,000-row file in a single call — so it must never be justified as one. The
reasons written down are retry blast radius, progress granularity and a shorter OCC window.

**No import audit row, deliberately**, and the doc comment records why: `assertConsent` writes none
either; this module's entire audit surface is still one event (`contact.unsuppressed`) under a
key-set EQUALITY test; CLAUDE.md §4 governs what a payload may *carry*, not that every write must
have one. The strongest available guarantee that an address or the attestation wording never becomes
a payload is that the path emits no payload at all — and the test asserts that as a **row count**,
not a substring.

## The 14 New Tests

**Isolation (BETA-05 block, both new functions):** B asks about A's address and is told it does not
exist, with A over the same DB told the truth (non-vacuity); B's import of an address A already
holds creates a **separate B-scoped row** while A's typed name, `user-entered` origin, empty company
and absent consent are all read back untouched.

**`matchExisting`:** request-order + per-field emptiness + server-side normalization in one test;
the over-long refusal, with the non-vacuity floor that exactly `IMPORT_MATCH_CHUNK` addresses still
answers (so the refusal is the length rule, not a broken function).

**`importContacts`, all eight behaviours, every one reading `contactRows(h)` back:**

| # | Behaviour | The trap it closes |
| --- | --- | --- |
| 1 | new batch → `created: 2`, both rows `origin: "imported"` | the happy path, asserted on stored state |
| 2 | empty company filled → `enriched: 1`, typed name survives, origin stays `user-entered` | fill-empty-only through the real mutation |
| 3 | all four fields set → `unchanged: 1` **and the consent DID land** | counting consent would make `unchanged` always 0 |
| 4 | `not-an-address` and `"   "` rejected, the two good rows still land | one bad row must not discard the batch |
| 5 | `IMPORT_BATCH_ROWS + 1` refused and writes NOTHING; exactly `IMPORT_BATCH_ROWS` writes | non-vacuity on the batch cap |
| 6 | blank attestation refused and writes NOTHING | refused before the loop, not half-way through |
| 7 | every row carries `imported-attested` + the wording compared to `IMPORT_ATTESTATION` | a re-typed literal would pass after the constant drifted |
| 8 | an `asserted-by-user` record survives an import that still fills its empty company | the non-downgrade floor, through the public path |

**The three scans and the tie:** the §4 audit test now runs a real `importContacts` with a
distinctive address, name, `IMPORT_ATTESTATION` and context, asserts the row count did not move, and
only then checks the serialized table for all four strings; the PIPE-01 structural scan now covers
`core/src/contactImport.ts` (guarded by the existing `src.length > 500` floor against a bad glob
key); and a 30-row import pages through `listContacts` at `limit: 10` with every returned id reached
exactly once.

## Mutation Evidence

All four guards broken, observed red with the exact text, and reverted.

| # | Guard | Mutation applied | Observed failure |
| --- | --- | --- | --- |
| 1 | `IMPORT_MATCH_TOO_MANY` | `if (false) throw …` | `AssertionError: promise resolved "[ { email: 'p0@x.com', …(2) }, …(500) ]" instead of rejecting` |
| 2 | server-side `isValidEmail` | `if (false) {` on the rejection branch | `CONTACT_EMAIL_REQUIRED` — the WHOLE batch throws |
| 3 | `fillEmptyOnly: true` | changed to `false` | **2 red:** `expected 'S. CHEN (OLD CRM)' to be 'Sarah Chen' // Object.is equality` and `expected { created: +0, enriched: 1, …(2) } to deeply equal { created: +0, enriched: +0, …(2) }` |
| 4 | the `COVERED` pin | removed `"importContacts"` | `expected [ 'assertConsent', …(11) ] to deeply equal [ 'assertConsent', …(10) ]` |

Mutation 2's red is the informative one: without the re-validation the blank-address row reaches
`upsertContactRow`'s `CONTACT_EMAIL_REQUIRED` floor and **takes the entire transaction down** — which
is precisely the "one bad row discards the 99 good ones" blast radius the rejection branch exists to
prevent. The `not-an-address` row would meanwhile have become a contact that exists and can never be
emailed.

## Deviations from Plan

### 1. [Rule 1 — Bug in the plan's premise] The createdAt tie had to be forced with a sentinel

- **Found during:** Task 3
- **Issue:** The plan asserts that "rows inserted in one transaction share a `Date.now()`". Written
  as specified, the test measured **19 distinct timestamps across 30 inserts** — `convex-test`'s
  clock advances mid-transaction where the real backend freezes it. The many-way tie the test exists
  to cover was not being produced, and a `createdAt`-only paging bug would have slipped through.
- **Fix:** After the import, every row's `createdAt` is patched to a sentinel (`1_234`) and the
  one-distinct-value precondition is **asserted** before the paging loop runs — the same
  sentinel-not-a-clock discipline 19.1-03 used for `updatedAt`. The comment records the measurement
  so the next reader does not "fix" it back.
- **Files modified:** `packages/backend/convex/contacts.test.ts`
- **Commit:** `c887528`

### 2. [Plan-internal] One commit, not per-task commits

Task 3 of the plan specifies the single pathspec commit and gives its exact message. Followed the
plan over the executor's per-task default — the same call 19.1-02 and 19.1-03 made, and for the same
reason: tasks 1 and 2 are one change and its pin, and task 3's mutation-proofs revert code that would
otherwise have been committed broken-then-fixed.

### 3. [Beyond the plan's list] Two extra assertions

The plan listed eight `importContacts` behaviours; a ninth test pins that an import does **not**
downgrade a per-person `asserted-by-user` consent record while still filling its empty company. That
floor was proven at the helper in 19.1-03 but never through the public mutation, which is the path a
user actually reaches. The batch-cap and attestation tests also assert `contactRows(h)` is **empty**
after the refusal — "refused" and "refused without writing half a batch" are different facts.

### 4. [Noted] The plan's line numbers were stale

The plan cites the §4 scan at ~533, the PIPE-01 scan at ~1057 and `COVERED` at ~1119. After 19.1-03
they are at 731, 1273 and 1315. Located by anchor text, not line number.

## What This Does NOT Do

No UI. No e2e. No agent path — an import stays human-only, because the attestation is a legal
statement a person makes. `pipelineTiles` still takes exactly `SCAN_LIMIT` and reports no bound, so
a max-size import into a non-empty book will under-count all four tiles until 19.1-05 lands; the
playbook's ceilings section now says so in as many words, including that **nothing caps a tenant's
contact count** — the 1,000-row ceiling is per import, not per book.
