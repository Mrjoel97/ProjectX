# Phase 19.1 Plan 03: fill-empty-only as a Flag on the ONE Writer Summary

`upsertContactRow` learned import semantics — fill an empty field, never overwrite a typed one, and
fold a consent record into the same insert/patch — as a **default-off flag** on the one shared
writer, with the two existing callers proven unmoved rather than asserted unmoved.

## What Was Built

**`upsertContactRow`, one function, three new tricks.** It now takes `company`, `phone`, `title`, a
`fillEmptyOnly` flag and an optional `consent` block, and returns `{ id, created, filled }` instead
of a bare id. Playbook invariant 13 — ONE implementation of the write rule, shared by both actors —
is intact: there is no second writer, and all three call sites still route here.

| Rule | Where it lives |
| --- | --- |
| `CONTACT_EMAIL_REQUIRED` trust boundary | unchanged, still first |
| blank-after-trim is ABSENT | one `fields` loop, both paths |
| a value may fill an empty field, never overwrite | `if (fillEmptyOnly && existing[key]) continue` |
| `origin` set once, on creation | no `origin` in the patch |
| consent written ONLY onto a row with none | `existing.consentAt === undefined ? consentBlock : undefined` |
| nothing to say ⇒ no write at all | `if (filled === 0 && !addConsent) return` |
| `filled` counts the four mappable fields only | `Object.keys(patch).length`, consent excluded |

**The default is the old rule, deliberately.** `fillEmptyOnly: false` keeps "a blank name must not
ERASE a name on record" — where a **non-blank one still overwrites**. `upsertContact` (hand-add) and
`applyCrmOperations` (the Approve-gated applier) pass no flag, so both behave exactly as they did
before this phase. Their only diff is `.id` on the destructured return; `upsertContact`'s public
signature is still `Promise<Id<"contacts">>`.

**The consent fold is zero extra writes.** The four consent columns go into the SAME insert/patch as
the fields. `assertConsent` is deliberately NOT called per row from an import: it re-reads the row
just written and hardcodes `"asserted-by-user"`, which is the wrong source and a downgrade in
disguise. The `?? "asserted-by-user"` read fallback was not copied into any of this.

**One guard added beyond the plan's list:** a blank `consent.wording` throws
`CONSENT_WORDING_REQUIRED`, the same refusal `assertConsent` already makes. 19.1-04's
`importContacts` takes the attestation from the wire, so a timestamped empty consent record was
reachable; the floor belongs at the shared writer, not in each caller (CLAUDE.md §8: fix once, where
all callers route through).

## The Eight New Tests, and Why Each Reads the Row Back

`upsertContactRow` is not a Convex function, so the block drives it in-transaction through
`h.t.run((ctx) => upsertContactRow(ctx, h.tenantA, ...))`. **Every assertion reads `contactRows(h)`
back.** A reply can agree with itself while the write is wrong — which is exactly how "don't erase"
passed as "fill empty only" for a whole phase.

| # | Test | The trap it closes |
| --- | --- | --- |
| 1 | a NAME on record survives a different incoming name | the headline rule, asserted on stored state |
| 2 | an EMPTY company is filled, and counted (`filled: 2` for company+phone, not the refused name) | proves the flag FILLS, not merely refuses |
| 3 | **hand-add (no flag) STILL overwrites** | NON-VACUITY. Without it, deleting the flag entirely leaves 1 and 2 green |
| 4 | `origin` stays `user-entered` under an `imported` touch | provenance is not restated by a file |
| 5 | consent lands with `imported-attested` + wording **byte-for-byte vs `IMPORT_ATTESTATION`** | a re-typed copy would pass even if the constant drifted |
| 6 | `asserted-by-user` keeps its source, wording AND timestamp | the non-downgrade floor |
| 7 | a call that changes nothing does not move `updatedAt` | an `unchanged` row must be untouched in the DB, not just on the wire |
| 8 | a consent-only write returns `filled: 0` — and the consent DID land | `unchanged` would otherwise be structurally always 0 |

Tests 6 and 7 patch a **sentinel** (`consentAt: 1_234`, `updatedAt: 1_234`) before the call rather
than reading a clock. Two writes inside one millisecond would make an "unchanged timestamp"
assertion pass while the field was being rewritten — a vacuity this file has been bitten by before.

## Deviations from Plan

### 1. [Rule 2 — Missing critical functionality] A `CONSENT_WORDING_REQUIRED` floor on the helper

- **Found during:** Task 1
- **Issue:** The plan specified the consent fold but no validation on `consent.wording`.
  `assertConsent` refuses a blank wording ("a consent record with no wording is a defaulted consent
  wearing a timestamp"); the new path had no equivalent, and 19.1-04 takes the attestation from the
  client.
- **Fix:** One line at the top of the helper, reusing the existing error name.
- **Files modified:** `packages/backend/convex/contacts.ts`
- **Commit:** `f281fce`

### 2. [Plan-internal] One commit, not per-task commits

Task 3 of the plan specifies the single pathspec commit and gives its exact message; tasks 1 and 2
say "do not commit yet". Followed the plan over the executor's per-task default — the same call
19.1-02 made, and for the same reason: the helper and the tests that pin it are one change.

### 3. [Noted, not a deviation] `filled` has no equality short-circuit

The plan's rule is literal: a patch entry exists when the incoming value is non-blank AND
(`fillEmptyOnly === false` OR the stored field is empty). Under `fillEmptyOnly` that means a patch
entry can only exist where the field WAS empty, so `filled` is exact everywhere it is read. Under
the hand-add default, re-saving an identical name counts as `filled: 1` — nobody reads `filled`
there, and adding a comparison would be code with no reader.

### 4. [Recorded] The no-op skip DOES change one hand-add behaviour

Before: a nameless re-save patched `{ updatedAt }` and moved the timestamp. After: it writes
nothing. This is required by the plan ("skip the `db.patch` entirely when nothing would change") and
no existing test asserted the old behaviour — the 19-06 `upsertContact` identity test asserts the
row id, name, origin and email, never `updatedAt`. Named here because "hand-add is byte-identical"
is otherwise slightly too strong a claim: hand-add's *field* semantics are byte-identical, and a
no-op re-save is now cheaper and quieter.
