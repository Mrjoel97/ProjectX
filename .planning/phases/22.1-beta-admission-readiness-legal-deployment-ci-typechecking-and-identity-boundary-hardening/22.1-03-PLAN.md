<objective>
Turn "typecheck and lint are green" from a fact a human re-establishes by hand into a fact the
repository enforces.

Purpose: SC3 is the last open criterion in Phase 22.1. Today the repo has exactly one workflow
(`skillopt.yml`) and it runs the skill optimizer — nothing in CI has ever typechecked, linted,
tested or built this codebase. Every "typecheck at the exact 150 baseline" line in the last
fifteen plan summaries is a human holding a number in their head and comparing it by eye. That
works for one contributor on one machine and fails the moment it matters.

The 150 is also not what it looks like. It is not 150 defects: **100 of them are a single dead
`@ts-expect-error` repeated across 37 test files**, and the other 50 are ordinary
`noUncheckedIndexedAccess` fallout in 13 test files. Production code is already at zero. The
baseline is an artifact of nobody ever having been forced to drive it to zero — not a hard
problem deferred for a good reason.

Output: a workspace that typechecks, lints, tests and builds clean, and a GitHub Actions workflow
that proves it on every push and pull request.

**PRECONDITION — this plan is `autonomous: false` for a reason.** Task 4 reformats ~200 files and
Tasks 2-3 touch ~40 test files. It must run against a QUIESCENT tree: no lane holding uncommitted
work. `git status --porcelain` must show nothing but this plan's own output. Running it while a
sibling lane has in-flight edits does not produce a merge conflict — it silently reformats and
commits another lane's half-written code. See <risks>.
</objective>

<risks>
- **The quiescence precondition is the whole risk surface, and it is not a merge conflict.** Task 4
  rewrites ~200 files. Git will not flag a lane's uncommitted work — the formatter simply rewrites it
  in place, and `git commit -- <paths>` then either commits a sibling's half-written code or misses
  the reformat. `PARALLELIZATION.md:12-17` (lanes share ONE working tree since 2026-07-27) is why
  this is an owner call taken BETWEEN lanes. Task 0 is the enforcement, and 151-vs-150 is the tell.
- **A shared-`tsconfig` change re-types every lane at once.** Unlike the union/mirror freeze items at
  `PARALLELIZATION.md:99-104`, a compiler-config change conflicts with nothing textually and
  re-types everything semantically: a lane green before the commit can go red without editing a
  line, and the failure surfaces in the OTHER lane's build. This plan therefore changes NO
  `compilerOptions` — the tsconfigs are read, cited, and left alone. If a fix in Task 3 appears to
  need a compiler-option change, stop and escalate; it does not belong in this plan.
- **The playbook Stop hook will fire wide on Tasks 2-4.** `check-playbooks.mjs` matches by path
  prefix, so a format-only sweep across `convex/*.test.ts` trips `cockpit.md`, `vault.md`,
  `voice.md`, `skill-registry.md`, `authorization.md`, `onboarding.md`, `audit-dead-letter.md` and
  `business-evaluation.md` at once — subsystems this plan does not semantically touch. Per CLAUDE.md
  §9 the correct resolution for a genuinely content-neutral change is to bump ONLY the
  `Last verified` line. Do it in the same commit as the sweep, and do not otherwise edit a playbook
  this plan has no business editing.
- **CI needs `CONVEX_DEPLOY_KEY` and it is not optional.** Without codegen the typecheck step is
  vacuous — `_generated/` is absent, every Convex import fails, and it fails LOUDLY, which is the
  good case. The bad case is somebody "fixing" that by excluding `convex/**` from typecheck. The
  playbook must say so.
- **`convex codegen` contacts the deployment** ("Downloading current deployment state... Uploading
  functions to Convex"), so every CI run touches the owner's real deployment. The CLI documents this
  as not modifying deployed code, and `skillopt.yml` already runs `convex run` against it, so this is
  precedent rather than a new exposure — but it means CI is not hermetic and a deployment outage
  reads as a CI failure. Note it in the playbook so that failure mode is diagnosable.
- **Do not add `--error-on-warnings` to `biome ci`.** 134 `noNonNullAssertion` warnings would turn
  the gate red on day one and the pressure would be to weaken the rule set rather than fix anything.
  Warnings stay visible and non-blocking; errors block.
</risks>
