# Phase 22.1 Plan 05: Tenant Deletion Summary

**Registry-driven, bounded, self-scoped tenant erasure with honest per-provider revocation — proven
against the live production deployment, including the audit-immutability invariant**

## Accomplishments

- Erasure walks `deletableTables()` and can only ever name `tenant_owned` / `tenant_credential`
  tables, so `audit` is unreachable **by construction**, not by a remembered `if`.
- Revoke-then-delete ordering: connected accounts are disconnected before any row is removed, and a
  revocation failure does not abort erasure — a user asking for deletion must not be blocked by a
  provider outage.
- Per-provider outcomes are reported individually and truthfully.
- The `/dashboard/settings` erasure surface arms only on the exact phrase `DELETE MY DATA` — the same
  literal the server takes as `v.literal` — so a mis-typed confirmation is refused before an
  irreversible call. There is deliberately no single-click path.
- The privacy policy and the card both name the Microsoft limitation and hand the user Microsoft's
  own consent surface, rather than implying parity with Google.

## The Production Defect This Gate Caught

The first two live attempts (`9a23216e3f16ebe8`, `431036cd611b309a`) both failed:

```
Uncaught Error: OWNER_REQUIRED at handler (../convex/tenantDelete.ts:48:19)
databaseWriteBytes: 0
```

`authorizeTenantDeletion` required `user.owner === true` alongside the self check. `users.owner` is
the **deployment-owner grant** `bootstrapOwner` mints for GOVN-01 — it gates the optimizer, skill
activation and `/ops`. Erasure is GDPR Art. 17. One predicate was answering two different questions,
and the control the privacy policy advertises to every user existed only for the operator.

**Why 6/6 green hid it:** every fixture in `tenantDelete.test.ts` seeded `owner: true`, including the
empty-tenant case, which made the clause literally unreachable by the suite. The regression guard
added in `1ca7c6f` omits `owner` entirely (`v.optional` — exactly what a real signup produces) and
asserts the bystander tenant survives. It went RED with `OWNER_REQUIRED` first, reproducing
production, then green.

The removed clause bought **no** isolation: `deleteTenantDataPage` already scopes the identity row by
`String(user._id) === args.tenantId` and every other table by the `by_tenant` index.

## Deviations from Plan

**1. Task 3's owner-gated design contradicted Task 3's own test procedure**
- Task 1 specified owner-gated erasure; Task 3 required proving it on a *disposable tenant*. A
  disposable tenant is by definition not the deployment owner, so both could not hold.
- Resolved in favour of the requirement: erasure is tenant-self.

**2. GOVN-03's Microsoft clause is met by disclosure, not implementation**
- The requirement text says disconnection "WITH revocation at the provider (not merely a local token
  delete)". Microsoft offers no per-application revocation an app can call for its own grant.
  `DELETE /oauth2PermissionGrants/{id}` needs admin-consent permissions; `revokeSignInSessions`
  revokes every application's tokens.
- Both are deliberately refused. The policy and the card now state the limit and link
  `account.microsoft.com/privacy/app-access` / `myapps.microsoft.com`. **Plan 25-06 Task 2 still owns
  any change to that posture.**

## Not Verified

- **The post-erasure re-export was not run.** The plan asked for an empty-but-well-formed export
  after deletion; the `users` row is deleted last, so that account can no longer authenticate to
  call the export. Completion is instead evidenced by the action returning `error: null` with a
  null final cursor, having walked every table in `deletableTables()`.
