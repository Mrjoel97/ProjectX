# Phase 50 research — Tenant merchant commerce

## Research question and authority

How should Phase 50 implement the tenant's catalogue-to-fulfilment commerce lifecycle while preserving the Phase 48/49 publication contract, tenant isolation, approval/audit rules, and the hard separation from Pikar's own subscription billing? This is implementation research, not a provider selection, merchant approval, legal determination, or claim of readiness.

Governing inputs: `CLAUDE.md` §§1–4, 8–10; `.planning/ROADMAP.md` Phase 50; `.planning/REQUIREMENTS.md` SHOP-02..05; `.planning/audits/2026-09-10-merged-audit-codebase-review.md` §§9.3, 9.4, 9.10, 9.12–9.13; Phase 48/49 RESEARCH, VALIDATION, VERIFICATION, and `docs/releases/phase-49-wave7-wave8-reentry.md`. Phase 49 is repository/local qualified on its recorded digest; its private storefront is presentation only. Wave 1 golden/founder evidence, Wave 7 external conditions, and Wave 8 exact-production acceptance remain open in `STATE.md`. Do not reinterpret Phase 49's local proof as merchant proof.

## Executive finding

Build a new, typed **tenant-commerce** domain in pure TypeScript and thin Convex adapters. Catalogue/inventory, cart quote, order, payment facts, notification, refund, and fulfilment each need their own closed state transitions, durable idempotency, and refs-only audit. A merchant adapter can be selected only after the owner decides the provider/account model and its sandbox contract. Keep the public storefront dark until code-owned readiness proves the complete declared local lifecycle; keep production merchant traffic dark until separate Wave 7 evidence. The Phase 49 static catalogue items (`id`, description, display price/availability text) are **not** inventory or prices. Render public purchasable entries from server-owned live catalogue/quote projections, pin exact product/price/inventory version into an order, and never trust presentation text or client totals for a charge.

Payment collection should redirect to a provider-hosted checkout page, with Pikar holding no card fields. This narrows the intended integration surface; it does not itself determine PCI SAQ eligibility. PCI SSC says SAQ A eligibility depends on all payment-page elements and all other criteria, which require a separate assessment. [PCI SSC FAQ](https://www.pcisecuritystandards.org/faqs/if-a-merchant-s-e-commerce-implementation-meets-the-criteria-that-all-elements-of-payment-pages-originate-from-a-pci-dss-compliant-service-provider-is-the-merchant-eligible-to-complete-saq-a-or-saq-a-ep/). Stripe's hosted Checkout and connected-account API are examples of a possible adapter, not a provider or account-model decision. [Stripe Checkout quickstarts](https://docs.stripe.com/payments/checkout/quickstarts), [connected-account API](https://docs.stripe.com/api/connected-accounts?api-version=2025-06-30.basil).

## Standard Stack

- Use existing `@pikar/contracts` closed public/merchant types and a new pure `@pikar/core` commerce module for state transitions, inventory reservation, quote/tax/shipping policy inputs, integer-minor money arithmetic, and deterministic idempotency keys. Reuse `@pikar/revenue` money utilities only if their pure contract fits; do **not** route merchant writes through the read-only connector package or business-finance projection.
- Use `packages/backend/convex/lib/functions.ts` `tenantQuery`/`tenantMutation`/`tenantAction` for authenticated admin commands; narrowly scoped internal functions for public host-derived operations and provider callbacks. Add `by_tenant` leading indexes and classification in `packages/core/src/tenantData.ts` for every new tenant table.
- Reuse Phase 48 `webProjects`, `webRuntime`, `webForms`, `http.ts` host/path resolution, immutable artifact/version/CAS approval, and exact rollback. Extend the renderer/contract deliberately where a storefront dynamic island or server-rendered commerce projection is required; retain stored published shell bytes and a versioned commerce contract. Do not create another publisher.
- Reuse Phase 19 `contacts.ts` contact, consent and suppression helpers for marketing permissions. Transactional order email/fulfilment communication needs its own purpose and delivery state; buyer checkout does not silently grant marketing consent. Reuse existing approved outbound-plan machinery for merchant-initiated messages where approval is required.
- Use Vitest, `convex-test`, existing two-tenant isolation drift tests, and Playwright through a fresh disposable local stack. Provider sandbox calls are **not** an automatic verification prerequisite in this research; fixtures can test the adapter contract and callback parser. Exact test-mode provider evidence is a distinct gate after a provider/account model is chosen.

## Architecture Patterns

### 1. Provider-agnostic merchant core, one explicitly selected adapter

Create a closed `MerchantProvider`/environment identity and a narrow interface: `createHostedCheckout(merchantAccountRef, exactQuote, idempotencyKey)`, `fetchCheckout/payment/refund` for reconciliation, `requestRefund` only after authorization, and `verifyAndParseWebhook(rawBody, headers)` returning normalized signed facts. The core may know provider refs, event ids and outcomes, but never provider SDK objects, secrets, card data or arbitrary URLs. Only the adapter owns provider endpoint/version/signature details. Add no speculative multi-provider registry or generic fetch proxy. The plan must choose **one** adapter after owner/provider facts; until then, complete pure flows and a fake adapter, but keep public checkout unavailable.

Possible account models are (a) business-owned direct merchant credentials, stored encrypted with scoped revocation/rotation, and (b) a platform connection with a per-tenant connected account, explicit seller-of-record/funds/fees/liability controls. The Stripe connected-account header illustrates per-request account scoping; it says nothing about the owner's chosen legal/fee model. [Stripe connected-account API](https://docs.stripe.com/api/connected-accounts?api-version=2025-06-30.basil). Choose the model before writing adapter secrets, onboarding, webhook routing or refund semantics. Never point tenant commerce at `BILLING_STRIPE_SECRET_KEY` or `STRIPE_APP_SECRET_KEY`.

### 2. Deterministic catalogue, inventory and quote authority

Use tenant-scoped product/variant/SKU identity, explicit active/draft/retired status, price in safe integer minor units and one currency per quote. Define inventory mode per sellable variant: `finite` with reservation/available counts or an explicitly approved `untracked` posture. Default to **no oversell** for finite stock. Atomically reserve on checkout intent (or choose commit-on-payment with a documented oversell policy), give reservation a bounded expiry, and release only once after expiry/failure/cancellation. Reconcile late payment after reservation expiry as `paid_needs_review`, not a fabricated shipped order. Use revision/CAS on product/stock writes; audit before/after refs and counts, not descriptions or buyer data. The server recalculates quote, taxes/shipping policy and total immediately before provider session creation; reject stale cart price/stock and unsupported geography/currency. No LLM arithmetic, client amount, free-text tax rate or implied FX.

Cart is a bounded, opaque public token or server-held cart with short retention and tenant/project binding. It holds item IDs/quantities, not financial authority. Checkout creates an immutable order snapshot (items, unit amounts, tax/shipping amounts, currency, policy identities, shipping/customer content under appropriate retention) and one durable checkout attempt. The same client retry resolves to the same order/attempt; a changed cart requires a new key/order. Provider idempotency complements, but does not replace, the local durable guard: Stripe documents that keys may be removed after at least 24 hours. [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests).

### 3. Separate order, payment, notification and fulfilment state

Represent provider event facts as an append/dedupe stream keyed by `(provider, merchantAccountRef, eventId)` with verified signature and tenant/account correlation. Apply a pure transition reducer under a Convex mutation. Record unknown/unmatched/out-of-order events as held reconciliation work; never invent tenant identity from callback metadata. Project payment into `unpaid`, `pending`, `paid`, `failed`, `partially_refunded`, `refunded`, `disputed`/`unknown` as supported by chosen provider. Keep order `placed`, `cancel_requested`, `cancelled`, `paid`, `fulfilment_pending`, `fulfilled`, `exception` independent; a cancellation request after payment is not a voided charge. Refunds are separate authorized commands and signed facts, with amount/currency caps and partial totals.

Do not fulfil or send “paid” confirmation from the checkout success redirect. Stripe explicitly recommends server-side events because redirect-only fulfilment is unreliable; asynchronous payment success/failure requires distinct outcomes. [Stripe Checkout fulfilment guidance](https://docs.stripe.com/payments/existing-customers?platform=web&ui=stripe-hosted). Reconciliation must poll/fetch by exact tenant-account/order/provider ref after missing callback or timeout, with capped retry, backoff, terminal/manual-review state and no cross-account lookup. A success callback, fetch result, duplicate delivery and retry must converge to one payment effect, one stock decision, one notification and one fulfilment hand-off.

Outbound matrix for planning: buyer checkout redirect is buyer-initiated; transaction receipt/required order notice follows a verified order event and an explicit tenant policy; promotional messages use Phase 19 consent/suppression plus the normal approval gate; merchant-issued refunds need owner/authorized tenant role and exact amount/order approval; fulfilment hand-off to a third party needs the tenant's explicit destination/configuration and approval policy. Every outbound action records authority ref, attempt id, idempotency key, cost/settlement if Pikar pays for delivery, and refs-only audit. The merchant gross/payment/refund ledger belongs to the business and must not be written into Pikar's subscription `billingEvents` or Pikar cost `spendEvents` as revenue.

### 4. Public/storefront activation as a conjunction, not a switch

Prefer a pure `storefrontReadiness`/`commerceContractReady` result with closed refusal reasons and immutable code-owned contract version. Publishing a public storefront requires valid approved exact document/version/hash, mapped active products, declared inventory posture, price/tax/shipping/refund policy, test-mode merchant adapter eligibility, verified platform host and complete order/reconciliation/notification/fulfilment paths. At Wave 5, test mode must be unmistakably marked and never appear as a live sellable store. Production enablement additionally requires Wave 7 account/domain/policy evidence and an exact configuration pin. Keep Phase 49's defense in depth: discovery, controls, publication mutation, runtime resolver and HTTP all test the same readiness and fail closed independently. Revoke/unpublish prevents new checkout but does not erase already committed orders or suppress reconciliation/refund duties. Rollback restores exact stored page bytes and the pinned commerce mapping/policy identity; current stock is read at checkout, never rewound by a page rollback.

## Don't Hand-Roll

- No card form, PAN/CVV handling, card vault, card tokenization or fake PCI certification. Use a provider-hosted checkout boundary and separately assess actual merchant eligibility.
- No custom payment signature scheme or optimistic success from URL query parameters. Use the selected provider's documented raw-body verification and signed event/fetch reconciliation.
- No second publication renderer, contact store, suppression store, Pikar billing ledger, or write-capable extension of the Phase 28 read-only connectors.
- No FX, tax-law determination, shipping carrier calculation or refund policy inferred by the model. Require explicit merchant/provider/tax/shipping inputs and closed refusal when missing.
- No universal payment abstraction before a real provider/account model is chosen; keep the core outcome contract small and adapter-specific concerns local.

## Common pitfalls and countermeasures

1. **Static catalogue mistaken for stock or price.** Reject publisher text as quote input; map stable presentation IDs to tenant product IDs and prove foreign/retired mappings fail.
2. **Checkout session succeeds but order write fails.** Persist order/attempt and reservation before external POST; send a deterministic idempotency key; reconcile unknown response by exact provider account/id rather than blindly issuing another session.
3. **Webhook duplicate, out of order, wrong account or forged.** Verify raw-body signature before parse/write; account-scoped event dedupe; correlate to pre-existing order; hold orphan facts; monotonic transition rules; test every permutation.
4. **Stock reservation expires before delayed payment.** Preserve late-paid exception and manual recovery/refund choice; never silently oversell or erase the financial fact.
5. **Refund or cancellation described as paid reversal before provider confirmation.** Separate requested/pending/succeeded/failed states and make inventory/notification effects conditional on terminal facts.
6. **Email consent conflated with receipt delivery.** Record purpose, recipient and policy; never let checkout toggle promotional consent implicitly; keep suppressions and unsubscribe behavior intact.
7. **Pikar and tenant Stripe credentials/events mixed.** Distinct route, secret namespace, table prefix, package/import boundary and static guard; two-tenant and two-account tests must fail on swapped IDs.
8. **Erasure deletes accounting evidence or leaves PII.** Decide retention/classification with owner/legal input, use existing export/erasure maps, keep audit refs-only and require no raw buyer fields in events/logs/metrics.
9. **External tax, shipping, domain or merchant assumptions hidden in a green test.** Fixture values prove branch behavior only; the UI names `configuration_required`/`provider_unavailable` and Wave 7 evidence stays open.
