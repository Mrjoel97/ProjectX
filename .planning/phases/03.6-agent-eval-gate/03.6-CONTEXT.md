# Phase 3.6: Agent Eval Gate - Context

**Gathered:** 2026-07-15
**Status:** Ready for planning
**Source:** PRD Express Path (`.planning/design/agent-eval-gate.md` — the phase's designated design record; its frontmatter decisions are treated as locked)

<domain>
## Phase Boundary

Agent behavior changes stop being blind. Four deliverables, nothing more:

1. **Golden-set harness** — ~15–25 scripted cockpit conversations as fixtures, run on demand via `pnpm eval:golden` against the live model through the real `runCockpitAgent` loop on a dev deployment, asserting on resulting plan/tool state (never reply text), with a hard per-run cost cap and zero possibility of a real send or mailbox read.
2. **Activation gate** — `activateSkill` refuses a never-before-active (candidate) version of a gated skill without a recorded passing eval run; rollback is structurally exempt.
3. **Ops read-side (EVAL-02)** — one new ops-page section showing production eval signals from existing telemetry/audit data, no new write paths.
4. **Housekeeping** — archive the dead `executive-agent.classifier` skill row; close the agent-runtime playbook's "no live-model eval gate" gap in the same phase.

This is the continuous-evaluation ring between the mock-model CI tests (Phase 3.2.1) and SkillOpt (Phase 8), which plugs into this harness instead of building its own.

</domain>

<decisions>
## Implementation Decisions

### Golden set & assertions (EVAL-01)
- Eval asserts on **plan/tool state, never reply text** (text is subjective; state is the contract): recipients (count/addresses), mode, subject present, plan status reached (`proposed`), attachment presence/absence.
- Standing invariants asserted every case: zero `requests` rows created, zero sends, refs-only audit.
- Delivery impossible by construction (no Approve click ever happens) — asserted anyway.
- Coverage: happy paths, mid-conversation edits ("remove #2", "make it formal"), bounce/re-ask paths (invalid address), attachment ops, and at least one prompt-injection probe (a user turn asking the agent to send without approval must end with nothing sent and no `proposePlan` acceptance of an invalid row).

### Runner
- Invocation: `pnpm eval:golden [--skill <name>@<version>]`.
- Reuses the existing smoke-harness conventions (Windows-safe runner like `packages/backend/scripts/run-smoke-*.mjs`).
- Seeds a throwaway tenant, runs cases sequentially, prints per-case pass/fail + total cost, exits non-zero on any failure.
- Hard cost cap per run — abort if cumulative spend exceeds it (expected well under $1 on the default model).
- Zero mailbox access: no Gmail token in the eval tenant — `resolveContacts` cases assert the graceful-degradation path instead.

### The gate
- Lives on `activateSkill` — activation is the behavior-deploy mechanism, so it is the choke point.
- Refuses to activate a **candidate** row (never-before-active) for a gated skill unless a passing eval run is recorded.
- Evidence written to the skill row's existing `evidence` field: runner id, cases passed, cost, model, timestamp — **refs/counts only**, never raw content.
- **Structural rollback exemption:** a target row whose status is `archived` or `rolled_back` was active before and activates without evidence — rollback during an incident must never be blocked by a broken eval harness.
- Gated skills v1: `cockpit-agent`, `document-drafter` (the two that drive tool behavior). `email-drafter`/`executive-router` join only when golden cases cover them (deferred).

### Production read-side (EVAL-02)
- One new ops-page section reading data that already exists: approve/edit/reject rates and `regenerateCount` (telemetry), `llm.fallback` count (audit), DLQ rate (`deadLetters` + aggregate), cost per delivered plan (telemetry).
- No new writes, no new tables — a query + a card.
- Falling approve-rate after an activation IS the production eval; rollback is already one click.

### Housekeeping
- Archive the dead `executive-agent.classifier` skill row (live routing uses `executive-router`; the two disagree on route-enum spelling).
- Update the agent-runtime playbook (close the "no live-model eval gate" gap) in the same phase; register any new watched paths in `watch.json`.

### Claude's Discretion
Design-record §6 open questions — recommendations below are the defaults; the planner may firm them up with research:
- **Fixture grammar:** JSON fixture per case recommended over extending the `SMOKE::agent::` sentinel grammar (sentinels are for offline determinism; evals want real reasoning).
- **Execution locus:** developer machine against a dev deployment (zero infra); CI job deferred (needs `OPENAI_API_KEY` as a CI secret).
- **Flake policy:** one automatic re-run of a failed case before red, with both attempts recorded in evidence.
- Exact cost-cap value, fixture file layout, per-case report format, ops-card layout/time-window.

</decisions>

<specifics>
## Specific Ideas

- Suggested plan breakdown from the design record (not binding): 3 plans / 2 waves — (01) golden-set harness: fixture format + eval tenant seeding + runner + first ~15 cases (Wave 1); (02) activateSkill gate: candidate-vs-rollback + evidence recording + gate tests + archive dead classifier (Wave 2); (03) ops-page eval-signals section + `eval:golden` script wiring + playbook/watch.json updates + human-verify checkpoint (Wave 2).
- Phase 8 impact: the golden set seeds SkillOpt's held-out validation pool; `evidence` on skill rows is the before/after record IMPR-03 wants; ops-page signals are its scoring inputs.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `packages/backend/convex/skills.ts` — `activateSkill` internalMutation already exists; skill rows are insert-only with only `status` and `evidence` patchable. The gate extends this function; the `evidence` field already exists.
- `packages/backend/scripts/run-smoke-*.mjs` + `smokeRun.mjs` — the Windows-safe runner convention (and seeding helpers) the eval runner mirrors.
- `apps/web/app/(app)/ops` — the existing ops page the eval-signals section lands on.
- Existing telemetry/audit/deadLetters tables + aggregates — the EVAL-02 read sources; no new write paths.
- `runCockpitAgent` + `buildCockpitTools` — the real loop the eval drives; `clientContext` threading (Phase 3.5) shows how trusted client params ride in.

### Established Patterns
- Refs/hashes/ids/counts only in audit/evidence payloads (CLAUDE.md §4).
- Skills load from the registry, never hardcoded (§5); `seedSkills` publish-on-change ships v-next rows.
- Domain logic in `packages/*`; convex functions are thin adapters (§1); tenant-scoped wrappers, no raw query/mutation imports (§2).
- Playbook updated in the same commit/phase as watched-path changes (§9).

### Integration Points
- `activateSkill` in skills.ts — gate insertion point.
- `package.json` scripts — `eval:golden` wiring.
- Agent-runtime playbook + `docs/playbooks/watch.json` — same-phase close of the eval-gate gap.

</code_context>

<deferred>
## Deferred Ideas

- Automated/scheduled eval runs (cron) — on-demand is enough until Phase 8 gives it a caller.
- LLM-as-judge / text-quality scoring — state assertions only in v1; subjective quality stays human until SkillOpt brings scored trajectories.
- Per-tenant eval variants, A/B activation, canary traffic — post-beta at the earliest.
- Gating `email-drafter`/`executive-router` — join the gated list when golden cases cover their surfaces.
- CI execution of eval runs (`OPENAI_API_KEY` as CI secret) — deferred.

</deferred>
