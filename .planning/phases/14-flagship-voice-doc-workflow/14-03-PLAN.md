<objective>
Make a voice session doc-scoped, and give it a server-side retrieval action that answers a
mid-call "what does it say about X?" from THIS document alone.

Purpose: this is Success Criterion 1's "drill in" — the half that makes the conversation grounded
rather than "discuss whatever fit in the pre-load cap". It is also where Success Criterion 4 and
BETA-05 are earned: the retrieval path is the one new place report content moves, so the refs-only
audit split and the tenant-namespace isolation are proven here.
Output: `voice.startSession({..., docRef})` and `voiceDoc.searchDocument({sessionId, query})`.

  args: { sessionId: v.id("voiceSessions"), query: v.string() },

Flow:
1. Read the session through an internal tenant-scoped query (`internal.voice.getSession` already
   exists) and take `docRef` from the ROW. **The model supplies only the free-text `query`; the
   document id is never model-supplied and never a client arg.** Identity comes from the browser's
   authenticated Convex client via `tenantAction`. Bail to `{passages: [], found: false}` when the
   session is missing, not this tenant's, or carries no `docRef`.
2. `const { docIds, chunks } = await ctx.runAction(internal.vaultGround.vaultGroundHydrated,
   { tenantId: ctx.tenantId, query })` — reuse the engine; do NOT read `vaultDocuments.text`
   directly (a book-sized `text` blob against the 16 MiB read cap, and it would re-implement chunk
   selection — RESEARCH Pattern 3 / rung 2).
3. Keep only the hits whose `docId === docRef`, slice to `RETRIEVAL_MAX_PASSAGES` and trim the
   total to `RETRIEVAL_CHAR_CAP` (realtime input tokens are re-billed every turn).
4. **Open Question 2, resolve in-task:** check whether `@convex-dev/rag` 0.7.5 supports a per-entry
   filter (Context7 for `@convex-dev/rag`, or read `node_modules/@convex-dev/rag`'s types for a
   `filter`/`filterValues` option on `search`). `vaultGround.ts` is frozen to Lane C, so a filter
   cannot be threaded through `vaultGroundHydrated` without a contract change — therefore: if a
   filter exists, record that finding in `docs/playbooks/voice.md` as the named upgrade path and
   still ship the post-hoc filter this phase; if it does not, ship the post-hoc filter and say so.
   Either way mark the honest ceiling with a `ponytail:` comment naming BOTH upgrade paths
   (raise `limit` and filter · a doc-scoped rag filter) and the failure mode it accepts: a top-K
   search across the whole tenant vault can miss this doc's best passage when another document
   dominates — the same shape as the Phase-12 defect fixed in `f5c279e`.
5. Audit exactly once, LAST, via `internal.audit.log`:
   `{ tenantId: ctx.tenantId, correlationId: String(sessionId), eventType: "voicedoc.searched",
      actor: "user", payload: { sessionId, queryHash: await contentHash(query),
      resultCount: passages.length } }`.
   The §4 split, stated in a comment above it: CONTENT PLANE = passages → the model over the data
   channel. LOG PLANE = refs + counts only. Do NOT write an `agentSteps` row (the table has no text
   field by construction and the closed-allow-list scan in `llmRedaction.test.ts` fails if that
   changes), and do NOT write to `telemetry` or `deadLetters`.
6. Never throw out of the handler: catch and return `{passages: [], found: false}`. A tool call the
   browser cannot answer leaves the model waiting and the user hearing silence for the rest of the
   turn inside a capped 15 minutes (Pitfall 5).
