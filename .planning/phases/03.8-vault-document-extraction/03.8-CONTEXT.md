# Phase 3.8: Vault Document Extraction - Context

**Gathered:** 2026-07-18
**Status:** Ready for planning
**Structure requirement:** ≥3 plans runnable as PARALLEL SESSIONS with disjoint file ownership (user mandate — tight schedule)

<domain>
## Phase Boundary

A document uploaded to the knowledge vault in a non-text format (**PDF, DOCX, XLSX, PPTX,
images**) has its text extracted and flows through the existing `vaultIngestText({docId, text})`
late-text seam into embedding/graph ingestion — closing the gap where such uploads sit at
`pending_extraction` forever and never become searchable.

Notes on the roadmap's format list:
- **CSV is already searchable** — `vault.ts` treats TXT/MD/CSV as text-on-upload; not in scope.
- **Videos are OUT** (deferred — see Deferred Ideas). They stay storage-only per Phase 5.

Everything downstream of the seam (embed → graph-extract → retrieval) already exists and is
untouched: this phase produces text and calls the seam, nothing more.
</domain>

<decisions>
## Implementation Decisions

### Parallel-session structure (LOCKED — the user's core requirement)
- **Wave 0 (short, sequential, lands on `main` FIRST):** one contract plan that creates the
  shared extractor interface/dispatcher stub, any new status value, the skill-registry row(s),
  file stubs establishing lane ownership, and playbook + `watch.json` entries. No lane starts
  before Wave 0 merges.
- **Then 3 lanes, truly parallel, carved by format family / file ownership:**
  - **Lane 1 — PDF + images (hosted path):** the Convex extraction action riding Phase 4's
    `extractVisual` pattern (multimodal file call, skill-loaded prompt, SMOKE:: short-circuit),
    governance wiring, PDF text-layer-first logic, tests. Owns `convex/vaultExtract*.ts`.
  - **Lane 2 — Office parsers (pure TS):** DOCX/XLSX/PPTX deterministic flatten in a pure-TS
    package behind the Wave-0 interface. Zero Convex edits. Owns the new/extended `packages/*`
    parser module only.
  - **Lane 3 — Sweep + UI + E2E:** backlog sweep + retry mutation (owns `convex/vaultSweep*.ts`),
    vault route status/retry/truncation UI (owns the `apps/web/.../vault` edits), offline E2E +
    any eval fixtures.
- **Integration = existing `.planning/PARALLELIZATION.md` discipline verbatim:** one git worktree
  + branch per lane, each with its OWN `npx convex dev` deployment; shared singletons
  (`schema.ts`, `skills.ts`, `STATE.md`/`ROADMAP.md`) append-only in own regions; merge `main`
  into lanes daily; merge a finished lane to `main` and announce.
- **Testing: offline-first** (`convex-test` + `SMOKE::` paths); live smokes/human-verify only in
  the lane's own deployment. No shared live backend.

### Format coverage (v1)
- **All five formats ship this phase:** PDF, images, DOCX, XLSX, PPTX.
- **Office fidelity = deterministic flatten, no model call:** DOCX paragraphs, XLSX cell values
  sheet-by-sheet, PPTX slide text. Charts/images inside Office files ignored in v1.
- **PDF path = text-layer first, hosted OCR fallback:** parse the text layer when present
  (free); only no/garbage-text-layer PDFs (scans) go to the hosted multimodal model.
- **Images = hosted model** (OCR/visual description), same engine as Phase 4 intake.

### Trigger & lifecycle
- **Auto-extract on upload:** `vaultUpload` of a binary schedules extraction immediately
  (guardrails/budget/kill-switch already gate every model call).
- **Backlog: one-time governed auto-sweep on ship** — walk existing `pending_extraction` rows
  oldest-first, rate-limited and budget-gated. The vault heals itself.
- **Retry: durable-workflow per-step retry absorbs transient failures; persistent failure marks
  the item `failed` with a manual Retry affordance.** No infinite spend loops.
- **Per-doc cost bound:** cap the input sent to the model (pages/bytes const, mirroring the
  `BODY_TRUNCATE_CHARS` / `PLAN_ATTACHMENT_CAP_BYTES` precedent) on top of the existing
  `VAULT_FILE_CAP_BYTES` upload cap. Oversize docs get truncated extraction, marked honestly.

### Failure & progress UX
- **Status pills extend the existing lifecycle:** `pending_extraction → extracting → processing
  → ready` (one new visible state; embed/graph half keeps `processing`). Reactive, no refresh.
- **Failed = badge + Retry on BOTH the item card and the detail panel**, with the failure
  reason in the panel.
- **Truncation is visible:** detail panel notes "extracted first N pages/characters — large
  file truncated" when the per-doc cap bit.
- **No notifications beyond the reactive pill flip.** (Calm, executive voice — BRAND §1.)

### Claude's Discretion
- Whether Office parsers need a small pinned dependency vs hand-rolled zip/XML walk (ponytail
  ladder: prefer stdlib/existing; a boring, tiny, well-pinned parser dep beats a fragile
  hand-rolled one — decide in research).
- Whether the hosted path reuses the existing `attachment-extractor` skill or seeds a
  `vault-extractor` skill row (registry rules apply either way, §5).
- Exact per-doc cap values and truncation units (pages vs chars).
- Sweep mechanics (scheduled action vs cron vs one-shot migration-style sweep) and batch size.
- Exact dispatcher shape and where the pure-TS parser package lives (new `packages/*` vs
  extending an existing vault package — NOT `@pikar/extraction`, which is intake-owned).

</decisions>

<specifics>
## Specific Ideas

- **The seam is sacred:** extraction NEVER writes embeddings or graph rows directly — it
  produces text and calls `vaultIngestText({docId, text})`; the identical Phase-5 pipeline does
  the rest. (Phase 5 CONTEXT's "extraction-boundary contract", now being fulfilled.)
- **Redact-then-extract order (§4):** hosted extraction output goes through `pii.scanText`
  fail-closed BEFORE any audit write — mirror `intake.ts`'s exact ordering. Audit payloads are
  refs/counts only.
- **Phase 4's `extractVisual` is the template** for the hosted path: skill-loaded prompt,
  `SMOKE::extract::` short-circuit, bounded file call, spend recorded.
- **Lane interference is prevented by ownership, not politeness:** Wave 0 creates the file
  stubs so each lane edits only files it owns; shared singletons are append-only regions.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`vault.ts` `vaultIngestText` (docId seam)** — already patches text onto a
  `pending_extraction` row, flips it to `processing`, and starts the ingest workflow. The
  integration point exists and is tested; this phase just needs callers.
- **`intake.ts` `extractVisual`** — the Phase-4 hosted extraction engine: multimodal `file`
  content part, `attachment-extractor` skill, `SMOKE::extract::` offline path, guardrails +
  spend recording. Copy the shape for Lane 1.
- **`vaultIngest.ts` durable workflow** — per-step retry pattern for the extraction workflow.
- **`@convex-dev/rate-limiter` + `guardrails.preCall`/`recordSpend`** — sweep + per-call
  governance, already wired for vault ingest.
- **`.planning/PARALLELIZATION.md`** — the proven multi-session worktree contract; reuse
  verbatim with new lane definitions.
- **`vaultSmoke.ts`, `vaultRedaction.test.ts`** — existing vault test seams to extend.

### Established Patterns
- Domain logic in pure-TS `packages/*`, Convex as thin adapter (§1) — Office parsers are pure
  package code; Convex only dispatches and orchestrates.
- Skill-registry prompts (§5); append-only `seedSkills` + 5-file mirror if a new skill is seeded.
- Redact-then-write (§4); refs-only audit payloads.
- Optional-field/additive schema growth; statuses as strings — check whether `extracting` needs
  a schema union change or is already an open string.
- Playbook + `watch.json` (§9): vault playbook exists — new files must land under watched
  prefixes (Wave 0 registers anything new).

### Integration Points
- `convex/vault.ts` `vaultUpload` — the ONLY existing-file edit expected outside lane-owned new
  files: schedule extraction after a binary stores (small, Wave-0-or-Lane-1 owned; decide in
  planning and record ownership explicitly).
- `apps/web/.../dashboard/vault` route + components — Lane 3 owns all edits there.
- `schema.ts` / `skills.ts` — append-only regions via Wave 0.
</code_context>
