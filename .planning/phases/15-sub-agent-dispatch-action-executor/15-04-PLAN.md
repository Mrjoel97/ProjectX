**RESOLVED (RESEARCH Open Question 1): `actOnGap` STAYS a `tenantMutation`. It does NOT become a
`tenantAction`.** It stages `status: "collecting"` and schedules the dispatch action.

Why, so a later reader does not "simplify" it back: a Convex mutation cannot call an action, and the
specialist takes 10-30s. Converting to a `tenantAction` would let it await the specialist and stage
one finished row — but it makes the plan-row transitions non-transactional (the recycle is
`resetPlan` + `patchPlan`, which must not be interruptible) and it leaves the card blank for 30s
anyway. Scheduling keeps the mutation atomic AND closes the Approve race **structurally**:
`executePlan:509` already refuses anything but `"proposed"`, so a `collecting` row is not approvable
by construction — no new guard, no new status literal, no UI change. The CKPT-05 trace step is the
progress indicator, which is what CONTEXT locked.

     with `body: buildMemo(row, gap)` and `status: "proposed"`. Nothing is scheduled. This is the
     honest terminal when there is no specialist to run, and it keeps the fail-closed guarantee at
     the ENTRY point as well as inside the dispatcher.
   - `ok` → `patchPlan` with `status: "collecting"`, `kind: "memo"`, `recipients: []`, the same
     `subject`, and `body: ""` (or a one-line placeholder). Then schedule.
2. Mint `const rootRequestId = crypto.randomUUID();` **here**, at the dispatch entry point.
