1. `docs/decisions/007-sub-agent-capability-is-code-owned.md` — new ADR (next free number is 007;
   confirm with `ls docs/decisions/` and take the next one if 007 is taken). ADRs are immutable —
   never edited after acceptance, only superseded. Follow the format of the existing ADRs.

   **Title:** Sub-agent capability is code-owned; the sub-agent prompt is registry-owned.
   **Context:** CLAUDE.md §5 requires agent prompts to be versioned `skills` rows, not source. A
   specialist is a `(skill body, tool-set)` pair, so the question is whether the tool-set is also a
   registry row.
   **Decision:** the BODY is a `skills` row (§5, loaded via `getActiveSkill`, eval-gated). The
   TOOL-SET is a `readonly` constant in `packages/core/src/specialists.ts`.
   **Consequences / why:** a tool-set is a CAPABILITY GRANT, not a prompt. §5 governs prompts so
   that prompt changes flow through the registry with rollback; it does not ask for capabilities to
   be DB-writable, and making them DB-writable would let a row edit widen what a sub-agent can do —
   a privilege escalation with no eval gate in front of it. Keeping the registry a pure data record
   in `@pikar/core` is also the seam Phase 15.1 plugs its tier filter into (PARALLELIZATION forbids
   Lane A from reading the tier in `llm.ts`), which makes 15.1 a filter layer rather than a router
   edit. Cost: adding a specialist is a code change, not a DB write — accepted.
