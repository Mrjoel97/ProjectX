## Summary

This phase is **mostly subtraction plus one new table**, with one genuinely open design question and
one genuinely open architecture question. The good news dominates: every dependency it needs is
already installed and already has an in-repo precedent, and Phase 15 deliberately left the exact
seam 15.1 plugs into (`SPECIALISTS` / `resolveSpecialist` in `packages/core/src/specialists.ts`, and
the shared governed loop `runAgentLoop` in `convex/llm.ts:1642`, which already has a second consumer
in `runSpecialistTurn`). **Do not fork the router** — `PARALLELIZATION.md` is explicit, and the code
supports a filter/ordering layer cleanly.

The two hard parts are not the schema:

1. **The conversational loop is not cleanly reusable as written.** `runAgentLoop` takes a mandatory
   `planId: Id<"plans">` and builds its tool record exclusively from `buildCockpitTools(ctx,
   tenantId, planId, …)` — a 20-tool, email-plan-centric factory. Onboarding has no plan row and
   needs one tiny tool (`recordSlot`). And the CKPT-05 activity trace writes into `agentSteps.tool`,
   a **closed `v.union` of literal tool names** (schema.ts:399-437) — a new onboarding tool literal
   is a schema change, and if you forget it the insert throws and *the SDK swallows it*, so the
   trace silently vanishes in prod while every test passes. This is design-doc Risk §13 ("cockpit
   loop reuse may not be clean") confirmed as real. Q1 lays out three options and a recommendation.

2. **"Which specialists are offered" is currently a set of one.** `runEvaluation` computes
   `const ranked = leverageRank([prescription])` — `diagnose()` returns exactly ONE `Prescription`,
   `leverageRank` sorts a single-element array, and `gaps` therefore holds at most one entry with
   one `route`. There is no candidate list for a tier filter to filter. Delivering SC#5's "which
   specialists are offered" honestly requires *creating* a multi-candidate surface, or reframing
   the tier's effect on dispatch as **framing/prompt-context** rather than set membership. Q2.

Everything else is well-trodden: `@convex-dev/migrations@0.3.5` is installed, registered in
`convex.config.ts`, and has two in-repo precedents (`migrations.ts:backfillRequestDefaults`,
`vaultSweep.ts:sweepPendingExtraction`); the skill registry has a documented 5-file mirror pattern
for adding an `onboarding-agent` skill and per-preset style directives; the tenant-scoped wrappers
(`tenantQuery`/`tenantMutation`/`tenantAction`, `convex/lib/functions.ts:41/47/57`) are the only
function surface allowed (CLAUDE.md §2).

**Primary recommendation:** Land the phase as five separable chunks in this order — (1) the pure
`deriveTier` + facts type in `@pikar/core` with the full boundary test table; (2) the new
`tenantProfiles` table + `@convex-dev/migrations` legacy backfill; (3) the *subtraction* (drop the
tier from `vProfile`, delete the persona pills, fix the two `personaConfirmed: true` hardcodes,
repoint `evaluations.ts` off the markdown string-match); (4) the conversational onboarding on
whatever Q1 resolves to; (5) the tier→treatment layer per Q2. Chunks 1–3 are low-risk, fully
offline-testable, and close four of six success criteria on their own. Chunks 4–5 carry all the
risk. **Plan them as separate waves so a Q1/Q2 surprise cannot stall SC#1/2/4/6.**

### Pattern 1 — `deriveTier` is a pure function in `@pikar/core` and the ONLY writer

**What:** A total function `deriveTier(facts: TierFacts) -> Exclude<Tier,"enterprise">`, colocated
with the existing `PERSONAS` / `isPersona` / `decideConfirm` in
`packages/core/src/businessProfile.ts`. Convex-free (CLAUDE.md §1), unit-tested with no harness.

**Why here:** `businessProfile.ts:1-7` already declares itself the home of the governance-critical
pure rules ("*SC#1: a persona is ALWAYS confirmed…*", "*Enterprise is not an emittable persona*").
`deriveTier` is the third rule of the same kind. Putting it anywhere else splits the invariant.

**Critical constraint — do not regress Phase 11's `decideConfirm`.** `decideConfirm` returns a
literal `{ needsConfirm: true }` with *deliberately no branch that auto-commits*
(`businessProfile.ts:48-55`). The design doc's "closing beat" (§6) is the same rule wearing a
conversational skin: `deriveTier` produces a *candidate*, the closing confirmation is what commits
it. **`deriveTier` returning a value is not a commit.** Keep `decideConfirm` and keep its test.

**Enterprise stays unrepresentable in the derived path.** `PERSONAS` is `["solopreneur","startup",
"sme"]` — enterprise is deliberately not in the union (`businessProfile.ts:9-12`). `deriveTier`'s
return type must be that union, not a widened `Tier`. If a widened `Tier` type is introduced for the
table (to hold an admin-granted `enterprise`), it must be a *separate, wider* type — the derivation
function's signature is what makes D6 a type error rather than a code review.

### Pattern 2 — The subtraction reaches the validator, not just the page

Today, three layers all accept a caller-supplied tier:

| Layer | Location | Today | After |
|-------|----------|-------|-------|
| Convex arg validator | `onboarding.ts:53-62` — `vProfile` includes `persona: v.union(v.literal("solopreneur"), v.literal("startup"), v.literal("sme"))` | accepts it | **field removed from `vProfile` entirely** — an extra arg key is a Convex *validation error*, so removal is self-enforcing |
| Domain validator | `businessProfile.ts:81-83` — `if (!isPersona(profile.persona)) errors.push(...)` | only checks set membership | either drops the check with `persona` leaving `BusinessProfile`, or the check moves to the facts |
| UI | `profile/page.tsx:143-160` (three pills, `onClick={() => set("persona", p)}`) and `onboarding/page.tsx:412-430` (the confirm/change pills) | freely settable | pills deleted; tier rendered read-only with a reason string |

**The load-bearing detail:** `persona` is a required field of the `BusinessProfile` type
(`businessProfile.ts:29`) and `serializeProfile` writes `` `- **Persona:** ${profile.persona}` ``
(`:105`), which `deserializeProfile` reads back at `:147` and `:169-173`, and which
`evaluations.ts:263` *detects the profile doc by* (`if (text.includes("- **Persona:**"))`). Removing
`persona` from `vProfile` while leaving it on the type means `commitProfile` can no longer construct
a valid `BusinessProfile` to serialize. **The mutation must fetch the derived tier from the table and
splice it in** — which is exactly design §4.2's "markdown as projection". Plan this as one atomic
change across `vProfile` → `commitProfile`/`updateProfile` → `writeProfileDoc`, not three.

### Pattern 3 — New table + `@convex-dev/migrations` backfill (widen-migrate-narrow, degenerate case)

There is **no existing table to widen**. The migration story is therefore the easy variant of
widen-migrate-narrow: the new table is created empty (all fields optional where a legacy row cannot
supply them), the backfill writes one row per onboarded tenant, and the "narrow" step is deliberately
*not taken* — `headcount`/`paidStaff`/etc. stay optional forever, because §10 forbids forced
re-onboarding and a `legacy` row has empty facts by definition.

Sketch (field names from design §4.1; validate against the planner's own naming pass):

```ts
// convex/schema.ts — a NEW table (there is no `tenants` table to add a column to)
tenantProfiles: defineTable({
  tenantId: v.string(),
  // ── Tier facts (all optional: a `legacy` row has none, and §10 forbids forced re-onboarding)
  headcount: v.optional(v.number()),
  paidStaff: v.optional(v.number()),
  revenueStage: v.optional(v.string()),      // consider a closed union once the slot copy is fixed
  funding: v.optional(v.string()),
  yearsOperating: v.optional(v.number()),
  // ── Derived (SC#2)
  tier: v.union(
    v.literal("solopreneur"), v.literal("startup"), v.literal("sme"),
    v.literal("enterprise"),                  // representable in the TABLE, never from deriveTier (D6)
  ),
  tierSource: v.union(
    v.literal("derived"), v.literal("confirmed"), v.literal("admin"), v.literal("legacy"),
  ),
  derivedAt: v.number(),
  // ── Agent identity (D4)
  agentName: v.optional(v.string()),          // sanitized: length cap, strip control chars + newlines
  behaviorPreset: v.optional(v.string()),     // closed union once the preset set is chosen (§7)
}).index("by_tenant", ["tenantId"]),          // the SC#2 "queryable, indexed" requirement
```

**Backfill** (SC#6) — the `vaultSweep.ts` precedent verbatim in shape:

**Read the whole `convex-migration-helper` SKILL.md before planning this** — it is at
`packages/backend/.claude/skills/convex-migration-helper/SKILL.md` and its "Prefer New Fields Over
Changing Types" / "Don't Delete Data" rules apply to the `persona` field's demotion.

### Pattern 4 — Scripted spine, conversational skin: the slot machine is code, not prompt

The design doc's non-negotiable (§6): "*It simply cannot **complete** with a required slot empty.*"
That guarantee **must not live in the prompt.** A prompt that says "always ask about headcount" is a
model-temperature guarantee — the exact defect (1a) this phase exists to fix. The guarantee lives in
a pure predicate:

```ts
// @pikar/core — the completion gate, testable with zero harness
export const REQUIRED_SLOTS = ["headcount", "paidStaff", "oneLineDescription"] as const;
export function missingSlots(state: Partial<TierFacts> & { oneLineDescription?: string }): string[];
export const canComplete = (s): boolean => missingSlots(s).length === 0;
```

…and the *mutation* that finalizes onboarding refuses when `missingSlots` is non-empty. The agent
gets `missingSlots(state)` injected into its per-turn context so it knows what to ask next; the
refusal is what makes it true. This is the `resolveSpecialist` fail-closed pattern
(`specialists.ts:81-87`) applied to onboarding, and it is the only version of SC#3 that survives a
model that decides to be chatty.

### Pattern 5 — New skills follow the 5-file mirror; the preset set is a registry set

Adding a skill in this repo is a **5-file mirror** (PARALLELIZATION.md singleton rule #2, and the 20
existing skills confirm it):

1. `packages/contracts/skills/<name>.md` — the human-authored body
2. `packages/contracts/src/skills/<camelName>.ts` — the derived TS body constant
3. `packages/contracts/src/skill.ts` — the `export const X_SKILL = "<name>" as const;` name constant
   (see `:32-86` for the 18 existing constants)
4. `convex/skills.ts` — the `seedSkills` row
5. a drift row (asserted by `packages/contracts/src/skills/skillBodies.test.ts`)

For 15.1 that means: **1 mirror for `onboarding-agent`, plus 1 mirror per behavior preset.** With 3
presets that is 4 × 5 = 20 file touches. This is the dominant *mechanical* cost of the phase and the
planner should size a task around it explicitly.

**Recommended preset set (discretionary, §7 is open):** three, differentiated on *how much the agent
pushes* rather than on tone adjectives — e.g. `direct` (blunt, names the constraint first),
`coaching` (asks before prescribing), `concise` (minimum words, no framing prose). Three keeps the
mirror count at 15 files and each preset genuinely distinguishable. **Do not exceed four** (§7 says
"3–4").

Also note `GATED_SKILLS` (`skill.ts:100`) — a skill-body edit rides the Phase-3.6 `EVAL_GATE`. The
planner must decide whether `onboarding-agent` and the style directives are gated skills, and if so,
budget for the eval gate. `business-profile` is currently **ungated** ("*Loads the UNGATED
business-profile skill*", `onboarding.ts:146`), which is the nearest precedent.

**Also required by §1a:** `packages/contracts/skills/business-profile.md:31` currently instructs the
model that "*a best-fit guess is correct behavior*". That line is the written form of defect 1a and
must be revised in the same phase, through the same mirror.

### Pattern 6 — Tier as a filter/ordering layer over `SPECIALISTS`, never a router fork

`PARALLELIZATION.md`: "*Lane A must not build tier awareness into the router*… *[Phase 15.1] plugs
into the dispatch seam afterwards as a filter layer*." `STATE.md:425`: "*`SPECIALISTS` stays a pure
readonly data record in `@pikar/core`, which is also the seam 15.1 plugs its tier filter into.*"

The shape that honors both: a **new pure function in `packages/core/src/specialists.ts`** — signature
along the lines of `specialistsForTier(tier): readonly SpecialistRoute[]` or
`orderByTier(tier, routes): readonly SpecialistRoute[]` — consumed by `applyActOnGap`
(`evaluations.ts:642`) *before* it calls `resolveSpecialist(gap.route)` at `:685`. `resolveSpecialist`
itself does not change; `dispatch.ts` does not change; `llm.ts` does not change.

**But see Open Question Q2** — with today's one-prescription-per-evaluation shape there is nothing
for the filter to filter, and a filter that can only *reject* the single available route turns SC#5
into "solopreneurs get no specialist", which is worse than tier-agnostic.

### Anti-Patterns to Avoid

- **Forking the router.** Explicitly forbidden by PARALLELIZATION.md. The seam exists; use it.
- **Reading the tier in `llm.ts`.** Same source. Tier reaches the loop as *prompt context assembled
  by the caller*, not as a read inside the loop.
- **A UI-only removal of the persona pills.** Design §9, amended: "*A UI-only fix hides the button
  and leaves the control.*"
- **Making `tierSource` a second tier concept.** Design §4.1 forbids it by name.
- **Correcting an audit row.** CLAUDE.md §3 — the audit module exposes only inserts. SC#4 is fixed by
  never writing the false field again, not by a repair pass over history.
- **Putting the slot-completeness guarantee in the prompt.** See Pattern 4.
- **Adding a second `"use node"` Convex module.** `onboarding.ts:7-11` documents the TS
  circular-inference cliff this re-triggers. If the conversational onboarding needs the gateway, it
  goes through `llm.ts` (already node) or through V8 `generateObject` like `extractProfile` does.
- **Omitting explicit `Promise<…>` return types on new Convex handlers.** `evaluations.ts:106-113`
  measures the cost: a missing annotation degraded the whole generated API to `any` and produced
  ~90 unrelated `apps/web` errors.

## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---------|-------------|-------------|-----|
| Backfilling existing tenants (SC#6) | A one-shot `internalMutation` that `.collect()`s `vaultDocuments` | `@convex-dev/migrations` (`migrations.define` + `migrations.runner`) | Installed, registered, two precedents. Resumable + batched; a `.collect()` over all vault docs is an unbounded read that will fail at scale mid-way with no cursor. `vaultSweep.ts:4-5` states the rule. |
| Enumerating onboarded tenants | A full-table scan filtered on `kind` | The existing `vaultDocuments.by_kind` index (`schema.ts:619`) | It was added for exactly this: "*enumerate onboarded tenants without reading every [row]*". |
| A second conversation engine | A new `generateText` loop for onboarding | `runAgentLoop` (`llm.ts:1642`) — subject to Q1 | "*There is NO second loop and NO generateText outside this file*" (`llm.ts:1779-1781`). | Tenant scoping on the new table | A hand-written `tenantId` filter in each function | `tenantQuery`/`tenantMutation`/`tenantAction` | CLAUDE.md §2 — Biome-enforced. The wrapper injects `ctx.tenantId`. |
| A slot state machine | A bespoke FSM library or a hand-rolled reducer | A pure `missingSlots()` predicate + a refusing mutation | The whole "machine" is "is this set empty". Rung 6 of the ponytail ladder. |
| Structured extraction from a user turn | Regex/heuristics over prose | `generateObject` + `jsonSchema` (`onboarding.ts:67-90,165`) | Already the house pattern, already zod-free (deliberately — keeps V8 modules off the inference cliff). |
| Prompt versioning / rollback for presets | A `presets.ts` constant map of strings | The `skills` registry rows | CLAUDE.md §5 and design §7. Hardcoded style strings are the exact thing §5 bans. |
| An immutable tier-change log | A `tierHistory` table | `internal.audit.log` | The audit table already is the append-only log (CLAUDE.md §3). A second one is a second thing to keep honest. Payload = refs/ids/counts/enums only (§4) — `{ from, to, tierSource }` are enums, which is fine; facts values are **not** (see Pitfall 4). |

**Key insight:** this phase's temptation is to build *infrastructure* (a tier service, a preset
engine, a slot framework, a history table). Every one of those already exists in a thinner form. The
phase's real work is a table, a pure function, three deletions, and two honest open questions.

## Common Pitfalls

### Pitfall 1: Removing `persona` from the validator without a plan for `serializeProfile`
**What goes wrong:** `vProfile` drops `persona`; `commitProfile` can no longer build a valid
`BusinessProfile`; `serializeProfile` emits `- **Persona:** undefined`; `evaluations.ts:263`'s
profile-detection (`text.includes("- **Persona:**")`) still matches, `deserializeProfile` falls back
to `"solopreneur"` (`businessProfile.ts:173`) — and **defect 1d reappears in a new costume**.
**Why it happens:** three files, one invariant, and the fallback is silent by design.
**How to avoid:** treat "table is the record, markdown is the projection" as one atomic change.
`commitProfile`/`updateProfile` read the tier from `tenantProfiles` and splice it into the profile
object before `serializeProfile`. Add a test asserting the serialized markdown's `Persona:` line
equals the table's `tier`.
**Warning signs:** a diff that touches `vProfile` but not `writeProfileDoc`.

### Pitfall 2: The `deserializeProfile` fallback stays load-bearing
**What goes wrong:** `persona: isPersona(persona) ? persona : "solopreneur"` (`:173`) is the literal
mechanism of defect 1d. SC#2 says a malformed doc "can no longer silently reclassify a tenant".
Leaving the fallback while *also* leaving `evaluations.ts:236,265` reading `personaHint` from it
means the tier still comes from the parse on the vault-grounded path.
**How to avoid:** SC#2 is satisfied by **removing the last authoritative reader**, not by changing
the fallback. Design §4.2 is explicit: the fallback "*stops being a silent reclassification risk
once nothing authoritative depends on it*". Repoint `evaluations.ts:295`
(`PERSONA_FRAMEWORK[personaHint ?? "solopreneur"]`) at the table. Then add a regression that the
markdown parse has no consumer that selects behavior.
**Warning signs:** a grep for `personaHint` still returning a use inside the framework auto-pick.

### Pitfall 3: "Fixing" the audit by writing a corrective row
**What goes wrong:** SC#4 gets read as "make the log accurate", and someone adds a compensating
row or (worse) a patch. CLAUDE.md §3: the audit module exposes only insert functions.
**How to avoid:** SC#4 is satisfied by *not writing the false field*. `onboarding.ts:278` and `:307`
both hardcode `personaConfirmed: true`. On the update path (`updateProfile`) nothing was confirmed —
drop the field, or replace it with something the code actually knows (`tierSource`, or a boolean the
caller genuinely supplies from the confirm interaction). Historical rows stay as they are; that is
what append-only means.
**Warning signs:** any new export in `convex/audit.ts` that is not an insert.

### Pitfall 4: Putting fact VALUES in the audit payload
**What goes wrong:** the tier-change event (SC#5) gets `{ headcount: 12, paidStaff: 3 }` in its
payload. CLAUDE.md §4: audit payloads carry "refs, hashes, ids, and counts ONLY". Headcount is
arguably a count — but `revenueStage`/`funding` free strings are not, and a tenant's staffing
numbers are exactly the business-sensitive data §4 exists to keep out of the log.
**How to avoid:** the tier-change payload is `{ from: <enum>, to: <enum>, tierSource: <enum>,
factsChanged: <number> }`. `onboarding.ts:182-189`'s `populatedFieldCount` is the in-repo precedent
for "a NUMBER, never a field value". There is also a `profileRedaction.test.ts` already scanning
this surface.
**Warning signs:** a payload object with a string value that came from user input.

### Pitfall 5: A new tool name that is not in the `agentSteps.tool` closed union
**What goes wrong:** the conversational onboarding adds a `recordSlot` tool. `agentSteps.tool` is a
closed `v.union` of literals (`schema.ts:399-437`). The activity-step insert throws — and **the AI
SDK swallows the callback error**, so there is no trace in production while every test passes. The
schema comments record this happening twice already ("*Research Pitfall 4*" for `searchVault`,
"*Pitfall 2*" for `evaluateBusiness`, and again for the three Phase-15 dispatch literals).
**How to avoid:** if Q1 resolves to "reuse `runAgentLoop`", the schema change lands **first**, in the
same wave as the tool. Add the literal, and add a test that drives the loop and asserts a row exists.
**Warning signs:** a plan that adds a tool to `buildCockpitTools` (or an onboarding tool factory)
without a `schema.ts` diff.

### Pitfall 6: `runAgentLoop` needs a `planId` and onboarding has no plan
**What goes wrong:** the reuse looks trivial until `runAgentLoop`'s signature
(`llm.ts:1642-1667`) requires `planId: Id<"plans">`, which it passes straight to
`buildCockpitTools(ctx, tenantId, planId, …)` (`:1682`). `plans.byThread` is a `.unique()` read
(`evaluations.ts:619-621`), so minting a throwaway plan row for onboarding risks colliding with the
thread's one real plan row.
**How to avoid:** decide Q1 explicitly. Do not discover this mid-implementation.

### Pitfall 7: Assuming an owner/admin primitive exists for D6
**What goes wrong:** a plan writes `grantEnterprise` as a `tenantMutation` and calls it
"admin-granted". `requireOwner` does not exist until Phase 22 (GOVN-01, `STATE.md:385`,
`REQUIREMENTS.md:143`), and STATE.md:469 records three Phase-8 functions **already** sitting
tenant-callable with no owner primitive — an open blocker, not a solved problem.
**How to avoid:** see Q4. The honest interim is an `internalMutation` with no public surface at all.
Adding a fourth tenant-callable pseudo-admin function makes the Phase-22 blocker worse.

### Pitfall 8: Missing explicit return-type annotations on new Convex handlers
**What goes wrong:** ~90 unrelated `apps/web` typecheck errors from an `internal`-graph circular
inference collapse. Measured and documented at `evaluations.ts:106-113` and `onboarding.ts:8-11`.
**How to avoid:** every new handler gets an explicit `Promise<…>`. Every new exported plain async
function that touches `internal` gets one too.

### Pitfall 9: Editing files frozen to another lane / skipping the playbook Stop hook
**What goes wrong:** the turn is blocked by `scripts/check-playbooks.mjs`, or the phase collides with
the Phase 14 lane. `evaluations.ts` and `packages/core/src/specialists*.ts` are Lane A property
(PARALLELIZATION.md), which this worktree is — fine. But **`apps/web/**` was FROZEN for Phase 15**
and 15.1 explicitly unfreezes it (two pages).
**How to avoid:** 15.1 touches `apps/web` (profile + onboarding pages), `convex/schema.ts`, and
`packages/contracts/skills/`. Confirm with the owner that the Phase-15 freeze is lifted for 15.1
before planning `apps/web` work, and register any new watched paths in
`docs/playbooks/watch.json`. CLAUDE.md §10 — read `docs/design/BRAND.md` before touching either page.

## Open Questions

### Q1 — How does the conversational onboarding get its loop? (blocks SC#3)

**What we know (HIGH confidence, read from source):**
- `runAgentLoop` (`llm.ts:1642`) is the ONE governed loop; `llm.ts:1779-1781` states there is no
  second `generateText` anywhere.
- It has already proven extensible to a second consumer: `runSpecialistTurn` (`:1790`), added by
  Phase 15, swaps `(skill body, tool allow-list)` through it.
- **But** it requires `planId: Id<"plans">` and builds its tools *exclusively* from
  `buildCockpitTools`. `toolNames` filters, it cannot add.
- A new tool name also needs a new `agentSteps.tool` literal (`schema.ts:399-437`), or the trace
  silently disappears in prod (Pitfall 5).
- `llm.ts` is the only `"use node"` module and a second one re-triggers a documented TS inference
  cliff (`onboarding.ts:7-11`).

**What's unclear:** which of three shapes the owner wants.

| Option | Shape | Cost | Risk |
|---|---|---|---|
| **(a) Generalize `runAgentLoop`** | make `planId` optional; accept an optional extra `tools` record merged into `built`; add `recordSlot` + an `agentSteps.tool` literal | edits `llm.ts` (2,985 lines, the hottest file in the repo) + `schema.ts` | Highest blast radius; but keeps "one loop" true and gets cost/fallback/trace free |
| **(b) `generateObject` slot-filler, no tool loop** | each user turn → one `generateObject` call returning `{ reply, slotUpdates }`; the *code* owns the state machine and the next question; the model owns the wording | a new V8 handler in `onboarding.ts`, ~80 lines; **zero `llm.ts` edits, zero `schema.ts` tool literal** | No CKPT-05 trace and no shared cost rail unless added; but onboarding is not a tool-using task — it is a **slot-filling** task, and `extractProfile` already proves the pattern in this exact file |
| **(c) Mint a throwaway plan row** | reuse `runAgentLoop` as-is against a synthetic onboarding plan | smallest diff on paper | `plans.byThread` is `.unique()` — a synthetic row on a real thread breaks every workspace reader. Fragile. **Not recommended.** |

**Recommendation: (b), with (a) as the documented upgrade path.** Reasons: it is the ponytail-ladder
answer (rung 2 — the pattern already exists 100 lines away in the same file); the design doc's own
framing is a *scripted spine* where code decides what to ask next, which is a state machine with a
phrasing model attached, not a tool-using agent; it needs zero edits to `llm.ts` and zero schema
change; and the §5 skill-registry requirement is satisfied identically (`getActiveSkill` +
`system: skill.body`, exactly as `extractProfile` does at `:158-169`). Mark it with a `ponytail:`
comment naming the ceiling ("no activity trace; upgrade to `runAgentLoop` if onboarding ever needs
real tools").
**This must be decided before planning, not during.** The design doc explicitly asks for it
("*Confirm this is cleanly reusable during planning before committing to it*", §6; Risk §13).

### Q2 — What does "which specialists are offered" mean when `diagnose()` returns exactly one? (blocks SC#5)

**What we know (HIGH confidence):** `runEvaluation` builds `gaps` from `leverageRank([diagnose(sc)])`
— a single prescription, hence at most one `gap`, hence one `route`. `applyActOnGap` acts on
`gaps[gapIndex]`. There is no offer *set*.

**What's unclear:** the design doc §8 says tier "*filters and orders which Growth OS specialists
(`offer-architect`, `money-model-designer`, `lead-engine`) are offered off a given diagnosis*" and
promises "*Same diagnosis, genuinely different recommended next steps*". That sentence presumes a
candidate set that does not exist.

**Options:**
1. **Widen `diagnose()` to emit candidates** — return the failing gate's prescription *plus* the next
   N gates as secondary candidates; `leverageRank` finally sorts a real array (it was clearly written
   for one — it takes `Prescription[]`); tier filters/orders the resulting list. Honest and matches
   the doc's language. Costs a `diagnose()` change + an `evaluations.gaps` array that can hold >1,
   plus `cards.tsx` rendering more than one gap. **Largest scope; also the only option that literally
   delivers the doc's sentence.**
2. **Tier changes the specialist's PROMPT, not the set** — same route, but the tier + agent name +
   behavior preset ride into `runSpecialistTurn`'s prompt, so a solopreneur's `money-model-designer`
   never proposes hiring. Cheap, honest, and directly satisfies "*A solopreneur does not receive
   advice premised on delegation*" (§8.1). Does NOT satisfy "*which playbooks run*" literally.
3. **Tier maps to the `playbook` field** — every `Prescription` already carries a `playbook` string
   (`"02-build-offer"`, `"06-assemble"`, …) that is currently pass-through. Tier could select a
   tier-appropriate playbook within the same specialist. Middle cost.

**Recommendation:** ship **(2) in this phase** (it is the perceivable half and it is nearly free —
the tier is already being loaded for the voice work), and record **(1)** as a follow-up with an ADR.
Reason: (1) changes the diagnosis contract and `apps/web` rendering, which is a second phase's worth
of blast radius riding on a phase whose actual job is the write path. **Owner decision required —
this changes what SC#5 means.**

### Q3 — Does `financialsPresent` still override the tier? (affects SC#5)

`evaluations.ts:291-295`: any tenant with one financial figure gets `growth-os` regardless of tier.
Design §1c flags this as part of defect 1c but §8.3 only says the rubric pick "*stays, now reading
from the table*". Literally read, the override stays and SC#5's rubric half remains a no-op for
financially-grounded tenants. **Recommendation:** keep the override for the *framework* (it is
correct — financials mean a growth-os diagnosis is possible) and make the tier's effect land on
voice/framing/specialist-prompt instead, which is unconditional. Say so explicitly in the plan so a
verifier does not read SC#5 as "the rubric must change".

### Q4 — There is no owner primitive for D6's admin-granted enterprise

**What we know (HIGH confidence):** `requireOwner` is GOVN-01, `[ ]` Pending, scheduled for **Phase
22** (`REQUIREMENTS.md:143,253`; `STATE.md:339,385`). `STATE.md:469` records it as an **open
blocker**: three Phase-8 functions (`setOptimizerEnabled`, `activateCandidate`,
`candidatesForReview`) are tenant-callable today with no owner primitive.

**Honest interim (recommended):** ship `tierSource: "admin"` as a *representable value* and an
`internalMutation` (no public API surface at all — the `actOnGapInternal` precedent,
`evaluations.ts:740`) that an operator invokes via `npx convex run`. No `tenantMutation`, no UI, no
route. Document in the playbook that enterprise grants are an operator action until GOVN-01 lands,
and note that `deriveTier` structurally cannot return `enterprise` (its return type excludes it), so
D6 holds by construction regardless of who can call the grant.
**Do not** add a fourth tenant-callable pseudo-admin function — that deepens the Phase-22 blocker.

### Q5 — Is `apps/web` unfrozen for 15.1?

PARALLELIZATION.md: "*`apps/web` is FROZEN for Phase 15 after Wave 0.*" 15.1 necessarily rewrites two
pages. The freeze was scoped to Phase 15 and Lane C (Phase 14) is the only other live lane — Phase 14

### Q6 — Is `onboarding-agent` a gated skill?

`GATED_SKILLS` (`packages/contracts/src/skill.ts:100`) determines whether a skill-body edit rides the
Phase-3.6 `EVAL_GATE`. `business-profile` is currently **ungated** (`onboarding.ts:146`), which is the

shapes every future call — an argument for gating. **Recommendation:** ungated for the beta (matching
`business-profile`), with the decision recorded; gating adds an eval-corpus obligation this phase has
no budget for. Owner call.

### Q7 — Exact facts field types

Design §4.1 names `headcount`, `paidStaff`, `revenueStage`, `funding`, `yearsOperating` without
types. `headcount`/`paidStaff`/`yearsOperating` are clearly numbers; `revenueStage` and `funding` are

`@pikar/core`, so `deriveTier` is total and its branch table is exhaustively testable. A free string
here reintroduces string-matching, which is the defect class this phase exists to close.
