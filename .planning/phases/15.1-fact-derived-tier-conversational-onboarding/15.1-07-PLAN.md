<objective>
Finish the two surfaces. The onboarding page becomes a conversation that asks the determining facts and
ends on the closing beat; the profile page becomes an editable facts form with the tier rendered
read-only beside its reason.

Purpose: design §9's anti-manipulation mechanism is *"mostly a subtraction"* — plan 03 did the
subtraction, this plan supplies what replaces it, so the user can move their tier the only legitimate
way: by changing the facts. And design §6's closing beat is where the tailoring becomes PERCEIVABLE —
*"a tailored experience the user cannot perceive is not a selling point."*
Output: both pages functional against the plan-02/03/06 backend.
</objective>

<task type="auto">
  <name>Task 1: The onboarding page becomes a conversation</name>
  <files>apps/web/app/(app)/dashboard/onboarding/page.tsx</files>
  <action>
Rewrite the flow, keeping every intake modality and every style object already in the file. Read
`docs/design/BRAND.md` first.

The flow, in order:
1. **Opening turn.** The agent greets and asks for the business in the user's own words. The three
   existing modalities (type / upload / speak) all still reduce to one `intakeText`, unchanged.
2. **Narrative extraction, once.** `extractProfile(intakeText)` fills the narrative fields
   (name/offering/target customer/goals/constraints). It no longer returns a persona — there is nowhere
   for a guess to go. Hold the result in state.
3. **The fact conversation.** Loop: `converse({ slots, userMessage, history })` → append `reply` as an
   agent bubble, replace `slots` with the returned slots, and continue while `done === false`. The UI
   renders the transcript; it does NOT choose the next question and must not display a progress
   checklist of slot names — the whole point of D3 is that this reads as a conversation, not a form
   wearing chat's clothes. A subtle "still to cover" affordance is fine if BRAND supports it; a form is not.
4. **Agent identity (D4)** — the agent asks for a name and offers the behaviour presets. The NAME is
   free text through a plain input (client-side length cap; the server sanitizes authoritatively via
   `sanitizeAgentName`). The PRESET is a choice among `BEHAVIOR_PRESETS` with the one-line descriptions
   from `15.1-05-SUMMARY.md` — a small pill/radio group is right here, because a preset genuinely IS a
   user preference, unlike the tier. This is the one place pills are correct; say so in a comment so a
   future reader does not read them as the persona pills returning.
5. **The closing beat (§6).** `done === true` → the agent's final turn makes the tailoring legible and
   asks for confirmation in one move — *"From what you've told me, I'll work with you as a solo
   operation, so I won't suggest hiring your way out of problems. Sound right?"* The wording comes from
   the model's `reply` (it is a registry-owned prompt's job, §5); the UI supplies the confirm affordance.
   Do NOT compose that sentence in the page — a hardcoded sentence here would be prompt content in
   source and would also drift from the skill body.
6. **Commit, on confirm, in this order:**
   - `tenantProfile.saveFacts({ ...slots, agentName, behaviorPreset })` — this is what DERIVES and
     persists the tier
   - then `onboarding.commitProfile({ profile: narrativeFields })` — which now REFUSES if the facts are
     not complete. Render `INCOMPLETE_ONBOARDING`'s `missing` list as a recoverable state that returns
     the user to the conversation, never a dead end and never a raw error code.
   - clear the localStorage draft only after BOTH succeed.
7. **Draft resumability** — extend the existing `DRAFT_KEY` payload with `slots`, the transcript, the
   agent name and the preset. Bump the key to `pikar:onboarding-draft-v2` so a stale v1 draft (which
   carries a `persona` and no slots) cannot rehydrate into the new shape; ignore/drop an unknown
   version rather than migrating it.

Accessibility (BRAND + CLAUDE.md "not lazy about"): the transcript is a live region, the composer has a
label, the preset group is a proper radio group with `aria-checked`, and every error is `role="alert"`.

**No tier control anywhere on this page.** The tier is never displayed as a choice; if you show it at
all, it is inside the agent's own sentence.

  <name>Task 2: The profile page becomes the facts surface</name>
  <files>apps/web/app/(app)/dashboard/profile/page.tsx</files>
  <action>
Read `docs/design/BRAND.md` first. Reuse `LabeledField`, `label`, `field`, `page` — no new patterns.

Add, above the existing narrative fields:
1. **A "Business shape" card with the five facts, editable:** `headcount` and `paidStaff` and
   `yearsOperating` as number inputs (`min={0}`, `step={1}`, and reject non-integers client-side);
   `revenueStage` and `funding` as selects over `REVENUE_STAGES` / `FUNDING_STATES`. Label them in the
   user's language, not the enum's — *"How many people work on this, including you?"*, *"How many are
   paid staff?"* Saved through `tenantProfile.saveFacts`. **There is no tier field to send.**
2. **The tier, read-only, with its reason** (§9): the tier value, `TIER_REASON[tier]` beneath it, and
   the `tierSource` rendered honestly in plain words (derived / confirmed / granted by Pikar AI /
   carried over from your earlier profile). Add one short line making the mechanism legible — editing
   the facts is what moves the tier; nothing sets it directly. Do not render it as disabled form
   controls; a greyed-out picker still reads as "there is a control here".
3. **Tier change is a moment, not a setting** (§9). When a save returns a `tier` different from the one
   rendered before it, surface it as an event — a short, warm acknowledgement that the product noticed
   they grew ("*You've moved from solo operation to startup — I'll adjust how I work with you.*"), not a
   silent field update. `saveFacts` returns `{ tier, tierSource, changed }`; drive off `changed`.
4. **Agent identity (D4):** the agent name as a text input and the behaviour preset as a radio group
   over `BEHAVIOR_PRESETS`, both saved through the same `saveFacts` call. Preset descriptions from
   `15.1-05-SUMMARY.md`.
5. **The legacy invitation (§10):** when `tierSource === "legacy"` or `missingSlots(row)` names any fact,
   show a non-blocking prompt to complete the facts, explaining what it improves. **Never a modal, never
   a redirect, never a gate** — design §10 is explicit that there is no forced re-onboarding, and
   `onboarding.status` deliberately still returns `needsOnboarding: false` for these tenants.
6. Handle `INCOMPLETE_FACTS` from `saveFacts` as an inline, recoverable message naming the missing
   fields in user language.

Accessibility: every input labelled, the radio group is a real radio group, the tier-change
acknowledgement is announced (`role="status"`), errors are `role="alert"`.
