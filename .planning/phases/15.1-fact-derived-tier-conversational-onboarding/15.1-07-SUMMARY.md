## Decisions Made

- **The closing beat costs a SECOND `converse` call, and that is the substantive decision.**
  `converse` computes `nextSlot` from the slots it was GIVEN, so the turn that finally completes the
  set was still under `Next fact to obtain: <last>` — its reply is an acknowledgement. Re-asking with
  the completed slots is what puts the registry prompt on its *"Nothing left to obtain — this turn is
  the closing beat"* branch. Using the acknowledgement instead would have been one call cheaper and
  would have silently deleted §6's whole point: *"a tailored experience the user cannot perceive is
  not a selling point."* The wording stays the model's; a sentence composed in the page would be
  prompt content in source (§5) and would drift from the skill body. If the second call throws, the
  acknowledgement stands and the user is not stranded. A `ponytail:` comment names the ceiling and
  the upgrade path (have `converse` also report a post-merge closing instruction — a backend change
  this plan did not own).
- **Commit order is `saveFacts` → `commitProfile`, and it is load-bearing, not stylistic.**
  `commitProfile` reads `tenantProfiles` to splice the tier into the markdown projection and refuses
  without a row. Reversed, every first-time onboarding fails at its last step. Stated as an invariant
  in the playbook so a later "tidy" reordering is visibly a regression.
- **The preset group is a NATIVE radio group.** The plan specified `role="radio"` + `aria-checked`;
  `useSemanticElements` correctly objected, and `fieldset`/`legend` + `input[type=radio]` gives the
  checked state, the group semantics AND arrow-key navigation from the platform (ponytail rung 4).
  The hand-rolled version had no keyboard navigation at all — an a11y gap the literal spec would have
  shipped.
- **The tier renders as TEXT, never a disabled control.** Plan-mandated and worth restating: a
  greyed-out picker still reads as *"there is a control here"*, which is the impression §9 removes.
- **The tier-move acknowledgement drives off `saveFacts`'s `changed` flag**, never a client diff. The
  server already made that comparison against the row it wrote; a page-side diff would be a second
  opinion that can disagree with the record.
- **The onboarding page never calls `canComplete`** — `done` comes back from the server, and the scan
  asserts the absence. A client-side mirror of a fail-closed server gate is how a gate quietly stops
  being one (the same reasoning that keeps `requiredFilled` off the fact slots).
- **The `PresetGroup` and the style objects are duplicated across the two pages, deliberately.** The
  app has no component library by design (BRAND §8.3), and `label`/`field`/`LabeledField` were
  already duplicated across exactly these two files — matching the established idiom beat inventing a
  shared-component location for ~30 lines.
- **The narrative REVIEW CARD was kept** (it is not in the plan's step list). Phase 11's SC#1 —
  *"the extracted draft is reviewed and edited first"* — is an invariant in this playbook, and
  deleting the card to match a step list would have quietly retired it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] The plan's `role="radio"` group had no keyboard navigation**
- **Found during:** Task 1, at the first `biome check`
- **Issue:** The plan specified "a proper radio group with `aria-checked`". Implemented literally as
  `<button role="radio" aria-checked>`, this tripped `lint/a11y/useSemanticElements` — a NEW biome
  finding against the file's baseline. More importantly the lint was right: a `role="radio"` group
  needs roving-tabindex and arrow-key handling to be operable, and none of that was in the spec.
- **Fix:** a real `fieldset`/`legend` + `input[type=radio]` group on both pages. Checked state, group
  semantics and arrow keys come from the platform. `aria-checked` becomes redundant (the native
  element exposes `checked`), which is why it is absent.
- **Files modified:** both pages.
- **Verification:** biome back to the file's baseline finding set; `tsc` exit 0.
- **Committed in:** `a995a81` / `fbb3c9b`

**2. [Rule 1 - Bug] The new `tier:` scan rule false-positived on a read-only ternary**
- **Found during:** Task 3, on the first run of the extended scan
- **Issue:** `/\btier\s*:/` matched `{tierRow ? tierRow.tier : "—"}` — a ternary's colon inside the
  read-only tier render. The rule fired on exactly the code §9 REQUIRES to exist.
- **Why it matters beyond the red:** the obvious response to a rule that fires on correct code is to
  loosen it until it stops, and a rule loosened under that pressure stops guarding. Caught before
  that happened.
- **Fix:** anchor on PROPERTY POSITION — `/(?:^|[{,(])\s*(?:tier|persona)\s*:/m`. A property key
  follows `{`, `,`, `(` or a line start; `.tier :` in a ternary follows a `.`. The test comment
  records the false positive and why the anchoring is not cosmetic.
- **Verification:** 14/14 green; the mutation still turns it RED (the planted `({ tier: "sme" })` is
  in property position).
- **Committed in:** `3446fd0`

**3. [Rule 1 - Bug] The playbook still described the deleted persona confirm/change control**
- **Found during:** Task 3
- **Issue:** `onboarding.md`'s frontend key-file bullet said the onboarding page renders *"a persona
  confirm/change control (SC#1)"*, and Purpose said the LLM extracts a profile *"with an inferred
  persona, the user CONFIRMS it"*. Both became false in plan 03 and stayed in the file. The `Last
  verified` line above them described the subtraction correctly, so the document contradicted itself.
- **Fix:** both rewritten to the shipped behaviour, alongside the new section.
- **Committed in:** `3446fd0`

### Measurement error caught (not a code deviation, but the phase's own lesson repeating)

`grep -c $'\r' <file>` under Git Bash here returned a count **equal to the line count** for three
files, i.e. it matched every line — I briefly concluded both pages were CRLF. The authoritative
count (`(s.match(/\r\n/g) || []).length` in node) said **0**. The mutation script was already
deriving its EOL from the file rather than trusting that reading, so nothing downstream was affected,
and it printed `=== MUTATION APPLIED ===` only after re-reading the file. **Do not measure line
endings with `grep -c $'\r'` in this worktree.** (After the post-mutation `git checkout --`, git's
`autocrlf` genuinely converted `profile/page.tsx` to CRLF — 27238B → 27955B, 717 CRLF — which is why
its `format` finding reappeared and the onboarding page's did not.)
