# Phase 15.1 Plan 02: The Tier's Home — `convex/tenantProfile.ts` Summary

**The tier now has an indexed, auditable, tenant-scoped record: `saveFacts` re-derives it on every
facts write and has no tier argument to be told otherwise, a move leaves exactly one four-key audit
row with no fact values in it, an operator grant survives the tenant editing headcount, and every
pre-15.1 tenant backfills to `legacy` idempotently.**

## Recorded values (the plan's `<output>` asked for these explicitly)

### The `saveFacts` contract — plans 03 / 06 / 07 call this

```ts
saveFacts({
  headcount?: number, paidStaff?: number, yearsOperating?: number,
  revenueStage?: "pre-revenue" | "early-revenue" | "steady-revenue",
  funding?: "bootstrapped" | "seeking" | "funded",
  agentName?: string, behaviorPreset?: "direct" | "coaching" | "concise",
}) : Promise<{ tier: Tier; tierSource: TierSource; changed: boolean }>
```

**There is no `tier` argument.** Arg validators are derived from
`schema.tables.tenantProfiles.validator.fields`, so they cannot drift from the table.

| Situation | Result |
|---|---|
| Facts complete, no existing row | INSERT `{tier: deriveTier(facts), tierSource: "derived", derivedAt: now}`; `changed: true`; event emitted with `from: null` |
| Facts complete, existing row, tier moves | PATCH facts + `{tier, tierSource: "derived", derivedAt: now}`; `changed: true`; event emitted |
| Facts complete, existing row, tier does NOT move | PATCH facts + a refreshed `derivedAt`; `changed: false`; **no event** |
| Facts complete, existing row at `tierSource: "admin"` | PATCH **facts only** — tier and source untouched; `changed: false`; no event |
| Facts INCOMPLETE, no existing row | `throw new ConvexError({ code: "INCOMPLETE_FACTS", missing })` — nothing written |
| Facts INCOMPLETE, existing row | PATCH facts only; returns the EXISTING `tier`/`tierSource`, `changed: false` |

Merging is provided-over-stored with `??` (nullish, never `||`) — `headcount: 0` is an ANSWER.
`agentName` is stored through `sanitizeAgentName`. `missingSlots` is fed a placeholder
`oneLineDescription` so only the FIVE fact slots gate the write (the narrative lives on the vault
doc and is not this mutation's business).

### The `tenant.tier_changed` payload key set — plan 07's UI and the phase verification read this

```
eventType: "tenant.tier_changed"    actor: "user"    correlationId: crypto.randomUUID()
payload keys, sorted: ["factsChanged", "from", "tierSource", "to"]
```

- `from`: `Tier | null` (null on a first-ever row) · `to`: `Tier` · `tierSource`: `TierSource`
- `factsChanged`: a COUNT, 0..5 — how many fact fields THIS call moved. `grantEnterprise` sends `0`.
- **No fact values, ever.** It rides the existing insert-only `internal.audit.log`; there is
  deliberately no `tierHistory` table.

### The `_generated/api.d.ts` hand-edit (so a fresh session does not re-discover it)

`convex codegen` cannot run in this worktree (no `CONVEX_DEPLOYMENT`). `api.d.ts` enumerates modules
by hand-written import, so a NEW module is invisible to `internal.*`/`api.*` **types** until it is
added in TWO places, alphabetically:

```ts
import type * as tenantProfile from "../tenantProfile.js";   // beside `import type * as telemetry`
declare const fullApi: ApiFromModules<{ … telemetry: typeof telemetry; tenantProfile: typeof tenantProfile; vault: … }>;
```

The file is git-ignored — **zero committed footprint**. Runtime is unaffected either way
(convex-test resolves modules through `import.meta.glob`); only the types break, and they break
loudly in `evaluations.ts` / `dispatch.ts` / `apps/web` in later plans.

### How `vaultSweep.test.ts` drives a migration under convex-test

`migrations.define` returns a plain internal mutation, so it is called DIRECTLY in the documented
one-off mode — one batch, synchronous, no component round-trip:

```ts
await t.mutation(internal.tenantProfile.backfillLegacyTier, {
  cursor: null, batchSize: 100, dryRun: false, oneBatchOnly: true,
});
```

The `migrations` component must still be registered (`t.registerComponent("migrations",
migrationsSchema, migrationsModules)`) so the module graph loads clean and the runner path stays
representable. **This backfill schedules nothing** — the test asserts zero pending/inProgress
`_scheduled_functions` rows and cancels any it finds, so the file has no hidden `OPENAI_API_KEY`
dependency (the 15-04 race).

## Decisions Made

- **The §4 no-fact-values scan targets audit PAYLOADS, not whole audit rows.** See Deviations — this
  is both a flake fix and a strictly stronger assertion.
- **`derivedAt` is refreshed on an unchanged re-derivation.** The timestamp answers "when did the
  rule last run over these facts", which is what makes a threshold retune a visible re-derivation
  event; the AUDIT ROW answers "when did the answer move". Two different questions, two different
  mechanisms — pinned by the "no event when the tier does NOT move" test.
- **Stickiness lives in `saveFacts`, not `grantEnterprise`.** `grantEnterprise` just writes
  `tierSource: "admin"`; `saveFacts` is the only function that could undo a grant, so the guard
  belongs at that one site. Adding a second guard inside the grant would be a second thing to keep
  honest.
- **`grantEnterprise` upserts.** A tenant with no row at all can be granted (the row it writes has
  no facts, exactly like a `legacy` row). Requiring a pre-existing row would make the operator's job
  order-dependent for no benefit.
- **Five two-directional binds, not four.** The plan grouped `revenueStage|funding` as one bind;
  they are separate unions with separate schema literals, so each got its own pair. Same mechanism,
  one more pair.
- **`FACT_KEYS` is a local 5-literal array, not a re-export of `REQUIRED_SLOTS`.** `REQUIRED_SLOTS`
  includes `oneLineDescription`, which this module deliberately does not own; slicing it at runtime
  would be more code and less obvious than the explicit list, and the compile-time binds already
  guarantee the enum VALUES agree.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The §4 no-fact-values scan reads audit PAYLOADS, not whole audit rows**
- **Found during:** Task 2 (while writing the test, before it ever ran)
- **Issue:** The plan said "assert the JSON of every `audit` row contains neither `137` nor `41`".
  An audit row carries `ts` and `_creationTime` — 13-digit epoch millis — plus a hex
  `correlationId`. A random 13-digit number contains a given 2-digit needle with probability ≈11%,
  and there are several such numbers per row across several rows, so the literal assertion would
  fail on a large fraction of runs *for reasons having nothing to do with redaction*. Worse, it is
  the WEAKER assertion: a real leak would be indistinguishable from timestamp noise.
- **Fix:** `auditPayloadJson()` scans `rows.map(r => r.payload)` — the object CLAUDE.md §4 actually
  governs. A non-vacuity assertion (`expect(payloads).toContain("tier")`) proves a populated payload
  is being scanned, so the check cannot pass by scanning nothing. The rationale is a comment on the
  helper so a later reader does not "restore" the flaky form.
- **Files modified:** `packages/backend/convex/tenantProfile.test.ts`
- **Verification:** mutation-checked — adding `headcount` to the payload turns it RED.
- **Committed in:** `03a2047` / `4405ca0`

**2. [Rule 3 - Blocking] `tenantProfile.test.ts` needed a typed convex-test instance**
- **Found during:** Task 1 (backend `tsc --noEmit` went 55 → 57)
- **Issue:** `ReturnType<typeof convexTest>` erases the schema generic, so `ctx.db.query(...)
  .withIndex("by_tenant", …)` inside `t.run` resolved against `SystemIndexes` — the exact
  "SystemIndexes wall" 15-04 hit. Two `TS2345`s, invisible to the plan's own vitest verify command.
- **Fix:** `TestConvex<typeof schema>` throughout (the 15-04 `gapAction.test.ts` precedent).
- **Files modified:** `packages/backend/convex/tenantProfile.test.ts`
- **Verification:** backend `tsc --noEmit` back to the exact 55-error baseline.
- **Committed in:** `3045077`
