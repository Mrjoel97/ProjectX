# Phase 15.1 Plan 05: The Tier Becomes Perceivable Summary

**A dispatched specialist is now told, as a FACT in every run, what shape of business it is advising
— so a solopreneur's `money-model-designer` cannot propose hiring — and the tenant's chosen agent
name and behaviour-preset voice ride in with it, through a registry row rather than a string in
source.**

### The three presets — plan 07's profile page renders these

| Preset | Registry row | One-line description |
|---|---|---|
| `direct` | `style-direct` | Blunt. Names the binding constraint in the first sentence, no preamble, states the cost of not acting, and never softens into "you might consider". |
| `coaching` | `style-coaching` | Opens with the tradeoff and asks the ONE question that would change the recommendation — then still lands a concrete next step. Never a therapy loop. |
| `concise` | `style-concise` | Minimum words. The step, the proof metric, the risk. No framing prose, no closing line. |

All three are **UNGATED** (Q6) and seed as v1 `active` on the next `seedSkills`.

### The exact `tierBriefing` output shape — the phase verification greps this

```
Agent name: Ada
Business tier: solopreneur — one person, no paid staff — there is nobody to delegate to, so every step must be executable by the owner alone

<DIRECTIVE BODY>
```

Verbatim, as JSON, for the four representative input shapes:

```
{tier,agentName,styleDirective} → "Agent name: Ada\nBusiness tier: solopreneur — one person, no paid staff — there is nobody to delegate to, so every step must be executable by the owner alone\n\n<DIRECTIVE BODY>"
{tier:"sme"}                    → "Business tier: sme — an established business with steady revenue and paid staff — there is a team to assign work to and an existing process to change"
{agentName:"Ada"}               → "Agent name: Ada"
{}                              → ""
```

Line order is fixed: agent name, then tier, then a blank line, then the directive body. Each line is
**omitted entirely** when its input is absent — never an empty label and never the string
`undefined`. An absent tier produces **no tier claim at all**, never an invented `solopreneur`.
`dispatch.ts` skips the block entirely when it is `""`.

### How `buildSpecialistPrompt` was driven from the test

**`t.run`, the plan's first-choice harness — the fallback stub was not needed.** I probed it before
writing the suite: `t.run`'s ctx **does** expose `runQuery` (`typeof ctx.runQuery === "function"`),
so

```ts
t.run(async (ctx) => buildSpecialistPrompt(ctx as never, { tenantId, threadId, gapIndex: 0, route }))
```

runs the function against the **real** `internal.tenantProfile.forTenant` and
`internal.skills.getActiveSkill`. That matters: the hand-built function-reference-identity stub the
plan offered as a fallback would have been a second implementation of the two queries, free to drift
from them. Deliberately NOT driven through `__runSpecialistWithScript` — the mock model swallows the
prompt, so the assertion would have been about nothing.

Two fixture details worth carrying forward:
- The tier row is seeded **after** `setupDispatched()` runs the evaluation, so 15.1-04's rubric pick
  is untouched and this suite characterizes the PROMPT only.
- The style sentinel is written by **patching the seeded active row's body**, not by inserting a
  second row: `loadSkill` uses `.unique()`, so two active rows for one name would throw. The
  fail-open fixture archives the seeded `style-coaching` row to leave the preset genuinely unseeded.

## Decisions Made

- **The distinctness assertion masks the tier literal.** This is the substantive decision of the
  plan and it came out of a mutation-check that refused to go red. See Deviations.
- **`tierBriefing` returns `""` rather than a placeholder when nothing is known**, and `dispatch.ts`
  branches on that (`briefing ? ... : rest`). The alternative — always emitting a header — would put
  a content-free line in every prompt of every tenant without a profile row.
- **`agentName` is sanitized inside `tierBriefing`, not at the call site**, so there is exactly ONE
  place a user-authored string can reach a model prompt. Stated in the doc comment so a later reader
  neither adds a second sanitation nor removes this one assuming the caller did it.
- **`TIER_FACT` clauses describe the STRUCTURAL CONSEQUENCE, not the user.** "one person, no paid
  staff — there is nobody to delegate to, so every step must be executable by the owner alone" is an
  instruction about what advice is admissible; "you are a small business" would be a label the model
  could ignore.
- **`buildSpecialistPrompt`'s export carries a comment naming the test as its only reason** and
  stating that production still calls it from one place — otherwise the export reads as an invitation
  to call it from somewhere else.
- **The UNGATED rationale lives on `GATED_SKILLS`**, not only in the playbook: that list is where a
  future reader would "fix" the omission, so that is where the reason has to be.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's SC#5b distinctness assertion was VACUOUS; it now masks the tier literal**
- **Found during:** Task 2, at the plan's own mandated mutation-check
- **Issue:** The plan specified `new Set(TIERS.map(t => tierBriefing({tier: t}))).size === TIERS.length`
  and predicted that making two tiers share a clause would turn it RED. It did **not** — the suite
  stayed **34/34 green** with `startup`'s clause copied byte-for-byte from `solopreneur`'s. The cause
  is structural: the briefing interpolates the tier NAME (`Business tier: startup — …`), so any two
  briefings differ by the name alone regardless of substance. As written the test proved only that
  the tier literal is interpolated — which the neighbouring "each briefing names its own tier" test
  already proved — and would have gone on passing if every tier had received identical advice. That
  is precisely the failure SC#5b exists to catch.
- **Fix:** compare `tierBriefing({tier: t}).replaceAll(t, "<TIER>")` — mask the discriminator, then
  assert distinctness of what remains. The comment records the observed vacuity so the masking is not
  "simplified" away later.
- **Verification:** re-ran the same mutation — now **1 RED**, exactly the distinctness test; reverting
  restored 34/34.
- **Committed in:** `dc2387c`

**2. [Rule 1 - Bug] My edit stranded `specialistMemoBody`'s doc comment above `PRESET_SKILL`**
- **Found during:** Task 2, while reverting the mutation
- **Issue:** I anchored the insertion on `export function specialistMemoBody(args: {`, which sits
  BELOW its own jsdoc — so the new `PRESET_SKILL` / `TIER_FACT` / `tierBriefing` block landed between
  that jsdoc and the function it documents. Harmless to the compiler, actively misleading to a reader:
  the "ponytail: ceiling is a body marker" note would have appeared to describe `PRESET_SKILL`.
- **Fix:** moved the jsdoc back to directly above `specialistMemoBody`.
- **Committed in:** `dc2387c`

**3. [Rule 3 - Blocking] Two mutation-check scripts silently no-op'd on CRLF files**
- **Found during:** Task 3
- **Issue:** `dispatch.ts` is a git-checked-out file and this worktree has `core.autocrlf=true`, so it
  is CRLF on disk (460 CRLF, 0 bare LF). A `perl`/`node` replacement whose pattern spans `\n` matches
  nothing — and because the failed `grep` broke the `&&` chain, the first attempt printed only
  `=== REVERT ===` and looked like a clean run. A mutation-check that never applied is worse than none:
  it reports a guard as proven when nothing was tested.
- **Fix:** CRLF-aware match strings, plus an explicit `NO MATCH` + `exit 1` in the mutation script so a
  non-applying mutation is LOUD rather than silently green. The fail-open guard was then genuinely
  mutation-checked (1 RED).
- **Note:** the Task-1 and Task-2 mutations were unaffected — Task 1's was a single-line substitution,
  and `specialists.ts` was LF at the time (freshly written and biome-formatted). Both were confirmed
  applied by observing the mutated text and the RED.
