  <action>
    Create `convex/gmail.ts` starting with `"use node"`, containing ONLY the send internalAction
    `send({ requestId })`:
    1. Load the tenant's token + the request draft/recipient via `ctx.runQuery`. Both readers must be
       INTERNAL queries keyed by explicit args (tenantId / requestId) — NOT 02-03's `requests.get`,
       which is a `tenantQuery` that derives tenantId from the caller's identity and has no identity in
       this system (retrier) context. Co-locate a `getForDelivery({ requestId }) → { draft, recipient,
       tenantId }` internalQuery in `gmailAuth.ts` (the non-node module) alongside the token reader.
    2. Refresh the access token via `fetch` POST to `oauth2.googleapis.com/token`
       (grant_type=refresh_token). If refresh FAILS (7-day expiry): set the request to
       `awaiting_reauth` via `ctx.runMutation(internal.pipeline.setStatus, { requestId, status:
       "awaiting_reauth" })` (the reusable status setter shipped by 02-01 — gmail.ts is `"use node"`
       and cannot hold its own mutation) and RETURN — do NOT throw (the approved draft is preserved;
       the user reconnects and delivery resumes). This is the token-expiry race resolved in favor of
       the user's consent (CONTEXT).
    3. Build the RFC-2822 MIME (To/Subject/plain body), base64url it, POST to
       `gmail.googleapis.com/gmail/v1/users/me/messages/send`. A 5xx THROWS so the retrier retries;
       a terminal failure flows onComplete → deadLetters → OPSG-07.
    4. On success: record the returned message id as an audit ref (refs only — never body) and
       RETURN. Do NOT set status `sent` here — the pipeline owns the `sent` transition after
       `retrier.run` returns (02-06 step 4), so setting it here too would be a redundant write.
    The pipeline (plan 02-06) invokes this via `retrier.run(ctx, internal.gmail.send, ...)`.
    Confirm the AI-SDK-independent `usage`/token field names are not needed here (send has no LLM).
