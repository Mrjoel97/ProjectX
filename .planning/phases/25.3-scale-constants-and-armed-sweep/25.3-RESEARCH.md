# Phase 25.3 — Scale constants and the armed sweep: research

**Source:** rev 5 system audit G17 and G1 (`.planning/design/system-audit-2026-09-03-merged.md` §4; Track A step 4). Verified against the tree at `6c515f2` (production, 2026-09-05).
**Audit's claim, restated:** "Four small diffs + arming G1's sweep make 10k users honest; sharding makes 100k feasible." This phase is the four diffs and the arming instruction. Sharding is the 100k step and is deferred by name.

## What the audit found, checked

| # | Finding | Where (verified) | Diff |
|---|---|---|---|
| 1 | Deployment-wide caps are compile-time constants: $50/day LLM, $100 media, $250 ingest | `guardrails.ts:43,60,78`; consumed by the rate-limiter config (`:80-98`), `finance.ts` rails view, `vaultFolders.ts` refusal | Read each from env (`DEPLOYMENT_BUDGET_CENTS`, `DEPLOYMENT_MEDIA_BUDGET_CENTS`, `DEPLOYMENT_INGEST_BUDGET_CENTS`) with the compiled value as the fallback; three `feature`-tier manifest rows. Owner decision 2 (free beta) makes these THE spend ceiling. |
| 2 | `runWeekly` collects every `business_profile` document (full text) in one mutation, then `runAfter(0)` for every tenant, with no fan-out budget gate; `reviewOne` has a bare `catch` | `proactiveReview.ts:41-112` | Walk `users` (one row per tenant) as a `@convex-dev/migrations` batch job; per user one indexed `by_tenant_kind` `.first()`; a `deploymentSpendCents` check before scheduling; a random spread over 30 min; the catch logs `{tenantId, error name}`. |
| 3 | `flagExpiringTokens` collects the whole `gmailTokens` table and inserts a fresh notification every day for the same expiring grant | `gmailAuth.ts` `flagExpiringTokens` | Batch job over `gmailTokens`; skip a tenant who already has an unread `gmail_reconnect` notification (`by_tenant_read`, bounded take). |
| 4 | WORM export writes ONE 10k-row page per daily run — a backlog can never catch up | `worm.ts` / `wormCursor.auditSince` | Loop pages inside the action until a short page or an 8-minute budget; each page is its own Object-Lock object and cursor advance. `pageSize` arg for tests. |
| 4b | `retryStuckIngests` and `backfillAuditCounts` `.collect()` whole tables — unrunnable on a real deployment | `vaultIngest.ts:95`, `audit.ts:105` | Both become batch jobs behind their existing names. |
| G1 | `reliabilitySweep` ships dormant behind `RELIABILITY_SWEEP_ARMED=1` | `reliabilitySweep.ts:353` | No code change. Owner arms it from their terminal after the first watched render: `cd packages/backend && npx convex env set --prod RELIABILITY_SWEEP_ARMED 1`. |

**Deferred with the ceiling named:** `shards` on the three deployment counters (`@convex-dev/rate-limiter@0.3.2` supports it). A sharded fixed window is approximate — one hot tenant can be refused at cap/shards — which is the wrong trade at beta scale. `ponytail:` comment at the config.

## Patterns reused (ladder rung 2 and 5)

- `@convex-dev/migrations` via `convex/migrations.ts` — the shape `vaultSweep.ts` and `reliabilitySweep.ts` already use for unattended table walks; `oneBatchOnly: true` is the synchronous test mode.
- `rateLimiter.check(ctx, "deploymentSpendCents", {count})` — the same call `prepareRequest` makes.
- `ENV_MANIFEST` rows + `env.test.ts`'s bidirectional literal scan.

## Tests

- `proactiveReview.test.ts`: fixtures gain a `users` row per tenant (tenantId is `String(userId)` — `lib/functions.ts:49`); the cron helper runs one batch and drains the spread with fake timers. The tenant-scope source guard still passes: the one remaining query is `by_tenant_kind`.
- `worm.test.ts`: a two-page export (pageSize 2 over 3 rows) → two PutObjects, cursor at the newest ts.
- New `scaleConstants.test.ts`: env parse (bad and good values), expiring-token dedupe across two runs, and a source pin that neither maintenance job collects a whole table any more.
