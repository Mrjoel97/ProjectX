# Phase 03.2.1 Plan 03: Governed Cockpit Tool Set Summary

**The Executive Agent's governed tool set (`buildCockpitTools`) + the index/label agent-context builder (`buildAgentContext`) landed inside `llm.ts` — each tool a thin wrapper preserving its primitive's governance (invalid address bounces at the boundary, remove resolves a 1-based #index server-side, draftBody redacts before drafting, proposePlan reads structural facts from the row), proven by per-tool + static tests.**

## Accomplishments
- `buildCockpitTools(ctx, tenantId, planId)` returns eight AI-SDK `tool()` closures, each wrapping the primitive it governs: `resolveContacts`→`gmail.search`+`rankCandidates`+`writeCandidates`; `addRecipients`/`removeRecipient`/`setRecipients`→`applyRecipientEdit`+`patchPlan`; `setSubject`/`setMode`→`patchPlan`; `draftBody`→`scanText`→`draftCockpit`+`patchPlan`; `proposePlan`→`proposeEmailPlan`.
- The tool IS the enforcement boundary: an invalid address bounces in `applyRecipientEdit` and never enters `recipients` (no patch on bounce); `removeRecipient` takes a 1-based `#index` ONLY and the server resolves the address; `draftBody` runs `scanText` (fail-closed) BEFORE the `draftCockpit` sub-call (GRDL-01/02); `proposePlan` reads recipients/subject/mode/body from the ROW, never from model args.
- `buildAgentContext(plan)` formats the plan state for the model with the `buildRecipientView` index+label view — a raw address never reaches the reasoning surface (§2-D).
- Per-tool tests (`cockpitTools.test.ts`) drive the tools through a live action ctx (the `__invokeCockpitTool` shim) against the REAL primitives offline via `SMOKE::`: validation bounce, index substitution, redaction-before-draft, refs-only resolve summary — the 100%-sampled tool-boundary coverage (Nyquist #2/#3).
- `llmRedaction.test.ts` extended with two static scans: `buildAgentContext` is built from `buildRecipientView` (no raw recipients array interpolated), and `draftBody`'s `scanText` provably precedes `draftCockpit`.

## Decisions Made
- **Read the row via `internal.plans.getById` (by planId), not `api.plans.byThread`.** The plan text suggested `byThread`, but that is a `tenantQuery` requiring identity+threadId; the tools hold a `planId` and run in the trusted node action. A minimal by-id reader is cleaner, tenant-guarded in the tool (`plan.tenantId !== tenantId` → throw), and directly unit-testable. (Deviation Rule 3.)
- **`jsonSchema<T>()` for tool inputs, not zod.** `@pikar/backend` has no zod dependency; adding one for a handful of JSON-schema literals is a needless dependency (ponytail rung 5). `ai`'s `jsonSchema` gives typed `execute` inputs with zero new deps.
- **No patch on a recipient bounce** (per the plan): `addRecipients`/`setRecipients` return the rejected tokens and leave the list untouched; the agent re-asks. Only `removeRecipient` (by index) and clean edits patch.
