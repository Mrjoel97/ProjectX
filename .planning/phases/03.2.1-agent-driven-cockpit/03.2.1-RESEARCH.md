# Phase 03.2.1: Agent-Driven Cockpit — Research

**Source:** This phase was brainstormed into a full design record before planning. The
authoritative design is **`.planning/design/agent-driven-cockpit.md`** — this RESEARCH.md
distills it for the planner and adds the Validation Architecture. Do NOT re-research; plan
against the locked decisions below.

**Phase goal:** Replace the deterministic `emailIntent` FSM cockpit with an Executive Agent
governed tool-loop so the conversation is flexible ("remove Bob", "make it more formal, add
Jane") while every governance invariant survives.

**Requirements:** AGNT-01, AGNT-02 (reshaped — the Executive Agent becomes a real reasoning
tool-loop instead of an inert message store; no new v1 ID).

---

## Locked decisions (from the design record — do not relitigate)

1. **Approach A — full tool-loop.** A new internalAction `runCockpitAgent` runs
   `generateText({ model, tools, system, maxSteps })` inside the existing `"use node"` `llm.ts`
   module (MUST stay the only node module — a second re-triggers the TS circular-inference
   cliff, guidelines §96 / cockpit playbook). `system` = a new `cockpit-agent` skill loaded
   from the registry (no hardcoded prompt, §5).
2. **§2-D redaction.** The agent reasons over recipient **display names + indices** (`#1: Bob`);
   raw email addresses NEVER enter the model context — they live in the `plans` row and are
   substituted server-side inside the tool. Display names reaching the model is already
   accepted (greeting personalization). Refs-only logs (§4), zero-retention provider, and the
   `draftBody` redaction sub-call all stay intact.
3. **Human Approve gate is NOT a tool.** `executePlan` stays a `tenantMutation` and remains the
   sole `workflow.start(deliverApprovedPlan)` call site — the grep-able zero-sends-before-Approve
   invariant. The agent can propose/edit a plan; only a human click sends.
4. **Structural facts never model-invented.** A recipient address is validated (`isValidEmail`)
   or resolved from a real mailbox match (`gmail.search` + `rankCandidates`) — enforced at the
   tool boundary, not by trusting the model.
5. **Clean cutover.** Delete the `emailIntent` FSM (`applyAnswer`/`nextQuestion` state machine +
   the `parseAnswer`/`questionText`/inline-resolve glue in `cockpit.ts`). Keep the pure
   validators (`isValidEmail`, `parseAddress`, `rankCandidates`, contact types) as tool internals.
6. **Loop guardrails reuse today's rails verbatim:** `guardrails.preCall` before `generateText`
   (governed stop → "paused" assistant message, never a DLQ); `maxSteps ≈ 8`; `recordSpend`
   after the call; `isFallbackEligible` → `CHEAP_MODEL` fallback.
7. **Cards unchanged.** `ResolutionCard`, PLAN, and REPORT cards render reactively off the
   `plans` row and do not change. Keep the clickable resolution card (agent triggers the search;
   human clicks a chip → `resolveRecipients`).
8. **Out of scope:** capability #2 (campaign approval) and #3 (standing rules) — deferred to a
   later milestone. No scope/grant abstraction in this phase (approval stays per-plan).

| Tool | Wraps | Governance kept |
|------|-------|-----------------|
| `resolveContacts(name)` | `gmail.search` + `rankCandidates` + `writeCandidates` | headers-only; one `mailbox.searched` refs-only audit |
| `addRecipients` / `removeRecipient` / `setRecipients` | validate → `patchPlan` | `isValidEmail` bounce; names route through `resolveContacts`; ops by **index/label** |
| `setSubject`, `setMode` | `patchPlan` | user-derived, never invented |
| `draftBody` | `scanText` (redact) → `draftCockpit` | redaction-before-model |
| `proposePlan` | `proposeEmailPlan` → status `proposed` | renders PLAN card |
| (not a tool) `executePlan` | human Approve mutation | send stays a human click |

## Suggested plan decomposition (guidance — planner owns the final shape)

Dependency-ordered; the FSM cannot be deleted until the agent loop replaces it (clean cutover):
- **Wave 1 (parallel foundation):** (a) the `cockpit-agent` skill row + seed constant + skills
  static-sync test; (b) the governed tool wrappers as pure-ish units (validation, redaction,
  index/label substitution) with per-tool unit tests — no loop yet.
- **Wave 2:** `runCockpitAgent` — the `generateText` tool-loop wiring the tools, preCall +
  maxSteps + recordSpend + fallback; mock-model integration test (deterministic scripted tool
  calls, no gateway).
- **Wave 3:** cut `sendCockpitMessage` over to the driver; delete the FSM; slim `emailIntent`;
  extend the `SMOKE::` E2E to drive a fixed tool sequence (name → resolution card → edit →
  propose, nothing sent).
- **Wave 4 (checkpoint):** playbook rewrite (§9) + human-verify: a real conversational edit
  ("remove a recipient", "make it more formal") reasons correctly and nothing sends before Approve.

## Pitfalls / risks

- **Node circular-inference cliff:** everything node-side stays in `llm.ts`; annotate explicit
  return types on new actions + runQuery/runAction results (guidelines §96).
- **AI SDK tool-calling shape:** `@convex-dev/agent@0.6.4` demands a v6 LanguageModel while the
  repo pins `ai@7`; the model is driven via the gateway string. Confirm `generateText` + `tools`
  works against the gateway string model id (the existing `generateObject` path does). Do NOT
  bump the pinned component (§6).
- **Deterministic testing of a tool-loop:** use the AI SDK mock model (scripted tool calls) for
  the loop integration test; the `SMOKE::` sentinel drives the offline E2E. No live gateway in CI.
- **Cost:** every turn is now an LLM call (vs one draft). `recordSpend` + daily-budget `preCall`
  must wrap the loop or the budget guardrail is bypassed.
- **Redaction regression:** the static `llmRedaction` scan must be extended so the reasoning
  loop's inputs/logs stay refs-only and raw addresses never reach the model (index/label only).

## Validation Architecture

Per the Nyquist validation strategy — how each phase truth is proven, and at what sampling rate:

| # | Phase truth to prove | Validation method | Sampling / evidence |
|---|----------------------|-------------------|---------------------|
| 1 | Conversational edits work ("remove Bob", "add Jane", "make it formal") | Mock-model loop integration test with scripted tool calls asserting the resulting `plans` row | Per-edit-verb unit coverage + one multi-edit sequence |
| 2 | Structural facts never model-invented | Tool unit tests: a bad address bounces; a name routes to `resolveContacts`; the model cannot write an unvalidated address to `recipients` | Every recipient-mutating tool |
| 3 | Raw addresses never reach the model (§2-D) | Extended static `llmRedaction` scan: the agent context builder emits names + indices only; addresses substituted server-side | Static scan (compile-time-ish) + unit assertion on the context payload |
| 4 | Zero sends before Approve | Grep invariant: `executePlan` is the sole `workflow.start(deliverApprovedPlan)` site and is not a tool; SMOKE E2E asserts no REPORT/send through a full edit→propose flow | Static grep + E2E |
| 5 | Loop is governed (kill-switch / budget / bounded) | Unit test: `preCall` stop → "paused" assistant message (not DLQ); `maxSteps` ceiling → agent asks; `recordSpend` called with usage | Unit tests on `runCockpitAgent` |
| 6 | Refs-only logs hold under the agent loop | Static/unit assertion that audit/DLQ/telemetry payloads from the loop carry hashes/ids/counts only | Extend `llmRedaction` refs-only assertions |
| 7 | AGNT-01/AGNT-02 delivered | Human-verify checkpoint: a real conversational edit reasons correctly on the live backend, nothing sends before Approve | Wave-4 human checkpoint |

**Nyquist note:** the send path is safety-critical, so truths #2/#3/#4 are sampled at 100%
(every tool, every log surface) rather than spot-checked — the human Approve gate is the
backstop, but the tool boundaries are the primary enforcement and must be exhaustively tested.
