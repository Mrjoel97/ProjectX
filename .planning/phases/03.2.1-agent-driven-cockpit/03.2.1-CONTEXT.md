<domain>
## Phase Boundary

**Delivers:** the cockpit conversation engine changes from a deterministic `emailIntent` FSM to
an Executive Agent governed tool-loop, so any reasonable conversational edit works ("remove Bob",
"add Jane", "make it more formal", "change the subject"). Approval stays per-plan. The `plans`
row stays the single source of truth; the cards (ResolutionCard/PLAN/REPORT) are unchanged.

**Does NOT deliver (out of scope, deferred to a later milestone):** capability #2 campaign
approval (approve-once-for-many), capability #3 standing pre-authorized rules, and any
scope/grant approval abstraction. Approval remains a single per-plan human click.
</domain>

<decisions>
## Implementation Decisions (LOCKED)

### Engine
- Full Executive Agent tool-loop (`generateText` + tools) — Approach A. Lives in `llm.ts` (the
  only `"use node"` module; a second re-triggers the TS circular-inference cliff).
- New `cockpit-agent` system prompt loaded from the skills registry — no hardcoded prompt (§5).
- `maxSteps ≈ 8` bounds the loop; ceiling without a proposal → the agent asks the user.

### Redaction (§2-D)
- The agent reasons over recipient **display names + indices** (`#1: Bob`); raw email addresses
  never enter the model context — substituted server-side inside the tools.
- `draftBody` still runs `scanText` (redact) before the drafting sub-call. Logs stay refs-only
  (§4). The LLM provider stays zero-retention/no-training.

### Safety invariants (non-negotiable)
- `executePlan` (send) stays a `tenantMutation`, NEVER a tool — sole `workflow.start` site
  (zero sends before Approve).
- Structural facts (recipients/subject) never model-invented — validated or mailbox-resolved at
  the tool boundary.
- `preCall` (kill-switch + daily-budget) gates the loop; `recordSpend` after each reasoning call.

### Cutover
- Clean cutover: delete the `emailIntent` FSM (`applyAnswer`/`nextQuestion` + `parseAnswer`/
  `questionText`/inline-resolve glue). Keep pure validators (`isValidEmail`, `parseAddress`,
  `rankCandidates`) as tool internals. No dual-engine / no feature flag.

### Testing
- Per-tool unit tests (validation bounce, redaction, index/label substitution, refs-only audit).
- Mock-model loop integration test (scripted tool calls, no gateway).
- Extended `SMOKE::` offline E2E (name → resolution card → edit → propose, nothing sent).

### Claude's Discretion
- Exact plan/wave decomposition (guidance in RESEARCH.md), tool signatures, the `cockpit-agent`
  prompt wording, the `SMOKE::` sentinel grammar extension, and how the agent-context builder
  formats the name+index recipient view.
</decisions>

<specifics>
## Specific Ideas
- Keep the clickable `ResolutionCard` for contact picks (agent triggers the search via
  `resolveContacts`; the human clicks a chip → `resolveRecipients`). Not agent-asks-in-prose.
- Reuse the read-auth fallback (notify `gmail_reconnect` + ask) inside `resolveContacts`.
</specifics>

<deferred>

- #3 standing pre-authorized rules (agent acts within categories set once; policy engine).
- The scope/grant approval abstraction generally — built with #2, not here.
</deferred>
