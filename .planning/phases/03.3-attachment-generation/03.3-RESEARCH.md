## 1. PDF Generation (Convex `"use node"` action)

**Decision: `pdf-lib@1.17.1` (pin exact, no `^`) + a ~50-line line-based markdown renderer.**

Why pdf-lib and not the alternatives — the governing constraint is Convex's esbuild bundler: it inlines all deps and **cannot bundle `fs.readFileSync` / `__dirname` / `*.node` / WASM assets**. So "does the lib read font files at runtime?" is make-or-break:

| Library | Runtime font-file reads? | Verdict |
|---|---|---|
| **pdf-lib 1.17.1** | **No** — Standard-14 metrics are compressed *inside JS modules* (`@pdf-lib/standard-fonts`). Pure-JS transitive deps only. | **CHOSEN** |
| pdfkit | **Yes** — reads `.afm` via `fs`, needs `brfs`. | Rejected (breaks in bundle) |
| pdfmake | No `fs`, but embeds a full Roboto TTF (fontkit path), heavy bundle. | Fallback only |
| @react-pdf/renderer | yoga **WASM** + React reconciler + fontkit. | Rejected (WASM/heavy) |
| jsPDF | No reads, but no advantage over pdf-lib. | Workable, not preferred |

Key facts:
- **No fonts to ship, no fontkit.** Use `StandardFonts.Helvetica`/`-Bold`/`-Oblique`. Do **not** call `embedFont(ttf)` — that pulls `@pdf-lib/fontkit` and forces inlining TTF bytes. Standard-14 covers clean/minimal (title/headings/body/margins, no logo) fully.
- `await doc.save()` returns a `Uint8Array` directly.
- **No markdown lib** — the LLM emits simple markdown (`#/##/###`, `-` bullets, paragraphs). A line-based tokenizer maps them to `drawText` calls. Add `marked` only if nested/inline markdown is ever needed. `// ponytail: line-based md parser; swap to marked tokens if inline/nested markdown needed.`

**Critical pitfall — WinAnsi throws (the #1 failure mode).** With Standard-14 fonts, `drawText` **throws** on the first non-Windows-1252 char (em-dash, curly quote, ellipsis, emoji) — and LLM prose is full of them. Mitigation is twofold and both are required:
1. Sanitize common cases before drawing (`toWinAnsi` map: curly→straight quotes, en/em-dash→`-`, ellipsis→`...`, nbsp→space, drop other non-WinAnsi).
2. Wrap the whole render in try/catch and **treat any throw as "render failed → block approval"** (CONTEXT decision). Never send a silently-empty/partial PDF.

**Determinism for offline SMOKE:** pdf-lib defaults `CreationDate`/`ModDate` to `new Date()` → bytes differ each run. Pin them (`setCreationDate(new Date(0))`, `setModificationDate(new Date(0))`). Assert on `%PDF-` prefix + a length band (byte-identity holds only within a pinned pdf-lib version). Path is pure-CPU (no model/network) → clean fixture.

**Size:** Standard-14 embeds no font data → a 1–3 page doc is a few KB, orders of magnitude under any cap. pdf-lib does **no** text flow/auto-pagination — measure with `font.widthOfTextAtSize()`, word-wrap and add pages manually before `y` underflows the bottom margin.

Reference sketch (`markdownToPdf(title, markdown): Promise<Uint8Array>`): US-Letter 612×792pt, 72pt margins, Helvetica 11pt body / HelveticaBold 18/15/13pt headings, 1.35 leading, manual word-wrap + page-break, `toWinAnsi` on every string, pinned dates. (Full sketch captured in agent output; ~60 lines.)

## 2. Gmail Multipart Attachment Send

**Decision: upgrade `buildMime` to emit `multipart/mixed` when attachments are present; keep the existing `raw` `messages.send` call unchanged; keep a byte-identical zero-attachment fallback.**

Structure (all `\r\n`):
```
To / Subject / MIME-Version: 1.0 / Content-Type: multipart/mixed; boundary="=_pikar_<uuid>"
--boundary
Content-Type: text/plain; charset="UTF-8"  + CTE: base64  → wrapped-76 body
--boundary
Content-Type: application/pdf; name="report.pdf"  + CTE: base64  + Content-Disposition: attachment; filename="report.pdf"  → wrapped-76 bytes
--boundary--            ← trailing "--" is MANDATORY
```

Hard rules:
- **CRLF everywhere**; blank line separates part-headers from part-body; `MIME-Version: 1.0` **once, top-level only**.
- **Base64 wrap at 76 chars** (RFC 2045). Gmail is lenient but intermediary MTAs enforce line caps — cheap insurance.
- **base64url (outer) vs standard base64 (inner) — the classic bug.** The whole message → `raw` field as **url-safe** base64 (`+`→`-`, `/`→`_`, strip `=`). Attachment bytes inside → **standard** base64 (`Content-Transfer-Encoding: base64`). Mixing these corrupts the message.
- **Boundary** = `=_pikar_` + `randomUUID().replace(/-/g,"")` — 122 bits entropy, satisfies the no-`Math.random`/`Date.now` rule (this is a normal node action so `crypto.randomUUID` is fine), and the `=_`/`_` prefix can't collide with base64 content.
- **Filename**: ASCII passes through; non-ASCII → RFC 2047 encoded-word (`=?UTF-8?B?...?=`). Our filenames are app-generated (topic+date, sanitized ASCII) → non-issue in practice. `// ponytail: RFC 2047 encoded-word; ASCII names skip it.`
- **Zero-attachment branch returns the exact legacy string** — assert byte-identity so today's plain-text sends are provably unchanged.

**Size math:** Gmail API `messages.send` accepts up to **35 MB** RFC-2822 message. base64 inflates ~33% + ~1.4% CRLF → budget ~37%; effective PDF budget ≈ 35/1.37 ≈ 25 MB total across parts. There's a practical ~5 MB ceiling on stuffing base64 into a JSON body before Google recommends `uploadType=resumable`. **We avoid all of it** by enforcing a hard per-plan byte cap (recommend **≤ ~8–10 MB total attachments**) — keeps us on the simple `raw` send, no resumable-upload code. `// ponytail: hard cap keeps us on simple raw send; add resumable upload only if a real doc exceeds the cap.` (Our few-KB PDFs are never near this.)

A runnable assert-based self-check (multipart structure + closing delimiter + 2 part-delims + byte-identical empty branch) is specified and belongs beside `buildMime`.

## 3. Convex Storage Round-Trip (generate → send → download)

All five calls verified against current Convex docs:

| call | allowed in | signature |
|---|---|---|
| `ctx.storage.store(blob, {sha256?})` | mutation, **action** | `→ Id<"_storage">` |
| `ctx.storage.get(id)` | **action only** | `→ Blob \| null` |
| `ctx.storage.getUrl(id)` | query, mutation, action | `→ string \| null` |
| `ctx.storage.delete(id)` | mutation, action | `→ void` |
| `ctx.db.system.get("_storage", id)` | query, mutation | `{ size, sha256, contentType, _creationTime }` |

- **Store from action:** `new Blob([bytes], { type: "application/pdf" })` → `ctx.storage.store(blob)`. `blob.type` becomes the stored `contentType` (drives correct preview/download headers). Authoritative size from `_storage` metadata, not `bytes.length`.
- **Retrieve for send:** `send` is an action → `const blob = await ctx.storage.get(id); if(!blob) throw; const buf = Buffer.from(await blob.arrayBuffer())`. Null = deleted/missing → throw → block/DLQ. Not callable from query/mutation.
- **Download URL for cards:** `ctx.storage.getUrl(id)` returns a **stable signed URL** (not short-TTL; lives until `delete`), safe to hand the browser (unguessable bearer capability). Serve it from a **tenant-scoped query** so cross-tenant users never receive it. PLAN card previews the not-yet-sent doc; REPORT card re-downloads the **exact sent bytes** (storage is immutable per id → byte-for-byte guarantee; persist the send-time id, never regenerate for the report).
- **Metadata + lifecycle:** hang an inline denormalized array on the **plan** row (`generated`/`attachments`: `{storageId, filename, mimeType, size}[]`) — lazier for the PLAN card (filename/size render with no join). The seam agent notes the existing `attachments` **table** can also carry these (its `requestId` is optional); pick one at plan time — see Open Question O1. **Delete on the events that drop the ref** (remove-attachment, plan-discard, regenerate-supersede) in the same mutation that splices the ref — storage is **not** GC'd; orphans bill forever. **Never delete an id a `sent` REPORT references** (retention window).
- **Isolation:** `Id<"_storage">` is **global, not tenant-scoped**. Enforce on the ref row (`plans`/`attachments` carry `tenantId`), mirroring `requests.get`. Never hand back a `getUrl` for a client-supplied storageId without a ref-ownership check.
- **Audit stays refs-only (§4):** log `storageId`/`size`/`sha256`/`filename`/counts — **never** bytes, base64, or the signed URL (the URL is a bearer capability; logging it leaks file access).

## Validation Architecture

Per-requirement observable proof that CKPT-02 holds. Every check is offline-runnable (SMOKE/asserts) except the one human-verify on the live Gmail backend, matching the phase's prior close-out discipline.

| # | Claim to validate | Method | Signal (pass) |
|---|---|---|---|
| V1 | markdown→PDF renders valid, deterministic bytes | assert-based self-check beside `markdownToPdf` | `bytes` starts `%PDF-`, length in band, pinned-date run reproducible |
| V2 | WinAnsi/smart-punctuation input does not silently corrupt | unit: feed curly quotes/em-dash/emoji | sanitized output renders; un-sanitizable → throw caught → render-failed |
| V3 | `buildMime` multipart is structurally correct | assert-based self-check beside `buildMime` | `multipart/mixed`, N part-delims, mandatory `--boundary--`, base64url-outer/base64-inner |
| V4 | Zero-attachment send is byte-identical to today | assert in same self-check | `buildMimeWithAttachments(...,[]) === legacy string` |
| V5 | Storage round-trip: store→get→bytes match; getUrl tenant-guarded | convex-test unit | stored id retrievable in action; `getUrl` only via tenant query; cross-tenant denied |
| V6 | Attachment rides the governed fan-out to every recipient w/ audit/telemetry/DLQ | `smoke:fanout` extended with a SMOKE attachment | each recipient's send carries the part; forced-fail row dead-letters alone; terminals write-once; **zero bytes/filename-content/URL in any log plane** |
| V7 | Render failure / over-cap → plan NOT approvable | unit on `proposePlan` gate | proposePlan refuses when an attachment is render-failed or total > byte cap |
| V8 | Budget/kill-switch during generation → pause-as-data, no DLQ, not approvable | `smoke:guardrails` extended | `preCall` stop returns paused reply; no attachment; no dead-letter |

| V10 | Live human-verify | one real send on the Gmail-connected dev backend | recipient receives the email with the PDF attached; audit shows refs only |

**Governance invariants that must not regress:** no raw email content, no file bytes, no base64, no signed URL in any audit/DLQ/telemetry payload (§4); model never sees raw addresses (§2-D); document prompt loaded from the registry, not hardcoded (§5); nothing sends before Approve; `proposePlan` reads the row not model args.

## Open Questions (for the planner to resolve — none block planning)

- **O1 — ref home:** plan-row inline `attachments` array (lazier for the card) vs rows in the existing `attachments` table (its `requestId` is optional). Storage agent recommends inline-on-plan for display; seam agent notes `attachmentRefs` at fan-out wants `Id<"attachments">`. **Likely both:** inline `{storageId,filename,mimeType,size}` on the plan for the card + create `attachments` rows at fan-out to populate `requests.attachmentRefs` (or store `attachments` rows at generation and keep only their ids on the plan). Planner picks the single lower-friction shape.
- **O2 — byte-cap value:** pick the hard per-plan cap (research suggests ≤ ~8–10 MB to stay off the resumable path; our PDFs are KBs). Enforce at generation (refuse over-cap → block approval), not at send.
- **O3 — regenerate semantics:** does regenerate supersede-in-place (delete old storage id, new id, same slot) or append? CONTEXT implies supersede (one doc, iterated) — confirm the storage-delete ordering (delete old after new ref persists).
- **O4 — "suggests" surface:** how the agent *suggests* an attachment without generating (a chat prompt/one question), given generation only happens on user confirm. Encode in the cockpit-agent skill prompt (v3) + document-drafter skill; no new tool needed.
