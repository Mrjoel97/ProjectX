# Phase 3.3: Attachment Generation - Context

**Gathered:** 2026-07-13
**Status:** Ready for planning

<domain>
## Phase Boundary

The Executive Agent can generate a document (PDF), attach it to an outgoing email within an
**approved plan**, and that attachment flows through the **existing governed send** (Gmail +
audit + telemetry + DLQ) and appears on the PLAN/REPORT cards. Requirement **CKPT-02** (distinct
from INTK-02, which is *inbound* attachment ingestion — not this phase).

Fixed by prior phases (not re-litigated here):
- New capability = a **new governed tool** in the agent tool-loop (like `draftBody`/`proposePlan`
  in `buildCockpitTools`), NOT a rewrite of the send spine.
- Generation prompt loads from the **skills registry** (§5 — no hardcoded prompts); model output
  is `scanText`-redacted before use (§2-D / §4).
- **One attachment set, same for all recipients** this slice — per-recipient tailoring is Phase 3.4.
- **Nothing sends before Approve.** `proposePlan` reads structural facts from the plan ROW, never
  from model args.
- Attachment audit/DLQ payloads stay **refs-only** (filename / hash / size / count — never contents, §4).

</domain>

<decisions>
## Implementation Decisions

### Document format
- **PDF.** LLM produces the document content; it is rendered to PDF (markdown→PDF pipeline and
  the specific JS PDF library are Claude's discretion — no binary/native dep; a pure-JS lib
  usable inside a `"use node"` Convex action).
- **Clean/minimal styling** — title, headings, body, generous margins, professional typography.
  **No logo / no letterhead.** (Branded/letterhead PDF is deferred, see below.)
- **Render failure → block approval.** If PDF rendering fails at generation time, the plan is
  NOT approvable; the agent reports the failure in chat (retryable). Consistent with "nothing
  sends on a broken assumption." Do NOT silently fall back to a text attachment.

### When the agent attaches
- **Asked + suggests.** The user can explicitly ask for a document ("attach a one-pager on X"),
  AND the agent MAY suggest attaching one when useful — but it **only generates after the user
  confirms**. Never attaches unprompted / on its own judgment.
- **Multiple attachments per plan allowed.** One plan can carry several generated documents.
  (Plan row therefore holds an array of attachment refs; `buildMime` assembles N parts.)

### PLAN card control (pre-approval review surface)
- **Download / preview** — the card shows filename(s) and lets the user open/download the actual
  PDF to inspect it before approving (verify the real document, not just its name).
- **Regenerate** — the user can ask the agent to redo a document with new instructions before
  approving; the card updates.
- **Remove** — the user can drop a generated attachment from the plan before approving
  (important because the agent can suggest/add them).

### Document content & naming
- **General-purpose, from the user's instruction** — the agent writes whatever the user describes
  (proposal, summary, agenda, cover letter, …). A **single drafter skill** in the registry handles
  all of it. Fixed document templates are deferred.
- **Filename = topic + date**, deterministic (e.g. `proposal-2026-07-13.pdf`) derived from the
  document topic + date. No LLM naming step. Sanitize to a safe filename; collision-safe suffix.

### Size / length cap
- **Both:** a **soft length target** in the drafter skill (aim ~1–3 pages, natural length) PLUS a
  **hard byte backstop** guard so a runaway generation can never push a plan past Gmail's ~25MB
  message limit (block/reject over the byte cap — never truncate a document into a broken PDF).

### Regeneration limit
- **No fixed count.** Regeneration is bounded only by the **existing governed spend / kill-switch
  budget** (same governance as drafting — `recordSpend` / `preCall`). No new limit code. Pre-approval only.

### REPORT card display
- **Delivered + download.** Each per-recipient REPORT row shows the message was delivered **with**
  its attachment filename(s) AND lets the user re-download the exact file that was sent. Backed by
  the existing per-recipient report row + audit ref.

### Budget / kill-switch behavior during generation
- **Pause as data.** If document generation hits the governed budget/kill-switch, reuse the
  existing `preCall` pattern: the agent returns a paused reply (as DATA) explaining the stop —
  **no attachment, no DLQ**, plan not approvable until resolved. No new branch; identical to how
  drafting is governed today.

### Claude's Discretion
- markdown→PDF rendering pipeline and the specific pure-JS PDF library.
- Exact PDF typography / margins / page setup within "clean/minimal."
- Exact plan-row schema shape for the attachment-ref array and how it fans out to request rows.
- Filename sanitization + collision-suffix details; the hard byte-cap threshold value.
- Whether generation is a distinct tool call vs. folded into an existing one (as long as it's a
  governed tool and the enforcement boundaries hold).

</decisions>

<specifics>
## Specific Ideas

- The attachment tool should mirror the existing governed-tool pattern exactly: a thin wrapper
  that IS the enforcement boundary (like `draftBody` → `scanText` redaction, `proposePlan` reads
  the row not model args).
- "Nothing sends on a broken assumption" extends to attachments: a plan with a failed-to-render
  or over-cap document is simply not approvable — never a degraded silent send.
- REPORT should let the user re-download the *exact bytes that were sent*, not a regenerated copy.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `convex/llm.ts` `buildCockpitTools(ctx, tenantId, planId)` — the governed Executive-Agent tool
  set (`resolveContacts`, `addRecipients`, `setRecipients`, `removeRecipient`, `setSubject`,
  `draftBody`, `proposePlan`). The new `generateAttachment`/regenerate/remove tools slot in here;
  each tool is the enforcement boundary. `runCockpitAgent` is the `generateText` tool-loop.
- `convex/llm.ts` `draftCockpit` — pattern for a registry-skill-backed LLM content generator that
  is redaction-safe by construction (SMOKE:: offline path, DEFAULT→CHEAP fallback, caller owns
  correlation-scoped logging). The document drafter skill mirrors `email-drafter`.
- **Convex file storage already in use** — `convex/requests.ts` `generateUploadUrl` +
  `storageId: v.id("_storage")`; schema `attachments` table (`tenantId`, `requestId`, `storageId`,
  `filename`, `mimeType`, `size`, `extracted`) indexed `by_request`. Outbound generated PDFs can
  store via `ctx.storage` and reuse/extend this metadata shape ("file metadata only — the agent
  sees filename/mimeType/size, never contents").
- `convex/gmail.ts` `send` (internalAction, `"use node"`) — reads the request row via
  `internal.gmailAuth.getForDelivery` (`{tenantId, recipient, subject, body}`) and builds the MIME
  via `buildMime(to, subject, body)` (currently `text/plain`). **This is the multipart seam:**
  `buildMime` upgrades to `multipart/mixed` when the row carries attachment ref(s); the send path,
  retrier, audit (`gmail.sent` message-id ref), telemetry, and onComplete-DLQ are otherwise reused
  VERBATIM (the whole point of CKPT-02).
- `convex/plans.ts` — content-plane adapter (`insertPlan`/`patchPlan`/`setPlanStatus`,
  `byThread`/`reportForPlan` reactive readers, `getById` for tools). Attachment refs hang on the
  plan row here; `reportForPlan` is a live projection that already joins audit by correlationId.
- `deliverApprovedPlan` durable workflow — fans out `gmail.send` once per recipient row (shared
  planId, per-row correlationId). Attachment refs propagate plan → per-request rows at fan-out seed
  (owned by `executePlan`), so every recipient's send carries the same document(s).
- Governance spine: `preCall` (kill-switch/budget → pause-as-data), `recordSpend` (priced usage),
  `scanText` (PII redaction), skills registry `seedSkills` publish-on-change (new drafter skill
  seeds like `cockpit-agent`/`email-drafter`).

### Established Patterns
- No hardcoded prompts (§5): the document-generation prompt is a versioned registry skill
  (canonical `.md` + byte-identical derived `.ts` + `seedSkills` row + static-sync test, like the
  other skills).
- Redact-then-write (§4) + §2-D: model never sees raw addresses; generated content is
  `scanText`-redacted; audit/DLQ payloads carry refs/hashes/counts only.
- Tools read structural facts from the ROW (`internal.plans.getById`), not from model args —
  the enforcement invariant for the send-safety spine.
- SMOKE:: offline sentinels drive deterministic tests without a model/Gmail call (extend to a
  `SMOKE::` attachment fixture — deterministic bytes, no render/model call — for the E2E and
  fan-out smoke).

### Integration Points
- New governed tool(s) registered in `buildCockpitTools`; drafter skill seeded via `seedSkills`.
- Plan row schema (`plans` table) gains an attachment-ref array; `attachments`/storage for bytes.
- `gmail.ts` `buildMime` + `getForDelivery` carry attachment refs through to the multipart send.
- PLAN/REPORT card UI (`apps/web` cockpit) gains attachment rows with download/preview + regenerate
  + remove (PLAN) and delivered-with-download (REPORT).

</code_context>

<deferred>
## Deferred Ideas

- **Branded / letterhead PDF** (logo, tenant brand assets, teal styling) — a later polish; this
  slice is clean/minimal.
- **Fixed document templates** (proposal/summary/cover-letter types) — this slice is
  general-purpose from-instruction with a single drafter skill.
- **Per-recipient tailored attachments** — already Phase 3.4 (per-recipient personalization); this
  slice sends the same document set to all recipients.
- **Inbound attachment ingestion / extraction** (INTK-02, `attachments.extracted`) — separate
  requirement/phase; not CKPT-02.

</deferred>
