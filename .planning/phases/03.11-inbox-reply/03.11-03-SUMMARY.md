# Phase 3.11 Plan 03: Delivery Threading Spine Summary

**The four reply fields now survive read → plan → requests → getForDelivery → buildMime → send, so a reply lands in-thread: `buildMime` emits In-Reply-To/References, `send` POSTs threadId, `getForDelivery` projects the anchor (Pitfall 4 closed), `executePlan` copies `plan.replyThreadId → request.threadId`, and the new `getReplyTarget` surfaces the target's From/Subject/threadId + RFC Message-ID header server-side — the governed single-arm fan-out unchanged, the only missing piece the tool that WRITES the fields (Plan 04).**

## Accomplishments
- `buildMime` (gmail.ts) gained an optional `threading?: { inReplyTo; references }` param — emits `In-Reply-To:` + `References:` header lines after Subject in BOTH the zero-attachment and multipart branches; absent → byte-identical to the pre-3.11 output (`threadHeaders` spreads to nothing; the V4 identity test still passes). The values carry the RFC 5322 Message-ID HEADER (angle-bracketed), never the Gmail id (Pitfall 2).
- `gmail.send` builds `threading` from the request row and POSTs `{ raw, threadId }` when `req.threadId` is set, `{ raw }` otherwise — RFC headers in `raw` are load-bearing, threadId is reinforcement (Pitfall 1; verified live in Plan 06, deliberately NOT unit-asserted here).
- `getForDelivery` (gmailAuth.ts) — the hand-built projection (Pitfall 4) — now returns `threadId`/`inReplyTo`/`references` from the request, so send actually sees them.
- `executePlan` (cockpit.ts) copies `plan.replyThreadId → request.threadId` (the GMAIL thread, distinct from `plan.threadId` the agent thread) plus `plan.inReplyTo`/`plan.references` onto EVERY seeded row. The single-arm-site fan-out (`startFanout`, the sole `workflow.start`) is unchanged.
- New `gmail.getReplyTarget` — a fixture-first target-header read: given a message id it returns From/Subject/threadId + the RFC Message-ID anchor (`inReplyTo` = Message-ID header, `references` = original References + Message-ID via `buildReferences`). Refs-only to the server-side caller (Plan 04's tool), no audit here (the reply tool owns correlation, §2-D/§4).
- All fields optional → every seam no-ops on a non-reply plan (the non-reply control test proves rows carry none and getForDelivery returns none).

## Decisions Made
- **getForDelivery in Task 1, not Task 2:** `send` (Task 1) reads `req.threadId`/`req.inReplyTo`/`req.references`; the hand-built `getForDelivery` projection must expose those or send does not typecheck. So the projection travelled with send in Task 1 (keeping every commit tsc-clean), and Task 2's `cockpit.test.ts` still proves the full plan→requests→getForDelivery spine end-to-end.
- **A dedicated getReplyTarget, not an extension of an existing read:** the untrusted BODY read (`fetchInboxBodies`, toolless-only) and the refs-only HEADER read (`getReplyTarget`) are different trust planes; keeping them in separate actions keeps the llmRedaction static-scan boundaries clean and gives Plan 04 a focused single-message header read.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] getForDelivery projection landed in Task 1, not Task 2**
- **Found during:** Task 1 (implementing send's threadId POST)
- **Issue:** The plan assigns `getForDelivery` to Task 2, but Task 1's `send` reads the threading fields off the `getForDelivery` projection. Without the projection returning them, `send` does not typecheck (the projection is hand-built, not a whole-row return — new fields are invisible unless added).
- **Fix:** Added `threadId`/`inReplyTo`/`references` to the `getForDelivery` return in Task 1 alongside the `send` change (they are one delivery-read seam). Task 2's `cockpit.test.ts` still asserts `getForDelivery` returns them end-to-end.
- **Files modified:** packages/backend/convex/gmailAuth.ts
- **Committed in:** `0a08052` (Task 1 GREEN)

### Design choice within plan latitude (not a fix)

**2. The target-header read is a new dedicated `getReplyTarget` action.** The plan's action said "extend the read plane (listInbox/fetchInboxBodies/search — whichever the Plan 04 tool will call)." A separate action was chosen instead of overloading an existing one, to keep the untrusted-body plane and the refs-only-header plane in distinct blocks (trust-boundary separation, and `fetchInboxBodies`' clean `{id, body}` contract that `briefInbox` relies on stays intact). Same fixture-first ordering and refs-only discipline as the existing reads.
