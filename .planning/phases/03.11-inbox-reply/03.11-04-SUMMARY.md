# Phase 3.11 Plan 04: replyToMessage Tool Summary

**The one governed tool that turns "reply to X" into a real threaded reply in ONE turn: it resolves the target SERVER-SIDE from a fuzzy `{intent, sender?, subject?, range?}` ref (the loop has no message ids), sets the recipient BY REF (`recipients=[fromAddr]` + a display-name label, no panel), the `Re:` subject + the four threading fields, drafts the body TOOLLESSLY from the untrusted original, and hands the loop LABELS/COUNTS only — with the body-and-From boundary held by mutation-verified static scans.**

## Accomplishments
- `patchPlan` (plans.ts) accepts the four optional threading fields (`replyToMessageId`/`replyThreadId`/`inReplyTo`/`references`) via the same drop-undefined patch; `resetPlan` clears all four explicitly (Pitfall 6 — a reply then "start over" must not leave a stale thread that silently threads the next fresh compose).
- `replyToMessage` added to `buildCockpitTools`: resolves via `internal.gmail.listInbox` (full metas with ids, server-side) filtered by sender/subject substring, newest-first; 0 -> "couldn't find that message", 2+ -> list candidates BY LABEL and ask, exactly 1 -> proceed (the `resolveContacts` no-guess discipline; never substitute, never guess).
- On a single match it reads the anchor via `internal.gmail.getReplyTarget`, then `patchPlan`s `recipients=[address]`, `recipientNames={[address]: displayName}` (the UAT-F1 label flow — NO `writeCandidates`/panel), `subject=Re: <stripRePrefix(subject)>`, and the four threading fields; fetches the original body via `fetchInboxBodies` and drafts the body through the toolless `internal.llm.draftReply`; returns the display-name label + Re: subject only.
- `stripRePrefix` pure helper (`^(?:\s*re\s*:\s*)+` -> once) so a reply subject is `Re: <subj>` exactly once, never "Re: Re:".
- Three mutation-verified `llmRedaction` scans: the fetched original body flows ONLY into `draftReply` (never a return/audit), the resolved From address reaches `patchPlan` ONLY (never a return interpolation), and `draftReply` is structurally toolless (`generateText`, no `tools:`). Each mutation (leak body into a return / leak `${address}` into the return / add `tools:{}` to draftReply) was confirmed to trip the scan RED, then reverted.

## Decisions Made
- **`intent` is a required tool arg:** `draftReply(tenantId, safeText, originalBody)` needs the user's reply wording as `safeText`. The plan's shorthand `replyToMessage({sender?,subject?,range?})` omitted it, but step 5 (scanText the reply intent -> draftReply) requires it — without it the tool could only echo a generic reply. Added `intent` (required) alongside the fuzzy-ref args.
- **Return echoes the real Re: subject:** subjects already cross to the loop via `listInbox`/`briefInbox`, and the must-have forbids only the From address, Message-ID, and body — so echoing `Re: <subject>` aids the agent's confirmation without breaking the boundary.
- **replyToMessage stays in BOTH tool sets (normal + omitRecipientEdits):** like `resolveContacts`, it sets recipients from a governed server-side source, not a fabrication; leaving it present keeps the UAT-F2 "withholding removes EXACTLY the three recipient-mutating keys" invariant intact.
