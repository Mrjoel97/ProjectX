<objective>
Orchestrate an N-hundred-document folder ingest without starving the delivery spine, without
fabricating failures, and without ever leaving a reservation stranded.

The fan-out mechanism already exists — each file is its own `vaultUpload` scheduling its own
`extractDoc`. What is wrong at folder scale is **throttling** (the raw scheduler is bounded only by
the deployment's job concurrency, 8 on S16, and `ingestDoc` shares the app's single
`WorkflowManager` at default parallelism 10 with `executePlan`/`deliverApprovedPlan`) and **the
watchdog** (armed at SCHEDULE time, so a healthy document queued for an hour is marked
`extraction_stalled` — which would put failures that never happened into the "honest" manifest).

Output: `vaultFolders.ts`, a named `vaultIngestPool`, watchdog arming moved to work-start, counter-
based completion hooked into the two terminal writers, and cancel.
</objective>

<task type="auto">
  <name>Task 3: vaultFolders.ts — create, reserve, complete, cancel</name>
  <files>packages/backend/convex/vaultFolders.ts</files>
  <action>
Use the tenant-scoped wrappers from `./lib/functions` (§2). Public surface:

- **`createFolder`** (tenantMutation) — insert at `status:"reserving"` with zeroed counters, return
  the id. The client then uploads members with `folderId` set.
- **`reserveFolder`** (tenantMutation) — calls `internal.guardrails.reserveFolder` (plan 03) with the
  re-derived manifest; on `ok` patch `reservedCents`/`reservedAt` and flip to `"ingesting"`; on
  refusal patch `"refused"` and return the governed refusal object unchanged. **Nothing is ingested
  on refusal — refuse-intact is proven by absence.**
- **`bumpFolder`** (internal helper, NOT exported as a function) — called from `markReady`/
  `markFailed`; increments `terminalCount` (and `failedCount`), and when
  `terminalCount === memberCount` performs the completion transition **once**, guarded by a CAS on
  `status === "ingesting"`.
- **Completion transition** does exactly three things, in order: (1)
  `internal.guardrails.settleFolder` (refund), (2) schedule the digest build (plan 06 fills this in —
  leave a named internal call and a TODO-free comment pointing at it), (3) flip to `"complete"`,
  which is what unseals the members.
- **`cancelFolder`** (tenantMutation) — `pool.cancelAll` for the folder's enqueued work,
  `settleFolder`, then **DELETE the folder row**. Touch ZERO `vaultDocuments` rows.

Comments that must be present:
- **Cancel deletes rather than marking.** A `cancelled` status would keep members sealed forever,
  because the seal is read through the folder row. Members keep a dangling `folderId`; **every folder
  read treats an unresolvable id as "no folder"** — a lenient join. Get that wrong and cancelled
  documents become invisible, the exact inverse of the locked decision.
- **Why not clear `folderId` on cancel:** a patch rewrites the whole document; 400 rows × up to
  400 KB of `text` blows the 16 MiB written-per-transaction cap. It would need a batched
  `scheduler.runAfter(0, self)` loop, and the dangling id already reads as folder-less.
- **In-flight actions are not killable** (workflow README: in-progress `step.runAction` calls finish).
  Cancel means **"no NEW spend"**; the refund settles after the last in-flight action, and refunding
  on the click would over-refund by whatever the running pages then charge.
  </action>

<task type="auto">
  <name>Task 4: Hook completion into the two terminal writers, and handle dedup</name>
  <files>packages/backend/convex/vault.ts</files>
  <action>
In `markReady` (`:473`) and `markFailed` (`:481`), after the existing patch:
```typescript
const doc = await ctx.db.get(vaultDocId);
if (doc?.folderId) await bumpFolder(ctx, doc.folderId, /* failed? */);
```
One place, all nine callers. Prefer the **counter** over a status-index probe: O(1), and it never
reads a `text` blob.

**Dedup is the trap that stops folders completing.** `vaultUpload` (`:177-183`) and
`vaultIngestText` (`:118-124`) return an EXISTING row on a `contentHash` match and start **no
workflow** — so no terminal event ever fires for that file. Therefore:
1. `memberCount` counts rows **actually inserted**, never files submitted. The upload path must
   report per-file whether it inserted or deduped, and the folder's count is incremented only on a
   real insert.
2. **Never assign `folderId` on a dedup hit.** Patching it would silently annex a pre-existing
   document into the folder — and, worse, seal a document the user could ground on yesterday. Report
   it as `deduped` in the manifest instead.
3. A document already carrying a `folderId` is never re-parented.

**Move `contentHash` computation server-side for the folder rail.** `Dropzone` currently buffers each
whole file in browser heap to hash it, and SubtleCrypto has no streaming digest — at a 200 MB cap
across a 1.5 GB folder that is not viable. The bytes are already in `ctx.storage`; hash there. The
single-file path keeps its client hash (unchanged, and it saves an upload). Record the accepted cost:
a folder cannot skip uploading a duplicate it has not yet sent.
  </action>
