# 15.3-09 — the Google Drive rail (VALT-13)

The last plan of phase 15.3. Executed inline (no workflow), six tasks, **$0 spent** — nothing in
this plan makes a model call.

## What shipped

- **`DRIVE_READONLY_SCOPE` appended to `GOOGLE_SCOPES`** (`packages/core/src/calendar.ts`), reaching
  both `gmailAuth.buildAuthorizeUrl` and the `http.ts` callback default. `drive.file` was rejected:
  it needs the Google Picker SDK from `apis.google.com` plus an API key and app id, which buys
  nothing while consent is in Testing mode.
- **`gmailStatus.driveReady`** — a derived boolean, never the raw scope string. It exists because
  `connected` cannot distinguish "connected before the widening" from "Drive-ready".
- **`packages/vault/src/driveEstimate.ts`** — `estimatedBytesFor`, which **never returns 0**.
- **`packages/backend/convex/vaultDrive.ts`** — the whole rail: enumerate → classify → diff →
  reserve → per-file export → land → fan-in → dispatch.
- **A Drive entry point on the vault page**, gated on `driveReady`; when false it routes to the
  existing reconnect flow rather than showing a Drive error.

## The order, which is the design

1. scope check → `reauth`, **before** `freshAccessToken` and before any network call;
2. enumerate (metadata only);
3. **reserve, from that metadata**;
4. only then download.

Step 3 before step 4 is the one place this rail is deliberately ordered differently from the upload
rail, where the browser has already sent the bytes by the time a manifest exists. `files.list`
returns count, size and type before a byte is exported, so a refused Drive folder is refused without
downloading a gigabyte first — refuse-intact stops being a property we assert and becomes one proven
by absence.

## Two locked decisions corrected on facts (CONTEXT §A6/§A7)

- **The byte cap DOES apply.** Non-native files are downloaded into a ~512 MB action; a 600 MB video
  OOMs it before any cap could refuse it. Enforced from `size` metadata during pre-flight.
- **Drive reports no `size` for Google-native docs.** Reading a missing size as 0 prices a 500-Doc
  folder at $0, reserves nothing, and trips the wall halfway through. `driveEstimate.test.ts` tests
  that exact branch — the single check keeping the reservation invariant true on this rail.

## What was found while building

- **The dup early-return trap, as the plan predicted.** `vaultUpload`'s dedup branch is correct
  there and wrong here. `landFile` attaches **identity without membership**: `driveFileId` yes,
  `folderId` never — annexing a pre-existing document into an `ingesting` folder would seal one the
  user could ground on yesterday.
- **The fan-in must count failures.** `driveLandedCount` counts inserted, deduped, updated *or
  failed to export*. Counting only insertions hangs the folder in `reserving` forever the first time
  one export 404s, holding a reservation nothing settles — there is no folder-level watchdog.
- **`"use node"` had to go.** The 01-07 rule is that a `"use node"` module holds only actions, and
  this rail's fan-in is a mutation. Nothing here needs a Node builtin.
- **A trust-boundary hole the plan did not name.** The folder id is interpolated into Drive's `q=`
  SEARCH EXPRESSION, which `URLSearchParams` percent-encoding does not protect. `DRIVE_ID_RE` guards
  it before anything else runs.
- **My own scan was vacuous, and the mutation caught it.** The audit name-leak check tested for
  `name:`; the mutation added the shorthand `name,` and walked straight through. Fixed to a
  property-position regex, then re-run RED.

## Deviations from the plan, stated

1. **No self-scheduling enumeration continuation.** The walk is bounded below the 10-minute action
   limit by `DRIVE_MAX_FILES` (2,000) / `DRIVE_MAX_FOLDERS` (200) — at `pageSize=1000` that is a
   handful of round-trips, not minutes. `ponytail:` comment names the ceiling and the upgrade path
   (the walk is already an explicit queue, so it lifts out unchanged).
2. **`vaultFolders.ts` was touched** (not in `files_modified`): `tryComplete` gained `export`, one
   word, so the Drive fan-in reuses the completion transition instead of duplicating it.
3. **`schema.ts` was touched** (not in `files_modified`): three optional `vaultFolders` fields
   (`driveFolderId`, `driveExpectedCount`, `driveLandedCount`). Zero tables, zero indexes, zero
   migration, zero backfill. The `vaultDocuments` half was already provisioned by 15.3-01.
4. **Export-time failure codes go to `audit`** (`vault.drive.unreadable`), not to the folder card.
   Ceiling and upgrade path stated at the site.

## Follow-up, 2026-08-05 — the picker, and what the live run actually proved

Two follow-up commits after the plan closed, both owner-directed, plus a partial live gate.

### `d677d84` — we render the Drive picker ourselves

The plan's entry point was a "paste a Drive folder link" field. The owner rejected it on sight, and
was right: if the user has to open Drive, navigate to the folder and copy its URL, they are already
in Drive and may as well download the files and drag them in. The integration only earns its place
if the folders are reachable from inside the vault. `DriveBrowser.tsx` replaces it — breadcrumb plus
a list, one level at a time, backed by a new `vaultDrive.listDriveFolders`.

**The Picker SDK is NOT mounted, and that is not a compromise.** Google's Picker exists to make the
narrow `drive.file` scope usable: that scope grants access only to files handed over through the
Picker itself. We took `drive.readonly`, so `files.list` already returns the folders and we draw
them with our own tokens — no external `apis.google.com` script, no API key, no app id, no CSP hole,
no new dependency. **The scope choice is what made the picker cheap. Do not "restore" the Picker
without re-opening the scope decision first.**

**The root level is THREE lists, not one** (`drives.list` + `'root' in parents` + `sharedWithMe`).
Collapse them and a user whose company runs on a shared drive is told they have no folders.

`listDriveFolders` repeats the import's scope-before-refresh ordering, and `dispatchGuard.test.ts`
now LOOPS over both Drive actions — the browse is what a pre-widening tenant hits FIRST, so pinning
only the import would have put the 403 on the very first click. Mutation RUN on `listDriveFolders`
specifically → RED.

### `39522a1` — the picker shows the FILES, from the same single request

Browsing listed folders only, so an empty folder and one holding 200 documents looked identical
until you pressed Import. **Two real folders were probed that way during the live run**, which is
how the gap surfaced. The fix is cheaper than what it replaced: drop the `mimeType='...folder'`
filter, keep ONE `files.list` per level, split server-side. Files are shown but never clickable (the
unit of import is the folder), each carrying a `readable` verdict from `classifyOne` — **the same
function the import runs**, extracted for this reuse so the picker and the import cannot disagree.

The count is the LEVEL; the import is the TREE. The copy says so.

**THE MUTATION CAUGHT MY OWN TEST BEING VACUOUS — the second time this plan.** Restoring the
folder-only filter left all 13 tests GREEN: a stub answers with whatever it was told to answer, so
asserting on the RESPONSE cannot see a query that changed. The test now reads `q` off
`fetchSpy.mock.calls`. **Rule: when a stubbed test covers behaviour that lives in the REQUEST,
assert on the request.** Same class as the shared-drive params, which is why those are a source scan.

### THE LIVE GATE IS PARTIAL. Read this before claiming VALT-13.

Run against a real Google account on the local deployment, 2026-08-05.

**PROVEN LIVE:**
- The scope widening reaches a real consent, and the grant now carries `drive.readonly`.
- **The reauth gate, against a genuinely pre-widening token** — the vault rendered "Your Google
  connection was made before Drive access existed" while Gmail and Calendar kept working. That is
  `driveReady` distinguishing `connected` from Drive-ready, live, exactly as designed.
- `files.list` against real Drive: ten real root folders listed.
- Drill-down and the breadcrumb: `ISO9001-QMS` returned its real subfolders.
- The `empty_folder` guard: it refused rather than creating an empty folder and calling it complete.
- The file listing: "No files at this level, plus everything inside 18 subfolders", and
  "Nothing here — no folders and no files" — which is what settled that the earlier `empty_folder`
  returns were CORRECT and not an enumeration bug.

**NEVER RUN, AND STILL OWED:**
1. **The import path itself.** No document has ever been exported from Drive and landed in the
   vault. Every folder opened during the gate was empty, so `exportOne` → `landFile` → the fan-in →
   `walkFolderMembers` → the digest has never executed against real bytes. **Zero cents have been
   spent on this rail.** The reservation, the dedup branch, the re-import diff and the folder
   completion are unit-proven and live-unproven.
2. **The shared-drive half.** No shared drive surfaced for that account, so `drives.list` returned
   none and `supportsAllDrives` / `includeItemsFromAllDrives` have still never been exercised against
   a real one. This is the failure whose live symptom is a silently empty folder, and it is the
   reason the source scan exists. **A stub proves we SEND the parameters; only a real shared drive
   proves Google honours them.**

VALT-13 and the Phase-15.3 checkbox therefore stay UNTICKED — the Phase-17 `human_needed`
convention. One import of a populated folder closes item 1; access to any shared drive closes item 2.
