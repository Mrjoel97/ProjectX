<objective>
Build the budget rail the phase's central invariant depends on: **estimate and reserve the whole
folder before the first cent, or refuse it intact.**

Three things make this harder than "add a window". (1) The rate limiter has **no refund API** — a
negative `count` credits the window, which is an undocumented arithmetic property. (2) That credit is
applied AFTER the capacity clamp, so a refund issued across the 24h window roll **manufactures
budget** — verified at 2900 against a capacity of 2500. (3) Ingest currently spends
`dailySpendCents`, the COCKPIT's $5 window, at six sites — so today a folder both starves the cockpit
and can be refused halfway by it.

Output: `INGEST_DAILY_BUDGET_CENTS` ($25) + its deployment sibling, a reserve/settle pair with a
clamped idempotent refund, a pure estimator, and an optional rail selector threaded from
`startIngest`.
</objective>

`check` · `limit({count, reserve, throws})` · `getValue` · `reset`. **There is no refund call.**

Verified arithmetic (`calculateRateLimit`): `value = min(state.value + rate*elapsed, capacity) - count`.
So a negative `count` credits — and the clamp precedes the subtraction, which is the money bug.
`getValue` returns `{value, config}` where capacity is `config.capacity ?? config.rate`.

non-reserve call — including `check()`. `media.ts` never hits this only because
`MEDIA_JOB_CAP_USD` ($3.50) sits below its $10 window.

  <name>Task 4: reserveFolder + settleFolder</name>
  <files>packages/backend/convex/guardrails.ts</files>
  <action>
**`reserveFolder`** — an internalMutation cloning `media.reserveJobInner`'s ORDER exactly:

1. Kill switch first.
2. **Re-derive `estCents` from the file manifest args** — never accept a client-supplied number from
   the pre-flight card.
3. **`if (estCents > INGEST_DAILY_BUDGET_CENTS) return { ok:false, reason:"over_folder_cap", … }`
   BEFORE any limiter call.** `check()` THROWS above capacity; without this the locked plain-language
   refusal becomes a stack trace. Same guard for the deployment ceiling.
4. `check` BOTH windows, then `limit(..., { reserve: true })` BOTH — **in ONE mutation**. Split them
   and two concurrent folders both pass their checks.
5. Return a discriminated result, never a throw:
   `{ ok:false, reason, estCents, remainingCents, shortfallCents, fileCount, totalBytes }` — all
   counts/ids, so the same object is legal as an insert-only `audit.log` payload (§3/§4).
   **No filenames in the audit payload.**

**`settleFolder`** — the ONE place a reservation is released. Called by folder completion AND by
cancel; one mechanism, not two.

1. Read the folder row; **CAS**: if `reservedCents` is already cleared, return a no-op. This runs in
   the same transaction as the credit — workflow `onComplete` can be re-entered.
2. Read `getValue` for the tenant's ingest window; compute
   `clampRefundCents(reservedCents, value, config.capacity ?? config.rate)`.
3. **Skip the refund entirely if the window rolled** — compare `folder.reservedAt` against the
   current window start. A refund into a window that never paid is free budget.
4. `limit(..., { count: -refund, reserve: true })` when refund > 0, then clear `reservedCents`.

Put a `ponytail:` comment on the negative-count call naming the ceiling — *"this is an arithmetic
property of rate-limiter@0.3.2, not an API; upgrade path is a real spend table"* — and pointing at
`media.ts`'s opposite decision.
