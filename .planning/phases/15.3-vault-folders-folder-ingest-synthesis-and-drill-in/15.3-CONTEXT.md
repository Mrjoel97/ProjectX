a bounded budget, synthesised into a folder-level digest that is itself a grounded vault document,

## Implementation Decisions

Everything in this section is a LOCKED owner decision from the 2026-08-02 discussion. The only

### The budget wall — the invariant this phase exists to protect

The governing rule, unchanged from the roadmap: **estimate and reserve for the WHOLE folder before
the first document, or refuse the folder intact.** A half-ingested folder is worse than a refused
one, because the agent grounds on it confidently without knowing what is missing.

- **Over budget ⇒ REFUSE INTACT.** Nothing is ingested. The refusal NAMES THE NUMBERS in plain
  language: the estimate, the remaining budget, and the shortfall. No partial ingest, no
  auto-trimmed subset, no cross-day queue, no silently-degraded processing. All three alternatives
  were considered and rejected.
- **Folder ingest gets its OWN named budget window.** A third pair alongside the existing
  `dailySpendCents` and `mediaSpendCents` (`guardrails.ts:56-62`) — direct precedent, including the
  rule that one window's spend never moves another's. **A folder upload must never be able to
  starve the cockpit agent the user relies on for actual work.**
- **The number: $25/day per tenant.** Deliberately above both existing windows ($5 tokens, $10
  media) because a folder upload is a bursty one-off onboarding-shaped event, not a daily habit.
  Accepted consequence: worst-case per-tenant daily exposure rises to $40. The always-on pre-flight
  summary is what keeps that honest.
- **HARD RESERVE, then refund the remainder.** Deduct the full estimate before document 1; release
  whatever was not spent when the folder completes. The folder can never trip the wall mid-run —
  that is the entire point — and a conservative estimator does not quietly cost the user budget
  they never used. "Check, then spend as you go" is explicitly REJECTED: concurrent activity (a
  cockpit turn, a media job) could eat the headroom and strand the folder mid-run, which is the
  exact shape the invariant forbids.
- **Pre-flight summary ALWAYS, never conditional.** Before the upload commits, show: file count,
  total size, estimated cost, estimated time-to-ready, and what will be skipped — then an explicit
  Start. Rationale: the ~8-minute byte transfer for 1.5 GB (see the SLO correction below) must be
  honest up front rather than a progress bar that appears to hang, and the refusal path needs a
  natural home.

### Ingest lifecycle — sealed, honest, cancellable

- **SEALED until complete.** A folder's documents are excluded from retrieval until the whole
  folder finishes ingesting. This resolves the standing tension in favour of the invariant: 15.2's
  SLO correction argues for time-to-first-useful, but grounding on a fraction of a company's
  records is the failure this phase exists to prevent. Accepted cost: the folder is dead weight for
  the duration of its ingest window.
- **Partial failure ⇒ the folder COMPLETES with an honest manifest.** Individual documents may fail
  (unsupported format, stalled extraction) — 15.2 already guarantees per-doc failure is loud and
  terminal. The folder is done and usable, carries a visible count of what failed and why, and
  **the digest itself states what it could not read.** The folder is not lying; it is disclosing.
  All-or-nothing was rejected (one corrupt file in 300 must not discard a $3 ingest) and so was a
  percentage threshold (arbitrary, and the user has to learn what it means).
- **Cancel ⇒ keep the documents, discard the folder.** Already-ingested documents remain in the
  vault as ordinary folder-less documents; the folder record is discarded; the unspent reservation
  is released. This leans on the zero-migration idiom — a document with no `folderId` is exactly
  what it is today.
  - **DERIVED CONSEQUENCE, deliberate, do not "fix" it:** because sealing is a property of the
    FOLDER, cancelled documents become groundable immediately once the folder is discarded. This is
    consistent — they no longer claim to be a complete folder — and it is the reason cancellation
    does not waste the money already spent.

### The folder digest

- **The digest IS ITSELF a vault document** (carve-out, locked before this session): it embeds,
  retrieves and grounds through the existing rails. There is no second plane.
- **Retrieval: digest AND members, digest competes normally.** No boost, no ranking special case,
  no digest-only mode. The retrieval path currently has no special cases and gains none here; if
  the digest is genuinely the best match for a broad question, similarity will say so.
- **Content: structure + synthesis + an explicit unreadable list.** Three parts, all required:
  1. What the folder IS — a manifest: counts, kinds, date range, and a per-document one-line
     identity.
  2. What the folder SAYS — the synthesised cross-document business content.
  3. What could NOT be read — the failed/unsupported documents, stated plainly.
  Part 3 is what makes the "honest manifest" decision land in the artifact the agent actually
  reads. Narrative-only and manifest-only were both rejected.
- **Staleness: stale banner + ONE-CLICK REBUILD.** When member documents change, the digest is
  marked stale and the user rebuilds on click. This is deliberately the Phase 17.1 Stage-1 idiom —
  a bounded set-difference against the documents the digest was synthesised from, surfaced as a
  banner (`blueprint.ts:553` `unincorporatedFor`, `DRIFT_SCAN_CAP = 100`). Costs nothing until the
  user asks; the user is never surprised by a charge. Auto-regeneration was rejected precisely
  because tidying a folder could silently fire a dozen model calls.
- **Provenance: a NEW `origin` literal for the digest** (e.g. `folder_digest`), added to the
  existing union at `schema.ts:835`.
  - **This is a correctness requirement, not a taxonomy preference.** `origin: "agent"` means
    agent-authored and is STRUCTURALLY EXCLUDED from vault retrieval — tagging the digest that way
    would silently make the entire feature ungroundable. Leaving `origin` absent (⇒ user-supplied)
    would ground correctly but makes a synthesised artifact indistinguishable from a document the
    user actually uploaded, which matters for blueprint drift and for trust. Reusing
    `agent_promoted` was rejected as overloading a literal minted for a deferred promote button.
  - The union was declared with future literals in mind, so this is a patch, not a migration.

### Document identity classification — IN, as a first-class classifier

Item (a) of the two carve-out deferrals the roadmap dropped. **In scope, and NOT merely as a
by-product of digest synthesis** — the owner explicitly chose the standalone form, which means it
applies to SINGLE-FILE uploads too, not only to documents inside a folder.

- **Vocabulary: a CLOSED `docType` union in `packages/` PLUS a free-text identity line.**
  - The closed union (P&L, balance sheet, contract, invoice, deck, policy, report, correspondence,
    spreadsheet-other, unclassified, …) is queryable and cannot drift. It follows the established
    repo idiom for closed sets (`TIERS`, `VAULT_CATEGORIES`, `REVENUE_STAGES`).
  - The free-text line is the human-readable identity — "2025 P&L", not "a spreadsheet" — and is
    what the grid and preview display.
  - Free-text-ONLY was rejected: nothing downstream could filter or reason over it, and it would
    reintroduce the string-matching defect class Phase 15.1 was built to eliminate.
  - The union MUST include an explicit unclassified member; a document matching nothing is
    unclassified, never forced to a nearest match.
- **The classifier PROMPT is a `skills` registry row** (CLAUDE.md §5 — non-negotiable, not a
  discussion outcome). The vocabulary is code; the prompt is data.
- **User-correctable, and the correction WINS.** Type and identity line are editable in
  `PreviewModal` where the user already inspects documents. A user-set value is marked as user-set
  and is NEVER overwritten by a later re-classification. Rationale: the label feeds the digest and
  grounding, so a wrong guess is not cosmetic — without this it is a permanent lie in the grounding
  corpus.

### Google Drive export rail — IN

Item (b) of the dropped deferrals. **In scope**, on the owner's reasoning that for many businesses
the folder they would upload already lives in Drive, so folder ingest without Drive misses the real
use case.

- **One-time import, 1:1, re-import on demand.** Picking a Drive folder creates ONE `vaultFolder`
  and exports its documents once. A visible "refresh from Drive" re-runs the import and shows what
  changed. Continuous sync is REJECTED for this phase: change-watch subscriptions, renewal, conflict
  handling and unbounded background spend against a budget the user is not watching. On-demand
  re-import composes exactly with the stale-digest banner already chosen.
- **Bounded by the SAME $25 window, estimated from Drive metadata.** The Drive API returns file
  count, sizes and types BEFORE exporting anything, so the same pre-flight estimate, hard
  reservation and intact refusal apply unchanged. One budget rail, one refusal path, one invariant —
  the only difference is where the size numbers come from.
  - The 200 MB byte cap does not apply (nothing is uploaded), but the expensive work — extraction,
    graph, embedding — is identical on both rails, which is why the budget bound is shared rather
    than loosened.

### Size caps

- Folder upload at **1–1.5 GB** total; per-kind file cap raised **100 MiB → 200 MB**.
- **Video stays at 25 MB** — bounded by the transcription API's hard limit, not our choice
  (`constants.ts:9`, `vaultTranscribe.ts:43`). Carried forward, not re-decided.

### Drill-in UI

- **Folders are cards in the SAME grid.** A folder renders as a card among documents; clicking it
  replaces the grid contents with that folder's documents plus a breadcrumb back. Reuses `DocGrid`
  wholesale, introduces no new navigation concept, and folder-less documents keep behaving exactly
  as they do today — matching the zero-migration spirit of the optional `folderId`.
- A separate folders rail and a digest-first `PreviewModal` were both rejected — the former makes
  `CategoryTabs`' meaning ambiguous inside a folder, the latter is a cramped place to browse 200
  documents.

Research surfaced seven collisions with the locked decisions above (`15.3-RESEARCH.md` §A) and
sixteen further blockers (§B). The owner was presented with them and instructed **"I want it built
and built now"** rather than ruling item by item.

**These are therefore CLAUDE'S CALLS, made under an explicit build-now instruction.** Each is
recorded with its reasoning and is REVERSIBLE — the owner may overrule any of them, and a plan that
contradicts one must say so rather than drift. They have the same binding force on the planner as the

## Resolutions to §A collisions

### A1 + A5 — the refund mechanism, and reversing `media.ts`
**DECIDED: use the negative-count refund, and reverse the media rail's written no-refund position
deliberately and visibly.**

The refund is `rateLimiter.limit(..., { count: -refundCents, reserve: true })`. It is an undocumented
arithmetic property of `@convex-dev/rate-limiter@0.3.2`, not an API. Accepted because the alternative
(a real spend ledger) is a larger build than the entire budget rail, and `reset()` — the only
supported alternative — nukes the tenant's whole window.

Required with it:
- A `ponytail:` comment on the refund call naming the ceiling ("this is arithmetic, not an API") and
  the upgrade path (a spend table).
- A test that goes RED if negative-count stops crediting (RESEARCH guarantee 1).
- **`media.ts:278-281` must be amended in the same phase** with a pointer explaining that the ingest
  rail deliberately takes the opposite position, and why: media over-reserves by CENTS (bounded by
  `MEDIA_JOB_CAP_USD`), ingest over-reserves by DOLLARS (the estimator cannot see page counts). Both
  rails then state the same fact from their own side, and neither reads as a bug to the next person.
- The same explanation goes in `docs/playbooks/guardrails.md`.

### A2 — the cross-midnight money bug
**DECIDED: mandatory clamp, as a pure function, tested pure.**
`refund = max(0, min(unspent, capacity - currentValue))` read via `getValue`, living in
`packages/vault/src/ingestEstimate.ts` and unit-tested there. The settle mutation additionally CASes
on the folder row in the same transaction. Non-negotiable: this is a money bug, and the clamp is the
only thing standing between a tenant and free budget for timing an upload across midnight.

### A3 — the throwing `check()`
**DECIDED: the ceiling comparison precedes every limiter call.** `estCents > INGEST_DAILY_BUDGET_CENTS`
returns the governed refusal directly. The test asserts it RESOLVES rather than throws.

### A4 — the estimator that cannot see the cost
**DECIDED: two-stage estimate. This refines the ESTIMATE; it does not weaken the reserve rule.**

1. **Instant card** from bytes + mime at pick time — what the user sees before uploading.
2. **Free local probe** after bytes land and BEFORE the first paid call: `unpdf`/`pdf-lib` page count
   plus the existing `MIN_CHARS_PER_PAGE` text-layer heuristic. **The reservation is taken off the
   probed number.**

"Reserve before document 1" is preserved in the only sense that matters — **before the first cent**.
The alternative (assume every PDF is scanned) refuses ~100-file PDF folders that would really cost
under $1, which would make the feature useless on day one.
⚠ The pre-flight card must show the stage-1 number as an ESTIMATE and the stage-2 number as the
amount actually reserved; if stage 2 lands materially higher, the refusal fires there and must read
as a refusal, not as a surprise charge.

### A6 — "the byte cap does not apply to Drive" is factually wrong
**DECIDED: the Drive rail enforces the SAME per-file byte cap, from `size` metadata, BEFORE download.**
A locked decision is corrected on a factual error, not on preference: non-native Drive files are
downloaded into a ~512 MB action, so a 600 MB video OOMs before any cap could refuse it. Files over
cap are pre-classified into the unreadable bucket during pre-flight, so the count the user approves
matches what imports.

### A7 — Drive metadata has no size for native docs
**DECIDED: conservative per-kind constants, and a test on that exact branch.**
`estimatedBytesFor` returns `size ?? DRIVE_NATIVE_ASSUMED_BYTES[kind]` (Doc 256 KB, Slides 512 KB,
Sheet 1 MB). Over-estimation is safe under reserve-then-refund. The "missing size never yields 0"
assert is the single check keeping the reservation invariant true on the Drive rail.

## Scheduled-job concurrency — resolved 2026-08-03

RESEARCH §2.10 flagged the deployment scheduled-job concurrency class (8 on S16 vs 256 on S256, a
30× swing) as unverified, and as something every time estimate depends on. **Checked: the project has
NO cloud deployment.** `npx convex deployments` reports `Type: local`
(`local:local-joel_feruzi-pikar_ai_50c69-1`), so there is no class to read — the number the research
asked for does not exist yet.

**That dissolves the risk rather than leaving it open, because plan 04 moves ingest off the raw
scheduler onto a named workpool with an EXPLICIT `maxParallelism`.** Once ingest runs on our own
pool, WE set the concurrency; the deployment class is only an upper bound we must stay under.
`VAULT_INGEST_PARALLELISM = 6` is below 8, so it is safe on the smallest class Convex offers and on
every larger one.

Therefore:

- The pre-flight "READY IN" estimate (plan 07) is computed from `VAULT_INGEST_PARALLELISM`, **never**
  from an assumed deployment class.
- `VAULT_INGEST_PARALLELISM` must stay STRICTLY BELOW the smallest class (8). Raising it above that
  is a deployment-class decision, not a tuning decision — assert the bound in `constants.test.ts`.
- Record in `docs/playbooks/vault.md` that provisioning a cloud deployment is the point at which this
  number may be revisited, and that the estimate is calibrated against observed throughput (the
  RESEARCH live-probe item), not derived on paper.

2. **Wave 1** — the budget rail (A1–A5, B3, B14).
3. **Wave 2** — folder model, ingest orchestration, sealing, completion (B2, B6, B7, B13, B15).
4. **Wave 3** — the digest (B4) and the drill-in UI (B9–B12).
5. **Wave 4** — the classifier.
6. **Wave 5** — the Drive rail (A6, A7, B8).

If execution stalls, waves 0–3 are a coherent, shippable "Vault Folders" and waves 4–5 are the
additions. That is the recorded fallback boundary honoured as SEQUENCING rather than as a split.
