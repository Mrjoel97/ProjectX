<objective>
Enforce the locked "sealed until complete" rule at **every** place a folder member could reach a
reader.

Sealing cannot be done the way `origin:"agent"` exclusion is done — that works by never calling
`startIngest`, and folder members must genuinely embed and graph-extract during the sealed window. So
sealing is an explicit filter, and research found it needs **three sites, not one**. Missing the
third is the expensive one: sealed members reach `status:"ready"` at ingest step 6, so a folder
mid-ingest would inflate the blueprint drift banner on **every cockpit turn**.

Output: one predicate, applied at `runVaultGround` (both seeds and graph neighbours), `vaultSearch`,
and `unincorporatedFor`.
</objective>

<task type="auto">
  <name>Task 1: The seal predicate, as one shared internal read</name>
  <files>packages/backend/convex/vaultGround.ts</files>
  <action>
Write ONE tenant-scoped internal helper that takes a batch of doc ids and returns the subset that is
sealed:

```
sealed(doc) === doc.folderId != null && folderRow(doc.folderId)?.status === "ingesting"
```

Three properties this exact shape gives you, all of them load-bearing:
- **A folder row that does not exist ⇒ NOT sealed.** That is what makes cancelled documents
  (whose folder was deleted) immediately groundable, per the locked decision. A predicate written as
  `status !== "complete"` instead would seal them **forever** — a one-word bug.
- `"refused"` folders have no members by construction, so they need no special case.
- Batch the folder lookups (a `Map` keyed by folderId) — a per-document `ctx.db.get` inside a
  retrieval hot path is the read amplification this phase has already been bitten by twice.
  </action>
