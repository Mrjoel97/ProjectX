## C. Accepted, documented limitations

- **The graph leak is partial and cannot be closed cheaply.** Sealed members' entities enter the
  shared tenant graph at ingest step 4, raising `graphNodes.degree` (feeding the blueprint spine) and
  creating edges between unsealed docs. That is **structural/metadata leakage, not content leakage**;
  closing it means deferring `upsertGraph` to folder completion, which breaks the per-doc workflow.
  The locked decision says "excluded from retrieval", which the doc-id filter satisfies literally. §3.6
- **In-flight actions are not killable**, so cancel means "no NEW spend" and the refund settles after
  the last in-flight action. §2.6
- **7-day refresh tokens (Testing mode)** make "refresh from Drive" fragile by construction — a copy
  and routing requirement, not a bug to fix here. §5.7
- **`files.export` has a hard 10 MB ceiling** — large Docs/Sheets land in the "could not be read"
  bucket. Budget for that bucket being non-empty on real company folders. §5.7

## 1. The budget wall — estimate, reservation, refund, intact refusal

### 1.1 The third window (exact shape)

In `guardrails.ts`, beside the media pair at `:43`/`:49`:

```ts
export const INGEST_DAILY_BUDGET_CENTS = 2_500;      // $25/day PER TENANT (owner decision)
export const DEPLOYMENT_INGEST_BUDGET_CENTS = 25_000; // $250/day — the SAME 10x ratio both existing rails hold
```

and two entries inside `new RateLimiter(components.rateLimiter, {...})` at `:51-68`, copying the
media pair verbatim:

```ts
ingestSpendCents:           { kind: "fixed window", rate: INGEST_DAILY_BUDGET_CENTS,     period: 24 * HOUR },
deploymentIngestSpendCents: { kind: "fixed window", rate: DEPLOYMENT_INGEST_BUDGET_CENTS, period: 24 * HOUR },
```

- **Do NOT set `maxReserved`.** Leaving it unset is what stops `limit({reserve:true})` from throwing
  regardless of count — `validateRequest` only enforces `maxReserved` on the reserve path.
- **No `convex.config.ts` change** — `app.use(rateLimiter)` is already registered.
- `@convex-dev/rate-limiter` is pinned EXACT at `0.3.2` (pre-1.0). CLAUDE.md §6 applies with extra
  force here: the refund depends on undocumented arithmetic, so a bump can silently stop refunds.

### 1.2 Reserve and refund — what the component can and cannot do

Client surface: `check`, `limit({count, reserve, throws})`, `getValue`, `reset`. **There is no
release/refund/credit call.** `reserve: true` only permits the value to go negative; it is not a
hold that can later be released.

Refund is therefore a negative `count`:

```ts
await rateLimiter.limit(ctx, "ingestSpendCents", { key: tenantId, count: -refundCents, reserve: true })
```

Verified against the shipped `_checkRateLimitInternal`: reserve 900 → value 1600; refund −400 in the
same window → 2000 exactly. **Refund −400 after a window rollover → 2900 against a capacity of 2500.**

**Two mandatory guards:**

1. **CLAMP (money bug).** `calculateRateLimit` computes
   `value = min(state.value + rate*elapsedWindows, capacity) - count` — the clamp precedes the
   subtraction. In the settle mutation:
   ```ts
   const { value, config } = await rateLimiter.getValue(ctx, "ingestSpendCents", { key: tenantId })
   const cap    = config.capacity ?? config.rate
   const refund = Math.max(0, Math.min(unspentCents, cap - value))   // skip the limit call when 0
   ```
   Put this arithmetic in a pure exported function in `packages/vault` (§1) so it is unit-testable
   without Convex.
2. **IDEMPOTENCY.** The settle mutation must CAS on a folder field (e.g. clear `reservedCents`) in
   the SAME transaction as the negative `limit`, exactly as `onIngestComplete` (`vaultIngest.ts:69`)
   guards on `doc?.status !== "processing"`. Workflow `onComplete` can be re-entered.

**Fallback if the planner rejects negative-count:** a ledger row on the folder
(`vaultFolders.spentCents`) changes only *what number* is refunded — giving budget back to a
rate-limiter window still requires the negative call. The only refund-free alternative is
`reset(name, {key})`, which nukes the tenant's entire window. Negative-count is load-bearing either way.

**Recommended settle shape (laziest correct).** Reserve `estCents` up front; per-document work
charges the ingest window through the normal `recordSpend` path; at completion refund the FULL
`estCents` (clamped). Net window movement equals actual spend, needs no per-doc counter, adds no OCC
hotspot on the folder row from the 6-wide OCR fan-out, and the refund is a fixed known number so the
idempotency guard is trivial. Transiently the tenant looks 2× spent — the fail-closed direction, and
consistent with the repo's existing over-reserve bias.

### 1.3 The intact-refusal ordering trap

`check()` does not return `ok:false` when `count > capacity` — `validateRequest` **throws**
`Rate limit ingestSpendCents count 3000 exceeds 2500`. So the reserve mutation must do:

```ts
if (estCents > INGEST_DAILY_BUDGET_CENTS)
  return { ok:false, reason:"over_folder_cap", estCents, remainingCents, shortfallCents }
```

**before** touching the limiter. Same guard for the deployment ceiling. `media.ts` never hits this
only because `MEDIA_JOB_CAP_USD` ($3.50) sits below its $10 window; ingest has no per-job cap.

Refusal payload — a discriminated governed result, never a throw, mirroring `ReserveRefusal`
(`media.ts:53-66`): `{ ok:false, reason, estCents, remainingCents, shortfallCents, fileCount,
totalBytes }`. All counts/ids, so the same object is legal as an `audit.log` payload (§3/§4).
**No filenames in the audit payload.**

### 1.4 The verified cost model

| Work | Cost | Notes |
|---|---|---|
| Extract txt/md/csv, office (docx/xlsx/pptx), text-layer PDF | **free** | pure-TS `officeText`/`xlsText`; `unpdf` returns `path:'text_layer'` with no spend |
| Embed | **free today** | `text-embedding-3-small` is ABSENT from `PRICING` (`cost.ts:43-47`) ⇒ `priceUsage` errs ⇒ `vaultRag.ts:127` returns 0 |
| Graph extract | **~$0.006/doc ceiling** | one `gpt-4o-mini` call over `capGraphText` ≤ 120k chars ≈ 30k tokens |
| Transcription | `ceil(min) × $0.006` | bounded by `VAULT_VIDEO_CAP_BYTES` = 25 MB |
| **Scanned PDF / image OCR** | **~$0.005/page ⇒ ≤ ~$0.25/doc** | ONE `gpt-4o-mini` vision call PER PAGE, capped at `VAULT_EXTRACT_PAGE_CAP = 50` (`vaultExtract.ts:269`) |

**Therefore:** a 300-file text/office folder ≈ **$1.80** worst case; a 100-file scanned-PDF folder ≈
**$25**. The $25/day window is calibrated to the OCR path and to nothing else.

The estimator must not hardcode "embedding is free" — add an `EMBED_USD_PER_MTOK` term set to 0 with
a comment, not a silent omission.

### 1.5 What pre-flight can actually see (collision #4)

A browser folder pick (`<input webkitdirectory>` / DataTransfer) yields per File only: `name`,
`size`, `type` (browser-guessed, often empty), `webkitRelativePath`, `lastModified`. **Not page
count. Not text-layer presence. Not audio duration** — the two variables that swing cost 40–50×.
`sniff.ts` runs server-side on stored bytes, not at pick time.

**Recommended two-stage estimate** (CONTEXT gives Claude discretion over "the cost-estimation model
itself"):

1. bytes + mime for the instant pre-flight card;
2. a **FREE local probe** after bytes land but BEFORE any paid call — `unpdf` `getDocumentProxy`
   page count (`pdf-lib` `getPageCount` at `vaultExtract.ts:146`) plus the existing
   `MIN_CHARS_PER_PAGE` text-layer heuristic (`vaultExtract.ts:257-258`) — and reserve off the
   probed number.

This still satisfies "reserve before document 1" in the only sense that matters: **before the first
cent**. Surface it to the owner as a refinement of the estimate, not a change to the reserve rule.

### 1.6 The rail selector — the biggest shared-code change in the phase

**Today, ingest spends the COCKPIT's budget.** Three `preCall` gates and three `recordSpend` sites in
the ingest path all run against `dailySpendCents`:

| Gate | Charge |
|---|---|
| `vaultIngest.ts:113` | `vaultIngest.ts:134` |
| `vaultExtract.ts:296-297` | `vaultExtract.ts:125` (per OCR page) |
| `vaultTranscribe.ts:56` | `vaultTranscribe.ts:93` |

So as shipped, a folder ingest both **starves the cockpit** and **can be refused halfway** by an
unrelated cockpit turn — the exact failure this phase exists to forbid. Both locked rules require
threading a rail selector down from `startIngest`.

Minimum change: **ONE OPTIONAL arg** on `preCall` and `recordSpend` (e.g. `rail?: "ingest"`,
`reserved?: boolean`), threaded from `startIngest` / `scheduleExtraction` (`vault.ts:62`) through the
workflow args.

- For **reserved** folder work, `preCall` checks the **kill switch ONLY** and skips both spend
  windows — the money is already reserved, so checking the ingest window would refuse precisely when
  the reservation drove it to 0.
- `recordSpend` for that work moves the **ingest** window, never `dailySpendCents`.
- Single-file (folder-less) uploads keep today's behaviour on the token rail — CONTEXT puts only
  FOLDER ingest on the $25 window.
- The arg MUST be optional: `preCall`/`recordSpend` have ~15 call sites across `blueprint.ts`,
  `intake.ts`, `llm.ts`, `dispatch.ts`, `media.ts` and the vault modules. And `dispatch.ts:365`'s
  envelope read (`remainingDailyCents`) must NOT start seeing the ingest window, or every sub-agent
  envelope silently resizes.

`startIngest` (`vaultIngest.ts:30-47`) is the SOLE workflow starter with 8 call sites (`vault.ts`
:113/:141/:203/:615, `onboarding.ts:500`, `research.ts:184`, `evaluations.ts:978`, `voice.ts`) — an
OPTIONAL rail/folder arg there leaves every caller unchanged.

### 1.7 Where the reservation races

- **Two folders at once** — safe PROVIDED check+limit happen in ONE mutation (the `media.ts:262-266`
  rule) and that mutation **re-derives `estCents` from the file manifest**, never trusting a
  client-supplied number from the pre-flight card. Both contend on one `rateLimits` row; Convex
  serializes and the loser is refused.
- **Folder + cockpit turn / folder + media job** — structurally impossible once rails are separated.
  Today they DO interact (§1.6).
- **Deployment ingest ceiling is keyless** ⇒ one row shared by every tenant ⇒ the real OCC point.
  Do **not** reach for `shards`: sharding makes `getValue` a sampled approximation, and the
  pre-flight card promises an honest "remaining" number.
- **The OCR fan-out** — `PAGE_BATCH_SIZE = 6` concurrent `recordSpend` mutations against ONE
  `rateLimits` row. `vaultExtract.ts:74-79` already documents this as why the batch is 6 and not 50.
  Routing to the ingest window MOVES the contention; it does not remove it.
- **Stale pre-flight** — the card's number is read at T, the reservation happens at T+8min of byte
  transfer. The reserve mutation refuses with fresh numbers; **design the Start button's failure
  state for this**, it is not an edge case.

### 1.8 Reservation leak (no folder-level watchdog exists)

A folder whose workflow dies after reserving leaves $X held with no refund for 24h.
`onIngestComplete` (`vaultIngest.ts:56`) handles per-DOCUMENT terminality only. `retryStuckIngests`
(`vaultIngest.ts:85`) is the sweep precedent and `EXTRACTION_WATCHDOG_MS` (15 min) the existing stall
threshold. **A folder-reservation watchdog must exist or "refund the remainder" is a promise the
system can silently break.** The locked Cancel path ("release the unspent reservation") hits the same
settle function — one mechanism, not two.

## 2. Ingest orchestration at folder scale

### 2.1 The byte transfer is not a Convex-function problem — but it has its own ceiling

`Dropzone.ingestOne` (`Dropzone.tsx:51-81`) does `requests.generateUploadUrl()` → browser
`fetch(POST)` straight to Convex storage → `vault.vaultUpload`. That POST is browser→storage, so the
10-minute node-action ceiling and `CALL_TIMEOUT_MS` never bind it.

**What DOES bind it, and is not recorded anywhere in this repo:** the upload POST has a **2-minute
timeout** per file and the upload URL expires after 1 hour. At 200 MB that demands **~13.3 Mbit/s
sustained upstream**. The 200 MB cap is only reachable on fast links, so the raise needs an honest
per-file failure path — not just edited literals.

**The cap raise has THREE edit sites, not two:**

| Site | What |
|---|---|
| `packages/vault/src/constants.ts:2` | `VAULT_FILE_CAP_BYTES` |
| `Dropzone.tsx:25` | duplicated literal |
| `Dropzone.tsx:174` | user-facing copy "Up to 100 MB per file" |

(plus the server error string at `vault.ts:173`, "max 100 MB"). **Laziest correct fix: delete the
client duplicate and import the constant.** Use a leaf subpath if the barrel drags Node-only code
into the client bundle — the `@pikar/vault/officeText` precedent at `vaultExtract.ts:29,32`.

### 2.2 Folder picking

Native platform feature, no library: `<input type="file" webkitdirectory multiple>`. Each `File` then
carries `file.webkitRelativePath`, giving the folder-relative path for the manifest.

- **Trap:** `webkitdirectory` is NOT in `@types/react` 19.2.17's `InputHTMLAttributes`. Pass it as
  `{...{ webkitdirectory: "" } as Record<string,string>}` or set it on the ref in an effect, or the
  web typecheck fails.
- **Folder drag-and-drop is a different, much larger API** (`DataTransferItem.webkitGetAsEntry()` +
  recursive `FileSystemDirectoryReader.readEntries` paging at 100 entries/call). Recommend: drop =
  files-only, folder = picker-only, with a `ponytail:` comment naming the upgrade path.
- `handleFiles` (`:83-100`) is already a sequential `for … await` loop — the right shape for 1.5 GB
  (one 200 MB ArrayBuffer live at a time; `hashBytes` needs the whole buffer, WebCrypto has no
  streaming digest). It currently swallows per-file errors into one `setError` that each failure
  overwrites — that must change for a manifest to be honest.
- **Do NOT** POST an archive and unzip server-side: `ctx.storage.get` returns a Blob into action
  memory and 1.5 GB cannot be held in a 10-minute node action.

### 2.3 Fan-out — the mechanism already exists; throttling is what's wrong

Each file is already its own `vaultUpload` mutation scheduling its own `extractDoc` + watchdog via
`vault.scheduleExtraction` (`vault.ts:62-80`). Two things break at folder scale:

1. **`scheduleExtraction` uses the raw scheduler**, unthrottled from the app side and bounded only by
   the deployment's scheduled-job concurrency class (**8 on S16**, 256 on S256). 400 queued
   `extractDoc` node actions sit in front of every delivery/cron job in the deployment.
2. **The `ingestDoc` workflow runs on the app's ONE `WorkflowManager`** (`convex/index.ts:6`) with
   **no `maxParallelism` ⇒ workpool default 10**, shared with `executePlan` / `deliverApprovedPlan`.
   A folder ingest structurally starves the delivery spine.

**Recommended fix — a dedicated pool, already in the dependency set:**
`@convex-dev/workpool@0.4.7` sits in `devDependencies` (unregistered). Move it to `dependencies`
(exact pin, §6), `app.use(workpool, { name: "vaultIngestPool" })` in `convex.config.ts`,
`new Workpool(components.vaultIngestPool, { maxParallelism: 4-8 })`, and swap the
`ctx.scheduler.runAfter(0, …extractDoc)` inside `scheduleExtraction:72` for `pool.enqueueAction`.
**ONE call site changes**; all three callers (`vaultUpload`, `sweepPendingExtraction`,
`retryExtraction`) inherit it.

- **Do NOT** raise the `WorkflowManager`'s parallelism instead — it applies to EVERY workflow in the
  app and would widen the delivery spine too. Platform guidance: avoid exceeding ~100 total
  parallelism across all workpools and workflows.
- **A folder-level WORKFLOW is the wrong tool.** The workflow journal is capped at 8 MiB, steps pass
  ≤1 MB total per execution, and 400 sequential `step.runAction` calls serialise the folder behind
  the shared pool with determinism-violation risk on redeploy. **Keep one workflow per document; make
  the folder a plain DB row + counter.**

### 2.4 OCC — 15.2's stated ceiling genuinely breaks here

`PAGE_BATCH_SIZE = 6` was chosen (`vaultExtract.ts:74-79`) as the OCC-contention width against ONE
keyless rate-limit row, reasoning about **one document at a time**. At folder scale it is
`pool width × 6` concurrent `recordSpend` writers on the same row — ~48 writers. OCC retries surface
as extraction failures under load.

**Mitigation is a config field, not code:** `@convex-dev/rate-limiter` supports `shards: N` per
limit. Add shards to the deployment-wide windows and the new ingest window — no semantic change.
Rule of thumb: shards ≈ peak QPS / 2, ≥5 capacity per shard. **But note §1.7:** sharding makes
`getValue` approximate, which conflicts with the pre-flight card's honest "remaining" number — so
shard the *deployment* windows, not the per-tenant ingest window.

### 2.5 Completion detection

`vault.markReady` (`:473`) and `vault.markFailed` (`:481`) are **the ONLY two terminal writers** for
every rail (extract fail, transcribe fail, `unsupported_format`, `pii_scan_failed`,
`empty_extraction`, `watchdogStalled`, `onIngestComplete`'s failed arm, and workflow success).
Verified callers: `vaultIngest.ts:70/:115/:140`, `vaultExtract.ts:293/:454`,
`vaultTranscribe.ts:51/:103`, `vaultSweep.ts:104`, `vaultSmoke.ts:97`.

So: inside those two handlers, `const doc = await ctx.db.get(id); if (doc?.folderId) bumpFolder(...)`.
One place, all callers.

- **Prefer a COUNTER** (`memberCount` / `terminalCount` / `failedCount` on `vaultFolders`) over a
  status-index probe: O(1), never reads a `text` blob.
- **Do NOT hang folder logic on `onIngestComplete`** — it returns immediately on success
  (`if (result.kind === "success") return null`, `:67`) and never fires for a doc that failed before
  the workflow started.

This completion mutation is the single place that (1) refunds the reservation, (2) enqueues the
digest, (3) fires 17.1 Stage-2. `17.1-CONTEXT.md:201-207` says Stage-2 is user-triggered *only*
because no bulk-completion event exists, and that it "attaches to the same action with no rework when
folder ingest lands". **`buildBlueprintDraft` is a `tenantAction` (`blueprint.ts:472`)** — a mutation
cannot invoke it, so an `internalAction` sibling is required.

### 2.6 Cancellation

Three parts, in order:

1. Client stops issuing further `vaultUpload` calls (AbortController on the in-flight POST).
2. Already-enqueued extractions are stopped via the **workpool's `cancel`/`cancelAll`** — a raw
   `ctx.scheduler.cancel` needs each scheduled function id, which nothing persists today. Another
   reason to move onto the pool.
3. **In-flight actions are NOT killable** (workflow README: in-progress `step.runAction` calls finish
   executing). So cancellation means **"no NEW spend"**, and the refund is computed after the last
   in-flight action settles — refunding on the click over-refunds by whatever the running pages charge.

**Implementing the locked "keep documents, discard folder":** DELETE the `vaultFolders` row and touch
zero documents. Members keep a dangling `folderId` resolving to nothing — observationally
folder-less, zero migration. **Actively clearing `folderId` on 400 rows is NOT viable in one
mutation:** a patch rewrites the whole document, and 400 rows × up to 400 KB of `text` blows the
16 MiB written-per-transaction cap. It would need the batch + `scheduler.runAfter(0, self)` idiom.

⚠ This interacts with the sealing predicate — see §3.5. Every folder read must treat an unresolvable
`folderId` as "no folder" (a lenient join), or cancelled documents become invisible, the exact
opposite of the locked decision.

### 2.7 ⚠ BLOCKER: the watchdog fabricates failures at queue depth

`EXTRACTION_WATCHDOG_MS = 15 min` is armed at **SCHEDULE** time (`vault.ts:77`), and its comment
justifies 15 minutes as "comfortably above the worst legitimate run". **With 400 documents queued
behind a concurrency of 8, a document sits QUEUED for an hour and the watchdog marks it
`extraction_stalled` while it is perfectly healthy.**

This directly breaks the locked "partial failure ⇒ completes with an **honest** manifest" decision —
the manifest would report failures that never happened. **Fix:** arm the watchdog when work STARTS
(from `markExtracting`, `vault.ts:498`, called at the top of every attempt) rather than when it is
scheduled; or scale the delay with queue depth. This is the one place where 15.2's guarantees and
folder scale genuinely collide.

### 2.8 ⚠ BLOCKER: the vault page breaks on its own first folder

`vault.listVaultDocs` (`:270`) and `vault.vaultStats` (`:285`) both `.collect()` the tenant's whole
`vaultDocuments` partition **including every `text` blob** (≤ `VAULT_EXTRACT_CHAR_CAP` = 400,000
chars per row, `extractKind.ts:53`). The vault page calls both (`page.tsx:54-55`).

At 200–400 documents that is 20–160 MB against a **16 MiB per-transaction read cap** and a 1-second
query budget. **The vault page hard-fails the moment the first folder lands — before any digest
exists, and independent of any folder feature.** ~40 max-size rows already exhaust the cap.

Options: (a) `.paginate()` the grid and derive stats from a maintained counter row; (b) move `text`
off `vaultDocuments` into a side table keyed by docId (a real migration, but it also fixes
`unincorporatedFor`'s ponytail note and every other whole-row read).

**This must be an explicit task in this phase or the phase's own acceptance demo cannot render.**
Note this is the same defect class as the `onboarding.status` timeout fixed on 2026-08-02 — an
unbounded `.collect()` over a table carrying large blobs.

### 2.9 ⚠ Hash-dedup breaks naive completion counting

`vaultUpload` (`:177-183`) and `vaultIngestText` (`:118-124`) return an EXISTING row on a
`contentHash` match and start **no workflow**. Therefore:

- A duplicate file inside the folder produces no new row and no terminal event — **a folder that
  counts to "number of files picked" never completes.** Count members from rows actually inserted.
- A file whose bytes already exist as a folder-less document returns that row. Patching its
  `folderId` **silently annexes a pre-existing document into the folder** — and worse, seals a
  document the user could ground on yesterday. Decide explicitly: skip `folderId` assignment on a
  dedup hit, or refuse to re-parent a row that already has one.
- The same physical document cannot be a member of two folders under a single optional `folderId`.

### 2.10 Platform limits that actually apply

Queries/mutations 1 s user code · Node actions 10 min · V8 actions 30 min · function args 16 MiB
(Node actions 5 MiB) · return values 16 MiB · document 1 MiB · **per transaction 16 MiB read /
32,000 docs scanned / 16 MiB written / 16,000 docs written** · 1,000 scheduled functions per
mutation · scheduled-job concurrency 8 (S16) / 256 (S256). File storage has no documented size cap,
but the upload POST times out at 2 minutes and the URL expires in 1 hour.

**Pre-flight "time-to-ready" needs TWO independent terms:** (a) transfer = `totalBytes / upstream`;
(b) processing = `ceil(docCount / poolParallelism) × per-doc time`, which at concurrency 8 and
1–2 min/doc is **50–100 minutes for 400 docs**. (b) dominates. Say so honestly rather than showing
one number.

⚠ **The deployment's concurrency class is unverified from inside the repo** (8 vs 256 — a 30×
difference). Confirm it from the Convex dashboard before writing the estimator.

## 3. Data model, sealing, retrieval and digest staleness

### 3.1 Table shape and the widening

```ts
vaultFolders: defineTable({
  tenantId: v.string(),
  name: v.string(),
  source: v.union(v.literal("upload"), v.literal("drive")),
  status: v.union(v.literal("reserving"), v.literal("ingesting"), v.literal("complete"),

  digestBuiltAt:      v.optional(v.number()),
  createdAt: v.number(),

```

`digestDocId` + `digestSourceDocIds` are a deliberate field-for-field clone of
`tenantProfiles.blueprintDocId` (`schema.ts:1046`) and `blueprintSourceDocIds` (`:1041`) — same
names, same meaning, so the 17.1 reader idiom transfers unchanged.

**The widening:** one line on `vaultDocuments` beside `origin` (`schema.ts:849`):
`folderId: v.optional(v.id("vaultFolders"))`. Zero backfill; absent = folder-less = today's behaviour.

**Indexes — one, possibly two:**
`.index("by_tenant_folder", ["tenantId", "folderId"])` serves drill-in listing AND the stale
set-difference. A `by_tenant_folder_status` is only needed if completion is counted by query —
**prefer the counter** (§2.5) and skip it.

⚠ **Never `.collect()` on `by_tenant_folder`.** Rows carry `text` up to 400k chars, so ~40 max-size
rows exhaust the 16 MiB cap. Drill-in must `.take(N)`/paginate and project `text` away before
returning — `ownedDocsMeta` (`vault.ts:438`) is the shipped precedent for a projected, refs-only read.

### 3.2 ⚠ The `origin` exclusion is structural by OMISSION, not a filter

`vault.ts:627-634` documents that `insertCreatedDoc` **deliberately never calls `startIngest`**, so an
`origin:"agent"` row has no rag entry and no graph edges and is unreachable by both halves of
retrieval. A grep of the whole convex tree found **zero `origin` predicates** in any retrieval or
drift path.

Two consequences:

1. **The new `folder_digest` literal is inert.** It excludes nothing — and it *includes* nothing
   either. **The digest becomes groundable only because its insert calls `startIngest`.** If a plan
   forgets that call, the digest is silently ungroundable and every test asserting
   `origin === "folder_digest"` still passes. **The observable check must be `ragEntryId != null`.**
2. **Sealing cannot be done by omitting ingest** — members must genuinely embed and graph-extract
   during the sealed window. Sealing must be an explicit filter.

**The union edit is genuinely one line** (`schema.ts:849`):
`v.optional(v.union(v.literal("agent"), v.literal("agent_promoted"), v.literal("folder_digest")))`.
The only consumer is `vault.ts:723`'s `doc.origin !== "agent"` guard in `patchCreatedDoc`, which
already refuses non-`"agent"`, so a digest is correctly un-revisable — **no edit needed, but add a
comment so nobody "fixes" it.**

### 3.3 The digest must be INGESTED — copy `research.ts:167-184` verbatim

Insert with `kind: "folder_digest"`, `category: categoryFor({source:"agent"})` (→ `workspace-docs`),
`source: "agent"`, `mimeType: "text/markdown"` (in `SEARCHABLE_MIME`), `text: markdown`,
`status: "processing"`, `origin: "folder_digest"`, then `await startIngest(...)` with the folder's
correlationId. Patch `digestDocId` / `digestSourceDocIds` / `digestBuiltAt` in the same mutation,
mirroring `blueprint.ts:372-378`.

**Generation:** a new V8 `internalAction` in `packages/backend/convex/vaultDigest.ts` — **NOT
`"use node"`** (`vaultLlm.ts:3-7` explains that a second node module re-triggers the TS
internal-graph inference cliff; carry an explicit `Promise<...>` return type). Prompt from the
registry (§5): `FOLDER_DIGEST_SKILL = "folder-digest"` in `packages/contracts/src/skill.ts` beside
`GRAPH_EXTRACTOR_SKILL` (`:64`), a body module, and a `seedSkills` row (`skills.ts:289`). Load the
skill FIRST, `scanText` fail-closed before the model call, price with `priceUsage`, and carry a
`SMOKE::` sentinel so convex-test drives it with no network.

**Digest input budget:** do NOT collect member `text`. Build parts 1 and 3 (manifest, unreadable
list) from projected metadata only; feed part 2 from a bounded head slice per member (`capGraphText`
is the precedent) under an overall char budget mirroring `vaultGround.ts:29-30`.

**Recursion guard — pick one and state it in code.** Preferred: the digest carries **no `folderId`**;
the folder points at it via `digestDocId`. Then a digest can never enter a member-set query at all
and no predicate is needed anywhere. (Alternative: give it `folderId` and write ONE
`folderMemberDocs()` helper applying `origin !== "folder_digest"`.) This mirrors `unincorporatedFor`'s
`kind !== "business_blueprint"` self-exclusion at `blueprint.ts:571`.

### 3.4 ⚠ Sealing needs THREE sites, not one

| Site | What leaks without it |
|---|---|
| **`runVaultGround` (`vaultGround.ts:35-103`)** | Every agent-grounding caller: `searchVault` (`llm.ts:1810`), blueprint probes (`:512`), evaluations (`:236`), voiceDoc (`:75`) |
| **`vault.vaultSearch` (`vault.ts:380`)** | The browse search box — same rag primitive, separate read |
| **`blueprint.unincorporatedFor` (`blueprint.ts:553`)** | Sealed members reach `status:"ready"` and **inflate the blueprint drift banner on every grounding call** (`spineForTenant:586`) and on the profile page (`:438`) |

In `runVaultGround`, filter after the vector branch produces `hits`/`seedDocIds` and **BEFORE**
`internal.vaultGraph.expand` (`:95`), then apply the same predicate to `neighborDocIds` before `fuse`
(`:102`). Filtering seeds before expand also stops a sealed doc's entities pulling unsealed neighbours.

- Predicate: `doc.folderId != null && folder.status !== "complete"`.
- **Do NOT** put the filter inside `ownedDocsMeta`'s existing return — `vaultGroundHydrated` (`:137`)
  keeps a titles array index-parallel to docIds, and silently dropping rows there desyncs titles.
- **Do NOT** use `rag.search` filters: `vaultRag.ts` declares no `filterNames`, and a filter baked at
  embed time cannot change when a folder unseals without re-embedding.

**⚠ Sealed members reach `status: "ready"` during the sealed window** (`vaultIngest.ts:140`). Anything
treating `ready` as "groundable" is wrong for folder members — including `vaultStats.processed`
(`vault.ts:301`). **There is no status meaning "embedded but sealed"; sealing is a property of the
FOLDER, exactly as CONTEXT locks it.** Adding a "sealed" status would seal nothing, because retrieval
never consults status.

### 3.5 ⚠ Cancel + the sealing predicate — a one-word bug

CONTEXT locks "cancel keeps the documents, discards the folder", deriving that cancelled docs become
groundable immediately. With the predicate above, a cancelled folder row merely **marked**
`status:"cancelled"` rather than DELETED **keeps its members sealed forever.** Either delete the row
(§2.6) or make the predicate treat `cancelled` as unsealed. Name it explicitly.

### 3.6 ⚠ The graph leak is partial and cannot be closed cheaply

`vaultGraph.upsertGraph` (`:26`) writes sealed members' entities into the **shared tenant graph** at
ingest step 4, before `markReady`. Filtering the expand OUTPUT hides sealed documents, but the sealed
folder's entities still (a) raise `graphNodes.degree`, feeding `blueprint.topEntities` (`:224-234`)
and therefore the blueprint spine on every cockpit turn, and (b) create edges making two previously
unconnected UNSEALED docs reachable from each other.

That is **structural/metadata leakage, not content leakage.** Closing it properly means deferring
`upsertGraph` to folder completion, which breaks the per-doc ingest workflow. **Recommend accepting
and documenting** — the locked decision says "excluded from retrieval", which the doc-id filter
satisfies literally.

### 3.7 ⚠ `DRIFT_SCAN_CAP = 100` is a `.take()`, and it is unsound at folder scale

The 17.1 staleness clone is otherwise near-verbatim: `unincorporatedForFolder(ctx, tenantId,
folderId, sourceDocIds)` reads members via `by_tenant_folder`, `.take(cap)`, filters
`status === "ready" && !sourceSet.has(doc._id)`, returns `{count, docIds}` — the exact shape of
`blueprint.ts:553-574`. Surface it through the folder read query the drill-in already needs (the
`blueprintState:428-439` pattern); rebuild-on-click re-runs synthesis and rewrites
`digestSourceDocIds` (the `confirmBlueprint:372-378` shape).

**But `DRIFT_SCAN_CAP` is a `.take()`, not a result limit.** Applied to a 200–300-member folder it
inspects an arbitrary index-ordered 100 and **can return 0 stale docs while dozens are stale — the
banner silently never fires.** The locked decision says reuse the 17.1 bounded set-difference;
reusing it verbatim at folder scale is unsound.

Options for the owner:
1. Raise the cap for folder scope (a folder's member count is known and bounded by pre-flight).
2. Paginate the diff.
3. **Cheapest, but a DEVIATION requiring owner sign-off:** compare `digestBuiltAt` against a
   `membersChangedAt` stamp bumped on any member add/remove/re-ingest — O(1) and exactly correct,
   but it is not a set-difference.

### 3.8 Playbook gating for new files

`docs/playbooks/watch.json:142-159` lists `vault.md`'s convex files **individually** (only
`packages/vault/` is a prefix). A new `packages/backend/convex/vaultFolders.ts` or `vaultDigest.ts`
**must be registered there**, and `docs/playbooks/vault.md` updated with a bumped `Last verified`
line in the same commit, or the Stop hook blocks the turn (CLAUDE.md §9).

Also note `retryStuckIngests` (`vaultIngest.ts:85-102`) already does a FULL `vaultDocuments` table
scan with `.collect()` (its own ponytail note admits it). Folder scale makes it an operational
landmine on the same 16 MiB cap — not in scope, but any ops sweep run during a folder ingest will now
throw.

would inflate the folder's failure count for a cosmetic label.

`ponytail:` comment: `getActiveSkill` is fail-closed by contract, but here the fallback is a degraded
**label**, not a degraded grounding corpus. Sequence the seed before the workflow edit reaches
production.

### 4.8 ⚠ Cent rounding multiplies folder cost 2×

`recordSpend` does `Math.ceil(costUsd * 100)` (`guardrails.ts:252`). A per-document ingest costing

real spend** — invisible in any estimate computed from model pricing. If the classifier ever gets its
OWN `recordSpend` call rather than folding into the per-doc sum, that doubles again (300 extra cents
= $3 for $0.10 of real spend).

**Fold classify cost into the ONE existing `recordSpend` per document, and have the folder estimator
model the ceil, not the true price.**

## 5. The Google Drive export rail

Buildable almost entirely by copying the shipped **Calendar** rail, which is itself a scope-widening
of the same single Google grant. **No new secret, no new HTTP route, no second token table.**

### 5.1 ⚠ A locked decision is factually wrong

> CONTEXT: *"The 200 MB byte cap does not apply (nothing is uploaded)."*

**Non-native Drive files (PDFs, videos, zips) ARE downloaded into a Convex action's memory** and
stored via `ctx.storage` — bytes very much move. A 600 MB video in a Drive folder would **OOM the
node action (~512 MB) before any cap could refuse it.**

The Drive rail needs the SAME per-file byte cap as the upload rail (arguably lower), enforced from
the `size` metadata **BEFORE** the download is attempted. This is a correction to hand the owner, not
a redesign.

### 5.2 ⚠ "Estimate from Drive metadata" survives only with a conservative fallback

Drive does **not** reliably populate `size` (or `md5Checksum`) for Google-native Docs Editors files.
An estimator reading a missing `size` as 0 prices a **500-Doc folder at $0**, reserves nothing, and
the folder then trips `preCall` mid-run — producing exactly the half-ingested folder the phase exists
to forbid.

**Required:** `estimatedBytesFor({mimeType, size})` returning `size ?? DRIVE_NATIVE_ASSUMED_BYTES[kind]`
(Doc 256 KB, Slides 512 KB, Sheet 1 MB). Over-estimation is safe because the design hard-reserves then
refunds. **Put a runnable assert on the "missing size never yields 0" branch — that single property is
what keeps the reservation invariant true on the Drive rail.**

### 5.3 The scope, and what it does to existing users

`GOOGLE_SCOPES` is one `.join(" ")` array at `packages/core/src/calendar.ts:18-22`. Adding
`DRIVE_READONLY_SCOPE = "https://www.googleapis.com/auth/drive.readonly"` there is a one-line edit
reaching both `gmailAuth.buildAuthorizeUrl` (`:58`) and the callback default (`http.ts:73`). One
scope covers metadata reads, `alt=media` downloads and exports.

*(`drive.file` would need the Google Picker JS SDK from `apis.google.com` plus an API key and app id
— an external client-side script that buys nothing in Testing mode.)*

**The critical question, answered:** adding a scope does **NOT** invalidate, revoke or expire any
stored refresh token. Existing tenants keep sending mail and creating events.
`include_granted_scopes=true` is **forward-only**: the NEXT consent returns a grant covering
gmail+calendar+drive (so the user is never re-asked for mail/calendar, and re-consent cannot narrow
the grant) — **it does not retro-grant Drive to tokens issued before the widening.**

So every already-connected tenant has `gmailTokens.scope` **without** Drive, and their Drive calls
403 `ACCESS_TOKEN_SCOPE_INSUFFICIENT`. **Correct handling is the shipped Calendar one:**
`hasScope(token.scope, DRIVE_READONLY_SCOPE)` → return a `reauth` outcome **BEFORE**
`freshAccessToken` — an ordering a static test already enforces for Calendar
(`dispatchGuard.test.ts:152-179`) and which should be extended to the Drive action.

**UI gap this creates:** `gmailAuth.gmailStatus` returns only `{connected, expiresAt}`, so the vault
Drive entry point cannot distinguish "connected but pre-widening" from "Drive-ready". Add a derived
**boolean** `driveReady` — never the raw scope string, keeping the never-leak-the-token discipline.
Consumers: `ConnectionsPanel.tsx:63` and the new vault control.

Because the app runs OAuth in **Testing mode** (7-day refresh tokens, `tokenExpiry.ts:13`), no
verification/CASA cost applies today, and `gmail.modify` is already RESTRICTED, so `drive.readonly`
adds no new verification category later.

### 5.4 The API calls

| Purpose | Call |
|---|---|
| List children | `GET /drive/v3/files?q='<ID>' in parents and trashed=false&fields=nextPageToken,files(id,name,mimeType,size,modifiedTime,md5Checksum,shortcutDetails,capabilities/canDownload)&pageSize=1000&supportsAllDrives=true&includeItemsFromAllDrives=true` |
| Binary download | `GET /drive/v3/files/{id}?alt=media&supportsAllDrives=true` |
| Native export | `GET /drive/v3/files/{id}/export?mimeType=<target>` — **hard 10 MB ceiling** |

Prefer the list projection over per-file `files.get`: N files = 1 request instead of N+1. Sub-folders
return `mimeType: application/vnd.google-apps.folder` — recurse breadth-first with an explicit node cap.

**Export targets — load-bearing for dedup (see §5.6):** Docs → `text/plain`; Slides → `text/plain`;
Sheets → **xlsx** (`text/csv` is **FIRST SHEET ONLY** — a multi-tab workbook silently loses every
other tab). `text/plain` is in `SEARCHABLE_MIME` so those skip extraction entirely and go straight to
`startIngest`; xlsx is in `OFFICE_MIME` so it rides the shipped extraction rail with zero new code.

### 5.5 How bytes enter the spine

A `"use node"` internalAction per file: `freshAccessToken` → fetch → `ctx.storage.store(new Blob(...))`
(precedent `http.ts:293-301`) → `ctx.runMutation(internal.vaultDrive.landFile, …)`. The landing
**internalMutation** inserts the row with `source:"google"`,
`category: categoryFor({source:"google", mimeType})` (→ `google-docs`, zero code change), `contentHash`,
`storageId`, plus `text` when the export was text — then `startIngest` (searchable) or
`scheduleExtraction` (binary).

**Why not `vaultUpload`:** it is a `tenantMutation` deriving tenantId from `getAuthUserId`, and
scheduled fan-out actions have **no identity**. The `internalMutation` + explicit `tenantId` shape is
mandatory and is already the repo idiom (`research.persistFindings`, `evaluations.ts:965`,
`onboarding.ts:486`).

**Fan-out:** enumerate in ONE action (paginated, metadata only — cheap), then one scheduled action per
file, exactly like the 15.2 extraction fan-out. Do not enumerate + export 300 files in one 10-minute
action.

**Token reuse:** `internal.gmailAuth.getTokens` for the scope check, `freshAccessToken(ctx, tenantId)`
from `./gmail` for the access token — `calendar.ts:21` is the existing proof a non-Gmail module may
import it.

### 5.6 Re-import and dedup

Add `driveFileId: v.optional(v.string())` + `driveModifiedTime: v.optional(v.number())` and an index
`by_tenant_driveFileId` — the same zero-migration widening idiom.

Per file: **(1)** found by `(tenantId, driveFileId)` with unchanged `modifiedTime` → UNCHANGED, skip,
no spend, no export; **(2)** found but `modifiedTime` moved → re-export, and if `contentHash` differs
update the row **in place** (so the member set and `digestSourceDocIds` stay stable) rather than
inserting a twin; **(3)** not found → NEW. That yields the locked "shows what changed"
(added/updated/unchanged/removed) essentially free.

**⚠ Do NOT ship Drive dedup on `contentHash` alone.** OOXML is a zip — docx/xlsx/pptx exports are
almost certainly **not byte-stable across calls** (timestamps, generated ids), so every refresh
re-hashes differently and duplicates the whole folder. This is the concrete reason to export
Docs/Slides to deterministic `text/plain` and make `driveFileId + modifiedTime` the PRIMARY key with
`contentHash` as fallback.

**⚠ The dup early-return trap:** `vault.ts:177-183` returns `{vaultDocId}` and does nothing else.
Copied verbatim, a file already in the vault silently gets NO `folderId`, NO `driveFileId`, and is
invisible to the folder — which then reports N files but owns fewer. The landing mutation must, on
the dup branch, patch `folderId`/`driveFileId`/`driveModifiedTime` and report it as `deduped`.

**⚠ Cross-boundary dedup + sealing.** If the user already uploaded a file manually and then imports
it from Drive, dedup resolves to a pre-existing, possibly already-groundable document. Under
SEALED-until-complete, attaching it to a sealed folder would **retroactively make a document the user
already had un-groundable.** Recommendation: dedup-matched pre-existing documents are reported in the
manifest but **NOT sealed**.

### 5.7 Failure modes that fail SILENTLY

- **⚠ Shared drives.** Omit `supportsAllDrives=true` / `includeItemsFromAllDrives=true` and
  `files.list` against a shared-drive folder returns **HTTP 200 with an EMPTY files array**. The user
  sees "imported 0 files, folder complete" — **a lying folder**, the exact failure the phase forbids.
  Both params on every call, and a zero-child result on a folder the user explicitly picked should be
  surfaced as suspicious, not as success.
- **Per-file permission denial is invisible until download time** — a listed file can still 403 on
  `alt=media`/`export` (`copyRequiresWriterPermission`, download restrictions, or
  `cannotDownloadAbusiveFile`, which this app must **not** bypass with `acknowledgeAbuse`). Read
  `capabilities/canDownload` in the list projection to pre-classify these into the unreadable bucket
  **during pre-flight**, so the count the user approves matches what actually imports.
- **Shortcuts** (`vnd.google-apps.shortcut`) must be resolved via `shortcutDetails.targetId` or they
  download as nothing. `form`, `site`, `map`, `jam`, `script`, `drive-sdk` have no text-bearing export
  → unreadable list. **Enumerate the handled set explicitly and default everything else to unreadable;
  never silently skip.**
- **Deep nesting is unbounded** and can cycle via shortcuts. BFS with an explicit node cap and a
  visited-id set is mandatory; enumeration must survive the 10-minute limit (paginate + continue in a
  scheduled follow-up).
- **`files.export`'s 10 MB ceiling** puts large Docs/Sheets in the "could NOT be read" bucket. That is
  the right home, but **budget for that bucket being non-empty on real company folders.** Google's
  async `files.download` is the documented upgrade path — verify against current docs, do not assume.
- **Quota:** a 300-file folder is 300+ requests; retry `userRateLimitExceeded` with backoff or a large
  folder reports spurious unreadable files.
- **7-day refresh tokens make "refresh from Drive" fragile by construction.** A user who imports and
  clicks refresh two weeks later hits `refresh_failed`, which must present as the **reconnect flow**,
  not a Drive error. Copy and routing requirement, not a bug to fix here.

### 5.8 Audit and playbooks

Audit rows are refs/counts only (§3/§4): `{folderId, fileCount, exportedCount, skippedCount,
failedCount, bytes}` — **never a Drive file name, folder name, or user-meaningful id**.
`gmailAuth.disconnectGoogle:293-301` is the model.

**⚠ Playbook gate (CLAUDE.md §9):** editing `calendar.ts` (GOOGLE_SCOPES), `gmailAuth.ts`, `gmail.ts`
or `http.ts` triggers **`docs/playbooks/cockpit.md`**; a new `vaultDrive.ts` is covered by NO playbook
until added to `watch.json` under `vault.md`. Both are hard blockers on turn completion, not polish.

One hardening note: `http.ts:73`'s `scope: tok.scope ?? GOOGLE_SCOPES` fallback becomes more dangerous
after the widening — if Google ever omits `scope`, the row claims Drive access it may not have and
`hasScope` passes for a grant that 403s. Storing `tok.scope ?? ""` fails closed, but it changes
behaviour for the existing Gmail/Calendar paths too: a deliberate decision, not a drive-by edit.

## Validation Architecture

**The sampling argument.** This phase's guarantees are mostly *absences* — a folder that is never
half-ingested, a document that is never groundable while sealed, a label that is never overwritten,
budget that is never manufactured. An absence cannot be observed by running the happy path, so every
guarantee below is paired with **the mutation that must turn its test RED**. A test whose stated
mutation does not break it is not sampling the guarantee; it is sampling the code's shape.

Three guarantees are **not** observable offline (window rollover, real concurrency, real throughput)
and are listed as live probes with an operator check recorded in the playbook — not pretended into a
unit test.
