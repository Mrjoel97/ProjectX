# 15.3-05 — sealing (VALT-07)

## What shipped

**A folder's members are excluded from retrieval until the folder is `complete`**, enforced at every
place a doc id can reach a reader. One predicate, four call sites, zero new dependencies, zero
schema change.

```
sealed(doc) === doc.folderId != null && folderRow(doc.folderId)?.status === "ingesting"
```

| Site | File | Why it is separate |
|------|------|--------------------|
| grounding seeds | `vaultGround.ts` | filtered BEFORE `expand`, else a sealed doc's entities pull unsealed neighbours in |
| graph neighbours | `vaultGround.ts` | `vaultGraph.expand` reads `graphEdges` with no filter of its own — independent leak path |
| browse search | `vault.ts` | same rag primitive, separate code path; disagreement reads as a bug in whichever surface is checked second |
| blueprint drift | `blueprint.ts` | members are `ready` during the sealed window and `spineForTenant` runs on EVERY grounding call |

## Deviations from the plan

1. **The predicate lives in `vaultFolders.ts`, not `vaultGround.ts`** (plan Task 1 named
   `vaultGround.ts`). `blueprint.unincorporatedFor` is a plain `QueryCtx` helper, not a registered
   function, so it cannot `ctx.runQuery` and needs a directly importable function. `vaultFolders.ts`
   is the only home all four callers reach without pulling the `rag` component into `blueprint.ts`'s
   module graph, and it already sits in a working import cycle with `vault.ts` via `bumpFolder`.
   `vaultGround.ts` still owns nothing but its two filter applications, as specified.
2. **Test 4 asserts through `unincorporatedCountForTenant`, not `spineForTenant`.** Same
   `unincorporatedFor` helper; `spineForTenant` returns `null` with no live blueprint, so driving
   the test through it would need a whole blueprint fixture just to avoid being vacuous.
3. **`docs/playbooks/onboarding.md` was bumped too** — it also watches `blueprint.ts`, and
   `check-playbooks` blocked without it. `blueprintState` (the profile page's one read) reaches
   `unincorporatedFor` through the same helper, so its `unincorporatedCount` now excludes an
   ingesting folder. No onboarding signature or state machine changed.

## The one-word bug, and why the predicate is positive

`cancelFolder` DELETES the folder row and writes ZERO document rows, so a cancelled folder's members
stay as ordinary documents carrying a **dangling `folderId`**. Written as
`folder?.status !== "complete"` the predicate evaluates `undefined !== "complete"` ⇒ `true`, sealing
every cancelled folder's documents **forever** — silently, with no row left anywhere to explain why
the user's documents stopped answering. Test 5 is that mutation.

`"reserving"` and `"refused"` need no seal: `vault.ts` inserts a folder member at
`pending_extraction` and dispatches nothing until `reserveFolder`, so those members hold no
`ragEntryId` and no graph edges. `schema.ts` already annotates the table with exactly this —
`ingesting` = "SEALED from retrieval", `complete` = "unsealed".

**The graph-neighbour test was VACUOUS on its first run and its own non-vacuity control caught it.**
`upsertGraph` dedups edges cross-doc, so giving both documents the identical `Alice—Bob` pair left
the second with no `graphEdges` row at all — `expand` resolves neighbours by `sourceDocId`, so the
member was invisible for a reason with nothing to do with sealing. Documents must be linked by a
SHARED NODE (`A(Alice—Bob)`, `B(Bob—Carol)`), the chain fixture `vaultGraph.test.ts` already uses.
That is the entire argument for writing the "flip to complete and assert it IS returned" half of
every test in this file: **this plan is made of absences, and an absence passes for free when the
thing it guards was never reachable.**

## Accepted limitation (documented at the site and in the playbook)

`upsertGraph` writes a sealed member's entities into the SHARED tenant graph at ingest step 4, so a
sealed folder still raises `graphNodes.degree` (feeding `blueprint.topEntities`) and can create an
edge joining two UNSEALED documents. **Structural/metadata leakage, not content** — no sealed text
and no sealed doc id reaches a reader. Closing it means deferring `upsertGraph` to folder
completion, which breaks the per-document ingest workflow. Upgrade path, not a bug fix.

## Rejected

- **Filtering inside `ownedDocsMeta`** — `vaultGroundHydrated` keeps a `titles` array index-parallel
  to `docIds`; silently dropping rows in the shared resolver desyncs titles from documents.
- **A `rag.search` filter** — `vaultRag.ts` declares no `filterNames`, and a filter baked in at embed
  time cannot change when a folder unseals without re-embedding every member.
- **A `sealed` document status** — sealing is a property of the FOLDER; retrieval never consults
  document status, so a status would seal nothing.
