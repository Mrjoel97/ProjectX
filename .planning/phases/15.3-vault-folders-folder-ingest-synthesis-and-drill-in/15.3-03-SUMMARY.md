# Phase 15.3 Plan 03: The Folder Budget Wall Summary

**Folder ingest got its own $25/day window, a whole-folder reservation that refuses intact with numbers instead of a stack trace, and a refund that is clamped, rollover-guarded and idempotent — and the entire vault ingest path stopped spending the cockpit's $5.**

## Is the refund provably clamped and idempotent?

Asked plainly in the plan, so answered plainly:

- **Idempotent: YES, provably, offline.** `settleFolder` CASes on `reservedCents` in the same
  transaction as the credit. Deleting that line turns "settling twice does not credit twice" RED —
  run, confirmed.
- **Clamped: YES for the arithmetic, offline.** `clampRefundCents` is pure and unit-tested in five
  directions; weakening it to `min(unspent, capacity)` turns 3 tests RED — run, confirmed.
- **Clamped ACROSS A WINDOW ROLL: NOT PROVEN OFFLINE, and no test here claims otherwise.** Every
  test in this plan runs inside one 24h window. The case that manufactures budget only exists
  across a real day boundary, and reproducing it under convex-test means hand-editing the
  component's private `rateLimits` rows — which tests the harness, not the guard.
  **What is only observable live:** run `npx convex run guardrails:ingestRemainingCents` before a
  folder, let the folder complete, let the window roll, run it again. The number must be at most
  2500. The procedure is written into `docs/playbooks/guardrails.md` §15.3-03 precisely so nobody
  reads a green suite as proof of it.

## Accomplishments

- **The B3 defect is closed.** Every paid step of vault ingest charged `dailySpendCents` — the
  COCKPIT's $5 — at six sites. A folder both starved the agent the user relies on for actual work
  and could be refused halfway by an unrelated cockpit turn. Both directions are now impossible
  and both directions have a test, including a CONTROL test that reproduces the old behaviour so
  the guarantee cannot rot into a tautology.
- **The reservation refuses intact, with numbers.** `check()` THROWS above capacity
  (`Rate limit ingestSpendCents count 2501 exceeds 2500`), so the ceiling comparison precedes every
  limiter call. Moving it after the check turns the test RED with exactly that message — the locked
  plain-language refusal really would have been a stack trace.
- **The refund's two guards are both load-bearing and both are documented as such.** The clamp
  handles "the window is already full"; the rollover skip handles "the window rolled and someone
  else has since spent, re-opening exactly their spend as headroom for our credit". Neither covers
  the other.
- **A finding the plan did not anticipate, and it changes the arithmetic:** `getValue` returns the
  **STORED** state, not a roll-forward. With one shard the component passes `now = state.ts`
  internally, so `elapsedWindows` is 0 — a window that rolled overnight still reports yesterday's
  value and yesterday's window start. Clamping against that raw number IS the 2900-against-2500
  bug rather than the fix for it. `settleFolder` now rolls both numbers forward using the
  component's own exported `calculateRateLimit`, so a version bump that changes the arithmetic
  changes the guard with it instead of silently desynchronising.
- **Both rails now explain themselves.** `media.ts`'s no-refunds `ponytail:` note is intact and
  gains a pointer; `guardrails.md` states the same fact from the ingest side with the size argument
  (media over-reserves by CENTS under `MEDIA_JOB_CAP_USD`, ingest by DOLLARS because the estimator
  cannot see page counts before the bytes land).
- **Nothing existing changed behaviour.** `rail`/`reserved` are optional at ~15 call sites;
  `dispatch.ts`'s sub-agent envelope sizing still reads `remainingDailyCents` over the token
  window; `pnpm test` went 1109 → 1118 with zero regressions and the typecheck delta is 0.

## Decisions Made

- **NEITHER ingest window is sharded — a deliberate deviation from the plan's Task 3.** The plan
  says to shard the deployment-wide window for the OCR fan-out's ~36 concurrent writers. Reading
  the shipped component says not to: `limit()` selects a shard **at random** and `getValue` samples,
  so a refund clamped against one sampled value can credit a shard that never paid — re-opening
  per-shard exactly the money bug the plan calls non-negotiable. It would also make the
  pre-flight card's "you have $1.10 left today" an approximation. 15.3-RESEARCH §1.7 independently
  says do not shard. The contention is also not new: those same writers already hit the unsharded
  `dailySpendCents`/`deploymentSpendCents` today, so keeping the shape is not a regression. The
  upgrade path (shard AND stop refunding the deployment window, or move to a spend table) is named
  at the site.
- **`reserveFolderInner` is a plain function with an `internalMutation` face**, the
  `reserveJobInner`/`reserveJob` split. 15.3-04's folder-create mutation must take the reservation
  in the SAME transaction as the `vaultFolders` insert; a Convex mutation cannot `runMutation`, and
  a reservation in a different transaction from the row that records it is a reservation that can
  leak.
- **A missing `reservedAt` makes settle refuse to refund** (and still clear `reservedCents`).
  Without the stamp there is no way to know which window paid, and the fail-closed direction on a
  money rail is "the tenant keeps the charge", never "mint the credit".
- **The estimator models the cent-ceiling PER `recordSpend` CALL, not per document or per folder.**
  `extractHosted` fires one `recordSpend` per OCR page, so a 50-page scan draws 50 cents even
  though its tokens price at ~28. Per-folder rounding under-reserves a 300-file folder by ~2×,
  which is B14 and the reason the wall would have failed at exactly the scale it exists for.
- **Conservatism asserted by DIRECTION, never against a literal.** The estimate is compared to
  per-doc ceilings derived from `@pikar/cost` at test time. A pinned number fights every
  price-table change and gets "fixed" by whoever is least able to judge whether the new number is
  still conservative — which is how an under-reservation ships.
- **Reason CODES are shared with the token rail** (`daily_budget_exhausted` /
  `deployment_budget_exhausted`) rather than minting ingest-specific twins. Three call sites
  declare those unions explicitly; new codes would widen all of them for no behavioural gain, and
  the codes mean the same thing to the caller.
- **No ingest arm added to `smoke:guardrails`** (the plan's verification asks for one). An arm
  writes `vaultFolders` rows to a live deployment, the rail is already proven against the REAL
  component offline, and the only thing an arm could not cover either is the cross-window refund.
  Recorded as a known gap in `guardrails.md` with the operator check that does cover it.
- **Requirements left `Pending`.** VALT-06 is this plan's frontmatter claim and the rail is built,
  but VALT-06 names user-observable refusal behaviour that has no surface until 15.3-04 and 15.3-07
  land. Following 15.3-01 and 15.3-02's precedent (and 17.1-01's reverted early flip),
  `requirements mark-complete` was NOT run.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `getValue` does not roll the window forward, so the plan's clamp reads a stale value**

- **Found during:** Task 4
- **Issue:** The plan (and RESEARCH §1.2) specifies
  `refund = max(0, min(unspent, cap - getValue().value))`. Reading the shipped component's
  `getValue` shows it returns `maxShard.value` / `maxShard.ts` — the **stored** state. Its internal
  `calculateRateLimit` call passes `now = maxTs`, which for a single shard equals `state.ts`, so
  `elapsedWindows` is always 0. A window that rolled overnight with nothing written since reports
  yesterday's drained value AND yesterday's window start. Clamping against that gives a large false
  headroom, and the rollover guard (`reservedAt < ts`) would also fail to fire — i.e. the plan's
  clamp as written reproduces the 2900-against-2500 bug rather than preventing it.
- **Fix:** `refundableCents` rolls both numbers forward with the component's OWN exported
  `calculateRateLimit` before applying the rollover skip and the clamp.
- **Files:** `packages/backend/convex/guardrails.ts`
- **Commit:** `2fe31a0`

**2. [Rule 1 - Bug] Sharding the deployment ingest window would re-open the money bug**

- **Found during:** Task 3
- **Issue:** The plan instructs adding `shards` to the deployment-wide window. The component picks
  a shard at random on `limit()` and samples on `getValue()`, so a negative-count refund clamped
  against one sampled value can credit a shard that never paid.
- **Fix:** neither ingest window is sharded; the reasoning and the upgrade path are at the
  definition site and in `guardrails.md`.
- **Files:** `packages/backend/convex/guardrails.ts`, `docs/playbooks/guardrails.md`
- **Commit:** `80f5477`

**3. [Rule 2 - Missing critical] The cross-rail isolation fixture did not sample its own guarantee**

- **Found during:** Task 6, by running the plan's stated mutation
- **Issue:** draining only `dailySpendCents` left all 17 tests green when `preCall`'s reserved
  early return was deleted.
- **Fix:** `drainBothRails` (a real `reserveFolder` for the full $25, asserted to zero the window)
  plus a third arm proving the rail alone is not sufficient. Mutation re-run → RED.

**4. [Rule 2 - Missing critical] `retryStuckIngests` would push folder members back onto the cockpit rail**

## Next Phase Readiness

- **15.3-04 (folder model + ingest orchestration) is unblocked** and inherits four contracts it
  must honour:
  1. **Call `reserveFolderInner` in the SAME mutation that inserts the `vaultFolders` row**, and
     **persist `reservedAt` from its result.** `settleFolder` refuses to refund without the stamp.
  2. **`settleFolder` is the ONLY release path.** Completion and cancel both call it, and cancel
     must call it BEFORE deleting the row (§B13). Two release mechanisms is two places to get the
     clamp wrong.
  3. **Pass `rail: "ingest", reserved: true`** on `startIngest` / `scheduleExtraction` for folder
     members. Omit either and the member silently charges the cockpit again.
  4. **The estimator's stage-2 fields are the reservation input.** Reserve off probed `pages` /
     `hasTextLayer` / `durationSec`; an unprobed PDF prices at the 50-page scanned ceiling by
     design, and a 100-file unprobed PDF folder therefore refuses.
- **15.3-07 (pre-flight card) has its number:** `ingestRemainingCentsInner` is a plain function, so
  a `tenantQuery` can read it without `runQuery`. The refusal payload already carries `estCents`,
  `remainingCents`, `shortfallCents`, `fileCount` and `totalBytes` — counts and ids only, legal as
  an `audit.log` payload, with no filenames.
- **The one open money risk is a reservation leak.** A folder whose workflow dies after reserving
  holds its cents for up to 24h; nothing sweeps for orphaned reservations. 15.3-04 owns the folder
  watchdog, and `settleFolder` is already the mechanism it should call.
- **Two things later waves must not undo:** never shard the ingest windows without also removing
  the refund, and never "simplify" `refundableCents` back to reading `getValue().value` directly.
