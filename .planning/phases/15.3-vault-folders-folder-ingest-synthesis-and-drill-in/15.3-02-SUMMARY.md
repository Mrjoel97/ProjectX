# Phase 15.3 Plan 02: Vault Read Survivability + Cap Single-Source Summary

**The vault page stopped reading every document's full text on every render — `listVaultDocs` and `vaultStats` now share one read bounded by rows AND bytes and return metadata only — and the per-file size cap went from five hand-typed literals to one 200 MB declaration guarded by the first test that has ever read the vault UI.**

## What the owner will SEE differently on the vault page

Plain language, because this plan changes a page in daily use:

1. **Small vault (today, ~12 documents): nothing changes.** Same tiles, same numbers, same cards,
   same chips, same preview, same Refresh. The measured behaviour is identical.
2. **The Dropzone helper line now reads "Up to 200 MB per file (video 25 MB)"** — it said 100 MB.
   Files between 100 MB and 200 MB now upload instead of being refused. (On a slow link a 200 MB
   file will hit Convex's 2-minute upload timeout and report an upload failure rather than a cap
   refusal — recorded at the constant, and plan 04 owns saying that better.)
3. **The preview pane fills a beat later.** The document's text is now fetched for the one document
   you opened rather than riding along with the grid; while it settles the pane says "Loading…"
   instead of showing "No inline preview for this file" and then swapping.
4. **Only at scale:** once a vault is bigger than one page, the four stat tiles read `200+` (or
   `43+` if the documents are huge) and a quiet line appears under them: *"Showing your newest
   documents — this vault holds more than one page."* The grid shows the newest window. Before this
   plan that same vault did not render at all — the page failed.

Nothing else on the page moved: no new controls, no layout change, no new colours, no component
library, no copy rewritten beyond the two lines above.

## Accomplishments

- **The B1 blocker is closed, and closed correctly.** `listVaultDocs` and `vaultStats` each used to
  `.collect()` the tenant's whole `vaultDocuments` partition *including every `text` blob* (≤400k
  chars/row). Convex has no projection, so ~40 max-size rows exhaust the 16 MiB per-transaction read
  cap. Both now go through `readVaultPage`, one streamed read that stops on **whichever bound bites
  first**: `VAULT_GRID_PAGE` (200) rows or `VAULT_GRID_READ_BUDGET_BYTES` (8 MiB) of text.
- **The plan's own row-only bound would not have worked, and that is the most important finding
  here.** 200 rows × 400 KB is ~80 MB — still 5× over the read cap. A `.take(200)` looks bounded and
  is not. The byte budget is what makes the must-have truth ("renders with 400 documents in the
  tenant") actually true, and `constants.test.ts` now asserts both directions so a later
  "simplification" back to a row cap fails.
- **`text` left the browser.** The grid projection carries metadata only — no `text`, and also no
  `tenantId`/`contentHash`. This is the CONCERNS.md "raw vault content is over-exposed to the
  browser" item, closed as a side effect.
- **Three surfaces that read `text` off the grid were repaired onto `vault.vaultDocText`**, a
  tenant-scoped fail-closed-as-null one-document read: the preview pane, the onboarding intake poll,
  and the voice dropped-brief banner.
- **Five cap literals became one declaration.** `Dropzone.tsx` (2 consts, 2 error strings, 1 helper
  line) and `vault.ts` (2 server messages) all now resolve from `@pikar/vault/constants` — the
  **subpath**, verified not to pull SheetJS into the client bundle.
- **The vault UI has test coverage for the first time.** `packages/core/src/vaultSurface.test.ts`,
  6 tests, mutation-verified.

## Decisions Made

- **The bound is rows AND bytes, not rows.** The plan specified `.take(VAULT_GRID_PAGE)` with
  `VAULT_GRID_PAGE = 200`. That does not satisfy the plan's own must-have truth. Implemented as a
  `for await` stream over the index with a text-byte accumulator, breaking on either bound. Both
  constants live in `@pikar/vault/constants` with the arithmetic in the comment.
- **`vaultStats` reads the same window, not five per-status `.take(cap+1)`s.** The plan offered the
  per-status shape; one shared scan is strictly cheaper (one pass, not five), states the ceiling
  once, and makes it impossible for the tiles to describe a different set of rows than the cards.
  The maintained-counter alternative was rejected outright: it needs a schema field and `schema.ts`
  is closed for this phase.
- **`capMB()` rather than `DocGrid`'s `fmtSize`.** The plan said to import `fmtSize`. `fmtSize` is
  binary (`1024*1024`), and the caps are decimal by construction, so `fmtSize(VAULT_FILE_CAP_BYTES)`
  renders **"190.7 MB"** for the constant the product calls 200 MB — the exact class of drift this
  task exists to delete. `capMB` is one line and lives beside the caps so the server error message
  and the client copy cannot disagree.
- **The `category` filter runs over the bounded window.** There is no `by_tenant_category` index and
  `schema.ts` is closed, so a tenant past the window can see fewer rows on a narrow tab than exist.
  Documented at the query and in the playbook; upgrade path is that index or folder drill-in.
- **The `folderId` arg landed now, unused.** It costs three lines inside `readVaultPage` and means
  the drill-in plan does not have to reopen this query. The lenient join is free: cancel deletes the
  folder row, and an unresolvable id simply matches nothing on `by_tenant_folder`.
- **Requirements left `Pending`.** VALT-05 and VALT-14 are this plan's frontmatter claim. VALT-14
  (the cap) is arguably satisfied; VALT-05 names folder behaviour that does not exist yet. Following
  15.3-01's precedent (and 17.1-01's reverted early flip), `requirements mark-complete` was NOT run
  — a half-satisfied id ticked green is a false signal for the next planner.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's row-only bound does not bound the read**

- **Found during:** Task 1
- **Issue:** `.take(VAULT_GRID_PAGE)` with `VAULT_GRID_PAGE = 200` reads 200 whole rows; at
  `VAULT_EXTRACT_CHAR_CAP` (400k chars) that is ~80 MB against a 16 MiB cap. The plan's own
  must-have ("renders with 400 documents — does not exceed the read cap") would still have failed.
- **Fix:** `VAULT_GRID_READ_BUDGET_BYTES` (8 MiB) alongside the row cap; `readVaultPage` streams and
  breaks on either. Pinned in `constants.test.ts` in both directions.
- **Files:** `packages/vault/src/constants.ts`, `packages/backend/convex/vault.ts`,
  `packages/vault/src/constants.test.ts`
- **Commits:** `fefb9e4`, `bc72c41`

**2. [Rule 3 - Blocking] Three shipped consumers read `text` off `listVaultDocs`**

- **Found during:** Task 1 (before touching the query — the consumer scan the plan's critical note
  demanded)
- **Issue:** `PreviewModal.tsx` renders `doc.text` as the whole preview pane; `onboarding/page.tsx`
  polls it to feed the opening turn; `voice/AbnormalBriefBanner.tsx` seeds a cockpit plan from it.
  Dropping `text` breaks all three. **The banner would NOT have been caught by the typechecker** —
  it cast the query result to a local `VoiceBrief` type, so `brief.text ?? ""` would have compiled
  and shipped an empty plan seed.
- **Fix:** added `vault.vaultDocText` (one doc, by id, tenant-scoped, fail-closed as null) and moved
  all three onto it. The banner's cast was **deleted** rather than updated, so its row type now comes
  from the query; and it refuses to seed rather than seeding empty text.
- **Files:** `packages/backend/convex/vault.ts` + the three components
- **Commit:** `fefb9e4`

**3. [Rule 3 - Blocking] Four backend tests asserted on dropped fields**

- **Found during:** Task 1
- **Issue:** `vaultGround.test.ts` and `research.test.ts` asserted isolation via `d.tenantId`;
  `createdDocs.test.ts` asserted `row.text`/`row.contentHash`; `research.test.ts` read `asB[0]?.text`.
- **Fix:** isolation now asserted on ids (what a caller actually feels), content assertions moved to
  `vaultDocText` or `ctx.db.get`. `research.test.ts`'s isolation test was **strengthened** — it now
  also proves tenant B cannot read tenant A's text through the new public query.
- **Commit:** `fefb9e4`

**4. [Rule 2 - Missing critical] The `capped` flag needed a user-visible rendering**

- **Found during:** Task 2
- **Issue:** The plan's Task 2 ends at the server. A `capped: true` that no surface renders means the
  tiles silently under-report at scale — the "honest manifest" spirit of the phase inverted.
- **Fix:** `VaultStats.tsx` renders `200+` and one plain sentence (a "+" alone encodes meaning in a
  glyph, BRAND §6). Wrapping the tile grid in a fragment made biome re-indent the JSX body; no tile
  markup, token or copy changed beyond the value formatter, and that is named in the commit message.
- **Commit:** `034e28a`

**5. [Rule 1 - Bug] Two stale prose mentions of the old cap**

- **Found during:** Task 3
- **Issue:** `vault.ts`'s `vaultUpload` docblock and `vaultExtract.ts:67` both stated "100 MiB",
  which became false the moment the constant changed.
- **Fix:** the docblock now names the constants; `vaultExtract.ts` says "200 MB since 15.3-02".
- **Commit:** `36d2944`

**6. [Rule 2 - Missing critical] Guards the plan did not name, added to the scan**

- `no doc.text on the surface` — the projection contract, i.e. the guard against re-introducing this
  exact defect from the UI side, plus `toContain("api.vault.vaultDocText")` so the guard is not

- `not.toContain("200 * 1000 * 1000")` and `not.toMatch(/100 MB/)` — the plan guarded the OLD
  literals; the NEW one re-typed is the same defect wearing a new number.
- **Commit:** `e0a2c5e`
