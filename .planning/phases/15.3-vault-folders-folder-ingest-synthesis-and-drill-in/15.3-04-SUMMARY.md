# Phase 15.3 Plan 04: Folder Ingest Orchestration Summary

**A folder now ingests as one bounded, cancellable unit: extraction runs on a named `vaultIngestPool` at parallelism 6 instead of flooding the deployment scheduler, the 15-minute stall clock starts when work starts instead of when it queues, completion is counted on the folder row through the only two terminal writers, and cancel settles the reservation and deletes the row without touching a single document.**

## Accomplishments

- **The delivery spine is protected by construction.** `vault.scheduleExtraction` — the ONE scheduling helper, inherited by `vaultUpload`, `sweepPendingExtraction` and `retryExtraction` — now enqueues on `vaultIngestPool` with `maxParallelism: VAULT_INGEST_PARALLELISM (6)`, asserted strictly below the smallest deployment class (8). The shared `WorkflowManager` was left untouched, and its real number (25, from `@convex-dev/workflow`'s own default, not workpool's 10) is now recorded correctly in code and playbook.
- **Fabricated failures at queue depth are gone.** `EXTRACTION_WATCHDOG_MS` moved from `scheduleExtraction` to `vault.markExtracting`. Proven by the plan's own before/after: the two watchdog tests were RED before the move (`vaultUpload` armed 1 watchdog) and GREEN after (arms 0; `markExtracting` arms exactly 1 at +15 min) with no test edit.
- **A folder reaches `complete` exactly once**, replay-safe, read-cheap, and after its last member — including the two degenerate cases counters alone cannot reach (an all-duplicate folder, and a member finishing before its siblings are uploaded).
- **Cancel writes zero `vaultDocuments` rows** and still stops new spend, via a folder-scoped work-start gate rather than the unscopeable `pool.cancelAll`.
- **Nine mutations were applied to the source, observed RED and reverted** — the suite is sampled, not merely green.

## Decisions Made

1. **`pool.cancelAll` is not used, and cancel stops work at work-start instead.** See "Deviations" #1 — this is the single largest departure from the plan text.
2. **`reserveFolder` runs AFTER the members are uploaded, and is the close signal.** The plan left the ordering implicit; both locked invariants force it. Recorded at length in `vaultFolders.ts`'s header and the playbook.
3. **`watchdogStalled` narrowed to `extracting` only**, as the necessary other half of the arming move. Keeping `pending_extraction` would re-create the same fabricated failure through the retry path: attempt 1's clock, fired at T+15, killing a healthy retry queued behind 400 folder members.
4. **The refund settles at the click**, not "after the last in-flight action" — the latter is unimplementable once the row is deleted. Shown safe by the existing capacity clamp; the residual (under-refund if a second folder reserves in the gap) is stated in code and playbook.
5. **The plan's Task 5 item 4 test text ("refund equals reservation minus spend") was written against shipped behaviour instead.** `settleFolder` credits back the FULL `reservedCents` on purpose: `reserveFolderInner` debited the estimate and `recordSpend` debits actual cents separately, so subtracting spend here would charge the tenant twice.
6. **Folder members are always inserted at `pending_extraction` and dispatched by `reserveFolder`**, including searchable text files — no cent may be spent before the reservation is held.
7. **`tryComplete`'s `>=` is defence in depth and the test file says so.** No reachable sequence distinguishes it from `===` while the transition guard holds; claiming a mutation for it would have been a false positive.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 4 → resolved in-plan] `pool.cancelAll` is not folder-scoped and is not tenant-scoped**
- **Found during:** Task 3 (`cancelFolder`)
- **Issue:** The plan specifies "`pool.cancelAll` for the folder's enqueued work". The shipped component (`@convex-dev/workpool@0.4.7`, `src/component/lib.ts:156`) takes `{ before?, limit? }` and nothing else: it pages the pool's entire `work` table and cancels every pending item — every folder, every tenant, and every single-file upload queued at that instant. Per-item `pool.cancel` needs the `WorkId` the enqueue returns, and nothing persists one (`schema.ts` is closed for this phase). Worse, combined with Task 2's watchdog move, foreign members killed by a stray `cancelAll` would strand at `pending_extraction` with no clock, so one user's cancel would permanently strand another user's reservation.
- **Fix:** cancel does not touch the pool. `vault.markExtracting` refuses to start work whose `folderId` no longer resolves and fails the row `folder_cancelled`; `extractDoc`/`transcribeDoc` return early on `{ ok: false }`. This is folder-scoped and tenant-scoped by construction, costs one `db.get` per attempt, and delivers a strictly better "no NEW spend".
- **Files modified:** `vaultFolders.ts`, `vault.ts`, `vaultExtract.ts`, `vaultTranscribe.ts`
- **Verification:** mutation M9 (drop the gate) → RED on "a queued member of a cancelled folder refuses to start work and fails honestly".
- **Committed in:** `0ed56c5`

**2. [Rule 1 - Bug] `retryStuckIngests` read a dangling `folderId` as "still reserved"**
- **Found during:** Task 3
- **Issue:** `vaultIngest.ts` used `d.folderId ? { rail: "ingest", reserved: true } : {}`. Cancel deletes the folder row and leaves `folderId` dangling, and `preCall` waves `reserved: true` ingest work through on the kill switch alone — so an ops sweep would spend the $25 window with no reservation and no folder to settle against. Its own `ponytail:` note named 15.3-04 as the owner.
- **Fix:** resolve the id (`ctx.db.get`) before deriving the rail.
- **Files modified:** `vaultIngest.ts`
- **Committed in:** `0ed56c5`

**3. [Rule 3 - Blocking] The convex-test scheduling observable broke on the pool swap**
- **Found during:** Task 1
- **Issue:** `vault.test.ts` and `vaultSweep.test.ts` assert on `_scheduled_functions` filtered by `/vaultExtract|vaultTranscribe/`. A workpool writes its `work` row and schedules its main loop inside the COMPONENT's namespace, and convex-test scopes `_scheduled_functions` per component with no component-scoped `t.run` — so those helpers return `[]` and ~14 assertions silently invert.
- **Fix:** the two suites assert the scheduling DECISION through a `vi.spyOn` on the exported pool, in the same `{ name, args }` shape the system-table rows had (so no assertion body changed). The suites that only need the enqueue to succeed — `vaultExtract`, `vaultTranscribe`, `guardrails` — register `vaultIngestPool` and drive the REAL pool end to end, so the component is not left unexercised.
- **Files modified:** `vault.test.ts`, `vaultSweep.test.ts`, `vaultExtract.test.ts`, `vaultTranscribe.test.ts`, `guardrails.test.ts`
- **Committed in:** `289aa0c`

**4. [Rule 2 - Correctness] The premature-completion race the plan did not name**
- **Found during:** Task 3
- **Issue:** With `reserveFolder` flipping to `ingesting` before members upload, `memberCount` grows one upload at a time — so a 3-file folder whose first file finished before its second was uploaded hits `terminalCount === memberCount` at 1 === 1, settles its reservation and would synthesise a digest over a third of itself. The status CAS does not help; it only stops a SECOND completion.
- **Fix:** members are only accepted while the folder is `reserving`; `reserveFolder` is the close signal, takes the money, flips to `ingesting`, evaluates completion once (for the all-duplicate case) and then dispatches. `vaultUpload` throws `folder not open for members` after the close.
- **Verification:** mutation M3 (open the folder at `ingesting`) → 8 tests RED.
- **Committed in:** `0ed56c5`

**5. [Rule 2 - Correctness] The plan's `bumpFolder` snippet double-counts**
- **Found during:** Task 4
- **Issue:** The plan's snippet reads the doc AFTER the patch, so it cannot distinguish a real transition from a replay. Neither terminal writer is idempotent and a workflow mutation whose journal write fails is re-run, so `terminalCount` would overshoot `memberCount`, jump an `===` test, and strand the reservation forever.
- **Fix:** `countTerminal` takes the PRIOR row and counts only a non-terminal → terminal transition; `tryComplete` tests `>=`.
- **Verification:** mutation M1 (drop the transition guard) → RED.
- **Committed in:** `0ed56c5`

**6. [Rule 2 - Correctness] `settleFolder` has no tenant guard**
- **Found during:** Task 3
- **Issue:** It takes a bare `folderId` and reads `folder.tenantId` for the limiter key, so a foreign id would refund and delete another tenant's folder. No such check existed anywhere on the path.
- **Fix:** `cancelFolder` asserts `folder.tenantId === ctx.tenantId` before settling or deleting; covered by a test.
- **Committed in:** `0ed56c5`

**7. [Rule 2 - Never-silent] Refused folders would have parked their members**
- **Found during:** Task 3
- **Issue:** On refusal the folder goes `refused`, but the already-uploaded member rows would sit at `pending_extraction` with nothing to dispatch them — exactly the silent parking 15.2 abolished.
- **Fix:** the refusal path fails every collected member `folder_refused` through the same bounded member walk. Terminal, honest, Retry-able one at a time.
- **Committed in:** `0ed56c5`

**8. [Rule 1 - Documentation bug] The mandated comment about `convex/index.ts` was factually wrong**
- **Found during:** Task 1
- **Issue:** The plan mandates a comment saying the WorkflowManager has no `maxParallelism` "so workpool's default 10 applies to EVERY workflow". `@convex-dev/workflow@0.4.4` declares its OWN `DEFAULT_MAX_PARALLELISM = 25` and resolves `opts ?? config ?? 25`; workpool's 10 is never reached. The `?? 10` cited is the per-execution step channel.
- **Fix:** the comment says 25, and names where the 10 actually lives. Also corrected the now-false "workpool is a test-only devDep" comment in `cockpit.test.ts`.
- **Committed in:** `289aa0c`
