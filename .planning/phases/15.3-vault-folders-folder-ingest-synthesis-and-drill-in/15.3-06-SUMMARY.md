# 15.3-06 — the folder digest (VALT-08, VALT-09, VALT-10)

Executed as a **5-agent workflow** (owner-requested): skill row + read-only recon in parallel, then
a single owner for `vaultDigest.ts`, then tests + playbook, then an adversarial verify pass. The
verify pass is the reason this summary has a second half.

## What shipped

**The digest is a vault document, and it grounds only because its insert calls `startIngest`.**
`origin: "folder_digest"` is inert — there is no `origin` predicate anywhere in retrieval — so the
observable check is `ragEntryId != null`. The mutation that deletes `startIngest` leaves the
`origin === "folder_digest"` assertion GREEN and takes `ragEntryId` RED; both assertions sit on
adjacent lines in the test so the difference is visible on the page.

- **`folder-digest` skill row** in all five places, **deliberately ungated** — `run-eval-golden.mjs`
  derives `--skill` from `GATED_SKILLS` and drives `runCockpitAgent` over text fixtures, so no
  fixture can assemble a folder manifest; gating would deadlock the row at v1 on its first body
  edit. No version pinned anywhere.
- **V8 `internalAction`** (no `"use node"`), skill loaded FIRST and fail-closed, `scanText` before
  the model, `priceUsage` on the **ingest** rail. Members are gathered a page at a time under a char
  budget; member `text` is never collected wholesale.
- **No `folderId` on the digest** — the recursion guard. The folder points at it via `digestDocId`,
  so it cannot enter its own member set on either the first build or a rebuild, and no
  self-exclusion predicate is needed anywhere.
- **Staleness** is a real set difference bounded by the folder's own `memberCount`, not the global
  `DRIFT_SCAN_CAP`. Nothing costs a cent until the user clicks Rebuild.

## The verify pass — three defects found after the suite was already green

The adversarial agent was instructed to check the **source on disk, not the implementer's report**,
and to default to VIOLATED/UNPROVEN without evidence. It re-ran three mutations itself rather than
trusting them. It found three majors, and **all three are consequences of the one decision this plan
is proudest of: the digest carries no `folderId`.**

> **The general lesson, worth carrying forward: a deliberate absence needs its own sweep of
> everything that used to find the thing by the field you removed.**

| # | Defect | Repair |
|---|--------|--------|
| 1 | `unincorporatedForFolder` bounded ROWS, not BYTES. Convex has no projection, so ~40 max-size members exhaust the 16 MiB cap — **inside `folderDigestState`, the drill-in banner read**, so the failure was the folder page THROWING, not a wrong number | streams like `readVaultPage` (rows OR `VAULT_GRID_READ_BUDGET_BYTES`), **newest-first** |
| 2 | `cancelFolder` orphaned the digest — no status guard on cancel, and `walkFolderMembers` keys on a `folderId` the digest does not have. It survived as a `ready`, embedded, **groundable** document describing a deleted folder, unreachable once `digestDocId` died with the row | cascaded through `vault.deleteVaultDoc` before the folder row is deleted |
| 3 | A budget refusal was **completely silent** — the build is scheduled and its return value discarded, `digestBuiltAt` never set (so the `already_built` belt does not apply and nothing retries), folder indistinguishable from one never attempted | one refs-only `folder.digest_refused` audit row, on the only refusal that leaves no other evidence |
| + | `vaultIngest.retryStuckIngests` derives the spend rail by resolving `d.folderId` — null for a digest — so an operator sweep charged its re-ingest to the **cockpit's $5 token window** | the ingest rail via `origin === "folder_digest"`, deliberately **without** `reserved` (no reservation exists behind a digest) |

`.order("desc")` is what makes the byte bound honest rather than merely safe: unincorporated members
are by construction the ones added since the last build, so they sort to the front and an early stop
has already seen them. **Residual, stated:** a member rescued `failed → ready` by
`vaultSweep.retryExtraction` is newly unincorporated but OLD by `_creationTime`, so in a folder whose
text exceeds the budget it can be missed until the next build. Under-reporting a rescued member is a
stale banner; throwing is a dead page.

**Ruled SAFE with evidence, so nobody re-litigates:** the sealing interaction (three independent
reasons a mid-ingest digest cannot leak — the action refuses a non-`complete` folder, the schedule
commits with the transaction that flips the status, and the row is `processing` until `markReady`
writes `ragEntryId`); the recursion guard on the rebuild path; §2/§4/§5 compliance.

## Notes for the next plan (15.3-07, the drill-in UI)

- `folderDigestState` returns `{state, unincorporatedCount}` and is the banner's one read. It is
  bounded and can under-report at extreme byte scale — **render the count, never a "definitely
  nothing new" claim.**
- The digest is reached by `folder.digestDocId` + one `ctx.db.get`, never by a member query.
- One test-seam wart is deliberate and documented: the cancel test clears the digest's `ragEntryId`
  first, because the offline embed returns a `smoke::<hash>` sentinel that is not an id of the rag
  component's `entries` table and `deleteVaultDoc`'s `rag.deleteAsync` half rejects it. Real entry
  ids are fine.
- `graphify update .` + `node scripts/extract-convex-edges.mjs` still owed once all lanes land —
  `graphify-out/*` carries another lane's uncommitted modifications.
