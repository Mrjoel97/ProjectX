# Phase 03.4 Plan 01: recipientBodies Content-Plane Foundation Summary

Added `plans.recipientBodies` — an optional address-keyed map (`v.record(v.string(), v.string())`, lowercased address → that recipient's tailored body override; missing key = the shared `body`) — plus the matching `patchPlan` arg, establishing the single content-plane contract every later wave of per-recipient personalization consumes.

## What was built

- **schema.ts** — `plans.recipientBodies: v.optional(v.record(v.string(), v.string()))` added additively next to `greetingName` (no migration, exactly how `attachments`/`candidates`/`greetingName` were added). Content-plane only, never audited (§4).
- **plans.ts** — `patchPlan` gains one optional `recipientBodies` arg. The handler is UNCHANGED — the existing `Object.fromEntries(...filter(v !== undefined))` drop-undefined pattern already persists the new key and preserves a stored map on a partial patch.
- **plans.test.ts** — three cases: patchPlan writes the address-keyed map (getById reads it back verbatim, shared `body` untouched); a subject-only patch leaves an existing map untouched (drop-undefined); a second patch replaces the whole map wholesale.
- **cockpit.md** — §9 playbook: Last verified → 03.4-01; plans.ts Key-files entry notes the new optional `recipientBodies` arg.

## Build-time confirmation (lane flag resolved)

`v.record(v.string(), v.string())` is **accepted by the pinned Convex version (1.42.1)** — it is already used in `telemetry.ts:28`. The documented `v.array(v.object({address, body}))` fallback was **NOT needed**. Waves 2/3 can use the record shape (one lookup by address, no `.find`).
