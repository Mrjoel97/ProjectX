# Phase 3.4: Per-Recipient Personalization (INSERTED) - Research

**Researched:** 2026-07-14
**Domain:** Cockpit send spine extension — per-recipient body tailoring behind the single plan-approval gate (Convex, AI SDK v7 tool-loop, existing governed delivery fan-out)
**Confidence:** HIGH (every claim grounded in the actual Lane-A source at file:line; no external library churn — this is a wiring extension over spine the repo already ships)

## Summary

This phase is a **small, additive wiring extension**, not new infrastructure. The single
most important discovery: **the delivery spine is already per-recipient.** `executePlan`
(cockpit.ts:242-259) already seeds ONE `requests` row per recipient, each with its own
`draft` field (today set to the shared `plan.body`), and `gmail.getForDelivery`
(gmailAuth.ts:120-142) reads the body **per request** as `r.editedBody ?? r.draft ?? ""`.
`deliverApprovedPlan` (deliverApprovedPlan.ts:31-56) loops per `requestId` and calls
`gmail.send({ requestId })`, which resolves that request's own body. So a recipient's
tailored wording only has to land in ITS `requests.draft` — **the send/audit/telemetry/DLQ
spine below `executePlan` needs zero changes.** Personalization is the OPPOSITE of the
Phase 3.3 attachment fan-out (which materialized ONE shared ref for all recipients); here
each recipient's row carries a DISTINCT body while sharing subject/mode/attachments.

The change surface is four small pieces, all inside Lane A: (1) one new optional field on
the `plans` row (`recipientBodies`, keyed by address — append-only optional-field discipline,
no migration, exactly like `attachments`/`candidates` were added); (2) one new governed tool
`personalizeRecipient({ index, instructions })` that mirrors `draftBody` verbatim
(scanText fail-closed → `draftCockpit` → patch) but targets ONE recipient resolved
server-side from a 1-based `#index` (§2-D address-free, exactly like `removeRecipient`);
(3) one line in `executePlan`'s existing seed loop — `draft: recipientBodies[recipient] ?? body`;
(4) a per-recipient body section on the PLAN card (mirror `PlanAttachments`).

**Guardrails parity is free by construction:** `personalizeRecipient` reuses the identical
`scanText → draftCockpit` path `draftBody` already uses, so PII redaction and cost governance
(`preCall`/`recordSpend` around the `runCockpitAgent` turn) are the SAME code. Per-recipient
audit/telemetry already exist — each `requests` row already has its own server-minted
`correlationId` and emits its own `gmail.sent` audit + terminal telemetry. **No new audit
event is needed.**

**Primary recommendation:** Add `plans.recipientBodies` (optional, keyed by lowercased
address); add a `personalizeRecipient` tool mirroring `draftBody`; change the ONE `draft:`
line in the executePlan seed loop; render per-recipient bodies on the PLAN card. Force
`individual` mode whenever any personalization exists (a group send is one combined email —
personalization is inherently per-individual). Do NOT touch `deliverApprovedPlan`,
`gmail.send`, `getForDelivery`, the CAS, or the single `workflow.start` call site.

### Pattern 1: The new governed tool mirrors `draftBody` exactly
**What:** `personalizeRecipient({ index, instructions })` — resolve `#index` → address
server-side, scan `instructions` fail-closed, call `draftCockpit`, patch the body into
`recipientBodies[address]` (NOT the shared `body`).
**When to use:** The agent calls it when the user asks to tailor one recipient's wording.
**Example (grounded in the existing `draftBody`, llm.ts:684-718 + `removeRecipient` index resolution):**
```typescript
// Source: pattern composed from llm.ts:644-656 (index→address, server-side) + llm.ts:695-717 (draftBody scan→draftCockpit→patch)
personalizeRecipient: tool({
  description:
    "Tailor the email wording for ONE recipient at the given 1-based #index, from a plain-language instruction. The shared body is unchanged; only that recipient gets the tailored version.",
  inputSchema: jsonSchema<{ index: number; instructions: string }>({
    type: "object",
    properties: {
      index: { type: "number", description: "1-based #index of the recipient to tailor." },
      instructions: { type: "string", description: "How this recipient's wording should differ, in plain language." },
    },
    required: ["index", "instructions"],
    additionalProperties: false,
  }),
  execute: async ({ index, instructions }): Promise<string> => {
    const plan = await readPlan();
    const recipients = plan.recipients ?? [];
    const i = index - 1;
    if (i < 0 || i >= recipients.length)
      return `Rejected: there is no recipient #${index}. The plan has ${recipients.length}.`;
    const address = recipients[i]!;              // resolved server-side — the model never handles it (§2-D)
    const scan = scanText(instructions);          // redact BEFORE the model (GRDL-01/02, §4) — same as draftBody
    if (!scan.ok) throw new Error("cockpit: personalize-intent scan failed");
    const draft = await ctx.runAction(internal.llm.draftCockpit, {
      tenantId, safeText: scan.value.safeText, safeTextHash: await contentHash(scan.value.safeText),
      greetingName: plan.greetingName,
    });
    const next = { ...(plan.recipientBodies ?? {}), [address]: draft.body };
    await ctx.runMutation(internal.plans.patchPlan, { planId, recipientBodies: next });
    return `Tailored the wording for recipient #${index}.`;
  },
}),
```
> The signature intentionally takes `instructions` (how to differ) not a full body — the
> model describes intent, `draftCockpit` produces the wording, exactly as `draftBody` does.

### Anti-Patterns to Avoid
- **Keying overrides by index:** a `removeRecipient`/reorder shifts indices and silently
  mis-assigns a tailored body to the wrong person — a wrong-recipient liability. Key by address.
- **Duplicating the shared body into every override:** store ONLY genuine overrides; let
  non-personalized recipients fall back at seed time (no duplication, matches the shared-attachment
  "materialize once" ethos of 3.3).
- **A second `"use node"` module or a new LLM action:** reuse `draftCockpit`. A new node module
  re-triggers the TS circular-inference cliff (playbook invariant "No NEW use node modules").
- **Personalizing in group mode:** a group send is one combined email. Block or force-individual
  (Pitfall 1) rather than silently dropping the tailoring.
- **Touching the delivery spine:** `deliverApprovedPlan`/`gmail.send`/`getForDelivery`/the CAS/the
  single `workflow.start` are all correct as-is. The whole feature lands above them.

## Common Pitfalls

### Pitfall 1: Personalization ⊗ group mode
**What goes wrong:** Group mode collapses recipients into a single comma-joined `requests` row
(cockpit.ts:221) with ONE body. A per-recipient override cannot apply.
**Why it happens:** The two features are semantically exclusive — a group thread is one email.
**How to avoid:** When any `recipientBodies` entry exists, force `mode: "individual"` in
`executePlan` (or refuse in `proposePlan` with a clear message telling the agent to switch to
individual). Recommend: `proposePlan` refuses a `group` plan that has personalization, and the
`cockpit-agent` skill explains "tailoring requires individual sends."
**Warning signs:** A group plan with `recipientBodies` set; a joined row whose body isn't the shared one.

### Pitfall 2: Index drift after a recipient edit
**What goes wrong:** User personalizes `#2`, then removes `#1`; an index-keyed override now points
at the wrong person.
**Why it happens:** `recipients` is an ordered array the agent edits mid-conversation.
**How to avoid:** Key overrides by lowercased **address**, not index. Filter orphaned overrides
(addresses no longer in `recipients`) at the `executePlan` seed step — harmless, no error.
**Warning signs:** A `recipientBodies` key not present in `recipients`.

### Pitfall 3: stepCountIs(8) ceiling on many recipients
**What goes wrong:** Asking to personalize 8+ recipients in ONE turn exhausts the loop's
`stepCountIs(8)` bound (llm.ts:911) before a `proposePlan`.
**Why it happens:** Each `personalizeRecipient` is one tool step; many in one turn hit the cap.
**How to avoid:** The skill should personalize conversationally (one/a few per turn) and the loop
already degrades gracefully — the ceiling makes the agent ASK rather than loop (playbook invariant).
Document as expected; not a blocker for realistic recipient counts. Note in Open Questions if the
beta expects large lists.

### Pitfall 4: Shared `greetingName` vs per-recipient greeting
**What goes wrong:** `greetingName` is a single plan field set from resolution pick #1
(cockpit.ts:125). A personalized body for a DIFFERENT recipient could open "Hi <pick-1-name>,".
**Why it happens:** Greeting is currently shared, not per-recipient.
**How to avoid:** For slice 1, let the `instructions` carry the intended greeting (the drafter
honors explicit intent), OR pass no `greetingName` on personalized drafts and let the instruction
drive it. Keep the shared `greetingName` for the shared body. Flag richer per-recipient greeting as
a ceiling if the human-verify surfaces it.

### Pitfall 5: Redaction/refs-only on the new field
**What goes wrong:** `recipientBodies` is raw drafted content; if it ever reached an audit/DLQ/
telemetry payload it would violate §4.
**Why it happens:** New content-plane field.
**How to avoid:** It lives ONLY on the `plans` row (content plane) and flows into `requests.draft`
(content plane) — the exact planes `body`/`subject` already occupy. Extend `llmRedaction.test.ts`
to assert `recipientBodies` never appears in any audit/DLQ write, exactly as it asserts today for
`recipients`/`subject`/`body`.

   - What we know: personalization is exclusive with group send (Pitfall 1).

   - What we know: `greetingName` is a single shared field.
   - What's unclear: whether the human-verify will demand each recipient's own greeting name.
   - Recommendation: slice 1 drives greeting via the personalization `instructions`; note a
     per-recipient greeting map as a ceiling if verify surfaces it.

3. **Schema shape: `v.record` support in the pinned Convex.**
   - What we know: `v.record(v.string(), v.string())` is standard current Convex.
   - What's unclear: nothing observed against it, but the plan should confirm at build time.
   - Recommendation: prefer `v.record`; fall back to `v.array(v.object(...))` if the pinned
     version rejects it (functionally equivalent, slightly more verbose lookup).
