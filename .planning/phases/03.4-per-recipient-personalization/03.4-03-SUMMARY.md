# Phase 03.4 Plan 03: executePlan Seed Override + PLAN Card Per-Recipient Bodies Summary

Wired the Wave-1 `recipientBodies` field into its two consumer ends for CKPT-03. Backend: the ONE `draft:` line in `executePlan`'s existing per-recipient seed loop now reads `(plan.recipientBodies ?? {})[recipient] ?? body`, so each recipient's `requests.draft` carries its DISTINCT tailored body while the `goal` (subject) and `attachmentRefs` stay SHARED — the pivotal research finding is that the delivery spine is ALREADY per-recipient (`getForDelivery` reads `body := editedBody ?? draft` per request row), so `deliverApprovedPlan`/`gmail.send`/the CAS/the single `workflow.start` needed ZERO changes. Frontend: a new `PlanRecipientBodies` PLAN-card section (mirrors `PlanAttachments`) shows each recipient's tailored/shared body before the single Approve. Plus the `cockpit.test.ts` distinct-draft executePlan case.

## What was built

- **cockpit.ts — executePlan seed override (ONE line)**: `draft: body` → `draft: (plan.recipientBodies ?? {})[recipient] ?? body`. Keyed by the RAW `recipient` value the loop iterates from `plan.recipients` — the SAME string `personalizeRecipient` wrote in Wave 2 (llm.ts `recipients[i]` at write), so the lookup can't miss. A non-personalized recipient falls back to the shared `body`; an orphaned key (address no longer in `recipients`) is simply never read (harmless, no filter needed); group mode's comma-joined `recipient` misses the address key and falls back to the shared body by construction (`proposePlan` already refuses group+personalization). Everything else in the seed loop — the per-recipient server-minted `correlationId`, the shared `goal`/`attachmentRefs`, the `requests` row shape, the CAS, the Gmail pre-check, and the SINGLE `workflow.start(deliverApprovedPlan)` call site (cockpit.ts:268, grep-verified sole starter) — is untouched.
- **cards.tsx — PlanRecipientBodies section**: mirrors `PlanAttachments`. One row per `plan.recipients` with the recipient's address chip + a "tailored"/"shared body" tag + the body (looked up via the exact-string key `overrides[r]`, truncated `.slice(0,240)` like the PREVIEW). Read-only (tailoring happens in chat, like `DraftCard`). Rendered in `PlanCard` right after the PREVIEW and before `PlanAttachments`. Renders NOTHING when no recipient has an override (the shared PREVIEW already covers the same-content case) — the breakdown appears only when tailoring exists (SC1). Reuses the existing `label`/`dim`/`chip` tokens (ponytail — no new component).
- **cockpit.test.ts — distinct-draft case**: seeds a proposed plan (3 recipients, `recipientBodies` with 2 tailored + 1 orphan `z@` key) via the `withDelivery()` workflow-component registration (03.3-05), runs `executePlan` end-to-end, and asserts each recipient's `requests.draft` is its distinct override, the non-personalized recipient falls back to the shared `body`, the `goal` (subject) is shared across all three, and the orphan key adds no row (3 rows for 3 recipients).
- **cockpit.md (§9)**: `Last verified` → 03.4-03; documents the seed override + the PLAN card `PlanRecipientBodies` section as the two consumer ends; notes CKPT-03 stays IN PROGRESS until Wave 4.
