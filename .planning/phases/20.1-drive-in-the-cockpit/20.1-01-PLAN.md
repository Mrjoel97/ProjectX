<objective>
Let the Executive Agent **read** the user's Google Drive: list folders, drill down, and answer
"which folder has the Q3 numbers". Nothing else.

**The scope does not move and the money does not move.** `drive.readonly` stays the whole grant,
so there is no new consent, no verification wall and no write risk; and the import stays a human
click in the vault picker, so the model has no path to the ingest budget. This phase makes Drive
*legible* to the agent — it deliberately does not make Drive *actionable* by it.
</objective>

  <files>packages/backend/convex/vaultDrive.ts, packages/backend/convex/vaultDrive.test.ts</files>
  <action>
A `tenantAction` `findInDrive({ query: string })` returning `{ ok: true; hits: DriveHit[] }` or the
same refusal union `listDriveFolders` already returns. A hit is
`{ id, name, kind: "folder" | "file", parentName?, readable }`.

**This is the one genuinely new capability.** The picker walks a tree; "which folder has the Q3
numbers" is a search, and Drive already answers it: `q=name contains 'Q3' or fullText contains 'Q3'`
with `trashed=false`. **Both shared-drive params, through `driveUrl` — the existing helper, never an
inline URL** (the source scan in `dispatchGuard.test.ts` forbids one, and a param-less search
returns 200 with an empty list on a shared drive).

⚠ **THE QUERY IS USER TEXT GOING INTO DRIVE'S QUERY LANGUAGE.** `DRIVE_ID_RE` guards ids; it does
not guard this. A `'` in the search term closes the literal and rewrites the query. Escape it
(`replace(/'/g, "\\'")`) or reject it — **decide and test it**, because percent-encoding does
nothing here. This is the same trust boundary 15.3-09 found late.

`pageSize: 20` and no pagination: this answers a question in a conversation, not a file browser.
Mark the ceiling with `ponytail:`.

Tests: (a) the `q` sent contains both `name contains` and `trashed=false` — **assert on
`fetchSpy.mock.calls`, not on the stubbed response**, per the rule vault.md records; (b) a quote in
the query cannot alter the `q` structure; (c) a pre-widening grant returns `reauth` with `fetch`
never called.

   human approves, riding `executePlan`'s `armFor(actionTypeOf(plan.kind))` switch. That is a phase
   of its own — a new plan kind, a new card, a new arm — and it should not be smuggled in here.
2. **Creating a Drive folder from Pikar is NOT possible** and this phase does not move toward it:
   it needs `drive.file` or full `drive`, and full `drive` is a RESTRICTED scope requiring a CASA
   assessment — the same verification wall as the social integrations, which is blocked on the legal
   entity existing.
3. **Should `findInDrive` search file CONTENT (`fullText`) or only names?** Content search is one
   `q` clause and much more useful; it also means Drive matches on documents we may then quote a
   name for. Names-only is the conservative default — owner's call at planning time.
