<objective>
Ship D9-REVISED's async research path: a `dispatchResearch` tool the executive agent calls mid-turn
which STAGES a memo plan row, SCHEDULES the governed specialist run, and returns immediately —
with the findings arriving as an approvable plan card while the live `agentSteps` trace streams.

Purpose: hosted `web_search` is the slowest operation in the system and D10 requires several
deliberately varied searches per run. Holding the user's conversational turn for that is the wrong
shape, and — the finding that killed the in-loop design — a loop that overruns its clock THROWS
(`llm.ts:1789`), killing the whole executive turn and discarding every partial finding. Async moves
the failure into the background where D11's wall-clock row catches it as a governed outcome.
Output: one optional prompt seam, one staging mutation, one internalAction, one tool, one honest
fallback body, and the tests that prove the guards are inherited rather than re-implemented.
</objective>

<two_derivations_the_planner_owes_you>
D9-REVISED explicitly told the planner to RE-DERIVE two things the superseded D9 had decided.
Both were re-derived against the shipped source; here are the conclusions and the reasoning, so

### 1. The `dispatchGuard.test.ts:16-24` amendment is VOID. Leave that comment ALONE.

Read it (it is 9 lines of prose above the first assertion). It argues against **a `generateText`
inside a tool's `execute`** — "a second agent loop running INSIDE the first one's step budget" —
and it prescribes the fix in as many words: *"dispatch RETURNS to the orchestrator, which starts
the specialist loop as its own governed call."*

**That is a verbatim description of what this plan ships.** The tool stages and schedules; the
specialist loop starts as its own governed call, in its own scheduled action, with its own step
budget, its own clock and its own `recordSpend`. Nothing runs inside the executive's step budget.
The comment is not merely un-contradicted — it is now SATISFIED, and it was the comment that
predicted the right architecture. D9 asked for the amendment because the in-loop
`ctx.runAction`-from-a-tool shape would have contradicted it; that shape is not being built.

**Deleting or "amending" a guard-comment that a later design vindicated would be vandalism on a
guard doing its job.** Do not touch lines 16-24. `dispatchGuard.test.ts` is deliberately ABSENT
from this plan's `files_modified` — if you find yourself opening it, the design has drifted back
toward an in-loop call and that is the thing to re-examine, not the file. (Its two shipped
assertions — zero `generateText` in `dispatch.ts`, exactly one tool-bearing call site in `llm.ts` —
stay untouched regardless, and 16-05 already extends that file in wave 3 for the SSRF scan.)

### 2. The per-turn envelope closure does NOT apply, and the shipped `collecting` interlock replaces it.

The closure existed because an in-loop tool could dispatch repeatedly inside ONE turn, and
`governedDispatch` derives a fresh 25%-of-remaining-day envelope whenever `envelopeCents === 0`
(`dispatch.ts`, guard 4) — so eight dispatches would have taken eight envelopes. It threaded
`{envelopeCents, spentCents}` from each result into the next call.

**A scheduled tool never sees a result**, so that thread cannot exist. But the hazard it guarded
does not either, for a stronger reason: `plans.by_thread` is `.unique()`, so a thread has exactly
ONE plan row, and a research run OWNS it at `status: "collecting"` until `landSpecialistResult`
flips it. Task 2's staging rule refuses to recycle a `collecting` row, so **a second research
dispatch on the same thread is refused while the first is in flight — by a PERSISTED interlock,
not an in-memory per-turn closure.** That is strictly stronger: it holds across turns, across
requests, and across a fallback retry that rebuilds the tool record.

Each research run therefore takes exactly ONE freshly-derived root envelope — byte-identical to
what every `actOnGap` dispatch does today. No new arithmetic, nothing to thread, nothing to drift.
The test that used to prove the closure becomes the test that proves the interlock (Task 3).
</two_derivations_the_planner_owes_you>
