<objective>
Land the findings in the vault with a queryable freshness stamp, from the DISPATCHER — never from
a tool the specialist could call — as the SECOND artifact of a research run, after 16-06's memo
plan card has already landed.

Purpose: ACTN-03's "storing findings in the vault", SC#2's freshness stamp, and SC#3's isolation
assertion. The storage choice does most of the work for free: once findings are an ordinary vault
document, every later read arrives through `searchVault`, which already wraps it in the shipped
`<vault_context …>` fence — web-derived text is fenced on every downstream read without a second
fencing mechanism. Embedding, graph extraction, retrieval, tenant scope, delete-cascade and the
preview modal all come along.
Output: one new non-node module, one persist call from the scheduled research action, one refs-only
audit row, one test file.
</objective>

<why_the_dispatcher_writes_it>
The research specialist has NO write capability — that is SC#1's whole containment (D4). So the
findings write CANNOT be a tool the specialist calls. It is a deterministic, code-owned terminal
that runs AFTER `dispatchAndLand` returns `ok: true`, exactly like `persistNextStepMemo` runs
after the human Approve. If you find yourself granting the specialist a write tool "so it can save
its findings", stop — that is the privilege-escalation path this phase exists to close.
</why_the_dispatcher_writes_it>

<the_two_artifacts_and_why_this_one_is_second>
D9-REVISED put research on the async memo terminal, so a successful run ALREADY produced a
user-visible artifact before this plan's code runs: `dispatchAndLand`'s `finally` calls
`landSpecialistResult`, which flips the staged `collecting` row to `proposed` with
`specialistMemoBody(...)` as its body. **The user has the findings on an approvable card whether or
not the vault write succeeds.**

That ordering is not incidental — it is what makes the error handling honest. Under the superseded
in-loop design a persist failure risked losing work the turn had paid for, so the plan wrapped it in
"return the body anyway". Now the body is already durable on the plan row, so a persist failure
degrades to a narrower, truthful statement: *the findings are on the card but are not yet
groundable*. Audit it and move on. **Do NOT add a retry, a dead-letter, or a compensating write** —
`dispatchAndLand`'s own comment records that the cockpit has never DLQ'd a user-facing turn.
</the_two_artifacts_and_why_this_one_is_second>

```ts
export async function persistNextStepMemo(ctx: MutationCtx, plan: Doc<"plans">)
  : Promise<Id<"vaultDocuments">> {
  const markdown = plan.body ?? "";
  const vaultDocId = await ctx.db.insert("vaultDocuments", {
    tenantId: plan.tenantId,
    title: plan.subject?.trim() || "Next step memo",
    kind: "next_step_memo",
    category: categoryFor({ source: "agent" }),      // → "workspace-docs"
    source: "evaluation",
    mimeType: "text/markdown",                        // in SEARCHABLE_MIME ⇒ chunked + embedded
    size: new TextEncoder().encode(markdown).length,
    contentHash: await contentHash(markdown),
    text: markdown,
    status: "processing",
    createdAt: Date.now(),
  });
  await startIngest(ctx, { vaultDocId, tenantId: plan.tenantId, correlationId: crypto.randomUUID() });
  return vaultDocId;
}
```
