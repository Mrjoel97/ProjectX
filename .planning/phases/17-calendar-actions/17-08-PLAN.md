Provider rules:

- Google supports conditional update/delete with `If-Match`; mismatch is HTTP 412.
- Graph v1.0 **PATCH** management is enabled because Plan 17-07's disposable event-specific probe
  measured `stalePatchStatus: 412` with `stalePatchPreserved: true` — Graph enforces `If-Match` on
  event PATCH and the refused write changed nothing. Revalidate the probe schema/deployment/account
  hash before enabling the Microsoft update branch.
- Graph v1.0 **DELETE** is NOT enabled and cannot be enabled by this plan. The same probe measured
  `staleDeleteStatus: 204` with `staleDeletePreserved: false`: Graph IGNORES `If-Match` on event
  DELETE and the stale delete destroyed the event anyway. There is no optimistic-concurrency
  protection of any kind on that path, so two racing cancels — or a cancel racing an edit — destroy
  an event whose state the caller never saw. See ADR-023.
- The earlier single `supported` boolean COLLAPSED these two results and could only report the
  worse of them, which is why a safe PATCH sat unreachable behind an unsafe DELETE. Read the two
  fields apart; never re-derive a single capability boolean from them. Generic OData or `changeKey`
  reasoning alone is not an acceptable concurrency basis for either verb.
- Graph cancel and delete can send cancellation messages for attendee-bearing meetings. Google
  update/delete can also notify guests. Therefore management is attendee-free only and both adapters
  GET a narrow projection before every write. Do not call `/cancel`; do not add `sendUpdates`.
- Exactly-once update: GET first; if provider state already equals the desired state, return success.
  Otherwise require the expected etag and conditionally write.
- Exactly-once delete (GOOGLE ONLY): GET first; 404/410 means success. Otherwise require etag and
  delete. Microsoft never reaches this path — the refusal is raised before any provider call.

Non-goals — FORBIDDEN, and more tempting after the probe result than before (ADR-023). Both would
let this plan execute as originally written; both are read-modify-write races wearing a seatbelt,
and the measured 204 proves the delete path has no seatbelt at all:

1. **Unconditional PATCH/DELETE** — dropping `If-Match` to make the call work.
2. **GET-then-compare `changeKey`** — reading the event, comparing a version marker in application
   code, then issuing the write. The gap between the read and the write IS the race; moving the
   comparison client-side does not close it, it only hides it from the HTTP status.

Also out of scope: any Microsoft delete/cancel implementation, however guarded. The absence is a
PRODUCT SURFACE (a named refusal), not a hole to be filled by a later executor.
</context>
