Add `proposeCalendarEvent: tool({ ... })`.

**`inputSchema`**: `{ title: string; when: string; durationMinutes: number }`, all required,
`additionalProperties: false`. `when` is the user's natural-language phrasing — the model passes the
*words*, never an instant. `durationMinutes` is a number the model may supply because it is not a clock
reading; clamp it to a sane range (e.g. 15–480) and say so in a `ponytail:` comment.

**Description** (split literals, §5 ceiling): it stages an event onto the plan for the user to approve;
it does NOT put anything on the calendar; the app supplies the current time and timezone.

**`execute`**:
1. `if (!clientContext)` → refuse conversationally, write nothing.
2. `const parsed = parseSendTime(when, clientContext.nowMs, clientContext.tz, CALENDAR_HORIZON_MS);`
   Exhaustive `switch (parsed.kind)` copying `setSendTime`'s shape — every non-`resolved` variant writes
   NOTHING and returns a re-ask. **Never guess a day, never silently pick a time.** Keep the switch
   exhaustive with no `default`, so a new `SendTimeParse` variant becomes a TS error rather than a silent
   fall-through (the `setSendTime:900` comment states this explicitly).
3. On `resolved`:
   ```ts
   await ctx.runMutation(internal.plans.patchPlan, {
     planId, kind: "calendar_event", status: "proposed",
     eventTitle: title, eventStartMs: parsed.epochMs,
     eventDurationMs: clampedMinutes * 60_000, eventTz: clientContext.tz,
   });
   ```
   The title is CONTENT and belongs on the plan row — `schema.ts:184-216` states outright that raw
   content lives in `plans` and NEVER in audit/DLQ. It is wiped by `resetPlan` (wired in Plan 01).
4. Return a confirmation built with `fmtSendInstant(parsed.epochMs, clientContext.tz)` instructing the
   model to confirm the exact time back to the user.
