# Phase 03.2 Plan 05: Resolution Card UI Summary

The user-facing half of SC2: the mailbox surfaces people into the guided conversation. A no-`@`
NAME recipient now renders a **resolution card** in the cockpit's right pane — one section per
unresolved name with clickable contact chips (each carrying a `count`/last-contacted hint), plus a
pre-selected `pendingValid` "already valid" row for same-turn valid addresses. Picking a chip and
clicking "Use these contacts" calls `api.cockpit.resolveRecipients`, folding the pick into the plan
and advancing the conversation to a PLAN — with nothing sent.

## What was built

- **Task 1 — `ResolutionCard` in `cards.tsx`** (commit `7805d62`): a new `CardList` branch dispatched
  when `plan.candidates?.length` is set and the plan is not yet `proposed`/`delivering` (resolution
  happens during `collecting`, before the PLAN). Renders one section per `candidates[]` entry — the
  name heading + its `matches` as clickable chips labeled `displayName · address · {count} msgs,
  {last contacted}` (USER-only hints, never sent to the LLM). Single-match sections pre-select their
  only chip but still require the "Use these contacts" confirm (a name→address is an inference).
  `pendingValid` addresses render as a pre-selected "already valid" row. The action builds `picks`
  from the selected chip per section and calls `useAction(api.cockpit.resolveRecipients)`.
- **Task 2 — activity chip in `ChatPane.tsx`** (commit `631ddbf`): extended the derived `activity`
  string so parked `plan.candidates` shows "Searching your mailbox… pick a contact →", taking
  precedence over the status-milestone chips (candidates only exist during `collecting`). Purely
  derived off the reactive `byThread` plan — no new query, composer + threadId lift untouched.
- **Task 3 — `cockpit-resolve` E2E + `cockpit-report` retrofit** (commit `6a7a494`): a new Playwright
  spec drives name→resolution card→pick→subject/body/mode→PLAN over the offline `SMOKE::` search
  fixture, asserting the `sarah@example.com` chip + hint, the `pendingValid` row, the personalized
  "Hi Sarah" greeting, exactly one Approve, and that NO REPORT card appears (nothing sends). The
  pre-existing `cockpit-report` recipients line was changed to comma-separated so it survives the
  new comma/"and" tokenizer.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] SMOKE draftCockpit now honors `greetingName`**
- **Found during:** Task 3
- **Issue:** The plan's Task 3 asserts the body preview opens with "Hi Sarah", but the offline
  `SMOKE::route=direct_llm::` draft branch in `llm.ts` returned a fixed `Smoke draft for <hash>` body
  that ignored `greetingName` (the greeting was only injected into the prompt sent to the REAL LLM).
  Over the offline E2E path the greeting could never appear, so the assertion was unsatisfiable.
- **Fix:** The SMOKE branch prepends `Hi ${greetingName},\n\n` when `greetingName` is present — the
  root-cause fix that makes SC3 (greeting personalization) genuinely verifiable offline. Greeting is
  only added when `greetingName` is set, so existing draft tests (no greetingName) get the identical
  body and stay green.
- **Files modified:** `packages/backend/convex/llm.ts`
- **Commit:** `6a7a494`

### Plan-reading clarifications (not deviations, but worth recording)

- **Mixed recipients answer in the E2E.** The plan's example `SMOKE::Sarah` implies a single
  recipient, but (a) the mode question only fires for >1 recipient, so a single-recipient resolution
  skips the plan's `mode` step, and (b) the `pendingValid` "already valid" row (a must-have) needs a
  same-turn valid address to exercise. The E2E answers `SMOKE::Sarah, bob@example.com` — 2 recipients
  → mode question fires (matching the plan's subject→body→mode→PLAN flow) AND the pendingValid row is
  exercised. The SMOKE fixture returns two contacts, so nothing is pre-selected and the E2E clicks the
  `sarah@example.com` chip explicitly.
