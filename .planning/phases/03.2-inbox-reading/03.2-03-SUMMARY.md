# Phase 03.2 Plan 03: Gmail Headers-Only Search Summary

**internal.gmail.search reads the requesting user's mailbox headers-only (messages.list + format=metadata) via the already-granted gmail.modify scope, sharing one freshAccessToken refresh root with send, degrading to a reauth signal without throwing, and auditing each search as refs-only { queryHash, resultCount }.**

## Accomplishments
- Extracted `freshAccessToken(ctx, tenantId)` — the ONE token-refresh root; `send()` refactored to call it with its awaiting_reauth-not-throw behavior preserved verbatim.
- Added `internal.gmail.search` internalAction with an explicit `Promise<SearchResult>` return type: headers-only two-step read (list → per-id `format=metadata` get), zero-match widen-once (drops `newer_than:1y`), and a deterministic `SMOKE::` offline fixture.
- Each search writes exactly one refs-only `mailbox.searched` audit event (`{ queryHash: contentHash(name), resultCount }`) on both the SMOKE and live paths — no names/addresses/subjects/message-ids (CLAUDE.md §4 / SC3).
- Read-time token/refresh failure returns `{ ok:false, reason: "reauth" | "not_connected" }` without throwing, so the caller lights the banner and falls back to asking.

- `search` returns RAW `HeaderRecord`s — parsing/dedupe/ranking is Plan 04's pure `@pikar/core` job. This keeps `gmail.ts` a thin fetch adapter (CLAUDE.md §1) with NO `@pikar/core` import, avoiding a same-wave dependency on Plan 01.
- `HeaderRecord` defined locally (mirrors the `@pikar/core` shape) rather than imported cross-package, for the same thin-adapter reason.
- `Promise.all` over the ~20-message cap (marked with a `ponytail:` comment) — well within the 6,000 units/min per-user budget; a p-limit is the upgrade only if the cap ever rises.
