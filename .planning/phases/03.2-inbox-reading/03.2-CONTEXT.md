# Phase 3.2: Inbox Reading (INSERTED) - Context

**Gathered:** 2026-07-12
**Status:** Ready for planning

<domain>
## Phase Boundary

The agent can **search and read the user's connected mailbox** (via the already-granted
`gmail.modify` read scope, scoped to the requesting user only) to **surface people and
context into the guided cockpit conversation** — e.g. resolving "email Sarah about the
invoice" into Sarah's real address from prior correspondence.

Read-only: **nothing sends** as a side effect of reading; every read is audited with
**refs/ids/counts only** (never raw message content). Delivers **CKPT-01** (slice 2 of the
Email Chat Cockpit).

Hard boundary — these are NOT this phase (own later slices/phases):
- Agent-generated attachments → Phase 3.3 (CKPT-02)
- Per-recipient personalized wording → Phase 3.4 (CKPT-03)
- Content-aware drafting from prior-thread **bodies** → deferred (see Decisions)
- Group / distribution-list resolution → detected and deferred here (see Decisions)

</domain>

<decisions>
## Implementation Decisions

### Read trigger & control (stays deterministic — Phase 3.1 DECISION #2 preserved)
- A mailbox search is triggered by **deterministic name-detection**, NOT an LLM tool-call.
  A recipients-slot segment without `@` becomes a new `needs_resolution` state in the pure
  `emailIntent` module; the cockpit then runs a bounded Gmail search. **No `generateText`
  tool-loop is introduced** — the LLM is still called only for the body draft.
- **Read depth: headers only.** Use `messages.list` + `format=metadata` (From/To/Cc names &
  addresses, plus Subject/Date for the disambiguation hints). **Message bodies are never
  fetched** in this slice.
- **Search window: recent + capped.** Query recent correspondence (~12 months) with a result
  cap (e.g. ~20–50 messages), dedupe to distinct addresses, rank by frequency + recency.
  Exact numbers = Claude's discretion.
- **Zero-match handling widens once:** if a 12-month search returns nothing, silently retry
  **all-time once**, then fall back to asking for the address if still nothing.

### How matches surface (resolution card in the workspace pane)
- Matches surface on a **resolution card** (new state alongside PLAN/DRAFT/REPORT in
  `cards.tsx`), with **clickable contact chips**; clicking a chip fills that recipient.
- **Single match → text-confirm before filling** ("Found sarah@acme.com (8 msgs, last week) —
  use this?"). A single name→address is still an inference; it is confirmed, never
  auto-assumed. On the combined card, a single-match section is **pre-selected but
  confirmable**.
- **Combined multi-section card for multiple names.** When a turn names several people to
  resolve, ONE card shows a **section per unresolved name**, each with its own chips; the
  user resolves them together before the conversation continues.
- Each candidate chip carries a **header-level hint** (last subject / last-contacted / message
  count) to help the user pick the right person.

### What context feeds drafting (mostly deferred; light greeting personalization in)
- **Header hints are shown to the USER only** (on the resolution card) and are **never passed
  to the LLM drafter** — no subject lines or snippets enter generation.
- **Exception — greeting personalization:** the resolved contact's **display name** IS passed
  to the drafter so the body opens "Hi Sarah,". Header-level only (no body). This lightly
  overlaps Phase 3.4 (per-recipient personalization) — captured as an explicit slice-2
  decision so the 3.4 planner knows a basic greeting already exists and should build ON it,
  not duplicate it.
- **Prior-thread body content does NOT feed the draft** in this slice (consistent with
  headers-only). Content-aware drafting is a deferred concern.

### Recipient parsing & name detection
- **Recipients are comma / "and"-separated segments.** A segment without `@` is **one name to
  resolve** (spaces allowed, so "Sarah Chen" stays whole). A segment WITH `@` but malformed
  routes to the existing bad-email re-ask path. **This requires adjusting the current
  whitespace-splitting tokenizer in `parseAnswer`** — flagged for planning.
- **Mixed "valid email + name" turn → resolve everything uniformly.** When a turn contains any
  name needing resolution, the resolution card presents **all** recipients from that turn —
  already-valid addresses pre-selected/confirmable, names as chip sections — for a uniform
  confirm step. (A turn of only valid emails keeps the Phase 3.1 direct path, no card.)
- **Group / distribution-list names → detect and defer.** A token that looks like a group
  ("team", "everyone", "all", etc.) is detected and the agent tells the user group resolution
  isn't supported yet and asks for explicit addresses. Group SENDS remain a later concern.
- **Re-resolution reuses the recipients turn — no new machinery.** Any later recipients answer
  ("no, the other Sarah") is treated as a fresh recipients turn that re-runs the same
  resolution flow / re-picks a chip and overwrites the slot.

### Ephemerality, auth, latency & audit (governance)
- **Ephemeral candidates.** Fetched candidate data (names, addresses, header hints) is stored
  **transiently on the plans row** only long enough to render the card, then **wiped once the
  user picks** (or the PLAN is proposed). Only the **chosen address persists** — in
  `recipients`, exactly as today. No contacts cache at rest.
- **Read-time auth failure reuses the send path's plumbing.** A search needs a live Gmail
  token (refresh, like `gmail.send`). On expiry/disconnect at search time, raise the same
  `awaiting_reauth` signal + `ReconnectBanner`, and in chat **fall back to asking for the
  address** so the conversation never dead-ends.
- **Search latency: activity chip + graceful degrade.** Show a "Searching your mailbox…"
  activity chip (matches the existing "Drafting…" pattern) while the Gmail call runs; on
  error/timeout, apologize in chat and fall back to asking for the address. A failed read
  never blocks the conversation.
- **Audit shape: minimal, refs-only.** One audit event per search (e.g. `mailbox.searched`)
  recording **`{ queryHash, resultCount }`** — a SHA-256 of the query term and the number of
  results. **No names, addresses, subjects, or message-ids** in any audit/DLQ payload
  (CLAUDE.md §4, CKPT-01).
- **No dedicated read rate limit for MVP (YAGNI).** Reads are naturally bounded by
  conversational turn cadence and v1 is single-user. Revisit a per-user read limit (reusing
  the installed rate-limiter component) at Phase 9 (multi-user).

### Claude's Discretion
- Exact Gmail query string / `q=` semantics (From/To header matching, name→`q` construction).
- Exact result cap, ranking weights (frequency vs recency), and how ties break.
- The precise group-name detection heuristic (word list vs pattern).
- Card visual layout, chip styling, and the transient `plans` schema field(s) for candidates.
- Whether single-recipient vs combined-card rendering share one component.

</decisions>

<specifics>
## Specific Ideas

- Canonical example throughout the discussion: **"email Sarah about the invoice"** →
  detect "Sarah" (no `@`) → `needs_resolution` → headers-only Gmail search → resolution card
  with chips (`sarah@acme.com · 12 msgs, last Tue`) → confirm/pick → draft opens "Hi Sarah,".
- The whole feature slots in **below** the existing single draft LLM call — no new governed
  LLM surface, so no new cost/PII-on-fetch machinery is needed for slice 2.
- The resolution card is a new `switch` case in the existing `cards.tsx` dispatcher, and
  clicking a chip flows back through the existing composer → `sendCockpitMessage` (or a small
  dedicated resolve mutation) — reuses the live-query reactive card pattern.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `packages/backend/convex/gmail.ts` — `"use node"` send action with the **token-refresh
  pattern** (on-demand access-token refresh via `oauth2.googleapis.com/token`,
  `awaiting_reauth` on `invalid_grant`). The read action reuses this refresh + the
  `getTokens` reader; a new read action lives in the same `"use node"` module (or a sibling)
  and, like send, must carry an **explicit return type** to avoid tipping the internal-graph
  circular-inference limit (guidelines §96).
- `packages/backend/convex/gmailAuth.ts` — `internal.gmailAuth.getTokens` (token reader,
  refs-only, never logged), `updateAccess`, reconnect/`buildAuthorizeUrl`, `awaiting_reauth`.
- `packages/backend/convex/cockpit.ts` — `sendCockpitMessage` (the deterministic guided turn),
  `parseAnswer` (**the tokenizer to adjust** for comma/"and" segments), `toIntentState`,
  `questionText`; `listThreadMessages` tenant-guarded thread reader. New `needs_resolution`
  copy joins `questionText`.
- `packages/core/src/emailIntent.ts` — the pure slot-filling brain. Add the
  `needs_resolution` state + name-detection to the recipients slot here (pure, unit-tested, no
  Convex/Gmail import — the Gmail call stays in the convex adapter).
- `packages/backend/convex/plans.ts` — content-plane adapter (`insertPlan`/`patchPlan`/
  `byThread`/`reportForPlan`). Add the **transient `candidates` field** + its writer/clearer
  here; the schema change lives in `schema.ts`.
- `apps/web` cockpit — `cards.tsx` (`switch(plan.status)` card dispatcher → add the resolution
  card), `ChatPane.tsx` (activity chips like "Drafting…" → add "Searching your mailbox…"),
  `ReconnectBanner` (reuse for read-time auth failure).
- `packages/backend/convex/audit.ts` — insert-only `internal.audit.log`; add the
  `mailbox.searched` refs-only event (`{ queryHash, resultCount }`). `lib/hash.ts`
  (`contentHash`) for the query hash.
- `@convex-dev/rate-limiter` — installed (GRDL-06 submit limit). Available if a read limit is
  ever wanted (deferred to Phase 9).

### Established Patterns
- **Deterministic cockpit control (DECISION #2):** the agent thread is a message store only;
  the LLM is invoked once (body draft). Inbox reading MUST preserve this — resolution is a
  structured Gmail query, not a model decision.
- **Refs/ids/counts-only audit payloads** (CLAUDE.md §4) — the crown-jewel invariant; the
  Gmail token and all fetched contact data stay out of every log/DLQ payload.
- **Tenant scoping** via `tenantAction`/`tenantMutation`/`tenantQuery` (`lib/functions.ts`) —
  mailbox reads are tenant-scoped by construction; `tenantId = userId`.
- **Domain logic in `packages/*`, convex is a thin adapter** (CLAUDE.md §1) — name-detection
  + slot rules go in `@pikar/core`; the Gmail fetch + persistence stay in the convex adapter.
- **`awaiting_reauth` + `ReconnectBanner`** graceful reconnect (DLVR-03) — reused for reads.
- **`SMOKE::` offline sentinels** — the read path should have an offline `SMOKE::` search
  fixture (deterministic candidates) so the E2E/smoke runs without a live mailbox, mirroring
  `llm.ts`/`gmail.ts`.

### Integration Points
- New pure state in `emailIntent` (`needs_resolution`) is the seam: it flags the cockpit to
  call the Gmail read action BEFORE proposing the PLAN.
- The resolution loop sits between the recipients slot and the rest of slot-filling
  (subject/body/mode) — resolution completes → normal `nextQuestion` flow resumes.
- The Gmail read action reuses the `gmail.ts` refresh + `gmailAuth.getTokens`; a new
  `schema.ts` transient `plans.candidates` field holds the in-flight candidate list.
- `cards.tsx` gains the resolution card; chip clicks re-enter via the composer/resolve path.

</code_context>

<deferred>
## Deferred Ideas

- **Content-aware drafting from prior-thread bodies** — fetching + PII-redacting message
  bodies to feed the drafter. Contradicts headers-only; larger GDPR/CASA surface. Later.
- **Group / distribution-list resolution & sends** — detected and politely declined here;
  a real capability for a later phase.
- **Persistent per-user contacts cache** — faster repeat resolution, but stores third-party
  PII at rest (largest GDPR/CASA surface). Revisit only on demonstrated need.
- **Dedicated mailbox-read rate limit** — revisit at Phase 9 (multi-user) reusing the
  installed rate-limiter component.
- **Deep per-recipient personalization** beyond the greeting name — Phase 3.4 (CKPT-03).

</deferred>
