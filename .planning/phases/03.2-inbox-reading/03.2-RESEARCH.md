## User Constraints (from CONTEXT.md)

### Locked Decisions
- **Read trigger:** deterministic name-detection, NOT an LLM tool-call. A recipients-slot
  segment without `@` becomes a new `needs_resolution` state in pure `emailIntent`; the cockpit
  then runs a bounded Gmail search. **No `generateText` tool-loop** — LLM is still called only
  for the body draft (preserves Phase 3.1 DECISION #2).
- **Read depth: headers only.** `messages.list` + per-message `format=metadata`
  (From/To/Cc/Subject/Date). **Bodies never fetched.**
- **Search window: recent + capped.** ~12 months, result cap (~20–50 messages), dedupe to
  distinct addresses, rank by frequency + recency. Exact numbers = Claude's discretion.
- **Zero-match widens once:** 12-month search returns nothing → silently retry all-time once →
  then fall back to asking for the address.
- **Resolution card** (new state alongside PLAN/DRAFT/REPORT in `cards.tsx`) with clickable
  contact chips; clicking a chip fills that recipient.
- **Single match → text-confirm before filling** ("Found sarah@acme.com (8 msgs, last week) —
  use this?"). On a combined card, a single-match section is pre-selected but confirmable.
- **Combined multi-section card** for multiple names — one section per unresolved name, resolved
  together before the conversation continues.
- Each candidate chip carries a **header-level hint** (last subject / last-contacted / count).
- **Header hints shown to the USER only** — never passed to the LLM drafter.
- **Exception — greeting personalization:** the resolved contact's **display name** IS passed to
  the drafter so the body opens "Hi Sarah,". Header-level only; a basic greeting now exists that
  Phase 3.4 builds ON, not duplicates.
- **Prior-thread body content does NOT feed the draft** (consistent with headers-only).
- **Recipients are comma / "and"-separated segments.** A segment without `@` = one name to
  resolve (spaces allowed → "Sarah Chen" stays whole). A malformed `@` segment routes to the
  existing bad-email re-ask. **Requires changing `parseAnswer`'s whitespace tokenizer.**
- **Mixed valid-email + name turn → resolve everything uniformly** on the combined card (valid
  addresses pre-selected/confirmable). A turn of only valid emails keeps the Phase 3.1 direct
  path, no card.
- **Group / distribution-list names → detect and defer** ("team", "everyone", "all", …): tell the
  user group resolution isn't supported yet and ask for explicit addresses.
- **Re-resolution reuses the recipients turn — no new machinery.**
- **Ephemeral candidates.** Fetched candidate data stored transiently on the `plans` row only
  long enough to render the card, then wiped once the user picks (or PLAN is proposed). Only the
  chosen address persists — in `recipients`. No contacts cache at rest.
- **Read-time auth failure reuses the send path's plumbing** — same `awaiting_reauth` /
  `ReconnectBanner`, and in chat fall back to asking for the address (never dead-end).
- **Search latency: activity chip + graceful degrade.** "Searching your mailbox…" chip; on
  error/timeout, apologize + fall back to asking. A failed read never blocks the conversation.
- **Audit shape: minimal, refs-only.** One `mailbox.searched` event per search recording
  **`{ queryHash, resultCount }`** — SHA-256 of the query term + result count. No names,
  addresses, subjects, or message-ids in any audit/DLQ payload.
- **No dedicated read rate limit for MVP** (YAGNI; single-user; revisit Phase 9).

### Claude's Discretion
- Exact Gmail `q=` semantics (From/To header matching, name→`q` construction).
- Exact result cap, ranking weights (frequency vs recency), tie-breaks.
- Group-name detection heuristic (word list vs pattern).
- Card visual layout, chip styling, transient `plans` schema field(s) for candidates.
- Whether single-recipient vs combined-card rendering share one component.

### Deferred Ideas (OUT OF SCOPE)
- Content-aware drafting from prior-thread **bodies** (PII/GDPR surface).
- Group / distribution-list resolution & sends (detected + declined here).
- Persistent per-user contacts cache (PII at rest).
- Dedicated mailbox-read rate limit (Phase 9).
- Deep per-recipient personalization beyond the greeting name (Phase 3.4, CKPT-03).

## Summary

This phase grafts a **headers-only Gmail read** onto the existing deterministic cockpit so a
name in the recipients slot ("email Sarah about the invoice") resolves to a real address from
prior correspondence. Every seam it needs already exists: the `"use node"` token-refresh +
`awaiting_reauth` pattern in `gmail.ts`, the tenant-keyed token reader `gmailAuth.getTokens`, the
pure slot brain `emailIntent.ts`, the content-plane `plans` row + `patchPlan`, the insert-only
refs-only `audit.log`, the `contentHash` helper, the `cards.tsx` dispatcher, and the
`ReconnectBanner`. **This is an extension, not a greenfield** — the ponytail-correct build reuses
each of those and adds the minimum new surface: one pure state, one Gmail read action, one
transient schema field, one card, one activity chip.

The single non-obvious technical fact: **`messages.list` returns only `{id, threadId}` — no
headers.** Extracting From/To/Subject/Date requires an N+1 `messages.get?format=metadata` per hit.
As of the **May 2026 Gmail quota update**, `messages.get` costs **20 units** (up from 5) and
`messages.list` costs **5 units**, against a per-user budget of ~6,000 units/min — so the result
cap is a real (if generous) cost lever: a cap of ~20 keeps a search at ~405 units, comfortably
within conversational cadence. `gmail.modify` is confirmed to authorize both read methods, so **no
re-consent / no scope change** is needed.

**Primary recommendation:** Add a `search` `internalAction` **inside the existing `gmail.ts`**
(reuse its refresh block — extract a shared `freshAccessToken` helper so send + search share one
root), carry an **explicit return type** (guidelines §96). Add a pure `needs_resolution` state +
comma/"and" tokenizer + name/group detection to `emailIntent.ts`. Store candidates transiently in
a new optional `plans.candidates` field, wiped on pick. Render a resolution card in `cards.tsx`.
Audit each search as `{ queryHash, resultCount }` only. Light the existing `ReconnectBanner` on a
read-time token failure by inserting a `gmail_reconnect` notification (its existing trigger) and
falling back to asking in chat.

### Pattern 1: Two-step Gmail people search (list → metadata get)

**What:** `messages.list?q=...` returns only `{id, threadId}` per hit — no headers. Fetch
`messages.get?format=metadata&metadataHeaders=From&metadataHeaders=To&...` per id to read
addresses. Never fetch `format=full`/`raw` (that pulls the body).

**When to use:** every name resolution.

```typescript
// Source: developers.google.com/gmail/api/reference/rest/v1/users.messages/list + /get
// (in a `search` internalAction inside gmail.ts — reuses the freshAccessToken helper)
const access = await freshAccessToken(ctx, tenantId); // extracted from send()'s refresh block
if (!access.ok) return { ok: false, reason: "reauth" as const }; // caller lights banner + asks

const q = `(from:${gq(name)} OR to:${gq(name)}) newer_than:1y`; // gq = quote if it has spaces
const listRes = await fetch(
  `https://gmail.googleapis.com/gmail/v1/users/me/messages?maxResults=20&q=${encodeURIComponent(q)}`,
  { headers: { Authorization: `Bearer ${access.token}` } },
);
const { messages = [] } = (await listRes.json()) as { messages?: { id: string }[] };

// N+1 metadata gets — headers only, body never leaves Google
const HEADERS = ["From", "To", "Cc", "Subject", "Date"];
const metaUrl = (id: string) =>
  `https://gmail.googleapis.com/gmail/v1/users/me/messages/${id}?format=metadata` +
  HEADERS.map((h) => `&metadataHeaders=${h}`).join("");
// ...fetch each, parse headers, dedupe+rank (Pattern 2). Return { ok:true, candidates }.
```

**Search operators (verified current):** relative window `newer_than:1y` (also `newer_than:12m`);
`from:`/`to:` scope the match to correspondents (not body text) — more precise for people-finding
than a bare `q=name`. Quote names with spaces: `from:"Sarah Chen"`. Zero-match widen: drop
`newer_than:` and re-list once.

### Pattern 2: Parse + dedupe + rank contacts from metadata (no bodies)

**What:** RFC 2822 header values look like `Sarah Chen <sarah@acme.com>` or bare `sarah@acme.com`.
Parse each into `{ displayName, address }`, collect across the From/To/Cc of every hit, dedupe by
lowercased address, count frequency, track the most-recent `Date` + `Subject` for the hint.

**When to use:** after the metadata gets, before writing `plans.candidates`.

```typescript
// Pure helper (put in @pikar/core — unit-testable, no Convex/Gmail import).
// "Display Name <addr@x>"  |  "addr@x"  →  { displayName?, address }
function parseAddress(raw: string): { displayName?: string; address: string } | null {
  const m = raw.match(/^\s*(?:"?([^"<]*?)"?\s*)?<([^>]+)>\s*$/);
  if (m) return { displayName: m[1]?.trim() || undefined, address: m[2].trim().toLowerCase() };
  const bare = raw.trim().toLowerCase();
  return bare.includes("@") ? { address: bare } : null;
}
// Rank: primary by frequency (count), tie-break by recency (max Date). Cap output ~5 chips/name.
```

Ranking weights + tie-break are Claude's discretion — a simple `count desc, then lastDate desc`
is the lazy-correct default.

### Pattern 3: Pure `needs_resolution` state (the deterministic seam)

**What:** `emailIntent` gains awareness that a recipients segment is a name, not an address.
Keep the Gmail call OUT of core — core only *flags*; the cockpit adapter *fetches*.

**Recommended shape (Claude's discretion on exact naming):**
- `EmailIntentState` gains `pendingResolution?: readonly { name: string }[]` and (optionally)
  `pendingValid?: readonly string[]` to hold same-turn valid addresses for the uniform combined card.
- `NextQuestion` gains `{ kind: "resolve_recipients"; names: readonly string[] }`.
- `nextQuestion` returns `resolve_recipients` before `ask_subject` whenever `pendingResolution`
  is non-empty. `applyAnswer` for `recipients`: classify each segment →
  valid email / malformed email (→ `rejected`, existing path) / name (→ `pendingResolution`) /
  group-name (→ a distinct `rejected`-like "group not supported" signal so the cockpit emits the
  decline copy and re-asks).
- A new resolve `Answer` (`{ slot: "resolution"; picks: {name,address}[] }`) folds chosen
  addresses + `pendingValid` into `recipients` and clears `pendingResolution`.

This keeps the "an invalid/unresolved recipient literally cannot enter `state.recipients`"
structural guarantee intact.

### Pattern 4: Transient candidates on the plans row (ephemeral, wiped on pick)

```typescript
// schema.ts — plans table, new OPTIONAL field (no migration; matches safeText optional-on-read):
candidates: v.optional(v.array(v.object({
  name: v.string(),                                  // the unresolved name this section answers
  matches: v.array(v.object({
    address: v.string(),
    displayName: v.optional(v.string()),
    lastSubject: v.optional(v.string()),             // USER-only hint — NEVER sent to the LLM
    lastDateMs: v.optional(v.number()),
    count: v.number(),
  })),
}))),
```

`plans.ts` gets `writeCandidates(planId, candidates)` and `clearCandidates(planId)` internal
mutations. **Wiped** in the resolve mutation the moment the user picks (and defensively at
`proposeEmailPlan`). Only chosen addresses persist in `recipients`. This is content-plane storage
(CLAUDE.md §4 allows raw content in `plans`), transient, never audited.

### Pattern 5: Greeting display-name passthrough (the one allowed context leak to the LLM)

The resolved **display name** (not the address, not any header hint) is the only mailbox-derived
value that reaches the drafter. Thread it as a new optional field on the `draftCockpit` call (e.g.
`greetingName`) so the body opens "Hi Sarah,". Subject/date/count hints must **not** be included.
Extend `llmRedaction.test.ts` to assert the drafter input carries at most the display name.

### Anti-Patterns to Avoid

- **A new `"use node"` module for the read action** → re-triggers the TS circular-inference cliff
  (guidelines §96, cockpit playbook invariant). Put `search` in the existing `gmail.ts`.
- **Fetching `format=full` / bodies** → violates headers-only + inflates the GDPR surface. Use
  `format=metadata` exclusively.
- **Passing header hints (subject/date/count) to the drafter** → only the display name is allowed.
- **Committing same-turn valid addresses to `recipients` before the combined card is confirmed**
  → the design mandates uniform confirm; hold them in `pendingValid` until pick.
- **Putting any name/address/subject/message-id in an audit or DLQ payload** → CLAUDE.md §4;
  `{ queryHash, resultCount }` only.
- **`t.split(/[\s,]+/)`** (current `parseAnswer`) → splits "Sarah Chen" into two tokens. Change to
  comma/"and" segmentation preserving intra-segment spaces.

| Problem | Don't build | Use instead | Why |
|---|---|---|---|
| Access-token refresh + `invalid_grant` handling | A second refresh block | Extract `freshAccessToken` from `gmail.send` | One root; send + search share it (root-cause discipline). |
| Query hashing | New hash fn | `lib/hash.ts` `contentHash` | The one SHA-256 impl; already the audit-hash pattern. |
| Refs-only audit write | New table/logger | `internal.audit.log` + `AuditPayload` | Insert-only, contract-typed; `{queryHash,resultCount}` is already representable. |
| Read-time reconnect UI | New banner/state | `gmail_reconnect` notification → existing `ReconnectBanner` | Banner already listens for that notification kind. |
| Tenant scoping of the read | Manual `tenantId` checks | `tenantAction` / `gmailAuth.getTokens` (tenant-keyed) | Scoping is structural, not conventional. |
| Email header address parsing | A full RFC 5322 parser dependency | The small `parseAddress` regex (Pattern 2) | Metadata `From/To/Cc` values are simple `Name <addr>` / bare-addr forms; a dependency is overkill for the covered shapes. `ponytail:` comment names the ceiling (no group-address / no comment syntax) — upgrade only on a demonstrated malformed-header failure. |

**Key insight:** the entire delivery/auth/audit spine this feature needs is already built for
`gmail.send`. The net-new code is: one pure state machine extension, one read action body, one
parse/rank helper, one card, one schema field. Everything else is reuse.

## Common Pitfalls

### Pitfall 1: `messages.list` returns no headers
**What goes wrong:** you `q`-search, get IDs, and expect From/To in the response — they aren't there.
**Why:** `list` returns `{id, threadId}` only by design.
**How to avoid:** N+1 `messages.get?format=metadata&metadataHeaders=...` per hit. Budget the cost
(get = 20 units in 2026) via the result cap.
**Warning sign:** a candidate list that's always empty despite non-zero `resultCount`.

### Pitfall 2: `q=name` matches bodies, not just people
**What goes wrong:** bare `q=Sarah` matches any message mentioning "Sarah" anywhere, surfacing
strangers.
**How to avoid:** scope with `(from:Sarah OR to:Sarah)`; quote multi-word names. (Gmail still
*indexes* on more, but you only ever read metadata headers — headers-only is preserved for what
you store/see.)

### Pitfall 3: the tokenizer change breaks space-separated multi-email input
**What goes wrong:** current `parseAnswer` splits on `/[\s,]+/`, so `"a@b.com c@d.com"` becomes two
valid emails. Switching to comma/"and" segmentation makes that one segment `"a@b.com c@d.com"` — a
malformed single email that bounces to re-ask.
**Why:** the design chose comma/"and" as the recipient separators so "Sarah Chen" survives.
**How to avoid:** this is an accepted behavior change — **document it, and add `parseAnswer` unit
tests** for: `"Sarah, john@x.com"` → `["Sarah","john@x.com"]`; `"Sarah and Bob"` →
`["Sarah","Bob"]`; `"a@b.com, c@d.com"` → two emails. (Existing `emailIntent.test.ts` tests
`applyAnswer` with pre-split arrays, so they're unaffected — the risk is entirely in the new
tokenizer, which currently has no direct test; `cockpit.test.ts` covers `parseAnswer`.)
**Warning sign:** a user pasting two space-separated emails suddenly gets a re-ask.

### Pitfall 4: read-time auth failure has no `requests` row to flip
**What goes wrong:** copying `gmail.send`'s `pipeline.setStatus(awaiting_reauth)` fails — a search
has no request row, and `ReconnectBanner`'s reactive trigger reads `requests` in `awaiting_reauth`.
**How to avoid:** insert a `gmail_reconnect` notification (the banner's *other* existing trigger,
already used by `flagExpiringTokens`) and fall back to asking for the address in chat.
**Warning sign:** token expires mid-search, banner stays dark, conversation dead-ends.

### Pitfall 5: circular-inference collapse (guidelines §96)
**What goes wrong:** the new `search` action joins the internal graph without an explicit return
type; TS tips past its circularity limit and collapses sibling actions (send/draftCockpit) to `any`.
**How to avoid:** annotate `search`'s handler return type explicitly (as `send` does:
`Promise<SendResult>`). Do NOT add a second node module.
**Warning sign:** `TS7022` / `send` or `draftCockpit` losing their types after adding `search`.

### Pitfall 6: candidates leaking past the card
**What goes wrong:** third-party names/addresses/subjects linger on the `plans` row (PII at rest)
or slip into an audit payload.
**How to avoid:** wipe `candidates` in the resolve mutation and defensively at `proposeEmailPlan`;
never pass any candidate field to `audit.log`. Extend `llmRedaction.test.ts` to assert the
`mailbox.searched` payload has exactly `{queryHash, resultCount}`.

### Extracted shared refresh (root for send + search)
```typescript
// gmail.ts — lift send()'s refresh block into one helper both actions call.
async function freshAccessToken(
  ctx: ..., tenantId: string,
): Promise<{ ok: true; token: string } | { ok: false; reason: "not_connected" | "refresh_failed" }> {
  const token = await ctx.runQuery(internal.gmailAuth.getTokens, { tenantId });
  if (!token) return { ok: false, reason: "not_connected" };
  const res = await fetch(TOKEN_ENDPOINT, { /* refresh_token grant, as in send() */ });
  if (!res.ok) return { ok: false, reason: "refresh_failed" };
  const j = (await res.json()) as { access_token: string; expires_in?: number };
  await ctx.runMutation(internal.gmailAuth.updateAccess, {
    tenantId, accessToken: j.access_token, expiresAt: Date.now() + (j.expires_in ?? 3600) * 1000,
  });
  return { ok: true, token: j.access_token };
}
```
`send` keeps its existing `awaiting_reauth`-via-`pipeline.setStatus` behavior on the `false`
branch; `search` returns the failure up to the cockpit, which inserts the notification + asks.

## Playbook & watch.json coverage (CLAUDE.md §9 — planner MUST fold the update in-phase)

**All changed backend/core files are watched by `cockpit.md`** (`watch.json` → `cockpit.md`):
`cockpit.ts`, `plans.ts`, `emailIntent.ts`, plus the E2E dir and the workspace UI dir. Changing any
of them **requires updating `docs/playbooks/cockpit.md` in the same phase** (and bumping its
`Last verified` line). The redaction static-scan lives under `audit-dead-letter.md`'s watch
(`llmRedaction.test.ts` is referenced there) — extending it is consistent with that playbook.

**Two coverage gaps the planner must handle:**
1. **`gmail.ts` / `gmailAuth.ts` are NOT in any `watch.json` watched-path list** (they're only
   mentioned in playbook *prose*). Adding the `search` action to `gmail.ts` therefore does **not**
   itself trip the Stop hook — but because the same phase also edits watched `cockpit.ts`/`plans.ts`,
   the `cockpit.md` update is triggered regardless. Recommend the planner **document the new
   `gmail.search` read action in `cockpit.md`'s Data flow + Key files** (it's a cockpit-path
   behavior) rather than leaving it prose-only.
2. **If a plan creates any NEW file under `packages/`/`apps/`** (e.g. a new `parseAddress.ts` in
   `@pikar/core`, or a new E2E spec), the Stop hook blocks the turn unless the path is covered. New
   `@pikar/core` files fall under `packages/core/src/emailIntent.ts`'s directory only if the watch
   entry is a prefix — it is a **file** path, not a prefix, so a sibling `parseAddress.ts` is
   **not** covered. **Action:** either co-locate the new pure helper *inside* `emailIntent.ts`
   (simplest — no new watched path), or add `packages/core/src/` (or the specific file) to
   `cockpit.md`'s `watch.json` list. New E2E specs under `apps/web/e2e/` **are** covered (that
   prefix is already listed).

## Open Questions

1. **Same-turn valid-address holding for the uniform combined card**
   - Known: design mandates presenting *all* recipients (valid + names) on one card, valid ones
     pre-selected.
   - Unclear: whether to add `pendingValid` to `EmailIntentState` or hold the raw turn in a
     transient plan field.
   - Recommendation: `pendingValid` in `EmailIntentState` (pure, testable) — cleaner than a schema
     field, and it's wiped with `pendingResolution` on pick.

2. **Metadata get concurrency vs. sequential**
   - Known: N=~20 `messages.get` calls per search.
   - Unclear: `Promise.all` (fast, ~20 concurrent) vs. sequential (gentle on per-user rate).
   - Recommendation: `Promise.all` with the modest cap — well within 6,000 units/min; add a
     `ponytail:` note that a p-limit is the upgrade if the cap ever rises.

3. **Group-name heuristic (Claude's discretion)**
   - Recommendation: a small word list (`team`, `everyone`, `all`, `staff`, `group`) in the pure
     module — a `ponytail:`-marked list beats a regex; extend on demonstrated need.
