# Phase 17.1 Plan 01: Blueprint Structural Half Summary

**The closed eleven-field business-blueprint set with ONE `satisfies Record<BlueprintField, FieldSpec>` totality table, blank-driven probe derivation, and a byte-deterministic serializer pair that structurally cannot be mistaken for a business-profile doc.**

## Accomplishments

- **`FIELD_SPEC` turns "someone forgot to handle a new field" into a compile error.** One
  `as const satisfies Record<BlueprintField, FieldSpec>` table carries `label` / `list` / `cap` /
  `derivable` / `probe` for all eleven fields, so the serializer, the diff, the probe map and the
  spine caps become total at once rather than needing four separate coverage tests. Deliberately not
  a switch — a `default` branch makes a new field silently inherit another field's behaviour and
  makes the coverage test vacuous forever (the `TIER_REASON` / `armFor` lesson).
- **The `stage`-vs-`revenueStage` trap is closed by SIGNATURE, not by a comment.**
  `statedFromProfile(profile: BusinessProfile, tier: Tier, entities: readonly string[])` takes the
  typed profile and the tier and nothing else, so `tenantProfiles.revenueStage` — the closed union
  with the confusingly similar name — is structurally unreachable from inside the function. This was
  the one bug in the plan explicitly called out as invisible to any test.
- **Cost scales with BLANKS.** `probesFor` emits nothing for a field the user typed and nothing ever
  for `name` / `tier` / `entities` (`derivable: false` — the user names their own business,
  `deriveTier` owns the tier, the graph owns the entities). A fully-typed profile yields `[]`; the
  common sparse-start profile yields the two fields nothing types (`revenueModel`,
  `bindingConstraint`), matching CONTEXT's cost model.
- **The stored markdown cannot be mistaken for a profile doc.** The scalar shape is the plain
  `- <Label>: `, never `- **<Label>:** `, because `- **Persona:**` is the exact BUSINESS-PROFILE
  DETECTOR string in `evaluations.ts` and `vault.profileSeedDocs`. Output is byte-deterministic,
  carries no date and no document count (both are computed at READ time in the spine — baking either
  in would make every rebuild "differ", breaking the drift diff and the `contentHash` dedup), and
  `deserializeBlueprint` is total and never throws, so a foreign blob degrades to "no blueprint"
  instead of crashing a grounding call.

## Decisions Made

- **`watch.json` registration under `onboarding.md`, not a new playbook.** The blueprint IS the next
  layer of the typed-profile subsystem `onboarding.md` already owns (`businessProfile.ts`,
  `tenantProfile.ts`, the profile page), so a new playbook would be a second home for one subsystem.
  All four paths registered (both core modules + the future `convex/blueprint.ts` pair, so plan
  17.1-04's new backend module is protected from day one).
- **Per-field caps sum to 2280 chars** (name 80, oneLineDescription 280, stage 100, tier 20, offering
  280, targetCustomer 240, revenueModel 240, bindingConstraint 240, primaryGoals 280,
  knownConstraints 280, entities 240), leaving ~220 for the eleven labels inside CONTEXT's ≈2500
  standing-context budget. Plan 17.1-03 owns the hard total assertion; these are the inputs to it.
- **`probesFor` takes `Partial<Record<BlueprintField, BlueprintEntry | null>>`**, so the
  `statedFromProfile` record and a whole `BusinessBlueprint` (where blank is `null`) both feed it.
  One function, not two — the drift rebuild uses the same code path as the first build.
- **Origin/source round-trip: the suffix is parsed from the LAST `[` on the line.** A source title
  containing `]` therefore round-trips (tested with `"Pricing & margins] — Q3 (final).pdf"`), and a
  value containing brackets still parses.
- **A `derived` entry with no `source` is a named ceiling, not silent handling.** The type contract
  is "present iff `origin === 'derived'`"; such an entry serializes with an empty title and reads
  back as `source: ""`. Marked with a `ponytail:` comment naming the upgrade path (a discriminated
  union making `source` required on `derived`) rather than adding a third marker form for a shape no
  producer can currently emit.
- **`origin` is a property of the FIELD, not of an individual list item.** On deserialize, a list
  section takes its origin/source from its first item. The serializer emits one marker per line
  (needed so each line is self-describing and the parse is offset-free), but the model is one origin
  per field.
