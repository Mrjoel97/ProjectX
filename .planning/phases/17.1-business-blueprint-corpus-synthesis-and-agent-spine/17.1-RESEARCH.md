# Phase 17.1: Business Blueprint — Corpus Synthesis & Agent Spine - Research

**Researched:** 2026-07-27
**Domain:** Convex adapter + pure-TS domain module + Next.js surface (in-repo patterns, not external libraries)
**Confidence:** HIGH for everything read directly in this repo. MEDIUM/LOW only where explicitly marked.

## Summary

This phase adds **no new dependency and no new external technology**. Every mechanism it needs already
exists in the repo: the prepend-a-synthetic-entry pattern (`packages/backend/convex/evaluations.ts:248-256`),
the free-string `kind` vault-doc pattern (`packages/backend/convex/onboarding.ts:483-496`), the one-shot
structured model call with fail-closed skill load (`packages/backend/convex/vaultLlm.ts:109-143`), the
pure-module round-trip serializer pair (`packages/core/src/businessProfile.ts:122-210`), and the
`satisfies Record<...>` totality idiom (`packages/core/src/businessProfile.ts:330-335`). So the research
question is not "what stack" — it is **"what breaks when entry 0 is synthetic"**, and that has a precise,
per-caller answer below.

**The single most important correction to the spec/context:** the phase documents claim **five callers**
of `vaultGroundHydrated`. There are **three**. `onboarding.ts` and `tenantProfile.ts` only *mention* the
function in doc comments — they never call it. Verified by exhaustive grep over
`packages/backend/convex` (non-test files): the only `ctx.runAction(internal.vaultGround.vaultGroundHydrated, …)`
sites are `packages/backend/convex/llm.ts:1346`, `packages/backend/convex/evaluations.ts:234`,
`packages/backend/convex/voiceDoc.ts:75`. This shrinks the phase's blast radius **and** changes what
BLPR-02 can honestly claim (Open Question 1).

The second-most important finding: **one of those three callers regresses under a prepended entry 0**
(`llm.ts`'s `searchVault`, whose no-match detection is `docIds.length === 0`) and **one silently drops
the spine entirely** (`voiceDoc.ts`, whose post-hoc `docIds[i] !== docRef` filter discards every entry
that is not the session's document). Neither is a crash; both need an explicit accommodation in the
plan, not an assumption.

**Primary recommendation:** implement the spine as an **unshift after the existing budget loop** in
`vaultGroundHydrated` (so `TOTAL_CHAR_CAP` is structurally untouched), dedupe the blueprint docId out of
the retrieval arrays first, store the live blueprint's docId on the `tenantProfiles` row so the
per-grounding-call read is one indexed row, and add exactly two per-caller accommodations: a
`docIds.length` guard change in `llm.ts`'s `searchVault`, and a documented decision about `voiceDoc.ts`.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**The five owner decisions (spec §2.1)**
- **D1 — Standing spine + retrieval**, never spine INSTEAD of retrieval. The blueprint is always
  present; RAG still runs on top for specifics.
- **D2 — Draft → user confirms → live.** Inferences never reach agents unconfirmed. Consistent with
  `decideConfirm`/SC#1 (`businessProfile.ts:78` — *"there is deliberately no branch that
  auto-commits a persona"*).
- **D3 — Auto-detect drift, propose an update** with a diff. No cron by default.
- **D4 — Content = profile fields + graph entities**, one artifact.
- **D5 — Typing is never removed and never overwritten.** Both entry routes (type it / upload it)
  are permanent and compose. A one-line profile edit costs NO model call and NO confirm step. The
  owner explicitly rejected an earlier framing that read as replacing typed input with derivation —
  do not reintroduce it.

**Storage — no migration anywhere**
- **Live blueprint = a `vaultDocuments` row**, `kind: "business_blueprint"`. Free-string kind, the
  exact precedent at `onboarding.ts:486` (*"NEW free-string kind — ZERO schema migration"*).
  Inherits tenant scoping, embedding, delete-cascade, PII redaction, audit, and `by_kind`.
- **Draft = three OPTIONAL fields on `tenantProfiles`** (`blueprintDraft`, `blueprintDraftAt`,
  `blueprintSourceDocIds`). Optional fields on an existing one-row-per-tenant table ⇒ no migration.
- **The draft must NOT be a vault document.** A draft row would embed into RAG and unconfirmed
  inferences would surface in retrieval BEFORE approval — the D2 gate would leak through the back
  door. This is the reason for the split; do not "simplify" it away.
- **Rejected:** a `blueprintDrafts` table — a whole table for one optional blob.
- One new index: `.index("by_tenant_degree", ["tenantId", "degree"])` on `graphNodes`. Convex builds
  it automatically — no migration.

**The field set is CLOSED**
Fields: `name`, `oneLineDescription`, `stage`, `tier`, `offering`, `targetCustomer`, `revenueModel`,
`bindingConstraint`, `primaryGoals[]`, `knownConstraints[]`, `entities[]`.
- `stage`/`tier` come from `tenantProfiles` — `deriveTier` already owns them, never re-inferred.
- `name` is never inferred — the user names their own business.
- `revenueModel` and `bindingConstraint` go on the BLUEPRINT type, **not** on `BusinessProfile`
  (`businessProfile.ts:22-24` marks that type a downstream contract).

**Precedence is CODE, never a prompt**
- `mergeBlueprint(typed, derived, live?) → { blueprint, diff }` — a pure function in
  `packages/core/src/blueprint.ts`.
- **The model returns derived CANDIDATES only. It is never shown the live blueprint and is never
  asked to merge anything.**
- Rule: typed ⇒ user's value wins; blank ⇒ derived fills it with a citation; typed AND contradicted
  ⇒ a `contradiction` diff row, never a silent change.
- Reuses the rule already live at `evaluations.ts:270-280`.

**Synthesis**
- Three inputs, ONE of which costs money: typed profile (`deserializeProfile`, free), graph entities
  (`graphNodes` by `degree`, top 20, free DB read), document content (probes → `vaultGroundHydrated`
  → **one** model call).
- **Probes derive from the BLANKS.** A typed field generates no probe.
- Prompt is a `business-blueprint` **skill-registry row**, not source (CLAUDE.md §5). Missing /
  unpublished ⇒ **fail closed** with `NO_ACTIVE_SKILL`.
- `guardrails.preCall` before, `priceUsage` → `recordSpend` after.

**Citation validation is a trust boundary (NOT a place to be lazy)**
An out-of-range source index means an invented citation and that field is **DROPPED, not kept uncited**.

**The spine**
- Prepended in `vaultGroundHydrated` as entry 0 — real `docId`, title `"Business blueprint"`.
  **No per-caller wiring.**
- Budgeted **OUTSIDE** `TOTAL_CHAR_CAP`, which stays 8000 for retrieval results.
- Target ≈ 2500 chars, enforced by per-field caps at serialize time plus a hard total assertion.
- **`[stated]` vs `[source.docx]` markers.**
- **A staleness line** (`⚠ N documents added since this was confirmed`).
- **No blueprint ⇒ output byte-identical to today.** Fail open, zero regression surface.

**Drift — two stages, no separate detector**
- **Stage 1 (free, always on):** any `ready` doc whose id is not in `blueprintSourceDocIds` is
  unincorporated. Pure comparison. Drives the profile-page banner.
- **Stage 2:** rebuild the draft and diff against live. **The diff IS the drift signal** — identical ⇒
  discard silently; different ⇒ that is the proposal.
- Stage 2 fires automatically on **bulk/folder-ingest completion**, NOT per single-doc upload. Until
  folder ingest exists (15.2 Phase 2), this degrades to the Stage-1 banner's one-click rebuild.

**The confirm surface (`/dashboard/profile`, 717 lines today)**
Four states: no blueprint / live-and-current / live-plus-unincorporated / draft-pending.
- **Additions** (blank → value + citation) ⇒ **one Accept applies them all**, defaulted ON.
- **Contradictions** (typed ≠ derived) ⇒ individually checkboxed, **defaulted OFF**, shown side by
  side with sources.
Confirmation writes an audit event (`blueprint.confirmed`) carrying **refs and counts ONLY** — docIds,
field counts, accepted-contradiction count. No field content (CLAUDE.md §4).

**Breakage A — the no-match branch dies (the serious one).** `llm.ts:1364` is
`if (docIds.length === 0) return noMatch;`. With a blueprint prepended, `docIds.length` is **never** 0
for any tenant that has confirmed one. The honest nudge defined at `llm.ts:1334-1336` —
*"I don't have anything in your vault about that. Tell the user plainly and suggest they upload a
relevant document so I can ground next time."* — becomes structurally unreachable, and every genuine
miss is instead reported to the model as *"Grounded in 1 document(s)"* with the blueprint as the sole
source. That directly inverts the phase's own stated value (§8 of the spec: *"the agent is told when the
spine is incomplete, so it can say so rather than assert into the gap"*). **Accommodation required:**
the no-match test must become "zero *retrieval* hits". Options: return a discriminating field from
`vaultGroundHydrated` (e.g. `spineCount: 0 | 1`), or have `searchVault` compare `docIds` against the
known blueprint docId. This is a contract change, not a one-liner — budget a task for it.

**Breakage B — the audit count inflates.** `llm.ts:1360` writes
`payload: { queryHash: …, resultCount: docIds.length }`. Every `vault.searched` row silently gains +1
forever. Refs-only, so no §4 violation, but the number stops meaning "how many documents matched".

**Breakage C — the source card always shows the blueprint.** `llm.ts:1367-1374` inserts `vaultSources`
with `docIds`/`titles` verbatim; the comment calls them *"PreviewModal targets"*. Every vault search
would render a "Business blueprint" chip. The docId is a real `vaultDocuments` row so PreviewModal opens
it correctly — this is a UX decision, not a crash. Decide it deliberately rather than by accident.

**Not a breakage:** `chunks.join("\n\n")` at `llm.ts:1386` — the blueprint text simply leads the fence.
That is the intended effect.

**Golden-eval note:** `docs/playbooks/vault.md:3` records that *"golden fixtures 25/26 and `searchVault`
ride this exact shape"*. If the eval tenant has a blueprint, fixtures 25/26 see changed grounding output.
Check before `pnpm --filter @pikar/backend eval:golden`.

**Why it is safe:** this caller *already does exactly what this phase proposes*. It prepends synthetic
entries and rebuilds all three arrays in lockstep (`evaluations.ts:251-253`), then iterates
index-parallel (`evaluations.ts:259-262`). It uses `.length` only as a loop bound, never as a

**This is the strongest in-repo evidence that the prepend pattern is correct here** — cite it in the plan.

(a) `deserializeProfile` runs over blueprint markdown here, and (b) `internal.vault.profileSeedDocs`

filter is


and a `text/markdown` blueprint passes the first clause. Use `- Stage:` / `- Tier:` as spec §8's sample
does. **Make this a test.**

**Ordering:** because `evaluations.ts` prepends its profile seeds *after* the grounding call, the final
order is `[profileSeeds…, blueprint, retrieval…]`. Harmless.

### Pattern 1 — the pure merge with compile-time totality

The repo idiom for "a new field must not be silently droppable" is `as const satisfies Record<K, V>`
(`businessProfile.ts:320-335`):

```ts
export const TIER_REASON = {
  solopreneur: "Solo operation — you're the only person working on this.",
  startup: "Early stage — still finding repeatable revenue, or building on outside funding.",
  sme: "Established business — steady revenue, paid staff, and no outside funding to answer to.",
  enterprise: "Enterprise — granted by Pikar, not derived from your answers.",

```

Its doc comment states the reason verbatim: *"deliberately NOT a switch or a ternary: a ternary is total
by construction, so adding a tier literal would silently inherit the else-branch's reason and the
coverage test would be vacuous forever… This way a new tier without a reason is a COMPILE error here."*
Apply the same shape to the closed blueprint field set — one per-field descriptor table
(`{ probe, cap, diffKind, serialize }`) bound `satisfies Record<BlueprintField, …>`. That single table
satisfies the CONTEXT's verification item 6 (field-set totality) for the diff, the serializer and the
probe map at once.

A second idiom exists if any blueprint union is mirrored in a Convex validator — the two-way
compile-time bind at `tenantProfile.ts:54-67`:

```ts
const _tierToDoc: readonly TpDoc["tier"][] = TIERS;
const _docToTier: readonly Tier[] = [] as TpDoc["tier"][];
```

`SLOT_PRESENT` (`businessProfile.ts:367-374`) is the same trick applied to per-field predicate functions
— the closest analogue to a per-field validation table.

### Pattern 2 — the seam edit: unshift AFTER the budget loop

The locked requirement is *"budgeted OUTSIDE `TOTAL_CHAR_CAP`, which stays 8000 for retrieval results"*.
The structurally-guaranteed way to satisfy it (rather than arithmetically) is: **do not touch the loop.**
Let `vaultGround.ts:142-167` run exactly as today over the retrieval `docIds`, then unshift:

```ts
// after the existing loop (vaultGround.ts:167), before the return (:169)
const bp = await ctx.runQuery(internal.blueprint.liveForTenant, { tenantId });
if (!bp) return { docIds, titles, chunks };            // fail open — byte-identical to today
// Dedupe: the blueprint IS embedded, so rag.search can return it as a hit too (Pitfall 3).
const keep = docIds.map((d, i) => [d, i] as const).filter(([d]) => d !== bp.docId);
return {
  docIds: [bp.docId, ...keep.map(([d]) => d)],
  titles: ["Business blueprint", ...keep.map(([, i]) => titles[i] ?? "")],
  chunks: [bp.text, ...keep.map(([, i]) => chunks[i] ?? "")],
};
```

Three properties for free: `used` never sees the spine so the 8000 budget is provably intact; the
no-blueprint path returns *the same object today's code returns* (zero regression surface, satisfying
the locked "byte-identical" requirement); and the three arrays stay parallel by construction.

`liveForTenant` must read the newest non-failed `kind === "business_blueprint"` row. The established
shape is `currentProfileDoc` (`onboarding.ts:521-533`):

```ts

```

⚠ **Do not copy the `.collect()`.** It reads the whole tenant's `vaultDocuments` *including the `text`
blob*. `schema.ts:636-639` warns about exactly this on the same table (*"this table holds book-sized
uploads; a `.collect()` would walk into the 16 MiB / 32k-doc read cap"*), and `vault.md:3` records the

`tenantProfiles` row** — you are already adding optional fields there, so a fourth (`blueprintDocId`)
turns this into one indexed row read plus one `ctx.db.get`. Strongly recommended.

Current definition (`schema.ts:645-651`):


Adding `.index("by_tenant_degree", ["tenantId", "degree"])` needs **no migration** (Convex builds indexes


`.order("desc")` on an index orders by the index columns — `packages/backend/convex/_generated/ai/guidelines.md`
(Ordering section, targeting Convex `^1.41.0`) states *"Document queries that use indexes will be ordered
based on the columns in the index and can avoid slow table scans."* With `tenantId` pinned by `.eq`, the
remaining sort key is `degree`, descending. **Confidence: HIGH** — documented behaviour, and
`vault.ts:476-477` already uses `.order("desc").take(40)` on `by_tenant` in production.

**No existing helper reads `graphNodes` tenant-scoped for you.** The only readers are
`vaultGraph.ts:40-46` (upsert lookup by `normalizedName`), `vault.ts:311-316` (`docEntities`, scoped to
one document) and `vaultSmoke.ts:240`. Write a new `internalQuery`.

Two data-quality notes on `degree` (`vaultGraph.ts:75-78`):

```ts
      const fromNode = await ctx.db.get(fromId);
      const toNode = await ctx.db.get(toId);
      if (fromNode) await ctx.db.patch(fromId, { degree: fromNode.degree + 1 });
      if (toNode) await ctx.db.patch(toId, { degree: toNode.degree + 1 });
```

(1) It is bumped per edge insert with no dedup, so re-ingesting a document inflates it — "top 20 by
degree" is "most-repeated", not "most-central". (2) It is a high-churn field, so the new index is
rewritten on every edge insert. Acceptable at this scale; worth a `ponytail:` comment naming the ceiling.

## Common Pitfalls

### Pitfall 1: The `llm.ts` no-match branch (HIGH severity)
**What goes wrong:** `if (docIds.length === 0) return noMatch;` (`llm.ts:1364`) can never fire once a
blueprint is prepended, so the agent stops being able to say "I have nothing on that".
**Why:** the guard conflates "retrieval found nothing" with "the array is empty".
**How to avoid:** make the spine distinguishable (an extra return field, or compare against the known
blueprint docId). Cover with a test asserting the no-match string is still returned for a
blueprint-bearing tenant whose query matches nothing.
**Warning sign:** the cockpit starts answering vault questions confidently from the blueprint alone.

### Pitfall 2: `voiceDoc.ts` silently drops the spine (MEDIUM — a requirements risk, not a bug)
**What goes wrong:** BLPR-02 claims all callers inherit the spine; `voiceDoc.ts:99` filters it out.
**How to avoid:** decide and document explicitly (Open Question 1). Do not assert coverage you do not have.

### Pitfall 3: The blueprint is also a RAG hit → duplicate entry 0 (MEDIUM)
**What goes wrong:** the locked design routes the live blueprint through `startIngest`, so it is
embedded. `rag.search` (`vaultGround.ts:62-68`) can then return it as a retrieval hit, and the unshift
adds it again — the same document twice in `docIds`, and `voiceDoc.ts`'s filter would match it twice.
**How to avoid:** the `keep` filter in Pattern 2. **Test it.**

### Pitfall 4: The blueprint's own entities feed back into `graphNodes` (MEDIUM)
**What goes wrong:** the blueprint is graph-extracted like any vault doc (`vaultIngest` pipeline,
`vault.md:39`), so its entity list re-upserts the same entities and bumps their `degree`
(`vaultGraph.ts:75-78`). The next rebuild reads `graphNodes` by degree and sees inflated numbers for
entities the blueprint itself named — a self-reinforcing loop.
**How to avoid:** either exclude `kind === "business_blueprint"` from graph extraction, or accept and
document the ceiling. Note: not embedding the blueprint at all would kill Pitfalls 3 and 4 together and
save the embed spend, but the CONTEXT explicitly lists "embedding" as a benefit of the vault-doc
decision — see Open Question 3.

### Pitfall 5: `- **Persona:**` collision (HIGH, cheap to avoid)
Covered above under the `evaluations.ts` verdict. `evaluations.ts:291` and `vault.ts:450/484` both key
off that literal. Test that `serializeBlueprint` output does not contain it.

### Pitfall 6: `rag.search` is action-only (HIGH — it dictates module shape)
`vaultGround.ts:7`: *"`rag.search` is action-only (Pitfall 1) — `tenantAction` is correct."*
`vault.md:259`: *"`rag.add/search/delete` are ACTION-only; `addAsync/deleteAsync/list/getEntry/findEntryByContentHash`
are mutation/query-safe."* Synthesis (which calls `vaultGroundHydrated`, itself an action) must be an
**action**; the confirm write must be a **mutation**; the profile-page reads must be **queries**. Also,
`ctx.storage.get` is action-only (`vault.md:231-235`) — irrelevant here, but the same class.

### Pitfall 7: 16 MiB / read-cap when scanning documents (MEDIUM)
`schema.ts:637-639`: *"this table holds book-sized uploads; a `.collect()` would walk into the 16 MiB /
32k-doc read cap."* Stage-1 drift needs the tenant's `ready` doc **ids**, not their text. Read metadata
only (`profileSeedDocs` at `vault.ts:473-477` shows the bounded `.take(40)` idiom). Never `.collect()`
`vaultDocuments` in a hot path.

### Pitfall 8: Windows vitest false-red (documented, will bite)
`docs/playbooks/vault.md:278`: *"convex-test files crash on parallel-fork teardown ('Cannot set
properties of undefined (setting 'exit')') → false red; each file passes run alone."* CONTEXT repeats it.
`vault.md:3` adds a second false-red mode: *"`crypto is not defined` in convex-test workers… appear under
CPU saturation."* **Always re-run `--maxWorkers=1` before trusting a red.**

### Pitfall 9: The blueprint appears in the user's vault UI
`listVaultDocs` (`vault.ts:230-239`) returns every row for the tenant with no kind filter, and
`categoryFor({ source: "agent" })` routes it to `workspace-docs` (the `onboarding.ts:487-488` precedent).
The blueprint will show as a card, be previewable, and be **deletable** (`deleteVaultDoc` cascade). That
is probably fine and consistent with the profile doc — but the UI must not break when the live blueprint
