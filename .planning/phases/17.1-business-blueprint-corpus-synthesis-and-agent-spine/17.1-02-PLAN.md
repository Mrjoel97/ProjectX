**Prompt body content — three properties it MUST have:**

(a) **It returns CANDIDATES ONLY and is never asked to merge.** It is never shown the live blueprint.
    A merge rule in a prompt is a request; `mergeBlueprint` is a guarantee. State plainly: *"You do
    not decide what the blueprint says. You propose candidates; code decides."*

(b) **It does NOT enumerate the field set.** The 15.1-06 split is the precedent and it is
    load-bearing: the CODE supplies the field names and their permitted shape at call time (from
    `FIELD_SPEC`), the BODY supplies the words. The closed set then has exactly ONE home and cannot
    drift between the prompt and the type. Write the body against "the FIELDS TO FILL listed in the
    request" and "the numbered SOURCES provided", never against a hardcoded list.

(c) **Every candidate cites a source INDEX, and inventing one is worse than declining.** The output
    shape it must produce (the adapter's strict `jsonSchema` in plan 05 mirrors this exactly — every
    property required, `additionalProperties: false`, because `llmRedaction.test.ts:236` statically
    asserts every `generateObject` schema is strict-mode legal):
    ```json
    { "candidates": [ { "field": "<a field name from the request>",
                        "values": ["..."],
                        "sourceIndex": 0 } ] }
    ```
    `sourceIndex` is a REQUIRED integer — model "no supporting source" as the sentinel `-1` rather
    than an optional field. Tell the model explicitly that a field it cannot support from a numbered
    source must be returned with `-1` (or omitted), and that a fabricated index causes the claim to
    be **dropped entirely**, so guessing gains it nothing.
