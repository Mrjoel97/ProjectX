## Sampling Rate

- **After every task commit:** the package's own quick command (`@pikar/core test blueprint` for
  pure work, `@pikar/backend test vaultGround --maxWorkers=1` for the seam) **plus that package's
  `typecheck`** — several requirements here fail only at compile time.
- **After every plan wave:** `@pikar/core` + `@pikar/contracts` + `@pikar/backend` full suites
  (`--maxWorkers=1`), `@pikar/web typecheck`, and `check-playbooks`.
- **Before `/gsd:verify-work`:** full suites green, **then the live gate below**.
- **Max feedback latency:** ~15 s (quick), ~120 s (full).

### Planning-time corrections to this document

1. **`check-playbooks.mjs` always exits 0** — it signals by PRINTING a block JSON, then falls
   through to a normal exit. Every plan's automated verify therefore asserts on its OUTPUT:
   `test -z "$(echo '{}' | node scripts/check-playbooks.mjs check)"`, never on the exit code.
2. **`pnpm --filter @pikar/backend typecheck` is NOT exit-0** — it sits at a documented ~55-error
   TEST-FILE baseline (STATE, 15.1-06/07). Plans assert the stable invariant instead: ZERO errors
   in any NON-test file, via
   `… | grep "error TS" | grep -v "\.test\.ts" | wc -l | tr -d ' ' | grep -qx 0`.
   The trailing `grep -qx 0` is load-bearing: `wc -l` ALWAYS exits 0, so without it the invariant
   is printed and never asserted.
3. **CONTEXT's *"`packages/core/src/blueprint.ts` needs no new `watch.json` entry — the
   `packages/core/` prefix covers it"* is FACTUALLY WRONG.** Verified against
   `docs/playbooks/watch.json`: there is no `packages/core/` prefix — only
   `packages/core/src/businessProfile.ts`, `packages/core/src/growth/` and
   `packages/core/src/specialists.ts`. `check-playbooks.mjs`'s creation-gap rule (line 127) blocks
   any NEW non-test `.ts` under `packages/` that no playbook covers, so BOTH
   `packages/core/src/blueprint.ts` and `packages/backend/convex/blueprint.ts` are registered under
   `onboarding.md` in plan 17.1-01 Task 1.
4. **Per-plan playbook obligations** (the hook's stale rule, so a plan that skips one is BLOCKED at
   turn end): 01/03/04/05/08/09 → `onboarding.md`; 02 → `skill-registry.md`; 06 → `cockpit.md`;
   07 → `vault.md` + `business-evaluation.md` + `voice.md`; 08 → also `vault.md` (the
   never-ingested exception); 10 → all three. No two plans in the same WAVE touch the same playbook.

5. **The backend FULL-suite gate must survive the one documented baseline red without swallowing a
   new one.** `… test --maxWorkers=1 | tail -20` always exits 0 — a red suite passes it. Every plan
   uses ONE identical form, and it carries BOTH a positive and a negative half:
   ```sh
   { OUT=$(pnpm --filter @pikar/backend test --maxWorkers=1 2>&1); echo "$OUT" | grep -q "Test Files" && ! echo "$OUT" | grep "FAIL " | grep -v "audit.test.ts" | grep -q .; }
   ```
   - **Positive** (`grep -q "Test Files"`) proves the run REACHED ITS SUMMARY. A negative-only
     assertion cannot tell *"nothing failed"* from *"nothing ran"*, and this suite has three
     documented ways to die silently: OOM, the Windows parallel-fork teardown crash, and
     `crypto is not defined` under CPU saturation.
   - **Negative** allows exactly the documented `audit.test.ts` `auditCounts` baseline red and
     nothing else.
   - `{ …; }` rather than `A; B` so the gate still chains with `&&` and still short-circuits the
     rest of the `<automated>` chain. The output rides in a shell VAR, not a temp file — Git Bash
     has no `/tmp` in this worktree.
   Verified across five inputs: green ⇒ pass, baseline-only red ⇒ pass, ADDITIONAL red ⇒ fail,
   crash-with-no-summary ⇒ fail, empty output ⇒ fail.
6. **Waves renumbered after checker review (B2).** `execute-phase` serializes on `wave` and runs
   same-wave plans in ONE working tree, so plan 07's `git diff` gate and plan 06's `llm.ts` edit
   were observing each other's uncommitted work. Final table: W1 = 01+02, W2 = 03, W3 = 04,
   W4 = 05+06, W5 = 07, W6 = 08, W7 = 09, W8 = 10. Plan task IDs in the map above are UNCHANGED.
