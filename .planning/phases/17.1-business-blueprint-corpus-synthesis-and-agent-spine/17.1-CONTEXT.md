<domain>
## Phase Boundary

**The problem is not extraction — it is that agents have no standing context.** Every agent surface
reaches the user's business through ONE function, `vaultGroundHydrated`
(`packages/backend/convex/vaultGround.ts:126`). It has **THREE** real callers: the cockpit
`searchVault` tool (`llm.ts:1347`), `evaluations.ts:235`, and `voiceDoc.ts:75`. That function is a
per-query RAG search capped at `TOTAL_CHAR_CAP = 8000` (`vaultGround.ts:30`). It answers *"which
passages mention X"*. It never answers *"what IS this business"*.

> **CORRECTED 2026-07-27 by research.** The source spec said FIVE callers, adding `onboarding.ts`
> and `tenantProfile.ts`. Those two mention the function in COMMENTS ONLY
> (`onboarding.ts:5,451,539,595`; `tenantProfile.ts:14,127`) and are not callers. Do not plan any
> work against them.

Three partial blueprints already exist and none is corpus-wide or agent-facing:
1. **Typed profile** — `packages/core/src/businessProfile.ts`, 8 hand-typed fields. Correct but thin.
2. **Entity graph** — `graphNodes`/`graphEdges` (`schema.ts:645`), extracted per document, used ONLY
   to hop-expand retrieval seeds (`vaultGraph.expand`). Never rendered, never reasoned over.
3. **Eval scorecard** — `evaluations.ts:250-320`, already reads documents into a structured model
   with per-field provenance and citations. Query-scoped, run for evaluation, not agent-facing.

This phase delivers:

1. **Synthesis** — one blueprint from typed profile + document-derived gap fields + top graph
   entities, every derived claim carrying a validated citation.
2. **Precedence as code** — a pure `mergeBlueprint()` with no branch that overwrites a non-empty
   typed field.
3. **The confirm gate** — draft → user review → live. Nothing derived reaches an agent unconfirmed.
4. **The spine — TWO seams** (see the locked decision below; the original one-seam plan was
   disproved by research and must not be reinstated).
5. **Drift** — rebuild + diff (no separate detector), with a free Stage-1 unincorporated-doc check.
   **User-triggered rebuild this phase** — automatic triggering is deferred.

**NOT in this phase:** folder ingest (that is 15.2's "Phase 2" line — folders, 1–1.5 GB upload, the
200 MB cap raise), visual rendering/diagrams, per-field re-derivation, cron-scheduled rebuild, and
multi-blueprint-per-tenant. See spec §9.

</domain>

<decisions>
## Implementation Decisions

Everything below is a LOCKED owner decision (spec approved 2026-07-27). None of it is open.

### The five owner decisions (spec §2.1)
- **D1 — Standing spine + retrieval**, never spine INSTEAD of retrieval. The blueprint is always
  present; RAG still runs on top for specifics.
- **D2 — Draft → user confirms → live.** Inferences never reach agents unconfirmed. Consistent with
  `decideConfirm`/SC#1 (`businessProfile.ts:78` — *"there is deliberately no branch that
  auto-commits a persona"*).
- **D3 — Auto-detect drift, propose an update** with a diff. No cron by default.
- **D4 — Content = profile fields + graph entities**, one artifact.
- **D5 — Typing is never removed and never overwritten.** Both entry routes (type it / upload it)
  are permanent and compose. A one-line profile edit costs NO model call and NO confirm step. The
  owner explicitly rejected an earlier framing that read as replacing typed input with derivation —
  do not reintroduce it.

### Storage — no migration anywhere
- **Live blueprint = a `vaultDocuments` row**, `kind: "business_blueprint"`. Free-string kind, the
  exact precedent at `onboarding.ts:486` (*"NEW free-string kind — ZERO schema migration"*).
  Inherits tenant scoping, delete-cascade, PII redaction, audit, and `by_kind`.
- **NOT embedded and NOT graph-extracted** (owner decision 2026-07-27; the original text listed
  embedding as a benefit). The spine is prepended unconditionally so the blueprint never needs to be
  retrievable. Embedding it creates two real defects and buys nothing: (a) RAG could return it as a
  hit AND the seam adds it ⇒ it appears twice in one context; (b) its own entities flow back into
  `graphNodes`, inflating the `degree` ranking the NEXT rebuild reads — the blueprint progressively
  re-derives itself from itself. Also saves the embedding spend.
- **`serializeBlueprint` must NEVER emit the literal `- **Persona:**` line.** `evaluations.ts:291`
  and `vault.profileSeedDocs` (`vault.ts:484`) both use that exact string as a BUSINESS-PROFILE
  DETECTOR; a blueprint carrying it is misread as a profile doc by both. HIGH severity, cheap to
  avoid.
- **Draft = OPTIONAL fields on `tenantProfiles`** (`blueprintDraft`, `blueprintDraftAt`,
  `blueprintSourceDocIds`, `blueprintDocId`). Optional fields on an existing one-row-per-tenant
  table ⇒ no migration.
- **`blueprintDocId` is a hot-path requirement, not a convenience.** The obvious `currentProfileDoc`
  clone (`onboarding.ts:521-533`) `.collect()`s `vaultDocuments` INCLUDING the `text` blob — fine on
  a profile save, unacceptable on a path that now runs on every grounding call. One indexed row
  read, never a scan.
- **Required-field trap:** `tier`/`tierSource`/`derivedAt` are REQUIRED on `tenantProfiles`
  (`schema.ts:768-783`). A draft writer therefore CANNOT insert a row for a tenant that has none
  without inventing a tier — precisely the silent-reclassification defect the tier design exists to
  kill. It must **refuse**, exactly as `saveFacts` does (`tenantProfile.ts:194`), never
  patch-or-create.
- **The draft must NOT be a vault document.** A draft row would embed into RAG and unconfirmed
  inferences would surface in retrieval BEFORE approval — the D2 gate would leak through the back
  door. This is the reason for the split; do not "simplify" it away.
- **Rejected:** a `blueprintDrafts` table — a whole table for one optional blob.
- One new index: `.index("by_tenant_degree", ["tenantId", "degree"])` on `graphNodes`. Convex builds
  it automatically — no migration.

### The field set is CLOSED
Fixed and closed, or the diff and the spine cap are both unbounded. Fields: `name`,
`oneLineDescription`, `stage`, `tier`, `offering`, `targetCustomer`, `revenueModel`,
`bindingConstraint`, `primaryGoals[]`, `knownConstraints[]`, `entities[]`.

- **`stage` is `BusinessProfile.stage`, NOT `tenantProfiles.revenueStage`.** Two different fields
  with confusingly similar names: `stage` is a free string in the user's own words
  (`businessProfile.ts:46-47`); `revenueStage` is a closed union (`schema.ts:758-760`). The blueprint
  uses `stage` — D5 makes typed content authoritative and `tier` already carries the derived shape.
  Reading the wrong one is a silent correctness bug NO test would catch, so it is stated here rather
  than left to the implementer.
- `tier` comes from `tenantProfiles` — `deriveTier` already owns it, never re-inferred.
- `name` is never inferred — the user names their own business.
- `revenueModel` and `bindingConstraint` are the only two fields not on `BusinessProfile` today.
  They go on the BLUEPRINT type, **not** on `BusinessProfile`: that type is a documented downstream
  contract read by the Phase 12 evaluator (`businessProfile.ts:22-24`), and widening it drags the
  evaluator, the onboarding validator and the profile form along for two fields only the blueprint
  uses.

### Precedence is CODE, never a prompt
- `mergeBlueprint(typed, derived, live?) → { blueprint, diff }` — a pure function in
  `packages/core/src/blueprint.ts`.
- **The model returns derived CANDIDATES only. It is never shown the live blueprint and is never
  asked to merge anything.** A merge rule in a prompt is a request; a pure function with no
  overwrite branch is a guarantee. Same reasoning as `canComplete`/`missingSlots`
  (`businessProfile.ts:345` — *"the guarantee is CODE, never prompt"*).
- Rule: typed ⇒ user's value wins; blank ⇒ derived fills it with a citation; typed AND contradicted
  ⇒ a `contradiction` diff row, never a silent change.
- Reuses the rule already live at `evaluations.ts:270-280` (*"the VALUE is first-write-wins…"* while
  the citation is still recorded). ONE rule in the codebase, not two.

### Synthesis
- Three inputs, ONE of which costs money: typed profile (`deserializeProfile`, free), graph entities
  (`graphNodes` by `degree`, top 20, free DB read), document content (probes → `vaultGroundHydrated`
  → **one** model call).
- **Probes derive from the BLANKS.** A typed field generates no probe, so a fully-typed profile
  costs almost nothing. ~6 probes × 8000 chars ≈ 12k input tokens, then ONE call producing all
  fields. NOT one call per field.
- Prompt is a `business-blueprint` **skill-registry row**, not source (CLAUDE.md §5). Missing /
  unpublished ⇒ **fail closed** with `NO_ACTIVE_SKILL` (existing precedent).
- **The skill is UNGATED** (owner decision 2026-07-27, REPLACES the "through the eval gate" line
  that was in the original Definition of Done). Mechanical reason: `run-eval-golden.mjs`
  hard-validates `--skill` against a closed name list (`skill.ts:68-72`), so gating a skill the
  golden runner cannot drive **deadlocks it at v1** on its first body edit — the documented reason
  `document-analyst` is ungated. Principled reason: the rationale for ungating `business-profile`
  (`skills.ts:282`) applies verbatim — its output is a vault doc a human confirms, not tool-state,
  and **D2's confirm gate IS that human check.**
- `guardrails.preCall` before, `priceUsage` → `recordSpend` after.

### Citation validation is a trust boundary (NOT a place to be lazy)
`vaultGroundHydrated` returns parallel `docIds`/`titles`/`chunks`, so the model cites a **source
index**. An out-of-range index means an invented citation and that field is **DROPPED, not kept
uncited**. A blueprint claim with no traceable source is the confidently-unfounded grounding this
whole phase exists to prevent (CLAUDE.md §8 — validation at trust boundaries).

### The spine — TWO SEAMS (owner decision 2026-07-27, REPLACES the original one-seam plan)

**Do NOT prepend the blueprint as entry 0 of `vaultGroundHydrated`.** Research proved this breaks
`llm.ts` three ways AND fails to deliver standing context there at all:

| # | Code | Breakage |
|---|---|---|
| A | `if (docIds.length === 0) return noMatch;` (`llm.ts:1364`) | Unreachable — the agent permanently loses its honest *"nothing in your vault"* answer. **HIGH severity.** |
| B | `resultCount: docIds.length` (`llm.ts:1360`) | Every `vault.searched` audit count inflated by one. |
| C | `vaultSources.insert` (`llm.ts:1367-1374`) | A "Business blueprint" source chip on EVERY search. |

And even patched, the spine would only reach the cockpit on turns that happen to call `searchVault`
— *"draft an email to Bob"* never does. `searchVault` is a SEARCH TOOL; the blueprint is not a
search result. That conflation is the root cause of A/B/C, not three separate bugs.

**Seam 1 — cockpit: the TURN PROMPT.** Prepend the blueprint as a labelled context block to the
`prompt` passed into `runAgentLoop`. Present on EVERY turn regardless of tool use.
**NOT the system prompt:** `system: skill.body` verbatim at 18 call sites (`llm.ts:1837` et al.);
the system string comes from the registry (§5) and tenant context does not belong spliced into a
versioned skill body.

**Seam 2 — `evaluations.ts` + `voiceDoc.ts`: a separate `spine` return field.**
`{ docIds, titles, chunks, spine }` — `spine: string | null`, ALONGSIDE the arrays, never inside
them. Both callers consume it explicitly. This is required for `voiceDoc.ts`: its
`if (docIds[i] !== docRef) continue;` (`voiceDoc.ts:99`) would have silently discarded a prepended
entry 0, so the spine would never have reached the model there.
**Budget:** `vaultGround.test.ts:179` asserts full-object equality
(`expect(out).toEqual({ docIds: [], titles: [], chunks: [] })`) and MUST be updated for the added
field.

- Budgeted **OUTSIDE** `TOTAL_CHAR_CAP`, which stays 8000 for retrieval results. The spine is not a
  search result and must not compete with them.
- Target ≈ 2500 chars, enforced by per-field caps at serialize time plus a hard total assertion.
- **`[stated]` vs `[source.docx]` markers.** The agent must distinguish what the user asserted from
  what the system inferred: a stated fact is settled and must not be second-guessed at the user; a
  derived fact is challengeable and should be cited when leaned on.
- **A staleness line** (`⚠ N documents added since this was confirmed`) so the agent can say it is
  missing something rather than assert into the gap.
- **No blueprint ⇒ output byte-identical to today.** Fail open, zero regression surface.

### Drift — two stages, no separate detector
- **Stage 1 (free, always on):** any `ready` doc whose id is not in `blueprintSourceDocIds` is
  unincorporated. Pure comparison. Drives the profile-page banner.
- **Stage 2:** rebuild the draft and diff against live. **The diff IS the drift signal** — identical
  ⇒ discard silently; different ⇒ that is the proposal, already computed. Nothing can disagree with
  the rebuild.
- **Stage 2 is USER-TRIGGERED this phase** (owner decision 2026-07-27, REPLACES "fires
  automatically on bulk/folder-ingest completion"). **No bulk-completion event exists** —
  `vaultIngest.onIngestComplete` is per-document (`vault.md:39`), and a 50-file folder would
  therefore trigger 50 model calls. Building a debounced bulk event means editing `vaultIngest.ts`,
  the file 15.2's lane is actively restructuring.
- So this phase ships the **always-on Stage-1 banner** plus a **one-click rebuild**, and nothing
  automatic. Detection is automatic and free; the SPEND is one click. Automatic triggering attaches
  to the same action with no rework when folder ingest lands (15.2 Phase 2).
- **Consequence for BLPR-02:** its *"proposes a reviewable diff when new documents drift"* clause is
  met by detection + one-click rebuild + diff, NOT by an automatic trigger. Plans must not claim
  automation.

### The confirm surface (`/dashboard/profile`, 717 lines today)
Four states: no blueprint / live-and-current / live-plus-unincorporated / draft-pending.
The diff has exactly TWO row kinds and they behave differently:
- **Additions** (blank → value + citation) are non-destructive by construction ⇒ **one Accept
  applies them all**, defaulted ON.
- **Contradictions** (typed ≠ derived) are the ONLY destructive case ⇒ individually checkboxed,
  **defaulted OFF**, shown side by side with sources.
This split falls out of D5 — it is not UI taste. The user must never lose typed content by clicking
Accept too fast, and must never click through 30 rows to accept obvious gap fills.

Confirmation writes an audit event (`blueprint.confirmed`) carrying **refs and counts ONLY** —
docIds, field counts, accepted-contradiction count. No field content (CLAUDE.md §4).

<specifics>
## Specific Ideas

### The live gate (NON-NEGOTIABLE)
Offline green does NOT close this phase. On the owner's real deployment: build a blueprint from the
real vault, confirm it, then observe a cockpit turn whose grounding carries the spine — **verified
by reading the agent's cited sources, not by asserting it should be there.** Precedent: the entire
2026-07-26 pdf-lib defect was invisible offline.

### Verification requirements
Pure-module tests in `packages/core/src/blueprint.test.ts`, no framework beyond existing vitest:
1. **Round trip** — `deserializeBlueprint(serializeBlueprint(b))` deep-equals `b`. Pins the pair to
   change together (the `businessProfile.test.ts` precedent).
2. **Precedence** — `mergeBlueprint` with a typed `targetCustomer` and a contradicting derived
   candidate leaves the typed value in place and emits a `contradiction` row. No model, no network.
   **This is the rule the owner explicitly required; it gets a dedicated test.**
3. **Citation validation** — an out-of-range source index drops that field rather than emitting it
   uncited.
4. **Size cap** — oversized derived fields serialize within the spine cap.
5. **Diff classification** — blank→value ⇒ `addition`; typed≠derived ⇒ `contradiction`; unchanged ⇒
   neither (an identical rebuild is silently discarded).
6. **Field-set totality** — `satisfies Record<...>` so a new field without diff/serializer handling
   is a COMPILE error, not a silently-dropped row (the `TIER_REASON` pattern,
   `businessProfile.ts:330`).

Backend adapter test in `vaultGround.test.ts`: with a live blueprint, `vaultGroundHydrated` returns
a non-null **`spine`** field AND `docIds`/`titles`/`chunks` are UNCHANGED by its presence AND the
retrieval entries still receive the full 8000-char budget. With no blueprint, output is unchanged
from today (`spine` is `null`).

> **This paragraph previously said "returns it as entry 0"** — a leftover from the pre-amendment
> one-seam design, contradicting the two-seam decision above. Corrected 2026-07-27. Entry-0
> prepending is the DISPROVED design: it breaks `llm.ts:1364`. Do not "fix" any plan back to it.

### Existing-code improvement in scope
`apps/web/app/(app)/dashboard/profile/page.tsx` is already 717 lines and this phase adds four
states plus a diff view. Decomposing the blueprint surface into its own component(s) is IN scope as

### Windows testing note
convex-test files false-red on parallel-fork teardown (*"Cannot set properties of undefined (setting
'exit')"*). Re-run `--maxWorkers=1` before trusting a red.

## Deferred Ideas

Spec §9 — each independently buildable later:

- **Folder ingest** (upload a company folder as a unit). Already sequenced as "Phase 2" of the vault
  line in 15.2's context (folders, 1–1.5 GB upload, the 200 MB cap raise). This phase CONSUMES
  whatever the vault contains and does not change how documents arrive; the bulk-ingest drift

  structure that must exist first. This phase renders structured fields plus an entity list.
- **Per-field re-derivation** — rebuilding one field rather than the whole blueprint. The whole
  rebuild is one model call; a per-field path is more machinery for less.
- **Cron-scheduled rebuild.** Adding a timer later is a cron entry over the same action; the weekly
  evaluation cron is precedent for the shape.
- **Multi-blueprint / multi-business per tenant.** One tenant, one business, one blueprint.
