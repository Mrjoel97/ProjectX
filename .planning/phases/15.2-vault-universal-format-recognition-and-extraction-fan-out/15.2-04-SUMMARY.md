# Phase 15.2 Plan 04: Staleness, the Graph Cap, and Failure Copy Summary

**A `ready` row can no longer report a previous attempt's error, `extractGraph` stopped being the one
uncapped model call in the repo, and 15.2-03's richer failure vocabulary now reads as plain English
with an actionable remedy on both vault surfaces.**

## Performance

- **Duration:** ~55 min total (Tasks 1–2 + most of Task 3 in a prior session; Task 3 completion +
  Task 4 + gates here)
- **Tasks:** 4
- **Files modified:** 9 (2 created)

## Accomplishments

**1. Stale attempt state cannot survive into a success (SC#6).** `markExtracting` — which runs at the
START of every attempt, before any parsing — now clears BOTH `failureReason` and
`extractionTruncated`. `markReady` clears `failureReason` only. A `failed("unsupported_format")` →
Retry → `ready` round trip ends with no `failureReason`, and a document whose current attempt
legitimately truncated still reports `extractionTruncated: true` after it reaches `ready`.

**2. The last uncapped model call is capped (SC#6).** `GRAPH_EXTRACT_CHAR_CAP = 120_000` +
`capGraphText` on the `@pikar/vault` barrel, applied as `prompt: capGraphText(safeText)` in
`vaultLlm.extractGraph`. Ordering is **redact-then-cap** — the PII scan sees the whole document or
tail PII escapes both the scan and the audit counts — and the SMOKE short-circuit stays above the
cap. A test asserts `GRAPH_EXTRACT_CHAR_CAP < VAULT_EXTRACT_CHAR_CAP` (400k): the relationship is
the point, because lowering the storage cap under the graph cap would make the graph cap dead code.

**3. `failureCopy` — the ONE place a reason code becomes prose (SC#4).** 21 reason codes → a
plain-language `title` (what happened) + `remedy` (what to do). `PreviewModal` renders both where the
underscored code and a HARDCODED sentence about scanned/image-only PDFs used to be; that sentence is
DELETED because it is wrong for most of 15.2-03's vocabulary (a legacy `.xls` is not an image-only
PDF). The DOCV-01 clause that a failed document offers no voice action, and the Retry button, both
survive. `DocGrid`'s failed card carries the title as one muted ellipsis-truncated line. **The raw
code is never shown** — it rides in a `title=` attribute only (§4: it is a refs-only label).

## Decisions Made

Recorded in full in the frontmatter `key-decisions`. The two that will bite someone later:

**`markReady` deliberately does NOT clear `extractionTruncated`, against the locked spec wording.**
`ingestExtractedText` (`vault.ts:552`) writes that flag on the CURRENT attempt, moments before the
ingest workflow reaches `markReady`. Clearing it there would erase a TRUE truncation flag on every
successful large-document ingest, and that flag is what tells a downstream consumer the grounded text
is a head slice. Anyone "restoring" the spec's wording re-breaks truncation reporting for every large
document. Pinned by a named test and written into the playbook as a trap.

**The `extract_error:` `startsWith` branch specified by the plan was not written.** The `Object.hasOwn`
lookup already misses on any `extract_error: <sdk message>` string and returns `GENERIC` — which is
precisely the outcome the branch would have produced. Writing it would have added a branch whose only
effect is to reach a fallthrough it already reaches (the 15.1-04 `?? "lean"` dead-branch lesson). The
source comment states this rather than silently omitting it.

### Choices inside the plan's latitude (not deviations)

- **The `DocGrid` failure line is card TEXT, not an `aria-label`.** The plan said *"set the card's
  existing `aria-label`/`title` to include it"*. The card `<button>` has NO `aria-label` — its
  accessible name comes from its text content (filename + size + status chip). Adding one would
  REPLACE that whole name and take the filename with it, which is a net accessibility LOSS. Rendering
  the title as text content gives a screen reader the same information in full (the ellipsis is
  purely visual) and keeps the filename. A `title=` supplies the full string on hover.
- **No unit test for `failureCopy`.** `apps/web` has no unit-test runner (`test:e2e` /playwright
  only). Adding vitest there is a new devDependency and a `pnpm-lock.yaml` change in a working tree
  with two other lanes merging — the exact coordination event 15.2-03 recorded as a hazard. The map
  is a pure lookup with no branch beyond the fallback; its risk is COVERAGE, which was verified by
  exhaustive grep and is now pinned in the playbook table with the "you owe a row" rule.
