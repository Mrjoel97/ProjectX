## Two findings the gate itself produced

**1. The plan's own gate command is a silent no-op.** `npx convex run vaultSweep:runSweep` returned:

```
{ "Status": "Migration already done.", "lastFinished": "2026-07-18T03:35:23.430Z", "processed": 12 }
```

`runSweep` is `migrations.runner(internal.vaultSweep.sweepPendingExtraction)` — a
`@convex-dev/migrations` migration that records completion and refuses to re-run. It last finished
**2026-07-18**; the `.xlsm` was uploaded **2026-07-26**, eight days later, so it was never in that
run's cursor range and a bare `runSweep` would never have looked at it again. Recovery required
`'{"reset": true}'`, the argument the component's own output advertises as `toStartOver`.

This is worth more than the pass. **A command documented in `vaultSweep.ts`'s header comment, in
15.2-03's summary, and in this plan's own `<verification>` block reports success while doing
nothing** — the exact silent-success family this phase exists to delete, sitting in the phase's own
tooling. Recorded in the playbook as a standing operational rule.

**2. `size` and `contentHash` are rewritten on every successful extraction.** `vault.ts:632-633`
(`ingestExtractedText`) writes `size: byteLen(text)` and `contentHash: await contentHash(text)`, so
after ingest `size` describes the extracted text, not the uploaded file. Pre-existing and intentional
(hash-dedup keys on the text hash) — **but it means the 803,281-byte fingerprint that identifies this
row in every Phase-15.2 planning document no longer matches the row.** Search by `_id` or title, and
do not conclude the row was deleted.

## NEW KNOWN GAP — PPTX titles-only, and scaffolding-only output reports `ready`

Surfaced by the owner's upload. **Not a Wave-5 regression** — the scheduling/dispatch spine worked;
the defect is one layer down. Both halves were independently verified before being written down.

Row `mx7a40n7460cj3d1ww97bms6wd8bb9zg` (`Rejection Review- Mar 2026.pptx`), `status: ready`,
`ragEntryId` populated (full ingest incl. `extractGraph` ran), **`size: 356` — the entire text**:
`Slide 1\n-March 2026\nMonthly Rejection Overview\n\nSlide 2\n…`.

**Root cause:** `pptxText` (`packages/vault/src/officeText.ts:70-76`) reads `<a:t>` runs from
`ppt/slides/slideN.xml` and nothing else. The deck's KPI content lives in `ppt/charts/chart*.xml`,
embedded worksheets and images — **entries already present in the same `unzipSync` result, never
opened.** The graph was empty because it received 356 chars of headings; `extractGraph` is not at
fault.

**The trap:** line 74 emits `` `Slide ${n}` `` **unconditionally**, so a deck with zero extractable
runs still produces non-empty text, **`empty_extraction` never fires, and the row reports `ready`** —
a false-ready of exactly the family this phase exists to delete. **`xlsxText` has the same shape at
line 65** (`` `Sheet ${n}` ``), so this is a *family*, not a single site: the honesty gap was closed
at the scheduler in 15.2-03 and is **still open in the parsers**.

**Owner disposition:** new plan **15.2-08, after 15.2-07**, covering both halves. **Deliberately not
fixed here** — a verification plan does not smuggle in an edit.
