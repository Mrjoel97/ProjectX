1. **Pitfall 9 (`:107-119`):** `pdf-lib` is a STATIC top-level import and must stay one. `pdf-lib`
   ships `main: cjs/index.js` with no `exports` map; Convex bundles node actions with esbuild
   `platform: node, format: "esm", splitting: true`, and across a dynamic-import chunk boundary
   esbuild cannot synthesise a CJS module's named exports — the namespace carries only `default`,
   so `{ PDFDocument }` destructures to `undefined`. Node/vitest recover the names via
   `cjs-module-lexer`, so a dynamic import looks fine offline and dies deployed. A static scan in
   `vaultExtract.test.ts` locks this; **do not weaken it**.
2. **`getDocumentProxy(bytes.slice())` (`:136-138`) — the `.slice()` is load-bearing.** pdf.js
   *detaches* the buffer it is handed. Anything that touches `bytes` twice must pass a copy. This
   was already caught once offline (pdf-lib read a zeroed buffer).
3. **`CALL_TIMEOUT_MS = 480_000` is PER CALL** (`:58-65`), tuned for one whole-document call on a
   14.4 MB scan. Under fan-out each page inherits all 480 s, so the binding constraint becomes
   Convex's 10-minute *action* ceiling — a per-page bound is now needed. Budget from RESEARCH §7:
   ~10 s/page × 50 pages ÷ 6 concurrent ≈ 9 batches ≈ 90 s nominal.
4. **`recordSpend` (`guardrails.ts:166-173`) is `rateLimiter.limit(ctx, "dailySpendCents", { count, reserve: true })`
   on a single KEYLESS window.** So the fan-out turns 1 write into N writes against one document.
   It cannot silently under-count (`reserve: true` lets the window go negative) and it never
   throws (the return value is ignored), so the exposure is OCC-retry latency at the batch width —
   6, not 50. Verified live in Task 3, not assumed.

`VAULT_EXTRACT_PAGE_CAP` is 50 (`packages/vault/src/extractKind.ts:32`) and still caps the work.

`fanOutPages(pageCount, run, opts)`:
- 7 pages, batch 3, `run = async (i) => "p" + i` → output is
  `"Page 1\np0\n\nPage 2\np1\n\n…Page 7\np6"` (or whichever exact shape you choose — assert it
  literally). **Order is by page index, never completion order:** make the stub resolve in
  *reverse* order (page 6 fastest, page 0 slowest) and assert the output is still ascending. This
  is the assertion that catches a `Promise.all`-order assumption.
- **Concurrency bound:** the stub records in-flight count on entry/exit; assert the maximum
  in-flight never exceeds the batch size, and that batch k+1 starts only after batch k has fully
  settled (sequential across batches).
- **Batch count:** 7 pages at batch 3 → the stub is called exactly 7 times, in 3 batches.
- **Per-page failure is isolated:** stub rejects for page index 2 → output contains a marker for
  page 3 (e.g. `Page 3\n[unreadable]`) and the other six pages' text, and `okPages === 6`.
- **A stuck page does not stall the batch:** stub for page 1 returns a promise that never settles;
  with a per-page timeout of e.g. 50 ms in the test, assert the call returns, page 2 is marked
  unreadable, and the rest land. Use vitest fake timers or a tiny real timeout — do not make the
  suite slow.
- **The wall-clock deadline stops the fan-out:** with a deadline already in the past, assert only
  the first batch runs (or none) and `okPages` reflects it — `truncated` (or an equivalent flag) is
  returned so the caller can tell.
- **Zero successes:** every page rejects → `okPages === 0`. Assert `fanOutPages` reports it rather
  than returning a document made entirely of markers; the caller decides (Task 2 fails the doc).
- Determinism: the same stub twice gives the same output string.
  </behavior>

```typescript
// Pages sent concurrently. 6 is a bounded fan-out, not a throughput knob: each page is its own
// hosted call AND its own recordSpend write against ONE keyless rate-limit window
// (guardrails.ts:171), so the batch width is also the OCC-contention width.
const PAGE_BATCH_SIZE = 6;
// Per-page wall-clock bound. CALL_TIMEOUT_MS (480 s) is PER CALL and was tuned for a single
// whole-document call; under fan-out it would let one stuck page eat the entire 10-minute action
// ceiling. ~10 s/page is the measured norm, so 60 s is 6x headroom.
const PAGE_TIMEOUT_MS = 60_000;
// Total budget for the whole fan-out, under Convex's 10-minute node-action limit with room for
// the surrounding scan/audit/seam work.
const FANOUT_BUDGET_MS = 420_000;
```

```typescript
/**
 * Run `run(i)` for pages 0..pageCount-1 in bounded-concurrency batches, sequential across
 * batches, and reassemble the results in PAGE ORDER.
 *
 * Exported for the offline test (the slicePdfToPageCap precedent): the orchestration — batch
 * width, ordering, per-page isolation, the deadline — is the non-trivial part, and it is provable
 * with a stub and zero model calls. The hosted call itself is not provable offline.
 *
 * A page that fails or times out contributes a marker, not a throw: 49 good pages beat losing the
 * document to one bad scan. `okPages` is what the caller judges success on — a document made
 * entirely of markers is a failure wearing a success costume, which is the shape this whole phase
 * exists to delete.
 */
export async function fanOutPages(
  pageCount: number,
  run: (index: number) => Promise<string>,
  opts?: { batchSize?: number; pageTimeoutMs?: number; deadlineAt?: number },
): Promise<{ text: string; okPages: number; truncated: boolean }>;
```

Implementation, shortest thing that holds:
- `for (let start = 0; start < pageCount; start += batchSize)`; before each batch,
  `if (Date.now() > deadlineAt) { truncated = true; break; }`.
- Per batch: `await Promise.all(indices.map(withTimeout))` where `withTimeout` is
  `Promise.race([run(i).then(ok), sleep(pageTimeoutMs).then(fail)])`, each settling into
  `results[i] = { ok, text }` — write into a **pre-sized array indexed by page**, which is what
  makes ordering structural instead of a sort you have to remember.
  - `// ponytail: Promise.race, not a real per-page AbortSignal. extractHosted's contract is
    reused UNCHANGED (a locked decision), and it owns its own 480 s abortSignal, so a raced-out
    page's request lingers in the background — it just stops blocking the batch, and
    FANOUT_BUDGET_MS bounds the whole thing regardless. Upgrade path if lingering requests ever
    matter: thread an optional timeoutMs through extractHosted (one optional parameter, every
    existing call site unchanged).`
- Reassemble: `results.map((r, i) => \`Page ${i + 1}\n${r.ok ? r.text : "[unreadable]"}\`).join("\n\n")`.
  `Page N` headers match the existing `Sheet N` / `Slide N` convention in `officeText.ts` — reuse
  the house style rather than inventing a third one.
- `[unreadable]` is a marker, never an error message: `§4` — no SDK/parser string, no document
  content, nothing that could carry PII.

Add a one-page emitter next to `slicePdfToPageCap`, loading the source **once**:
```typescript
/** Emit each of the first `limit` pages as its own single-page PDF, from ONE loaded source. */
async function pdfPages(bytes: Uint8Array, limit: number): Promise<Uint8Array[]>;
```
`PDFDocument.load(bytes)` once, then per page `PDFDocument.create()` + `copyPages(src, [i])` +
`addPage` + `save()`. Reloading the source 50 times is the memory pressure the playbook already
flags for large documents — the whole point of the fan-out is to bound per-action memory. Do NOT
convert the `pdf-lib` import to a dynamic one (Pitfall 9).
