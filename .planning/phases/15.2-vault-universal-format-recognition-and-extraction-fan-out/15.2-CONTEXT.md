**Gathered:** 2026-07-27

<domain>
## Phase Boundary

A document the user uploads is either **READ** or it **FAILS** — never a silent "reading…" pill
forever. This phase delivers:

1. Content-based (magic-byte) format recognition replacing the MIME-string allow-list.
2. Coverage of every common business document format, including legacy Office.
3. A hard never-silent guarantee on the two non-terminal statuses that lack one.
4. Per-page fan-out so scanned PDFs transcribe VERBATIM instead of being summarised.
5. An input cap on the one uncapped model call in the repo.

**Origin (live-diagnosed 2026-07-27, not hypothesised):** the owner reported the vault "reading a
document for 10+ minutes". Reading the live `vaultDocuments` table showed a `.xlsm` at
`pending_extraction` for ~20 hours with **0 chars and NO `failureReason`**. `extractionKindFor`
returns `null` for any MIME outside a three-entry allow-list, and `null` schedules no extraction
action at all. The file was never processed — it was not slow, and it was not retrying.

**NOT in this phase** (Phase 2 of this line of work): folders, 1–1.5 GB folder upload, the 200 MB
per-file cap raise, document-identity classification, folder-level synthesis, folder UI drill-in,
Google Drive export. The cap raise is explicitly sequenced AFTER this phase because the playbook
already flags large-doc extraction memory/time at the CURRENT 100 MiB cap — the fan-out is what
bounds per-action memory and makes a raise safe.

</domain>

<decisions>
## Implementation Decisions

Everything below is a LOCKED owner decision (spec approved 2026-07-27). None of it is open.

### Recognition — content over declaration
- `sniffContainer(bytes)` in a NEW pure module `packages/vault/src/sniff.ts` decides the rail from
  magic bytes: `%PDF` (scan first 1 KiB — leading junk is legal), `PK\x03\x04`/`PK\x05\x06`/`PK\x07\x08`,
  OLE2 `D0 CF 11 E0 A1 B1 1A E1`, `{\rtf`, UTF-8 text heuristic, else `binary`.
- The sniffed container is an **override AHEAD of** the existing MIME/extension checks in
  `extractionKindFor`; those remain as fallback. Content wins over what the browser claims.
- Rationale: the allow-list is an enumeration that will always be incomplete. This repo already
  carries a second bug from the same cause (playbook 2026-07-25: Windows sends an empty MIME type
  for `.md`, so the cockpit rejected a supported file). ~20 lines replace a list needing perpetual
  maintenance.

### Format coverage
- **`extractOfficeText` LOSES its `mimeType` parameter.** It unzips once and dispatches on the
  ENTRIES it finds — self-identifying. Every ZIP-based format is then covered by construction
  rather than enumeration. This is a net SIMPLIFICATION of the current signature, not an addition.
- Marker entries → format: `word/document.xml` (DOCX/DOCM), `xl/workbook.xml` (XLSX/**XLSM**),
  `ppt/presentation.xml` (PPTX/PPTM), `mimetype` = `...opendocument.{text,spreadsheet,presentation}`
  (ODT/ODS/ODP), `META-INF/container.xml` (EPUB).
- ODF/EPUB walkers REUSE the existing `runsOf()` + `decodeEntities()` helpers. `fflate` is already
  a dependency. **No new dependency for this tier.**
- Non-ZIP, no dependency: RTF (strip `{\*\…}` groups + `\control` words, unescape `\'hh`),
  HTML/XML (drop `<script>`/`<style>` bodies, strip tags, decode entities), JSON/YAML/TSV/LOG
  (pass-through, added to the searchable MIME set).
- **Legacy DOC/PPT:** OLE2 printable-run sweep (CP1252 + UTF-16LE, min run 4, OLE2 stream-name
  stop-list). No dependency — Word and PowerPoint store text AS TEXT.
- **Legacy XLS/XLSB: SheetJS.** A text sweep is NOT acceptable for BIFF: numbers are stored as
  binary doubles, so a sweep recovers column headers and silently loses every number. That fails
  PLAUSIBLY, which is worse than failing.

### SheetJS — the one new dependency (owner-approved)
- Pinned tarball from `https://cdn.sheetjs.com/` — the vendor's official channel.
- **NOT** npm `xlsx@0.18.5`, the last registry publish, which carries CVE-2023-30533 (prototype
  pollution) and CVE-2024-22363 (ReDoS). This parses untrusted uploads.
- Pinned EXACTLY, no `^` (CLAUDE.md §6 discipline, doubly so for a non-registry dependency).
- Lives behind its OWN subpath module so it is pulled only into the node action that needs it —
  preserving the existing bundle discipline (`officeText.ts` is subpath-only specifically to keep
  `fflate` out of the V8 bundle).
- **Considered and REJECTED:** consolidating all spreadsheet handling onto SheetJS and deleting the
  fflate XLSX path. It removes code but adds ~1 MB to a deliberately lean bundle, and the existing
  path is shipped and tested. Revisit only if the two paths diverge in behaviour.

### Never-silent failure — the ROOT-CAUSE fix
- Unresolvable format → terminal `markFailed("unsupported_format")` at the `vaultUpload`
  chokepoint. NEVER left `pending_extraction`.
- **Watchdog:** a scheduled sweep flips rows stuck in `pending_extraction` or `extracting` to
  `failed("extraction_stalled")`. Threshold **15 minutes** since `createdAt` — comfortably above
  the worst legitimate run (480 s `CALL_TIMEOUT_MS` + the 10-minute action ceiling bound any single
  honest attempt), so it can never kill live work.
- This is the same guarantee `onIngestComplete` gave `processing` after the 2026-07-20 stranding
  incident, extended to the two statuses that never got one. **The format coverage above only
  reduces how OFTEN this fires; the watchdog is what makes silent parking impossible.**
- `markReady` clears `failureReason` + `extractionTruncated` (today a `ready` row can still report
  a stale error from before its successful retry — observed live).
- UI: `DocGrid`/`PreviewModal` render `unsupported_format` in plain language plus the remedy,
  reusing the existing failed-card Retry affordance shell.

### Per-page fan-out for scanned PDFs
- `extractPdf`'s hosted-OCR branch slices to 1-page PDFs with `pdf-lib` `copyPages` (already used
  for the page cap, already a STATIC import per Pitfall 9), extracts in bounded-concurrency batches
  of ~6, sequential across batches, reassembled in PAGE ORDER.
- This matches the `attachment-extractor` skill's documented single-page contract — so CLAUDE.md §5
  is satisfied by REUSE: **no new skill row, no prompt change.**
- Budget: ~10 s/page × 50-page `VAULT_EXTRACT_PAGE_CAP` ÷ batch 6 = 9 batches ≈ 90 s, well inside
  the 480 s `CALL_TIMEOUT_MS` and the 10-minute action ceiling.
- Per-page spend summed through the existing `priceUsage` → `recordSpend` path.
- `ponytail:` ceiling — batching inside one action, NOT a workflow. Beyond the page cap this needs
  a durable workflow or the already-installed `@convex-dev/workpool`. Named, not built.
- Text-layer PDFs are UNTOUCHED — `unpdf` already returns the complete text layer, free.

### `extractGraph` cap
- New `GRAPH_EXTRACT_CHAR_CAP` (~120k chars ≈ 30k tokens), well inside the 128k window for
  token-dense content.
- `ponytail:` ceiling — head slice, not chunk-wise fan-out; entities in the tail of a very long
  document are missed. Upgrade path is chunk-wise extraction with node/edge union, deferred because
  a 254k-char row is observed working today.

### Data model
- **No schema change. No migration.** `failureReason` already exists and is an unconstrained
  string; the `status` union is UNCHANGED. "Stored but unreadable" is `failed` + reason, NOT a new
  state.

### Claude's Discretion
- Plan/wave partitioning and the Wave-0 freeze boundary.
- Exact module/file layout within `packages/vault/src/` beyond `sniff.ts` being new.
- Internal helper signatures, batch-size constant naming, stop-list contents for the OLE2 sweep.
- Test-case enumeration within the verification requirements below.

<specifics>
## Specific Ideas

### The live phase gate (NON-NEGOTIABLE)
`vaultSweep:runSweep` on the owner's real deployment must take the stuck `.xlsm` to `ready` with
**non-zero `textChars`**. Offline green does NOT close this phase — Pitfall-1 class, only the
deployed run proves it. (Precedent: the whole 2026-07-26 pdf-lib defect was invisible offline
because Node/vitest recover CJS named exports via `cjs-module-lexer`.)

### Recovery path for the existing stuck row
`vaultSweep.sweepPendingExtraction` re-dispatches `pending_extraction` rows whose kind is now
recognized. After the sniff change the owner's `.xlsm` becomes recognizable, so the EXISTING sweep
is the recovery mechanism. No new migration.

### Verification convention — NO binary fixtures in repo
Every fixture is built in-test (the precedent Lane 2 set in Phase 3.8):
- ZIP formats → `fflate` `zipSync`.
- Legacy XLS → written **by SheetJS itself** (`XLSX.write(wb, {bookType:'xls'})`), asserting
  **numbers survive** — the specific failure a text sweep would cause.
- Legacy DOC/PPT → synthesized OLE2 byte buffer in-test.
- Hosted PDF branch → observed via the unseeded registry's fail-closed `NO_ACTIVE_SKILL`; no model
  call is ever attempted in tests (existing precedent).

### Already ruled out — do NOT re-investigate
`@pikar/pii` `scanText` is NOT a bottleneck. Measured against the real function: 400k chars of
prose = **8 ms**; 112k chars of tab-joined spreadsheet rows = **4 ms**. The playbook's Phase-3.8
quadratic note concerns long UNBROKEN uniform character runs, a different pathology, not this one.

### Windows testing note
convex-test files false-red on parallel-fork teardown ("Cannot set properties of undefined
(setting 'exit')"). Re-run `--maxWorkers=1` before trusting a red.

### Definition of done
- `docs/playbooks/vault.md` updated in the SAME commit with `Last verified` bumped (CLAUDE.md §9).
- `packages/vault/src/sniff.ts` needs no `watch.json` registration — the existing
  `packages/vault/` prefix covers it.
- The live sweep run and its result recorded in the playbook.

</specifics>

<deferred>
## Deferred Ideas

**Phase 2 of this line of work** (folders), explicitly out of scope here:
- User-created folders (`vaultFolders` table + optional `folderId` — new table, new optional field,
  no migration), with add / remove / replace.
- Folder upload at 1–1.5 GB and the per-kind file cap raise to 200 MB. **Sequenced AFTER this phase**
  — unsafe until the fan-out bounds per-action memory. Video stays at 25 MB (external transcription
  API limit, not our choice).
- Document identity classification (a `.xlsm` recognised as "2025 P&L", not just "a spreadsheet").
- Folder-level synthesis. Lazy shape: the folder digest IS ITSELF a vault document, so it embeds,
  graph-extracts and grounds through machinery that already exists.
- Folder-scoped UI drill-in reusing `PreviewModal`.
- Google Docs/Sheets/Slides via the Drive export API — a distinct rail (no bytes to upload). The
  `google-docs` category and `source: "google"` already exist as the seam.
- Per-folder budget estimate + reservation. Every ingest opens with `guardrails.preCall`, which
  enforces a daily budget; a large folder can trip it mid-run leaving half the documents `failed` —
  and a half-ingested folder is WORSE than a refused one, because the agent grounds confidently on
  the half it got.

**SLO correction to carry into Phase 2:** "1.5 GB understood in 5 minutes" is not achievable and
the bottleneck is not agents — 1.5 GB across a typical 25 Mbps business uplink is ~8 minutes of byte
transfer before any processing starts. The target must be **time-to-first-useful, not
time-to-complete**.

**Chunk-wise graph extraction** (vs. this phase's head-slice cap) — deferred until entity recall is
observed to suffer.
