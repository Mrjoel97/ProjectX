## Summary

Both defects are small and precisely located. Defect A is one unconditional `{brief}` render at
the top of `PlanCards` (cards.tsx:1078) with zero demotion logic; every signal needed to detect
"composition active" (candidates, subject, body, recipients, status) is already on the `plan` prop
in that function's scope — the fix is a boolean + JSX reorder (and optionally a collapsed summary
wrapper OWNED BY PlanCards, never inside the briefing card's testid, or the SC-4 zero-button E2E
assertion breaks). Defect B is a skill-body gap, and — crucially — a skill-only fix is VIABLE
because the agent already sees the pending state every turn: `buildAgentContext` emits an
"Awaiting the user's contact pick" block (name + match count) whenever `plan.candidates` is
non-empty, and `draftBody`/`setSubject` have no recipient precondition, so they work fine with
candidates parked. The skill simply never says what to DO in that state.

The one non-obvious blocker: the mandated eval fixture cannot currently reach the stalled state.
`gmail.search` (the resolveContacts backend) has NO `inboxFixtures` seam — only `listInbox`/
`fetchInboxBodies` do — and the eval tenant has no Gmail token, so every NL resolveContacts turn
degrades to "couldn't read the mailbox" and parks nothing (fixture 09 asserts exactly this today).
The SMOKE:: search sentinel is banned in eval turns. So the phase needs a small Wave-0 change:
a fixture-first branch in `gmail.search` (map fixture messages' `from`/`subject`/`internalDate`
into `HeaderRecord`s, same "fixture rows only exist for smoke/eval tenants" argument as listInbox).
Then "email Sarah Chen…" parks the fixture's `sarah.chen@example.com` candidate and the stalled
turns become assertable with the existing closed expect vocabulary — no new expect keys needed.

**Primary recommendation:** Two lanes. Lane 1 (web-only): compute `composing` in `PlanCards` from
the plan row and demote `{brief}` below the plan cards (reorder; optional PlanCards-owned collapse).
Lane 2 (backend + gate): fixture-first branch in `gmail.search` → new "## While a pick is pending"
skill section via the 2-file mirror edit → new eval fixture 19 (and optionally 20) → full 03.7-05-shaped
gate cycle (seedSkills → refused activate → `pnpm eval:golden --skill cockpit-agent@N` → activate) →
one blocking human-verify replaying the UAT transcript.

## Architecture Patterns

### Finding 1 — Defect A anatomy (cards.tsx, verified at HEAD)

`CardList` (cards.tsx:1025) runs three independent queries (plan byThread, briefing byThread,
agentSteps latestTurn), renders the Activity trace above everything, then delegates to
`PlanCards` (cards.tsx:1067) when a plan row exists. `PlanCards` is the defect:

```tsx
// cards.tsx:1067-1087 — VERBATIM current code
function PlanCards({ plan, threadId, brief }: { plan: Plan; threadId: string; brief: ReactNode }) {
  const reporting = plan.status === "delivering" || plan.status === "done";
  const halted = plan.status === "scheduled" || plan.status === "canceled";
  const hasDraft = (Boolean(plan.body) || Boolean(plan.subject)) && !halted;
  const resolving = Boolean(plan.candidates?.length) && plan.status !== "proposed" && !reporting;

  return (
    <div style={{ display: "grid", gap: "1rem" }}>
      {brief}                                                          // ← THE BUG: unconditional, always first
      {resolving && <ResolutionCard plan={plan} threadId={threadId} />}
      {plan.status === "proposed" && <PlanCard plan={plan} threadId={threadId} />}
      {plan.status === "scheduled" && <ScheduledCard plan={plan} />}
      {plan.status === "canceled" && <CanceledCard plan={plan} threadId={threadId} />}
      {hasDraft && <DraftCard plan={plan} />}
      {reporting && <ReportCard planId={plan._id} />}
    </div>
  );
}
```

**Every composition signal the locked decision names is already in scope on `plan`:**
- candidates parked → `plan.candidates?.length` (already computed as part of `resolving`)
- subject/body set → `plan.subject` / `plan.body` (already computed as `hasDraft`, minus the `!halted` clamp)
- recipients set → `plan.recipients?.length`
- status proposed+ → `plan.status !== "collecting"` (STATUS order: collecting → proposed → approved → scheduled → delivering → done; canceled terminal — `STATUS_ORDER` in run-eval-golden.mjs:66 and schema.ts)

**Minimal fix shape** (Claude's discretion per CONTEXT, recommendation):

```tsx
// Composition-active per the locked decision: candidates OR subject/body/recipients OR status past collecting.
const composing =
  Boolean(plan.candidates?.length || plan.subject || plan.body || plan.recipients?.length) ||
  plan.status !== "collecting";
// ...
return (
  <div style={{ display: "grid", gap: "1rem" }}>
    {!composing && brief}
    {resolving && <ResolutionCard plan={plan} threadId={threadId} />}
    …existing cards unchanged…
    {composing && brief /* demoted: still reachable, below the work */}
  </div>
);
```

The briefing-only flow (plan row exists at `collecting` with nothing set — the common
`sendCockpitMessage`-inserts-a-plans-row-on-thread-creation case, 03.7-04 lesson) keeps the brief
primary. The moment `resolveContacts` writes candidates, Convex reactivity re-renders and the
ResolutionCard is the top artifact card. If a collapsed-summary look is wanted, wrap the demoted
`{brief}` in a PlanCards-owned `<details><summary>Inbox briefing</summary>…</details>` — native
element (ponytail rung 4), no new CSS needed, and the toggle lives OUTSIDE the briefing card's
testid so SC-4's zero-`button`/`a`-inside-the-card E2E assertions (cockpit-briefing.spec.ts:150-153)
stay green. Reorder alone already satisfies the owner's done-condition ("SEES the picker without
scrolling").

**Note on ActivityCard:** the LATEST TRACE card renders above `PlanCards` output entirely
(CardList:1058-1063) and is not part of this arbitration — "top card" means top card in the
`PlanCards` grid. Do not touch the trace placement (03.9-03's first-turn/plan-status traps live there).

### Finding 2 — What the agent sees while a pick is pending (llm.ts, verified)

`buildAgentContext` (llm.ts:466-532) is rebuilt from the plan row EVERY turn and injected into the
prompt (llm.ts:1575). When `plan.candidates` is non-empty it emits:

```
Awaiting the user's contact pick (NOT yet recipients — tell the user to pick from the card, do NOT claim you added them):
  Brett J. Fox: 2 contact(s) found
```

(name + count ONLY — §2-D/§4; llm.ts:498-519). It also always emits `Subject: (not set)` /
`Body drafted: no` lines. **Conclusion: the loop CAN see the pending state and what is already
filled — skill wording alone can fix the re-announce/re-ask loop.** The context line's own
imperative ("tell the user to pick from the card") actually FEEDS the re-announce loop — every
stalled turn re-instructs the model to point at the card. The skill edit must override this with
turn-scoped guidance ("if you have already told them once, don't repeat it; act on new info
instead"); optionally the plan may also soften that one context string in llm.ts:516 — but that
string is code, not skill, so prefer fixing it in the skill body first and touch the context line
only if eval shows wording alone can't beat the per-turn instruction.

`draftBody` (llm.ts:813-847) and `setSubject` have NO recipient/candidate precondition — draftBody
scans intent (fail-closed), calls `draftCockpit` with `plan.greetingName`, patches `bodyIntent`+`body`.
Confirmed: **they work fine with candidates parked** (matches CONTEXT's claim). `greetingName` is only
set on pick (resolveRecipients folds pick #1's name), so a body drafted pre-pick has a generic
greeting — acceptable; the user reviews on the PLAN card.

### Finding 3 — Eval harness mechanics (run-eval-golden.mjs, verified at HEAD)

- **Fixture format** (`packages/backend/scripts/eval-cases/NN-name.json`): `{ id, description,
  turns: string[], expect: {…}, needles: string[] }`. Turns are plain NL, `SMOKE::` prefixed turns
  REJECTED offline (line 80). At least one needle required (scanned against every audit/DLQ/telemetry
  row by `smokeAssert:assertEvalCaseClean`).
- **Closed expect vocabulary** (line 43-63): `status`, `statusAtMost`, `recipients`, `recipientCount`,
  `mode`, `subjectPresent`, `bodyPresent`, `attachmentCount`, `attachmentError`, `candidatesPending`,
  `briefingPresent`, `ledePresent`. **Everything the stalled-resolution fixture needs already exists**
  — `candidatesPending: true` + `subjectPresent: true` + `bodyPresent: true` + `recipientCount: 0` +
  `statusAtMost: "collecting"` expresses "pick still stalled, but subject/body were absorbed." No new
  expect key, no runner surgery (unlike 03.7-05 which had to mint `briefingPresent`).
- **Multi-turn is native**: `attemptCase` (line 292) seeds ONE plan per case (`smoke:seedCockpitPlan`)
  and feeds each turn sequentially through `llm:runCockpitAgent` with the same planId/threadId —
  a pending-resolution mid-conversation is just turn 1 parking candidates and turn 2+ speaking into
  the stall. State is read ONCE at the end (`plans:getById`), so assertions are on the FINAL state —
  fine here: candidates stay parked (nothing unparks them without the human pick).
- **The harness CANNOT simulate the panel pick.** `resolveRecipients` is a public tenantAction driven
  by the authenticated UI; the runner only calls internal functions with an explicit tenantId and by
  design never performs human actions (same structural zero-send argument as never calling
  executePlan). **The fixture must stay in the stalled state** — which is exactly what CONTEXT locks
  ("the assertion is that setSubject/draftBody are CALLED … rather than the agent re-asking").
- **Self-check floor** is `>= 18` fixtures (line 189) — adding fixture 19/20 passes without a floor
  bump (optionally bump to keep it tight).
- **Gate cycle** (proven live 03.6-05, 03.7-05): persistent `npx convex dev` running →
  `npx convex run skills:seedSkills` publishes candidate vN (active row untouched) → prove the gate:
  `activateSkill` vN REFUSES (EVAL_GATE, no evidence) → `pnpm eval:golden --skill cockpit-agent@N`
  all-green records `EvalEvidence` on the row (refs/counts-only) →
  `npx convex run skills:activateSkill '{"name":"cockpit-agent","version":N}'` succeeds. Cost cap
  $1.00/run, expected $0.05–0.15 at gpt-4o-mini. Exit 2 = environment (governed stop/cap), never a
  case failure. One-retry flake policy per case on a fresh plan.

### Finding 5 — THE BLOCKER: `gmail.search` has no fixture seam (gmail.ts, verified)

`resolveContacts` (llm.ts:655-705) calls `internal.gmail.search`. `search` (gmail.ts:242-308) has
exactly two offline affordances: the `SMOKE::` name sentinel (banned in eval fixtures) and… nothing
else — it goes straight to `freshAccessToken`, and the eval tenant has no token, so it returns
`{ok:false}` → resolveContacts returns "I couldn't read the mailbox … ask for the address" and
**writes no candidates**. Fixture `09-resolve-degradation.json` asserts this exact degradation
(`candidatesPending: false`). Meanwhile `listInbox`/`fetchInboxBodies` (gmail.ts:394-408, 474-480)
check the `inboxFixtures` seam FIRST ("real tenants never have fixture rows — the seam cannot
shadow a live mailbox"), and the eval run already seeds that fixture at run start
(run-eval-golden.mjs:355, 5 messages incl. `Sarah Chen <sarah.chen@example.com>`).

**Required Wave-0 change:** a fixture-first branch in `search`, mirroring listInbox's:

```ts
// gmail.ts search handler, after the SMOKE:: branch, before freshAccessToken:
const fixture = await ctx.runQuery(internal.smoke.getInboxFixture, { tenantId });
if (fixture) {
  const records: HeaderRecord[] = fixture.messages.map((m) => ({
    from: m.from,                                  // "Sarah Chen <sarah.chen@example.com>"
    subject: m.subject,
    date: new Date(m.internalDate).toUTCString(),  // rankCandidates Date.parse-es rec.date
  }));
  await audit(records.length);                     // same refs-only mailbox.searched audit
  return { ok: true, records };
}
```

`rankCandidates` (packages/core/src/emailIntent.ts:144-190) then does the rest: parses each `from`,
scores name-match (2 = full-name substring of displayName/address, 1 = any token, 0 dropped —
no-match returns `[]`, the 03.3-06 never-substitute rule), so "Sarah Chen" matches the fixture row
and candidates park; "Alonzeva" (fixture 09) matches nothing → still `candidatesPending: false`,
though via the no-match branch instead of not_connected — fixture 09's state assertions still hold
(update its `description` string; keep the not_connected degradation covered in `gmail.test.ts`
unit tests where it already lives). Unit-test the new branch in `gmail.test.ts` (fixture-first,
audit refs-only, live tenants unaffected).

## Common Pitfalls

### Pitfall 1: Breaking cockpit-briefing.spec.ts's SC-4 / order assertions
**What goes wrong:** Demotion adds a toggle/button inside `data-testid="briefing-card"` → the spec's
`card.locator("button")).toHaveCount(0)` (line 152) fails; or a collapse hides the card in the
brief-only flow → `toBeVisible` assertions (lines 97-146) fail.
**How to avoid:** Demote ONLY when `composing` — the spec's scenario (brief=today, nothing composed,
plan at `collecting` with nothing set) must keep the brief primary and fully rendered. Any wrapper
lives in PlanCards, outside the card's testid. Verify by running the spec's type-load/discovery and
reading its assertions (live run stays blocked — see Pitfall 6).

### Pitfall 2: The plan-status dispatch traps (03.7-04 / 03.9-03 recorded lessons)
**What goes wrong:** Moving cards around in CardList/PlanCards re-introduces the traps STATE.md
records: gating something behind `plan === null` / plan-status branches ("a status-'collecting' row
made the OLD dispatch render literally nothing"), or nesting the ActivityCard/trace under a status
branch, or touching the no-args `latestTurn` first-turn logic.
**How to avoid:** Confine the change to the `PlanCards` return JSX + one derived boolean. Do not
touch `CardList`'s three-query structure, the `rest()` early returns, or the trace placement.
Structural check after the edit: `useQuery(api.agentSteps.latestTurn)` still above `!threadId`,
still above `plan === null`, `<ActivityCard>` still outside `PlanCards`.

### Pitfall 3: The eval fixture silently measures nothing (the not_connected trap)
**What goes wrong:** Without the `gmail.search` seam, fixture 19's turn 1 degrades ("couldn't read
the mailbox"), no candidates park, and `candidatesPending: true` FAILS — or worse, a fixture written
without that expect key "passes" while measuring nothing (the 03.7-05 Pitfall-3 class).
**How to avoid:** Seam first (Wave 0), fixture second; keep `candidatesPending: true` in the expect —
it is the anti-silent-pass guard here, exactly as `briefingPresent` was for briefings.

### Pitfall 4: Activating on the wrong version / skipping the refused-activate proof
**What goes wrong:** `seedSkills` may mint vN where N is unknown from the repo (runtime fact);
hardcoding N, or activating without first proving the gate refuses, repeats nothing and proves nothing.
**How to avoid:** Copy 03.7-05 Task 2 verbatim: seed → read back N → prove EVAL_GATE refusal →
pinned run → activate. Keep ONE persistent `npx convex dev` for the whole cycle (per-command cold
starts contaminate the runner's stdout — 03.6-05 finding; the eval-env-recovery memory adds: after a

### Pitfall 5: The context line fights the skill
**What goes wrong:** buildAgentContext:516 injects "tell the user to pick from the card" EVERY
stalled turn — a skill edit that only says "don't re-announce" is arguing with a per-turn instruction.
**How to avoid:** Word the skill section to explicitly supersede repetition ("your context reminds
you a pick is pending every turn — that is state, not an instruction to repeat yourself; mention the
panel again at most once, with new words"). If the pinned eval run shows the model still looping,
the fallback is softening llm.ts:516's imperative to a neutral state description ("the user has not
picked yet") — a code change, but to a CONTEXT string, not a prompt (no §5 issue; llmRedaction scans
unaffected since no new content crosses §2-D). Prefer skill-only; hold the context edit in reserve.

### Pitfall 6: Known baseline reds and blocked live E2E — don't chase them, don't regress them
**What goes wrong:** Time lost re-diagnosing documented noise, or a real regression hiding in it.
**Baseline (verified in STATE.md 03.5-06 close):** `audit.test.ts` auditCounts red (pre-existing);
`runCockpitAgent.test.ts` 5000ms machine-load timeout (reproduces on base under load, green under
light load); backend source typecheck has a documented 30-error `.test.ts`-only baseline; cards.tsx
carries 3 pre-existing Biome findings (sole `useHookAtTopLevel` at ResolutionCard) — verify no NEW
findings via the stash-diff method. Live Playwright runs remain blocked (E2E_USER_EMAIL/PASSWORD
absent; composer gated on `gmailAuth.status.connected` which no smoke helper can seed — do NOT
weaken that gate); specs must type-load + be discovered, with the live run owed to the human-verify
session which has a connected user by construction.

### Pitfall 7: gsd-tools commit quoting on Windows
**What goes wrong:** `gsd-tools.cjs commit` breaks on Windows quoting.
**How to avoid:** Use plain `git commit` (established workaround).
