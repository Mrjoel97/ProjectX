<domain>
## Phase Boundary

Fix the two shipped defects that made a real cockpit conversation collapse. NO new capability:
"Draft a reply" as a true reply is Phase 3.11, NOT this phase. This phase makes the EXISTING
brief → resolve → compose flow survive a real user, in the panel and in the agent's turn logic.

The verbatim UAT transcript (2026-07-19) is the fixture source. Its failure chain:

1. User: "What happened in my inbox?" → briefing renders (25 messages). Fine.
2. User: "Draft a reply to Brett Jay Fox." → not found (mailbox has "Brett J. Fox"). Fine —
   the never-guess recipient guard working as designed.
3. User: "Brett J. Fox" → resolveContacts parks candidates; agent says "ready to pick in the
   panel". User NEVER completes the pick — the tall BriefingCard sits pinned above the
   ResolutionCard and buries it (user literally typed: "where is the list" and "the workspace
   still has the brief card").
4. With the pick stalled, the agent loops: re-announces "ready to pick in the panel" three
   times, re-asks for a subject, and on "tell him i will attend the workshop" (stated TWICE)
   fails to call draftBody/setSubject until several turns later.
5. Final plan ships with recipient "#1 (no name)" — a plan the user must not be shown as
   normal output of a healthy flow.

Defect A (PANEL): `apps/web/app/(app)/dashboard/workspace/cards.tsx` — CardList/PlanCards
renders `{brief}` unconditionally above every plan card (line ~1078) and nothing ever
dismisses/demotes the BriefingCard when the conversation pivots from briefing to composing.

Defect B (AGENT): `packages/contracts/skills/cockpit-agent.md` — the skill's "call
resolveContacts then STOP" rule has no guidance for the turns AFTER the stop: while a pick is
pending the agent should still absorb subject/body/intent the user supplies (call setSubject/
draftBody — those tools work fine with candidates parked), never re-announce the panel more
than once, and be able to tell the user plainly that the pick is still pending if they seem
lost. Also honor its own "Never re-ask for something the user already told you" rule in this
state.

</domain>

<decisions>
## Implementation Decisions

### Panel arbitration (Defect A)
- When a plan enters active composition (candidates parked for resolution, OR any of
  subject/body/recipients set, OR status proposed and beyond), the BriefingCard must yield
  primacy: the ResolutionCard/PlanCard renders on top and the brief is demoted (collapsed
  summary row or moved below) — NOT silently destroyed; the user may still want to glance at it.
  Exact demotion mechanic (collapse vs reorder) is Claude's discretion, but the picker must be
  visibly the top card the moment candidates exist.
- BRAND.md rules apply (no new component library, reuse box/label/dim idioms, a11y basics).
- The briefing row remains reachable — deleting the briefings row or its query is out of scope.

### Agent stalled-resolution recovery (Defect B)
- The cockpit-agent skill body edit is REGISTRY-GATED (Phase 3.6): mirror-edit →
  seedSkills publish candidate → pnpm eval:golden --skill cockpit-agent@N → activateSkill.
  The plan MUST include the full gate cycle — an unactivated candidate fixes nothing live.
- New eval fixtures MUST reproduce the transcript's failure shape: a pending-resolution state
  where the user supplies body intent ("tell him i will attend the workshop") and the
  assertion is that setSubject/draftBody are CALLED (plan state carries subject/body) rather
  than the agent re-asking. Assert on plan/tool state, never reply text (3.6 harness rule).
- While a pick is pending, the agent must: (a) still act on any subject/body/attachment/time
  info in the user's message; (b) point at the panel at most ONCE more, and only with new
  words (e.g. "the contact list is in the workspace panel, below the briefing"); (c) never
  re-ask for a slot already given.
- The recipient guard itself is UNTOUCHED: never guess an address, panel-only resolution
  stays. "Brett Jay Fox" failing to match "Brett J. Fox" is accepted v1 behavior (fuzzy
  middle-name matching is NOT in scope — defer).

### Governance invariants (unchanged, restated because both defects touch their surfaces)
- No hardcoded prompts (§5) — all agent-behavior change flows through the skill registry.
- Audit refs-only (§4); no new audit event types expected in this phase.
- proposePlan/executePlan seams untouched.

</decisions>
