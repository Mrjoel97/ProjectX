# Phase 28.1 Plan 08: The Erasure Billing Arm, and the Phase Seal — Summary

## What this plan was for

`convex/tenantDelete.ts` said nothing about billing. Erasing a tenant revoked Google and Microsoft
and then walked the tables — leaving a live Stripe subscription **charging a card belonging to
nobody**. That is BILL-06, and it is the loop this plan closes.

## Ordering is the whole task

```
deleteTenantData
  ├─ authorizeTenantDeletion  → { googleConnected, microsoftConnected, billingActive }
  ├─ google disconnect      ┐
  ├─ microsoft disconnect   ├─ revoke-first, each in its own try/catch
  ├─ billing terminate      ┘   ← NEW
  └─ deleteTenantDataPage loop  ← DELETES billingCustomers
```

`billingCustomers` is `tenant_owned`, so the page loop erases the row holding `subscriptionId` — the
only place it is stored. **An arm placed after the loop finds nothing to cancel and reports
`hadSubscription: false`, which is indistinguishable from a tenant who never subscribed**: a silent,
permanent leak that no test or audit row would ever flag.

**The regression test does not read source order.** It asserts `revokedAtProvider: true`, and that
value cannot be true unless the subscription id was read while the row still existed. There is no
call-sequence bookkeeping to drift out of sync with the code.

Both closed unions were widened — the TypeScript `ProviderDeletionResult` and the Convex
`providerResultValidator`. Widening one and not the other is a runtime rejection under a green
typecheck, which is why the plan named both.

## `terminateBilling` holds two opposite properties

| It must | Because |
|---|---|
| **never throw** | an erasure that stops because Stripe is down is a worse outcome than one that completes with a recorded failure the owner can act on |
| **never report a silent success** | a no-op cancel that reads as done is how a subscription outlives its tenant, and in the audit row it looks identical to a real cancellation |

So an HTTP error, a timeout, a network drop, an unusable stored id and missing configuration all
come back as `failure: true` with a **code token** (never Stripe prose, §4) — while an absent
subscription is `hadSubscription: false, failure: false`, because reporting "never subscribed" as a
failure trains the owner to ignore the field.

`billingConfigured()` is asked *before* the call rather than catching `requireSecret`'s throw,
specifically so `billing_not_configured` and `stripe_http` are different answers.

## The erasure tradeoff is now asserted, not commented

| Table | Class | After an erasure |
|---|---|---|
| `billingCustomers`, `billingPeriods`, `billingUnapplied` | `tenant_owned` | **gone** |
| `billingEvents`, `billingCoverage` | `audit_immutable` | **survive** |

Erasing a tenant removes the mapping and the working rows; it does not rewrite Pikar's financial
book. Both halves are asserted in one test so the tradeoff stays deliberate.

## The naming boundary is now enforced by the suite

Two Stripe integrations live in this repo and they point in opposite directions across opposite
trust boundaries:

- **Pikar's own merchant account, charging outward** — `packages/billing/`, `convex/billing*.ts`,
  `BILLING_STRIPE_*` (a write-capable secret key)
- **A tenant's Stripe account, read-only** — `packages/revenue/src/providers/stripe.ts`,
  `convex/stripeAuth|stripeConnector.ts`, `STRIPE_APP_*` (an OAuth app grant into somebody
  else's books)

`billing.test.ts` now scans every merchant-rail module for `STRIPE_APP_`, `connectorFetch`,
`providers/stripe`, `stripeAuth` and `stripeConnector`, and pins `BILLING_STRIPE_SECRET_KEY` to
exactly one consumer. **Proven non-vacuous by mutation** — injecting both a `connectorFetch` string
and a `STRIPE_APP_SECRET_KEY` read into `billingApi.ts` turned it red.

The split is the safety property of the whole phase. If the two ever share a module or a secret, a
write-capable merchant key reaches a surface built to read a customer's account — a mix-up invisible
in every other test, because both are "a Stripe key that works".

## The seal

The playbook's stale `Status: PARTLY IMPLEMENTED` block (which still described the 28.1-05 state) is
replaced with what is true at this commit, including a step-by-step list of what a live run would
need and the plain statement that **nothing in this phase has ever spoken to Stripe**.

`BILLING_STRIPE_SECRET_KEY` was set on the LOCAL deployment on 2026-08-30 (owner-supplied test-mode
key, to be rotated). `BILLING_STRIPE_PRICE_ID` and `BILLING_STRIPE_WEBHOOK_SECRET` are unset
everywhere, and Convex env vars are per-deployment — the cloud dev and production deployments carry
no billing variable at all.

`requirements-completed: []` — BILL-06's mechanism exists and is proven offline against a stubbed
`fetch`. No subscription has ever been cancelled at Stripe, so the requirement stays PENDING like
every other requirement in this phase.
