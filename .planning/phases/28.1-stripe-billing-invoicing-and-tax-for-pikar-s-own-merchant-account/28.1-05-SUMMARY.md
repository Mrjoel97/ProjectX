# Phase 28.1 Plan 05: Tenant↔Stripe-Customer Mapping and the Refusal to Invent a Tenant — Summary

## What this plan was for

A `checkout.session.completed` can arrive for a customer who paid before onboarding finished, or
whose tenant was already deleted. The obvious "helpful" behaviour — create the tenant from the
webhook — is how a billing system starts inventing users, and anyone able to drive a Stripe checkout
could mint rows in this database. **The locked decision is: never.** An unmatched customer is
dead-lettered by ref and nothing is created.

## What landed

- **`billingCustomers`** — `by_tenant` and `by_customer`, so the mapping resolves in both
  directions. `by_customer` is deliberately NOT tenant-led and carries a written justification in
  `isolation.test.ts`: a `customer.subscription.*` delivery carries a `cus_…` and nothing that names
  a tenant — no session, no cookie, no `client_reference_id`. That is the entire reason the row
  exists. The tenant it then acts as comes FROM the row, never from the request.
- **`BillingEventFacts` / `eventFacts`** — the redact-then-write boundary expressed as a **closed
  type**. Every member is an id, an enum token or a timestamp. `refId()` also unwraps an expanded
  object, because a Dashboard-configured expansion turning `"cus_…"` into `{ id, email, name }` is
  exactly how a whole object gets carried into a row.
- **`deadLetters.workflowId` → optional**, plus `source: "workflow" | "billing"`. Readers treat a
  missing `source` as `"workflow"`.
- **`billingStatus` now has evidence.** Its `not_subscribed` / `subscribed` arms were advertised by
  the validator and unreachable as of 28.1-04; they are reachable now.

## The two things that matter more than the feature

**1. Nothing personal can reach `deadLetters`.** That table is `audit_immutable` — insert-only, and
excluded from BOTH the tenant-deletion walk and the export walk *by construction*. Anything personal
that lands there outlives every erasure request this deployment can honour. So the guard is
structural: `refuse()` takes `facts`, not the raw event, and there is no object in scope to leak
from.

**2. No auto-provisioning.** The unknown-tenant arm dead-letters under the sentinel tenant
`billing:unattributed` — not an invented id, and not one borrowed from elsewhere.

## Deviations from the plan

**1. `eventFacts` is not in the plan at all.** The plan described redaction as something the webhook
arm does. It became a typed boundary in `packages/billing/src/events.ts` instead, which is a
strictly stronger version of the same requirement and lives on the pure side per CLAUDE.md §1.

**2. `packages/core/src/tenantData.{ts,test.ts}` were not in `files_modified`, and had to be.**
Adding a table moves the schema-drift pin from 51 to **52** and demands a classification. Chosen:
**`tenant_owned`** (deletable) — with the ordering hazard recorded at the site: 28.1-08's deletion
arm must cancel the Stripe subscription BEFORE the walk reaches this table, because the walk deletes
the row holding the customer id it needs.

**3. `http.ts`, `isolation.test.ts` and `apps/web/.../ops/page.tsx` were also untracked by the plan**
— the ops screen renders dead letters and had to stop assuming `workflowId` exists.

### Mutations — 2 verified directly, both RED, both restored byte-identical

The executing agent was terminated mid-run by a session rate limit and **its own mutation record was

mutations itself.

| # | Mutation | Result |
| --- | --- | --- |
| M1 | Leak `customer_details.email` through `BillingEventFacts` into the dead-letter payload | **RED** — 25 tests, including both whole-row PII assertions |
| M2 | Replace the unknown-tenant `refuse(...)` with `ctx.db.insert("users", ...)` — the "be helpful" regression | **RED** — 5 tests, disjoint set, including *"creates zero users, zero mappings, one dead letter"* and the source scan *"the mapping module contains no way to create a user or a tenant"* |

**M1 is also evidence about the design, not just the test.** Leaking an email required editing **two
files** — widening the closed type AND threading the field through — because `refuse()` never sees a
raw object. There is no single-line edit that leaks PII here. That is the difference between a
redaction *step* (skippable by a future caller) and a redaction *boundary*.

Backups size-verified after writing; both restores confirmed with `cmp` and `git status`, not by
trusting harness output.

**Not verified by this session:** whatever other mutations the agent ran before it was cut off. If
the duplicate-delivery and conflict arms need mutation evidence, they do not have it yet.

## What this plan does NOT prove

- **Nothing has still ever spoken to Stripe on a billing path.** Every test drives the real route
  via `convexTest(...).fetch(...)` with a **fabricated** `whsec_` and a **fabricated** event body.
  No `BILLING_STRIPE_*` is set in any deployment and `CONVEX_SITE_URL` is `http://127.0.0.1:3211`.
- **`BILL-01` is NOT complete.** A subscription has never provisioned end to end: no real Checkout
  session has been completed, no real webhook delivered, and the mapping has only ever been written
  from a body this repo wrote itself. `requirements-completed: []`.
- **The deletion arm does not exist yet.** `billingCustomers` is classified deletable, but
  `tenantDelete.ts` still says nothing about billing — deleting a tenant today would leave a live
  subscription charging a card. That is 28.1-08, and the cancel-before-walk ordering above is a
  constraint it inherits.
- **Ordering is defended, not proven against Stripe.** The `event.created` guard against an
  out-of-order re-delivered `updated` following a `deleted` is tested against fabricated timestamps.
