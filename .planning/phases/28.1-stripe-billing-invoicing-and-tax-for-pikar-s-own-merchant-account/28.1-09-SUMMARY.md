# Phase 28.1 Plan 09: The Tenant-Facing Billing Surface — Summary

## What this plan was for

**A capability nobody can reach is not shipped.** Before this plan, four things this phase built
were invisible from `apps/web`:

| Built by | Thing | Callers in `apps/web` |
|---|---|---|
| 28.1-06 | `unappliedFunds` — the 75/90-day clock | 0 |
| 28.1-03 | `renderTaxPosture` — the function whose whole job is to make a bare `0.00` unreachable | 0 |
| 28.1-07 | `billing.invoices` — hosted invoice links | 0 (asserted by a test) |
| 28.1-04 | `?checkout=` — the `success_url`/`cancel_url` handed to Stripe | ignored by `page.tsx` |

A tenant finishing a Stripe Checkout landed on a page headed **"Control your data"** about JSON
export. 28.1-08 was about to seal the phase over that.

## What landed

`apps/web/app/(app)/dashboard/settings/BillingPanel.tsx`, mounted above `<DataControls />` on
`/dashboard/settings`, with the page header rewritten ("Your billing and your data"). It closes all
four gaps in one card stack: the `?checkout=` acknowledgement, subscription state + the Customer
Portal control, held bank-transfer funds with their age, hosted invoice links, and the tax posture.

**The structural decision that makes this testable.** `apps/web` has no jsdom and no
testing-library, and `vitest.config.mts` scopes the runner to `.ts` — never `.tsx` — deliberately,
because a `.tsx` test here once "read as coverage in the diff and in review" while executing
nowhere. So the file is split:

- `BillingPanel` — hooks (`useQuery` ×3, `useAction`, `useEffect` for `?checkout=`). Not importable
  by the test.
- **`BillingPanelView` — hook-free, every value a prop.** `billingPanel.test.ts` renders it to a
  string with `renderToStaticMarkup` (the `../finance/cashView.test.ts` idiom).

That is what makes 12 of the 32 assertions about **rendered markup** rather than about a helper's
return value. Every refusal below is pinned twice — once on the derivation, once on the markup.

### The five honesty rules, and what holds each

1. **Unknown is not zero.** `subscriptionCopy("unknown")` returns "Your subscription state is not
   something we can tell you yet." / "…so we do not know… We are not saying you owe nothing — we
   are saying we cannot see." Asserted against written-out literals: contains neither `"$0"`,
   `"0.00"`, `"free"` nor `"no charge"`, in the helper AND in the markup.
2. **A redirect is not evidence.** `checkoutNotice("success")` acknowledges the return and is
   asserted **not to contain `subscriptionCopy("subscribed").headline`** — two disjoint literals, so
   the only sentence that can claim a subscription is the one `billingStatus` owns. Also asserted
   not to contain `"active"`. A rendered `?checkout=success` over `billingStatus: "unknown"` shows
   the banner AND "we do not know".
3. **An unrecognised token renders nothing.** `checkoutNotice` matches exact tokens only; the markup
   for `?checkout=garbage` contains no `data-checkout-notice` attribute at all — not an empty
   banner.
4. **No portal without a proven billing record.** `manageSubscription("unknown")` is
   `{ enabled: false, reason }`; the button renders `disabled` with the reason beneath it. **And
   `manage()` repeats the guard as an early return**, because `disabled` is presentation a devtools
   user can strip and `portalLink` must never be nudged into provisioning a Stripe customer.
5. **No amber outside the approval gate (BRAND §2).** Unapplied funds *feel* like a warning; they
   are emphasised with `--ink-soft` + weight instead. A source scan over `BillingPanel.tsx` and
   `page.tsx` for `/--held|#f0a22e/i` holds it.

### Reuse, not reimplementation

- **`FigureTile`** is imported from `../finance/CashView` for the held-balance COUNT. Unknown
  coverage renders the em-dash and a prompt — never a zero — which is the whole reason the
  component exists.
- **`unappliedStage`** from `@pikar/billing/reconcile` derives the 75/90 stage. Its own JSDoc named
  this call site in advance ("later by the tenant-facing surface that renders a stored observation
  whose age has since grown"). No second copy of the boundaries.
- **`moneyFromMinor` / `formatMoneyAmount`** from `@pikar/revenue/money` format the amounts.

## Deviations from the plan

**1. [Rule 3 — Blocking] `apps/web` could not import `@pikar/billing` or `@pikar/revenue`.**
Neither was a dependency of `apps/web`, and there is no `paths` mapping in `tsconfig.base.json`, so
`renderTaxPosture` was unreachable from the web app by construction. Added both as **workspace**
deps + `pnpm install` (`pnpm-lock.yaml` +6 lines, no other package churn). **No external dependency
was added.**
*Files: `apps/web/package.json`, `pnpm-lock.yaml`. Commit `4c543aa`.*

**2. [Rule 1 — Bug] `packages/backend/convex/billing.test.ts` asserted `billing.invoices` has NO
caller in `apps/web`.** True when written, and it was the gap — not the goal. Inverted: it now
asserts exactly one caller (`BillingPanel.tsx`), that the caller contains `hostedInvoiceUrl`, and
that it contains no `line_items`/`subtotal`/`amount_due`/`total_taxes`/`tax_amount` renderer — the
locked "we serve a link, never a document" decision, now asserted against a file that exists. Given
its own non-vacuity guard (`panel.length > 2000`), because every clause below it is negative.
*Commit `4c543aa`.*

**3. [Rule 2 — Missing critical] The in-code portal guard had nothing holding it.** Deleting

*Commit `602bf1f`.*

**4. The plan named the wrong playbook.** It listed `docs/playbooks/billing.md`, which `watch.json`

**`dashboard-pages.md`**. Both updated: `billing.md` owns the domain, `dashboard-pages.md` owns the
page.
*Commit `ed7131c`.*

**5. A third invisible surface, not in the plan's objective.** The plan named three gaps;
`billing.invoices` (28.1-07, landed after the plan was written) was a fourth. Rendered here too.

## How the source scan was proved NOT vacuous

28.1-07 found `codeOf` in `convex/billing.test.ts` gutting the files it scanned — a 468-line file
reduced to 13 — so every negative assertion over it passed for the wrong reason. The guard that
missed it only checked that the file LIST was non-empty. So the amber scan checks four things a
blanked file cannot satisfy:

1. **Content, per file, not the list.** `BillingPanel.tsx` length > 2000 AND contains
   `"BillingPanelView"`; `page.tsx` contains `"BillingPanel"`; `DataControls.tsx` contains
   `"DELETE MY DATA"`.
2. **A positive control on the pattern itself.** `AMBER.test("color: var(--held-text)")`,
   `AMBER.test("background: var(--held)")` and `AMBER.test("background: #F0A22E")` are all asserted
   `true`.
3. **A negative control.** `AMBER.test("color: var(--ink-soft)")` is asserted `false`, so the
   pattern is not simply matching everything.
4. **Mutation C** inserted a real `var(--held-text)` into the panel and the scan went RED.

The scan reads **raw source, not `codeOf`** — no comment-stripping regex is involved, so the
28.1-07 failure mode is structurally absent. The cost is that a comment mentioning the token would
trip it; the file is written to avoid the literal in prose, on purpose.

The same non-vacuity discipline was applied to the inverted `billing.invoices` assertion in
`convex/billing.test.ts` (`panel.length > 2000` + a positive `hostedInvoiceUrl` check before the
negatives).

## What this plan does NOT prove — read this before believing anything above

- **Nothing here has spoken to Stripe, and nothing has run in a browser.** No `BILLING_STRIPE_*`
  variable is set in any deployment. On the live stack `billingStatus` answers `unknown` for every
  tenant and both lists are empty under `coverage: "unknown"`, so **the only arm a real user can
  currently see is the unknown one**. The `subscribed` / `not_subscribed` / held-balance /
  invoice-link arms are proven by `renderToStaticMarkup` over fixture props and by nothing else.
- **The query wiring is proven only by a source assertion and a successful build.** That
  `useQuery(api.billing.unappliedFunds, {})` returns what `BillingPanelView` expects is enforced by
  `FunctionReturnType<typeof api.billing.unappliedFunds>` at the type level — which is real, and is
  not a runtime observation. No Convex round-trip was made.
- **`?checkout=` is read in a `useEffect` inside the HOOKED component**, which the DOM-free runner
  cannot execute. The *handling* of the token is fully pinned; the *reading* of it from
  `window.location.search` is not. This is the exact shape of the "clock plane dead in production"
  defect (a param not threaded through the caller while every unit test passes) — the mitigation
  here is that there is only one reader and one consumer in one file, but that is an argument, not
  evidence.
- **The portal redirect is unexercised.** `window.location.assign(door.url)` has no test.
- **The in-code portal guard is held by a SOURCE assertion, not a behavioural one.** It fails if the
  line is deleted; it proves nothing about the call at runtime. Upgrade path is stated in the test:
  a Playwright assertion on `/dashboard/settings` for a tenant with no `billingCustomers` row.
- **BILL-03 and BILL-05 now have a surface, which is not the same as being verified.** BILL-03's
  clock renders correctly for a given `ageDays`; no `billingUnapplied` row has ever existed on any
  deployment. BILL-05's posture is honest for `CONFIG_CONFIRMED === false`; the `true` branch says
  "unknown" and has never been exercised because the business is not registered.
- **No visual check was made against `docs/design/brand/`.** BRAND compliance here is by rule
  (tokens, tracked-caps labels, card radius/shadow, teal as a fill only) and by the amber scan — not
  by looking at the rendered page.
- **The backend suite reports `1 error` alongside 3135 passed / 0 failed.** It is a pre-existing
  unhandled rejection in `convex/dispatch.test.ts` (`Component "rag" is not registered`, via
  `vaultIngest.ts`), unrelated to this diff, which touches no dispatch/RAG path. Flagged because the
  recorded baseline said "0 failed" and did not mention the error.
