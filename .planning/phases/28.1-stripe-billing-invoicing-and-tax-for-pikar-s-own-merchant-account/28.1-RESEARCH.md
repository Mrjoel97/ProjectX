## Summary

Every Stripe-side product decision is already locked, so the research value here is entirely in the
seam: **how a write-capable Stripe integration behaves inside Convex's runtime and inside this
repo's existing money/audit/erasure machinery.** Four things dominate.

**First, the runtime.** A Convex `httpAction` runs in the *same sandbox as queries and mutations* —
no Node APIs, and `"use node"` is not permitted in `http.ts`. Stripe's synchronous
`webhooks.constructEvent` therefore cannot run there; the edge-safe path is either
`constructEventAsync(..., Stripe.createSubtleCryptoProvider())` from `stripe-node`, or ~25 lines of
Web Crypto HMAC. The repo already owns that HMAC helper — `hmacHex` at
`packages/backend/convex/gmailAuth.ts:26` — and `stripe` is **not** an installed dependency, so the
ponytail-correct rung is a hand-verified signature plus plain `fetch` against
`https://api.stripe.com`, exactly as every other provider in this repo is called.

**Second, idempotency has to be a read-then-insert inside ONE mutation, because Convex has no unique
index.** What makes that safe is not a constraint but OCC: Convex mutations are serializable and are
transparently re-run when their read set is invalidated, so a concurrent duplicate loses the race,
re-runs, sees the row, and returns early. This exact pattern already exists and is battle-tested —
`recordMovement` at `packages/backend/convex/spendLedger.ts:107-133` reads `by_correlation`, checks
`(tenantId, phase)`, and returns the existing `_id` on a replay. Copy that shape, do not invent one.
The `httpAction` is *not* transactional, so the dedupe must live in the mutation it calls, and the
mutation must return "was this new?" so the action can skip the side effects.

**Third, the ledger question is not settled and the planner must decide it explicitly.** The
"existing append-only ledger" is `spendEvents` — and it is a **cost** ledger: `SPEND_RAILS` is a
closed three-value union (`reasoning | media | ingest`, `packages/core/src/spend.ts:16`), amounts are
**positive USD cents only** (`validateSpendMovement`, `spend.ts:62`), `aggregateSpend` hard-codes all
three rails in five places, and the whole Finance surface renders it as *what Pikar spends*. Adding a
fourth `revenue` rail would put money-in and money-out in one `Record<SpendRail, SpendTotals>` and
silently corrupt every existing total. The recommendation is a **separate `billingEvents` table that
reuses the phase vocabulary verbatim** (`estimated | reserved | actual | refunded | adjustment`) and
the `spendCoverage` "unknown, never zero" discipline — same law, different book.

**Fourth, the tax requirement has a concrete field and a sharp edge.** `taxability_reason` on the
invoice tax breakdown is exactly the "not owed vs calculated zero" discriminator BILL-05 asks for —
but Stripe's own docs say `not_collecting` is **ambiguous**: it means *either* no registration in the
customer's jurisdiction *or* a Nontaxable product tax code (`txcd_00000000`). Since this phase also
configures the product tax category, the two inputs interact: pick `txcd_00000000` and the honest
"not registered" signal becomes unreadable forever. Threshold monitoring is additionally **live-mode
only** and its notifications require **$10,000 USD revenue in the previous year** — so for a
pre-revenue merchant, BILL-05's "explicit alert" is a posture we record, not a signal we receive.

**Primary recommendation:** build `packages/billing` (pure: signature verification, event
classification, money mapping, tax-posture derivation) + `convex/billingWebhook.ts` (one `httpAction`
that verifies and hands a raw string to one `internalMutation` that owns the `billingStripeEvents`
insert-if-absent) + `convex/billingApi.ts` (outbound `fetch` with a deterministic `Idempotency-Key`)
+ a `billingEvents` ledger table that mirrors `spendEvents`' law without joining its rails. Prove the
entire thing offline with `convexTest(...).fetch()` and a fabricated `whsec_` secret.

## Architecture Patterns

### Finding 1 — Webhook signature verification inside a Convex `httpAction` (BILL-02)

**Raw body.** Convex `Request` supports `.text()`, `.json()`, `.blob()`, `.arrayBuffer()`; request and
response size is capped at 20 MB ([Convex HTTP Actions](https://docs.convex.dev/functions/http-actions)).
Call `await request.text()` **once** and verify against that exact string. Stripe is explicit: *"Stripe
requires the raw body of the request to perform signature verification… Any manipulation to the raw
body of the request causes the verification to fail."* Never `JSON.parse` and re-serialize — key
order and whitespace change and the HMAC will not match.

**Runtime.** HTTP actions *"run in the same environment as queries and mutations so also do not have
access to Node.js-specific JavaScript APIs"*, and **`"use node"` cannot be used in `http.ts`**. This
kills `stripe.webhooks.constructEvent` (synchronous, Node `crypto`). Two working options:

1. **`constructEventAsync` + `Stripe.createSubtleCryptoProvider()`** — the documented edge path
   (Cloudflare Workers / Supabase Edge Functions use exactly this). Requires adding `stripe`.
2. **Web Crypto by hand** — HMAC-SHA-256 over `` `${t}.${rawBody}` `` with the `whsec_` secret as
   key, compared constant-time against every `v1=` value in the `Stripe-Signature` header, plus a
   tolerance check on `t`. `hmacHex` at `gmailAuth.ts:26` already does the HMAC half.

**Cost of `"use node"`, for the record:** a `"use node"` module may hold **only actions** — a
completion mutation cannot sit beside its action (`cockpit.ts:847` records this exact lesson, and
`calendar.ts`/`calendarComplete.ts` is the repo's worked example of the split). Since the webhook
route must call a mutation to do the dedupe, and `http.ts` cannot be `"use node"` anyway, this is
moot: **do not reach for `"use node"` on this path.**

**Confidence:** HIGH (Convex docs + Stripe docs + repo source read directly).

### Finding 2 — Structural idempotency in Convex (BILL-02)

**Convex has no unique indexes.** Multiple documents may share indexed field values; uniqueness is
enforced by querying before insert. Convex has stated it may add `.unique()` on indexes in future; it
does not exist today ([Convex Community: Unique Indexes](https://discord-questions.convex.dev/m/1066140499402031135)).
`db.query(...).unique()` is a *read helper that throws on >1 row* — not a constraint.

**What makes read-then-insert safe is OCC, not a constraint.** Convex mutations are
*serializable* — "a declarative proposal to write records on the basis of any read record versions",
and at commit time writes succeed only if every read version is still current. On conflict Convex
**re-runs the mutation automatically** ([Convex OCC and Atomicity](https://docs.convex.dev/database/advanced/occ)).
So for two concurrent duplicate deliveries of the same `event.id`:

- both mutations read the `by_event` index range (which enters both read sets),
- one commits the insert,
- the other's read set is invalidated → Convex re-runs it → this time the read **finds** the row →
  it returns `{ inserted: false }` and writes nothing.

**The exact pattern already exists in this repo.** `recordMovement`
(`packages/backend/convex/spendLedger.ts:107-133`) reads `by_correlation`, finds a row matching
`(tenantId, phase)`, and `return already._id` on a replay — with the comment at
`spendLedger.ts:98-99`: *"A replay returns the id already stored and ignores the replayed amount."*
Mirror this. Do not invent a second idiom.

**The httpAction→mutation boundary matters and is the trap.** An action is **not** transactional. If
the `httpAction` does `runMutation(insertEvent)` and then applies side effects itself, a crash between
them leaves a `stripeEvents` row with no effect applied — and the Stripe retry will now be *suppressed*
by that row. Two safe shapes:

- **(A) Claim + settle (recommended).** The mutation inserts with `status: "received"` and returns
  `{ inserted }`. Only `inserted === true` proceeds. All ledger writes happen in a **second mutation**
  that also flips the row to `applied` in the *same transaction*. A row stuck at `received` past a
  threshold is exactly what `reliabilitySweep` (`crons.ts:62`, every 30 min) already exists to find.
- **(B) One mutation does everything.** Insert + all ledger writes in a single `internalMutation` —
  atomic by construction. Viable here because no side effect needs `fetch`. Simplest, and the ponytail
  answer unless a handler genuinely needs an outbound call.

**Return 2xx fast.** Stripe: *"you must return a `200` response before updating a customer's invoice
as paid in your accounting system"*, and a timeout is a delivery failure. Both shapes above are DB-only
and fast; if any handler ever needs an outbound call, `scheduler.runAfter(0, ...)` from the mutation is
transactional-with-the-mutation and returns immediately.

**A nuance the plan must record: `event.id` is not a complete dedupe key.** Stripe's own guidance:
*"In some cases, two separate Event objects are generated and sent. To identify these duplicates, use
the ID of the object in `data.object` along with the `event.type`."* So `event.id` is the *structural*
dedupe (it stops redelivery), but a handler that must be effect-idempotent should key its ledger write
on `(data.object.id, event.type)` — which is what the `correlationId` field is for.

**Ordering is not guaranteed.** Stripe: *"Stripe doesn't guarantee the delivery of events in the order
that they're generated."* A `customer.subscription.created` can arrive after its `invoice.paid`. Every
handler must be order-independent or explicitly re-read from the API.

**Confidence:** HIGH.

### Finding 3 — Scheduling the invoice rollup (BILL-04)

| Mechanism | Guarantee | Source |
|---|---|---|
| `crons.daily/weekly/interval` | **At most one run of each cron executes at any moment**; a run is *skipped* if the previous one is still going (and logged in the dashboard) | [Convex cron jobs](https://docs.convex.dev/scheduling/cron-jobs) |
| `scheduler.runAfter/runAt` **from a mutation** | Scheduling is **atomic with the mutation**. Mutation fails → nothing is scheduled | [Convex scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions) |
| `scheduler.runAfter/runAt` **from an action** | **Not** atomic — the scheduled function may run even if the action later fails | ibid. |
| Scheduled **mutations** | *"guaranteed to be executed exactly once"*; internal errors auto-retried | ibid. |
| Scheduled **actions** | *"executed at most once"* and **not** automatically retried; they permanently fail on transient errors | ibid. |

**The consequence for BILL-04 is sharp: a cron pointing straight at an `internalAction` that POSTs to
Stripe can silently drop a whole billing period.** No retry, no error surface, no invoice. The
correct shape:

1. `crons.daily("billing-invoice-rollup", …, internal.billingRollup.tick, {})` → an
   **`internalMutation`**.
2. That mutation *claims* the due period by inserting/patching a period row (transactional; a second
   tick finds it claimed and no-ops — same read-then-insert law as Finding 2), and only then
   `scheduler.runAfter(0, internal.billingRollup.postInvoice, {periodId})`.
3. `postInvoice` is the action. Its POST carries `Idempotency-Key: billing-invoice:{tenantId}:{periodKey}`.
4. On success it calls a mutation that records the Stripe invoice id on the period row.
5. A period claimed but never settled past a threshold is found by the next tick or by the existing
   30-minute `reliabilitySweep` — the repo's established answer to a severed scheduler chain
   (`crons.ts:51-62`).

**How this interacts with Stripe idempotency keys.** Stripe saves the status code and body of the
first request per key and replays it — *but* "You can remove keys from the system automatically after
they're at least 24 hours old. We generate a new request if a key is reused after the original is
pruned." **So the Stripe key protects a same-day retry only.** A rollup retried more than 24 h later
with the same key mints a *second* invoice. The durable guard must be our own period row, with the
Stripe key as the inner belt. Also: replaying a key with *different parameters* errors, so the key must
be derived from the same inputs that build the body.

**Bounding the window.** `POST /v1/invoices` pulls **all** pending invoice items for a customer.
Bound the rollup by filtering/creating invoice items with a `period` and only rolling customers whose
period row is due — do not rely on "whatever is pending".

**Confidence:** HIGH.

### Finding 5 — Tax (BILL-05): the concrete field, and why it is ambiguous

**The field exists.** `taxability_reason` appears on the tax breakdown of the invoice
(`invoice.total_details.breakdown.taxes[].taxability_reason`, per Stripe's own worked example on
[Zero tax amounts and reverse charges](https://docs.stripe.com/tax/zero-tax)) and on invoice line
items (`tax_amounts[].taxability_reason`). On a `tax.calculation` object it is
`tax_breakdown[].taxability_reason` alongside `tax_rate_details` and `taxable_amount`.

| `taxability_reason` | Meaning |
|---|---|
| `not_collecting` | **Either** no active registration in the customer's jurisdiction **or** the product carries the Nontaxable code `txcd_00000000` |
| `product_exempt` | Product is exempt |
| `reverse_charge` | B2B reverse charge; customer accounts for VAT |
| `customer_exempt` | Customer is exempt |
| `not_supported` | Stripe Tax doesn't support that country/territory or product there |
| `not_subject_to_tax` | Jurisdiction imposes no tax / the sale isn't a taxable transaction |
| `product_exempt_holiday` | US sales-tax holiday |
| `portion_product_exempt` | Tier rule; part exempt |
| `zero_rated` | Subject to the zero rate |
| `standard_rated` | Normal taxed line |

**So: "not owed because unregistered" IS distinguishable from "calculated as zero" — `not_collecting`
vs `zero_rated`/`not_subject_to_tax`/`product_exempt`/`reverse_charge` — but `not_collecting` itself
does NOT distinguish "unregistered" from "we marked the product nontaxable".** Stripe says this
verbatim: *"`not_collecting` is ambiguous: it means either no active registration in the customer's
jurisdiction **or** a Nontaxable product tax code (`txcd_00000000`) on the product. Check the
product's tax code before concluding it's a registration gap."*

**Therefore the honest model must be ours, and it needs BOTH halves:** the Stripe-reported
`taxability_reason` AND our own recorded product tax code. `not_collecting` + a real SaaS code
(`txcd_10103001`) = *not owed, unregistered*. `not_collecting` + `txcd_00000000` = *we declared it
nontaxable*, which is a different claim entirely and is **not** the posture this phase wants.
**Concrete consequence: the product tax category MUST NOT be `txcd_00000000`.** Choosing it would
make the honest posture permanently unreadable and would also poison threshold monitoring, which
*"assume[s] that all sales are conducted with your preset tax code."*

**What threshold monitoring does and does not do** ([Monitor your obligations](https://docs.stripe.com/tax/monitoring)):

Does: tracks Stripe-processed sales minus refunds, attributes a location per transaction (once per
day; new transactions appear within ~7 days), compares against local registration thresholds in
supported locations, and surfaces status per location in the Dashboard (`Needs attention` /
`Collecting tax` / `Not collecting tax` / `Issue` / `Registration in progress`). Refunds and credit
notes adjust the calculation within 24-48 h.

Does **not**:
- **Does not run in test mode.** *"Obligations are only monitored in live mode."* **This is the single
  most important operational fact for planning: BILL-05 cannot be demonstrated in the test-mode
  sandbox.**
- **Does not monitor your home state/country.** *"We provide insight into the places where you don't
  have a physical presence so obligations aren't monitored for your home US state or country."* The
  head office address is therefore what *excludes* a jurisdiction, not just what includes ones.
- **Does not emit a webhook.** There is **no** `tax.threshold.*` event in
  [the event types list](https://docs.stripe.com/api/events/types) — the only tax event is
  `tax.settings.updated`. Notification is **email** (from `support+updates@stripe.com`) and a
  **Dashboard bell**, to the account owner.
- **Does not notify a pre-revenue merchant.** Notification preconditions: opted into Stripe Tax,
  notifications not disabled, **$10,000 USD in revenue in the previous year**, no active live-mode
  registration for the location, and no tax-threshold notification in the past 7 days. Below $10k/yr,
  **no notification will ever fire.**
- Does not cover out-of-band payments except invoices processed off Stripe and Tax-API transactions;
  does not differentiate retail/wholesale or marketplace/non-marketplace; does not monitor retail
  delivery fees, amusement or parking taxes.

**Planning consequence.** BILL-05's "crossing a monitored threshold surfaces as an explicit alert"
cannot be delivered by code in this phase. The buildable, honest version is: (1) a code-owned constant
recording the configured product tax code and head office country, (2) a derived tax-posture value
persisted per invoice from `taxability_reason` + that code, rendered as *"no tax owed — not registered
in this jurisdiction"* and never as *"tax: $0.00"*, and (3) a documented operations item in
`docs/playbooks/billing.md` stating that threshold alerts arrive by email to the account owner,
live-mode only, gated at $10k/yr. **Say this out loud in the plan rather than shipping a monitor that
can never fire.**

**Confidence:** HIGH on every quoted fact. MEDIUM on the recommended modelling (a design call).

### Finding 6 — Bank transfer and the cash balance (BILL-03)

**Where funds sit.** A bank-transfer customer has a **cash balance** — *"funds that were paid by the
customer to a merchant, but have not yet been allocated to a payment."* Money lands there first, then
Stripe reconciles it onto invoices/PaymentIntents.

**Automatic reconciliation is the default** ([Reconciliation](https://docs.stripe.com/payments/customer-balance/reconciliation)).
Stripe applies funds in this order (USD/EUR/GBP/MXN):
1. Match the bank-transfer **reference** to a single invoice with a matching **invoice number**.
2. Else match the reference to a single incomplete PaymentIntent via
   `next_action.display_bank_transfer_instructions.reference`.
3. Else look for a group of **1-5** invoices/PaymentIntents awaiting the **exact** amount sent.
4. Else fully fund as many invoices as possible, oldest finalized first.
5. Else apply any remainder to incomplete PaymentIntents, oldest first.

An invoice is eligible only while `open` and *"either hasn't passed its due date or became overdue
within the last 365 days."*

**`customer_cash_balance_transaction` types** ([Cash Balance Transaction](https://docs.stripe.com/api/cash_balance_transactions/object)):
`funded`, `applied_to_payment`, `unapplied_from_payment`, `refunded_from_payment`, `funding_reversed`,
`adjusted_for_overdraft`, `return_initiated`, `return_canceled`, `transferred_to_balance`.
`net_amount` is signed: **positive = funds added, negative = funds removed.** An
`applied_to_payment` transaction carries the PaymentIntent the funds went to.

- **`funded`** — new money arrived in the cash balance. **This is arrival, not collection.**
- **`applied_to_payment`** — money left the cash balance onto a specific PaymentIntent. **This is
  collection.**
- **`funding_reversed`** — a prior funding was **reversed** (the incoming transfer was pulled back).
  Money we may already have counted has gone away. This is the event that makes "record `actual` on
  `invoice.paid`" a real financial error, not a theoretical one.
- **`unapplied_from_payment`** — funds were pulled *back off* a payment into the balance.

**`cash_balance.funds_available` has a mode-dependent meaning, and this is easy to get backwards.**
Stripe's own description: *"Occurs whenever there is a positive **remaining** cash balance after Stripe
automatically reconciles new funds into the cash balance. If you enabled manual reconciliation, this
webhook will fire whenever there are new funds into the cash balance."* So under the **default
automatic** mode this event is **the unapplied-money signal** — exactly the "unapplied funds are
visible rather than assumed collected" half of BILL-03 — and NOT a "money arrived" signal.

**Event sequence for an invoice paid by bank transfer (automatic mode), typical:**

```
invoice.created → invoice.finalized                      (invoice number minted; open)
   ... customer wires to the VBAN, 1-5 business days ...
customer_cash_balance_transaction.created  type=funded            ← ARRIVAL, not collection
customer_cash_balance_transaction.created  type=applied_to_payment ← COLLECTION (per PI)
invoice.paid / invoice.payment_succeeded                          ← invoice closed
[cash_balance.funds_available]                                    ← ONLY if money is left over
[invoice.overpaid]                                                ← paid with non-zero amount_overpaid
[payment_intent.partially_funded]                                 ← amount_remaining changed
```
Order is **not** guaranteed (Stripe's own warning). Do not build a state machine that requires it.

**The correct signal that money is actually collected:**
`customer_cash_balance_transaction.created` with `type === "applied_to_payment"`, whose `net_amount` is
negative and whose `applied_to_payment.payment_intent` ties it to the invoice. `invoice.paid` alone is
**not** sufficient for bank transfer, and `type === "funded"` is **not** collection either.

**Mapping onto the phase vocabulary (recommendation):**

| Stripe signal | Ledger phase | Note |
|---|---|---|
| invoice finalized / open | `estimated` | Amount we expect to collect |
| `customer_cash_balance_transaction` `type=funded` | `reserved` | Money exists but is not ours yet — this is precisely `reserved`'s meaning, and `UNLANDED_RESOLVES`-style "in flight" |
| `type=applied_to_payment` | `actual` | Collected |
| `invoice.paid` **for a card payment** | `actual` | Card is synchronous; the trap does not apply |
| `charge.refunded` / `credit_note.created` / `type=refunded_from_payment` | `refunded` | Positive amount; direction lives in the phase |
| `type=funding_reversed` / `unapplied_from_payment` | `refunded` (or a new `reversed`) | **Must not be silently dropped** |

**Unreconciled money has a clock.** Stripe emails reminders; at **75 days** it attempts to return
unreconciled funds to the customer's bank; by **90 days** unreturnable funds are swept to the Stripe
account balance. A billing "unapplied funds" surface should show age, not just amount.

**Confidence:** HIGH on every event/type/behaviour (Stripe docs, quoted). MEDIUM on the phase mapping
(a design recommendation).

## Common Pitfalls

### Pitfall 1: The dedupe row commits, the effect does not
**What goes wrong:** the `httpAction` inserts the `stripeEvents` row, then crashes before the ledger
write. Stripe retries; the row already exists; the retry is suppressed; the payment is never recorded.
**Why:** an action is not transactional; only the mutation is.
**How to avoid:** either do insert + effects in ONE mutation, or use `status: "received" → "applied"`
with the flip in the same transaction as the effect. Never "insert here, apply there, no status".
**Warning signs:** a `stripeEvents` row whose `status` is still `received` minutes later.

### Pitfall 2: Signature verification that passes on the wrong inputs
**What goes wrong:** four separate ways.
- Verifying a re-serialized body → always fails (Stripe: *"Any manipulation to the raw body … causes
  the verification to fail"*).
- Using `constructEvent` (sync) in the Convex runtime → throws; you need `constructEventAsync` with
  `Stripe.createSubtleCryptoProvider()`, or hand-rolled Web Crypto.
- Ignoring the timestamp → a captured payload replays forever. Stripe libraries default to a **5
  minute** tolerance. *"Don't use a tolerance value of `0`. Using a tolerance value of `0` disables the
  recency check entirely."*
- Taking only the first `v1=` value → **during a secret roll an endpoint has multiple active secrets
  and Stripe sends one signature per secret**, on ONE header line. Check every `v1=`; ignore any
  non-`v1` scheme (there is a fake `v0` on test events, and honouring it is a downgrade attack).
**How to avoid:** split on `,` then `=`; take `t`; collect ALL `v1` values; HMAC
`` `${t}.${rawBody}` ``; constant-time compare against each; reject if `|now - t| > 300s`.
**Warning signs:** verification works in tests and fails in production (secret roll), or a replayed
capture succeeds.

### Pitfall 3: The Stripe idempotency key is treated as durable
**What goes wrong:** a rollup fails, is retried 30 hours later with the same key, and mints a second
invoice — the customer is billed twice.
**Why:** *"You can remove keys from the system automatically after they're at least 24 hours old. We
generate a new request if a key is reused after the original is pruned."*
**How to avoid:** our own period-claim row is the durable guard; the Stripe key is the same-day belt.
Also: replaying a key with different parameters **errors**, so derive the key from the same inputs
that build the body.

### Pitfall 4: `invoice.paid` treated as cash in hand
See Finding 6. Card: fine. Bank transfer: wrong, and `funding_reversed` can take it back afterwards.

### Pitfall 5: `not_collecting` read as "we are unregistered"
See Finding 5. It also means "the product is coded Nontaxable". Store the product tax code alongside
the reason, or the honest posture is unprovable.

### Pitfall 6: Auto-provisioning a tenant from a webhook
**What goes wrong:** a `checkout.session.completed` arrives for a Stripe customer with no tenant (paid
before onboarding finished, or tenant already deleted) and the handler creates one.
**How to avoid:** the locked decision is **never auto-create**. Dead-letter by ref and leave the
customer orphaned but visible. Note the `deadLetters.workflowId` obstacle in Finding 4 — the plan must
decide how to widen it, and must not put the customer's email in the payload.

### Pitfall 7: A green vitest suite over a red typecheck or a red sibling test file
**What goes wrong:** twice in Phase 28 alone, `convex/env.test.ts` was red on unclassified provider env
names while filtered runs read green (28-05 `0dca7bd`, and again in 28-06). This phase adds
`BILLING_*` names — the same trap, aimed at the same file.
**How to avoid:** every new `process.env.BILLING_X` literal gets an `ENV_MANIFEST` row **in the same
commit**; run the whole package suite, not a filter; run `tsc --noEmit` per package separately.

### Pitfall 8: Cron overlap silently skipping a billing period
Convex: *"At most one run of each cron job can be executing at any moment"*, and a run is **skipped**
if the previous is still executing. Combined with actions being at-most-once, a slow or failed rollup
loses a period with no error surface. See Finding 3 for the claim-row shape.

### Pitfall 9: A new billing table with no `TENANT_TABLE_CLASSIFICATION` entry
`tenantData.ts:28` is `satisfies Readonly<Record<string, TenantTableCategory>>` and there is a
source-level drift test. A new table must be classified: `billingCustomers` →
`tenant_owned` (or `tenant_credential` if it holds anything secret-ish), `billingEvents` →
decide deliberately (`tenant_owned` means a tenant erasure rewrites financial history — `audit_immutable`
is the safer read, and carries the insert-only + never-personal-data obligations).

### Pitfall 10: CRLF in `.planning/` and `docs/playbooks/`
Those files are CRLF. Multi-line `\n` edit anchors silently no-op. Normalize and assert uniqueness
before editing `docs/playbooks/watch.json` or any planning doc.

### 1. Raw-body signature verification in a Convex `httpAction` (hand-rolled, no new dependency)

```ts
// packages/billing/src/signature.ts — PURE (CLAUDE.md §1). No ctx, no fetch, no DB.
// Header shape per https://docs.stripe.com/webhooks#verify-manually :
//   Stripe-Signature: t=1492774577,v1=<hex>,v0=<hex>
// Multiple v1= values appear DURING A SECRET ROLL. v0 is a fake test scheme — ignore it.
export const SIGNATURE_TOLERANCE_S = 300; // Stripe's own library default. Never 0.

export function parseStripeSignature(header: string): { t: number; v1: string[] } | null {
  let t: number | null = null;
  const v1: string[] = [];
  for (const part of header.split(",")) {
    const eq = part.indexOf("=");
    if (eq <= 0) continue;
    const k = part.slice(0, eq).trim();
    const v = part.slice(eq + 1).trim();
    if (k === "t") t = Number(v);
    else if (k === "v1") v1.push(v);       // v0 and any future scheme are DROPPED (downgrade attack)
  }
  return t !== null && Number.isFinite(t) && v1.length > 0 ? { t, v1 } : null;
}

/** Constant-time hex compare. `!==` on a digest is a timing oracle. */
export function timingSafeEqualHex(a: string, b: string): boolean {
  if (a.length !== b.length) return false;
  let diff = 0;
  for (let i = 0; i < a.length; i++) diff |= a.charCodeAt(i) ^ b.charCodeAt(i);
  return diff === 0;
}
```

```ts
// packages/backend/convex/billingWebhook.ts (the adapter half)
import { hmacHex } from "./gmailAuth"; // gmailAuth.ts:26 — Web Crypto HMAC-SHA-256 hex, already here

export async function verifyStripeSignature(
  rawBody: string, header: string, secret: string, nowS: number,
): Promise<boolean> {
  const parsed = parseStripeSignature(header);
  if (!parsed) return false;
  if (Math.abs(nowS - parsed.t) > SIGNATURE_TOLERANCE_S) return false;   // replay window
  const expected = await hmacHex(`${parsed.t}.${rawBody}`, secret);
  return parsed.v1.some((sig) => timingSafeEqualHex(sig, expected));      // ALL v1s, secret roll
}
```

```ts
// packages/backend/convex/http.ts — the route. Verify, then parse, then hand to ONE mutation.
http.route({
  path: "/billing/stripe/webhook",
  method: "POST",
  handler: httpAction(async (ctx, req) => {
    const secret = process.env.BILLING_STRIPE_WEBHOOK_SECRET;
    const header = req.headers.get("stripe-signature");
    if (!secret || !header) return new Response("unauthorized", { status: 400 });

    const raw = await req.text();  // THE RAW STRING. Never json()-then-stringify.
    if (!(await verifyStripeSignature(raw, header, secret, Math.floor(Date.now() / 1000)))) {
      return new Response("invalid signature", { status: 400 });
    }

    // Only AFTER verification is parsing safe. One transactional mutation owns dedupe + effects.
    const { id, type } = JSON.parse(raw) as { id: string; type: string };
    await ctx.runMutation(internal.billingWebhook.receiveAndApply, { eventId: id, type, raw });
    return new Response(null, { status: 200 }); // 2xx fast — a timeout is a delivery failure
  }),
});
```

### 2. Structural idempotency — the `recordMovement` shape, verbatim in spirit

```ts
// packages/backend/convex/billingWebhook.ts
// Convex has NO unique index. What makes this safe is OCC: the by_event read enters the read set,
// so a concurrent duplicate is re-run by Convex, finds the row on the second pass, and no-ops.
// This is spendLedger.recordMovement (spendLedger.ts:107-133) applied to event.id.
export const receiveAndApply = internalMutation({
  args: { eventId: v.string(), type: v.string(), raw: v.string() },
  handler: async (ctx, args) => {
    const existing = await ctx.db
      .query("billingStripeEvents")
      .withIndex("by_event", (q) => q.eq("eventId", args.eventId))
      .unique();                       // read helper, NOT a constraint — it throws on >1
    if (existing) return { inserted: false };   // the insert IS the dedupe

    await ctx.db.insert("billingStripeEvents", {
      eventId: args.eventId, type: args.type, receivedAt: Date.now(), status: "applied",
    });
    // ...ledger writes here, in the SAME transaction. No `runAction`, no fetch, no await on I/O.
    return { inserted: true };
  },
});
```

### 3. The rollup: cron → claiming mutation → action, with a durable key

```ts
// packages/backend/convex/crons.ts (addition)

// packages/backend/convex/billingRollup.ts
export const tick = internalMutation({                 // MUTATION, not action: exactly-once
  args: {},
  handler: async (ctx) => {
    for (const period of await dueUnclaimedPeriods(ctx)) {
      await ctx.db.patch(period._id, { status: "claimed", claimedAt: Date.now() });
      // Scheduling from a mutation is ATOMIC with it — if the patch rolls back, nothing is scheduled.
      await ctx.scheduler.runAfter(0, internal.billingRollup.postInvoice, { periodId: period._id });
    }
  },
});
```

### 4. Honest tax posture (pure, both halves required)

```ts
// packages/billing/src/tax.ts
export const NONTAXABLE_TAX_CODE = "txcd_00000000";

export type TaxPosture =
  | { state: "not-owed"; because: "unregistered" }        // not_collecting + a REAL product code
  | { state: "not-owed"; because: "declared-nontaxable" } // not_collecting + txcd_00000000
  | { state: "calculated-zero"; reason: string }          // zero_rated | not_subject_to_tax | ...
  | { state: "collected"; minor: number };

/** `not_collecting` is AMBIGUOUS per Stripe's own docs — the product tax code is the second half. */
export function taxPosture(reason: string, productTaxCode: string, taxMinor: number): TaxPosture {
  if (taxMinor > 0) return { state: "collected", minor: taxMinor };
  if (reason === "not_collecting") {
    return productTaxCode === NONTAXABLE_TAX_CODE
      ? { state: "not-owed", because: "declared-nontaxable" }
      : { state: "not-owed", because: "unregistered" };
  }
  return { state: "calculated-zero", reason };  // zero_rated, not_subject_to_tax, reverse_charge, ...
}
```
