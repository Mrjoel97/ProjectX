# Phase 28.1 Plan 11: The Adversarial-Audit Fix Wave — Summary

## What this plan was for

A 10-agent adversarial audit over waves 1–7 produced 37 candidates, 27 survived batch skepticism,
and 15 were distinct confirmed defects (`.planning/audits/28.1-billing-audit-2026-08-30.md`). The
owner chose to fix all 15 as one wave before 28.1-10 and the phase seal, so that 28.1-08 seals a
subsystem rather than an audit.

**Nine of the fifteen were behavioural. Four were guards that could not fail.** The second group is
the more expensive kind: every one of them read as coverage in a diff and in a review.

**Two tests are honestly marked "mutation" rather than "RED".** For #2 and one arm of #9 the code
path the assertion covers was *unreachable* on the unfixed tree, so a new test passed vacuously
rather than failing. Disabling `statusIsFresh` reddens the ordering test; dropping
`customer.subscription.created` from `ONE_SHOT_EVENT_TYPES` reddens the suppression test. A test
that passes before the fix is not evidence unless something can make it fail.

## The three things worth carrying forward

**1. The root cause of #1, #6 and #7 is one sentence.** A correlation was built from an entity that
REPEATS (a customer, an invoice, a charge) instead of from the movement that is UNIQUE (a
transaction id, a refund id, a credit-note id). `billingLedger.ts:142` answers a second movement on
an existing `(tenant, correlation, phase)` identity by returning the first row and discarding the
amount — which is correct replay behaviour, and is exactly what turned three correlation choices
into silent money loss. The ledger did not need changing. The correlations did.

**2. Duplication is what made #10 possible, so the fix was deduplication.** The stripper had been
diagnosed and repaired once already, in 28.1-07 — in two of the three files that ran it. There is
now ONE copy, in `packages/backend/__fixtures__/sourceScan.ts`, with both failure modes written into
its header and `nonBlankLines` exported beside it. The playbook's "How to change safely" now says to
import it, and names the one remaining private copy (`spendLedger.test.ts`).

**3. Two existing rollup tests had to be REWRITTEN, and that was the real work of #3.** One asserted
`expect(row?.stripeInvoiceId).toBeUndefined()` after a failed finalize — the assertion *was* the
bug, written down and defended. The other promised "a transient failure costs a day, not a period"
while stubbing a failure at the finalize step, i.e. after the invoice already existed at Stripe. The
retry promise now fails at the DRAFT post, which is the case it is genuinely about; a failure after
the draft exists is deliberately not retried, with the reason written at both sites. Deleting the
two tests would have thrown away real intent.

## What is NOT proven

**Nothing here has spoken to Stripe.** No `BILLING_STRIPE_*` variable is set in any deployment. Every
fix above is proven against fabricated payloads and a stubbed `fetch` at $0. In particular #4's
`payment_method_types[0]=card` probe is read from Stripe's documentation for the pinned API version
`2026-08-26.dahlia`, not from a response; and #8's premise — that `cash_balance.funds_available`
fires with a zero balance when a hold clears — is Stripe's documented behaviour and has never been
observed. The playbook records the fallback if it turns out not to fire at zero: clear the row on
`applied_to_payment` for that customer and currency.

**BILL-04 is still not claimed.** Nothing writes a `billingPeriods` row; that is 28.1-10.
