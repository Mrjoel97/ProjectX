    - A NON-owner calling `raiseAdjustment` is refused and **writes nothing** — assert the period
      row is absent/unchanged, not merely that it threw
    - An owner raising a charge against a tenant with no period row CREATES the row at
      `status: "pending"`, with the window and `dueAt` derived the same way `tick` expects
    - A second charge in the same period APPENDS — one row, two charges
    - **The same `ref` twice adds ONE charge.** Assert `charges.length === 1` after two calls
    - **A period at `claimed`, `posted` or `failed` REFUSES the charge**, and the stored charges are
      byte-identical afterwards. Test all three statuses separately — an invoice already sent cannot
      grow, and a charge landing on a `claimed` period would silently ride onto a retry
    - `amountMinor` must be a positive integer: `0`, a negative, a float and a non-finite are each
      refused, and each writes nothing
    - A non-ref-safe `ref` is refused (it is half an HTTP header value)
    - **PROVENANCE: the stored charge records the OWNER's identity as the author**, taken from
      `ctx` — assert that an `actor`/`raisedBy` field on the row equals the authenticated owner and
      is NOT read from any argument. Pass a conflicting value in the args if the signature allows it
      and assert the STORED row ignores it
    - An audit row is written, refs/ids/counts only (CLAUDE.md §4): no free-text description, no
      amount prose. The amount itself is a number and may be recorded; a human note must not be
    - After a charge is raised, `tick` at `dueAt` claims the period — the rollup has a real input
  </behavior>
  <action>
Add `raiseAdjustment` to `billingRollup.ts` as an **`ownerMutation`** (CLAUDE.md §2 — never
`tenantMutation`, and never raw `mutation`). A tenant must not be able to bill themselves, and a
tenant must not be able to bill anyone else.

**Provenance is the sharp edge here and this repo has paid for it before.** A money figure that a
model or a request body can author, stored in a row that later renders as the owner's own charge, is
the recorded `provenance-laundering` defect class. The author identity must come from `ctx`
(`requireOwner` already resolved it) and MUST NOT be accepted as an argument. If the shape makes it
possible to pass one, ignore it and prove that with a test.

**Refuse on a non-`pending` period rather than creating a second period.** Silently opening a new
period for a late charge would split one month across two invoices; the honest answer is a refusal
the caller can see.

Keep `kind` hard-coded to `"adjustment"` at this call site. Do not accept it as a parameter — a
parameter is how `"usage"` gets written by accident, and the whole point is that it stays unwritten.

`ponytail:` no admin UI. This is a backend surface the owner reaches through the Convex dashboard or
a script. Name that ceiling in a comment with the upgrade path.
