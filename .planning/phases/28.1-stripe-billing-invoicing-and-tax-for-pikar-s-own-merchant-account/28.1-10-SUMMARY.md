# Phase 28.1 Plan 10: `raiseAdjustment` — the Rollup Finally Has an Input — Summary

## What this plan was for

28.1-07 shipped a correct, bounded, 28-mutation-proven invoice rollup **with no input**. Nothing in
the deployment inserted a `billingPeriods` row, so the daily cron ran, found nothing due, and did
nothing — for every tenant, forever. Every period in every test was seeded by hand.

The owner's decision (2026-08-30) was to give it exactly ONE writer: **owner-raised adjustments** — a
one-off charge the owner types, for a setup fee, custom work or a correction. That invents no
pricing model, uses the `adjustment` kind already in the closed union, and leaves usage-derived
billing deferred exactly where the phase put it.

## What landed

`raiseAdjustment`, an `ownerMutation` in `billingRollup.ts`, plus `raisedBy` on every charge and a
`PostedCharge` type that keeps it out of the Stripe-facing half.

**Provenance is the sharp edge, and this repo has paid for it before.** The author identity comes
from `ctx` — `requireOwner` has already resolved it — and there is no parameter that could override
it. A conflicting `raisedBy` in the request body is rejected outright by Convex's validator, and the
test asserts that AND that the stored row carries the authenticated owner rather than the billed
tenant.

**Every refusal is at the door, not at the invoice**: a non-`pending` period, a non-positive amount,
an unsafe `ref`, a non-ref-safe tenant, a second currency, one line over the cap. A charge that
`prepareInvoice` would later reject would otherwise turn a period into one that can only fail, with
nobody watching.

One end-to-end offline test now walks **owner-charge → `tick` claims → `postInvoice` → `settlePeriod`**
through the real scheduled hop, asserting that both raised amounts reach Stripe on their own lines,
that the draft carries `pending_invoice_items_behavior=exclude`, and that no Pikar user id appears in
any request body. This is the test 28.1-07 could not write.

## The mutation round, and why it is the most useful part of this plan

**8 mutations, 8 killed — but only after two corrections.**

**1. The harness lied, and it lied in the safe-looking direction.** It wrote each mutant with
`io.open(path,'w').write(...)` and never closed the handle, so on three of eight mutants the bytes
were still in a Python buffer when vitest read the file. It ran unmutated code, saw 70/70, and
reported **SURVIVED**. Survivors read as "your test is weak", so the failure mode was three false
accusations rather than three false clean bills — luck, not design. Had it instead failed to
*restore*, it would have reported KILLED for a mutant that was never applied: a clean bill on a guard
that does not exist. The replacement `fsync`s and reads the file back before running anything.

**2. Then one mutant survived for real, and it mattered.** Deleting the currency guard left this
green:

```ts
await expect(raise(as, { currency: "XYZZY" })).rejects.toThrow();
```

because `normalizeCurrency`'s failed `Result` has no `.value`, so the insert carried
`currency: undefined` and the **schema** rejected it. The refusal was real; the test was measuring
something else. The day someone writes `currency.ok ? currency.value : args.currency`, an
unnormalised currency reaches Stripe under a fully green suite. All three guard tests now pin their
own message.

## What is NOT closed

- **There is no automatic producer.** No subscription renewal, no usage meter and no cron opens a
  period. That is a decision, not an omission: recurring subscription revenue is collected by Stripe
  on the subscription rail (28.1-04's hosted Checkout), which never touches `billingPeriods`.
- **`kind: "usage"` stays in the union and stays unwritten**, and the source assertion keeps it that
  way. The day metered events go to Stripe, the Customer Portal can no longer manage those
  subscriptions — a migration, not a flag flip.
- **Nothing has spoken to Stripe.** The end-to-end proof is against a stubbed `fetch` at $0.

`requirements-completed: []` — BILL-04's mechanism now has an input, but no invoice has ever been
posted to Stripe, so the requirement stays PENDING.
