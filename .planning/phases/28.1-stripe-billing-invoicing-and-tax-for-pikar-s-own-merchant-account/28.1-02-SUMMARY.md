# Phase 28.1 Plan 02: The Code-Owned Stripe Dashboard Mirror — Summary

## What this plan was for

Seven Stripe settings are **Dashboard-only** by locked decision — no API surface is being built to
manage them. That makes the Dashboard the source of truth and leaves the codebase blind to it. This
plan builds the mirror: `packages/billing/src/config.ts` is the one place the rest of the repo can
*see* what was configured, and `docs/billing/stripe-dashboard-setup.md` is the human half. The two
are independent recordings of the same facts, so **diffing them is the drift detector**.

## What landed

Five of the six recorded values are now real, each backed by an object or a document rather than an
assumption:

| Constant | Value | Where it came from |
| --- | --- | --- |
| `PRODUCT_TAX_CODE` | `txcd_10105002` | Stripe's own tax-code list, set on the product via API |
| `STRIPE_API_VERSION` | `2026-08-26.dahlia` | Stripe's versioning doc; pinned by us |
| `TRIAL_DAYS` | `14` | `recurring.trial_period_days` on the price |
| `BANK_TRANSFER_ENABLED` | `true` | reported by the account owner |
| `NONTAXABLE_TAX_CODE` | `txcd_00000000` | the value we must never select |
| `HEAD_OFFICE_COUNTRY` | `null` | **does not exist yet** — see below |

Plus real test-mode Stripe objects, created through the API on `acct_1U9DJHV05ajSTq7I`:

- product `prod_VA8pHxqMVhfHZ3` ("Pikar AI", tax code `txcd_10105002`)
- price `price_1U9oXpV05ajSTq7I4Z4U1se9` — USD 4900 minor units / month, 14-day trial,
  `tax_behavior: exclusive`, set as the product's `default_price`

**The price AMOUNT is a placeholder.** Pricing was never decided. It carries the Stripe metadata tag
`pikar_placeholder_amount: "true"` so it cannot later be mistaken for a decision.

## Why this plan is PARTIAL and not CLOSED

`CONFIG_CONFIRMED` is still `false`, and `HEAD_OFFICE_COUNTRY` is the **only** reason.

This is not an unanswered question — it is a fact that does not exist yet. The business is not
registered, so there is no head office to record. Inventing a country to make the flag flip would
be the exact failure the flag exists to prevent: `CONFIG_CONFIRMED` asserts *completeness*, and
completeness is genuinely not true.

The value is load-bearing twice over, which is why it cannot be guessed:

1. Threshold monitoring **EXCLUDES** the home jurisdiction — the origin address is what leaves it
   out, not just what brings others in.
2. Bank-transfer eligibility is country-dependent.

**Close this plan when registration completes**: set the origin address in Tax → Settings, record
the country in both `config.ts` and the As-configured table, and flip the flag.

## Deviations from the plan

**1. `packages/backend/convex/lib/env.ts` was in `files_modified` and was NOT touched.**
`env.test.ts` is *bidirectional*: it fails on an `ENV_MANIFEST` row that no source file literally
reads, not only on a read with no row. A name nothing reads is treated as removed, not as carried.
So `BILLING_STRIPE_SECRET_KEY` and `BILLING_STRIPE_PRICE_ID` cannot be classified here — each row
must land **in the same commit as its first literal read**, which is 28.1-04.
`BILLING_STRIPE_WEBHOOK_SECRET` is already classified because 28.1-01 reads it.

**2. The product and price were created via the Stripe API, not by the owner in the Dashboard.**
The plan assumed a human would do it. The API path is faster, exact, and leaves the ids in the tool
transcript. The setup doc's steps 3, 4 and 6 are now marked **DONE** so a later reader does not
create a second product and split the catalogue in half.

**3. `PRODUCT_TAX_CODE` is not the code research proposed.** Research suggested `txcd_10103001`
(generic SaaS) at explicitly LOW confidence. Reading Stripe's actual list surfaced `txcd_10105002` —
*"Artificial Intelligence as a Service (AIaaS) - Cloud Based - Business Use"*, described as *access
to cloud-hosted artificial intelligence platforms for commercial, professional, or organizational
purposes*. That is Pikar exactly. The plan was right to record the RULE (never `txcd_00000000`) as
certain and the id as a suggestion.

**4. NO webhook endpoint was registered — deliberately.** `CONVEX_SITE_URL` is
`http://127.0.0.1:3211`, a local deployment Stripe cannot reach. Registering one would fail every
delivery, be auto-disabled by Stripe, and leave an object in the account that *looks* configured —
worse than none. The Stripe CLI (v1.40.2) is installed but not authenticated; `stripe login` then
`stripe listen --forward-to localhost:3211/billing/stripe/webhook` is the local path and prints its
own session `whsec_`. Nothing is blocked: 28.1-01 already proves signature verification offline.

**5. `config.test.ts`'s completeness guard was widened from all-or-nothing to per-field.** As
written it demanded all five values be `null` *or* all five be set, so the owner answering exactly
one question read as red. The intent it protected — *a value is format-checked the moment it lands*
— is unchanged and is what the per-field guards now enforce. "Landing together" was never the
hazard; landing unchecked was.

## What this plan does NOT prove

Nothing here has spoken to Stripe on a *billing* path. No Checkout session has been created, no
invoice issued, no webhook delivered. The objects exist; the code that would use them is 28.1-04
onward. A green `config.test.ts` proves the constants are well-formed and mutually consistent — not
that Stripe would accept a single request built from them.

## Still owner-only

Branding, Customer Portal and Smart Retries (no API surface in the tooling available here), and the
three `npx convex env set` calls (secrets only the owner holds). None block the code — every plan in
this phase is provable offline against a stubbed `fetch`. They block live traffic, which is a later
gate.
