<objective>
Programmatic invoicing on our own schedule, with a claim row that survives what Stripe's idempotency
key cannot.

Purpose: BILL-04. Stripe has no built-in recurrence for standalone invoices, so the schedule is ours
— and Convex's scheduling guarantees make the obvious shape wrong.
Output: `billingPeriods`, `convex/billingRollup.ts`, one new cron.

**The trap this plan exists to avoid:** a cron pointing straight at an `internalAction` that POSTs an
invoice can silently drop a whole billing period. Convex **actions are at-most-once and are NOT
auto-retried** (mutations are exactly-once), and a cron run is **skipped** if the previous run is
still executing. No retry, no error surface, no invoice.
</objective>

<interfaces>
Convex scheduling guarantees — these dictate the shape, not a preference:
| Mechanism | Guarantee |
|---|---|
| `crons.daily/interval` | At most one run of each job at any moment; an overlapping run is SKIPPED |
| `scheduler.runAfter` FROM A MUTATION | ATOMIC with the mutation — mutation fails, nothing is scheduled |
| `scheduler.runAfter` FROM AN ACTION | NOT atomic |
| Scheduled MUTATIONS | executed EXACTLY ONCE; internal errors auto-retried |
| Scheduled ACTIONS | executed AT MOST ONCE; **not** auto-retried; permanently fail on a transient error |

From packages/backend/convex/crons.ts — the existing registrations and the house style:
```ts
const crons = cronJobs();
crons.daily("worm-export", { hourUTC: 3, minuteUTC: 0 }, internal.worm.exportAudit, {});
crons.interval("reliability-sweep", { minutes: 30 }, internal.reliabilitySweep.runSweep, {});
export default crons;
```
`reliabilitySweep` (every 30 min) exists precisely to find a severed scheduler chain — a
non-terminal state that outlives its threshold. Reuse it; do not build a second watchdog.

`convex/billingRollup.ts`:

```ts
export const tick = internalMutation({ args: {}, handler: async (ctx) => {
  for (const period of await dueUnclaimedPeriods(ctx)) {
    await ctx.db.patch(period._id, { status: "claimed", claimedAt: Date.now(), attempts: period.attempts + 1 });
    await ctx.scheduler.runAfter(0, internal.billingRollup.postInvoice, { periodId: period._id });
  }
}});
```

`tick` is a **mutation, not an action** — that is the whole design. Scheduled mutations are
exactly-once and auto-retried on internal errors; scheduling from a mutation is atomic with it, so
if the claim patch rolls back nothing is scheduled. The claim is read-then-patch under OCC, the same
law as `spendLedger.recordMovement`: a concurrent second tick is re-run by Convex, finds the row
claimed, and no-ops.

Bound the claim scan — `dueUnclaimedPeriods` uses `by_status_dueAt` with a page limit, never a full
scan.

Register in `crons.ts`, matching the house style and comment density:
`crons.daily("billing-invoice-rollup", { hourUTC: 7, minuteUTC: 0 }, internal.billingRollup.tick, {});`
with a comment naming the reason it points at a mutation.

  <behavior>
    Against a stubbed `fetch` that captures every Request:
    - `postInvoice` POSTs `/v1/invoiceitems` for each accumulated charge with an explicit `period`,
      then ONE `/v1/invoices` with `auto_advance=true` and `collection_method=charge_automatically`
    - Every one of those POSTs carries an `Idempotency-Key`; the invoice key is exactly
      `billing-invoice:{tenantId}:{periodKey}`
    - The SAME period posted twice sends the SAME key AND the same body — Stripe errors when a key
      is replayed with different parameters, so key and body must derive from the same inputs.
      Assert both together.
    - On success, `settlePeriod` (a mutation) records `stripeInvoiceId`, `hostedInvoiceUrl`,
      `status: "posted"`. Assert the period cannot be posted again afterwards.
    - On a Stripe failure, the period goes to `failed` with the attempt count incremented and NO
      invoice id — and it is re-claimable, so a transient failure does not lose the period
    - **The 24-hour hole is asserted:** a period re-posted more than 24h later with the same key must
      still be refused by OUR period row, because Stripe prunes idempotency keys after ~24h and then
      generates a NEW request. Simulate by clearing the fetch stub's key memory and asserting the
      claim row — not the header — is what refuses.
    - The rollup is bounded by the period: only invoice items belonging to the claimed period are
      created. Assert that a pending item outside the period window is not included.
  </behavior>
  <action>
Add `postInvoice` (an `internalAction`) and `settlePeriod` (an `internalMutation`) to
`billingRollup.ts`.

Accumulate charges with `POST /v1/invoiceitems` through the period, then roll them into ONE invoice
with `POST /v1/invoices`, `auto_advance: true` against the saved payment method. One clean document,
not a fragmented bill (locked decision).

**Bound the window explicitly.** `POST /v1/invoices` pulls ALL pending invoice items for a customer.
Create and filter items with an explicit `period` and only roll customers whose period row is
claimed — never "whatever is pending". This is the difference between one correct invoice and a bill
that swallows next month.

Write the idempotency contract as a comment where the key is built: **the Stripe key covers a
same-day retry only.** Stripe removes keys once they are ~24h old and generates a new request if one
is reused after pruning, so a rollup retried a day later would mint a SECOND invoice and double-bill
the customer. The durable guard is the `billingPeriods` row; the header is the inner belt.

If an outbound POST needs to survive a transient failure, use the already-pinned
`@convex-dev/action-retrier` (0.3.1) rather than a hand-rolled loop — and note that this is exactly
why the deterministic key is mandatory. Do not add a new dependency.

`settlePeriod` must be a separate mutation because the action is not transactional: the action posts,
the mutation records. A period claimed but never settled past its threshold is found by the next
`tick` (Task 1) — and `reliabilitySweep` (`crons.ts`, every 30 min) is the repo's existing answer to
a severed scheduler chain. Do not build a second watchdog.
