# Phase 28.1 Plan 03: Pure Tax Posture and Stripe-Event-to-Ledger-Phase Mapping Summary

Two pure modules that encode the phase's two sharpest laws — a zero on a tax line carries WHICH
kind of zero it is, and `invoice.paid` on a bank transfer is not money in hand — proven by 66 new
offline tests at $0 and 15 rename/boundary mutations.

## What shipped

**`packages/billing/src/tax.ts` (BILL-05).** `taxPosture(reason, productTaxCode, taxMinor)` returns
one of four states. Stripe's `not_collecting` is ambiguous by its own documentation — it means
EITHER "no active registration in the customer's jurisdiction" OR "this product carries the
Nontaxable code `txcd_00000000`" — and the product's own tax code is the only disambiguator, which
is why the function takes two arguments and structurally cannot be written with one. Every other
published `taxability_reason` with a zero amount is `calculated-zero`: a real calculation ran, which
is a different claim and never renders the same sentence. `renderTaxPosture` exists because BILL-05's
promise is about what a human READS: **no zero arm emits an amount at all**, so a bare `0.00` is
unreachable rather than discouraged.

**`packages/billing/src/reconcile.ts` (BILL-03).** `reconcileEvent(event, nowMs)` maps one Stripe
event to `{ movements, observations }`, wrapped in a `Result`. The mapping:

| Stripe signal | outcome |
| --- | --- |
| `invoice.finalized` | `estimated`, correlated on the invoice id |
| `invoice.paid` — CARD | `actual` |
| `invoice.paid` — bank transfer | **no movement**, one `awaiting-cash-application` observation |
| `invoice.paid` — method undeterminable | **no movement**, one `payment-method-undetermined` observation |
| cash-balance `funded` | `reserved` (arrival, not collection) |
| cash-balance `applied_to_payment` | `actual` (the ONLY collection signal on this rail) |
| cash-balance `funding_reversed` / `unapplied_from_payment` / `refunded_from_payment` | `refunded` |
| `cash_balance.funds_available` | **zero movements**, one `unapplied-funds` observation with an age |
| `charge.refunded` / `credit_note.created` | `refunded`, positive |
| `invoice.payment_failed` and everything else | nothing, never a throw |

## Key decisions

**`taxPosture` takes the product tax code as an argument.** `PRODUCT_TAX_CODE` is still `null` (the
owner deferred it) and reading it inside would make the function impure, untestable at a boundary,
and unable to re-derive a historical invoice's posture from the code configured *then*.

**`not_collecting` + a `null` product code is `unknown`, not `unregistered`.** This is the honest
third branch the plan's example shape did not have. Guessing "unregistered" would assert a
registration gap we have no evidence for. Missing history is unknown, never zero — `CashFigure`'s
discipline, borrowed without borrowing the type (`cash.ts` is USD dollars about the TENANT's
business and must never carry Pikar's billing cents).

**`invoice.paid` fails closed on an UNDETERMINABLE method too, not only on bank transfer.**
`payment_settings.payment_method_types` is what was ALLOWED, not what was USED, so an invoice that
merely permitted `customer_balance` cannot prove a card paid it. Three tiers, most specific first:
the charge's actual `payment_method_details.type`, then an expanded PaymentIntent's types, then the
invoice's allow-list. Empty or containing `customer_balance` ⇒ no `actual`. This is a Rule 2
addition — "unknown is never card" is a correctness requirement, not a feature.

**`reconcileEvent` returns `Result`.** An amount that cannot be turned into money is an error. A
ledger that writes a zero because it could not read a number is worse than one that refuses. A raw
amount of `0` is different: nothing moved, so no movement and no error.

**`tax.ts` imports `NONTAXABLE_TAX_CODE`, it does not re-export it.** The plan's artifact contract
listed it among `tax.ts`'s exports, but `index.ts` uses `export *` from both `./config` and
`./tax` — two star-exports of one name make it ambiguous and silently absent. Importing is also
ponytail rung 2: it already exists one file over.

## Deviations from Plan

### Auto-fixed / adjusted

**1. [Rule 2 - missing critical correctness] `invoice.paid` with an undeterminable payment method**
- **Found during:** Task 2
- **Issue:** The plan specified card ⇒ `actual` and bank transfer ⇒ no `actual`, but said nothing
  about an invoice whose method cannot be resolved. Defaulting such an invoice to "card" would book
  `actual` on exactly the case we know least about.
- **Fix:** Both guards fail closed, and they are mutation-proven INDEPENDENTLY (disabling one kills
  3 tests, disabling the other kills exactly 1 — neither absorbs the other).
- **Commit:** `c601223`

**2. [Rule 3 - blocking] `NONTAXABLE_TAX_CODE` re-export would have been a silent star-export collision**
- **Fix:** imported, not re-exported. Documented above.
- **Commit:** `2eb10b0`

**3. [Rule 1 - would-be defect] the literal `tax.threshold` was written in a `tax.ts` comment**
- **Issue:** The plan's own verification is a bare `grep -rn "tax.threshold" packages/ apps/`
  returning nothing, and a mention in a comment is indistinguishable from a use by grep — the same
  reasoning `index.ts` already applies to the reserved Phase 28 names.
- **Fix:** the fact is stated without the literal. `git grep` over `packages`/`apps` is empty.
- **Commit:** `2eb10b0`

**4. Formatting-only follow-up commit.** Biome reformatted three of the four new files. Committed
separately as `style(28.1-03)` rather than amending, so the RED/GREEN history stays truthful.

### Not deviations, but worth recording

- `renderTaxPosture` takes a `currency` second argument (the plan wrote it as one-arg). Only the
  `collected` arm uses it, via `moneyFromMinor` + `formatMoneyAmount`; rendering a collected amount
  without a currency would have meant either a bare number or a fabricated symbol.
- `funded` correlates on the CUSTOMER id, not a PaymentIntent — a `funded` transaction has no
  PaymentIntent yet, by definition.

## Honest limits

- **Nothing calls either function.** `receiveAndApply`'s effect switch is still empty; no movement
  has ever reached a table. The `billingEvents` book of record is 28.1-06. A green
  `reconcile.test.ts` proves the LAW, not that any money was ever reconciled.
- **Nothing has spoken to Stripe.** Every event object in these tests is fabricated. A handler
  cannot tell a fabricated `customer_cash_balance_transaction` from a real one, which is exactly why
  this was provable at $0 — and exactly why it is not evidence that Stripe sends these shapes.
- **`PRODUCT_TAX_CODE` is still `null`.** So today the live config drives `taxPosture` into the
  `unknown` arm on `not_collecting`, which is the correct and intended answer. BILL-05 is not
  complete until the owner reports a real code.
- **No requirement is marked complete.** BILL-03 also needs 28.1-06's ledger wiring; BILL-05 also
  needs the owner's product tax code. `requirements mark-complete` was deliberately NOT run.
