# Phase 28.1 Plan 04: Outbound Stripe Transport and the Two Hosted Doors Summary

One form-encoded transport to Pikar's own Stripe account with a pinned `Stripe-Version` and a
REQUIRED `Idempotency-Key`, plus the only two tenant-facing billing surfaces the locked decisions
allow — hosted Checkout and the Customer Portal — proven by 42 new offline tests at $0 and 31
mutations. **No request has ever been sent to Stripe.**

## What shipped

**`packages/backend/convex/billingApi.ts` (BILL-02).** `stripePost(path, params, { idempotencyKey })`
and `stripeGet(path, query?)`. Plain `fetch` against `STRIPE_API_BASE`, form-encoded with a
key-SORTED encoder so the body is a pure function of the parameter set rather than of the order the
caller wrote them in — Stripe errors when one key is replayed with different parameters, so
"same inputs ⇒ same body" has to hold byte-for-byte. Four headers on a POST (`Authorization`,
`Content-Type`, `Stripe-Version`, `Idempotency-Key`); three on a GET, because Stripe honours the key
on POST only and sending one on a GET is a silent no-op that reads like a guarantee.

Three refusals fire before `fetch`, and each was disabled independently and killed a DISJOINT set of
tests:

| Refusal | Why it is a refusal and not a fallback |
| --- | --- |
| `BILLING_STRIPE_SECRET_KEY` unset or blank | `p25-no-dev-fallback`. A fallback key charges a real card from a misconfigured deployment |
| `STRIPE_API_VERSION` null | An unpinned request still SUCCEEDS — it silently inherits the Dashboard default, and the version decides whether the invoice tax field is `total_tax_amounts` or `total_taxes`. Sending a payload our parsers may not read is worse than not sending it |
| `idempotencyKey` missing or blank | A required parameter, not an option. Optional-with-a-default is how it gets forgotten |

A Stripe failure is `{ kind, status, code, requestId }` and nothing else. `error.message`,
`error.param`, `request_log_url` and any non-JSON body are dropped inside `send()`; `error.code` is
accepted only if it matches `^[a-z0-9_]{1,64}$` and `Request-Id` only if it matches
`^req_[A-Za-z0-9]{1,64}$`, so neither field is a route for prose to reach an audit row or a log
(CLAUDE.md §4). `timeout` is kept distinct from `network` because they differ operationally: a
timeout already spent the whole budget.

**`packages/backend/convex/billing.ts` (BILL-01).** `startCheckout` and `portalLink` are
`tenantAction`s; `billingStatus` is a `tenantQuery` (CLAUDE.md §2 — no raw `_generated/server`
import anywhere). The checkout body:

```
mode=subscription
line_items[0][price]=<BILLING_STRIPE_PRICE_ID>   line_items[0][quantity]=1
subscription_data[trial_period_days]=14          payment_method_collection=always
client_reference_id=<tenantId>                   metadata[tenantId]=<tenantId>
success_url=<SITE_URL>/dashboard/settings?checkout=success
cancel_url=<SITE_URL>/dashboard/settings?checkout=cancel
```

keyed `checkout:<tenantId>:<priceId>:<UTC day>`. `payment_method_collection=always` is what makes
this a trial rather than freemium. `client_reference_id` is the load-bearing field: it is the ONLY
thread 28.1-05's `checkout.session.completed` handler has back to a tenant, and it is asserted
across TWO tenants on ONE backend so a hardcoded value cannot pass.

Only `{ ok: true, url }` reaches the caller, and only after `hostedUrl()` confirms the url is
`https:` on a `*.stripe.com` host — the caller redirects a browser to it, so an unvalidated `url`
field is an open redirect sourced from a Stripe response. The session's `customer`,
`customer_details.email`, name and amount are dropped at this boundary, not at the UI.

`portalLink` resolves the tenant's `stripeCustomerId`, which is `null` for every tenant until
28.1-05 lands the mapping, and returns `{ ok: false, reason: "no_stripe_customer" }`. It never
creates a customer to make itself work.

**Two `ENV_MANIFEST` rows.** `BILLING_STRIPE_SECRET_KEY` landed in the same commit as
`billingApi.ts`, `BILLING_STRIPE_PRICE_ID` in the same commit as `billing.ts`. `env.test.ts` is
bidirectional — a row nothing reads is as red as a read nobody classified — so neither could have
landed in 28.1-02, and both use a LITERAL `process.env.X` because a computed `process.env[name]` is
invisible to that scan (the blindness that let `CONNECTOR_CREDENTIAL_KEY_V1/_V2` escape entirely).

## Key decisions

**A null `STRIPE_API_VERSION` refuses like an unset secret.** This was a correction to the plan, and
it is the least obvious guard in the file. An unpinned request works; it just quietly inherits the
account default. Because that default decides the payload SHAPE, shipping the request is worse than
refusing it. Proven through a real re-import of the module under `vi.doMock("@pikar/billing/config")`
rather than through an exported validator taking the version as an argument — what has to be proven
is that the SHIPPED path consults the pin, not that some helper would have rejected null if called.

**Config refusals throw; upstream failures return `Result`.** A missing secret, an unpinned version,
an unset price id and an unset `SITE_URL` are deployment bugs and are loud. A Stripe 4xx, a network
error and a timeout are facts about the world and are data. `portalLink`'s "no customer" is also
data, not a bug — it is a legitimate state for every tenant today.

**`SITE_URL` has no `?? "http://localhost:3111"` fallback**, unlike the two older routes in
`http.ts`. A checkout whose `success_url` points at a dead origin takes the money and strands the
buyer. Not in the plan; added as deviation Rule 2.

**The portal idempotency window is 60s, not the checkout's day.** A Customer Portal `url` is
single-use and short-lived. Replaying a day-old key hands the user back a link that has already been
spent — worse than minting a second session. The two windows are deliberately different and the
constant is asserted as a written-out literal.

**`billingStatus` returns `unknown`.** Not `not_subscribed`, not `0`, not "free tier". There is no
row to read for anyone until 28.1-05. The `not_subscribed` / `subscribed` arms of the returns
validator are the contract 28.1-05 fills; they are UNREACHABLE today and no test pretends otherwise.

**`portalSession` is exported so the transport arm is tested rather than dead.** `portalLink` cannot
reach its POST until 28.1-05, and an untested arm behind a green suite is a gap this repo has paid
for. The test drives `portalSession` directly for the request shape and `portalLink` for the refusal.

**No `automatic_tax`.** Stripe Tax calculates nothing without a registration and there is none, so
enabling it would produce `not_collecting` on every line — which `taxPosture` (28.1-03) already
models. Turning it on is a deliberate later edit paired with a sandbox registration.

## Deviations from Plan

### The plan's `<interfaces>` block was wrong about `config.ts`

It quoted `export const BILLING_STRIPE_PRICE_ID_ENV = "BILLING_STRIPE_PRICE_ID"` and
`STRIPE_API_VERSION: string` / `TRIAL_DAYS: number`. **`BILLING_STRIPE_PRICE_ID_ENV` does not exist**,
and the two real constants are `string | null` and `number | null`. Neither was cast or `!`-asserted;
each got a refusal and a test instead. Corrected from the real file before writing any code.

### Auto-fixed and added (Rules 1–3)

**1. [Rule 2 — missing critical functionality] `SITE_URL` refusal.** Not in the plan. Without it the
only options were a localhost fallback (silent, wrong in production) or a `!`. Test: "an unset
SITE_URL refuses loudly rather than sending a localhost return url". Commit `83fb153`.

**2. [Rule 2 — security] Stripe-host validation on the returned `url`.** Not in the plan. The caller
redirects a browser to whatever comes back. Test: "a `url` that is not a Stripe host is REFUSED".
Commit `83fb153`.

**3. [Rule 2 — security] Shape-checking `error.code` and `Request-Id`.** The plan said the failure
carries "the Stripe `error.code` and `request-id` ONLY". Trusting Stripe's documentation that
`error.code` is an enum token is the exact shape of trust this repo has been bitten by, so both are
regex-gated and anything else becomes `null`. Two dedicated tests. Commit `4379271`.

**4. [Rule 3 — blocking] `npx convex codegen`.** `api.billing` did not exist in
`_generated/api.d.ts`, so `tsc --noEmit` failed with 15 errors while vitest was green. Ran
`npx convex codegen --typecheck disable` (NOT `convex dev`, `deploy` or `run`). The diff is 8 lines:
`billing`, `billingApi`, **and a pre-existing staleness it corrected** — `connectorFetch` was missing
from the generated list entirely and `http` was mis-sorted, both landed by an earlier plan that
hand-edited this file. Incidental, not scope creep. Commit `83fb153`.

**5. [Rule 3 — blocking] Two source scans were catching their own documentation.** The card-data scan
matched `billing.ts` (its header comment says "card data, CVCs, expiry and 3DS" while explaining that
none of it exists) and the read-rail scan matched `billingApi.ts` (whose comment says "NOT
`connectorFetch.ts`"). Fixed the way `env.test.ts` and `importGuard.test.ts` already fix it: strip
comments before scanning, **line comments first** — that ordering is load-bearing.

**6. [Rule 1 — bug in my own test] The two-tenant tests were vacuous-in-the-failing-direction.** Each
called a helper that booted its OWN `convexTest` backend, so both "different" tenants got the same
first `users` id and `expect(a).not.toBe(b)` failed against correct code. Fixed by adding both
tenants to ONE backend, and the tenant-ids are now asserted different in the same test.

## Honest limits

- **Nothing has been sent to Stripe, and nothing can be from here.** No `BILLING_STRIPE_*` variable
  is set in any deployment and `CONVEX_SITE_URL` is `http://127.0.0.1:3211`. Every test stubs
  `fetch`. **A green suite proves the REQUEST, not that Stripe accepts it** — not the price id, not
  the parameter names, not the API version, not the trial behaviour, not the returned url's shape.
  The first live `stripe listen` / `stripe trigger` run is where any of that becomes evidence.
- **`portalLink`'s success path has never run end to end.** Its transport is proven through the
  exported `portalSession`; the wiring from a real `stripeCustomerId` is 28.1-05.
- **`billingStatus`'s two other arms are unreachable** and the returns validator advertises a
  contract the code cannot currently produce. That is deliberate and stated; 28.1-05 fills it.
- **`stripeGet` has no production caller.** Tested, unused.
- **That `startCheckout` passes `TRIAL_DAYS` rather than a hardcoded `14` is proven by a SOURCE
  assertion, not a behavioural one.** While the constant is 14 the two are behaviourally identical,
  so no runtime test can separate them. The source assertion kills the hardcode mutation (N6); it
  would not catch a `TRIAL_DAYS ?? 30`.
- **Nothing stops a tenant subscribing twice.** There is no mapping table to check. The daily key
  stops a double-click, not a second checkout tomorrow. 28.1-05/07.
- **No UI calls either door.** `apps/web` has no `/dashboard/billing`; the return urls point at
  `/dashboard/settings?checkout=…`, a page that exists but ignores the parameter.
- **No requirement is marked complete.** BILL-01 needs 28.1-05's mapping before a subscription
  actually provisions anything; BILL-02's inbound half shipped in 28.1-01 and its outbound half here,
  but neither has been exercised against Stripe. `requirements mark-complete` was deliberately NOT
  run.
- **STATE.md was not updated.** Every `gsd-tools state *` subcommand was withheld per the executing
  instruction (seven recorded STATE.md corruptions). `.planning/ROADMAP.md` was hand-edited instead.
