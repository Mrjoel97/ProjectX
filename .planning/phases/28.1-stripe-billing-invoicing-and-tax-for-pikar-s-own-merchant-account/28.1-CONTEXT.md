<domain>
## Phase Boundary

Pikar charges for **itself**. A tenant subscribes to pikar-ai.com through Stripe-hosted Checkout with
a free trial and a card on file; invoices are issued programmatically and can be paid by card or bank
transfer; tax runs in honest threshold-monitoring mode because no registrations exist. Billing
outcomes reconcile into the **existing append-only ledger, which stays the book of record** — Stripe
is a payment processor, not the source of truth.

### THE BOUNDARY THAT MUST NOT BLUR

Two Stripe integrations now live in this repo, pointing in **opposite directions**:

|  | Phase 28 (plan 28-07) | THIS phase |
| --- | --- | --- |
| Whose account | the **tenant's** | **Pikar's own** |
| Direction | reads in | charges out |
| Capability | `*_read` only, fails closed | write-capable by necessity |
| Names | `convex/stripe*.ts`, `packages/revenue/src/providers/stripe.ts`, `STRIPE_APP_*` | `convex/billing*.ts`, `packages/billing/`, `BILLING_STRIPE_*` |

Owner decision, 2026-08-28: **`billing*` naming**, so the wrong secret cannot reach the wrong code
path. Phase 28's `stripe*` names are RESERVED — do not take them.

### Not in this phase

- Usage-based / metered billing pushed to Stripe. Metering stays **internal** for v1; we bill
  flat-rate. (Recorded below as the trigger that ends Customer Portal.)
- Per-seat and volume-tiered pricing.
- Sales-led quotes, multi-phase contracts, Salesforce. Self-serve only, solo founder.
- Managed Payments — eligibility is country-gated and **unverified** for this merchant; do not assume it.
- Any e-invoicing mandate format (SDI/CFDI/ZUGFeRD/PEPPOL).

<decisions>
## Implementation Decisions

All of the following are **locked** — they are accepted answers from Stripe's implementation planner,
not open questions.

### Checkout and subscription
- **Stripe-hosted Checkout**, redirect flow. Not Elements, not embedded, not Payment Links.
- **Flat-rate plan tiers.** No per-seat, no volume tiers.
- **Free trial with card on file at signup**, auto-converting to paid. This is a trial, not freemium —
  payment details are collected up front.
- **Customer Portal** for upgrade / downgrade / cancel / payment-method update. No custom
  subscription-management UI.
- **Smart Retries + automated emails** for failed-payment recovery. Dashboard configuration, no code.

### Invoicing
- **Invoicing API driven by a Convex scheduled function.** Stripe has no built-in recurrence for
  standalone invoices, so the schedule is ours.
- Accumulate charges with `POST /v1/invoiceitems` through the period; roll into one invoice with
  `POST /v1/invoices` on billing day. One clean document, not a fragmented bill.
- `auto_advance: true` against a saved payment method.
- **Bank transfer enabled**, with the **Hosted Invoice Page** (`invoice.hosted_invoice_url`) served to
  B2B customers who cannot pay by card.
- **No custom 3DS and no card data anywhere in this codebase.** The hosted page handles authentication.
- Invoice **branding** only (logo, colour, footer). No per-segment rendering templates at beta scale.

### Reconciliation
- **Webhook-driven** updates into our own ledger. Not the Stripe Dashboard, not a warehouse, not Sigma.
- Events that matter: `invoice.paid`, `invoice.payment_failed`, `charge.refunded`,
  `credit_note.created`, `checkout.session.completed`,
  `customer.subscription.created|updated|deleted`, and — because we take bank transfer —
  `cash_balance.funds_available` and `customer_cash_balance_transaction.created`.

### Tax
- **Stripe Tax in threshold-monitoring mode, with NO collection.** There are no registrations today,
  so **zero tax is the correct answer** and must be reported as *not owed*, never as *calculated*.
- Must configure: **product tax category** and **head office address**. These are the only two inputs
  monitoring depends on, and getting them wrong is the real silent failure.

### Claude's Discretion
- Table and module layout within `packages/billing` and `convex/billing*.ts`.
- Whether to call Stripe via the official SDK under a Convex `"use node"` action or directly over
  `fetch` (signature verification is available through Web Crypto either way).
- Scheduled-function cadence and how the rollup window is bounded.
- Plan/wave decomposition.

</decisions>

<specifics>
## Specific Ideas

### The four traps, each already cost-bearing

1. **`invoice.paid` is NOT cash in hand.** Bank-transfer funds land in the customer **cash balance**,
   not on the invoice. Stripe auto-applies only when amount AND reference match exactly — partial
   payments, VBAN typos or a missing reference leave funds unapplied. Settlement is 1–5 business days.
   The ledger's `estimated / reserved / actual / refunded` states must **not** record `actual` on
   `invoice.paid` alone for bank transfer.
2. **Usage-based billing is the moment Customer Portal stops working.** The day metered events go to
   Stripe, the Portal can no longer manage those subscriptions and management must move to the
   Subscription Update API. Treat as a migration, not a flag flip. v1 avoids it by keeping metering
   internal.
3. **Convex retries actions AND Stripe retries webhooks.** Idempotency must be *structural*: a
   `stripeEvents` row keyed on `event.id`, inserted **before** side effects, the insert itself being
   the dedupe. Every mutating POST to Stripe needs an idempotency key or a Convex retry mints a
   second invoice.
4. **`convex/tenantDelete.ts` says nothing about billing.** Today it reports only Google/Microsoft
   disconnects. Deleting a tenant would leave a live subscription charging a card. (The same file was
   already flagged in 28-03 for saying nothing about connector grants — this phase owns only the
   billing arm.)

### Repo constraints inherited
- CLAUDE.md §1 pure domain logic in `packages/billing`; `convex/` is a thin adapter.
- §2 tenant-scoped wrappers from `convex/lib/functions.ts`; never raw `_generated/server`.
- §3 audit insert-only. §4 refs / hashes / ids / counts only — a raw Stripe payload must never reach
  audit, telemetry or logs.
- §9 needs `docs/playbooks/billing.md` plus a `watch.json` entry or the Stop hook blocks the turn.
- Money: reuse `packages/revenue/src/money.ts` — integer minor units, explicit currency, `parseMoney`.
  **Stripe is natively minor units; do not double-convert, and never use floats for money.**
- Missing history is **unknown, never zero** — reuse `CashFigure` from `packages/core/src/cash.ts`.
  Phase 26 Finance "never fabricates historical zeroes"; billing must not backfill before an explicit
  coverage start.
- Secrets: `npx convex env set` only. Never Vercel, never `.env`. New names must be classified in
  `ENV_MANIFEST` (`convex/lib/env.ts`) or `env.test.ts` goes red. No development fallback
  (`p25-no-dev-fallback`).

### Known repo hazards that will bite this phase
- A green vitest suite does **not** mean the package typechecks — run `tsc --noEmit` separately. It
  has caught 41 real errors under a green 24-test suite in Phase 28 alone.
- A *filtered* vitest run cannot tell you a sibling file is red. `env.test.ts` was red twice in
  Phase 28 for exactly this reason, both times over unclassified env names — which this phase will
  also add.
- `scripts/check-playbooks.mjs` always exits 0 and blocks forever on bare stdin; read its STDOUT.
- Never run any `gsd-tools state *` subcommand — seven confirmed STATE.md corruptions.
