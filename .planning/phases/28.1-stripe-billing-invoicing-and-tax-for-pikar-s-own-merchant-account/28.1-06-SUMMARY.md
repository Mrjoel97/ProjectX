# Phase 28.1 Plan 06: The Billing Book of Record — Summary

## What this plan was for

**`invoice.paid` is not cash in hand.** `BANK_TRANSFER_ENABLED` is `true` for this merchant, so
bank-transfer funds land in the customer's CASH BALANCE and are collected only when a
`customer_cash_balance_transaction.created` arrives with `type=applied_to_payment`. Booking `actual`
on `invoice.paid` would record money we do not have, in an append-only ledger that cannot quietly
correct it — and `funding_reversed` is what turns that from a theoretical error into a real one.

28.1-03 encoded that law as a pure function and **it had no caller**. This plan is its first one.

## What landed

**Task 1 — `billingEvents`, mirroring `spendLedger`'s law** (`feat(28.1-06): billingEvents …`)

- Three additive tables. `billingEvents` carries the `SPEND_PHASES` union verbatim, a POSITIVE
  integer count of MINOR units, and an EXPLICIT currency — unlike `spendEvents`, which is USD cents
  by construction; Stripe can send any currency and an implicit one is a fabricated one.
- `convex/billingLedger.ts` mirrors `spendLedger.ts` symbol for symbol over a different table.
  Identity is `(tenantId, correlationId, phase)`; a replay returns the stored id and ignores the
  replayed amount; a currency mismatch inside one correlation is REFUSED rather than summed;
  validation runs before coverage is opened so a rejected movement leaves nothing behind.
- Only plain functions — no `internalMutation`/`internalQuery` wrappers, because there is no caller
  for them (YAGNI). `recordBillingMovement` is the plain-function half so the webhook's dedupe row
  and the ledger rows commit or fail together.
- Classification bumped the schema tripwire **52 → 55** with a deliberate, argued row per table.

**Task 2 — the money arms** (`feat(28.1-06): the money arms …`)

- `applyMoney` writes what `reconcileEvent` returns and re-derives nothing. Tenant resolution is the
  `billingCustomers` mapping and nothing else: a money event has no `client_reference_id` thread,
  and guessing one would book a stranger's payment to a tenant permanently.
- The effect switch is now EXHAUSTIVE over `HandledEventType` with a `never` arm.
- `cash_balance.funds_available` RE-OBSERVES rather than re-inserts. A CashBalance object has no
  `id`, so `billingStripeEvents`' by-object dedupe cannot see two notifications as the same thing,
  and a plain insert would report one pile of money three times. The amount moves; `observedAt`
  does not, or every notification would restart a clock that is actually running.
- `invoiceTaxabilityReason` reads `total_taxes[]` against the PINNED `2026-08-26.dahlia`, refuses
  anything outside Stripe's published list, and returns null when entries disagree.

**Task 3 — unapplied funds with their age, and the guard on the ledger decision**
(`feat(28.1-06): unapplied funds with their age …`)

- `billing.unappliedFunds`: bounded (`UNAPPLIED_FUNDS_PAGE_LIMIT` = 100) with an explicit
  `truncated` flag, each row carrying `ageDays` and its `stage` on Stripe's 75/90 clock.
- Coverage is reported separately: `unknown` beside an empty list is a DIFFERENT statement from
  `known` beside an empty list, and a test asserts the two payloads are not equal.
- `unappliedStage` extracted in `reconcile.ts` so the 75/90 boundaries have ONE definition, with
  day-74/75 and day-89/90 asserted directly.

**Task 4 (mutation-driven)** — `test(28.1-06): close the mutation hole …`. See below.

## Deviations from the plan

1. **`reconcileEvent` is called at the HTTP boundary, not inside the mutation.** The plan's
   `key_links` put it in `billingLedger.ts`. Calling it inside `receiveAndApply` requires passing
   the raw Stripe object across the mutation boundary — exactly what CLAUDE.md §4 and 28.1-05's
   `eventFacts` exist to prevent. Its OUTPUT is already a closed, redaction-safe type. The money
   arms still run inside the one transaction, so nothing was lost.
2. **The plan's `REF_SAFE` export from `spend.ts` does not exist.** `spend.ts:42` has a PRIVATE
   `TOKEN`, and `spend.ts` had to show an empty diff. `REF_TOKEN` was exported from `reconcile.ts`
   instead — the pattern that BUILT the values now also validates them, rather than a third copy.
3. **`billingUnapplied` indexes on `by_tenant`, not `by_tenant_observedAt`.** `tenant_owned` puts
   the table on the erasure and export walks, and both hard-code `.withIndex("by_tenant")`
   (`tenantDelete.ts:223`, `tenantExport.ts:108`) — the plan's compound-only index makes the
   classification fail to typecheck. Caught by `tsc`, not by a test.
4. **`isolation.test.ts` needed a written justification for `billingEvents.by_correlation`.** The
   non-tenant-leading-index tripwire fired on the first run, correctly. Same shape and reason as
   `spendEvents.by_correlation`: the tenant check is part of the identity in code.
5. **Two refusal codes the plan did not name** — `billing_undetermined_payment_method` and
   `billing_unreconcilable_event`. Without them, "we could not tell what paid this" and "we could
   not read this amount" are silently indistinguishable from "nothing moved".

## What this plan does NOT prove

- **Nothing in this repo has ever spoken to Stripe.** Every event above is fabricated and
  correctly signed against a fabricated `whsec_test_…`. The handler cannot tell the difference —
  that is what makes the coverage $0 and complete **for the payload SHAPES Stripe documents**. It
  is NOT evidence that Stripe sends those shapes, that `total_taxes[]` is the field on a real
  `2026-08-26.dahlia` invoice, that a real `customer_cash_balance_transaction` carries
  `applied_to_payment.payment_intent`, or that bank transfer is actually enabled on
  `acct_1U9DJHV05ajSTq7I`. **`BILL-03` should be read as "the ledger and the mapping are correct
  for the documented shapes", not as "money has reached the ledger on a real path."**
- **No live delivery has ever arrived**, so every `billingEvents` table on every deployment is
  empty and `unappliedFunds` answers `coverage: "unknown"` for every tenant that exists.
- **No UI renders any of this.** `unappliedFunds` has no caller in `apps/web`; the 75/90 clock is
  visible only to a query nobody calls yet. `taxPosture`/`renderTaxPosture` still have no renderer
  either (28.1-03's gap, unchanged).
- **The 75/90 stage is derived from `observedAt`, which is `event.created` of the delivery**, not
  from Stripe's own view of when the funds arrived. Those should agree; nothing here checks it.
- **A ledger write that throws is a 500 and a Stripe retry.** `recordBillingMovement` throws rather
  than coercing (spendLedger's posture). Every caller today comes through `reconcileEvent`, which
  pre-validates, so a throw means a programming error — but the currency-mismatch guard *could* be
  reached by real cross-currency data, and it would be loud rather than absorbed. Documented in the
  playbook, not mitigated.
- **`CONFIG_CONFIRMED` is still `false`** (`HEAD_OFFICE_COUNTRY` is null — the business is not
  registered), so `taxPosture` on a real `not_collecting` still has an unanswerable half.
- `invoice.payment_failed` is recorded and deliberately books nothing. Dunning is not modelled.
