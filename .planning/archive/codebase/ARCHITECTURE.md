# Architecture

## System shape

- Pikar AI is a pnpm/Turborepo TypeScript monorepo whose product surface is a Next.js application in `apps/web` and whose data, realtime, function, scheduling, and durable-orchestration plane is one Convex deployment in `packages/backend/convex`.
- The main architectural rule in `CLAUDE.md` is “pure domain packages, thin Convex adapters”: reusable decisions and transformations belong in `packages/*/src`, while Convex modules authenticate, validate, persist, schedule, and call external services.
- The web application imports the generated Convex function references through the `@pikar/backend/api` export; `packages/backend/package.json` maps that export to `packages/backend/convex/_generated/api.js`.
- Shared packages use source exports rather than compiled package outputs. Turborepo coordinates `dev`, `build`, `typecheck`, and `test`, but application code consumes the TypeScript under each package’s `src` directory directly.
- The system is deliberately state-centric: humans and agents both mutate the same governed Convex records, and React renders those records through reactive queries. Agents do not drive browser UI.

## Layers and boundaries

- Presentation and browser integration live in `apps/web/app`. Next.js App Router route groups separate public/auth pages under `apps/web/app/(auth)` from the authenticated product shell under `apps/web/app/(app)`.
- The client/server provider boundary is in `apps/web/app/layout.tsx` and `apps/web/app/providers.tsx`: the server provider manages the Convex Auth cookie during SSR, while `ConvexAuthNextjsProvider` supplies authenticated Convex calls in client components.
- `apps/web/middleware.ts` is a default-deny route gate. Only marketing, legal, sign-in, and sign-up routes are public; product routes require Convex Auth before rendering.
- `apps/web/app/(app)/layout.tsx` is the authenticated shell and second gate: it waits for an authenticated client token, enforces first-run onboarding through `api.onboarding.status`, and hosts global notification, Gmail-reconnect, and abnormal-voice-session banners.
- Framework-neutral contracts and prompt seed sources live in `packages/contracts`: Zod/data contracts are under `packages/contracts/src`, while canonical registry prompt bodies are Markdown under `packages/contracts/skills`.
- General business rules and deterministic helpers live in `packages/core/src`, including plan/action types, business profiles, growth diagnostics, document generation, notification copy, review thresholds, retention, and specialist capability definitions.
- Narrow pure-domain packages isolate higher-risk or heavier concerns: `packages/cost/src` prices model/voice usage, `packages/pii/src` redacts text, `packages/extraction/src` classifies intake, `packages/vault/src` recognizes and extracts document formats, and `packages/voice/src` owns Realtime/session/brief rules.
- `packages/backend/convex/lib/functions.ts` is the public-function trust boundary. Its `tenantQuery`, `tenantMutation`, and `tenantAction` wrappers derive `tenantId` from authenticated identity and inject it into the handler context; feature modules must not accept a caller-supplied tenant for authorization.
- Internal orchestration uses generated `internal.*` references and raw internal Convex builders where necessary. Public client-callable functions use the tenant wrappers so tenant isolation is structural rather than a convention at each call site.
- External I/O belongs in Convex actions, frequently Node-runtime action modules, while queries and mutations own transactional reads/writes. `packages/backend/convex/index.ts` exposes the configured Workflow Manager and Action Retrier used across those seams.

## Backend components and state

- `packages/backend/convex/convex.config.ts` registers pinned Convex components for Workflow, Agent, RAG, Rate Limiter, Action Retrier, Migrations, Aggregate, and Action Cache. Component versions are intentionally exact because their pre-1.0 APIs are treated as volatile.
- `packages/backend/convex/schema.ts` is the application schema source of truth. Its tables cover governance (`audit`, `deadLetters`, `skills`, `telemetry`, `notifications`, `feedback`, `optimizerConfig`), workflow state (`requests`, `plans`, `pendingTimeouts`), product state (`briefings`, `evaluations`, `agentSteps`, `tenantProfiles`), integrations (`gmailTokens`), intake/storage metadata (`attachments`, `intakeArtifacts`, `vaultDocuments`, `vaultSources`), graph data (`graphNodes`, `graphEdges`), and realtime voice (`voiceSessions`).
- Convex file storage holds uploaded and generated bytes. Application tables store `StorageId` references and metadata; signed download URLs are produced only by tenant-guarded queries such as those in `packages/backend/convex/plans.ts` and `packages/backend/convex/vault.ts`.
- Vector retrieval is owned by the RAG component configured in `packages/backend/convex/vaultRag.ts`; graph expansion is stored in `graphNodes`/`graphEdges` and implemented in `packages/backend/convex/vaultGraph.ts`.
- Prompts are runtime data, not source literals. `packages/backend/convex/skills.ts` loads the single active row by skill name, fails closed when missing, activates versions atomically, and seeds initial versions from the contract package.
- The audit plane is insert-only through `packages/backend/convex/audit.ts`. Audit, dead-letter, notification, and structured telemetry payloads are restricted to references, hashes, identifiers, and counts; user content belongs in content-plane tables, not logs.
- `packages/backend/convex/guardrails.ts` centralizes kill-switch, daily-budget, PII-safe instruction, rate-limit, and spend-recording rails. Model entry points call the guard before generation and record priced usage afterward.

## Entry points

- Browser navigation enters through Next.js pages in `apps/web/app`; the principal product routes are `/dashboard`, `/dashboard/workspace`, `/dashboard/vault`, `/dashboard/voice`, `/dashboard/onboarding`, `/dashboard/profile`, `/connect-gmail`, and `/ops`.
- Most browser-to-backend calls are generated Convex queries, mutations, or actions referenced as `api.<module>.<function>`. Reactive queries keep plan cards, activity steps, vault status, notices, Gmail status, and operational counters synchronized without a separate websocket layer.
- Auth and service HTTP endpoints enter through `packages/backend/convex/http.ts`. It mounts Convex Auth routes and defines `/gmail/callback`, `/skillopt/export`, and `/skillopt/writeback`.
- The Gmail callback validates signed OAuth state, exchanges the authorization code server-side, stores tokens through `internal.gmailAuth.store`, and redirects back to the Next.js site; the refresh token never traverses browser application state.
- Scheduled work enters through `packages/backend/convex/crons.ts`: daily WORM audit export, daily Gmail token-expiry scanning, and the weekly proactive business review.
- Operational and evaluation entry points live under `packages/backend/scripts`; they invoke deployed Convex functions for seeding, golden evaluations, and live smoke tests that cannot be represented by `convex-test`.

## Cockpit and agent request flow

1. The workspace UI in `apps/web/app/(app)/dashboard/workspace` calls `cockpit.sendCockpitMessage` from `packages/backend/convex/cockpit.ts`.
2. A first turn creates a thread and one shared `plans` row; each turn stores user/assistant messages and creates a server-side `turnId` used by `agentSteps`.
3. `internal.llm.runCockpitAgent` in `packages/backend/convex/llm.ts` runs `guardrails.preCall`, loads the active `cockpit-agent` skill, constructs address-safe context from current plan state, and enters a bounded `generateText` tool loop.
4. `buildCockpitTools` exposes validated capabilities that patch the same `plans` row: contact resolution, recipient/subject/body/mode edits, vault search, evaluation, research dispatch, attachment generation, and proposal. Tool start/end callbacks persist refs-only activity records through `agentSteps`.
5. Specialist dispatch is governed in `packages/backend/convex/dispatch.ts`. Specialist prompt bodies come from the skill registry, but the allowed tool set is code-owned in `packages/core/src/specialists.ts`; withheld tools are absent from the tool record rather than merely discouraged in a prompt.
6. Dispatch lineage, depth, ancestry, envelope, and spend travel as validator-checked internal-action arguments, not mutable run rows. Completed specialist/research work lands back into the shared plan through `evaluations.landSpecialistResult`.
7. The model can only move a plan to `proposed`. The irreversible transition is `cockpit.executePlan`, a human-triggered tenant mutation with an idempotent compare-and-set guard.
8. For email plans, approval creates per-recipient `requests` rows and starts `deliverApprovedPlan` immediately or via a stored scheduler job. The workflow calls `gmail.send` with retry behavior, marks delivery state, emits audit/telemetry, and dead-letters failures per recipient without stopping the fan-out.
9. Memo/non-email plans use the same proposal and approval surface but complete through the action-type-specific executor branch, preserving one governed approval abstraction.

## Intake, vault, and grounding flow

1. Browser upload controls request a Convex storage URL, upload bytes directly, then call an intake or vault mutation with the resulting storage reference and metadata.
2. `packages/extraction/src` classifies cockpit attachments; `packages/backend/convex/intake.ts` selects OCR/extraction, transcription, or rejection and records progress in `intakeArtifacts`.
3. Vault uploads enter through `packages/backend/convex/vault.ts`, which creates a `vaultDocuments` row and delegates durable processing to `packages/backend/convex/vaultIngest.ts`.
4. `vaultIngest.ingestDoc` orchestrates extraction/transcription, PII-safe embedding preparation, RAG indexing, graph extraction/upsert, and the final `ready` or `failed` document state. Watchdog/retry support is in `vaultSweep.ts`.
5. Format recognition and local parsing rules are pure functions in `packages/vault/src`; Node-only heavyweight Office/SheetJS paths are imported by subpath only so they do not contaminate Convex V8 bundles.
6. Grounding combines vector results from `vaultRag.ts` with graph neighbors from `vaultGraph.ts`; fusion/ranking rules live in `packages/vault/src/fusion.ts` and traversal limits in `packages/vault/src/traversal.ts`.
7. Agent tools consume hydrated, tenant-owned vault passages through `vaultGround.ts` or related internal actions, keeping retrieval behind the same tenant and governance boundaries as other capabilities.

## Voice flow

1. `packages/backend/convex/voiceToken.ts` loads the registry persona and mints a short-lived OpenAI Realtime client secret; the server API key is never returned to the browser.
2. `apps/web/app/(app)/dashboard/voice/useVoiceSession.ts` connects the browser directly to OpenAI over WebRTC, using an `RTCPeerConnection` and data channel, so audio does not pass through Next.js or Convex.
3. The browser relays the OpenAI `call_id` to `voice.startSession`; `packages/backend/convex/voice.ts` persists session state and arms one server-authoritative wall-clock watchdog for the fixed cap.
4. Client-reported usage is priced and recorded as telemetry, while the watchdog and `voiceToken.hangupCall` are the actual bounded-cost actuator.
5. Raw audio is discarded. Client/server end paths converge on one transcript-derived brief, store it through the vault ingestion workflow, and optionally seed the existing cockpit flow; voice does not have a separate approval or delivery pipeline.
6. Document-grounded voice sessions additionally use `packages/backend/convex/voiceDoc.ts` for document search/review and the pure shaping contracts in `packages/voice/src/docSession.ts`.

## Background, failure, and optimization flows

- Convex Scheduler handles delayed sends, review timeouts, voice watchdogs, vault watchdogs, asynchronous specialist/research work, and notification dispatch; durable multi-step sequences use the Workflow component.
- `packages/backend/convex/deadLetter.ts` is the pipeline completion/failure bridge, while `deadLetters.ts` exposes the tenant operator surface. Failures also pass through the centralized notification choke point in `notifications.ts` and optional external notification action in `notifyExternal.ts`.
- `packages/backend/convex/worm.ts` exports append-only audit windows to S3 Object Lock. `wormCursor.ts` advances the cursor only after a successful durable write, making retries idempotent and preventing unexported gaps.
- `.github/workflows/skillopt.yml` is a separate GitHub Actions runtime for the dormant prompt optimizer. It checks the Convex kill switch and eligibility, exports scrubbed feedback trajectories, trains Python code under `skillopt`, writes a candidate through authenticated HTTP, and records held-out eval evidence; a human still activates the candidate.

## Runtime and deployment topology

- In production, the Next.js web application is intended for Vercel and receives only `NEXT_PUBLIC_CONVEX_URL` plus deployment credentials; server-side product secrets do not belong in Vercel.
- Convex hosts the database, storage, realtime subscriptions, auth routes, server functions, scheduled functions, component state, and HTTP actions. Secrets used by actions—OpenAI, Google OAuth, AWS, and future sidecar URLs—are Convex environment variables.
- The browser talks to Next.js for pages/auth integration, to Convex for application data/functions/storage URLs, directly to Convex-site HTTP routes for OAuth callbacks when redirected, and directly to OpenAI only for ephemeral-credential Realtime WebRTC.
- Gmail, OpenAI model APIs, and S3 are called from Convex actions. Calls that need retry semantics use the Action Retrier or workflow workpool policies.
- `sidecars/README.md` describes future HTTPS Python containers hosted on Fly.io with Railway as fallback; current repository sidecar service directories have not landed, so these are an extension seam rather than a present runtime dependency.
- Local development runs Next.js and `convex dev` through Turborepo. Convex codegen must run first because `packages/backend/convex/_generated` is ignored and absent in a clean clone; `scripts/boot-check.mjs` codifies install, codegen, and typecheck after deployment configuration.
