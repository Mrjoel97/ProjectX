## Product contract

The owner asks for a business website, landing page, or shop. The agent reads the approved business
Foundation, Blueprint, and selected owned document evidence, asks only for unresolved business
information, writes the brief and copy, and creates the supported private project. The owner does
not assemble prompts, wire agents, write code, or operate a document/JSON editor to get that draft.
Actual publication remains an explicit review of an immutable version; the leaf workflow cannot
approve or publish it. A reference to a private document is not permission to disclose its contents.

This is a one-time attended operation using the existing agent execution model. It does not build
the planned generalized managed-service boundary or recurrence engine, and it does not declare
their readiness gates complete. Existing workflow packs remain leaves with their existing grants.
The dedicated online-presence body runs through the existing specialist-turn mechanism and a
frozen narrow tool allowlist. It does not require a new diagnostic specialist route or a new agent
delegation capability. The Executive may initiate the same trusted operation with real thread/plan
lineage; a model-supplied tenant, source approval, or publication flag confers no authority.

## Executable brief contract

`packages/core/src/onlinePresence.ts` owns the framework-free assessment and progress derivation.
`assessOnlinePresenceBrief(raw, trustedSources)` accepts only a bounded closed field set:

| Field | Meaning |
| --- | --- |
| `kind` | `landing`, `website`, or `shop`; shop remains explicitly unavailable |
| `businessName`, `headline`, `summary`, `audience` | Required business identity, prepared copy, and intended visitor |
| `offer`, `services`, `about`, `proof` | Optional supported content; do not fabricate factual claims |
| `ctaLabel`, `ctaHref` | Paired label and actual supported destination; HTTPS for external inquiry/booking |
| `contactConsent` | Explicit owner-supplied disclosure copy; absence means no inquiry form |
| `sourceRefs` | Exact selected references issued by the adapter; at most 32 |

The adapter supplies the source snapshots with stable reference, revision, kind, content, approval,
current/planned intent, publication visibility, and optional stale state. The model cannot upload
those snapshots or mark a source approved through brief arguments. Explicit owner answers can be
represented as `user` sources by the server. A missing Foundation does not forbid useful work when
the owner supplies the missing business facts directly. A source list is provenance rather than a
claim-support proof; the draft is never automatically certified as true by reference existence.

Refusals use a closed reason set: `missing`, `invalid`, `unknown_source`, `unapproved_source`,
`conflicting_source`, `unsupported_sales_path`, and `commerce_unavailable`. Return only the needed
questions; do not ask for already provided fields. Approved private, unspecified-publication,
planned, and stale sources may inform a private draft with preserved warnings. The owner must see
the actual generated public copy and warnings at exact-version review. No boolean supplied by the
agent creates legal consent or publication authorization.

Landing briefs map to the recovered `campaign-landing` recipe and business websites to
`business-site`. Validation reuses `validateWebRecipeInput`, including safe content and destination
rules. Actual materialization uses the recovered core/compiler and adapter's project/version
helper. `onlinePresenceServiceState` distinguishes missing information, ready to build, review,
approved, and published. Only real receipts for the same exact version establish approved or
published state. Neither brief completeness nor successful rendering establishes publication.

## Runtime integration recipe

1. The dedicated workflow or Executive calls `readOnlinePresenceContext`. The tenant-scoped
   adapter returns selected approved Foundation/Blueprint context, server-issued source references,
   any saved brief, and existing project/version receipt for this thread/plan.
2. The model prepares copy from that context and calls `saveOnlinePresenceBrief`. The adapter
   resolves source references against tenant-owned records and user statements, calls the pure
   assessment, and persists the structured brief plus selected revision identities. It returns
   missing information or the exact supported recipe input. Audit payloads contain references,
   hashes, and counts only, never source text or website copy.
3. `buildOnlinePresenceProject` reloads that trusted saved brief and current selected sources,
   assesses again to avoid building from changed revisions, and invokes the recovered private
   project materializer. Retries reuse the real plan/thread-owned project result. A failed or
   unknown creation must be reconciled before retrying, rather than producing duplicates.
4. The result card links the actual project and immutable preview. The agent explains the built
   outcome and source warnings. Human-only controls operate existing exact-version approval,
   publication, unpublish, and rollback paths. No publication tool belongs to this workflow grant.
5. Only the real public route and its exact stored version receipt can support a live claim.
   Hosted acceptance and functioning inquiry delivery require separate current observations.

The registry body is canonical at
`packages/contracts/skills/online-presence-specialist.md` with a byte-identical bundled constant
`onlinePresenceSpecialistSkillBody`. It names the actual tools and preserves source, missing-data,
commerce, and review boundaries. Registry seeding creates a candidate; local code is not evidence
that any deployed row has been activated or qualified.

The implementation now includes `convex/onlinePresence.ts` and `onlinePresenceRun.ts`. Sessions
belong to a real tenant-owned plan/thread. Only authenticated cockpit messages enter the human
source list. The initial start/send handoff is idempotent; later identical actual answers remain
separate turns. A routing lookup distinguishes an absent service session before a model is invoked.
Service conversations must be refused on registered authoring-probe threads rather than mixing
reserved evaluation accounting with ordinary model spend.

Context sources retain their server-issued identities while their text is bounded to 24,000
characters total and 6,000 per excerpt. Truncation remains explicit, and the model can prioritize
specific references without asking the owner to copy the document. Source validation and revision
checks use full server-side records. Mutable sessions keep selected reference/revision identities;
each immutable project version separately freezes `ref#revisionHash` provenance and its exact
private/planned/stale/disclosure/claim-review warnings. Review of an older artifact never borrows
warnings from a later saved brief.

site using its actual allocated slug, and appends a new version on a changed brief. Repeating the
same saved brief reuses the actual artifact. Missing exact version rows, changed source revisions,
invented consent or destinations, mismatched receipt hashes, and unavailable commerce fail closed.
The public `sessionForProject` query returns the selected immutable version's evidence and its
owned service-chat link for exact-version review. The leaf tool set includes no approval or
publication operation.

Backend checks include a scripted `runSpecialistTurn` through the actual model-mock seam and real
context/save/build tools, with real versioned pages and no provider call. Test-only active recipe
and registry rows are isolated fixtures, not hosted qualification evidence. Additional native
checks cover tenant/plan/thread ownership, erasure fences, revision CAS, missing qualification,
bounded excerpts, first-turn idempotence, source authority, exact warning/provenance preservation,
and public authoring-probe refusal. The root recovery receipt owns final integrated check counts
