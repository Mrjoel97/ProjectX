## 1. CRITICAL — Cash-balance movements correlate on the CUSTOMER, so only the first bank transfer that customer ever makes is booked
**`packages/billing/src/reconcile.ts:217`** (also `:232`, and the `?? txn.customer` fallbacks at `:252` and `:263`)
**Lenses: money, pii, idem, authz — 4 of 6 independently found it. Strongest signal in the set.**

`movement("reserved", "cash-funded", txn.net_amount, txn.currency, txn.customer, txn.id)` builds `correlationId = "billing/" + txn.customer`. Every cash-balance transaction that customer will ever have collapses to one correlation. `recordBillingMovement` (`packages/backend/convex/billingLedger.ts:142`) makes `(tenantId, correlationId, phase)` the identity and on a hit does `if (already) return already._id;` — no insert, no error, no counter, and it explicitly ignores the replayed amount. The transaction's own unique id is right there and is already passed one argument later as `stripeObjectId`; it is simply not what the correlation is built from.

**Failure:** `cus_1` wires $49 in January → `{reserved, billing/cus_1, 4900}`. February, a distinct `ccsbtxn_` for $120 → new event id, new object id, so both `billingStripeEvents` dedupe keys pass, the movement is again `{reserved, billing/cus_1}`, `already` matches January, the row is returned, nothing is written, and `applyMoney` reports `"applied"`. Reserved funds read 4900 forever. `funding_reversed` collides identically on phase `refunded`, so the first reversal permanently blocks every later reversal. If February's transfer is EUR, the currency-clash guard at `billingLedger.ts:137` throws instead → `receiveAndApply` rolls back with no dedupe row → the httpAction 500s → Stripe retries for days.

The justification in `billingLedger.ts:86-89` ("a `reserved` arrival and its `actual` collection SHARE one correlation on purpose") does not describe this code: `funded` yields `billing/cus_`, `applied_to_payment` yields `billing/pi_` (`reconcile.ts:228`). They never share a correlation.

**Smallest fix:** pass `txn.id` as the correlation source in the `funded` and `funding_reversed` arms, and change both `?? txn.customer` fallbacks to `?? txn.id`. Four token changes. Nothing regresses — `reserved` was never tied to an invoice anyway (there is no PaymentIntent yet, as the comment at `:215` says). Add one test that sends two `funded` events for one customer and asserts two rows; `billingWebhook.test.ts:958`/`:984` each send exactly one, which is why nothing caught this.

## 2. CRITICAL — The `(objectId, eventType)` dedupe suppresses the EFFECT, so every subscription transition after the first is dropped
**`packages/backend/convex/billingWebhook.ts:189-198`**
**Lenses: idem, authz.**

The second dedupe key is `(data.object.id, event.type)` and a hit sets `status = "ignored"` without calling `applyEffect`. But that pair is not a transition key for the event families that legitimately repeat on one object: a subscription emits `customer.subscription.updated` on *every* transition of one `sub_`, and `charge.refunded` fires per refund on one `ch_`. Only the first is ever applied.

**Failure:** `sub_1` goes trialing → active (applied, `billingCustomers.status = "active"`). Three months later dunning exhausts and Stripe sends `customer.subscription.updated` with `status: "unpaid"` → `duplicate_object` → `applyMapping` never runs. `subscriptionState("active")` keeps answering `subscribed` and `billing.billingStatus` reports a paying subscriber to a customer who is not paying. `unpaid` never emits `customer.subscription.deleted`, so nothing can ever correct it.

This also **absorbs the `statusAt` freshness guard** at `:435-439`: a repeated `updated` never reaches it, so that guard's only live coverage is the `deleted`-then-`updated` case (two different event types) the tests exercise. `billingWebhook.test.ts` never sends two `customer.subscription.updated` for one subscription — the suite is green over the broken capability.

**Smallest fix:** apply the by-object suppression only to a closed set of one-shot event types (`checkout.session.completed`, `invoice.finalized`, `invoice.paid`, `customer.subscription.created`, `customer.subscription.deleted`). For the repeatable types, still record the delivery row but let `applyEffect` run — they are already protected by the `by_event` key, by the `statusAt` freshness guard, and (once #1 and #7 land) by the ledger's correlation identity. One constant plus one condition at `:190`.

## 3. HIGH — A failed rollup discards the Stripe invoice it already created, and the daily cron guarantees the retry lands past Stripe's key-pruning horizon → the customer is billed twice
**`packages/backend/convex/billingRollup.ts:372` / `:461` / `:140`**
**Lenses: money, idem.** *The only finding here where money leaves a customer's account twice.*

Step 1 creates the invoice with `auto_advance: "true"` (`:341`), so Stripe finalizes and collects on its own. If any later step fails — an invoice-item POST (`:372`), the finalize (`:381`), `no_hosted_url`, `unreadable_invoice_total` — `settlePeriod`'s failure branch (`:461`) patches only `{status: "failed", failureCode}`. `settleOutcome`'s failure variant (`:418-427`) has **no field for `stripeInvoiceId`**, so the invoice that exists at Stripe is discarded. `claimable()` (`:127-132`) treats `failed` as re-claimable, `periodForPost` (`:207`) gates only on `status === "claimed"`, and `postInvoice` re-POSTs `/v1/invoices` from scratch. `CLAIM_STALE_MS` is one hour but `crons.ts:76` is `crons.daily(hourUTC: 7)` — there is no tick between 1h and 24h, so **every** retry lands at or past the ~24h idempotency-key pruning. The module header states this consequence verbatim and asserts the claim row is the guard; the claim row guards only `posted`.

**Failure:** in_A created with 3 of 5 line items, item 4 times out → row `failed`, no trace of in_A. Stripe auto-finalizes in_A an hour later and charges a partial bill. Next day 07:00 the tick re-claims, the key is pruned, in_B is minted with all 5 lines and collects. Two invoices, one period; the row records only in_B.

The test at `billingRollup.test.ts:528` stubs a *fresh* Stripe with no key memory, watches the module re-POST and asserts only that key and body are byte-identical — a mechanism assertion that passes with a second invoice minted.

**Smallest fix:** add `stripeInvoiceId: v.optional(v.string())` to `settleOutcome`'s failure variant, thread the created id into `fail()`, and make `claimable()` refuse to re-claim a `failed` row that carries one. Fail-closed: a period whose invoice already exists at Stripe becomes an operator problem instead of a second charge. ~4 lines.

## 4. HIGH — `invoice.paid` can never identify a card payment on this deployment, so `actual` is unreachable for card collection
**`packages/billing/src/reconcile.ts:166-176`**
**Lenses: money, pii.**

`invoicePaymentMethods` probes three fields and all three are dead on a real delivery:
- (a) `obj(obj(inv.charge).payment_method_details).type` — `obj()` returns `{}` for the bare `"ch_…"` string a webhook carries, and `events.ts` states this deployment never requests expansions.
- (b) `obj(inv.payment_intent).payment_method_types` — same, and the pinned `STRIPE_API_VERSION = "2026-08-26.dahlia"` is post-Basil, where both fields are gone from Invoice entirely.
- (c) `inv.payment_settings.payment_method_types` — and **nothing in this repo ever sets it**: `postInvoice` (`billingRollup.ts:337-345`) POSTs customer / currency / collection_method / auto_advance / pending_invoice_items_behavior / metadata and no `payment_settings`; `billing.ts` `checkoutParams` sets no `subscription_data[payment_settings]`.

So `methods.length === 0` on every delivery → `payment-method-undetermined` → `applyMoney` refuses with `billing_undetermined_payment_method` and writes a dead letter. The fail-closed posture is correct; the consequence is that collected revenue reads as $0 `actual` across the deployment while the dead-letter queue fills with one entry per successful payment. The tests are green only because `reconcile.test.ts:33` hand-writes `payment_settings` and `:125-137` hand-writes an expanded `charge` — shapes the live endpoint never receives.

**Smallest fix:** add `"payment_settings[payment_method_types][0]": "card"` to `postInvoice`'s POST body (`billingRollup.ts:337`). That makes probe (c) live for the only invoices this deployment creates, without touching the fail-closed logic. Add a `reconcile.test.ts` case whose invoice carries *only* `payment_settings` and no `charge`/`payment_intent`.

## 5. HIGH — Checkout never passes `customer`, so a re-subscribing tenant is permanently unmappable and their money is never booked
**`packages/backend/convex/billing.ts:96-112`, `startCheckout` at `:193-205`**
**Lens: idem.**

`checkoutParams` sends mode, line items, trial, `payment_method_collection`, `client_reference_id` and metadata — no `customer`, no `customer_email` — and `startCheckout` never calls `stripeCustomerFor`, which exists and would supply it. Stripe Checkout in subscription mode therefore mints a **new** Customer for every completed session. `applyMapping` (`billingWebhook.ts:423-428`) refuses that with `billing_tenant_customer_conflict` ("the FIRST mapping stands"), and `applyMoney` resolves tenants only through `billingCustomers.by_customer` (`:500-504`), so every payment on the new customer refuses with `billing_unattributable_customer`. `billingCustomers` survives a cancellation by design (asserted at `billingWebhook.test.ts:548-552`), so the conflict is permanent.

**Failure:** T subscribes (cus_1 mapped), cancels via the portal, re-subscribes three months later on cus_2. Every `customer.subscription.*` and `checkout.session.completed` for cus_2 is refused; `billingStatus` still reads the canceled cus_1 row and returns `not_subscribed` for a paying customer; every `invoice.paid` on cus_2 is refused as unattributable and **never reaches `billingEvents` at all**.

The test at `billingWebhook.test.ts:580` asserts the second-customer refusal as *correct* without noticing that this deployment's own checkout guarantees it on re-subscribe.

**Smallest fix:** in `startCheckout`, look up `stripeCustomerFor(tenantId)` and pass `customer: <id>` in `checkoutParams` when a mapping exists. ~3 lines.

## 6. HIGH — `charge.refunded` books Stripe's CUMULATIVE `amount_refunded`, and no path can ever record a second partial refund
**`packages/billing/src/reconcile.ts:343-352`**
**Lens: money.**

`object.amount_refunded` is the running total on the charge, not this refund's delta. Two mechanisms then compound: the by-object dedupe (#2) keys on the charge id, so the second `charge.refunded` is `duplicate_object` and `applyEffect` never runs; and even if it got through, the movement is `{refunded, billing/<payment_intent>}` both times, so the ledger's phase-identity guard returns the first row and discards the larger cumulative amount.

**Failure:** ch_1 refunded $5 (`amount_refunded=500`) → refunded row 500. A week later a further $12 (`amount_refunded=1700`, same charge id, same type) → ignored. Ledger says 500 refunded; 1700 left. Net revenue overstated by 1200 minor units, permanently, in an append-only table.

**Smallest fix:** map `refund.created` instead of `charge.refunded` — `object.amount` is the delta and `object.id` (`re_…`) is unique per refund, so the correlation is per-movement and both mechanisms stop biting. Requires adding `refund.created` to the handled set in `packages/billing/src/events.ts:29` and removing `charge.refunded`. If you keep `charge.refunded` for other reasons, it must not book money.

## 7. HIGH — `credit_note.created` correlates on the INVOICE, so the second credit note against one invoice is swallowed
**`packages/billing/src/reconcile.ts:354-364`**
**Lens: money.**

`object.invoice ?? object.id` gives `billing/in_…` at phase `refunded` for every credit note against that invoice. Stripe permits multiple credit notes per invoice. The second has a distinct `cn_` id so the by-object dedupe correctly lets it through, and it then lands on the identical `(tenant, billing/in_X, refunded)` identity and is returned without insert or error at `billingLedger.ts:142`.

**Failure:** in_1 credited $30 (cn_1) → 3000 booked. A month later a further $40 (cn_2) → never recorded. The ledger reports $30 credited against a customer credited $70.

**Smallest fix:** use `object.id` as the correlation source (the credit note is the movement); keep `object.invoice` in `stripeObjectId` or as the tie-back. One-token change at `:361`. Same root cause as #1.

## 8. HIGH — A `billingUnapplied` row is never cleared or zeroed, so the held-funds surface reports money we no longer hold and ages it toward "swept"
**`packages/backend/convex/billingWebhook.ts:556-583`**
**Lens: money.**

`observeUnapplied` only inserts or patches `amountMinor`; there is no delete and no zeroing path (grep confirms `:576`/`:579` are the only writers outside the erasure walk). `fundsAvailable` in `reconcile.ts:297` does `if (money.value.minor === 0) continue`, so a delivery reporting the leftover is gone yields zero observations, and `applyMoney` returns `"ignored"` at `:496` before `observeUnapplied` is reached. `applied_to_payment` — precisely the signal that the leftover was consumed — books a `billingEvents` row and touches nothing here. `billing.unappliedFunds` (`:312-323`) then recomputes `ageDays` from a frozen `observedAt` and derives the stage from it.

**Failure:** customer wires $60 against a $49 invoice → row `{1100 USD, observedAt=T}`. Two weeks later the next invoice consumes the $11. The billing page still shows $11.00 held; at T+75 it renders `return-attempted` and at T+90 `swept`, for money collected 76 days earlier. No event and no code path can correct it.

**Smallest fix:** stop skipping zero in `fundsAvailable` (emit a zero `unapplied-funds` observation), and in `observeUnapplied` delete the row when `observation.amount.minor === 0`. Two small edits in one flow. If `cash_balance.funds_available` turns out not to fire at zero, the fallback is to clear the row on `applied_to_payment` for that customer/currency — see the completeness note.

## 12. MEDIUM-HIGH (guard) — `codeOf` truncates every line at `https://`, so the two scans hunting a hardcoded Stripe URL are blind to exactly that offender
**`packages/backend/convex/billing.test.ts:167`** (copied into `billingRollup.test.ts:39`)
**Lenses: vacuous, authz, schema — 3 of 6.**

`content.replace(/\/\*[\s\S]*?\*\/|\/\/.*/g, "")` has no string-literal awareness, so the `//` in any `https://` opens the line-comment alternative and the tail is deleted. **Verified by execution:** `codeOf('const u = "https://api.stripe.com/v1/customers";')` returns `const u = "https:`. Under `codeOf`, `billingApi.ts` contains `api.stripe.com` **zero** times (raw: 1); `config.ts:16` reduces to `export const STRIPE_API_BASE = "https:`.

So `test("billingApi.ts is the ONLY module that names Stripe's origin")` (`:447`) passes only because the *identifier* `STRIPE_API_BASE` is the other half of the alternation, and `test("no billing module ever POSTs to /v1/customers")` (`:386`) cannot see the URL form of the path it forbids. `backendSources` globs `./billing*.ts`, so a new `convex/billingSync.ts` doing `await fetch("https://api.stripe.com/v1/customers", {method:"POST", ...})` **is scanned and still passes both** — bypassing `stripePost`'s version pin, idempotency requirement and error mapping, and minting Stripe customers outside the mapping law. The anti-vacuity block at `:420-427` checks that `export` survives and that a `/*` inside a `//` is inert, but never that a URL survives.

**Smallest fix:** put a string-literal alternative first so a string is consumed before a comment can open:
```js
const codeOf = (c) => c.replace(/("(?:[^"\\\n]|\\.)*"|'(?:[^'\\\n]|\\.)*'|`(?:[^`\\]|\\.)*`)|\/\*[\s\S]*?\*\/|\/\/.*/g, (_, s) => s ?? "");
```
Plus one tripwire: `expect(codeOf('const u = "https://a/b"; //x')).toContain("https://a/b")`.
