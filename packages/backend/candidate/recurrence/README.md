# Disabled recurrence candidate

This six-file directory is a synthetic, test-only build-for-evidence candidate under ADR-050. It is outside `convex.json`'s `packages/backend/convex` functions root, the app bundle, the backend's default TypeScript include and its default Vitest discovery. Run only the explicit candidate Vitest configuration and candidate TypeScript project. There is no registered callable, cron, self-arm, tenant activation, feature-flag route, production deployment, real provider/paid call, external write or send.

The schema is separate from production. Tests use synthetic tenant identifiers and `convex-test` transactions; injected reservation and model stubs are not the real rate-limiter component. The rail fixture accounts for tenant-scoped daily holds and one shared deployment hold separately: a reservation exactly at either ceiling is admitted, while another tenant cannot cross an exhausted deployment ceiling. This corrected a prior shared-counter false refusal in two red-before-green controls. A green suite provides automated design evidence only. It does not prove production atomicity, real limiter integration, live DST/OAuth/provider traces, or ADR-046 D6 cancellation of a pending scheduled function. The historical operational decision remains `defer`; this directory must never be treated as `enable-safe` or a release path.

The test-only routine stores an approval anchor and the last local occurrence key, not a next-due instant, next-local date/time, arm timestamp or callback ID. A claim derives the latest eligible occurrence in a bounded fifteen-day cadence horizon with the core IANA-zone helper, re-reads tenant/status/version and active run in the claim transaction, then records one claimed, missed or overlapping outcome. The single grace window is five minutes. Approval and material reapproval anchor at their actual acceptance time, so they never run pre-approval dates. Delayed sweeps skip at most the latest missed occurrence rather than draining old dates; the repeated fall-back hour shares one local key, ordinary spring gaps shift within the local day, and skipped local dates are omitted by the core helper.

Creation, material edits and approval now validate the actual schedule rule against a safe, nonnegative instant before persisting it. Invalid wall times, zones or timestamps refuse at the write boundary; an invalid approved row must not repeatedly throw before the due sweep can advance its cursor. This is local candidate liveness evidence, not a deployed scheduler or live DST result.

The two manually invoked synthetic sweep lanes use finite pages of at most 16 and tenant-scoped monotonic ordinals assigned transactionally with routine/run creation. Each durable lane records cursor, pass high-water mark and epoch. A pass does not grow indefinitely under insertion, and a deleted or ineligible row does not pin later rows; wrap revisits previously blocked rows. Due claim and cursor advance commit together. Recovery performs keyed rail effects outside a DB transaction, then advances its cursor only after classification/settlement; replay after a crash is safe under the synthetic idempotent rail contract. A stale page cannot rewind a newer epoch. These are repeated-invocation design controls, not a deployed caller or liveness proof.

Approval versions, routine/run scan ordinals and sweep epochs use one checked safe-integer increment. At exhaustion they refuse the transaction before a new pause fence, row, claim or pass is persisted; a rounded JavaScript number must never masquerade as a newer version or cursor. Synthetic boundary controls cover both version-changing operations, both ordinal counters and both sweep lanes. This does not prove a deployed cursor or production scale.

The test-only run records one reservation admission before either keyed rail effect. Daily and deployment rails have separate stable keys and reserve/lookup/release outcomes. A thrown reserve followed by an `absent` lookup is still ambiguous: the original allocation may land later. A terminal release requires a `released` tombstone on each attempted key; `absent` after a thrown release is not proof and keeps the run and envelope held for reconciliation. A partial hold is compensated, and unresolved allocation or release has no paid admission. Confirmed whole-run holds survive `retry_pending` only when the synthetic callback explicitly confirms its failure had no physical effect; a timeout, 5xx or generic throw after the paid-start claim is otherwise unknown and quarantined, not automatically retried. Holds are released on known terminal outcomes. This is a stub contract, not evidence that the real rate limiter allocates or refunds atomically or that a real provider can furnish the no-effect proof.

A terminal transition with a possible hold first stores `pendingTerminal` and keeps `activeRunId`. Its audit/dead-letter and final status land only after both keyed releases are confirmed. A keyed release also tombstones an absent key in the synthetic stub so an in-flight reserve cannot allocate later. The bounded `syntheticReconciliationSweep` scans all run ordinals, settles pending terminals, conservatively stops interrupted running work that has not claimed a paid start, and inspects held `retry_pending` rows without automatically retrying a paid call. An approved retry remains held for the explicit worker path; a revoked retry is stopped and released. An unknown `start_claimed` physical outcome is quarantined with its paid-step identity, active run and both holds intact; the sweep neither guesses, redispatches nor refunds it. Only an exact later step landing can settle it in this synthetic model. A running attempt may separately resume after process loss at attempt start, reservation admission, or a rail effect through `syntheticAttempt`: it looks up each stable key before trying reserve and still needs the one-winner paid start claim. No sweep is registered or scheduled in this disabled candidate; production reconciliation liveness, provider-result authentication and real limiter semantics remain open.

Each paid step has a bounded ID, a committed admission and a separate single-use start claim. Only the claim winner may invoke the synthetic `prepare` callback. One run has at most one outstanding step; a claimed start with unknown outcome is never dispatched again and cannot be closed by merely declaring the worker lost or classifying an ambiguous thrown error as retryable. Landing matches the ID/token and rechecks the routine fence before storing a proposed plan. Pause or material change commits status and a monotonic version in one Convex transaction. A reservation admission or paid admission that commits first can settle later, but pause-first refuses admission; an earlier paid admission may start after pause and then lands without an actionable plan or successor.
If a worker restarts after paid admission but before start claim, it resumes that same persisted step ID/token through the one-winner claim even when pause committed meanwhile. It does not perform a new reservation or paid admission; the late result lands as stopped and releases the held rails without an actionable plan.

`actionablePlan` and the synthetic external-action admission check require the current fence. External-action admission also requires a separate per-run human approval ref. No external action is implemented. The candidate keeps prompt fields directly, uses `candidateDeadLetters` rather than the shared production table, and has no deployed sweep, real spend rails, approval integration, live traces, or literal ADR-050 pause/cancel reconciliation. Its single tenant progress row is a synthetic design point that can contend under high write volume; no production scaling claim is made. ADR-051 D6 and ROUT-02 remain open.
